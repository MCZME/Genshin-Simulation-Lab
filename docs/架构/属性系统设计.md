# 属性系统架构

> 状态：已确认。
> 本文档描述属性系统的职责、边界、组件关系和长期设计原则。具体属性 key、模型字段、枚举、公式、错误和序列化规则见[属性系统契约](../契约/属性系统契约.md)。

最后更新：2026-07-13

## 1. 系统定位

属性系统是 `core/` 内的确定性查询与解析能力，用于回答：

```text
在指定帧、主体和查询上下文下，某个属性的有效值是多少，来源是什么？
```

属性系统不是可写角色面板，也不是保存全部战斗状态的通用容器。

核心原则：

- 原始属性在组装阶段生成并冻结。
- 派生属性在查询时解析，不写回角色或目标运行态。
- modifier 只贡献结构化修饰项，不直接修改属性值。
- 动态 modifier 的生命周期由机制运行时管理。
- 属性查询和 modifier provider 必须无副作用。
- 缓存只能优化查询，不能成为属性真值来源。
- 完整解析结果必须可审计、可快照、可测试。

## 2. 设计目标

- 为动作、机制和后续结算系统提供统一只读属性入口。
- 区分资产基础值、配置静态贡献、运行时机制修饰和派生属性。
- 支持条件 modifier、属性依赖和跨主体读取。
- 保证相同输入和运行态得到相同结果。
- 支持快照、审计和 golden case。
- 允许 content 扩展私有属性与 provider，但不允许覆盖公共属性。
- 保持 `core/attributes` 不依赖资产库、配置、content 或基础设施。

## 3. 非目标

属性系统不负责：

- 当前生命、当前能量等资源状态。
- Buff、Debuff、冷却、层数、持续时间和元素附着。
- 输入解释、动作时间轴和 impact 调度。
- 伤害、治疗和反应的最终结算。
- UI 面板缓存和显示格式。
- 结果库具体表结构。

## 4. 属性与机制状态的边界

适合作为属性的内容：

- 基础与最终生命、攻击、防御。
- 暴击率、暴击伤害、元素精通、元素充能效率。
- 治疗加成、受治疗加成和元素伤害加成。
- 目标抗性等需要统一读取和修饰的稳定数值。

不适合作为属性的内容：

| 内容 | 归属 |
| --- | --- |
| 当前生命 | `CharacterRuntimeState.health` 与 `HealthRuntime` |
| 当前能量 | 实体资源运行态 |
| Buff、被动激活状态 | 对应领域 Runtime 与领域 Store |
| 持续时间、层数、冷却 | 领域机制实例或专用运行态 |
| 元素附着、ICD | 专用 aura / ICD 运行时；按需复用时间原语 |
| 护盾实例 | `ShieldRuntime` 与 `ShieldStore` |
| 元素附魔 | 机制决策或规则选择 |
| 技能倍率 | 资产数据或动作参数 |
| 一次性保证暴击等效果 | 触发机制 |
| content 专属计数器和模式 | `ContentStateStore` 或机制实例状态 |

判断原则：

- 需要被多个来源数值修饰并统一查询的稳定量，适合建模为属性。
- 具有生命周期、触发、消耗、层数或离散模式的内容，优先建模为机制状态。
- 只服务于一个 handler 的内部数据，优先保存在内容状态中。

## 5. 总体结构

```text
资产数据 + SimulationConfig + content contribution
                    |
                    v
        application/assembly
                    |
        +-----------+------------+
        |                        |
        v                        v
BaseAttributeSet        ModifierProviderIndex
        |                        |
        +------------+-----------+
                     |
                     v
        AttributeDefinitionRegistry
                     |
                     v
            AttributeResolver
                     |
                     v
           AttributeResolution
```

主要组件：

- `AttributeDefinitionRegistry`：保存公共与私有属性定义、解析策略引用和叠加组定义。
- `BaseAttributeSet`：按主体和属性保存不可变基础贡献。
- `ModifierProviderIndex`：按写入属性索引静态和动态 provider。
- `AttributeResolver`：统一解析依赖、收集 term、执行 policy 并生成审计结果。
- `AttributeResolutionSession`：管理单次顶层查询内的依赖栈、memo 和 provider 读取校验。
- `AttributeSnapshot`：保存调用者明确请求的历史属性事实。

## 6. 身份模型

属性主体第一版只支持角色和目标。

- 角色使用稳定战斗实体身份，不使用 `player:active` 空间实体。
- 目标使用稳定目标运行态身份，不使用显示名称。
- 队伍、空间创建物和机制实例不作为属性主体。
- 创建物需要属性时，应显式读取其来源角色或目标。

属性归属主体和属性贡献来源使用不同引用类型：

- subject/target ref 表达“查询谁的数值”。
- source ref 表达“该基础值或 modifier 来自哪里”。

这样可以避免把资产、动作、机制实例和角色身份混入一个万能引用类型。

## 7. 属性空间

属性空间分为两部分：

```text
公共属性：由 core 定义，封闭且稳定
content 私有属性：由 handler 在自身命名空间内扩展
```

公共属性可以被核心系统和多个内容实现依赖，content 不得覆盖其定义或解析策略。

私有属性：

- 必须位于对应 `handler_key` 命名空间。
- 默认只供对应 content 或明确协作者使用。
- 不得成为核心系统的隐式依赖。
- 通过 `ContentRuntimeContribution` 在组装阶段注册。
- 若实际是计数器、模式或临时状态，应改用内容状态或机制实例。

## 8. 属性来源分层

属性采用“原始值预组装，派生值延迟查询”。

### 8.1 Primitive Base

来自资产和配置的不可变原始值，例如角色等级属性、武器基础攻击和目标配置抗性。

这些值由 application 读取并转换为 core 基础贡献。`core/attributes` 不读取 SQLite，也不解析配置 JSON。

### 8.2 Static Modifier

本次仿真中始终存在的修饰，例如角色突破属性、武器副属性和无条件装备属性。

静态 modifier 必须绑定明确属性主体，不能跨队伍槽位泄漏。

### 8.3 Runtime Modifier

来自活动领域实例的动态修饰，例如限时 Buff、武器被动、命座效果和目标 Debuff。

对应领域 Store 拥有完整实例与生命周期，属性系统只读取当前有效 provider。

### 8.4 Derived Attribute

根据基础属性、依赖属性和 modifier 延迟解析的最终属性，例如最大生命和最终攻击。

派生值不写回 `CharacterRuntimeState` 或 `TargetRuntimeState`。

## 9. 查询与解析流程

```text
AttributeQuery
-> 校验属性定义与主体类型
-> 解析 definition dependencies
-> 读取 BaseAttributeSet
-> 从 ModifierProviderIndex 选择 provider
-> provider 基于只读 query/session 返回 ModifierTerm
-> 校验 reads/writes、私有命名空间和 stage
-> 应用 stacking group
-> 执行 ResolutionPolicy
-> 应用 override 与 bounds
-> 生成 AttributeResolution
```

属性查询上下文只保存会影响数值语义的结构化信息，例如 tags、source 和 target。

审计明细级别与数值查询语义分离。切换 trace level 不得改变 final value。

## 10. Protocol 边界

属性层使用小型 Protocol，不建立可修改所有属性的万能接口。

- `ModifierProvider`：声明 reads/writes 并贡献 term。
- `AttributeReader`：向动作、机制和后续结算系统提供只读解析入口。
- `ResolutionPolicy`：实现有限且明确的聚合公式。

provider 可以读取其他属性，但必须通过当前 resolution session，并且读取范围必须提前声明。

provider 不得：

- 直接修改属性或机制状态。
- 绕过 session 创建独立 resolver。
- 产生未声明 target key 的 term。
- 访问其他 content 的私有属性。

## 11. 依赖与循环

属性定义和 provider 都可以声明依赖。

- definition dependency 表达稳定派生关系。
- provider dependency 表达条件修饰计算中需要读取的属性。
- 明确的同主体静态循环在组装阶段拒绝。
- 跨主体依赖在运行时按完整查询身份检测。
- 不通过 priority 或执行顺序掩盖循环。

单次顶层查询使用独立 session。session memo 只在该次查询中有效，不形成跨帧或跨查询真值缓存。

## 12. 叠加与覆盖

- Buff 是否共存、刷新或替换由机制运行时决定。
- 属性 resolver 只处理当前有效 term 的数值聚合。
- 同组互斥使用显式 stacking group，而不是全局 priority。
- override 必须由属性定义显式允许。
- 多个有效 override 不进行隐式仲裁，直接报错。

具体 stage、policy 和公式见[属性系统契约](../契约/属性系统契约.md)。

## 13. 快照与审计

属性默认实时查询。需要固定值时，由调用者显式创建局部快照。

快照原则：

- 只保存明确请求的 query，不复制完整角色面板。
- 同一快照内 query 必须属于同一主体和帧。
- query context 必须被保留。
- 快照不可变，不随后续运行态变化。
- 依赖和 term 明细由 trace level 控制。
- 机制通过 `snapshot_id` 引用快照，不维护私有属性字典。

`core/attributes` 生成快照模型，结果基础设施决定具体持久化形式。快照不进入资产库或 `SimulationConfig`。

## 14. 确定性与数值原则

- 相同 query、基础值和 provider 状态必须得到相同结果。
- term 聚合不依赖字典或集合的偶然遍历顺序。
- 加法使用稳定聚合方式。
- 核心解析不做显示舍入。
- 非有限数字在模型边界拒绝。
- 真实游戏需要的取整或截断必须由明确 policy 或机制实现，并有来源与 golden case。

第一版只实现 session 内 memo，不实现跨顶层查询缓存。未来只有性能数据证明必要时，才引入 revision token 和跨查询缓存。

## 15. 与其他模块的关系

### 15.1 application/assembly

负责读取资产与配置、创建基础贡献、注册 content 私有定义和 provider，并构造属性运行时。

### 15.2 content

可以贡献：

- 私有属性定义。
- 原生 `ModifierProvider`。
- legacy modifier；该兼容入口按 owner 绑定主体。

content 不得覆盖公共定义或直接写最终属性。

### 15.3 领域机制 Store

对应领域 Runtime 和 Store 拥有动态实例及其生命周期。活动实例可以提供 modifier provider，属性 resolver 不创建、刷新或移除领域实例。

详细领域运行态边界见[领域运行态设计](./领域运行态设计.md)。

### 15.4 SimulationContext

组装器将 `AttributeResolver` 注册为只读运行时系统，其他系统通过协议获取属性，不依赖 application 或资产对象。

`HealthRuntime` 通过 `AttributeResolver` 查询 `stat.hp.max`，但角色当前生命仍保存在 `CharacterRuntimeState.health` 中，不注册为公共属性，也不写回属性解析结果。

### 15.5 infrastructure/results_sqlite

负责属性快照和审计结果的持久化技术实现。当前属性系统不修改结果库 schema。

## 16. 模块组织

```text
core/attributes/
├── keys.py
├── definitions.py
├── models.py
├── protocols.py
├── policies.py
├── indexes.py
├── resolver.py
├── session.py
└── errors.py

application/assembly/
└── attributes.py
```

`core/attributes` 不能 import `assets`、`content`、`application` 或 `infrastructure`。

## 17. 已确认决策

- 属性系统是查询解析引擎，不是可写面板。
- 属性主体第一版只支持角色和目标。
- 公共属性封闭，content 私有属性按 handler 命名空间扩展。
- 属性来源分为 primitive base、static modifier、runtime modifier 和 derived attribute。
- 原始值在组装阶段冻结，派生值在查询时解析。
- modifier 使用固定阶段与属性专属 policy，不引入通用表达式语言。
- provider 必须声明 reads/writes，并通过 session 读取依赖。
- 属性查询和 provider 无副作用。
- 默认实时查询，快照由调用者显式创建。
- 第一版不实现跨顶层查询缓存。
- 真实内容验证切片暂缓到内容迁移阶段。
