# 角色能力条件协调器契约

> 状态：正式。第一版查询模型、无状态协调器和稳定结果契约已经实现；不包含 ActionManager 注入或资源写入接入。

最后更新：2026-07-14

## 1. 适用边界

本契约冻结角色元素战技与元素爆发的公共条件组合查询：

```text
CooldownConditionReadPort
+ BurstEnergyConditionReadPort
-> CharacterAbilityConditionCoordinator
-> CharacterAbilityConditionResult
```

公共条件只包括技能冷却和标准元素能量，不包括 content 私有条件或 ActionManager 最终准入。

## 2. CharacterAbilityConditionQuery

```text
frame: int
character_id: str
ability_key: str
```

约束：

- `frame` 是非负整数。
- `character_id` 是非空、去除首尾空白后不变的稳定战斗实体 id。
- `ability_key` 是非空稳定能力身份。
- 核心能力推荐使用 `elemental_skill` 和 `elemental_burst`。
- `ability_key` 不等于具体动作 `action_key`；共享冷却的动作变体使用同一个 ability key。
- query 不接受 `ability_kind`，该值必须来自冷却 definition。
- query 不同时接受冷却主体和能量主体，领域引用由协调器按 `character_id` 映射。

## 3. 冷却条件端口

协调器依赖：

```text
CooldownConditionReadPort
└── query_condition(query: CooldownQuery) -> CooldownConditionResult
```

`CooldownQuery`：

```text
key: CooldownKey(
  subject=CooldownSubjectRef(character, character_id),
  ability_key=ability_key,
)
frame: int
```

`CooldownConditionResult` 至少提供：

```text
query: CooldownQuery
satisfied: bool
reason: charge_available | no_available_charge
view:
  key
  ability_kind
  max_charges
  available_charges
  active_ready_frame?
  remaining_frames
  queued_recoveries
  chain_id?
  revision
```

`CooldownConditionResult.query` 必须与协调器提交的 `CooldownQuery` 完全相等。

端口调用无副作用。`frame` 晚于 `CooldownRuntime.normalized_through_frame` 时必须由冷却领域抛出未规范化错误，不能隐式推进。

## 4. BurstEnergyConditionResult

元素能量领域提供稳定状态：

```text
BurstEnergyConditionStatus
├── READY
├── INSUFFICIENT_ENERGY
└── NONSTANDARD_RESOURCE
```

结果：

```text
character_ref: AttributeSubjectRef(character)
frame: int
status: BurstEnergyConditionStatus
current_energy: float
capacity: float
```

不变量：

```text
READY
-> capacity > 0 and current_energy >= capacity

INSUFFICIENT_ENERGY
-> capacity > 0 and current_energy < capacity

NONSTANDARD_RESOURCE
-> capacity == 0 and current_energy == 0
```

`frame` 必须是非负整数。`current_energy` 和 `capacity` 必须是有限非负数，且 `current_energy <= capacity`。

## 5. 爆发能量条件端口

协调器依赖：

```text
BurstEnergyConditionReadPort
└── query_burst_condition(
      character_ref: AttributeSubjectRef,
      frame: int,
    ) -> BurstEnergyConditionResult
```

能量系统拥有状态分类公式。协调器不得通过 `get_current_energy()` 和 `get_capacity()` 的裸数值读取重新实现第 4 节不变量。

现有 `EnergyReadPort.is_burst_ready()` 可以作为兼容便利查询，但协调器必须使用结构化条件结果，以保留能量证据并区分能量不足和非标准资源。

## 6. AbilityConditionBlockingReason

```text
AbilityConditionBlockingReason
├── COOLDOWN_UNAVAILABLE
└── STANDARD_ENERGY_UNAVAILABLE
```

稳定字符串值：

```text
cooldown_unavailable
standard_energy_unavailable
```

顺序固定为冷却在前、标准元素能量在后。多个条件同时不满足时必须全部保留。

## 7. AbilityConditionDelegation

```text
AbilityConditionDelegation
└── CONTENT_PRIVATE_RESOURCE
```

稳定字符串值：

```text
content_private_resource
```

委托条件不是阻塞原因。它表示协调器负责的公共标准资源不适用，角色解释器必须继续判断 content 私有资源，不能直接把公共结果当作完整动作放行。

## 8. CharacterAbilityConditionResult

```text
query: CharacterAbilityConditionQuery
ability_kind: AbilityKind
shared_conditions_satisfied: bool
cooldown_condition: CooldownConditionResult
burst_energy_condition: BurstEnergyConditionResult | None
blocking_reasons: tuple[AbilityConditionBlockingReason, ...]
delegated_conditions: tuple[AbilityConditionDelegation, ...]
```

通用不变量：

- `cooldown_condition.view.key` 必须对应 query 的 `character_id` 和 `ability_key`。
- `cooldown_condition.query.frame == query.frame`。
- `burst_energy_condition` 非空时，其 `frame == query.frame` 且主体 id 等于 `query.character_id`。
- `ability_kind == cooldown_condition.view.ability_kind`。
- `blocking_reasons` 无重复并按第 6 节顺序冻结。
- `delegated_conditions` 无重复并按枚举稳定顺序冻结。
- `shared_conditions_satisfied == (len(blocking_reasons) == 0)`。
- 结果不可变且可稳定序列化。

### 8.1 元素战技

```text
ability_kind = ELEMENTAL_SKILL
burst_energy_condition = None
delegated_conditions = ()
blocking_reasons = () if cooldown satisfied
                   else (COOLDOWN_UNAVAILABLE,)
```

### 8.2 标准元素爆发

```text
ability_kind = ELEMENTAL_BURST
burst_energy_condition.status = READY | INSUFFICIENT_ENERGY
burst_energy_condition.frame = query.frame
delegated_conditions = ()
```

阻塞原因分别由冷却和能量条件独立贡献。不能在冷却不满足时跳过能量查询。

### 8.3 非标准资源爆发

```text
ability_kind = ELEMENTAL_BURST
burst_energy_condition.status = NONSTANDARD_RESOURCE
burst_energy_condition.frame = query.frame
delegated_conditions = (CONTENT_PRIVATE_RESOURCE,)
```

此时能量条件不贡献 `STANDARD_ENERGY_UNAVAILABLE`。`shared_conditions_satisfied` 只取决于冷却条件。

## 9. CharacterAbilityConditionPort

动作层只依赖：

```text
CharacterAbilityConditionPort
└── evaluate(
      query: CharacterAbilityConditionQuery,
    ) -> CharacterAbilityConditionResult
```

调用契约：

- `evaluate()` 无副作用。
- 不修改冷却、元素能量、动作实例或输入会话状态。
- 不发布 Event。
- 不保存长期查询记录。
- 不返回 commit token、reservation 或可重复提交的 plan。
- 相同领域前值上的相同 query 必须返回相同结果。

## 10. 评估顺序

```text
1. validate query
2. query cooldown condition
3. validate cooldown evidence
4. read ability kind from cooldown evidence
5. if skill: build result
6. if burst: query energy condition even when cooldown is unavailable
7. validate energy subject
8. collect blocking reasons and delegations
9. build immutable result
```

稳定顺序用于测试和审计，不能根据 dict、set 或 provider 注册顺序变化。

## 11. 与动作准入的契约

角色解释器使用结果时：

```text
shared_conditions_satisfied = false
-> 解释器返回公共条件拒绝

shared_conditions_satisfied = true
-> 解释器继续判断 content 私有条件
-> 有 CONTENT_PRIVATE_RESOURCE 时必须完成对应私有资源判断
-> 全部内容条件通过后才构造 PreparedAction
```

`PreparedAction` 仍需由 `ActionManager` 检查动作锁、中断、owner、会话和开始帧。协调器结果不能替代 `ActionDecision`。

解释器应保存稳定 reason code 和必要 evidence。中文显示文本不属于本契约，不作为机器判断依据。

## 12. 查询与写入分离

协调器不得调用：

```text
CooldownRuntime.prepare_start / start / commit
CooldownRuntime.reduce_remaining
CooldownRuntime.reset_active
EnergyRuntime.spend_burst
EnergyRuntime.restore
EnergyRuntime.drain
```

查询通过后：

- 冷却何时开始由具体能力时序决定。
- 爆发何时扣能由 content 声明的扣能帧决定。
- 中间状态变化不会使旧查询结果成为 reservation。
- 扣能帧能量不足仍按能量领域契约报错。

## 13. 帧契约

- query frame 必须等于动作解释器处理当前输入时的 `session.current_frame`。
- CooldownRuntime 必须在同帧 ActionManager 之前规范化。
- `frame == ready_frame` 的次数在解释输入前视为已经恢复。
- 协调器不得修正、推进或回退 query frame。
- 查询历史帧或未来未规范化帧使用领域错误，不返回普通条件拒绝。

## 14. 错误类型

目标错误层级：

```text
CharacterAbilityConditionError
├── CharacterAbilityConditionValidationError
├── CharacterAbilitySubjectMappingError
└── CharacterAbilityConditionConflictError
```

用途：

- `ValidationError`：query 字段或未知 ability kind 非法。
- `SubjectMappingError`：无法从稳定 character id 构造一致领域引用。
- `ConditionConflictError`：领域返回的 key、主体、frame 或 kind 与 query 冲突。

冷却和能量领域的查找、未规范化或状态错误保留其领域异常。协调器可以附加 query 上下文，但不能捕获宽泛异常并降级为阻塞原因。

## 15. 序列化

- enum 使用稳定字符串 value。
- `blocking_reasons` 和 `delegated_conditions` 使用稳定数组顺序。
- `CooldownConditionResult` 和 `BurstEnergyConditionResult` 保存完整数值证据。
- 浮点遵循元素能量领域有限数值和 `-0.0` 规范化规则。
- 新增或删除字段属于契约变化，必须同步本文、动作审计模型和 JSON 往返测试。

## 16. 验证矩阵

| 场景 | 公共通过 | blocking | delegation |
| --- | --- | --- | --- |
| 战技有 charge | 是 | 空 | 空 |
| 战技无 charge | 否 | cooldown | 空 |
| 标准爆发 CD 好且满能 | 是 | 空 | 空 |
| 标准爆发 CD 不好但满能 | 否 | cooldown | 空 |
| 标准爆发 CD 好但能量不足 | 否 | energy | 空 |
| 标准爆发 CD 和能量均不足 | 否 | cooldown, energy | 空 |
| 非标准爆发 CD 好 | 是 | 空 | private resource |
| 非标准爆发 CD 不好 | 否 | cooldown | private resource |

还必须覆盖：

- 多充能剩余至少一个 charge。
- 同一 ability key 的多个动作变体。
- `frame == ready_frame`。
- 冷却未规范化。
- 未知 character id 或 ability key。
- 冷却与能量证据主体冲突。
- 查询不产生 Store、revision、Event 或 coordinator record 变化。
