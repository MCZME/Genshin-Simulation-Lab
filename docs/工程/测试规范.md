# 测试规范

> 状态：生效，持续维护。
> 最后更新：2026-08-28。

## 1. 文档定位

测试代码与生产代码同等对待：可读、可审、可维护，并接受同一套质量工具检查。本文的职责是定义 `backend/tests/` 与 `frontend/` 测试的组织方式、命名、脚手架复用、参数化与断言、golden case 的代码形态以及质量门禁。

本文不保存具体机制、公式或数值真值。机制与数值以 `docs/契约/`、`docs/架构/` 和已确认的 golden case 为准；各系统的测试矩阵与验收入口由对应架构/契约文档拥有。

本文落实[项目决策记录](../决策/项目决策记录.md)中“测试策略”的已确认结论，并与以下文档分工：

- [系统自治与跨系统协调规范](./系统自治与跨系统协调规范.md)：后端单元测试的组装边界。
- [原神游戏机制实现规范](./原神游戏机制实现规范.md)：数值可信度与机制实现要求。
- [前端工程规范](./前端工程规范.md)：前端工程边界、工具链与质量入口。

后端与前端使用不同工具链与目录形态，但共享“测试即代码、单一关注点、可复现、可隔离”的原则；本文先给出总则，再分别给出后端与前端的规则。

### 1.1 测试目的与价值判断

测试不是数量指标，而是“可执行的契约、安全网和行为说明”。每个测试必须能回答：它失败时，是哪个已确认的行为或契约被破坏了？回答不上来的测试不应保留。

清理/合并测试时按以下价值层级判断：

- 保留：契约真值（golden、server 路由 DTO、API 客户端映射、前端编译/形状推导）、错误边界、状态与事件顺序、跨系统协调不变量、关键交互链路。
- 合并/精简：同一行为在多层重复且锁定同一真值；同构参数化矩阵；同一关注点拆散在多文件。
- 迁移：断言承载契约真值但放在错误层级；唯一覆盖要从低价值层删除前，先迁到对应持有层。
- 删除：锁实现细节、测试第三方库/框架自身、无可信来源的 golden、无回归价值的纯展示渲染、与已确认契约无关的临时用例。

具体清理按领域分批执行；删除前必须确认没有唯一覆盖。

## 2. 测试分层职责

归类规则：先问“这个测试要锁定什么”。被测单元自身专有的行为进单元测试；跨模块闭环进集成测试；有真实数据来源且预期值需要冻结的数值基准进 golden case；纯逻辑与组件行为按前端分层执行。同一行为不应为凑层级而复制到多个层级；两种层级同时存在时，应确认它们锁定的真值确实不同（例如 unit 锁内容自身行为、golden 锁可信来源下的最终数值）。

### 2.1 后端分层职责

| 层级 | 目录 | 验证对象 | 典型内容 | 不应包含 |
| --- | --- | --- | --- | --- |
| 单元测试 | `backend/tests/unit/` | 被测单元（模块/内容）自身专有的行为、状态提交、错误分支与边界 | 内容专属门槛与公式分支、领域 Store、resolver、handler、纯模型、边界与异常 | 跨模块行为、访问 SQLite、启动前端/浏览器、依赖具体角色/武器内容（除非测试内容本身）、其它模块已覆盖的机制 |
| 集成测试 | `backend/tests/integration/` | 跨模块组装与运行闭环、跨模块事件流、仓库、持久化与任务执行 | 资产 -> handler -> 装配 -> 运行、跨系统协调、内容切片接线、错误暴露时机 | 代替单元测试逐分支验证公式；把多个无关纵向关注点堆进一个文件 |
| golden case | `backend/tests/golden/` | 有真实数据来源的数值基准 | 伤害、治疗、反应倍率、Buff 覆盖率、时间轴等冻结数值 | 未确认数值；资产库数值快照；以版本/交付批分类；承担普适单元覆盖 |

golden 与 integration 的边界：golden 只承载有真实数据来源的数值基准，预期值必须来自已确认资料或旧项目复核，不从实现推导；integration 允许合成输入，主要验证跨模块装配闭环、事件流和错误暴露时机，即使闭环中出现数值，也不以“数值正确”为断言目标。生产装配 + 可信数值属于 golden；生产装配 + 合成输入/错误时机属于 integration。同一行为不得在两层重复锁定同一目标。

### 2.2 前端分层职责

| 层级 | 位置 | 验证对象 | 隔离方式 |
| --- | --- | --- | --- |
| 纯逻辑测试 | `frontend/src/**/*.test.ts`，与被测源文件同目录 | 状态转换、工作流语义、校验、编译、变体展开、API 客户端与轮询逻辑 | node 环境；stub `fetch`；不使用 DOM |
| 组件/壳测试 | `frontend/src/**/*.test.tsx`，与被测源文件同目录 | 渲染、交互、组件间接线、页面壳流程 | jsdom；mock `api/client`、轮询模块与第三方组件；不启动后端 |
| E2E | 后置（Playwright） | 真实前端 + 后端 + 结果库链路 | 引入时单独定义目录与准入标准，本文不提前固定 |

当前前端测试沿用与被测源文件同目录的 co-located 形态，不另建 `frontend/tests/` 总目录；共享脚手架确有需要时按 §5.2 提取。

前端规则：

- 纯逻辑与组件测试都不发真实 HTTP、不依赖真实后端、不读取本地资产库/结果库；API 行为通过 stub `fetch` 或 mock `api/client` 固定响应。
- 组件测试优先断言用户可见语义与稳定行为；确需锁定第三方库渲染结构时，在用例注释中说明原因与升级风险。
- 前端不使用“golden case”保存机制数值；需要冻结的编译/转换/形状结果叫契约回归基准，放在对应测试文件或 fixture 中。分析模板等口径基准按对应设计文档要求处理。

### 2.3 前后端契约对齐

- 后端 server 路由测试（`backend/tests/unit/server/`）锁定 HTTP 状态码、DTO 形状、错误模型与路由到 application 用例的适配；前端 API 客户端测试锁定 URL、方法、请求体、响应解析与错误映射。
- OpenAPI 是前后端共享类型的单一来源；`frontend/src/api/schema.d.ts` 由 `openapi-typescript` 生成并提交，不手写两套类型。
- 契约改动顺序：先改契约文档与 OpenAPI，再重新生成前端类型，同步更新两端测试 fixture，最后改实现。两端测试不得各自发明与契约不一致的 fixture。
- 未引入 E2E 前，前后端契约由“后端 server 测试 + 前端 API 客户端测试 + OpenAPI 类型”共同保证；组件测试不需要启动真实后端。

## 3. 后端专属规范

### 3.1 资产数据库数据验证边界

资产库（SQLite）与标准 manifest 是只读生成产物，其中的资产绑定（`handler_key`）、等级数值、效果参数等属于数据内容，**不在测试中验证**：

- 测试不读取本地资产库或 manifest 的固定路径，不断言具体数据库数值，不验证“某个资产绑定了哪个 handler”。
- 测试只验证代码行为：内容工厂、注册表、装配、运行时、repository 接口、审计规则和错误分支。需要资产形状作为测试输入时，使用内联合成数据或 `backend/tests/helpers/` 共享构造器，合成数据只包含接线所需的最小字段，不携带、不复制真实资产数值。
- 资产库中的真实数据（攻击倍率、治疗量、冷却时长、能量数额、效果参数等）不得作为测试输入或预期进入任何测试：内容测试不验证也不使用这些数值，例如角色测试不通过“打出真实倍率”来证明装配可用。
- 真实数据内容的正确性由资产构建与校验链路承担：`assets fetch-source` → `build-manifest` → `audit-manifest` → `build` → `validate`（见[资产数据库设计](../契约/资产数据库设计.md)）。数据库层测试只验证读取/写入代码的行为契约，不充当数据审计。
- golden case 的“可信输入与预期输出”指机制或公式基准，数值必须来自已确认资料或旧项目复核，不来自本地资产库；资产库数值基线不写入测试，需要固定时由数据版本与 audit 规则承载。

### 3.2 内容切片测试必要性

内容层（角色、武器、圣遗物、效果等具体实现）是测试最容易膨胀的地方：它主要是数据与接线，不是共享算法。内容测试不是默认产物，只有“必要的”行为才专门写测试；必要性判断回到 §1.1——该测试失败时，是哪个已确认的行为或契约被破坏了？回答不上来的测试不写。

内容测试的两个硬边界：

- 不把其它模块/系统的行为搬到内容层重复测试：例如“角色造成了伤害”属于伤害系统，内容层不写“伤害是否成功造成、数值是否正确”的测试；治疗、能量、冷却、附着等一般机制同理，由对应系统测试与 golden case 承担。
- 内容自身专属的逻辑也不是必然有测试：只有承载契约真值、错误边界，或装配/校验链路无法保证的行为才值得保留。

内容测试的断言边界：

- 数值断言只能以相对或行为形式出现：`> 0` / `== 0`、`A < B`、触发次数、`N 目标 = N×单目标`、封顶 = `上限×单单位`；不得硬编码数据库来源的最终数值，也不得把“伤害/治疗成功产生且数值正确”当作内容测试目标。
- 纯注册结构快照（“注册了几个动作/冷却/ICD”）不作为测试保留；登记本身由装配契约保证，只有校验失败分支才值得保留。
- 引擎已覆盖的一般机制（能量门槛、冷却拦截等）不在内容层重复；与内容非重点机制（如普通攻击倍率闭环）直接不测。

不默认测试的内容：

- 实现细节：逐帧衔接矩阵、动作编译字段、修饰器内部贡献步骤、每个命座的编译细节。
- 内容数据本身：范围半径、tick 次数、天赋等级加成表；数值正确性由资产库校验链负责，内容测试不直接断言。
- 引擎已覆盖的重复行为：面积查询、创建物 tick 等 core 层已有测试的机制，内容层不再重复。

### 3.3 Golden case 代码形态

golden case 是“针对数值的测试”：只承载有真实数据来源的数值基准，没有可信来源的数值不得进入 golden。

- 目录与命名：`backend/tests/golden/<稳定业务领域>/test_<机制或流程>.py`；领域契约入口与状态在领域 README 或收敛清单维护（元素反应见[元素反应收敛切片](./元素反应收敛切片.md)）。
- 一个 golden 文件聚焦一个机制或跨机制流程，不写成该目录下所有功能的集合。
- 数据格式：默认使用 Python 内联数据并通过参数化表达同构矩阵；只有数据量大到影响可读性时才使用同目录 `data/` 下的 JSON 文件，并声明键约定与 schema；引入新数据格式时同步更新本文档。
- 每个 golden case 至少记录最小记录集：验证能力、真实数据来源及适用版本（资料出处与确认方式）、旧项目参考（如使用）、完整输入条件、预期输出与允许误差、不覆盖的行为。记录放在用例 docstring 或数据记录中。
- 未确认的机制数值不得写成 golden 预期；只能以草案/待确认状态留在文档或契约中。golden 预期值不得从当前实现推导后自我验证，也不得取自本地资产库（见 §3.1）。
- golden 用例标识不使用版本时间线；资料来源中的“版本”只描述游戏版本或数据来源，不描述本项目交付批次。

## 4. 目录与文件组织

### 4.1 公共规则

- 测试文件名与测试函数名描述行为或关注点，不使用版本时间线作为分类依据。
- 一个文件只承担一个关注点，这是硬规则，与行数无关：文件内出现多个独立行为组（例如普攻、战技、命座各自成组，或互不相关的状态转换）时必须拆分，即使总行数没有超限。
- 一个测试函数只验证一个行为主题。准备步骤进 fixture 或 helper，断言集中在本次行为的输入与结果上；同一行为可以有多条断言。
- 测试内禁止真实网络、真实时钟与未固定种子的随机；随机路径必须显式固定种子。

### 4.2 后端目录

- `backend/tests/unit/` 按 `unit/<顶层模块>/<子路径>/test_<关注点>.py` 镜像 `src/genshin_sim/` 结构；`backend/tests/integration/` 按纵向关注点或基础设施模块组织；`backend/tests/golden/` 按稳定业务领域组织（当前为 `damage/`、`reactions/` 等）。

### 4.3 前端目录

- 测试文件与被测源文件同目录：`*.test.ts`（纯逻辑）、`*.test.tsx`（组件/壳）。
- 需要 jsdom 的文件在文件头显式声明 `// @vitest-environment jsdom`，不依赖全局默认环境。
- 同一关注点只保留一个测试文件；文件内出现多个独立行为组时拆分。
- 测试间隔离与 mock 清理：在 `afterEach`/`beforeEach` 中清理 `vi.restoreAllMocks()` 与 `vi.unstubAllGlobals()`，不依赖执行顺序或上一个测试的副作用。

## 5. 脚手架与复用

### 5.1 公共规则

- 禁止跨文件复制私有构造/装配 helper（例如配置 payload、`_assemble`、`_apply_aura`、工作流构造这类）；同一脚手架出现第二份时立即提取。
- fixture 优先使用工厂形态（返回构造器而不是固定实例），避免测试间共享可变状态；后端 fixture 作用域默认 `function`，只读、不可变或重量级资源才使用更高作用域；前端测试工具同样按用例独立创建，不共享可变状态。
- 临时资产库、结果库、缓存一律使用临时目录，不使用固定路径或共享文件；后端统一走 `tmp_path`，前端确需临时文件时使用系统临时目录并在用例结束后清理。
- 测试之间必须隔离：不依赖执行顺序、模块级可变状态或上一个测试留下的副作用。
- 跨文件共享的 key、常量与基线数值放在共享 helpers 或 fixtures，不逐文件复制。

### 5.2 后端

- 提取位置按复用范围：
  - 跨领域/跨目录共享：`backend/tests/conftest.py` 或 `backend/tests/helpers/` 包（纯函数与数据构造器通过 `from tests.helpers... import ...` 导入）；
  - 单领域内共享：该领域目录的 `conftest.py`；
  - 单文件内私有 helper：允许，但不得被其他文件复制。
- 单一角色或内容单元：测试文件放入镜像 src 结构的角色目录（例如 `backend/tests/unit/content/characters/mondstadt/barbara/`），其私有脚手架放同目录 `conftest.py`。
- `backend/tests/helpers/` 是显式包：`backend/tests/` 必须提供 `__init__.py`，helper 通过 `from tests.helpers... import ...` 导入；禁止隐式依赖测试目录被加入 `sys.path` 后直接 `import helpers`。
- 与 pytest 生命周期相关的共享能力（临时路径、装配完成的运行时、事件捕获、清理）一律做成 fixture，不进 `backend/tests/helpers/`；`backend/tests/helpers/` 只放无副作用的纯构造器、常量与工具函数。

### 5.3 前端

- 当前以 co-located 为主；跨文件共享 helper 出现第二份时提取，不复制 fixture 构造。
- 提取位置按复用范围：
  - 跨目录共享：`frontend/src/test/`（如 `helpers.ts`、`fixtures/`）；
  - 单领域内共享：该领域目录的 `testUtils.ts` 或 `__fixtures__/`；
  - 单文件内私有 helper：允许，但不得被其他文件复制。
- mock 声明按测试文件局部生效；需要跨文件复用的 mock 响应构造器提取为工厂函数，不在模块顶层共享可变 mock 状态。
- 与生命周期相关的共享能力（渲染壳、事件清理、全局替身）做成可复用测试工具或 `beforeEach`/`afterEach`，不放纯构造器目录。

## 6. 参数化与断言

### 6.1 后端

- 两个及以上同构测试函数（相同断言体、仅输入不同）优先合并为 `@pytest.mark.parametrize`；参数化用例使用稳定、可读的 `ids`。
- 断言行为优先于实现：优先断言公开结果、事件、快照与数值；仅当内部记录本身就是被验证的契约（例如分发记录、提交计划）时才断言内部对象。
- 浮点数值统一使用 `pytest.approx`；golden 的允许误差随用例记录。
- 错误分支使用 `pytest.raises` 断言异常类型与关键信息，不复制堆栈。
- 测试必须包含有效断言；仅“能跑通”不能作为测试。
- 数值预期不得从实现推导后自我验证：golden 预期值必须先有资料或旧项目复核，再写入测试。

### 6.2 前端

- 两个及以上同构用例优先合并为 `it.each`/`test.each`，提供稳定可读的用例标题。
- 断言行为优先于实现：优先断言返回结果、DOM 可访问语义、调用参数与错误信息；仅当内部记录本身就是被验证的契约时才断言内部对象。
- 浮点使用 `toBeCloseTo` 或显式误差；普通对象优先 `toEqual`，不用快照掩盖无关差异。
- 错误分支使用 `rejects.toMatchObject`/`toThrow` 断言错误码与关键信息，不复制完整堆栈。
- 测试必须包含有效断言；仅“能跑通”不能作为测试。
- 快照（`toMatchSnapshot`/`toMatchInlineSnapshot`）只用于有明确回归价值的稳定结构；快照变更必须人工审阅，不把第三方库内部输出或随机内容快照化。
- 契约回归预期不得从当前实现临时推导后自我验证；预期来自契约文档或已确认 fixture。

## 7. 质量门禁

- 测试代码与生产代码使用同一套工具。
- 后端：`ruff check`、`ruff format --check`、`pyright`（`pyproject.toml` 已包含 `tests`）；`pytest` 保持 `--strict-config` 与 `--strict-markers`。
- 前端：`pnpm lint`、`pnpm typecheck`、`pnpm test`；`frontend/src/api/schema.d.ts` 是生成产物，不手改。
- 小修改只运行与改动对应的测试路径，不需要全量运行；全量 `pytest` 仅在大改动或改动横跨多个模块时运行。涉及后端数值或机制必须运行对应 golden case；涉及前端语义或契约必须运行对应 Vitest 文件/目录。
- 覆盖率只作为线索，不设统一阈值；关键分支（边界、错误、提交顺序、确定性）必须有覆盖。
- 纯文档改动可以不运行代码检查，但必须在交付说明中明确。

完整检查命令见 [AGENTS.md](../../AGENTS.md)。

## 8. 重构与演进

- 测试重构是独立主题：按仓库提交工作流，一个 PR 只处理一个主题，测试规范化不与功能提交混入。
- 存量测试按领域/模块分批套用本文规则，不做一次性大范围重排；每个迁移切片在完成实现时顺带清理本领域脚手架。
- 删除或合并测试的标准是覆盖密度而非数量：不降低契约覆盖；若断言承载契约真值，先迁入对应持有层（后端按 §2.1，前端按 §2.2/§2.3）再删除；删除前确认没有唯一覆盖，并同步领域收敛清单中的登记。
- 行为变更的顺序：先确认并更新契约与 golden/回归基准，再改实现与测试，避免用测试反推实现。
- 前后端契约变更时，先更新契约文档与 OpenAPI，再重新生成类型并同步两端测试，最后改实现。
