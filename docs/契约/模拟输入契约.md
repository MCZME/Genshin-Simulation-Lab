# 模拟输入契约

> 本文档记录新项目第一版模拟输入契约与应用端 MVP 范围。
> UI 具体交互方案暂缓设计，本文只定义应用需要编辑、保存和运行的数据契约。

## 1. 模拟输入契约目标

模拟输入用于描述一次仿真“要模拟什么”。

第一版模拟输入契约需要满足：

- 可以由 UI 编辑。
- 可以由 CLI 运行。
- 可以由批量任务复用和变异。
- 可以被 `application/assembly/SimulationAssembler` 组装为仿真运行时对象。
- 可以长期保存，并通过 `schema_version` 做兼容处理。

模拟输入契约不包含：

- UI 布局状态。
- 分析图表状态。
- 数据库路径。
- Flet 控件状态。
- 资产显示名作为识别依据。

## 2. 顶层结构

第一版使用 `SimulationInput` 作为单次模拟输入。

顶层结构：

```text
SimulationInput
├── schema_version
├── kind
├── meta
├── team
├── scene
├── input_trace
├── rules
└── run_options
```

建议 JSON 结构：

```json
{
  "schema_version": 2,
  "kind": "simulation_input",
  "meta": {
    "name": "芙宁娜测试",
    "description": ""
  },
  "team": [],
  "scene": {},
  "input_trace": [],
  "rules": {
    "enabled": []
  },
  "run_options": {
    "max_frames": 18000
  }
}
```

`meta.name` / `meta.description` 由画布上的元信息节点配置并写入，工作流存档名称不进入输入文档；缺少非空 `meta.name` 时运行被阻止。

## 3. 身份引用规则

配置中的资产统一使用 `asset_key`。

示例：

```text
character:75
weapon:11512
artifact_set:15032
```

规则：

- 角色、武器、圣遗物套装引用 `asset_key`。
- 不使用显示名称作为仿真识别依据。
- `display_name` 可以作为辅助缓存存在，但不能参与组装判断。
- 按键输入轨迹记录按键输入事实，不使用角色名称。

## 4. 队伍配置

`team` 是队伍槽位列表。

组装阶段会为每个队伍槽位创建一个 `CharacterRuntimeState`，保存槽位、角色 `asset_key`、等级、命座、天赋等级和最小可变状态；`TeamRuntimeState` 通过这些角色运行态推导队伍规模与当前场上角色。

示例：

```json
[
  {
    "slot": 1,
    "character": {
      "asset_key": "character:75",
      "level": 90,
      "constellation": 2,
      "talents": {
        "normal_attack": 1,
        "elemental_skill": 10,
        "elemental_burst": 10
      }
    },
    "weapon": {
      "asset_key": "weapon:11512",
      "level": 90,
      "refinement": 1
    },
    "artifacts": {
      "sets": [
        {
          "asset_key": "artifact_set:15032",
          "pieces": 4
        }
      ],
      "stats": {}
    }
  }
]
```

第一版先支持：

- 角色资产。
- 角色等级。
- 命座。
- 天赋等级：普通攻击、元素战技、元素爆发三项，第一版编辑器限制 1–10。
- 武器资产。
- 武器等级。
- 武器精炼。
- 圣遗物套装与件数。
- 圣遗物属性总词条。

### 4.1 圣遗物属性（总词条模型）

`artifacts.stats` 使用扁平的 `{ 词条: 数值 }` 对象，表示该角色全部圣遗物（主词条与副词条合计）的总加成，不区分具体部位与来源。

- 百分比词条统一使用小数倍率（20% 保存为 `0.2`），与[属性系统契约](./属性系统契约.md)一致；数值必须为有限非负数。
- `sets` 与 `stats` 均可为空；前端圣遗物节点要求套装与属性至少配置一项，后端允许 `artifacts` 整体缺省。
- `sets` 中每条 `pieces` 只允许 `1`、`2`、`4`。
- `pieces` 表示装备件数：配置 `4` 件时同时启用该套装 ≤ 4 件的全部效果（通常为 2 件套 + 4 件套），配置 `2` 件时只启用 2 件套效果。

支持词条（显示名只用于界面，词条 key 是稳定契约）：

| key | 显示名 | 输入形态 |
| --- | --- | --- |
| `hp_percent` | 生命值% | 百分比 |
| `atk_percent` | 攻击力% | 百分比 |
| `def_percent` | 防御力% | 百分比 |
| `flat_hp` | 固定生命值 | 数值 |
| `flat_atk` | 固定攻击力 | 数值 |
| `flat_def` | 固定防御力 | 数值 |
| `crit_rate` | 暴击率 | 百分比 |
| `crit_damage` | 暴击伤害 | 百分比 |
| `elemental_mastery` | 元素精通 | 数值 |
| `energy_recharge` | 元素充能效率 | 百分比 |
| `healing_bonus` | 治疗加成 | 百分比 |
| `physical_damage_bonus` | 物理伤害加成 | 百分比 |
| `pyro_damage_bonus` | 火元素伤害加成 | 百分比 |
| `hydro_damage_bonus` | 水元素伤害加成 | 百分比 |
| `electro_damage_bonus` | 雷元素伤害加成 | 百分比 |
| `cryo_damage_bonus` | 冰元素伤害加成 | 百分比 |
| `anemo_damage_bonus` | 风元素伤害加成 | 百分比 |
| `geo_damage_bonus` | 岩元素伤害加成 | 百分比 |
| `dendro_damage_bonus` | 草元素伤害加成 | 百分比 |

示例：

```json
{
  "sets": [],
  "stats": {
    "crit_rate": 0.311,
    "atk_percent": 0.466,
    "flat_atk": 311.0,
    "elemental_mastery": 80.0
  }
}
```

`flat_hp` / `flat_atk` / `flat_def` 是配置侧词条 key，不属于资产库 stat 枚举（见[资产数据库设计](./资产数据库设计.md) 4.4）；它们在属性系统中映射为 `stat.hp.max` / `stat.atk.total` / `stat.def.total` 的 `flat_add` 修饰，映射表见[属性系统契约](./属性系统契约.md) 18.3。

## 5. 场景配置

`scene` 描述本次仿真的当前场上角色空间起点、目标与场景条件。

敌人基础抗性/等级信息第一版不进入资产库，因此目标直接写在配置中。

第一版运行时空间使用 X/Z 平面做普通范围查询；`position.y` 保留给下落攻击等高度敏感机制，暂不参与普通半径判定。目标支持多个，但每个目标在空间层只作为简单点位靶子，不模拟复杂体型、碰撞、多 hitbox 或目标挤压。

组装阶段会为每个 `scene.targets[]` 创建一个 `TargetRuntimeState` 和一个 `target:<id>` 空间实体。目标运行态保存目标 id、等级、抗性和展示名；空间实体保存目标点位。两者通过 `spatial_entity_id` 关联。

`id` 是仿真识别依据，必填且在同一输入内唯一：空间实体、属性主体与结果引用都使用它。`label` 是可选展示名，只用于界面与结果展示，不参与组装判断或机制计算。`resistance` 支持 `physical / pyro / hydro / electro / cryo / anemo / geo / dendro` 八个元素键，值表示抗性数值（通常为百分比，例如 `10` 表示 10%）。

元素反应第二版不向 `scene.targets[]` 增加阵营、敌对、可伤害或可减抗字段。`scene.targets[]` 继续表示本次仿真的敌人目标，组装后由窄运行时资格协议提供 hostile 关系以及实际 `aura`、`damage`、`attribute_status` capability；Space 和配置模型不拥有通用阵营状态。环境目标配置与敌方主动 Impact 入口不属于第二版。完整语义见[元素反应运行时与事务契约](./元素反应/运行时与事务契约.md)。

动作层可以使用运行时空间查询候选空间实体。候选实体只表示“在本次范围查询内”，不表示最终命中、伤害结算或元素反应已经发生。

`player` 描述当前场上角色的初始空间实体；如果省略，默认位置为 `(0, 0, 0)`，朝向为 `(0, 0, 1)`。后台角色默认没有独立空间实体，切人只改变当前场上角色空间实体对应的队伍槽位。

示例：

```json
{
  "player": {
    "position": {"x": 0, "y": 0, "z": 0},
    "facing": {"x": 0, "y": 0, "z": 1}
  },
  "targets": [
    {
      "id": "target_1",
      "label": "遗迹守卫",
      "level": 90,
      "position": {"x": 0, "y": 0, "z": 5},
      "resistance": {
        "physical": 10,
        "pyro": 10,
        "hydro": 10,
        "electro": 10,
        "cryo": 10,
        "anemo": 10,
        "geo": 10,
        "dendro": 10
      }
    }
  ]
}
```

## 6. 按键输入轨迹

`input_trace` 描述仿真中的按键输入轨迹。

按键输入轨迹按帧分组，记录键盘或鼠标按钮的按下与松开。输入层只记录按键事实，不直接生成具体角色动作。组装阶段会把按键事实配对为 `InputSessionPlan`，再由运行时 `ActionManager` 按帧调用队伍或角色动作解释器；战技点按、长按、切人后摇导致输入无效等行为不写入模拟输入契约。

示例：

```json
[
  {
    "frame": 120,
    "events": [
      {"key": "keyboard.e", "phase": "press"}
    ]
  },
  {
    "frame": 145,
    "events": [
      {"key": "keyboard.e", "phase": "release"}
    ]
  }
]
```

第一版按键输入轨迹只支持键盘和鼠标按钮，不支持移动键、鼠标视角、手柄或自定义键位；第 0 帧保留为仿真初始化帧，输入帧号必须为正整数。详细契约见：[按键输入契约](./按键输入契约.md)，运行时协作关系见：[按键输入系统设计](../架构/按键输入系统设计.md)。

## 7. 规则配置

`rules` 用于保存本次仿真的额外规则或开关。

第一版保留结构，但不急于扩展复杂规则系统。

示例：

```json
{
  "enabled": []
}
```

## 8. 运行选项

`run_options` 保存仿真运行控制项。

第一版保留：

```json
{
  "max_frames": 18000
}
```

确认决策：

- 不设置 `mode`。
- 所有仿真都保存完整结果数据。
- 不区分 `summary_only` 和 `recorded`。
- 结果数据体积通过结果清理、归档或会话管理策略处理。

未来可考虑加入：

- 随机种子。
- 结果标签。
- 运行备注。

## 9. ProjectConfig 与 SimulationInput 的关系

`SimulationInput` 只描述一次仿真。

未来可以设计 `ProjectConfig`，用于保存：

- 多个模拟输入。
- UI 工作区信息。
- 最近分析会话。
- 项目级模板。

但 `SimulationInput` 本身应保持干净，避免混入 UI 状态。

## 10. 第一版 MVP

第一版应用端 MVP 定为最短闭环：

1. 创建或编辑一个 `SimulationInput`。
2. 选择角色、武器和基础圣遗物构建。
3. 编辑按键输入轨迹。
4. 运行一次仿真。
5. 保存完整仿真结果数据。
6. 查看摘要结果。

第一版 MVP 暂不强制包含：

- 完整战斗复盘。
- 参数扫描。
- 多结果对比。
- 配置模板库。
- 复杂 UI 工作区。

这些能力作为后续阶段扩展，并以当前模拟输入契约为基础。
