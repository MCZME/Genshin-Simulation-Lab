## 2. 已确认决策

### 2.1 产品方向

- 新项目核心仍然是仿真引擎。
- 应用端从简单伤害计算器扩展为更广义的分析工具。
- 分析能力围绕仿真结果、战斗复盘、参数扫描和结果对比逐步展开。

### 2.2 技术与项目管理

- UI 继续使用 Flet，但具体 UI 方案暂缓设计。
- 新项目采用单仓库单包。
- Python 包名暂定 `genshin_sim`。
- 使用 `src/` 布局。
- 使用 `uv` 管理项目。
- `pyproject.toml` 作为项目配置入口。
- 质量工具确定为 `ruff`、`pyright`、`pytest`。

### 2.3 数据源

- 新项目数据库统一使用本地 SQLite。
- 静态资产库使用 SQLite，作为正式运行时携带的只读生成产物。
- 运行期结果库使用 SQLite，并与基础资产库职责分离。
- 基础资产数据来源确定为 Project Amber / Yatta 当前默认数据。
- 已实现 `infrastructure/assets_project_amber/` 源站适配层，用于抓取开发期 raw JSON cache 并转换为标准资产 manifest。
- 资产数据构建流程确定为 `genshin-sim assets fetch-source` -> `genshin-sim assets build-manifest` -> `genshin-sim assets audit-manifest` -> `genshin-sim assets build --manifest` -> `genshin-sim assets validate`。
- 原 MySQL 服务器已销毁，新项目不再依赖旧 MySQL。

### 2.4 基础资产数据库

- 资产库作为只读生成产物存在。
- 不设置 `raw_assets` 表。
- 采用结构化索引表与 JSON Payload 混合模型。
- `asset_key` 使用 `{asset_type}:{source_id}` 格式。
- `handler_key` 与 `asset_key` 分离，用于绑定仿真代码实现。
- 真实资产若尚无行为实现，`handler_key` 默认保持为空；`generic.noop` 与 `generic.test_*` 只用于测试或占位，不代表真实机制已经实现。
- 技能倍率使用 `scaling_json`。
- 武器、天赋、命座、圣遗物等复杂效果使用 `params_json`。
- `sim-core` 不直接访问 SQLite，而是依赖 `AssetRepository` 协议。

详细方案见：[资产数据库设计总结](../契约/资产数据库设计.md)。

### 2.5 基础资产范围

- 角色、武器、圣遗物等数据进入基础资产数据库。
- 敌人基础抗性/等级信息不接入基础资产数据库。
- 多语言文本第一版不纳入基础资产数据库。
- 复杂机制行为由仿真代码实现；数据库只保存参数和处理器标识。

### 2.6 模块边界

新项目在 `src/genshin_sim/` 下采用以下顶层模块：

- `core/`
- `content/`
- `assets/`
- `infrastructure/`
- `application/`
- `analysis/`
- `ui/`
- `cli/`

核心原则：

- `core/` 是纯仿真运行时核心，不依赖数据库、UI、应用层或具体内容实现。
- `content/` 保存具体角色、武器、圣遗物和 handler 实现。
- `application/` 负责编排 UI/CLI、资产库、内容实现、仿真核心、结果库和分析能力。
- `infrastructure/` 保存 SQLite、文件存储、日志等具体技术实现。
- `analysis/` 负责结果加工、聚合、对比和报告模型。
- `ui/` 作为 Flet 入口，通过 `application/` 调用能力；具体 UI 设计暂缓。
- `core/space` 使用统一的轻量空间实体表示当前场上角色空间实体与多个简单目标点位；内容创建空间对象运行态也归入 `core/space`，并复用 `core/entity_states/lifecycle.py` 的通用生命周期值对象；目标不在空间层建模复杂体型、多 hitbox 或碰撞。
- 按键输入事实在组装阶段由 `InputTraceCompiler` 配对为不可变 `InputSessionPlan`；`ActionManager` 按帧处理 PRESS、RELEASE、派生 HOLD 和 CANCEL。完整计划中的未来 release 不向解释器提前暴露。
- 不再保留 `TeamActionController`。`ActionManager` 统一拥有运行时输入会话、解释器调用、动作准入、具名锁、动作实例和生命周期；它通过 `ActionInterpreterRegistry` 路由输入，不硬编码切人键或具体角色动作含义。
- 动作是否发生、动作类型和动作开始帧由输入会话固定绑定的队伍或角色解释器决定。解释器只返回 `ActionInterpretationResult`、`PreparedAction` 或语义化控制命令，不直接修改动作实例或提交动作状态。
- 元素战技与元素爆发解释器通过显式 `CharacterAbilityConditionPort` 查询冷却与标准元素能量公共条件，再判断 content 私有状态和专属资源；`ActionManager` 仍负责锁、中断、会话和实例创建的最终准入。
- 所有 Action 在组装阶段注册到 `ActionRegistry`；解释器只返回稳定 `action_key` 和准备参数。`ActionManager` 获取不可变 Action 定义后创建 `ActionInstance`，实例持有本次动作的可变 `action_state`。
- 所有被接受的动作都创建 `ActionInstance`，包括切人。切人由 `TeamActionInterpreter` 准备 `TeamSwitchAction`，再由动作实例修改 `TeamRuntimeState` 并同步 `player:active`，不再由 SpaceRuntime 动作消费器执行。
- HOLD 始终先交给原输入会话绑定的解释器；解释器可以继续等待、启动动作或返回控制已有实例的语义命令。ActionManager 同时独立逐帧调用 Action 推进动作运行态。
- 动作冲突不再使用单一全局 busy。Action 声明具名锁和中断策略，ActionManager 完成最终准入检查，并在全部冲突可中断时原子取消旧实例和创建新实例。
- 解释器不得回溯生成开始帧早于当前仿真帧的动作请求；真实角色缺少解释器或其声明的 Action 时应在组装阶段报错。
- `Space` 保存 `player:active`、`target:*` 与内容创建实体的空间实体；`TargetRuntimeCollection` 由 `SpaceRuntime` 持有并管理多个简单目标运行态；`TargetRuntimeState` 第一版只保存 `scene.targets` 已有的目标 id、等级、抗性和空间实体关联，不引入生命值、韧性、元素附着等尚未确认的机制状态。
- `core/` 不保留独立 `summons` 模块。游戏语义上的召唤物、场地物或临时造物若存在于战场空间中，应作为带生命周期的空间实体处理；无空间位置的持续逻辑归机制、状态或 hook。
- Action 在运行过程中产生 `ActionImpactPoint`。动作索敌只负责选择瞄准目标与攻击方向；伤害 Impact 到期时再由 `ImpactRuntime` 按实际 AOE 和当前空间状态解析全部受击目标。
- Action、Reaction、周期状态和空间实体产生的伤害统一进入 Damage Impact 流程；Reaction 不直接构造 `DamageRequest`，也不拥有独立伤害结算入口。
- `ImpactFactory` 接收 `ActionImpactContext` 并展开为真实 `ImpactRequest`，不再使用 `ImpactRequest(kind=action)` 作为临时入口；反应生成的 Damage Impact 由元素结算协调器在下一 settlement round 交给同一 Impact 目标解析与机制分发流程。
- `content` registry 第一版按角色、武器、圣遗物和 impact 拆分专用 runtime request 与创建入口，不保留泛化 `RuntimeHandlerRequest`。
- `SimulationAssembler` 通过 `ContentUnitRegistry` 编译 `ContentUnit` 并构造 `RuntimeContentBundle`，再拆分注入 `ActionInterpreterRegistry`、`ActionRegistry`、`CharacterAbilityConditionCoordinator`、解释上下文 provider、`ImpactDispatcher`、`ImpactRequestDispatcher`、`ActionManager`、`ImpactRuntime`、`CreatedObjectRuntime`；内容专属状态由 `ContentStateMount` 挂载在 `CharacterRuntimeState.content_states`；`core/` 不接触完整内容单元对象。
- 当前 content 验证阶段只确认“资产 -> `handler_key` -> content unit -> runtime 注入”的装配链路，不验证真实伤害、治疗、Buff、反应或属性修饰数值。

详细方案见：[新项目模块边界设计](../架构/模块边界设计.md)。

### 2.7 仿真快照与结果库

- 新项目允许 `sim-core` 生成快照。
- 快照用于复盘、审计、分析和调试。
- 快照不是资产数据，也不是项目配置文件。
- 快照生成属于 `core/`，快照持久化属于 `infrastructure/`。
- 运行期结果库与基础资产库职责分离。
- 所有仿真都保存完整结果数据，不区分 `summary_only` 与 `recorded` 模式。
- 运行期结果库参考旧项目中较完善的 SQLite 持久化、事件流与投影表方案，按新模块边界重新落位和整理。

### 2.8 重设计与参考迁移分层

旧项目能力按以下方式处理：

- 资源数据库：重新实现。
- 模拟架构中的按键输入与动作解释：重新设计并重新落位。
- UI：完全重设计。
- 其余游戏逻辑：保留有价值的行为目标、算法思路和测试入口，按新边界、契约与验证要求参考迁移。
- “直迁”不再作为正式分类；旧代码即使可以局部复用，也不能绕过新架构和数值可信度要求。

能力覆盖与当前迁移工作流分别见：[旧项目能力盘点](../工程/旧项目能力盘点.md)和[迁移阶段安排](../工程/迁移阶段安排.md)。

### 2.9 日志系统

第一版日志系统采用 Python 标准库 `logging`，不新增第三方依赖。

已确认原则：

- `infrastructure/logging/` 保存日志配置、handler、formatter、输出路径和轮转策略。
- CLI 与 UI 作为入口负责初始化日志。
- 其他模块只使用标准库 `logging.getLogger(__name__)`，不依赖 `infrastructure/logging`。
- 工程日志不替代 `core/events`、快照或结果库。
- 日志配置不进入 `SimulationConfig`。

详细方案见：[日志系统设计](../架构/日志系统设计.md)。

### 2.10 领域运行态与共享抽象

有身份和生命周期的运行态由对应 `core/systems/<domain>/` 直接拥有：

- 每个领域直接定义强类型实例引用、完整记录、生命周期、索引、命令、计划和提交入口。
- 护盾由 `ShieldStore` 原子拥有完整 `ShieldRecord`，不再拆分为全局实例 Store 与能力组件 Store。
- `source_context`、`creator_ref` 和领域 affected scope 使用不同语义，废弃含义模糊的通用 `owner_ref`。
- capability 是领域 Runtime 暴露的类型化只读协议，不是实例上的单一字符串字段。
- Buff、冷却、ICD 和元素附着分别设计自己的状态模型；不能为了复用护盾记录而进入通用 Store。
- 只有至少两个已实现领域证明了相同不变量，才提取中立值对象或提交工具，不因字段相似预建共享模块。
- 状态先按领域计划提交，事实后发布；事件回调不能同步写入当前结算。

技术边界见[领域运行态设计](../架构/领域运行态设计.md)；所有原神游戏机制的设计、数值可信度和验证要求见[原神游戏机制实现规范](../工程/原神游戏机制实现规范.md)。

### 2.11 属性与伤害
- 属性采用确定性查询与解析，不保存可任意修改的最终面板：公共属性由 `core/attributes` 封闭定义，content 只注册私有属性；modifier 以结构化 term 固定阶段贡献；当前生命、能量、Buff、冷却、附着等运行态不作为普通公共属性。
- 伤害统一走 Damage Impact：先经 Space 解析实际 AOE 目标，再逐目标构造单目标 `DamageRequest`；主攻击标签经 `DamageProfileRegistry` 选择 Profile 并映射公式，`DamageType` 不作为 content/Reaction 显式填写的字段。
- `elemental_amount=0` 仍可造成元素伤害但不产生元素施加；正元素量经 ICD 后与目标 Aura 决定反应；`strike_type=BLUNT` 是碎冰的稳定攻击侧证据。
- 通用公式固定倍率、增伤、暴击、反应、防御和抗性区；调试倍率通过 `DebugDamageAdjustment` 构造注入，生产默认 `1.0`，content 不得使用。
- 角色伤害由角色受伤协调器应用到护盾和血量，协调器不参与或反馈伤害计算。

详细见[属性系统设计](../架构/属性系统设计.md)、[属性系统契约](../契约/属性系统契约.md)和[伤害系统设计](../架构/系统/伤害系统设计.md)。

### 2.12 生命、治疗、护盾与受伤协调
- 生命：角色当前生命由 `CharacterHealthStore` / `HealthRuntime` 拥有，只接受角色主体；最大生命来自 `stat.hp.max`；有效变化发布事件，满血恢复、零伤害和完全阻止的扣血不发布。
- 治疗：理论结算与生命提交分层，`HEALING_RESOLVED` 先于提交发布；`HealthRuntime` 是当前生命唯一受控写入口。
- 护盾：`ShieldStore` 以完整 `ShieldRecord` 聚合拥有；创建帧快照公式属性，动态护盾强效在承伤帧查询；多盾基于同一承伤前快照扣减，穿透取单盾可保护来伤量的最大值。
- 受伤协调：`CharacterDamageTakenCoordinator` 只编排护盾与血量计划，预校验后无回调提交；`DAMAGE_APPLIED` 表示正伤害目标是角色（即使被完全吸收），`CHARACTER_HEALTH_CHANGED` 只表示血量实际减少；直接扣血和流血不进入协调器。

详细见各系统设计/契约与[角色受伤协调器设计](../架构/协调/角色受伤协调器设计.md)；护盾剩余工作见[护盾系统后续实现计划](../工程/护盾系统后续实现计划.md)。

### 2.13 系统自治与跨系统协调
- `core/systems/<domain>/` 只拥有本领域状态、公式、计划、写入口和领域事实；领域系统不依赖其他领域的具体 Runtime 或 Store。
- 跨 Store 写入由 `core/coordination/<flow>/` 写协调器统一准备、预校验、无回调提交并按契约发布事实；只读协调器只能组合领域条件和校验证据。
- coordinator 不拥有长期领域状态，不实现领域公式，也不充当全局万能 pipeline；EventEngine 只发布和记录已提交事实。

正式决策见[系统自治与跨系统协调](./系统自治与跨系统协调.md)。

### 2.14 状态效果（Buff）系统架构
- `core/systems/buff/` 直接拥有有限时长 Buff/Debuff/状态标记的定义、完整记录、Store、应用策略、生命周期与领域事实；第一版支持 replace、refresh、stack refresh 和 coexist。
- 属性 provider 在组装阶段固定注册，查询无副作用；直接或间接改变 `stat.hp.max` 的 Buff 在第一版组装阶段拒绝。
- 事件触发、周期 tick、动态场上角色作用域等按真实内容单独升级契约，不进入万能 callback 框架。
- 第一版工程闭环已落地；真实 Buff golden case 因缺少可信资料仍待补充，测试 content 不代表真实机制完成。

详细见[状态效果系统设计](../架构/系统/状态效果系统设计.md)和[状态效果系统契约](../契约/状态效果系统契约.md)。

### 2.15 能量、冷却与能力条件
- 能量：`EnergyRuntime` 是元素能量唯一写入口；微粒/晶球以在途记录调度，同元素/无元素/异元素倍率 `3/2/1`，四人/三人/二人队后台倍率 `0.6/0.7/0.8`；标准爆发扣能入口与只读条件已提供，`cost=0` 的专属资源角色不走普通元素能量。
- 冷却：`core/systems/cooldown/` 拥有充能次数、串行恢复、时长解析与修改命令；真值使用整数帧 `ready_frame`，查询不推进时间；效果自身触发 CD 与附着 ICD 不进入该 Store。
- 条件协调：`CharacterAbilityConditionCoordinator` 是只读协调器，返回逐项领域证据和全部稳定阻塞原因；E 只要求冷却，标准 Q 要求冷却加满能量，私有资源条件委托 content；动作解释器只依赖 `CharacterAbilityConditionPort`。

详细见[元素能量系统设计](../架构/系统/元素能量系统设计.md)、[冷却系统设计](../架构/系统/冷却系统设计.md)和[角色能力条件协调器设计](../架构/协调/角色能力条件协调器设计.md)。

### 2.16 元素附着、ICD 与反应架构
- 真值来源：元素机制以项目维护者确认的资料为真值；AI 查询、旧代码和第三方实现不得单独成为正式规则。
- Aura：逐来源贡献账本是元素量与贡献归属的唯一真值，`current_amount` 只是投影；标准强度档位（弱/中/强/超强）与衰减已固定；Aura 不进入 `TargetRuntimeState`。
- ICD：只拥有附着冷却的 Definition、Binding 和限时序列；按攻击者、目标、标签、组别四维 Key；结果是精确元素量系数而非布尔，系数 `0` 仍推进游标但阻止施加。
- Reaction：定义、候选、状态、Gate 与资源由 reaction 领域拥有；content 只提供类型化意图和能力证据；复合候选由公共组件拥有，机制目录不得互相调用。
- 协调器：Aura/ICD/Reaction 通过隔离 BatchPlanner 准备、统一校验并无回调提交，原子性止于一个 `ElementalInteractionBatch`；后续工作走强类型工作队列（单 root 最大轮次 `64`），不使用 Event 回调。
- 事实收敛为 `REACTION_OCCURRED`、`REACTION_STATE_CHANGED` 和 `REACTION_RESOURCE_CHANGED` 三类通用事件。

详细见[元素反应架构文档索引](../架构/系统/元素反应/文档索引.md)、[元素反应协调器设计](../架构/协调/元素反应协调器设计.md)和[元素附着、ICD 与反应设计规范](../工程/元素附着、ICD与反应设计规范.md)。

### 2.17 元素反应契约冻结
- 普通反应由本次元素、ICD 后实际元素量和目标 Aura 决定；碎冰额外读取稳定 `strike_type=BLUNT` 证据，来源种类、武器显示类型和布尔“允许反应”开关不参与。
- 反应处理当前 Impact 时只能调整该 Impact 已携带的关联伤害；新增伤害一律成为同帧下一 settlement round 的子 Damage Impact。
- 增幅/剧变：Profile 拆为 `AmplifyingReactionProfile | TransformativeReactionProfile` 强类型联合；超载、超导使用独立稳定 key 与 Gate，effect group 在下一 settlement round 执行。
- 燃烧：普通燃烧火草建立时创建 `2 GU` 燃元素与 `BurningState`；周期火每 `15` 帧造成 `0.25` 倍率火元素剧变伤害，普通火每 `120` 帧施加 `1 GU`，不进入 Aura ICD。
- 激化：原激化按草雷 `1:1` 实际消费创建 `QUICKEN`；超激化/蔓激化不消费激元素，使用独立公式 `damage_formula.catalyze_additive`，倍率 `1.15/1.25`，精通公式已固定。
- 绽放：普通绽放/绽放爆炸/超绽放/烈绽放，水与类草 `2:1` 消费；草原核持续 `360` 帧、每队最多五枚，容量淘汰引爆最老核心；`bloom_family` 共享 `30` 帧两次 Gate，三种伤害分类独立。

各反应稳定字段、key 和验收入口见[元素反应契约文档索引](../契约/元素反应/文档索引.md)下的对应设计/契约。

### 2.18 月反应独立契约冻结
- 月绽放：独立 `ReactionKey`、handler 与方向，capability 准入加严格水草签名，排他替代普通绽放；反应本身不产生伤害，草露由 ReactionStore 拥有，角色月曜伤害走 `CHARACTER_DIRECT`；生产公式已注册。
- 月感电：独立 key 与严格水雷签名，排他替代普通感电；occurrence 不消费水雷（后手按 `20%` 损耗保持共存）；`LunarStormCloudState` 生命周期 `360` 帧、每 `15` 帧攻击、逐目标 Gate 并消费 `0.4 GU`；复合月曜伤害按 `0.60/0.30/0.05` 加权。
- 月结晶：独立 key 与严格水岩签名，只替换水结晶方向；场上最多三枚月笼、共享累计器、每三次月结晶触发一次谐奏；谐奏复合月曜伤害不产生元素附着。
- 三条月反应均已有生产 bootstrap 与 golden case；未确认项（可回放随机、岩造物干扰、精确倍率等）记录在正式契约，不改变生产注册状态。

详细见[月绽放反应设计](../架构/系统/元素反应/反应/月绽放反应设计.md)、[月感电反应设计](../架构/系统/元素反应/反应/月感电反应设计.md)、[月结晶反应设计](../架构/系统/元素反应/反应/月结晶反应设计.md)及对应契约。

### 2.19 动作、空间与移动
- 动作系统升格为正式架构与契约：解释器边界、动作注册/绑定、准入/锁/中断、实例生命周期、影响点与位移契约统一收编；Damage Impact 与 AOE 解析由伤害系统和战场空间文档拥有。
- AOE/索敌语义：资料表“球”是实际攻击范围、“圆柱”是索敌范围；运行时按分数（距离，并列取稳定实体 id 较小者）选最近目标为锚点展开球 AOE，当前 X/Z 模型投影为同半径圆，高度暂不参与查询。
- `TimedActionSpec` 支持多影响点；`CreatedObjectSpec` 支持多 tick 调度与 `follow_entity_id`，旧单调度字段保持兼容。
- `SpatialEntity` 新增 `collision_box`（默认圆柱），仅参与 MovementSystem 下坠碰撞判定；普通 AOE 命中仍只使用 X/Z。
- `core/systems/movement/` 唯一拥有实体垂直运动状态（高度、速度、重力），落地/碰撞以事实发布；下落攻击改为事件驱动（`FallPlungeAction`），推翻“动作独占位置写入口”的旧结论。
- 法器通用下落攻击数据已接入 `generic/plunge.py`；低空/高空线与重力的时序数值仍为临时值，待统一资料确认后替换。

详细见[动作系统设计](../架构/动作系统设计.md)、[动作系统契约](../契约/动作系统契约.md)和[战场空间设计](../架构/战场空间设计.md)。

### 2.20 内容与运行时接线

## 3. 待讨论事项

### 3.1 应用端 MVP

第一版 MVP 定为最短闭环：

- 创建或编辑一个 `SimulationConfig`。
- 队伍/角色构建配置。
- 按键输入轨迹编辑。

- 保存完整仿真结果数据。

- 完整战斗过程复盘。

- 多结果对比。
