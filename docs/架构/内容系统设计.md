# 内容系统设计

> 状态：当前生效架构。
> 本文描述 `content/` 层的稳定职责、内容单元模型，以及与 `core/`、`application/assembly` 的边界。
> 构建阶段与失败边界见第 2.1 节；效果、动态条件与 generic 构成见第 5–7 节；运行模型契约见第 10 节；暂定决策与未决事项见第 14–15 节。
> 包目录、导出风格与 `version` 工程写法见 `docs/工程/内容/` 下已确认约定。

最后更新：2026-08-31。

## 1. 定位

`content/` 是具体游戏内容的行为实现层。它把资产静态数据与核心通用运行时接口连接起来，在组装阶段产出可注入的运行时贡献。

### 1.1 目标

- 通过 `handler_key` 绑定具体内容实现。
- 保存角色、武器、圣遗物、通用影响、状态和修饰等行为代码。
- 为动作系统提供角色动作解释器与 Action 定义。
- 为对应领域系统提供影响展开、修饰、Buff 定义与事件钩子等贡献。
- 在内容编译阶段产出 `ContentUnit`，由 `application/assembly` 注入运行时。

### 1.2 非目标

- 不读取 SQLite，不解析用户配置文件。
- 不创建 `SimulationAssembler`，不控制模拟器帧循环。
- 不直接写结果库或 UI。
- 不把具体角色、武器、圣遗物逻辑放进 `core/`。
- 不拥有或注册全局元素反应 Definition、Rule、状态和资源；这些由 `core/systems/reaction/` 负责。

角色、武器和圣遗物可以产生类型化命中、元素施加意图或能力证据，但不能自行判断目标触发哪种反应，也不能直接修改 Reaction Store。

## 2. 装配链路

```text
SimulationInput
-> AssetRepository 读取资产数据
-> handler_key 查找 content factory
-> content factory 创建 ContentUnit（身份 + 编译参数 + 能力切片 + 状态 schema）
-> application/assembly 编译并聚合内容单元，构造 RuntimeContentBundle
-> 拆分注入 Action / Impact / Hook / Modifier / 属性 / Buff 等运行时对象
-> core 只通过通用协议调用
```

分层职责：

| 层 | 职责 |
| --- | --- |
| `assets/` | 静态数据与 `asset_key` |
| `content/` | 行为代码与 `handler_key` 实现（产出 `ContentUnit`） |
| `application/assembly` | 读取资产、调用内容单元工厂、编译并拆包注入 |
| `core/` | 通用协议、领域运行时与结算 |

缺资产、缺 handler、JSON 格式错误或 handler 参数不合法，应在组装阶段失败，不延迟到仿真运行中。

### 2.1 构建阶段与失败边界

一次仿真顶层流程：输入 -> 构建 -> 模拟 -> 结果。

构建阶段拆成三步骤，组装内部再拆两步：

```text
配置转化 -> 数据查询 -> 组装
组装 = 内容编译 -> 运行时装配
```

阶段模型与产出：

| 阶段 | 产出 |
| --- | --- |
| 配置转化 | 规范化 `SimulationInput` |
| 数据查询 | `RuntimeAssetBundle` |
| 内容编译 | `ContentUnit` / `RuntimeContentBundle` |
| 运行时装配 | `AssembledSimulation`（可运行世界） |

最早失败原则：配置错误在配置转化阶段报出，缺数据在数据查询阶段报出，缺 handler、
参数不合法、重复键、挂点非法在组装阶段报出；不延迟到模拟期。

## 3. 内容类型与贡献边界

### 3.1 角色

角色内容负责角色主行为，典型贡献包括：

- 动作解释器与 Action 定义
- 角色专属运行态
- 技能影响工厂
- 内容创建对象行为
- 天赋、命座与角色专属触发逻辑
- 角色专属修饰与属性/伤害 provider
- 静态 `reaction_capabilities` 声明

角色内容不读取资产库、不推进帧循环、不写结果，也不绕过通用动作与领域系统直接结算。

### 3.2 武器

武器内容负责武器被动与相关行为，典型贡献包括：

- 静态或条件属性修饰
- 触发器 / event hooks
- 影响请求修饰或特定影响工厂

武器不提供角色动作解释器，不贡献内容创建对象行为，也不能通过修饰器或触发器改变动作解释结果。武器只影响属性、事件响应、影响请求和后续机制结算。

### 3.3 圣遗物

圣遗物内容负责套装行为与参数化机制，典型贡献包括：

- 套装属性修饰
- 条件 Buff
- 触发器 / event hooks
- 影响请求修饰

圣遗物同样不提供动作解释器，不贡献内容创建对象行为，不改变动作解释结果。

首个真实套装实现为「被怜爱的少女」（`artifact.maiden_beloved`）：2 件套
静态治疗加成，4 件套施放战技/爆发后 10 秒内全队受治疗加成 Buff。

### 3.4 通用内容

`generic` 用于可复用的基础影响、状态、修饰或测试占位实现，例如：

- 通用静态修饰
- `generic.noop` / `generic.test_*`
- 可复用的 Buff 或 impact 展开逻辑

通用内容不替代真实角色、武器、圣遗物实现，也不作为真实机制已完成的标记。

## 4. 运行时贡献模型

### 4.1 ContentUnit

内容编译的产出模型是 `ContentUnit`，定义在 `content/definitions/content_unit.py`。
它不属于 `core/`，也不属于 `application/`。

概念结构：

```text
ContentUnit
├── owner_type / owner_key / handler_key / version / slot
├── compiled_params（已解析为确定值的编译参数）
├── 能力切片
│   ├── action_interpreter? / actions
│   ├── effects（命座、天赋、被动、套装、精炼的统一效果定义）
│   ├── state_schema?（宿主内容状态形状）
│   ├── impact_factories
│   ├── created_object_behaviors
│   ├── event_hooks / modifiers
│   ├── attribute_definitions / attribute_stacking_groups / attribute_providers
│   ├── talent_level_boosts / cooldown_duration_terms
│   ├── buff_definitions / cooldown_definitions
│   ├── aura_icd_definitions
│   ├── damage_modifier_providers / damage_modifier_stacking_groups
│   ├── reaction_capabilities
│   └── mount_points
└── metadata
```

规则：

- 内容定义全局共享、不可变；运行期每宿主只持有轻量挂载实例，状态只存在于
  宿主状态容器。
- `version` 是内容当前状态标签，语义与写法见[内容版本约定](../工程/内容/内容版本约定.md)。
- `slot` 绑定队伍槽位；角色内容单元必须提供 `slot`。
- `action_interpreter` 与 `actions` 只由角色内容单元贡献；解释器应无实例可变
  字段，动作进度经 `state_patch` 意图提交宿主状态容器。
- `impact_factories` 将 `impact_key` 展开为 `ImpactRequest`，不负责最终数值结算。
- `created_object_behaviors` 仅由角色内容贡献。
- `cooldown_definitions` 是强类型 `CooldownDefinition` 切片，装配器据此创建
  冷却定义与运行态；`aura_icd_definitions` 是内容声明的自定义元素附着 ICD
  定义，装配时与标准/无冷却定义一起注册进 `AuraIcdRuntime`。
- `talent_level_boosts` 是编译期静态贡献（天赋键 -> 等级提升，如命座 +3），
  在内容编译阶段按解锁过滤后与配置天赋等级合并，生成有效等级；
  `cooldown_duration_terms` 按 `CooldownKey`（角色主体 + 能力键）声明冷却
  时长修正 term，编译后挂到对应定时动作，随
  `StartCooldownRequest.duration_terms` 进入冷却解析。
- `reaction_capabilities` 只由角色内容声明；`application/assembly` 将其转换
  为核心层证据，content 不直接创建 Reaction 运行时对象。

### 4.2 拆包与注入

- `application/assembly` 调用 `ContentUnitRegistry` 工厂，收集 `ContentUnit`，再构造 `RuntimeContentBundle`。
- bundle 拆分出动作解释器、Action、impact factory、创建物行为、hooks、属性定义/provider、Buff 定义、伤害 provider 与 `StateContainerRegistry` 等。
- `core/` 不接触完整 `ContentUnit`，只接收拆分后的通用协议实现。
- `content` 不依赖 `application`。
- `core/` 不 import `content`，也不认识 `RuntimeContentBundle`。

### 4.3 内容专属状态

有身份的内容专属运行态由 `ContentStateMount` 挂载在
`CharacterRuntimeState.content_states` 下：编译期按内容单元 `state_schema`
实例化每宿主挂载，挂载 owner 与角色 `combat_entity_id` 一致；
解释器、hook 与写入路径均以宿主 `content_states` 为唯一真值；
不再有独立的注册表索引（`StateContainer` / `StateContainerRegistry` 已随
M6 删除）。

状态 schema 契约与片段合并（`StateField` / `StateSchema` /
`StateSchemaFragment` / `merge_state_schema_fragments`）统一定义在
`core/contracts/state_schema.py`，core 与 content 共用；内容层不再有
独立的 state_schema 模块。

写入唯一通道是 `state_patch` 意图（统一意图队列，载荷带 `handler_key`
作为 `state_key`），读取为宿主挂载的只读视图；hook 的 `state_patches`
只能描述自己 owner 与自己 `state_key` 的变更，跨宿主或跨状态段写入在
分发阶段确定性报错。

规则：

- 只有对应 owner 的 content 能写自己的 state。
- 武器、圣遗物第一版不能直接写角色专属 state。
- 状态值必须 JSON 兼容；帧末经 `content_state` 快照 provider 导出，进入
  `SimulationSnapshot`。
- 快照只序列化宿主状态，不序列化共享内容定义。

## 5. 效果 Effect

效果是命座、天赋、被动、套装效果、精炼效果的统一抽象。

生命周期：

```text
EffectSpec（数据 + 配置）
   ↓ handler_key 绑定
handler（编译期实现入口）
   ↓ handler.compile(...)
行为切片集合
   ↓ 运行时装配
挂到阶段管线的运行时对象
```

- 静态解锁条件在编译期判定：`constellation >= C`、`set_pieces >= n`、
  `refinement >= r`、`talent_level >= n`、`always`；不通过的效果不进入运行时。
- 动态条件不放在 `EffectSpec` 中，而是内嵌在行为切片内（见第 6 节）。
- 行为切片：`modifiers` / `damage_modifiers` / `healing_modifiers`、
  `buff_definitions`、`initial_state_contributions`、`hook_subscriptions`、
  `intent_generators`、`state_schema_fragments`、`parameter_rewrites`。
- 当前已接线的最小闭环：资产 `effect_payloads`（params + unlock_key +
  handler_key）-> effect handler 工厂 -> ContentUnit 行为切片 -> 运行时
  bundle。每个效果的 `handler_key` 直接来自资产；已实现效果贡献
  `event_hooks` 切片并在 ContentUnit.effects 上保留 EffectSpec 声明，
  空实现/未实现效果由带 `HandlerImplementationStatus` 标记的空实现消费
  （编译通过但不贡献行为），未添加的效果保持 `*.unimplemented_*` 占位键。
- 解锁条件由效果 handler 在代码实现中直接声明（`EffectSpec.unlock`），
  不解析资产 `unlock_key`；`unlock_key` 仅作为资产侧效果位置元数据保留。
  解锁在第 0 帧初始化时求值（事件 hook 运行时按宿主突破阶段、命座与天赋
  等级判定），组装阶段不解锁；`UnlockKind` 当前支持 ALWAYS、ASCENSION、
  CONSTELLATION、SET_PIECES、REFINEMENT、TALENT_LEVEL。

编译顺序固定为：同一槽位先编译效果单元 -> 静态解锁过滤 -> 收集静态贡献
（`talent_level_boosts` / `cooldown_duration_terms` / 属性 provider）-> 计算
有效天赋等级 -> 编译角色单元（倍率/数值/动作）-> 展开各效果的运行期行为
切片（事件 hook 仍由第 0 帧初始化解锁求值）。

静态贡献与运行期行为分开：`talent_level_boosts`、`cooldown_duration_terms`
与延迟绑定属性 provider 在内容编译/装配阶段收集注入；`event_hooks` 只响应
已发布事实。芭芭拉 C1–C5 已按该链路接入。

handler 术语：

- `handler` 只指编译期行为实现入口，通过 `handler_key` 绑定；运行期对象是
  具体切片/运行时对象（`ImpactFactory`、`EventHook`、`ModifierProvider`、
  `ContentStateMount` 等）。
- 共享 handler 一个实现服务多个效果；私有 handler 一个效果一个实现。两个以上
  内容复用同一形状才沉淀为共享 handler。
- generic 部件不带键，只表达形状与行为；内容包包装时传入内容级键。

## 6. 动态条件

条件不是独立运行实体，而是每个行为切片内置的只读纯谓词。按求值时机分四类：

| 种类 | 求值时机 | 挂载切片 |
| --- | --- | --- |
| 查询条件 | 修饰被查询时 | modifier provider |
| 事实过滤 | 事实发布后、响应前 | hook 订阅 |
| 意图门槛 | 意图生成时 | intent generator |
| 状态约束 | 状态提交时 | state schema |

规则：

- 条件输入只读：已提交领域状态（经窄端口）、事实载荷、owner 自己的内容状态。
- 条件求值禁止写任何东西；同一输入必须同一结果。
- 条件读取的是已提交状态，不是本轮计划中的状态。
- “条件从假变真需要激活”的场景用 hook 表达：订阅相关事实、评估谓词、产出
  意图；不建条件系统、不做条件激活事件、不做通用 if-then 脚本。
- 常用谓词沉淀为 generic 谓词库（`hp_ratio_above` / `hp_ratio_below`、
  `has_buff`、`stacks_at_least`、`is_active_character` 等），两个以上复用才入库。

## 7. generic 构成

两形态：

- A 构成部件：普攻骨架、天赋等级框架、命座挂载框架、谓词库——不注册、不带键，
  被内容编译调用；采用声明式 `GenericComponent(kind, params)`，内容包包装时
  传入内容级键。
- B 共享 handler：标准直伤、标准治疗、静态属性修饰等——注册，多个效果通过
  参数复用。

普攻与动作数据表：

- 每个角色只有一张动作数据表（如芭芭拉的 `BARBARA_ACTION_TABLE`），普攻段
  与重击、战技等独立动作统一用 `TimedActionSpec`
  （`generic/timed_action.py`）表达；稳定身份键、帧表与伤害数据留在角色包
  内容数据文件（如 `data.py`），资产库只放倍率/参数。
- 每个角色只有一个动作解释器，独占消费自己的动作数据表；普攻推进（末段后
  回第 1 段）与跨输入衔接按表内 transitions 实现。
- generic 提供统一动作编译 `build_timed_actions` 与连段状态 schema
  （`generic/chain_state.py`：`chain_last_action_key` /
  `chain_last_start_frame`）；解释器读已提交状态，经 `state_patch` 提交。
  当前已验证形态为芭芭拉动作表（单输入键/单输入种类、单段单命中）。
- `TimedActionSpec` 已支持多影响点（同一动作内的创建物、自附着、命中伤害
  等）与冷却开始帧；创建物支持多 tick 调度（一个场地物多个独立节奏）与
  跟随实体（每帧跟随当前场上角色等指定实体）。
- 创建物支持延长持续时间：`EXTEND_CREATED_ENTITY` 影响请求按实例累计
  延长预算（`max_extra_frames` 上限），只更新 `expires_at_frame` 并同步到
  空间；刷新（重放技能）创建物时实例预算归零。
- 伤害影响点：动作表声明 hit_frame / impact_key / targeting，影响点到期后由
  content impact factory 展开为带 `DamageImpactSpec` 的 DAMAGE 请求；普攻倍率
  由资产库 `TalentScalingEntry` 在内容编译期经 `ScalingCompiler` 编译为
  确定倍率项（芭芭拉普攻已按该链路接入）。倍率条目以（角色, 天赋, 具体文本）
  三元组定位，具体文本在该三元组内唯一，缺失、归属不符或重复在编译期报错。
  芭芭拉普攻与重击伤害数据（主攻击标签、打击/远近类型、元素量、ICD 序列/标签、
  AOE 与索敌）按已确认资料表补齐：运行时先按“分数”选择最近目标，再以该
  目标为锚点展开球 AOE（当前 X/Z 模型投影为同半径圆）；普攻绑定标准 ICD 序列与
  弱水附着，重击无 ICD，每次命中直接施加 `1 GU` 弱水。

天赋等级框架：

- `TalentLevelResolver`：配置天赋等级 + 编译期等级提升（C3/C5）-> 有效
  天赋等级并截断。
- `ScalingCompiler`：把资产 `TalentScalingEntry.level_table` 编译为指定等级
  的确定倍率项；运行期不查询倍率表。

命座挂载框架：

- `ConstellationDefinition`：key + 静态解锁 + generic 部件 + 参数/覆盖。
- `resolve_unlocked_constellations` / `mount_effects` 处理解锁、排序与挂载；
  effect_key 冲突在编译期失败。
- 真实命座效果由效果 handler 产出解锁声明与行为切片（`event_hooks` /
  `talent_level_boosts` / `cooldown_duration_terms` / `attribute_providers`）；
  静态贡献在编译期按解锁收集，事件 hook 仍由第 0 帧初始化解锁求值。

构成规则：

- 角色 `ContentUnit` = generic 部件组合 + 角色私有部件。
- generic 部件不允许出现角色数值；覆盖点必须显式声明。
- 部件组合冲突（重复 effect_key、状态字段冲突、覆盖点未声明）在内容编译期失败。

## 8. handler_key 与内容单元注册

`handler_key` 是代码绑定入口，不等于 `asset_key`。

```text
asset_key   = character:75
handler_key = character.furina
```

理解分档：

| `handler_key` | 含义 |
| --- | --- |
| 空（角色/武器/圣遗物套装） | 资产存在但未绑定代码条目；组装不创建 content |
| 唯一键 + `IMPLEMENTED` | 行为已实现 |
| 唯一键 + `EMPTY` | 空实现：效果可能不需要实现，代码已确认该状态 |
| 唯一键 + `UNIMPLEMENTED` | 需要实现但尚未实现 |
| `*.unimplemented_*`（`NOT_ADDED`） | 代码中尚未添加该效果 |
| `generic.noop` / `generic.test_*` | 测试或占位，只验证装配链路 |
| `character.*` / `weapon.*` / `artifact.*` 等真实实现 | 需要测试或 golden case 支撑 |

规则：

- `handler_key` 全局唯一，即使按内容类型分注册入口。
- 角色、武器、圣遗物、效果使用专用 request、factory、注册入口与创建入口：
  `CharacterContentUnitRequest` / `WeaponContentUnitRequest` /
  `ArtifactContentUnitRequest` / `EffectContentUnitRequest`，统一注册进
  `ContentUnitRegistry`。
- 效果 payload（资产 `EffectPayload`）经 `EffectContentUnitRequest` 走同一注册表。
- 组装按资产类型调用对应入口并强校验；角色 handler 不接收武器 request，反之亦然。
- 缺 handler、参数不合法、重复键在内容编译阶段报错（`MissingRuntimeHandlerError`
  或 `InvalidRuntimePayloadError`），不延迟到仿真运行中。

占位 handler 不代表真实游戏机制已实现。效果资产在代码未添加前使用
`*.unimplemented_*` 占位键；代码添加条目后资产侧改用唯一键，具体实现程度由
注册表标记说明。

### 8.1 测试内容与开发者模式

测试内容统一放在 `content/test/` 包（如 `content/test/characters/reaction_probe`），
与正式内容在目录上分离；测试 `handler_key` 统一使用 `testing.*` 命名空间
（如 `character.testing.test_a`），与正式键不可能冲突。

- 测试内容只在**开发者模式**下注册：`create_default_content_unit_registry(developer_mode=True)`
  追加调用 `content.test.register_test_content_units`；正常模式不导入测试包。
- 开关位于项目配置 `config.toml` 的 `[developer] enabled`，组装期读取；
  CLI 与 server 共用同一装配入口，切换后需重启进程（重建注册表与资产仓库）生效。
- 开发者模式同时叠加代码定义的测试资产（见[资产系统设计](./资产系统设计.md)），
  使测试内容走与正式内容完全相同的"资产 -> handler_key -> content"装配链路。
- `BUILTIN_NOOP_CONTENT_HANDLER_KEYS` 中的 `generic.test_*` 等 noop 占位键
  **不门控**：它们贡献零行为，只是 minimal 静态资产库的绑定目标。
- 测试内容本身**不设测试用例**：`content/test` 是测试脚手架与合成夹具，不是被测对象；不为该包代码设计单元、集成或 golden 用例，其正确性由使用这些夹具的正式内容与系统测试间接覆盖。
- 测试内容的倍率与行为不视为真实机制完成（见第 13 节验证要求）。

## 9. 与核心运行时的协作

### 9.1 依赖方向

```text
content -> core 协议与数据类
application/assembly -> content + core + assets
core 不依赖 content / application / assets 实现
```

`core` 定义协议与运行时容器，例如：

- `ActionInterpreter`、`Action`、`CharacterAbilityConditionPort`
- `ImpactFactory`、`ImpactRequest`、`ImpactDispatcher`
- 创建物行为与空间实体生命周期
- `EventHook`、`Modifier` 及领域 Runtime

`content` 提供具体实现；`application/assembly` 负责注入。

### 9.2 动作

```text
ActionManager
-> 按输入会话找到角色 ActionInterpreter
-> 解释 InputSessionView
-> E/Q 经 CharacterAbilityConditionPort 查询公共条件
-> 解释器继续判断 content 私有条件与资源
-> 得到 PreparedAction
-> ActionRegistry 取 Action 并创建 ActionInstance
```

解释器只产生通用动作语义，不直接创建 `ActionInstance`，不直接计算伤害。
角色能力条件协调器只组合冷却与标准能量等公共条件；content 不通过 contribution 持有具体 `CooldownRuntime` 或 `EnergyRuntime`。

### 9.3 影响结算

```text
ActionImpactPoint
-> ImpactDispatcher
-> content impact factory
-> ImpactRequest[]
-> ImpactRequestDispatcher
-> 对应领域系统或 CreatedObjectRuntime
```

content 可生成伤害、治疗、护盾、元素、创建实体等请求，但不做最终公式结算。

内容创建空间实体：

- 第一版只能由角色内容贡献
- 由动作影响创建，对象运行态与空间登记归 `core/space`
- 生命周期值对象复用 `core/entity_states/lifecycle.py`
- 无空间位置的持续逻辑不放创建物行为，而归机制、状态或 hook
- `core/` 不保留独立召唤物模块

### 9.4 hooks 与 modifiers

`event_hooks`：

- 只响应已发生事实
- 产出下一结算轮次的 `ImpactRequest`、领域命令或 owner state patch
- 不直接改 `RuntimeWorld` 或领域 Store
- 不改写输入解释、动作时间轴或取消窗口
- 经 `HookDispatcher` 挂到 `FACT_RESPONSE` 阶段，只消费本帧新增事实，结果
  转为下一轮统一意图；首个真实事件 hook（环存在期命中触发治疗）已按该链路
  落地；`modifier_commands` 尚未接线，产出即确定性报错
- `FRAME_STARTED` 是边界事件，按事件记录契约不进入 `frame_events`；订阅它的
  hook 由 `HookDispatcher` 在每帧事实分发后收到一次合成空 tick（同一帧多轮
  结算只分发一次），用于周期行为（如芭芭拉 C1 每 600 帧回能）

`modifiers` 与类型化 provider：

- 纯查询、无副作用
- 由对应领域系统聚合
- 不能改变动作解释结果
- 新伤害实现使用 `damage_modifier_providers`，不靠 `scope` 字符串猜测协议

## 10. 运行模型契约（content 挂点环境）

- 时间：统一整数帧，固定 60 帧/秒；秒级时长在编译期折算为帧，运行期无浮点
  时间累积。
- 帧 0：初始化全部发生在构建阶段；帧 0 只发布 `SIMULATION_STARTED` 并导出
  初始快照，不跑阶段管线、不处理输入与动作；领域系统不接受 `frame == 0`
  的普通意图。
- 阶段管线：帧开始 -> 时间推进（到期 -> 意图）-> 输入解释 -> 动作推进 ->
  结算轮次（可多轮：分发计划 -> 预校验 -> 原子提交 -> 发布事实 -> hook
  响应）-> 状态快照 -> 帧结束。到期先于输入与动作；同帧多轮设最大轮数上限，
  超过按确定性错误处理。
- 统一意图队列：所有变更走类型化意图队列（`impact` / `buff` / `cooldown` /
  `state_patch` / `action`）；稳定排序键为 frame -> 阶段 -> 轮次 -> 来源 ->
  id；跨系统计划由协调器预校验，提交阶段无回调、不允许业务失败，之后才发布
  事实；hook 只能读事实、产出意图。
- 快照：每帧提交完成后导出事件 + 各领域状态 + content 状态；帧 0 初始快照
  是复现基准。
- 结束条件：意图队列为空 + 无运行中动作 + 无待处理影响点 + 无活动实体/
  在途能量/冷却。

## 11. 多贡献汇合与处理归属

`content/` 对数值、状态、修饰和触发的职责是**定义并交出贡献**，不是具体处理多来源如何合并、互斥或仲裁。

已确认：

1. content 侧主要提供定义与贡献，例如属性修饰、伤害修饰、Buff 定义、impact factory、hook 声明。
2. 多个 content 贡献同时作用于同一属性、伤害修饰、Buff 或其他状态点时，由对应领域系统或既有协调器按自身规则处理。
3. content 不另设全局贡献优先级，例如“角色 > 武器 > 圣遗物”这类总排序。
4. `hook.priority` 只用于稳定排序，不升级为机制仲裁器。
5. 同 `handler_key`、同 `impact_key` 等注册键冲突，在组装期失败；不允许静默覆盖。

因此：

```text
content        -> 定义“有什么”
领域系统/协调器 -> 处理“怎么合并、怎么生效、怎么结算”
```

## 13. 验证要求

- 具体角色、武器、圣遗物机制需要可信来源或 golden case 支撑。
- 测试专用 content 可以验证装配与运行时连接，其倍率与行为不视为真实机制完成。
- 治疗、Buff、反应、能量、冷却等真实数值能力，仍按其领域契约与工程规范验收。

## 14. 暂定决策（可调整）

- 动态条件内嵌切片，不建独立条件系统。
- 编译顺序：参数改写 -> 数值编译 -> 行为展开。
- handler 双粒度：共享 + 私有。
- 运行期对象采用“共享不可变定义 + 每宿主轻量挂载实例 + 状态在宿主状态容器”。
- generic 部件不带键，内容包包装时传键并保留现有命名。
- 普攻骨架：角色唯一动作数据表 + 角色唯一动作解释器；generic 提供
  `TimedActionSpec`、`build_timed_actions` 与 `ChainState` 状态 schema。
- 同帧多轮结算（设最大轮数上限）。
- 内容状态第一版生命周期为战斗全程。

## 15. 未决事项

- generic 第一批正式能力名单：普攻 / 重击 / 天赋等级 / 命座各自的最小通用
  骨架，武器、圣遗物侧通用构成如何并列设计。
- 资产参数进入 content 的编译细则：天赋倍率、CD、能量等参数编译到哪一层，
  哪些必须在 factory 期冻结，角色私有参数与通用参数的表达方式。
- event_hook 进入正式 content 的门槛已部分落地：通用命令队列就绪后，首个
  真实事件 hook 已按“只读事实 -> 下一轮 Impact 意图”接入；允许的 hook
  模式与领域强类型命令/Buff 的分工继续按真实需求收敛。
- 圣遗物内部目录细分与武器类型目录的英文命名清单。
- 解释器状态与可快照性：哪些必须进入内容状态、哪些允许留在 interpreter
  临时字段、与快照 provider 的验收关系。
- UI “是否允许非正式版”的交互。
- 武器/圣遗物内容状态的宿主形态（挂在角色下含所有权限制，还是各自运行时对象）。
- `schema_version` 的版本演化语义。
- 运行期接线遗留：`PredicateContext.facts` 事实过滤谓词、`has_buff` 默认端口、
  modifier_commands 意图直出；天赋倍率与 `DamageScalingTerm` 的组件键映射已由
  芭芭拉普攻伤害切片落地（资产倍率表 -> `ScalingCompiler` -> `DamageImpactSpec`）。
