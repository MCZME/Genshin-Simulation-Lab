# 模块边界设计

> 状态：正式规范。
> 本文定义项目的顶层目录结构、模块职责、依赖方向与硬规则。
> 最后更新：2026-08-29。

## 1. 总体决策

- 单仓库双工程：`backend/` 为 Python 后端（Python 包 `genshin_sim`，使用 `src/` 布局与 `uv` 管理），`frontend/` 为 Web 前端（计划中）。
- Python 顶层模块（位于 `backend/src/genshin_sim/`）固定为：`core/`、`content/`、`assets/`、`infrastructure/`、`application/`、`cli/`、`server/`。
- 项目配置 `config.toml`（本地生成，git 忽略）与 `config.example.toml`（提交到仓库的模板）位于 `backend/`。
- 工作区数据目录由 `workspace.data_dir` 推导（默认 `data/`），子目录为 `inputs/`、`results/`、`exports/`、`templates/`、`workflows/`、`logs/`；资产库位于 `data/assets/`，不随 `data_dir` 搬迁。
- 目录约定见[结果存储系统规范](../工程/结果存储系统规范.md)，日志目录与命名见[日志系统设计](./日志系统设计.md)。

## 2. 总体依赖方向

核心原则：

```text
core            -> 运行仿真
content         -> 具体角色/武器/圣遗物实现
assets          -> 资产数据对象与仓库协议
infrastructure  -> 外部存储与具体技术实现
application     -> 用例编排与组装（含分析查询用例）
application     -> Python 后端唯一公开能力出口
cli / server    -> Python 后端入口适配
frontend        -> 浏览器客户端，通过 server 调用后端
```

依赖方向：

```text
ui / cli
  -> application
      -> core
      -> assets（数据对象）
      -> content（注册表与内容贡献）
      -> 仓库 / 写入协议
          <- infrastructure 实现（含分析查询执行器）
```

硬规则：

- `core/` 不能 import `assets`、`infrastructure`、`application`、`ui`、`content`。
- `assets/` 只保存资产数据对象、仓库协议与相关错误，不实现 SQLite 访问。
- `content/` 保存具体角色、武器、圣遗物和 handler 实现，可以依赖 `core/` 与 `assets/` 数据对象。
- `application/` 负责编排用例与组装，不直接编写具体 SQLite 查询。
- `infrastructure/` 保存 SQLite、文件存储、日志、任务执行等具体技术实现。
- `application/` 是 Python 后端唯一公开能力出口；`cli/` 与 `server/` 只能通过 `genshin_sim.application` 的公开接口调用能力。
- 唯一出口约束面向外部入口（`cli/`、`server/`、`frontend/`），不要求内部模块之间的调用都经过 `application/`；`core/` 不反向依赖 `application/`。
- `cli/` 与 `server/` 不得导入具体 repository、writer、job runner、`SimulationAssembler`、`Simulator`、content registry 或查询计划执行器；新增入口能力时，先在 `application/` 定义稳定用例与模型，再做入口适配。
- `application/` 公开出口不暴露可变 Store、数据库连接或具体基础设施对象。
- `frontend/` 通过 `server/` 提供的 HTTP API 调用 application 能力，不直接访问 SQLite 或组装仿真核心对象。

## 3. `core/`

`core/` 是纯仿真运行时核心，负责“怎么模拟”。它不负责数据来源、结果存储、UI 展示或具体游戏内容实现。

当前结构：

```text
core/
├── simulation/      # 仿真上下文、时钟、Simulator、帧阶段管线、意图队列与结算
├── events/          # EventType、payload、EventSpec、EventEngine
├── actions/         # 输入会话、ActionManager、动作实例与具名锁
├── impacts/         # 影响点、ImpactFactory、机制请求与请求分发
├── entity_states/   # 角色/目标运行态、生命周期、内容状态挂载
├── attributes/      # 属性解析器、属性面板快照与差异同步器
├── elements/        # 元素中立值对象与引用
├── contracts/       # 意图、帧阶段等跨系统中立契约
├── systems/         # 领域自治系统
├── coordination/    # 限定流程的跨系统协调器
├── space/           # 空间实体、范围查询与空间运行态
└── snapshots/       # 帧快照导出运行时
```

职责要点：

- `simulation/`：`SimulationContext`、`Simulator`、声明式帧阶段管线（`FramePipeline`）与统一意图结算；模拟器只负责帧循环、运行世界推进和终止条件。
- `events/`：结构化事件类型、payload、`EventSpec` 与 `EventEngine`；`EventEngine` 只发布和记录已经提交的事实，不作为跨系统写入或当前结算递归调用入口。
- `actions/`：按键输入会话、`ActionManager`、动作实例与中断/锁语义；不硬编码切人键或具体角色动作。
- `impacts/`：到期影响点、目标解析、`ImpactDispatcher` 与 `ImpactRequestDispatcher`；不解释输入、不管理动作实例。
- `entity_states/`：角色运行态、目标运行态、通用生命周期值对象和内容状态挂载；实体空间表达由 `space/` 承担。
- `attributes/`：查询式属性解析器（基础属性 + 修饰项 -> 值）、属性面板序列化与 `AttributePanelSynchronizer`。
- `systems/`：领域自治系统。当前领域包括 `damage`、`health`、`healing`、`shield`、`buff`、`cooldown`、`energy`、`infusion`、`aura`、`aura_icd`、`reaction`（含 `mechanics/` 各反应）、`resonance`、`moonsign`、`movement`。
- `coordination/`：只处理一个明确跨系统流程，当前包括 `character_damage_taken`、`character_ability_condition`、`elemental_reaction`、`resonance_reaction`；不拥有长期领域状态，不实现领域公式。
- `space/`：`Space`、`SpaceRuntime`、`CreatedObjectRuntime` 与 X/Z 平面范围查询；目标只建模简单点位，不做复杂体型、多 hitbox、刚体碰撞或目标挤压。
- `snapshots/`：统一导出链路 `Simulator -> SnapshotRuntime -> FrameSnapshot`；各领域 provider 由组装阶段注册，`core/` 只生成快照，不写库。

系统自治与协调外置的完整规则见[领域运行态实现规范](../工程/领域运行态实现规范.md)与[系统自治与跨系统协调规范](../工程/系统自治与跨系统协调规范.md)。

## 4. `content/`

`content/` 是具体游戏内容实现层，负责角色、武器、圣遗物、命座、天赋和复杂效果 handler，以及通用效果 handler 与队伍级内容。

当前结构：

```text
content/
├── __init__.py
├── bootstrap_content_units.py
├── registries.py
├── models.py
├── hooks.py
├── state_container.py
├── definitions/
├── characters/
│   └── mondstadt/barbara/
├── test/
│   └── characters/reaction_probe/
├── weapons/
├── artifacts/
├── generic/
└── team/
```

注册与组装规则：

- `handler_key` 是代码实现绑定入口；不使用显示名称或 `asset_key` 直接绑定行为。
- 每个内容模块提供显式注册函数，不依赖自动扫描和隐式导入。
- `content/bootstrap_content_units.py` 提供默认内容单元注册表（`create_default_content_unit_registry`）。
- 组装链路为：`资产 -> handler_key -> content contribution -> runtime 注入`；缺资产、缺 handler、JSON 格式错误在组装阶段报错，不延迟到仿真运行。
- `content/` 可以构造类型化领域请求和内容状态补丁，但不得直接写领域 Store，也不注册全局反应规则。

## 5. `assets/`

`assets/` 保存资产数据对象、仓库协议与资产相关错误（`models.py`、`repository.py`、`errors.py`）。

- 定义 `AssetRepository` 协议与 `CharacterAsset`、`WeaponAsset`、`ArtifactSetAsset`、成长曲线、效果 payload 等数据对象。
- 不负责 SQLite 查询、数据导入、具体角色行为或 UI 展示。
- 资产系统的分层、构建链路见[资产系统设计](./资产系统设计.md)；资产数据库与字段契约见[资产数据库设计](../契约/资产数据库设计.md)。

## 6. `application/`

`application/` 是用例编排层，负责连接 CLI/HTTP API、资产库、handler 注册表、`content/`、`core/` 运行时、结果库与分析查询用例。

当前结构：

```text
application/
├── __init__.py
├── errors.py
├── validation.py
├── input/          # 模拟输入契约与校验（SimulationInput）
├── config/         # 项目配置契约与校验（ProjectConfig）
├── assembly/       # 仿真组装（含 stages/）
├── execution/      # 同步执行原语、运行记录与失败写入
├── jobs/           # 任务模型、状态与调度器协议
├── services/       # 对外用例服务门面（含工作流 JSON 不透明存档）
└── batch/          # 已展开成员的批次编排，当前占位
```

职责：

- `input/`：`SimulationInput` 顶层结构、字段校验与 JSON 文件读写。
- `config/`：`ProjectConfig`（`config.toml`）结构、校验与工作区路径推导。
- `assembly/`：`SimulationAssembler` 与分阶段组装（`ConfigTranslator`、`AssetBundleLoader`、`ContentCompiler`、`RuntimeAssembler`），构造领域 Runtime、Registry、adapter、coordinator 与快照 provider。
- `execution/`：同步仿真执行、事件收集、`session_id` 分配、成功/失败运行记录构造与结果写入协议调用。
- `jobs/`：内存/进程任务 runner 边界；具体调度实现由 `infrastructure/jobs/` 提供。
- `services/`：`assets`、`input`、`project`、`results`、`analysis_query`、`simulation` 等对外用例门面，以及工作流 JSON 的不透明存档；CLI 与 HTTP API 只调用这一层。
- `batch/`：接收前端编好的 `(item_id, SimulationInput)` 有序集合，按批提交任务、跟踪成员状态、整批取消；不做变体编译，不解析工作流图。

依赖规则：

- 可以依赖 `core/`、`assets/`、handler 注册表和仓库协议。
- 不依赖任何 UI 框架或前端实现；不直接编写 SQLite 查询；SQLite 实现通过构造函数注入。
- 第一版使用显式构造函数注入，不引入重型 DI 框架。
- `execution/` 可以调用 `assembly/` 与 `core/`，但不处理 UI 状态、CLI 参数解析或任务队列持久化。

## 7. `infrastructure/`

`infrastructure/` 是具体技术实现适配层，负责 SQLite、文件、日志、进程调度等外部技术细节。

当前结构：

```text
infrastructure/
├── __init__.py
├── assets_sqlite/          # 只读资产库实现（SQLiteAssetRepository）
├── assets_project_amber/   # Project Amber / Yatta 抓取、manifest 构建与审计
├── results_sqlite/         # 结果库 schema、写入器、仓库读取与查询计划编译执行器（analysis_query.py）
├── file_storage/           # 项目配置与工作流 JSON 不透明读写
├── jobs/                   # 进程任务 runner
└── logging/                # 日志配置、JSONL formatter、上下文与清理
```

数据存储职责：

```text
data/assets/assets.db    -> 只读资产库
data/results/results.db  -> 可写运行期结果库
```

结果库保存运行记录、输入快照、初始快照与事件流；派生结果由查询计划编译执行器在读取侧计算（取数节点 + 关系算子，一次 CTE 链执行），物化产物可重建。schema 与读写协议见[结果库契约](../契约/结果库契约.md)，结果存储系统职责见[结果存储系统设计](./结果存储系统设计.md)。

## 8. 分析查询计划（替代原 `analysis/` 模块与 v1 模板）

分析能力按「数据 = 结果库内容、加工 = 关系算子」的模型落地，不再保留顶层 `analysis/` 模块与 v1 模板模型：

- 计划编译与执行：`infrastructure/results_sqlite/analysis_query.py`。取数/算子节点编译为 CTE 链一次执行，形状推导与列白名单校验与 SQL 同处，避免与结果库 schema 漂移。
- 契约模型与用例：`application/models.py` 的 `AnalysisPlan` / `AnalysisTableResult` 等 + `application/services/analysis_query.py` 的 `AnalysisQueryService`（声明级结构校验 + 委托执行协议）；事件类型 schema 由 `application/services/analysis_schema.py` 从 core 聚合。
- HTTP 端点：`server/` 提供 `POST /api/v1/analysis/query` 与 `GET /api/v1/analysis/schema`。

关键约束：前端只提交结构化查询计划（节点 + 参数 + 有序输入 + 输出清单），不接触 SQL 文本；字面量全部参数绑定，列名经白名单校验后引用，中间结果不出后端。完整契约见[分析系统设计](./分析系统设计.md)与[分析系统契约](../契约/分析系统契约.md)，节点模型见[分析区域设计](./UI/分析区域设计.md)。

## 9. `frontend/` 与 `server/`

`frontend/` 是仓库根目录下的独立 Web 前端工程（React + React Flow，计划中），产品形态、状态设计与工程规范见[前端工程规范](../工程/前端工程规范.md)。

`server/` 是 Python 侧的网页服务端入口，与 `cli/` 同级，负责：

- 托管 `frontend/` 构建出的静态文件（同源服务，避免跨域）。
- 把 REST/WebSocket 请求翻译为 `genshin_sim.application` 的公开接口调用。
- 提供统一错误模型与 OpenAPI 契约。

边界原则：

- `frontend/` 是纯客户端，只调用 HTTP API，不 import 任何 Python 代码、不直接访问 SQLite、不组装仿真核心对象、不实现分析算法。
- `frontend/` 拥有工作流图语义（定义校验、变体展开、成员预览），通过 HTTP API 提交已展开成员；CLI 不运行工作流。
- `frontend/` 与 CLI 通过各自入口共享资产、仿真与结果等 application 能力；`application/` 不依赖任何前端实现。
- 桌面形态与网页服务形态共用同一 server 与前端构建产物；桌面启动方式（pywebview 或自动打开浏览器）后置，不经过 CLI。网页服务形态通过同一服务绑定 `0.0.0.0` 部署。
- pydantic 只允许出现在 `server/` 的请求/响应 DTO 层，领域模型保持 dataclass。

## 10. `server/`

`server/` 是 HTTP 服务入口，负责服务生命周期、路由、DTO、错误映射、访问控制和前端静态文件托管。它不直接访问 `core/`、`content/`、`assets/` 或 `infrastructure/` 的具体实现。

HTTP 服务端是入口适配层，不属于 `infrastructure/` 的子模块；`infrastructure/` 提供 server 经 application 间接使用的外部技术实现（SQLite、文件存储、日志、进程任务执行）。

server 入口直接负责启动 HTTP 服务（`genshin-sim-server` 或 `python -m genshin_sim.server.main`），托管 API 与前端静态文件；CLI 不启动服务。网页服务形态与桌面本地形态使用同一 server 和前端构建产物。

## 11. `cli/`

`cli/` 是命令行入口，当前为单文件 `main.py`（`argparse`），只做参数解析与用例调用。

第一版命令：

```text
genshin-sim assets init
genshin-sim assets build [--manifest ...]
genshin-sim assets fetch-source
genshin-sim assets build-manifest
genshin-sim assets audit-manifest
genshin-sim assets validate
genshin-sim assets info
genshin-sim assets list <asset_type>
genshin-sim assets inspect <asset_key>
genshin-sim assets set-handler / reset-handler / show-handlers / sync-handlers

genshin-sim input validate <input_path>
genshin-sim input list [--root ...]

genshin-sim project init [--root ...] [--asset-manifest ... | --fetch-assets]
genshin-sim project show [--root ...]

genshin-sim run <input_path> [--root ...] [--db ...] [--results-db ...]

genshin-sim results init
genshin-sim results list [--state ...] [--limit ...]
genshin-sim results inspect <session_id>
genshin-sim results events <session_id> [--frame-min ...] [--frame-max ...] [--event-type ...]
```

Web 服务由 `server/` 入口启动（`genshin-sim-server` / `python -m genshin_sim.server.main`），不属于 CLI 命令。

规则：

- CLI 只调用 `genshin_sim.application` 的公开能力，不直接写 SQL，不重复实现仿真组装逻辑，也不直接构造基础设施适配器。
- CLI 不提供工作流的创建、校验或运行；工作流是 UI 产品面。
- `--root` 指定项目根目录，默认当前目录；结果库与日志路径默认由项目 `config.toml` 推导。
- 项目模式日志启用与 `--log-file` 优先级见[日志系统设计](./日志系统设计.md)。
- 第一版使用标准库 `argparse`；数据构建逻辑放在 `infrastructure/` 与 `application/services/`，不塞进 CLI 文件。

## 13. 后续待细化

- `frontend/` 页面级实现与性能基准；结构设计见[前端工程规范](../工程/前端工程规范.md)。
- `application/batch/` 已展开成员的批次编排；工作流图语义与变体编译在 `frontend/`。
- 更多真实角色/武器/圣遗物纵向切片与 handler 覆盖。
- 分析算子扩展：文本匹配条件、嵌套条件 AST、跨列比较与专门处理节点（区间配对、曲线等）；算子输出列显示名解析后置（任意列隐藏已由投影算子支持）。
- 任务后台 worker 的进度推送（SSE/WebSocket）、取消语义与批量执行模型。
