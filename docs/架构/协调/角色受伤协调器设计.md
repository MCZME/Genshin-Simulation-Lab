# 角色受伤协调器设计

> 状态：第一版已实现。
> 本文定义已经完成伤害计算的角色伤害，如何协调护盾与角色血量状态并形成角色受伤事实。

最后更新：2026-07-13

## 1. 定位

角色受伤协调器是护盾系统和血量系统之间的一条固定跨领域流程，不属于其中任何一方，也不属于伤害系统。

目标结构：

```text
伤害系统完成伤害计算
-> CharacterIncomingDamage
-> CharacterDamageTakenCoordinator
   ├── ShieldAbsorptionPort
   ├── CharacterHealthDamagePort
   ├── 准备并校验两个领域计划
   ├── 无回调、不得产生业务失败的提交阶段
   └── 发布护盾、血量和角色受伤事实
-> CharacterDamageTakenRecord
```

`CharacterDamageTakenCoordinator` 位于 `core/coordination/character_damage_taken/`。它只接受已经确定的角色伤害数值，并编排护盾与血量两个领域入口。

协调器不依赖或调用 `DamageResolver`、伤害公式、伤害 modifier provider 或具体 `DamageRuntime`。伤害系统是上游生产者，不是本协调流程内被写入或受影响的系统。

## 2. 处理范围

所有满足以下条件的伤害都进入角色受伤协调器：

- 伤害计算已经完成。
- 伤害目标是角色。
- 该数值在游戏语义上属于伤害，而不是生命流失或直接扣血。

伤害是单次还是周期性发生，不决定入口。周期性效果如果每次结算的是正式伤害，仍然进入角色受伤协调器。

以下变化不进入本协调器：

- `CharacterHpDeduction` 表达的直接扣血。
- 流血、侵蚀或其他在本项目中建模为生命流失的效果。
- 最大生命变化和由此产生的当前生命同步。

这些请求直接使用血量系统的独立类型化入口，不经过护盾，也不通过 `ignore_shield` 一类旁路字段伪装成伤害。

## 3. 设计目标

- 让护盾系统只拥有护盾状态、保护范围和吸收规则。
- 让血量系统只拥有角色当前生命和生命变化规则。
- 让已经完成计算的角色伤害统一经过同一应用入口。
- 在任何状态提交前完成目标、属性、容量和 Store 前值校验。
- 防止护盾已经扣除而血量提交失败的部分成功。
- 明确角色受伤、护盾变化和血量变化是不同事实。
- 让完全吸收、部分穿透、无盾和零伤害形成统一审计记录。

## 4. 非目标

角色受伤协调器不负责：

- 计算攻击方或伤害来源的伤害公式。
- 决定倍率、防御、抗性、暴击、反应或伤害 modifier。
- 修改或反馈伤害系统的计算结果。
- 处理直接扣血、流血、侵蚀或其他生命流失。
- 解释 Action、Impact payload 或敌人 AI。
- 用通用优先级列表动态拼接任意受伤中间件。
- 预先接入护盾和血量之外的第三个领域系统。

## 5. 输入边界

`CharacterIncomingDamage.amount` 是伤害系统已经完成伤害计算、但尚未应用角色护盾和血量的有限非负数。

上游 adapter 可以从伤害系统结果构造该请求，但协调器不直接依赖伤害系统结果类型。请求只描述实际目标和已经确定的伤害，不携带 `protection_ref`。

```text
damage_id
frame
target_ref
amount
element
source_ref?
source_context?
tags
```

精确字段见[角色受伤协调器契约](../../契约/角色受伤协调器契约.md)。

## 6. 受影响系统

协调器只写入两个领域：

```text
ShieldSystem
HealthSystem
```

### 6.1 ShieldSystem

护盾系统根据目标解析全部适用保护范围，并准备本次吸收产生的完整护盾记录变化。

- `active_team`：目标必须是对应队伍当前场上角色。
- `character`：目标必须与固定角色保护 id 一致。
- 同一目标可以匹配多个保护范围和多个并行吸收护盾。

来伤调用方不能指定 protection ref，也不能选择绕过某一组护盾。

### 6.2 HealthSystem

血量系统接收护盾计划产生的 `health_bound_damage`，准备角色当前生命变化。它不查询护盾、保护范围或伤害系统。

### 6.3 DamageSystem

伤害系统只在本流程之前产生已经完成计算的伤害。协调器不修改伤害结果、不重新结算任何伤害区，也不向伤害系统提交状态。

因此 DamageSystem 不属于本协调器的受影响系统，也不出现在协调器的依赖端口中。

## 7. 准备阶段

协调器在 `apply()` 入口获得重入保护。准备阶段只查询和计算，不修改任何 Store，也不发布事件。

### 7.1 护盾计划

`ShieldAbsorptionPort.prepare_absorption()` 返回不可变 `ShieldAbsorptionPlan`：

- 查询帧和目标。
- 匹配的完整护盾记录。
- 动态护盾强效查询结果。
- 每个护盾的吸收结果。
- 预期 ShieldStore version 和记录前值。
- 提交后的完整记录替换集。
- protected damage 和 health-bound damage。

### 7.2 血量计划

`CharacterHealthDamagePort.prepare_damage()` 使用 health-bound damage 返回不可变 `CharacterDamagePlan`：

- 当前生命和最大生命前值。
- 请求量、有效变化量和未应用量。
- 提交后的当前生命。
- 预期 HealthStore version 或完整前值。

准备任一计划失败时，护盾和血量都不得变化，也不发布本次角色受伤事实。

## 8. 统一预校验

两个计划都准备完成后，协调器必须在任何写入之前校验：

- 两个计划属于同一个 damage id、frame 和 target ref。
- 血量计划请求量等于护盾结果的 health-bound damage。
- ShieldStore version 和全部护盾记录前值未变化。
- HealthStore version 或角色血量前值未变化。
- 两个计划尚未提交。

任一校验失败时，两个 Store 均不提交。

## 9. 提交原子性

统一预校验通过后进入无回调提交阶段：

```text
进入 coordinator mutation guard
-> ShieldStore.commit_prevalidated(shield_plan)
-> HealthStore.commit_prevalidated(health_plan)
-> 形成 CharacterDamageTakenRecord
-> 退出状态提交阶段
```

这里的原子性表示：第一次写入之前已经排除所有正常业务失败；一旦开始提交，两个领域提交必须完成，期间其他逻辑不能观察或修改中间状态。

`commit_prevalidated()` 只能执行计划中已经准备好的确定性内存替换，禁止：

- 查询属性或重新读取外部运行态。
- 重新计算护盾吸收量或血量变化量。
- 执行 content、hook 或其他领域代码。
- 发布事件或触发同步回调。
- 执行可能产生领域验证错误的二次业务判断。

若某个领域无法保证预校验后的提交不产生业务失败，不能先提交另一个 Store；必须改用 copy-on-write 世界状态或正式事务边界。不得在部分成功后通过补偿事件恢复状态。

协调器的重入保护覆盖准备、提交和完整事实发布。事件 handler 不能递归调用当前角色受伤入口；未来触发行为必须产生下一结算轮次的类型化命令。

## 10. 事实语义与顺序

“角色受伤”和“血量变化”是两个独立事实：

- `DAMAGE_APPLIED`：`CharacterIncomingDamage.amount > 0` 且目标是角色时成立，即使伤害被护盾完全吸收。
- `CHARACTER_HEALTH_CHANGED`：角色当前生命实际减少时成立。

完整提交后按以下顺序发布：

```text
SHIELD_CAPACITY_CHANGED（instance ref 稳定顺序）
-> SHIELD_REMOVED（仅耗尽，instance ref 稳定顺序）
-> SHIELD_ABSORPTION_RESOLVED（正伤害且有匹配护盾）
-> CHARACTER_HEALTH_CHANGED（仅血量真实减少）
-> DAMAGE_APPLIED（仅 amount > 0）
```

典型语义：

| 情况 | DAMAGE_APPLIED | 护盾事实 | CHARACTER_HEALTH_CHANGED |
| --- | --- | --- | --- |
| 护盾完全吸收 | 是 | 是 | 否 |
| 护盾部分吸收 | 是 | 是 | 是 |
| 没有护盾 | 是 | 否 | 是 |
| amount 为零 | 否 | 否 | 否 |

无盾和零伤害仍可以形成 `CharacterDamageTakenRecord` 供审计。事实只能在护盾和血量两个 Store 完整提交后发布。

## 11. 领域事实所有权

协调器决定事实发布顺序，但不替领域构造事实内容：

- ShieldSystem 根据已提交的 ShieldAbsorptionPlan 提供护盾事实数据。
- HealthSystem 根据已提交的 CharacterDamagePlan 提供血量事实数据。
- 协调器构造最终 CharacterDamageTakenRecord 和 `DAMAGE_APPLIED`。

计划在提交前只保存结果和事实数据，不把尚未提交的结果当作已经发生的 `GameEvent`。

## 12. 错误模型

至少区分：

- 角色伤害请求验证错误。
- 目标不是角色或目标不存在。
- 护盾属性与容量计算错误。
- 血量前值或最大生命错误。
- 护盾计划、血量计划或跨 Store 前值冲突。
- 预校验后的领域提交违反“不得产生业务失败”约束。
- 协调器重入。

非法目标或提交冲突不得静默退化为无盾或零伤害。

## 13. 验证要求

- 无盾、零伤害、完全吸收和部分穿透。
- 多保护范围与多盾并行。
- 周期性正式伤害进入协调器；直接扣血和流血不进入协调器。
- 护盾计划失败时血量不变。
- 血量计划失败时护盾不变。
- 任一预校验冲突时两个 Store 均不提交。
- 提交阶段不查询、不计算、不发布事件且不产生领域业务错误。
- 完整事实顺序和稳定实例排序。
- 完全吸收仍发布 `DAMAGE_APPLIED`，但不发布 `CHARACTER_HEALTH_CHANGED`。
- 零伤害不发布角色受伤、护盾变化或血量变化事实。
- 事件回调不能递归进入当前协调器。
- `CharacterDamageTakenRecord` 稳定序列化与结果库 JSON 往返。

## 14. 当前实现

第一版代码位于 `core/coordination/character_damage_taken/`。`CharacterIncomingDamage` 与 `CharacterDamageTakenRecord` 已由协调层拥有，ShieldRuntime 和 HealthRuntime 均已提供 prepare、validate、commit_prevalidated 与领域事实构造入口。

生产对象图使用 `CharacterDamageTakenCoordinator` 作为正式角色伤害应用入口；ShieldRuntime 不再依赖或调用 HealthRuntime。失败注入测试覆盖血量准备失败、血量预校验冲突、护盾计划冲突和事件发布前的完整提交边界。
