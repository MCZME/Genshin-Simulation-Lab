# 状态效果（Buff）系统设计

> 状态：正式设计已确认，第一版工程闭环已实现；真实简单 Buff golden case 因仓库缺少可信资料仍待补充，不宣称真实机制覆盖完成。
> 本文定义状态效果系统的长期职责、领域边界、运行流程与分阶段实现范围。稳定模型、枚举、策略、事件、错误和序列化见[状态效果系统契约](../../契约/状态效果系统契约.md)。

最后更新：2026-08-07

## 1. 结论

项目使用 `core/systems/buff/` 作为状态效果领域的代码包。本文中的 `Buff` 是技术术语，统一表示“具有运行时身份和生命周期、可附着于角色或目标的状态效果”，不推断它对目标有利、有害或中性。

选择 `buff` 而不是 `effect` 或 `status` 的原因：

- `effect_payloads` 已用于资产效果参数，不能与运行时实例混为一谈。
- `ImpactRequest` 已表达一次性机制意图，不能再把一次伤害、治疗或创建物称为运行时效果。
- `status` 在任务、动作和影响点模型中已有广泛含义，单独使用过于模糊。
- 现有领域运行态和迁移路线已经使用 `BuffStore`、`BuffRecord` 与 `ApplyBuffRequest` 作为目标名称。

系统目标结构：

```text
content / Impact
-> ApplyBuffRequest
-> BuffRuntime
-> BuffResolver
-> BuffMutationPlan
-> BuffStore -> BuffRecord
-> BuffAttributeModifierProvider 只读查询
-> AttributeResolver
```

第一版只实现两类无回调状态效果：

- 有限时长的属性修饰 Buff / Debuff。
- 有限时长、可被其他类型化适配器查询的纯状态标记。

第一版不实现事件触发器、周期 tick、独立计时的每层 Buff、驱散分类规则、动态最大生命 Buff 或任意脚本回调。它们都有明确的后续接入边界，不需要在第一版预建万能效果框架。

## 2. 设计目标

- 为限时 Buff、Debuff 和纯状态标记提供唯一状态所有者。
- 明确定义创建、刷新、叠层、替换、共存、过期和显式移除语义。
- 使用稳定实例身份、半开生命周期和不可变记录保证可复现。
- 让属性系统无副作用地读取当前活动 Buff，并保留 modifier 审计来源。
- 支持角色自身 Buff、角色间施加的 Buff 和目标 Debuff；队伍效果按固定目标展开。
- 让资产参数、content 行为、Buff 状态和属性聚合保持分层。
- 保证批量应用、替换和到期清理是先完整计划、后原子提交、再发布事实。
- 为事件记录、快照和 Buff 覆盖率分析提供稳定数据。
- 给实现者提供完整字段、失败语义、顺序和测试基线，不把关键选择留到编码阶段临时决定。

## 3. 非目标

状态效果系统不负责：

- 伤害、治疗、反应、护盾、生命、能量、冷却、元素附着或 ICD 的领域公式。
- 一次性 Impact 请求的通用封装。
- 角色、武器、圣遗物或命座的具体触发条件。
- 事件订阅、当前事件调用栈内的后续结算或通用命令队列。
- 每帧执行 content 回调。
- 空间实体、召唤物、场地物或范围索敌。
- 角色专属复杂计数器、模式状态或不可泛化的状态机。
- 资产参数解释、SQLite 读取、配置文件解析、UI 展示或结果库写入。
- 通过有利/有害标签决定驱散、冲突或数值规则。

## 4. 与旧项目的关系

旧项目 `core/effect/` 证明了以下需求确实存在：

- 有限持续时间和永久标记。
- 刷新、叠层和独立共存。
- 属性 Buff、目标减抗、纯状态标记和按次数消费的复杂效果。
- 效果开始、结束、层数和覆盖率审计。
- Buff 作为其他数值 provider 或内容状态机的启用条件。

旧实现不直接迁移，原因包括：

- 使用显示名称和 Python 具体类查找冲突，身份不稳定。
- 把可变效果对象直接挂到实体，状态所有权与生命周期写入口不唯一。
- `on_apply()`、`on_remove()` 和事件 handler 直接改属性、订阅事件或修改其他系统。
- 每帧递减剩余时间，永久值、边界帧和刷新时点容易出现歧义。
- 效果、动态 modifier 和事件订阅分别保存真值，异常清理可能只移除其中一部分。
- 叠层和刷新依赖子类覆写，缺少统一结果、原子计划和失败语义。
- 事件回调可以修改正在结算的伤害或生命流程，形成隐式顺序和重入风险。

新系统只保留行为需求，不保留旧 `BaseEffect` 继承体系、实体 `active_effects` 列表或生命周期回调。

## 5. 状态归属判断

进入 `BuffStore` 的对象必须同时满足：

- 需要稳定运行时身份。
- 具有有限生命周期。
- 附着于一个固定角色或目标属性主体。
- 需要刷新、叠层、替换、共存或显式移除中的至少一种状态语义。
- 状态可以用无回调记录完整表达。

常见能力的归属：

| 能力 | 归属 | 原因 |
| --- | --- | --- |
| 无条件常驻武器副属性 | 静态 `ModifierProvider` | 没有运行时生命周期 |
| 限时攻击力提升 | `BuffRuntime` | 有有限生命周期并向属性提供 term |
| 限时目标减抗 | `BuffRuntime` | 目标状态与属性 provider 协作 |
| 纯“已激活”标记 | `BuffRuntime` | 有身份、有限生命周期且只需存在性查询 |
| 气氛值、模式、专属计数器 | `ContentStateMount`（挂载于 `CharacterRuntimeState.content_states`） | 是单个 handler 的复杂私有状态 |
| 护盾容量与吸收 | `ShieldRuntime` | 有独立公式、容量和受伤流程 |
| 冷却 | 专用 Cooldown Store | 更适合 key 到 ready frame |
| 元素附着与 ICD | 专用领域运行时 | 有附着量、衰减、计数和窗口规则 |
| 周期伤害或周期治疗 | 后续调度命令 + 对应领域系统 | Buff 不执行 tick 公式 |
| 元素附魔 | 后续附魔/规则能力 | 不是普通属性 term |
| 场地物、召唤物 | `Space` / `CreatedObjectRuntime` | 有空间身份与行为 |
| 一次伤害、治疗或能量变化 | 对应领域请求 | 没有长期实例 |

不能因为某项能力在游戏描述中称为“效果”就放入 Buff 系统。

## 6. 总体结构

```text
core/systems/buff/
├── enums.py         # 生命周期、应用策略、结果与移除原因
├── errors.py        # 领域错误
├── definitions.py   # BuffDefinition 与只读注册表
├── models.py        # 请求、记录、结果、计划和值对象
├── resolver.py      # 纯应用策略解析
├── store.py         # 完整 BuffRecord 的唯一所有者
├── protocols.py     # BuffReader 等窄只读协议
├── providers.py     # 属性 modifier provider 适配
├── runtime.py       # 计划、提交、生命周期与事实顺序
├── handler.py       # ImpactRequest 到强类型请求的适配
├── snapshots.py     # 活动 Buff 快照
└── __init__.py      # 稳定公共导出
```

组件职责：

| 组件 | 职责 |
| --- | --- |
| `BuffDefinitionRegistry` | 保存组装期已编译、运行时只读的 Buff 定义 |
| `BuffResolver` | 根据定义、请求和冲突记录纯计算应用结果与替换集合 |
| `BuffStore` | 原子拥有全部完整记录、实例序列、版本和已提交操作 |
| `BuffRuntime` | 准备计划、提交、过期清理、显式移除和事实发布 |
| `BuffReader` | 向 provider 暴露活动记录查询，不暴露 Store 写入口 |
| `BuffAttributeModifierProvider` | 把活动记录转换为属性 `ModifierTerm` |
| `BuffImpactRequestHandler` | 校验 `ImpactKind.APPLY_STATUS` 结构并适配目标 |

## 7. 定义与实例分离

### 7.1 BuffDefinition

`BuffDefinition` 是组装期从资产参数和 content 行为编译出的不可变运行时定义。它声明：

- 稳定定义 key、机制 key、handler key 和冲突 key。
- 允许附着的属性主体种类。
- 应用策略、数值刷新策略和最大层数。
- 属性 modifier 模板或纯标记模式。
- 允许写入的属性、modifier 阶段、查询标签条件和审计标签。

定义不是资产数据库对象。`effect_payloads` 只保存参数和 `handler_key`；content factory 负责把参数转换为 `BuffDefinition`，application 负责注册和交叉校验。

定义 key 在一次组装中全局唯一，由稳定来源绑定和 content 局部语义组成，例如：

```text
buff.definition:slot_1:weapon.some_weapon:passive_1
buff.definition:artifact.slot_2:four_piece.atk
buff.definition:reaction.superconduct:physical_resistance
```

`mechanic_key` 表达跨运行期稳定的游戏机制语义；`definition_key` 还承担本次组装中不同槽位、精炼或参数版本的唯一绑定。显示名称不进入两者。

### 7.2 BuffRecord

`BuffRecord` 是运行时真值，必须单条记录即可判断实例是否合法。它直接包含不可变 `BuffDefinition`、目标、来源、层数、已解析 modifier 值、生命周期和移除审计，不要求跨 Store 拼接元数据。

```text
BuffStore
└── BuffRecord
    ├── instance_ref
    ├── definition
    ├── created_frame
    ├── last_applied_frame
    ├── expires_at_frame
    ├── lifecycle_state
    ├── state: BuffState
    ├── removed_frame?
    └── removal_reason?
```

`BuffDefinitionRegistry` 是创建请求的白名单和 provider 组装来源，不是活动实例的第二份真值。

## 8. 身份与语义

以下概念必须分开：

- `BuffInstanceRef`：一次运行中的具体 Buff 实例身份。
- `definition_key`：本次组装中使用哪份已编译定义。
- `mechanic_key`：稳定的机制语义和分析聚合 key。
- `handler_key`：哪段 content 代码负责编译定义。
- `conflict_key`：哪些活动记录参与应用策略冲突判断。
- `target_ref`：Buff 附着并影响谁。
- `applier_ref`：哪个角色或目标施加了 Buff，可为空。
- `source_context`：稳定资产、内容、施加者或上游机制绑定；单次动作/Impact 的发生身份放在 request id，不把每次施放的瞬时 instance id 当成 Buff 来源身份。

冲突身份第一版固定为：

```text
(target_ref, definition.conflict_key)
```

如果同名机制允许不同来源分别存在，content 必须把稳定来源身份编入 `conflict_key`；如果不同来源本来就不应叠加，则使用相同 `conflict_key`。系统不使用显示名称、类名、注册顺序或全局 priority 猜测冲突。

## 9. 目标范围

第一版每条 `BuffRecord` 只附着于一个 `AttributeSubjectRef`：

- `character`：固定战斗角色身份，例如 `character:slot_1`。
- `target`：固定目标身份，例如 `target:target_1`。

每个 BuffDefinition 必须显式声明允许的 target kinds；application 会把它与所有属性模板对应定义的 owner kinds 交叉校验，错误目标不能等到 provider 查询时才被忽略。

队伍 Buff 在应用时展开为每个固定角色一个请求，并通过 `apply_many()` 在一个 Buff Store 计划中提交。这样可以：

- 不让 Buff 系统依赖 `TeamRuntimeState`。
- 避免 `player:active` 空间实体成为属性主体。
- 让每个角色的覆盖率、刷新和移除独立可审计。
- 保证当前固定队伍中的批量应用原子完成。

“始终跟随当前场上角色”的动态作用域不在第一版中伪装成固定角色 Buff。需要该语义的真实内容必须先评审窄的 active-character scope reader 或在后续命令轮次中按切换事实迁移状态。

## 10. 应用策略

第一版固定四种策略：

| 策略 | 无冲突记录 | 有冲突记录 |
| --- | --- | --- |
| `replace` | 创建新实例 | 原子移除全部冲突记录并创建新实例 |
| `refresh` | 创建新实例 | 保留同一兼容实例，刷新期限和值 |
| `stack_refresh` | 创建新实例 | 保留同一兼容实例，加层至上限并刷新期限 |
| `coexist` | 创建新实例 | 忽略冲突集合，始终创建独立实例 |

兼容记录要求定义、目标、施加者和稳定来源上下文完全一致。重复施放同一来源的 Buff 必须复用相同来源绑定，只改变 request id。`refresh` 或 `stack_refresh` 遇到多个冲突记录、其他定义或不同来源时抛结构化冲突错误，不隐式选择赢家。

统一刷新规则：

```text
candidate_expires_at = request.frame + request.duration_frames
expires_at_after = max(existing.expires_at_frame, candidate_expires_at)
```

因此刷新不会缩短仍在活动的期限。需要以新实例强制替换并缩短期限时使用 `replace`。

`stack_refresh` 使用单记录、统一期限模型：

```text
stacks_after = min(max_stacks, stacks_before + stack_delta)
```

同一 Buff 的每层独立计时不属于该策略；这类机制后续使用独立栈记录或专用领域状态，经真实内容验证后再设计。

## 11. 数值与快照时机

Buff 系统不实现任意表达式语言，也不在属性查询期间修改自身状态。

第一版使用“应用前解析、记录中保存”的值模型：

```text
content / adapter 查询所需属性或读取资产常量
-> 构造 BuffModifierValue(term_key, value)
-> BuffRuntime 按 BuffDefinition 校验
-> BuffRecord 保存 BuffResolvedAttributeModifier
-> provider 在查询时只应用层数和标签条件
```

这明确表示 modifier 基础值是应用帧快照或资产常量。每个模板声明：

- `constant`：无论层数多少只贡献一次 value。
- `linear`：贡献 `value * stack_count`。

重新应用时由定义的 `value_refresh_policy` 决定：

- `keep_initial`：保留首次应用的已解析值。
- `replace_latest`：用本次请求的已解析值替换。

第一版 `APPLY_STATUS` Impact 合同要求 content 明确携带全部 `BuffModifierValue`，不会由 BuffImpactRequestHandler 自动查询属性。当前 ImpactFactory 验证切片只接入资产/handler 已知常量；需要应用帧属性快照的真实内容，必须由一个已经持有 `AttributeReader` 的类型化命令生产者先完成查询再构造请求。该生产者的晚绑定装配入口在出现第一个真实需求时进入阶段 D，但不会改变 BuffRequest、BuffRecord 或 provider 的本契约。

需要在每次属性查询时动态读取施加者属性、目标生命比例或其他领域状态的复杂 Buff，不通过通用模板表达。它应由 content 提供声明 reads/writes 的专用 provider，并且只读取 `BuffReader` 与其他窄只读协议；该 provider 仍不能写 BuffStore。

## 12. 与属性系统的关系

`BuffStore` 拥有生命周期，`AttributeResolver` 拥有数值聚合。两者通过组装期固定的 `BuffAttributeModifierProvider` 协作。

```text
BuffDefinition
-> 组装 provider_spec，提前声明 writes
-> provider 注册到固定 ModifierProviderIndex

AttributeQuery(frame, subject, key, context)
-> provider 查询 BuffReader.active(...)
-> 过滤 definition_key、target_ref 和半开生命周期
-> 检查 required/excluded query tags
-> 生成 ModifierTerm
-> AttributeResolver 应用 stacking group 和 policy
```

关键规则：

- 不为每个运行时 Buff 实例动态注册或注销 provider。
- provider 只能返回定义中声明的 target key 和 stage。
- provider 查询无副作用，不触发过期提交、不发布事件、不改变层数。
- 已过期但尚未物理清理的记录因 `is_active_at(frame)` 为假，不会贡献 term。
- Buff 的 `conflict_key` 处理实例共存；属性 `stacking_group` 处理多个有效 term 的数值择优。两者不能互相替代。
- `ModifierTerm.source_ref` 使用 `RuntimeSourceKind.MECHANIC`、`mechanic_key` 和稳定 Buff instance key；原始 `source_context` 保留在 Buff 记录、事件与快照中。

第一版通用模板支持 required/excluded query tags，足以表达“只在某类查询中生效”的简单条件。它不读取任意 content 状态或执行脚本条件。

## 13. 动态最大生命边界

动态修改 `stat.hp.base`、`stat.hp.max` 或其传递依赖会要求 `HealthRuntime` 按旧最大生命比例同步当前生命。仅提交 Buff 记录会让属性真值与当前生命短暂不一致，因此第一版明确禁止这类 Buff 定义进入组装。

启用动态最大生命 Buff 前必须新增限定协调流程：

```text
BuffMaxHpChangeCoordinator
-> 准备 BuffMutationPlan
-> 用计划投影视图解析 old/new stat.hp.max
-> 准备 CharacterMaxHpReconcilePlan
-> 统一校验 BuffStore 与 HealthStore
-> 无回调提交两个领域
-> 按契约发布 Buff 与最大生命事实
```

在计划投影查询和该协调器落地前，application 必须拒绝直接或通过属性依赖图间接影响 `stat.hp.max` 的动态 Buff。不能先提交 Buff、再查询新值、最后尽力修正生命。
这里的属性依赖图包含 `AttributeDefinition.dependencies`，也包含已注册属性 provider 声明的 `ModifierProviderSpec.reads -> writes` 边；Buff 写入 provider 会读取并进一步写入最大生命的私有属性时，同样必须在组装阶段失败。

## 14. 与其他系统的关系

### 14.1 Damage

减抗优先通过目标 `resistance.*` 属性 modifier 表达，普通元素伤害加成优先通过 `bonus.damage.*` 表达。

需要伤害专用阶段、component 或复杂 DamageQuery 条件的 Buff 不让 `core/systems/buff` import Damage Runtime 或 Store。后续由组装器向 content 的类型化 `DamageModifierProvider` 注入 `BuffReader`，provider 只读活动记录并返回伤害 term。

### 14.2 Healing、Shield、Energy 与 Aura

Buff 系统不直接调用这些系统的写入口，也不在记录中保存它们的可变状态。若某个 Buff 应触发治疗、授盾、能量变化或附着，事实到强类型后续命令的流程由后续命令轮次完成。

### 14.3 内容状态挂载（ContentStateMount）

BuffRecord 只保存通用层数、期限、已解析 modifier 值和稳定来源。角色专属累计量、复杂模式、每次命中计数或特殊状态机继续由 owner content state 保存。不能在两个 Store 中复制同一计数。

### 14.4 Space 与 Team

Buff 目标使用稳定战斗主体，不使用空间实体显示名或位置。范围选取和候选目标解析在 Impact/Space 层完成，BuffRuntime 只接受已经确定的目标引用。

## 15. Impact 与 content 接入

现有 `ImpactKind.APPLY_STATUS` 作为动作或空间行为申请状态效果的通用意图，不新增重复的 `APPLY_BUFF` kind。

```text
ActionImpactPoint / CreatedObjectBehavior
-> content ImpactFactory
-> ImpactRequest(kind=apply_status, params.buff=...)
-> BuffImpactRequestHandler
-> ApplyBuffRequest[]
-> BuffRuntime.apply_many()
```

`ContentUnit` 目标新增：

```text
attribute_stacking_groups: tuple[ModifierStackingGroupDefinition, ...]
buff_definitions: tuple[BuffDefinition, ...]
```

content 负责：

- 使用资产 `params` 编译定义。
- 生成稳定 definition/mechanic/conflict key。
- 在 impact factory 或后续命令 adapter 中生成请求和已解析 modifier 值。
- 为真实机制提供资料来源和 golden case。

content 不负责：

- 分配 Buff instance ref。
- 构造 BuffRecord 或 MutationPlan。
- 访问 BuffStore 或修改活动记录。
- 在 provider 查询中刷新或移除 Buff。
- 用显示名称查找冲突。

缺定义、重复 definition key、非法属性、modifier value key 不完整或 `params.buff` 格式错误必须在组装或请求适配边界失败。

## 16. application 组装顺序

为了让固定属性 provider 持有 Buff 只读视图，组装顺序调整为：

```text
加载资产与 content contribution
-> 收集并校验 BuffDefinition
-> 创建 BuffDefinitionRegistry 与 BuffStore
-> 为有属性模板的定义创建 BuffAttributeModifierProvider
-> 构造 AttributeRuntime（静态 provider + content provider + Buff provider）
-> 创建 BuffResolver / BuffRuntime / BuffImpactRequestHandler
-> 把 APPLY_STATUS 接入 ImpactRequestDispatcher
-> BuffRuntime 在 ActionManager 之前进入 RuntimeWorld
```

`core/attributes` 不 import Buff，`core/systems/buff` 可以依赖属性值对象与 provider 协议。application 负责连接两者。

第一版不改变 `SimulationInput`、资产库 schema 或结果库 schema。测试初始 Buff 通过测试 content 或 frame 0 受控组装入口提供；不能把任意 Buff 配置偷偷塞进 `rules.enabled`。

## 17. 帧顺序与生命周期

有限生命周期使用半开区间：

```text
created_frame <= frame < expires_at_frame
expires_at_frame = applied_frame + duration_frames
```

例如在第 100 帧应用、持续 3 帧的 Buff 在 100、101、102 帧有效，第 103 帧无效。

帧内顺序：

```text
FRAME_STARTED
-> BuffRuntime 清理 expires_at_frame <= frame 的记录
-> ActionManager 处理输入与动作
-> ImpactRuntime 展开并按请求顺序结算
-> 同帧 APPLY_STATUS 提交后，后续查询可看到新 Buff
-> 其他运行态收尾
-> FRAME_ENDED
```

即使过期清理尚未运行，provider 也必须按查询帧判断有效性，不能把 `lifecycle_state=active` 单独视为生效。

简单属性 Buff 和状态标记本身不产生未来工作，因此 `BuffRuntime.is_idle()` 第一版返回 `True`，不会仅为了等待一个无副作用 Buff 过期而延长仿真。分析使用事件中的期限和仿真结束帧计算覆盖区间。未来周期命令由其调度器决定是否阻止仿真结束。

## 18. 计划、原子性与重入

单个或批量应用流程：

```text
请求与定义校验
-> 冻结同一批次请求顺序
-> 查询全部冲突前值
-> BuffResolver 纯计算所有结果
-> 生成一个 BuffMutationPlan
-> 校验 Store version、全部记录前值和 operation id
-> 一次提交 replacement_records
-> 生成 receipt
-> 按请求顺序为每个结果先发布关联移除事实，再发布应用事实
-> 纯移除批次按 instance ref 发布移除事实
```

规则：

- `apply_many()` 要求同一批请求 frame 一致、order 唯一、request id 唯一，并按显式 `order` 处理。
- 任一请求失败，整批记录不变化。
- 替换多个旧实例与创建新实例属于一个 Store 提交。
- commit 阶段不查询属性、不调用 content、不发布事件。
- 记录按 instance ref 稳定排序，事实按请求 order、目标和 instance ref 稳定排序。
- 状态提交或事实发布期间再次调用 Buff 写入口抛重入错误。
- 事件 handler 不能在当前发布调用栈中直接 apply/remove Buff。

## 19. 事件与后续命令

第一版新增两个事实事件：

- `BUFF_APPLIED`：一次创建、替换、刷新、叠层或到顶刷新已经提交。
- `BUFF_REMOVED`：一个实例因过期、替换、驱散、消费或显式原因离开活动状态。

两者都是 `STATE_CHANGE`、默认记录、不可取消、载荷不可修改。替换时先按旧 instance ref 发布 `BUFF_REMOVED`，再发布 `BUFF_APPLIED`。

事实驱动后续效果的目标流程是：

```text
已提交事实
-> content EventHook 生成 ApplyBuffRequest 或其他强类型命令
-> 同帧下一结算轮次或未来帧
-> 对应 Runtime 提交
```

命令队列必须先单独确认轮次、稳定排序、最大轮次、循环检测和仿真终止条件。BuffRuntime 不通过订阅 EventEngine 自行实现触发器。

## 20. 快照、持久化与分析

`BuffSnapshot` 只包含指定帧活动的记录，按 instance ref 排序。快照保存定义身份、目标、来源、层数、已解析 modifier、创建/最近应用/到期帧和标签。

第一版结果持久化继续使用通用事件 JSON，不新增 Buff 专用表。analysis 可以从事件重建覆盖区间：

```text
开始或刷新边界 = BUFF_APPLIED.frame
计划结束边界 = BUFF_APPLIED.expires_at_after
提前结束边界 = BUFF_REMOVED.frame
会话裁剪边界 = SIMULATION_ENDED.end_frame + 1
```

同一实例刷新时更新其计划结束边界；替换时旧实例结束、新实例开始。`end_frame` 是最后完成处理的帧，因此离散帧覆盖的会话半开结束边界是 `end_frame + 1`。覆盖率按半开区间并集计算，不能简单相加重叠实例时长。

专用投影、UI 图标、显示名称和 Buff 分类属于后续 analysis/UI 需求，不进入 core 事实模型。

## 21. 确定性与错误边界

- 所有 key、目标、请求 order、记录和事件使用稳定排序。
- 所有 modifier 数值先拒绝 `bool`，再校验有限数。
- 百分比使用小数倍率。
- 不依赖 dict、set、handler 注册或 Event 订阅的偶然顺序。
- 不使用 priority 解决 Buff 冲突。
- 不静默忽略未知 definition、非法 target、缺失 modifier value 或不兼容冲突。
- application 把资产/content/定义错误转换为 assembly 错误；运行中合法状态冲突保留 Buff 领域错误。

错误层级与稳定 code 见[状态效果系统契约](../../契约/状态效果系统契约.md)。

## 23. 第一版验收标准

- BuffStore 是完整 BuffRecord 的唯一写入与真值来源。
- definition、instance、mechanic、handler、conflict、target 和 source 身份不混用。
- 四种应用策略和统一刷新公式没有未定义分支。
- 同帧应用、查询、刷新、替换和过期顺序可稳定复现。
- provider 无副作用，过期记录不贡献 term。
- 批量应用任一失败时没有部分状态。
- 事实只在提交后发布，事件回调不能同步重入写入。
- 目标隔离、层数、查询标签和 modifier 审计有单元测试。
- Impact、content、组装、事件 JSON 与覆盖区间有集成测试。
- 至少一个真实简单 Buff 具有版本、来源和 golden case；测试 content 不冒充真实机制。
- `pytest`、`ruff` 和 `pyright` 通过后才能把实现状态改为第一版已实现。
