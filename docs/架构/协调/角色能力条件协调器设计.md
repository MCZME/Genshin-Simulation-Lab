# 角色能力条件协调器设计

> 状态：正式。第一版只读条件查询 Runtime 已实现；ActionInterpretationContext 注入和真实角色动作接入仍待后续专题确认。
>
> 适用范围：组合元素战技与元素爆发的冷却条件和标准元素能量条件，为角色动作解释器提供公共条件查询。
>
> 明确排除：动作锁与中断、角色专属状态和私有资源、冷却启动、元素能量扣除、资源预留以及 Action 最终准入。

最后更新：2026-07-14

## 1. 定位

角色能力条件协调器是一条只读跨系统协调流程，位于：

```text
core/coordination/character_ability_condition/
```

它组合冷却系统和元素能量系统已经给出的领域条件，为角色动作解释器回答：

```text
当前帧，这个角色的这项能力是否通过冷却与标准元素能量公共门槛？
```

协调器不回答“动作最终能否执行”。完整判断仍然分为三层：

```text
CharacterActionInterpreter
├── CharacterAbilityConditionCoordinator：冷却与标准元素能量公共条件
├── content：角色专属状态、姿态、私有资源和动作语义
└── PreparedAction
        ↓
ActionManager
└── 动作锁、中断、会话和实例创建的最终准入
```

## 2. 核心结论

1. 协调器只读，不修改 `CooldownStore` 或 `CharacterEnergyStore`。
2. 协调器不调用 `StartCooldownRequest`、`SpendBurstEnergyRequest` 或任何资源预留入口。
3. 元素战技查询冷却条件；标准元素爆发同时查询冷却和标准元素能量条件。
4. `capacity = 0` 表示不使用标准元素能量，公共能量条件委托给 content 的私有资源判断，不能当成普通能量不足。
5. 协调器返回结构化逐项证据和全部阻塞原因，不只返回一个 `bool`。
6. 冷却查询前必须由整帧运行时把冷却状态显式规范化到当前帧；协调器查询不推进时间。
7. 查询结果不是 reservation、permit 或 ActionManager 的最终 `ActionDecision`。
8. 协调器只依赖两个领域的窄只读 Protocol，不接收完整 Runtime、Store 或任意 `SimulationContext`。

## 3. 设计目标

- 消除各角色解释器重复组合“E 查冷却、Q 查冷却和能量”的逻辑。
- 保持冷却条件、能量条件和动作最终准入三个概念分离。
- 让一次拒绝可以同时保留冷却和能量两项证据。
- 让专属资源角色不会被标准能量规则错误拒绝。
- 保持查询无副作用，不让解释顺序隐式推进冷却或发布事实。
- 为动作拒绝记录、测试和后续 UI 提示提供稳定 reason code。

## 4. 非目标

协调器不负责：

- 判断普通攻击、重击、下落攻击、冲刺、跳跃或切人是否可用。
- 解析按键、选择 `action_key` 或创建 `PreparedAction`。
- 检查动作锁、并发策略、中断窗口或输入会话状态。
- 判断角色姿态、天赋、命座、Buff 条件或 content 私有状态。
- 实现专属资源公式或拥有专属资源状态。
- 启动、减少、重置或恢复冷却次数。
- 扣除、恢复或预留元素能量。
- 记录“能力已经释放”事实或发布 Event。
- 把任意资源条件动态注册成通用 gate pipeline。

## 5. 只读协调器边界

本协调器属于 `core/coordination/` 的只读条件协调器，不属于跨 Store 写协调器。

只读条件协调器的固定流程为：

```text
类型化查询
-> 查询领域条件 A
-> 根据稳定领域类型决定是否查询领域条件 B
-> 校验跨领域身份和证据一致性
-> 形成不可变组合结果
```

它不执行写协调器的 prepare/commit 流程，因为整个查询没有 MutationPlan、Store 提交或事实发布。只读类别不能削弱角色受伤等写协调器的统一预校验和无回调提交要求。

## 6. 稳定输入身份

公共查询使用：

```text
CharacterAbilityConditionQuery
├── frame
├── character_id
└── ability_key
```

规则：

- `character_id` 是本次仿真内稳定的角色战斗实体 id，例如 `character:slot_1`。
- `ability_key` 是共享同一冷却状态的能力身份，不是 `action_key`、显示名称、`asset_key` 或 `handler_key`。
- 推荐核心 key 为 `elemental_skill` 和 `elemental_burst`。
- 多个动作变体只要共享同一冷却，就使用相同 `ability_key`。
- 调用方不能同时提交一份冷却主体引用和一份能量主体引用，避免两者指向不同角色。

协调器根据 `character_id` 构造或映射各领域查询引用。组装阶段必须保证同一角色在队伍运行态、冷却 definition 和能量 profile 中使用同一个战斗实体 id。

长期若形成中立 `CharacterRuntimeRef`，可以替换字符串映射；第一版不为此迁移现有全部主体引用。

## 7. 领域只读端口

### 7.1 冷却条件端口

```text
CooldownConditionReadPort
└── query_condition(CooldownQuery) -> CooldownConditionResult
```

冷却系统拥有：

- definition 和 record 查找。
- `AbilityKind`。
- `available_charges > 0` 条件。
- `CooldownView`、reason 和 revision。
- 当前帧是否已经规范化的校验。

协调器不读取 `CooldownStore`，也不重复计算 charge 或 remaining frame。

### 7.2 爆发能量条件端口

```text
BurstEnergyConditionReadPort
└── query_burst_condition(character_ref, frame) -> BurstEnergyConditionResult
```

元素能量系统拥有：

- 当前能量和 capacity 查询。
- 原样保存本次查询帧，供协调器校验证据一致性。
- 是否使用标准元素能量。
- `capacity > 0 and current_energy >= capacity` 条件。
- `ready`、`insufficient_energy` 或 `nonstandard_resource` 领域 reason。

协调器不通过两次裸数值读取重复实现满能量公式。

## 8. 组合结果

```text
CharacterAbilityConditionResult
├── query
├── ability_kind
├── shared_conditions_satisfied
├── cooldown_condition
├── burst_energy_condition?
├── blocking_reasons
└── delegated_conditions
```

`shared_conditions_satisfied` 只表示本协调器负责的公共条件均已满足，不表示动作最终可执行。

稳定阻塞原因第一版为：

```text
cooldown_unavailable
standard_energy_unavailable
```

稳定委托条件第一版为：

```text
content_private_resource
```

阻塞原因按以下顺序冻结：

```text
cooldown_unavailable
-> standard_energy_unavailable
```

即使冷却已经不满足，标准爆发仍查询能量条件并保留两项证据，不做隐藏短路。

## 9. 组合规则

| 能力类型 | 冷却条件 | 标准元素能量条件 | 公共结果 |
| --- | --- | --- | --- |
| 元素战技 | 必须查询 | 不适用 | 冷却满足时通过 |
| 标准元素爆发 | 必须查询 | 必须查询且 ready | 两项都满足时通过 |
| 非标准资源爆发 | 必须查询 | `nonstandard_resource` | 冷却满足时公共条件通过，同时委托 content 私有资源判断 |

`AbilityKind` 必须从冷却 definition 对应的 `CooldownConditionResult.view` 得到，不由调用方重复传入。调用方不能通过伪造 ability kind 绕过爆发能量条件。

第一版只接受 `ELEMENTAL_SKILL` 和 `ELEMENTAL_BURST`。未知类型属于契约或组装错误，不降级成普通技能。

## 10. 查询流程

```text
evaluate(query)
-> 校验 frame、character_id 和 ability_key
-> 构造 CooldownKey
-> query CooldownConditionReadPort
-> 校验返回 key、主体和 frame
-> 从 CooldownView 读取 AbilityKind
-> skill：形成冷却组合结果
-> burst：query BurstEnergyConditionReadPort
-> 校验能量主体
-> 收集全部 blocking reasons 和 delegated conditions
-> 返回不可变 CharacterAbilityConditionResult
```

查询不保存 coordinator records。需要审计动作拒绝时，由动作解释结果或动作决策记录保存本次结构化证据。

## 11. 帧语义

冷却查询要求 Runtime 已规范化到 `query.frame`。整帧顺序目标为：

```text
BuffRuntime
ShieldRuntime
CooldownRuntime.normalize(frame)
ActionManager
ImpactRuntime
EnergyRuntime
SpaceRuntime
```

含义：

- 在 `frame == ready_frame` 时，次数先恢复，随后本帧输入可以使用该能力。
- 协调器不能为了方便而在 `evaluate()` 中调用 normalize。
- 当前帧此前已经提交的能量变化对后续顺序输入可见。
- 同帧多个输入仍按 ActionManager 的输入边界顺序解释。

如果后续整帧结构把 normalize 合并进 `CooldownRuntime.update_frame()`，仍必须保持它发生在 ActionManager 之前且查询本身无副作用。

## 12. 与动作解释器的连接

动作解释器依赖协调器的只读 Protocol，不查找具体协调器类：

```text
ActionInterpretationContext
├── simulation_context
└── ability_condition_port
```

目标调用方式：

```text
interpreter 识别 E/Q 和 ability_key
-> ability_condition_port.evaluate(...)
-> 公共条件未通过：返回结构化 reject
-> 公共条件通过：继续判断 content 条件
-> content 条件通过：返回 PreparedAction
-> ActionManager 执行最终锁与中断准入
```

不允许角色解释器使用 `SimulationContext.get_system()`、类名字符串或完整 Runtime 查找协调器。推荐由 `ActionManager` 显式持有 `CharacterAbilityConditionPort`，并在构造解释上下文时注入。

当前 `ActionInterpretationResult.reason` 仍是字符串。协调器实现阶段应同步评审结构化拒绝证据的最小扩展；在该扩展落地前，解释器至少使用稳定 reason code，不能把完整中文提示当作机器判断依据。

## 13. 查询不是预留

协调器查询不会冻结冷却次数或元素能量：

- 爆发准入后，实际扣能仍发生在 content 声明的扣能帧。
- 扣能前能量被其他机制降低时，仍由 EnergyRuntime 抛出 `InsufficientEnergyAtSpendError`。
- 冷却开始帧仍由具体能力行为决定；动态冷却不能在公共查询时提前启动。
- 查询结果不能重复提交，也没有 commit 接口。

同帧重复输入不能依赖协调器 reservation 解决。普通动作必须通过具名动作锁防止不合法的并发接受；某项能力何时消费冷却次数则由其真实 content 时序和后续冷却写入接入专题确定。

## 14. 错误与正常阻塞

以下是正常条件结果，不抛异常：

- 没有可用冷却次数。
- 标准元素能量不足。
- 角色使用非标准爆发资源并委托 content 判断。

以下属于错误：

- query 字段非法。
- 角色或冷却 definition 未注册。
- 冷却尚未规范化到查询帧。
- 冷却证据的 key、主体或 frame 与 query 不一致。
- 能量证据指向另一角色。
- 冷却 definition 返回未知 ability kind。

协调器不能捕获宽泛异常并把错误降级为 `shared_conditions_satisfied=False`。领域错误保留原始类型和上下文；跨领域身份或证据冲突使用协调器自己的错误类型。

## 15. Event 与审计

- 查询不发布 Event，因为没有新事实发生。
- 查询不创建长期 coordinator record。
- `CooldownConditionResult` 和 `BurstEnergyConditionResult` 是查询证据，不是领域事实。
- 动作解释器拒绝、ActionManager 拒绝和能力实际释放是三个不同审计概念。
- 后续若需要结果库记录公共条件拒绝，应扩展动作解释或动作决策 payload，不给协调器添加查询事件。

## 16. 组装

目标组装顺序：

```text
创建并初始化 CooldownRuntime
-> 创建 EnergyRuntime
-> 创建 CharacterAbilityConditionCoordinator(cooldown_port, energy_port)
-> 创建 ActionInterpretationContext provider
-> 创建 ActionManager
-> 将 CooldownRuntime 放在 ActionManager 之前推进
```

组装阶段校验：

- 每个真实角色的核心技能冷却 definition 已注册。
- cooldown subject id 与 energy profile 的角色实体 id 一致。
- `elemental_skill` definition 的 kind 是 `ELEMENTAL_SKILL`。
- `elemental_burst` definition 的 kind 是 `ELEMENTAL_BURST`。
- 标准元素爆发存在能量 profile。
- `capacity = 0` 的真实角色由 content 提供对应私有资源准入逻辑，不能静默放行完整动作。

## 17. 验证要求

- 战技冷却可用与不可用。
- 标准爆发：两项均满足、仅冷却不足、仅能量不足、两项均不足。
- 非标准资源爆发返回委托条件，不返回标准能量不足。
- 多个动作变体共享一个 `ability_key`。
- `frame == ready_frame` 时先规范化再查询。
- 未规范化查询失败且不修改冷却状态。
- 协调器查询不产生 Event、不修改 Store、不保存 record。
- 结果阻塞原因顺序稳定且不短路丢失证据。
- query 主体与领域证据主体不一致时失败。
- 解释器公共条件通过后仍可能被 content 条件或 ActionManager 拒绝。
- 查询通过后不预留能量，扣能帧不足仍由 EnergyRuntime 报错。

## 18. 延期事项

- 冷却实际启动、动态基础时长和 duration terms 如何由 Action/content 提交。
- `ActionInterpretationResult` 的结构化拒绝 evidence 最终字段。
- 专属资源的统一只读协议；第一版仍由 content 私有状态判断。
- 同帧 Action 启动写入与 ImpactRuntime 的最终命令顺序。
- 条件拒绝如何投影到公共 EventType 和结果库。
