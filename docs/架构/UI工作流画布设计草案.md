# UI 工作流画布设计草案

> 状态：讨论草案，尚未形成正式架构决策。
>
> 本文记录当前 UI 上层设计讨论形成的方向、约束与待确认问题。内容暂不定义具体业务节点、视觉稿、Flet 控件实现或持久化契约。

## 1. 讨论范围

当前讨论先从设计、交互与工程边界出发，不展开具体项目内容。目标是先确定 UI 的产品形态和交互语言，再讨论具体页面、节点类型与实现技术。

本文覆盖：

- UI 的整体体验目标。
- 无限画布与工作流的核心交互模式。
- 节点的信息结构与空间组织原则。
- 运行反馈、导航和大型工作流的初步方向。
- 后续工程设计需要遵守的分层边界。

本文暂不覆盖：

- 具体工作流的业务语义和节点清单。
- 工作流是否属于 `SimulationConfig` 或其他配置契约。
- 工作流、布局和运行记录的持久化 schema。
- 具体前端库、画布库或新增依赖选择。
- 完整视觉规范、主题与组件实现。

## 2. 当前方向

### 2.1 产品形态

UI 定位倾向于强调探索、即时反馈和快速试错的交互工作台，而不是以固定表单和线性步骤为主的传统配置界面。

核心体验目标为：

> 调整一个条件后尽快看到影响，保留探索上下文，并能够继续调整、比较、回退和复现。

当前优先级包括：

- 反馈紧贴操作。
- 保持探索上下文。
- 支持低成本试错。
- 支持分支、比较和中间结果检查。
- 系统状态可见且可解释。
- 有价值的探索可以保存、恢复和复现。

### 2.2 采用无限画布工作流

当前倾向选择无限画布路线，并以节点工作流作为主要交互模型：

```text
放置节点 -> 配置节点 -> 建立连接 -> 执行工作流
                 |                     |
                 v                     v
          检查中间状态与结果 <- 调整、分支和比较
```

画布不是自由摆放内容的普通白板，而是表达工作单元、数据关系、执行状态和结果的结构化工作空间。

### 2.3 画布即工作流

理解和编辑工作流所需的关键信息必须直接存在于画布上。节点不是配置入口或占位符，而是可阅读、可编辑、可执行的完整工作单元。

明确不采用以下主要交互：

- 选中节点后，必须前往固定属性检查器才能查看或编辑关键配置。
- 节点只显示名称和端口，把真实工作流信息隐藏在侧栏、弹窗或其他页面。
- 用户必须逐个选中节点，才能理解完整工作流。

辅助界面可以负责节点搜索、全局命令和临时工具，但不能成为节点关键语义的唯一载体。

## 3. 设计原则

### 3.1 信息直接可见

- 节点的有效配置默认直接展示。
- 输入、处理规则、输出摘要和运行状态在空间上保持关联。
- 错误尽量显示在对应字段、端口或节点附近。
- 折叠应由用户主动控制，不能因失焦或运行而自动隐藏关键内容。

### 3.2 工作流在未运行时也可读

节点名称、字段、值和连接关系应形成可直接理解的结构。用户不应依赖运行结果或属性侧栏才能判断工作流做了什么。

### 3.3 操作结果可预期

- 相同控件和端口保持相同语义。
- 输入使用连线值还是本地值必须有明确规则。
- 断开连接不能无提示地丢失原有本地配置。
- 输入发生变化后，只把实际受影响的结果标记为过期。

### 3.4 探索可以恢复

- 支持撤销和重做。
- 支持保存、恢复和重置工作区。
- 运行结果能够对应到确定的一组输入。
- 失败和取消不应破坏已有的有效结果或工作流定义。

### 3.5 自由度由结构化规则支撑

无限画布提供空间和流程自由，但节点、端口、连接、分组和执行状态仍需遵守稳定语法，避免工作流退化为无法维护的自由布局。

## 4. 节点信息结构

节点建议采用统一外壳和可扩展内容区，分为四层：

```text
+--------------------------------------+
| 1. 身份层：名称、类型、状态、操作    |
+--------------------------------------+
| 2. 输入层：连接输入与直接填写的参数  |
+--------------------------------------+
| 3. 处理层：规则、选项、关键过程信息  |
+--------------------------------------+
| 4. 输出层：端口、摘要、预览、指标    |
+--------------------------------------+
```

### 4.1 身份层

身份层只承载节点级信息：

- 节点类型和用户定义名称。
- 未运行、等待、运行中、成功、失败或结果过期等状态。
- 节点级运行、停止、复制等高频命令。
- 耗时、缓存命中等简短运行指标。

节点类型与实例名称应分开。例如类型表示稳定能力，实例名称说明该节点在当前工作流中的用途。

### 4.2 输入层

- 输入端口靠近它所控制的具体字段，而不是无语义地集中排列在节点边缘。
- 输入可以来自上游连接，也可以使用节点内的固定值。
- 连接状态、数据来源和本地备用值应直接可见。
- 字段校验错误显示在对应输入附近。

### 4.3 处理层

- 只展示真正影响节点行为的配置。
- 复杂设置按业务语义分段，而不是统一放入不透明的“高级设置”。
- 条件或规则优先使用接近自然表达的行式布局，使节点能够直接阅读。

### 4.4 输出层

- 输出同时呈现端口和当前结果摘要。
- 摘要可以包含数量、警告、时间、耗时或小型预览。
- 表格、图表等大型结果允许在原画布位置扩展。
- 结果详情不应只能通过离开画布或打开固定检查器查看。

### 4.5 节点尺寸

当前建议为：

- 普通节点使用少数几种标准宽度。
- 高度由实际内容决定。
- 表格、图表和时间轴等可视节点允许调整尺寸。
- 输入字段不能因为节点缩小而消失。
- 节点内部尽量避免双向滚动。

节点尺寸规则仍待通过原型验证。

## 5. 画布空间语法

### 5.1 主方向

当前倾向采用从左到右的数据流：

- 左右位置表达依赖先后。
- 上下位置表达并行分支、不同方案或结果比较。
- 对齐的节点可以表达相同处理阶段。
- 执行顺序由连接关系决定，不能依赖视觉位置推断。

节点内部主要纵向排列字段，工作流沿水平方向展开，可以减少两个层级对同一空间方向的竞争。

### 5.2 框架分组

框架用于表达阶段、主题或方案，不只是装饰背景。框架建议支持：

- 名称和简短说明。
- 整体移动。
- 内部运行状态汇总。
- 用户主动折叠和展开。

框架分组仍属于当前画布，不等同于可复用的子工作流。

### 5.3 连线

- 端口位置与具体输入输出字段对齐。
- 连线表达明确的数据方向和关系类型。
- 必要时直接显示名称、类型或数据摘要。
- 不仅依靠颜色区分连接类型，还应结合线型、端口形状或标签。
- 支持转接点、上游或下游突出显示，以及长距离连接整理。
- 数据依赖、执行顺序、条件分支和资源引用不应在没有区分的情况下共用同一种连线语义。

## 6. 画布导航与编辑

大型工作流至少需要以下导航能力：

- 平移与缩放。
- 框选、多选和追加选择。
- 聚焦选中内容。
- 搜索节点并定位。
- 适应全部、适应选中和返回上次视口。
- 可隐藏的小地图或结构概览。
- 关键区域书签。

节点创建建议支持：

- 在画布空白处呼出节点搜索。
- 从输出端口拖到空白处，搜索兼容的下游节点。
- 在连线上插入兼容节点。
- 复制、粘贴、批量移动、分组和批量运行。

远距离缩放可以进入结构概览状态，只显示名称、状态、框架和主要连接；正常编辑比例下应恢复节点完整信息。该行为的阈值和可读性仍需原型验证。

## 7. 运行反馈

初步状态模型为：

```text
未运行 -> 等待 -> 运行中 -> 成功
                    `-----> 失败

成功 + 输入变化 -> 结果过期
```

运行反馈原则：

- 节点标题显示汇总状态。
- 错误信息贴近具体字段或端口。
- 连线可以显示数据是否已产生或已经过期。
- 动画只用于短暂反馈，避免持续流动效果干扰阅读。
- 旧的异步结果不能覆盖由新输入触发的结果。
- 失败、取消、部分结果和过期结果需要成为明确状态，而不是统一显示为加载结束。

## 8. 大型工作流与复用

需要区分：

- 框架分组：组织当前画布上的节点，不形成独立执行单元。
- 子工作流：拥有明确输入输出，可以复用、独立执行和版本化的工作单元。

当前建议让子工作流成为可在原画布内展开的复合节点：

- 收起时显示输入、输出和内部结构摘要。
- 展开后在原位置呈现内部节点。
- 可以进入独立画布集中编辑，但独立画布不应成为理解内部结构的唯一途径。

复合节点的展开方式、版本语义、引用方式和运行边界尚未确认。

## 9. 工程分层建议

画布控件不应同时拥有工作流定义、编辑状态和执行逻辑。后续工程设计至少需要区分：

```text
WorkflowDefinition   持久化的节点、连接和工作流元数据
WorkflowEditorState  选择、视口、拖拽和临时交互状态
WorkflowValidator    类型、连接、循环和配置校验
WorkflowRuntime      调度、执行、取消、状态与结果
```

仍需遵守项目既有模块边界：

- `ui/` 负责画布交互与展示。
- UI 通过 `application/` 的服务门面调用能力。
- UI 不直接访问 SQLite，不直接组装仿真核心对象。
- 画布编辑状态不应泄漏到 `core/`。
- 工作流执行语义及其与现有应用层、任务模型的关系需要另行设计和确认。

在选择画布库或新增依赖前，应先确定工作流数据模型、交互原型和性能验收场景。

## 10. 当前尚未确认的问题

以下内容留待后续讨论：

1. 工作流采用数据流 DAG、显式顺序流程、状态机，还是受约束的混合模型。
2. 连接究竟表达数据依赖、执行控制还是多种类型化关系。
3. 节点的标准宽度、内部布局和可调整范围。
4. 输入连线与本地值之间的覆盖、恢复和校验规则。
5. 子工作流的展开、复用、版本和独立运行语义。
6. 工作流定义、画布布局、运行记录和用户工作区如何分别持久化。
7. 撤销重做以命令、状态快照还是其他模型实现。
8. 大型工作流的性能目标、节点规模和测试基准。
9. 键盘操作、无障碍和非精确指针设备的支持范围。
10. 当前 Flet 技术选择能否满足无限画布、复杂节点和高频交互需求。

## 11. 后续讨论顺序

建议按以下顺序继续：

1. 确定工作流执行语义和连接类型。
2. 确定节点输入、本地值和结果过期规则。
3. 设计复合节点与子工作流模型。
4. 制作不依赖具体视觉风格的交互原型。
5. 通过典型小型和大型工作流验证可读性与性能。
6. 再决定画布技术方案、状态管理方式和持久化契约。
