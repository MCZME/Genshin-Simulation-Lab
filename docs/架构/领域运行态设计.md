# 领域运行态设计

> 状态：已确认；护盾领域第一版已完成迁移，Buff 领域第一版工程闭环已实现，元素能量与技能冷却第一版领域 Runtime 已实现，真实内容 golden case 待补。
> 本文确定有身份和生命周期的领域运行态由对应 `core/systems/<domain>/` 直接拥有。

最后更新：2026-07-14

## 1. 结论

伤害、治疗、护盾、Buff、冷却、元素附着和 ICD 都属于原神游戏机制，但它们不天然共享同一种状态模型。目标结构采用“领域直接拥有，验证后再提取”的方式：

```text
core/systems/shield/
├── ShieldInstanceRef
├── ShieldRecord
├── ShieldStore
└── ShieldRuntime

core/systems/buff/（第一版工程闭环已实现，真实内容待补）
├── BuffInstanceRef
├── BuffRecord
├── BuffStore
└── BuffRuntime
```

每个领域直接定义完整记录、索引、生命周期、命令、计划、提交和事实。

若两个以上已经落地的领域出现相同不变量，再把最小且中立的值对象或提交工具提取到合适的公共位置；不能仅凭字段相似提前建立共享模块。

## 2. 领域直接拥有的原因

不同领域的运行态尚未形成统一且内聚的状态概念：

- `systems/<domain>` 本身就是具体游戏机制的状态和规则所有者，不需要再经过一个“机制系统”。
- 当前护盾和 Buff 已经是确定的完整记录使用者，冷却、ICD 和元素附着仍具有不同状态模型，不能因字段相似提前共享 Store。
- 泛型 Store 容易为了不同领域不断增加可选索引、生命周期和提交策略，最终把领域差异变成共享层例外。
- 动作、空间创建物和其他运行态同样拥有身份与生命周期，但不因此属于统一机制聚合。
- 仓库已经存在实体生命周期值对象；在真实复用关系确认前再定义机制生命周期会制造重叠概念。

因此，共享层是否成立必须由多个真实领域证明，而不是由第一个领域预先假设。

## 3. 领域状态所有权

每个 `core/systems/<domain>/` 必须直接拥有：

- 领域实例引用和稳定序列化。
- 完整领域记录和全部不变量。
- 活动、过期、移除或其他适合本领域的生命周期。
- 领域查询索引和只读 view。
- 创建、刷新、替换、消费和移除命令。
- 不可变 MutationPlan、前值校验和提交入口。
- 已提交的领域结果与事实。

领域 Store 中的一条记录必须足以判断该领域实例是否合法。不得把一个合法实例拆成必须跨 Store 拼接的元数据和组件。

例如护盾目标结构为：

```text
ShieldStore
└── ShieldRecord
    ├── instance_ref
    ├── mechanic_key
    ├── handler_key
    ├── created_frame
    ├── expires_at_frame
    ├── lifecycle_state
    ├── removal_audit
    └── state: ShieldState
```

`ShieldStore` 直接实现完整记录提交，不封装泛型机制 Store。

## 4. 引用与语义

不同语义仍必须分开表达，但不要求使用通用机制引用类型：

- `source_context`：由哪个资产、动作、内容或上游机制产生。
- `creator_ref`：创建时读取谁的属性。
- 领域影响范围：例如护盾的 `protection_ref`。
- 生命周期清理依据：由领域根据自己的记录和规则推导。

不得恢复含义模糊的通用 `owner_ref`。领域需要稳定实例身份时定义自己的强类型引用，例如 `ShieldInstanceRef`；跨领域事件和持久化可以保留领域标识，但不要求所有领域继承同一个运行时基类。

## 5. 生命周期

生命周期属于领域记录，而不是独立全局 Store。

领域可以采用：

- 有限半开区间 `created_frame <= frame < expires_at_frame`。
- 无时间上限、由消费或显式命令移除。
- key 到 ready frame 的专用时间模型。
- 计数与时间窗口组合的专用状态机。

护盾和第一版有限时长 Buff 都使用半开生命周期；Buff 另外确认简单属性 Buff 本身不因等待过期而延长仿真。该结论不构成共享生命周期抽象的充分证据，冷却、ICD 和元素附着也不得为了复用而改造成通用实例。

领域 Runtime 负责在确定的帧阶段准备并提交到期状态。是否因为活动实例延长仿真，也由领域运行时明确声明。

## 6. 命令、计划与提交

content 只能构造领域命令，例如 `ShieldGrantRequest` 或未来 `ApplyBuffRequest`，不能构造或直接写领域 Store 记录。

单领域写入顺序为：

```text
领域请求
-> 纯计算或查询
-> 不可变领域 MutationPlan
-> 校验 Store version 和全部记录前值
-> 一次提交完整记录集
-> 生成领域结果与事实
-> 发布事实
```

计划和 Store API 由领域定义。若版本校验、批量替换等技术实现之后在多个领域完全相同，可以提取小型提交工具，但不因此建立统一领域模型。

跨领域结算由 `core/coordination/<flow>/` 准备多个领域计划，并在禁止外部回调的阶段提交。具体规则见[系统自治与跨系统协调](../决策/系统自治与跨系统协调.md)。

## 7. Event 与后续命令

`EventEngine` 只发布和记录已经提交的事实。事件 handler 不得同步写入领域 Store。

需要由事实触发后续行为时，目标流程为：

```text
已提交事实
-> Trigger/Rule 生成强类型领域命令
-> 同帧下一结算轮次或明确未来帧
-> 对应领域 Runtime 处理
```

通用后续命令队列、同帧轮次上限、循环检测和稳定排序在引入真实触发型 Buff 前单独评审。

## 8. 各领域建模方向

| 领域 | 目标状态所有者 | 当前判断 |
| --- | --- | --- |
| 护盾 | `ShieldStore` | 使用完整 `ShieldRecord`，有稳定身份、容量、冲突和有限生命周期 |
| 限时 Buff / Debuff | `BuffStore` | 正式设计与契约已确认，待独立实现完整 `BuffRecord`、四种应用策略和只读属性 provider |
| 冷却 | `CooldownStore` | 按角色 ability key 保存可用次数和单个活动 ready frame；多充能使用串行恢复链，不建模为通用实例 |
| ICD | 专用 ICD Store | 按来源、组和目标维护计数与时间窗口 |
| 元素附着 | Aura Runtime / Store | 使用专用附着量、衰减和反应状态 |
| 元素能量 | `CharacterEnergyStore` 与 `EnergyTransitQueue` | 角色保存最小当前能量状态；能量领域拥有唯一写入口和在途微粒/晶球调度，不进入通用实例 Store 或 Space |
| 空间创建物 | `Space` 与 `CreatedObjectRuntime` | 继续使用空间实体和实体生命周期 |
| 伤害、治疗 | 对应 Resolver / Runtime | 一次性请求、解析和结果，不创建长期实例 |

## 9. 与属性系统的边界

活动领域实例可以提供 `ModifierProvider` 或其他类型化只读 view。属性系统查询当前有效 provider，但不拥有领域生命周期，也不能在属性查询期间修改领域状态。

provider 从对应领域 Store 的只读视图判断记录是否在查询帧有效。记录移除后 provider 自然不再贡献 term；不向属性系统写入最终面板。

## 10. 与 content 和 application 的边界

- `content/` 构造领域请求、规则和只读 provider，不访问领域 Store。
- `application/assembly/` 创建各领域 Runtime、Store 和跨系统协调器。
- 领域系统不加载 handler，不扫描 content，也不接触资产数据库。
- 缺 handler、请求 schema 错误和不支持的领域能力尽量在组装阶段失败。

## 11. 共享提取门槛

只有满足以下条件，才评审提取中立公共原语：

- 至少两个已经实现并通过领域测试的使用者。
- 共享的是行为和不变量，而不只是同名字段。
- 提取后不需要领域类型开关、可选组件表或通用 patch API。
- 使用者仍由各自 Store 原子拥有完整领域记录。
- 公共 API 能独立测试，并且不会迫使新领域采用不合适的生命周期。

优先提取最小值对象或技术工具。若未来证据确实支持独立公共模块，必须先更新模块边界和项目决策记录。

## 12. 当前实现

护盾领域已完成第一版实现：ShieldStore 直接拥有 ShieldRecord，并由 ShieldMutationPlan 执行完整记录提交；角色受伤时的护盾与血量提交由独立协调器编排。

## 13. 迁移顺序

1. 已在护盾领域实现 `ShieldInstanceRef`、完整 `ShieldRecord` 和直接拥有记录的 `ShieldStore`。
2. 已将角色受伤时的护盾与血量提交移动到独立协调器。
3. 已独立确认简单限时属性 Buff 的设计与稳定契约，下一步实现领域记录、四种应用策略和属性 provider。
4. Buff 第一版实现和测试完成后，再与护盾比较共同不变量；不能仅凭两份设计提取共享原语。
5. 有至少两个已实现真实使用者后，再决定是否提取中立生命周期或提交工具。
6. 在真实触发型内容前评审同帧后续命令队列。
