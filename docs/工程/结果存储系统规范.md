# 结果存储系统规范

> 状态：生效，持续维护。
> 本文规定与结果存储系统相关的工程约定：术语、数据类别边界、目录与文件组织、schema 版本与开发期处理、事件契约变更流程。系统设计见[结果存储系统设计](../架构/结果存储系统设计.md)，表结构与读写协议见[结果库契约](../契约/结果库契约.md)。
> 最后更新：2026-08-12

## 1. 术语约定

正式文档、契约与代码命名统一使用以下术语：

- **模拟输入**：一次仿真要模拟什么——队伍、场景、按键输入轨迹、规则、运行帧数，即当前 `SimulationInput` 的内容；源文件归工作区。
- **项目配置**：项目级 TOML 文件（`config.toml`），保存 `schema_version`、`workspace.data_dir` 等设置。
- **结果存储系统**：本系统正式名称（Results Store）。
- **结果库**：SQLite 具体实现（`infrastructure/results_sqlite/`）。
- **输入快照**：进入仿真的不可变输入副本，随运行记录保存。
- **初始快照**：第 0 帧状态基线，随运行记录保存。

动词统一使用保存/写入/读取/投影/归档/清理。“持久化”不作为正式术语出现在正式文档、契约和代码命名中，日常口语可用。

## 2. 数据类别边界

| 数据类别 | 归属 |
| --- | --- |
| 资产数据 | 独立系统；结果侧只记录 provenance。 |
| 模拟输入源文件 | 工作区/文件存储。 |
| 项目配置 | 工作区，`config.toml`。 |
| 仿真会话/运行记录 | 结果存储。 |
| 摘要数据 | 运行元摘要归结果存储；分析摘要由 analysis 计算。 |
| 事件流 | 结果存储，事实真值层。 |
| 帧快照 | 不存全量逐帧快照；初始快照归结果存储。 |
| 高频状态数据 | 事件流承载变化，基线 + 折叠还原。 |
| 投影数据 | analysis 读取侧；按性能物化。 |
| 任务状态 | 任务系统，独立于结果存储。 |
| 日志 | 独立系统，仅通过关联 ID 关联。 |
| UI 工作区/工作流定义 | UI 系统，只引用 `session_id`。 |
| 分析报告/导出物 | 导出/文件存储。 |

## 3. 目录与文件组织

- `config.toml` 位于项目根目录，使用 TOML（支持注释），程序写入采用 `tomlkit`；第一批配置项为 `schema_version` 与 `workspace.data_dir`，`kind`、`meta` 后续按需添加。`config.example.toml` 是提交到仓库的配置示例模板，`project init` 从示例复制生成 `config.toml`，后者不进入 git。
- 数据目录由 `workspace.data_dir` 指定，默认 `data/`；子目录按约定推导：`inputs/`、`results/`、`exports/`、`templates/`、`workflows/`，不逐个配置。
- 资产库位置独立（默认 `data/assets/`），不随 `data_dir` 搬迁；它是生成物，不视为用户数据。
- 模拟输入文件放在 `<data_dir>/inputs/`，一个 JSON 文件一个输入，平铺不嵌套；文件内 `input_key` 定身份，文件名仅作展示；发现方式为扫描目录，第一版不做索引。
- 工作流定义文件放在 `<data_dir>/workflows/`，一个 JSON 文件一个工作流，保存配置、模拟与分析节点定义及画布布局。
- 结果库位于 `<data_dir>/results/results.db`。
- 日志文件位于 `<data_dir>/logs/`，归日志系统所有；本规范只在目录约定上联动，不定义日志存储细节（见[日志系统设计](../架构/日志系统设计.md)）。
- `project init` 会创建上述工作区目录骨架并初始化结果库；后续命令使用目录时仍允许按需懒创建。

## 4. schema 版本与开发期处理

- 结果库 schema 版本（`result_db_meta.schema_version`，库级）与输入 schema 版本（`input_schema_version`，运行级）语义分离。
- 事件契约不设独立版本：事件类型名冻结 + payload 只增不改。
- 开发阶段（未发布正式版）：不做自动迁移，版本不兼容时明确报错，由用户显式重建结果库，不静默覆盖。
- 发布正式版后：设计逐级迁移，迁移前备份、单事务执行；第一版仅允许兼容变更（加表、加列、加索引）。

## 5. 事件契约变更流程

- `EventType.name` 冻结：只允许追加，不允许改名或复用；语义变化走新事件类型。
- `payload.to_dict()` 只增字段、不改语义；破坏性变更必须走新事件类型。
- 状态变化事件必须携带 `before/after` 或稳定引用证据（HP、能量、Buff、护盾、Aura 等逐领域核对），保证可还原。
- 新增或修改事件契约时，同步更新[事件类型](../架构/事件系统/事件类型.md)、[结果库契约](../契约/结果库契约.md)与持久化测试。
- 初始快照 provider 与领域还原覆盖登记在[结果库契约](../契约/结果库契约.md)第 5.1 节；新增/移除 provider、调整证据事件或排除边界时，同步该表、[事件类型](../架构/事件系统/事件类型.md)与[分析系统契约](../契约/分析系统契约.md)。

## 6. 文档职责

## 7. 变更同步要求

改动结果存储系统的边界、schema 或事件契约时，必须同步：

- 本规范。
- [结果存储系统设计](../架构/结果存储系统设计.md)与[结果库契约](../契约/结果库契约.md)。
- [文档入口](../文档入口.md)、[项目决策记录](../决策/项目决策记录.md)等受影响文档。
