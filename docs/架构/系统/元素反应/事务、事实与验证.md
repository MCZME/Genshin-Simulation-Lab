# 元素反应事务、事实与验证

> 状态：生效；已按当前生产协调器的计划、校验、提交和发布顺序整理。

最后更新：2026-08-02

## 1. 事务单位

原子边界是一个 `ElementalInteractionBatch`，不是整个 Action，也不是由反应派生出的完整 root chain。

一个 batch 固定：

- 当前帧和 root work 身份；
- 目标级 work 顺序；
- ICD、Aura、Reaction、ReactionState 与可选 Space 计划；
- 当前 Damage Impact 的预备记录；
- 反应 occurrence、决策步骤和应用记录引用。

同帧后续 settlement round 属于新的 batch。前一批已经发布的事实不会因为后续批失败而回滚。

## 2. Planner 与 seal

普通元素交互使用以下计划器：

```text
AuraIcdBatchPlanner
AuraBatchPlanner
ReactionBatchPlanner
ReactionStatePlanner
可选 Space Planner
```

Reaction 的公共入口是：

```text
ReactionRuntime.begin_batch(frame, batch_id)
-> ReactionBatchPlanner.prepare(request)
-> ReactionBatchPlanner.seal()
-> ReactionMutationPlan
```

`ReactionMutationPlan` 保存 `operation_id`、`frame`、排序后的 `interaction_ids`、`expected_store_version`、`resolutions` 和可选成立 Gate 计划。

## 3. 预校验

所有写入在第一次提交前完成准备和校验。当前主元素交互路径依次校验：

1. ICD plan；
2. Aura plan；
3. Reaction occurrence plan；
4. Reaction Store mutation plan；
5. Aura 与 ReactionState Link 一致性；
6. 可选 Space plan 与实体绑定一致性；
7. 当前 Damage Impact 的完整预备结算。

Damage 预备阶段会读取 Damage Profile、属性和增幅/激化反应输入并生成待提交记录。激化还必须校验当前 Impact、触发元素和 `damage_formula.catalyze_additive` Profile。任何一步失败时，前述领域都不得提交。

## 4. 当前提交顺序

全部预检通过后，当前主路径使用以下顺序：

```text
ICD commit
-> Reaction occurrence commit
-> Aura commit
-> Reaction Store commit
-> 可选 Space commit
-> Damage records commit
```

这里的 Reaction occurrence commit 主要冻结 operation/interaction 幂等身份；普通蒸发、融化不创建长期状态，也不增加 Reaction Runtime version。Reaction Store commit 用于状态、Gate 等后续能力，普通蒸发、融化通常没有对应状态变更。

冻结与碎冰的 Aura/ReactionState 变更在逻辑上属于同一原子提交。提交顺序虽然先 Aura、后 Reaction Store，但首次提交前已经冻结两侧前值并验证最终投影；任何单边计划或悬空 Link 都会在写入前失败。

commit 只应用已准备好的内存变更，不查询其他系统、不调用机制 handler，也不发布事件。

## 5. 事实发布顺序

提交完成后才发布已发生事实。主元素交互路径的相对顺序为：

```text
AURA_ICD_RESOLVED
-> AURA_APPLIED（若有普通附着）
-> AURA_INTERACTION_RESOLVED（若有精确消费）
-> REACTION_OCCURRED（按 DecisionSequence 顺序）
-> ReactionState 领域事实（若有）
-> DAMAGE_RESOLVED（若有当前伤害）
-> ELEMENTAL_INTERACTION_RESOLVED
```

`AURA_DEPLETED` 由 Aura 自己在相应衰减或状态变化路径发布，不应为了反应流程伪造。

事实发布期间启用 Aura 写保护。同步事件回调可以读取已提交状态，但不能创建新的 Aura 写计划、直接施加 Aura 或递归推进当前元素结算。

即时剧变 Effect Group 的普通事实顺序为可选 Buff 移除/应用、Damage、最终元素交互记录。若超载钝击在 group 内形成碎冰，则先发布 Aura 消费、碎冰 occurrence 和 ReactionState 变化事实，再发布本 group 的 Damage；碎冰 Damage 在子 round 单独发布。

冻结自然到期不产生新的 `REACTION_OCCURRED`。生命周期 batch 先提交 linked Aura 移除与 ReactionState 变化，当前路径在两侧提交完成后发布 ReactionState 事实；按需留下的 `FreezeRecoveryState` 只是速率历史，不是活动冻结事实。

感电周期 root 在帧规范化时推进状态游标并形成独立 scheduled root batch；其后续 Effect Group 再原子准备逐目标 Gate、条件水雷消费、跨目标来源接管和 Damage。周期脉冲不伪造 occurrence；Gate blocked 不消费 Aura、不接管来源，但不回退已推进的周期游标。

## 6. 幂等与 stale 防护

Reaction 计划同时使用三类保护：

- `operation_id` 防止同一计划重复提交；
- `interaction_id` 防止同一元素交互经不同批次重复提交；
- `expected_store_version` 拒绝基于过期 Reaction 状态准备的计划。

无状态反应提交不增加 version，但仍检查准备时捕获的 version。这样可以拒绝与同批外状态变更冲突的旧计划，同时避免为 occurrence 创建伪状态版本。

## 7. 记录与审计

`ElementalInteractionBatchRecord` 至少保留：

- batch、root work、帧和 settlement round；
- work、ICD request、Aura interaction、occurrence 和 Damage request 引用；
- Reaction 决策步骤及候选 key；
- Effect group、状态、Gate 和空间实体相关引用；
- 最终成功或正常阻止结果。

Damage 的通用反应区审计另保存基础倍率、元素精通、精通收益、反应加成和最终乘数。Reaction occurrence 与 DamageResult 通过 `occurrence_ref`、`reaction_profile_key` 和 `target_impact_ref` 关联。

## 8. 同帧 Effect Group 事务

一个 Effect Group 是独立原子 batch，不拆成逐目标提交。协调器必须在第一次写入前完成：

- 范围候选、relation、capability 和 `target_order` 冻结；
- 可选状态型 Reaction、Aura 与 ReactionState 计划；
- 每目标 Damage Gate；
- 可选 Buff 计划；
- Damage 与角色受伤计划；
- 跨领域身份、前值和 Link 校验。

Gate blocked、关系不适用和 capability 不支持是目标级正常结果。缺端口、Definition、Profile、adapter、非法公式输入或 stale plan 是技术错误，阻止整个 group 提交。round 1 失败不补偿撤销 round 0。

## 9. 验证要求

公共 Reaction 基础至少覆盖：

- Registry 重复 key 与缺失引用；
- Definition 签名/Profile 方向不一致；
- Planner 重复 interaction/order、错误帧和 seal 后写入；
- stale plan、重复 operation 和重复 interaction；
- 空决议不产生 occurrence；
- 无状态 occurrence 不推进 Reaction version；
- Damage 预检失败时跨领域零提交；
- 事实顺序与写保护；
- 快照、序列化和稳定身份。
- Aura/FrozenState Link 的原子创建、刷新、自然到期和碎冰移除；
- `FreezeRecoveryState` 不参与活动冻结查询且不单独延长仿真；
- 碎冰 `30/2` Gate 只阻止伤害，不撤销状态消费。
- 感电 `30/1` Gate、`0.4 GU` 条件双消费、13 米传播和周期 root 的事实顺序。
- 激化 `1:1` 消费、Quicken 覆盖身份、附加值审计、复合步骤和类草燃烧 Link 的事实顺序。

各反应的精确数值与纵向验证分别记录在对应反应专文和契约中。即时剧变公共验证还必须覆盖范围稳定性、Gate 窗口、跨目标原子性、Buff/Damage 解耦、follow-up round 和事实写保护。
