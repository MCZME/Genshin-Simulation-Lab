# 结果存储系统设计

> 状态：正式规范。
> 本文定义结果存储系统的职责与数据分层：结果数据为何以运行记录、事件流和初始快照为真值，派生查询如何还原任意帧状态，以及与结果库、分析、任务系统的边界。
> 最后更新：2026-09-05。

结果存储系统是“结果存储系统”（Results Store）这一职责域的正式名称，负责保存一次仿真运行产生的完整结果数据；其 SQLite 实现称为结果库（`infrastructure/results_sqlite/`）。表结构、schema 版本、写入读取协议与错误语义见[结果库契约](../契约/结果库契约.md)，工作区目录与文件组织见[结果存储系统规范](../工程/结果存储系统规范.md)。

## 1. 定位

结果存储系统支撑查询、分析、复盘与结果对比。它回答三个问题：

- 这次运行是谁、什么时候跑的（运行记录）。
- 用了什么输入和什么版本的资产（输入快照与 provenance）。
- 运行过程中发生了什么、任意时刻状态如何（事件流与初始快照）。

明确不在范围内：

- 资产库：只读生成物，独立系统。
- 日志：工程运维数据，独立系统。
- UI 工作区与工作流定义：归 UI 系统，只引用 `session_id`，不拥有结果。
- 项目配置源文件：归工作区文件存储。
- 分析报告与导出物：归导出 / 文件存储。

## 2. 结果数据的目的

- 结果数据服务于分析与可视化。
- 结果数据的第一职责是还原模拟的整个过程；只有保证可还原，才可以进行分析。
- 还原依靠存储的事实（事件流 + 初始快照），不依靠重跑。
- 复现不等于历史保真：用当前引擎重跑旧输入得到的是新结果。重跑只能作为验证手段或显式“重新计算”动作（生成新的运行记录），不能作为查看历史的方式。

## 3. 真值层与派生层

真值层（存储，成功后不可变）：

- 运行记录：`session_id`、状态、时间、输入快照、provenance、运行元摘要。
- 事件流：过程事实，按 `ordinal` 有序。
- 初始快照：第 0 帧状态基线。

派生层（读取侧计算，不落库）：

- 分析摘要：总伤害、DPS、反应统计、覆盖率等。
- 时间序列：伤害曲线、HP / 能量曲线、Buff 覆盖等。
- 任意帧状态视图。
- 伤害事件完整审计视图。
- 跨运行对比数据。

物化（可选）：跳变表（jump track）等派生轨道只在具体查询被证明慢或高频时建立；物化产物永远可重建，不进入真值 schema。

## 4. 数据类别边界

| 数据类别 | 边界结论 |
| --- | --- |
| 资产数据 | 独立系统；结果侧只记录 provenance。 |
| 模拟输入源文件 | 归工作区；扫描 `inputs/` 目录发现，`input_key` 定身份，平铺不嵌套。 |
| 项目配置 | 归工作区 `config.toml`；结果侧不拥有。 |
| 仿真会话 / 运行记录 | 运行前分配 `session_id`；成功后不可变；失败 / 取消留最小记录。 |
| 摘要数据 | 运行元摘要落结构化列；分析摘要读取时计算。 |
| 事件流 | 事实真值层，存结果库表；文件化归档为预留方向。 |
| 帧快照 | 不存全量逐帧快照；初始快照作为状态查询基线。 |
| 高频状态数据（HP / 能量等） | 不按帧存数值；事件携带 `before/after`，基线 + 折叠还原。 |
| 投影数据 | 投影不是真值；归分析查询执行器读取侧；按性能物化。 |
| 任务状态 | 归任务系统；`job_id ↔ session_id` 单向关联。 |
| 日志 | 独立；仅通过关联 ID 关联。 |
| UI 工作区 / 工作流定义 | 独立；只引用 `session_id`，不拥有结果。 |
| 分析报告 / 导出物 | 归导出 / 文件存储；可再生成。 |

## 5. 运行生命周期

```text
运行开始前分配 session_id
-> 组装并运行仿真（core 发布事件、导出帧快照）
-> 执行器订阅事件并按记录规则收集
-> 成功：写入完整运行记录（输入快照、初始快照、元摘要、provenance）+ 事件流
-> 失败/取消：写入最小运行记录（状态、时间、输入快照、错误），不写事件流与元摘要
-> 运行记录不可变，同一 session_id 不允许覆盖
```

## 6. 存储组织

结果库承担真值存储：运行记录、输入快照、初始快照与事件流位于 `<data_dir>/results/results.db`，事件流与运行记录同库同事务。

事件流文件化归档是预留方向（单次运行超限、结果库总体积超限、批量 / 长仿真模式触发；文件不可变并带校验；读取透明；删除结果联动清理），当前不实现。

## 7. 模块边界与依赖

- `core/events/`、`core/snapshots/`：生成事实与快照，不负责存储。
- `application/execution/`：订阅事件、组装运行记录、调用写入协议。
- `infrastructure/results_sqlite/`：SQLite 实现（schema、writer、repository、归档预留）。
- `application/services/`：对外读取门面与帧状态折叠用例。
- 分析查询：查询计划与节点运行时执行器提供读取侧派生，用例门面在 `application/services/`；派生结果表，不写库。完整边界见[分析系统设计](./分析系统设计.md)。

### 7.1 与任务系统的关系

- `job_id ↔ session_id` 单向关联：任务侧持有 `session_id`，结果库不存 `job_id`。
- 失败信息分工：结果库只留 `error_code` / `error_message` 摘要；完整堆栈与调度细节归任务系统与日志。

## 8. 还原与查询模型

- **事件层面查询**：按 `(session_id, frame)` 或 `event_type` 过滤读取事件流。
- **状态层面查询**：任意帧值 = 初始快照基线 + 折叠该帧前的状态变化事件（依赖 `before/after` 证据）。
- **高频状态数据**（HP / 能量等）：不按帧存数值；事件流本身即稀疏变化记录。
- **性能优化**：跳变表（jump track）物化“最后一次变化”索引，供任意帧状态查询和曲线渲染加速；可重建。

### 8.1 帧状态投影

- `frame N` 状态定义为：第 0 帧初始快照作为基线，按 `ordinal` 顺序应用 `frame <= N` 的状态变化事件后的帧末状态。
- 帧状态属于派生层，不新增第二份状态真值，不改变仿真计算。
- `team` 只表达队伍身份与场上角色；角色生命、能量、属性面板、Buff、护盾、附魔、冷却和内容状态由对应领域事件折叠。
- 响应通过 `coverage` 逐组标注 `folded` 或 `baseline_only`；`coverage` 是必填字段，语义见本节。
- 折叠范围：
  - 已折叠：`team`、`characters.health`、`characters.energy`、`characters.attributes`、`characters.buffs`、`characters.shields`、`characters.infusion`、`characters.cooldowns`、`characters.content_states`。
  - 仅基线：`aura`、`aura_icd`、`reaction`、`space`。
  - 不作为帧状态还原范围：移动状态、动作实例完整生命周期、输入会话和随机状态。
- 各领域变化证据、排除边界与 provider 登记以[结果库契约](../契约/结果库契约.md)第 5 节为真值；API 响应形状见[UI API 契约](../契约/ui/UI%20API%20契约.md)第 8 节。
