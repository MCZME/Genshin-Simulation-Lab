## 2. 重建目标

当前项目将进入归档与迁移阶段：

1. 归档当前项目。
2. 创建新项目。
3. 确定新项目架构与管理模式。
4. 逐步迁移当前项目中仍然有效的内容到新项目。

新项目不是简单重写旧代码，而是在保留有效概念的基础上重新整理边界、数据层和应用形态。

## 3. 已确认决策

### 3.1 产品方向

- 新项目核心仍然是仿真引擎。
- 应用端从简单伤害计算器扩展为更广义的分析工具。
- 分析能力围绕仿真结果、战斗复盘、参数扫描和结果对比逐步展开。

### 3.2 技术与项目管理

- UI 继续使用 Flet，但具体 UI 方案暂缓设计。
- 新项目采用单仓库单包。
- Python 包名暂定 `genshin_sim`。
- 使用 `src/` 布局。
- 使用 `uv` 管理项目。
- `pyproject.toml` 作为项目配置入口。
- 质量工具确定为 `ruff`、`pyright`、`pytest`。

### 3.3 数据源

- 新项目数据库统一使用本地 SQLite。
- 静态资产库使用 SQLite，作为正式运行时携带的只读生成产物。
- 运行期结果库使用 SQLite，并与基础资产库职责分离。
- 基础资产数据来源确定为 Project Amber / Yatta 当前默认数据。
- 已实现 `infrastructure/assets_project_amber/` 源站适配层，用于抓取开发期 raw JSON cache 并转换为标准资产 manifest。
- 资产数据构建流程确定为 `genshin-sim assets fetch-source` -> `genshin-sim assets build-manifest` -> `genshin-sim assets audit-manifest` -> `genshin-sim assets build --manifest` -> `genshin-sim assets validate`。
- 原 MySQL 服务器已销毁，新项目不再依赖旧 MySQL。

### 3.4 基础资产数据库

- 资产库作为只读生成产物存在。
- 不设置 `raw_assets` 表。
- 采用结构化索引表与 JSON Payload 混合模型。
- `asset_key` 使用 `{asset_type}:{source_id}` 格式。
- `handler_key` 与 `asset_key` 分离，用于绑定仿真代码实现。
- 真实资产若尚无行为实现，`handler_key` 默认保持为空；`generic.noop` 与 `generic.test_*` 只用于测试或占位，不代表真实机制已经实现。
- 技能倍率使用 `scaling_json`。
- 武器、天赋、命座、圣遗物等复杂效果使用 `params_json`。
- `sim-core` 不直接访问 SQLite，而是依赖 `AssetRepository` 协议。

详细方案见：[资产数据库设计总结](../契约/资产数据库设计.md)。

### 3.5 基础资产范围

- 角色、武器、圣遗物等数据进入基础资产数据库。
- 敌人基础抗性/等级信息不接入基础资产数据库。
- 多语言文本第一版不纳入基础资产数据库。
- 复杂机制行为由仿真代码实现；数据库只保存参数和处理器标识。

### 3.6 模块边界

新项目在 `src/genshin_sim/` 下采用以下顶层模块：

- `core/`
- `content/`
- `assets/`
- `infrastructure/`
- `application/`
- `analysis/`
- `ui/`
- `cli/`

核心原则：

- `core/` 是纯仿真运行时核心，不依赖数据库、UI、应用层或具体内容实现。
- `content/` 保存具体角色、武器、圣遗物和 handler 实现。
- `application/` 负责编排 UI/CLI、资产库、内容实现、仿真核心、结果库和分析能力。
- `infrastructure/` 保存 SQLite、文件存储、日志等具体技术实现。
- `analysis/` 负责结果加工、聚合、对比和报告模型。
- `ui/` 作为 Flet 入口，通过 `application/` 调用能力；具体 UI 设计暂缓。
- `core/space` 使用统一的轻量空间实体表示当前场上角色空间实体与多个简单目标点位；内容创建空间对象运行态也归入 `core/space`，并复用 `core/entity_states/lifecycle.py` 的通用生命周期值对象；目标不在空间层建模复杂体型、多 hitbox 或碰撞。
- 按键输入事实在组装阶段由 `InputTraceCompiler` 配对为不可变 `InputSessionPlan`；`ActionManager` 按帧处理 PRESS、RELEASE、派生 HOLD 和 CANCEL。完整计划中的未来 release 不向解释器提前暴露。
- 不再保留 `TeamActionController`。`ActionManager` 统一拥有运行时输入会话、解释器调用、动作准入、具名锁、动作实例和生命周期；它通过 `ActionInterpreterRegistry` 路由输入，不硬编码切人键或具体角色动作含义。
- 动作是否发生、动作类型和动作开始帧由输入会话固定绑定的队伍或角色解释器决定。解释器只返回 `ActionInterpretationResult`、`PreparedAction` 或语义化控制命令，不直接修改动作实例或提交动作状态。
- 元素战技与元素爆发解释器通过显式 `CharacterAbilityConditionPort` 查询冷却与标准元素能量公共条件，再判断 content 私有状态和专属资源；`ActionManager` 仍负责锁、中断、会话和实例创建的最终准入。
- 所有 Action 在组装阶段注册到 `ActionRegistry`；解释器只返回稳定 `action_key` 和准备参数。`ActionManager` 获取不可变 Action 定义后创建 `ActionInstance`，实例持有本次动作的可变 `action_state`。
- 所有被接受的动作都创建 `ActionInstance`，包括切人。切人由 `TeamActionInterpreter` 准备 `TeamSwitchAction`，再由动作实例修改 `TeamRuntimeState` 并同步 `player:active`，不再由 SpaceRuntime 动作消费器执行。
- HOLD 始终先交给原输入会话绑定的解释器；解释器可以继续等待、启动动作或返回控制已有实例的语义命令。ActionManager 同时独立逐帧调用 Action 推进动作运行态。
- 动作冲突不再使用单一全局 busy。Action 声明具名锁和中断策略，ActionManager 完成最终准入检查，并在全部冲突可中断时原子取消旧实例和创建新实例。
- 解释器不得回溯生成开始帧早于当前仿真帧的动作请求；真实角色缺少解释器或其声明的 Action 时应在组装阶段报错。
- `Space` 保存 `player:active`、`target:*` 与内容创建实体的空间实体；`TargetRuntimeCollection` 由 `SpaceRuntime` 持有并管理多个简单目标运行态；`TargetRuntimeState` 第一版只保存 `scene.targets` 已有的目标 id、等级、抗性和空间实体关联，不引入生命值、韧性、元素附着等尚未确认的机制状态。
- `core/` 不保留独立 `summons` 模块。游戏语义上的召唤物、场地物或临时造物若存在于战场空间中，应作为带生命周期的空间实体处理；无空间位置的持续逻辑归机制、状态或 hook。
- Action 在运行过程中产生 `ActionImpactPoint`。动作索敌只负责选择瞄准目标与攻击方向；伤害 Impact 到期时再由 `ImpactRuntime` 按实际 AOE 和当前空间状态解析全部受击目标。
- Action、Reaction、周期状态和空间实体产生的伤害统一进入 Damage Impact 流程；Reaction 不直接构造 `DamageRequest`，也不拥有独立伤害结算入口。
- `ImpactFactory` 接收 `ActionImpactContext` 并展开为真实 `ImpactRequest`，不再使用 `ImpactRequest(kind=action)` 作为临时入口；反应生成的 Damage Impact 由元素结算协调器在下一 settlement round 交给同一 Impact 目标解析与机制分发流程。
- `content` registry 第一版按角色、武器、圣遗物和 impact 拆分专用 runtime request 与创建入口，不保留泛化 `RuntimeHandlerRequest`。
- `SimulationAssembler` 收集 `ContentRuntimeContribution` 并构造 `RuntimeContentBundle`，再拆分构造 `ActionInterpreterRegistry`、`ActionRegistry`、`CharacterAbilityConditionCoordinator`、解释上下文 provider、`ImpactDispatcher`、`ImpactRequestDispatcher`、`ActionManager`、`ImpactRuntime`、`CreatedObjectRuntime` 和 `ContentStateStore`；`core/` 不接触完整内容贡献对象。
- 当前 content 验证阶段只确认“资产 -> `handler_key` -> content contribution -> runtime 注入”的装配链路，不验证真实伤害、治疗、Buff、反应或属性修饰数值。

详细方案见：[新项目模块边界设计](../架构/模块边界设计.md)。

### 3.7 仿真快照与结果库

- 新项目允许 `sim-core` 生成快照。
- 快照用于复盘、审计、分析和调试。
- 快照不是资产数据，也不是项目配置文件。
- 快照生成属于 `core/`，快照持久化属于 `infrastructure/`。
- 运行期结果库与基础资产库职责分离。
- 所有仿真都保存完整结果数据，不区分 `summary_only` 与 `recorded` 模式。
- 运行期结果库参考旧项目中较完善的 SQLite 持久化、事件流与投影表方案，按新模块边界重新落位和整理。

### 3.8 重设计与参考迁移分层

旧项目能力按以下方式处理：

- 资源数据库：重新实现。
- 模拟架构中的按键输入与动作解释：重新设计并重新落位。
- UI：完全重设计。
- 其余游戏逻辑：保留有价值的行为目标、算法思路和测试入口，按新边界、契约与验证要求参考迁移。
- “直迁”不再作为正式分类；旧代码即使可以局部复用，也不能绕过新架构和数值可信度要求。

能力覆盖与当前迁移工作流分别见：[旧项目能力盘点](../工程/旧项目能力盘点.md)和[迁移阶段安排](../工程/迁移阶段安排.md)。

### 3.9 日志系统

第一版日志系统采用 Python 标准库 `logging`，不新增第三方依赖。

已确认原则：

- `infrastructure/logging/` 保存日志配置、handler、formatter、输出路径和轮转策略。
- CLI 与 UI 作为入口负责初始化日志。
- 其他模块只使用标准库 `logging.getLogger(__name__)`，不依赖 `infrastructure/logging`。
- 工程日志不替代 `core/events`、快照或结果库。
- 日志配置不进入 `SimulationConfig`。

详细方案见：[日志系统设计](../架构/日志系统设计.md)。

### 3.10 领域运行态与共享抽象

有身份和生命周期的运行态由对应 `core/systems/<domain>/` 直接拥有：

- 每个领域直接定义强类型实例引用、完整记录、生命周期、索引、命令、计划和提交入口。
- 护盾由 `ShieldStore` 原子拥有完整 `ShieldRecord`，不再拆分为全局实例 Store 与能力组件 Store。
- `source_context`、`creator_ref` 和领域 affected scope 使用不同语义，废弃含义模糊的通用 `owner_ref`。
- capability 是领域 Runtime 暴露的类型化只读协议，不是实例上的单一字符串字段。
- Buff、冷却、ICD 和元素附着分别设计自己的状态模型；不能为了复用护盾记录而进入通用 Store。
- 只有至少两个已实现领域证明了相同不变量，才提取中立值对象或提交工具，不因字段相似预建共享模块。
- 状态先按领域计划提交，事实后发布；事件回调不能同步写入当前结算。

技术边界见[领域运行态设计](../架构/领域运行态设计.md)；所有原神游戏机制的设计、数值可信度和验证要求见[原神游戏机制实现规范](../工程/原神游戏机制实现规范.md)。

### 3.11 属性系统架构

属性系统采用确定性的查询与解析模式，不保存可任意修改的最终角色面板：

- 公共属性由 `core/attributes` 定义并保持封闭稳定；content 只允许注册自身命名空间内的私有属性。
- 属性来源分为 primitive base、static modifier、runtime modifier 和 derived attribute；原始值在组装阶段冻结，派生值在查询时解析。
- modifier 通过结构化 term 和有限固定阶段贡献数值，不直接修改属性或拥有生命周期。
- 不同属性绑定明确 `ResolutionPolicy`，由 policy 决定允许阶段、聚合规则和上下限，不使用一套万能公式。
- `AttributeQuery` 保存结构化主体、帧、标签和来源上下文；modifier provider 根据 query 判断是否贡献 term。
- 属性依赖通过 resolution session 管理，统一提供 memo、审计和循环检测。
- 属性默认实时查询；快照由使用属性的动作或机制显式创建，缓存不作为属性真值来源。
- 当前生命、当前能量、Buff、冷却、附着和 content 私有计数等运行态不作为普通公共属性。

架构说明见：[属性系统架构](../架构/属性系统设计.md)。

具体公共 key、模型字段、枚举、解析公式、错误和装配映射见：[属性系统契约](../契约/属性系统契约.md)。

### 3.12 伤害系统架构

当前伤害公式代码只实现非反应直接伤害；统一 Damage Impact 目标契约已经冻结，代码按该契约迁移：

- `core/systems/damage/` 保存类型化请求、修饰项、公式族 policy、完整公式、resolver 和同步请求处理入口。
- 一次 Damage Impact 先通过 Space 解析实际 AOE 目标，再为每个目标构造一份单目标 `DamageRequest`；Damage 不拥有索敌、AOE 或目标集合判断。
- Damage Impact 使用稳定主攻击标签、附加攻击标签、打击类型、远近类型、伤害元素、基础元素量、ICD 衰减组/标签和伤害参数引用。角色、武器和显示简称不在每次请求中重复保存。
- 主攻击标签通过 `DamageProfileRegistry` 选择 Damage Profile，Profile 再选择完整公式；`DamageType` 不再作为上游或 content 显式填写的请求字段。通用、激化、剧变和月反应仍作为 Damage 内部完整公式结构存在。
- `strike_type=BLUNT` 是碎冰的稳定攻击侧证据；Reaction 不读取武器类型或显示名称推断碎冰。
- `elemental_amount=0` 表示仍可造成对应元素伤害，但不产生元素施加；正元素量经过 ICD 后与目标 Aura 决定是否发生元素反应，不设置“是否允许触发 Reaction”开关。
- `AttributeResolver` 提供属性真值，`DamageResult` 保存不可变公式结果和审计；护盾与生命变化属于后续伤害应用结果。
- 第一轮只注册 `GENERAL` 公式；通用公式包含 component 倍率、统一基础伤害固定加值、增伤、暴击、恒等反应、防御和抗性区。
- `final_multiplier` 已从伤害 modifier stage 移除；调试倍率通过 `DebugDamageAdjustment` 显式构造注入，生产默认 `1.0`，content 不得使用。
- 防御区按 `(1 - 无视防御) * (1 - 防御减免)` 作用于目标等级防御因子；抗性使用旧项目迁移基线的分段 policy。
- 暴击由注入式 `CriticalDecisionProvider` 决定；第一版组装器默认固定不暴击，不使用全局随机数。
- `DamageModifierProvider` 是无副作用纯查询协议，支持稳定顺序和 stacking group；动态 provider 生命周期由对应领域 Store 管理。
- 现有带结构化 `params.damage` 的 `ImpactKind.DAMAGE` 仍由 `ImpactRequestDispatcher` 转交 `DamageRequestHandler`，迁移后由类型化 Damage Impact Spec 替代自由 `params.damage`。
- 结算后发布 `DAMAGE_RESOLVED` 事实事件；角色伤害由上游适配为 `CharacterIncomingDamage`，再由角色受伤协调器应用到护盾和血量。协调器不参与或反馈伤害计算。
- 第一版不改变结果库 schema，完整审计先保留在 core 结果模型和事件 payload。
- 后续完整公式结构分为通用伤害、激化反应伤害、剧变反应伤害和月反应伤害；增幅反应仍由通用公式的反应区处理，超激化和蔓激化使用独立激化公式。
- 伤害处理按“主攻击标签 -> Damage Profile -> 完整公式 -> 可复用公式族”分层；附加攻击标签只参与条件与修饰，不与主标签混成无序集合来决定攻击身份。
- 通用倍率区只区分属性倍率 component 与统一的基础伤害固定加值；普通固定加值不再按请求、内容效果等来源拆成不同数值字段，来源差异保留在 term 审计中。
- 月反应内部公式和可复用公式族尚未确认，必须在可信机制来源和 golden case 完备后评审。

详细方案见：[伤害系统设计](../架构/系统/伤害系统设计.md)。

### 3.13 生命值系统架构

第一版生命值系统只实现角色当前生命：

- `CharacterRuntimeState.health` 保存角色当前生命，`TargetRuntimeState` 不增加生命字段。
- 角色最大生命继续由 `AttributeResolver` 查询 `stat.hp.max`，当前生命不注册为公共属性。
- 组装器在 frame 0 查询每个角色最终最大生命，并以满血创建 `HealthState`。
- `CharacterHealthStore` 和 `HealthRuntime` 只接受 `AttributeSubjectKind.CHARACTER`。
- `HealthRuntime` 提供角色承伤、已结算恢复量应用和直接扣血三个写入口，并返回统一的 `CharacterHealthChangeResult`。
- 有效角色生命变化发布 `CHARACTER_HEALTH_CHANGED`；满血恢复、零伤害和被最低生命限制完全阻止的扣血不发布生命变化事件。

- 生命值系统本身不实现治疗公式、护盾、生命之契、死亡、击败、复活、目标移除或索敌过滤；治疗与护盾通过类型化 adapter 进入现有生命写入口。
- 结果库继续使用通用事件 JSON，不新增生命值专用表，也不升级结果库 schema。

### 3.16 角色受伤协调

- 角色受伤协调器负责把已经完成计算的角色伤害应用到护盾和血量，不归 ShieldRuntime、HealthRuntime 或 DamageSystem 单独拥有。
- `CharacterIncomingDamage` 只描述实际角色目标和已完成计算的 `amount`，不携带 protection ref 或 ignore-shield 开关。
- `CharacterDamageTakenCoordinator` 只依赖护盾吸收端口和角色血量端口；DamageSystem 是上游生产者，不属于受影响系统。
- 协调器先准备并统一预校验护盾和血量计划，再调用不得产生业务失败的 `commit_prevalidated()`；完整提交后发布护盾、血量和角色受伤事实。
- `DAMAGE_APPLIED` 是角色受伤 `FACT`，表示正伤害的目标是角色，即使完全被护盾吸收也成立；`CHARACTER_HEALTH_CHANGED` 只表示血量实际减少。
- 任一计划准备或前值校验失败时两个 Store 均不变化；提交阶段不得查询、计算或发布事件，Event handler 不得递归进入当前协调器。
- 直接扣血和按生命流失建模的流血不进入角色受伤协调器。
- ShieldRuntime 不再依赖 HealthRuntime；HealthRuntime 不读取护盾状态。
- 当前 `ShieldRuntime.apply_incoming_damage()` 作为迁移前行为基线保留。

正式架构见[角色受伤协调器设计](../架构/协调/角色受伤协调器设计.md)，目标字段见[角色受伤协调器契约](../契约/角色受伤协调器契约.md)。

### 3.17 系统自治与跨系统协调

- `core/systems/<domain>/` 只拥有本领域状态、公式、计划、写入口和领域事实。
- 领域系统不依赖其他领域的具体 Runtime 或 Store；只读协作使用中立共享模型或窄 Protocol。
- 跨 Store 写入流程放在 `core/coordination/<flow>/`，由写协调器统一准备、预校验、无回调提交并按契约发布事实。
- 明确的跨系统只读条件流程也可以进入 `core/coordination/<flow>/`；只读协调器只能组合领域条件和校验证据，不推进领域时间、不修改 Store、不发布事实或提供 reservation。
- coordinator 不拥有长期领域状态，不实现领域公式，也不充当全局万能 pipeline。
- EventEngine 只发布和记录已提交事实，不作为当前结算的跨系统写入入口。

正式决策见[系统自治与跨系统协调](./系统自治与跨系统协调.md)。

### 3.18 状态效果（Buff）系统架构

- `core/systems/buff/` 直接拥有有限时长 Buff、Debuff 和纯状态标记的定义、完整记录、Store、应用策略、生命周期与领域事实；`Buff` 是中性技术名，不表达有利或有害。
- 第一版只实现固定角色/目标上的无回调状态效果，支持 replace、refresh、stack refresh 和 coexist；永久静态属性、冷却、附着、ICD、护盾、空间对象和 content 私有状态继续由各自边界拥有。
- BuffDefinition 在组装阶段声明稳定 key、冲突、层数和属性 modifier 模板；BuffRecord 单条保存定义、目标、来源、层数、已解析值和生命周期，不依赖跨 Store 组件拼接。
- 属性 provider 在组装阶段固定注册，运行时只读 BuffStore 活动记录；创建、过期或移除实例不动态注册 provider，属性查询无副作用。
- 有限生命周期使用 `created_frame <= frame < expires_at_frame`；简单 Buff 不单独延长仿真，覆盖率用事实期限和会话结束边界计算。

- 第一版运行时、组装、`APPLY_STATUS`、属性 provider、事件和快照工程闭环已落地；真实简单 Buff golden case 因缺少可信资料仍待补充，测试 content 不代表真实机制完成。

### 3.19 元素能量系统架构

- `core/systems/energy/` 直接拥有元素能量公式、角色能量受控写入口和在途微粒/晶球队列；角色运行态只保存最小 `EnergyState`，所有业务写入必须经过 `EnergyRuntime`。
- 微粒和晶球不进入 `Space`，而是以带生成帧和结算帧的在途记录调度；前后台身份、队伍人数和元素充能效率都在实际结算帧读取。
- 同元素、无元素、异元素倍率固定为 `3/2/1`，晶球是微粒的 `3` 倍；四人、三人、二人队后台倍率分别为 `0.6/0.7/0.8`。
- `stat.energy_recharge` 只影响微粒/晶球收入；直接恢复、直接扣除和爆发消耗使用独立强类型请求。
- 标准爆发的能量只读查询与完整扣能入口已经由能量领域提供；角色能力条件协调器已实现只读运行时，用于组合冷却与能量条件。content 仍须在有来源支撑的扣能帧提交完整消耗；同帧直接能量 impact 先于在途载体结算。
- `cost = 0` 的专属资源角色不使用普通元素能量，也不能因 `0 >= 0` 被判定为标准爆发就绪；专属资源继续由 content 私有状态拥有。
- 资产层已从角色爆发天赋的结构化 `cost` 字段导入 `burst_energy_cost`，不解析本地化显示标签；SQLite 资产 schema 已升级为 `2`。

### 3.20 元素战技与元素爆发冷却系统架构

- `core/systems/cooldown/` 直接拥有元素战技与元素爆发的 `available_charges`、串行恢复链、时长解析、修改命令、事实和快照；效果自身触发 CD、元素附着 ICD、协同攻击间隔和产球间隔不进入该 Store。
- 冷却系统只返回指定 key 的冷却条件是否满足，不判断技能或爆发整体能否释放。
- 冷却真值使用整数帧和活动 `ready_frame`，不逐帧递减浮点秒数；查询不隐式推进时间。
- 单次与多充能使用统一串行恢复模型；恢复链开始时快照 CDR，链内排队次数沿用同一 interval，链清空后重新解析。
- Runtime 只处理外部提交的强类型开始请求；固定基础时长来自 definition，动态基础时长由 `REQUEST_PROVIDED` 请求提供，系统不判断请求产生时点或动态公式来源。
- 百分比时长 term、固定减秒、重置当前计时和未来的恢复次数/临时无视 CD 使用不同语义；单键和多键修改均采用 prepare/commit。
- 冷却与标准元素能量的公共条件组合已经由角色能力条件协调器定案；冷却实际启动、动态时长请求、Impact/Event、资产持久化和结果投影仍按各自专题处理。

### 3.21 角色能力公共条件协调

- `CharacterAbilityConditionCoordinator` 是 `core/coordination/character_ability_condition/` 下的只读跨系统协调器，只组合元素战技/元素爆发的冷却条件和标准元素能量条件。
- 协调器返回逐项领域证据、全部稳定阻塞原因和委托给 content 的私有资源条件；不只返回一个缺少上下文的 `bool`。
- 元素战技只要求冷却条件；标准元素爆发要求冷却和满能量；`capacity = 0` 的非标准资源爆发不视为普通能量不足，而是委托角色 content 判断私有资源。
- 公共条件通过不等于动作最终可执行。角色解释器继续判断姿态、私有状态和专属资源，`ActionManager` 最后判断动作锁、中断、会话和实例准入。

### 3.22 元素附着、ICD 与反应设计基础原则

- 项目维护者明确提供的来源、数据和判断是元素附着、ICD 与反应机制的项目真值；AI 查询资料、AI 记忆、旧代码和第三方实现不得直接作为正式规则或数值依据。
- 元素反应属于一次元素命中的跨系统结算流程，不是伤害完成后的附加观察逻辑；原始伤害与元素施加语义分离，但必须通过稳定命中或施加身份关联。
- ICD、Aura 与 Reaction 保持领域自治，不直接依赖彼此的 Runtime 或 Store；限定用途的元素状态帧、交互批次和 Settlement 协调器负责编排计划、统一校验、提交和事实顺序。
- Damage、Aura、ICD 与 Reaction 使用 `core/elements/` 下的中立元素语义；`Element` 不包含物理，元素施加与持久 `AuraKind` 分开。
- Aura、元素附着 ICD、Reaction 领域和跨系统协调器设计已形成；具体反应、特殊附着和派生 Aura 数据仍必须由项目维护者逐项确认，未确认内容不得根据外部查询自行补齐。

完整范围、覆盖规则、当前工作顺序与待确认清单见[元素附着、ICD 与反应设计规范](../工程/元素附着、ICD与反应设计规范.md)。

### 3.23 元素附着系统架构

- `core/systems/aura/` 直接拥有按主体聚合的 Aura Record、精确元素量、同元素叠加、逐帧衰减、计划、提交、事件和快照；Aura 不进入 `TargetRuntimeState`。
- Aura 第一版采用逐来源贡献账本。`AuraComponent.contributions` 是元素量和贡献归属的唯一真值，`current_amount = max(contribution.remaining_amount)` 只作为 View、Snapshot 和审计投影，不允许绕过贡献集合直接写入。
- 普通反应可以忽略贡献明细，只读取投影后的当前元素量；月反应生产规则不随 Aura 第一版实现，但 Aura Store、View、Snapshot、revision 和事实 payload 从第一版起保留逐来源贡献结构。
- Aura 不为月反应额外引入 `emitter_ref`、独立 contributor 类型或 `source_context` 归属模型；现有 `source_ref` 与逐来源 contribution 已足够保存元素贡献。需要多角色结算时，由 Reaction occurrence 在消费前从本次实际使用的正贡献和当前角色触发来源中去重、冻结角色 `participant_refs`。
- 当前角色 content 只在 `ContentRuntimeContribution.reaction_capability_keys` 中声明静态 Reaction 准入 key；application/assembly 负责生成 `ReactionCapabilityEvidence`，协调器通过 `ReactionEligibilityReadPort` 读取，具体月反应机制不因该基础设施自动注册。
- Aura 贡献的剩余元素量使用 `Fraction` 物化为 Store 真值，并由 `ElementalStateFrameCoordinator` 在每帧影响点前与 Reaction 同步推进；查询不隐式推进时间。
- 四档标准强度固定为弱 `1u/9.5s`、中 `1.5u/10.5s`、强 `2u/12s`、超强 `4u/17s`，标准附着保留原始元素量的 `80%`。
- 同元素叠加时同一 `contributor_ref` 的 contribution 元素量与衰减档位分别取最大值；元素量来源和衰减档位来源独立保存，component 的 `current_amount` 只作为 contributions 投影。
- 每个主体只保存一条目标聚合 Record，同一 `AuraKind` 最多一个活动 component；多目标与同帧多请求按显式顺序准备并原子提交。
- Aura 每帧真实衰减但不发布逐帧状态事件，只为真实应用变化和归零发布事实；自然衰减本身不延长仿真。
- Aura 先实现标准附着闭环，再通过 BatchPlanner 接入 Reaction 的异元素 transition；单个 Component 使用稳定复数 `state_link_refs` 关联一个或多个 Reaction 状态。
- Aura 衰减模式区分普通衰减、状态关联衰减和反应管理衰减；第七版燃烧中的普通草保留普通 decay profile，但由 `REACTION_MANAGED` 模式替代普通自然衰减。

完整状态、公式、帧端点、请求计划、事件、快照和测试矩阵见[元素附着系统设计](../架构/系统/元素附着系统设计.md)。

### 3.24 元素附着 ICD 系统架构

- `core/systems/aura_icd/` 只拥有元素附着冷却的 Definition、Binding、限时序列 Record、计划、提交、事实和快照，不承接攻击触发冷却或反应伤害冷却。
- ICD 使用攻击者、目标、标签和组别四维 Key；只有四项全部相同才共享状态，攻击元素不进入 Key，附魔不清空计数。
- ICD 由攻击命中驱动，系数为 `0` 和附魔前的物理命中仍可推进游标；多段攻击按独立命中计数。
- Definition 保存正整数重置帧数和有限精确系数序列；序列越界后持续使用末尾系数，不循环。
- ICD 核心结果是精确元素量系数而不是布尔值；系数 `0` 阻止 Aura 请求，正系数与基础元素量相乘后交给 Aura。
- 无标签攻击不创建 Record；活动窗口不延长仿真，窗口自然到期不发布事件。
- ICD、Aura 与 Reaction 分别通过 BatchPlanner 准备并统一预校验，进入无回调提交阶段后原子提交；EventEngine 不作为 Aura 或 Reaction 调用入口。
- 第一阶段只接入少量定义和真实 content 切片，不自动抓取整张 Wiki 数据表。

完整模型、序列算法、时间端点、事务、事件、快照与测试矩阵见[元素附着 ICD 系统设计](../架构/系统/元素附着ICD系统设计.md)。

### 3.25 元素反应系统架构

- `core/systems/reaction/` 只依赖中立元素语义和自身模型，拥有 Reaction Definition、Rule、候选选择、持续状态、专用 Gate、草露等资源、计划、事实和快照。
- 已确认的具体反应实现归 `core/systems/reaction/mechanics/`，以共享状态、资源或生命周期的机制簇组织；简单机制不强制拆分空文件，复杂机制按交互、状态和实体行为拆分。
- `content/` 不拥有或注册全局 Reaction Definition 与 Rule，只能提供角色、武器和圣遗物产生的类型化意图及能力证据；内置反应通过 Reaction 自身的显式 bootstrap 注册。
- 跨反应复合候选规则由 Reaction 系统内部公共组件拥有，负责注册、歧义检查、稳定排序以及顺序、并行、排他和 effect group 决策；机制目录不得互相 import 或调用其他机制 Runtime、Store 或 handler。
- Reaction 决定跨元素反应、消耗关系和有序步骤；Aura 负责精确元素量运算并拥有 Component 真值；两者通过协调器 prepare/finalize 两阶段交互。
- `ReactionStore` 使用同一个 version 原子拥有强类型 StateRecord 与 GateRecord；即时反应只产生 occurrence，不创建伪状态。
- 派生 Aura 与持续 Reaction 状态使用复数 `ElementalStateLinkRef` 集合关联，任一侧结束时必须跨域原子更新，不允许悬空 link。
- `ReactionDecisionStep.state_planning_intents` 使用按机制注册的判别联合，允许表达没有 occurrence 但必须维护的持续状态真值；新机制不得继续增加等价的散落旁路字段。
- Reaction Effect 使用无回调判别联合表达当前 Impact 修正、派生 Damage Impact、元素传播、状态、控制、空间实体和拾取物；Reaction 不直接构造 `DamageRequest` 或调用 Damage Runtime。
- Reaction 事实统一收敛为 `REACTION_OCCURRED`、`REACTION_STATE_CHANGED` 和 `REACTION_RESOURCE_CHANGED` 三类通用事件；具体机制差异通过强类型 payload 的 operation、状态种类、资源种类和审计字段表达，不新增机制专属事件类型。
- 月反应使用队伍 capability 准入和严格元素签名。伊涅芙提供月感电准入；月结晶只匹配水岩；月绽放草露由 ReactionStore 作为专属资源拥有。
- 月候选满足准入与签名时排他替代对应普通候选；准入者、触发者、状态所有者和效果所有者分别记录。

完整规则、状态、时间、Effect、错误与验证入口见[元素反应架构文档索引](../架构/系统/元素反应/文档索引.md)。

### 3.26 元素反应协调器架构

- `core/coordination/elemental_reaction/` 包含元素状态帧协调、单批次元素交互和同帧 Settlement Queue 三条限定用途流程。
- Aura、ICD 与 Reaction 使用隔离 BatchPlanner 维护未提交虚拟投影；协调器按 interaction order 交错准备，最终统一 seal、validate 和无回调提交。
- 结算原子性止于一个共同因果来源的 `ElementalInteractionBatch`；一次原始 Impact 的全部直接目标属于同一 batch，任一目标非法时该 batch 整体不提交。
- 已提交 batch 的事实不可回滚，后续 settlement round 或 root chain 失败只能终止仿真，不能补偿撤销已经发布的 Aura、Reaction、Damage 或跨领域事实。
- 每帧先同步规范化 Aura/Reaction，再按计划顺序处理周期根及其完整连锁，最后按 impact order 逐个处理原始 Impact 及其完整连锁。
- 同帧 follow-up 使用强类型工作队列和稳定 parent/child 身份，不使用 Event 回调；单 root 最大轮次固定为 `64`。
- 周期根使用强类型 `ScheduledReactionRootWork` 判别联合和显式 adapter registry；公共协调器不根据 reaction key、state key 或目录顺序增加机制分支。
- Current-transaction Effect 在反应批次内准备；反应新产生的伤害统一物化为 Damage Impact，并与传播及其他后续效果一起进入同帧下一结算轮次。下一轮仍经 Impact/Space 解析目标并逐目标构造 `DamageRequest`，不存在 `ReactionDamagePort` 专用伤害流程。
- 完整提交后依次发布 ICD、Aura、Reaction 状态/资源、occurrence、内联领域、Damage 和最终元素交互事实。

完整端口、事务、帧顺序、队列、事实与测试矩阵见[元素反应协调器设计](../架构/协调/元素反应协调器设计.md)。

### 3.27 元素反应公共契约冻结

当前已冻结的公共契约如下：

- Aura 第一版采用逐来源贡献账本；`current_amount` 仅为投影，不能绕过贡献集合独立写入。
- 跨反应复合候选规则由 Reaction 系统内部公共组件拥有，负责注册、歧义检查、稳定排序以及顺序、并行、排他和 effect group 决策。
- 结算原子性止于单个 `ElementalInteractionBatch`；已提交 batch 不可回滚。
- Reaction 事实收敛为 `REACTION_OCCURRED`、`REACTION_STATE_CHANGED` 和 `REACTION_RESOURCE_CHANGED` 三类通用事件。
- 所有伤害都先形成统一 Damage Impact；Action、Reaction、周期状态和空间实体只在来源与因果身份上不同，不拥有不同的目标解析或伤害结算流程。
- 反应处理当前 Impact 时只能调整该 Impact 已携带的关联伤害；处理过程中新增的伤害一律成为同帧下一 settlement round 的子 Damage Impact。
- 普通元素反应由本次元素、ICD 后实际元素量和目标 Aura 决定；碎冰额外读取稳定 `strike_type=BLUNT` 证据。来源种类、武器显示类型和布尔“允许反应”开关不参与成立判断。

### 3.28 元素反应第二版契约冻结

- 第二版生产触发来源只覆盖队伍角色；敌人/环境剧变等级系数保存在 Damage 共享直接表中，但不为其伪造生产 Impact 入口。
- 不新增 `SimulationConfig` 阵营字段。Space 只返回几何候选，元素协调器通过窄目标资格协议读取 `self`、`ally`、`hostile`、`neutral_or_unknown` 关系和 `aura`、`damage`、`attribute_status` capability。
- Reaction Profile 拆为 `AmplifyingReactionProfile | TransformativeReactionProfile` 强类型联合；超载、超导使用独立稳定 Reaction、Profile、Damage、Gate 和 Status key。
- 一个 occurrence 可以冻结一个或多个 `ReactionEffectGroup`；第二版 Effect group 在同帧下一 settlement round 执行，并使用稳定 parent、group、effect、target 和 work 引用。
- ReactionStore 第二版只新增 Damage Gate Record，不提前实现 ReactionState。Gate 按 Definition、触发来源、伤害目标和伤害种类分槽，30 帧半开窗口内超载最多一次、超导最多两次。
- 一个 round 1 Effect group 是新的原子 batch；统一预校验后按可选状态型 Reaction/Aura、Reaction Store、Buff、Damage 顺序无回调提交。Gate 阻止只影响对应伤害，超导 Buff 与超载钝击语义仍然成立。
- 第二版不新增超载、超导或 Gate 专属事件；只扩展通用 `REACTION_OCCURRED` payload 和 `ElementalInteractionBatchRecord`，并复用 Buff、Damage 与元素交互事实。

完整字段、key、正常阻止、技术失败和事实顺序已拆分到[元素反应契约文档索引](../契约/元素反应/文档索引.md)下的公共契约、超载契约和超导契约。

### 3.29 元素反应第七版普通燃烧契约冻结

- 第七版只实现普通燃烧。火草建立时不执行一次性直接消费，后手按普通持久附着形成底层 Aura，同时创建固定 `2 GU` 燃元素与 `BurningState`。
- 普通草在燃烧期间使用 `REACTION_MANAGED` 模式，以 `1/150 GU/frame` 替代普通衰减；普通火继续普通衰减。燃元素与普通草都链接同一状态，元素量真值仍只在 Aura。
- `BurningState` 保存当前 effect owner、捕获式剧变基础、伤害/施火游标和预计草耗尽帧，不复制 Aura 元素量。普通正火或正草维护更新来源捕获但不重置周期，周期火自身不刷新来源。
- 燃烧建立当前帧首次伤害，之后每 15 帧对主体周围 X/Z 平面 1 米内合法敌对目标造成倍率 `0.25` 的火元素剧变伤害；使用 120 帧最多八次的来源/目标/伤害种类 Gate。
- 创建后 15 帧首次、之后每 120 帧向主体施加 `1 GU` 普通火，不进入 Aura ICD。周期伤害与施火合并为一个 `BurningCycleRootWork`，同帧固定伤害先于施火。
- 周期工作使用 `ScheduledStateTickCause + CapturedTransformativeScalingBasis`，不得伪造 occurrence 或实时来源观察。无 occurrence 的建立、维护和终止统一使用 step 级强类型状态计划意图。
- Damage Gate 的请求、解析和 Record 使用 `ReactionEffectCause`；即时反应保留 occurrence cause，感电与燃烧周期使用 scheduled cause，不再把周期 cause ref 写入 `last_occurrence_ref`。
- 后手水、冰、雷、风、岩使用共享输入预算并行消费普通火与燃元素，只产生一个 occurrence 和一组效果。普通草与普通冰正式允许共存；剩余水雷预算进入未实现绽放或激化时稳定失败。
- 燃元素或草归零时原子结束状态并停止未来工作。第七版交付通用主体失效通知与燃烧清理响应，但当前不提供没有真实上游依据的目标死亡/离场生产检测调用方。
- 当前 effect owner 失效不终止燃烧，周期继续使用已捕获 basis；只有后续合法正火或正草维护才替换来源。
- scheduled root 和状态计划均通过显式 adapter registry 接入，并同步迁移现有感电路由；公共协调器不新增 burning key 分支。

完整数值、字段、稳定 key、交付边界和验收入口见[燃烧反应设计](../架构/系统/元素反应/反应/燃烧反应设计.md)及[燃烧反应契约](../契约/元素反应/反应/燃烧反应契约.md)。该契约已经确认，生产 bootstrap、assembler 注入与纵向 golden case 已落地。

### 3.30 元素反应第八版激化机制簇契约冻结

- 第八版只实现原激化、超激化与蔓激化。原激化按草雷 `1:1` 实际消费创建无附着损耗的 `AuraKind.QUICKEN` 与 `QuickenState`；超激化和蔓激化不消费激元素，也不使用独立 Reaction Gate。
- 激元素量与衰减档案唯一保存在 Aura。连续实例只保留一份稳定贡献；覆盖取新旧当前量较大者，只有新值严格更大时替换来源和衰减档案，State occurrence 与 revision 每次更新。
- Quicken 状态计划使用 establishment、coverage、termination 三个强类型 intent 与唯一 adapter，不增加公共协调器的 reaction key 分支。Aura、State、Link 与当前 Impact 调整在同一批次预校验并原子提交。
- 超激化与蔓激化分别使用 `1.15`、`1.25`，固定 `reaction_bonus = 0.0`。Damage 从当前查询实时读取来源等级和元素精通，并用 `level_multiplier * reaction_multiplier * (1 + 5 * EM / (1200 + EM) + reaction_bonus)` 计算基础伤害附加值。
- 激化使用主攻击标签唯一选中的独立完整公式 `damage_formula.catalyze_additive`，不新增 `DamageReactionCapability.CATALYZE_ADDITIVE`。关联 Impact 必须至少有一个 `coefficient > 0` 的 scaling term；仅有 flat base、零倍率或后续修饰加值均不合格。
- Reaction 输出独立的 `CatalyzeCurrentImpactDamageAdjustment`，协调器转换为 Damage 的 `CatalyzeReactionInput`。DamageResult 保存强类型 `CatalyzeReactionResolution`，并把同一附加值投影到 `base_damage_additions`；本版不改变结果库 schema。
- 激雷受草与激草受雷采用“附加反应后原激化”的两个顺序 Step；激冰受雷时超导与超激化并行；冰草受雷时先超导，再以剩余雷预算执行原激化。
- 激元素可与普通草共同作为一份 BurningState 的类草依赖并分别按 `1/150 GU/frame` 消费。`next_dendro_depletion_frame` 直接迁移为 `next_dendro_like_depletion_frame`，不保留兼容别名。
- 水进入未实现绽放候选、扩散雷进入未实现激化候选时在提交前稳定失败。事实继续使用通用 Reaction/Aura/Damage EventType，不增加机制专用事件。
- 稳定 key 与错误类型已经从第八版规划迁移到[激化反应设计](../架构/系统/元素反应/反应/激化反应设计.md)和[激化反应契约](../契约/元素反应/反应/激化反应契约.md)；Aura、Reaction、Damage 与协调器文档分别保留所属领域规则。本决策记录只保留冻结结论。

完整字段、跨领域边界和验收入口见[激化反应设计](../架构/系统/元素反应/反应/激化反应设计.md)和[激化反应契约](../契约/元素反应/反应/激化反应契约.md)。生产 bootstrap、assembler 注入、公式审计与纵向 golden case 已落地。

### 3.31 元素反应第九版绽放机制簇契约冻结

- 第九版实现普通绽放、绽放爆炸、超绽放和烈绽放；普通草与激元素都可作为类草 Aura 参与普通绽放，水与类草按 `2:1` 实际消费。
- 每个正普通绽放 occurrence 创建一枚持续 360 帧的草原核；同一玩家队伍最多五枚，创建第六枚时按稳定 `creation_sequence` 淘汰并引爆最老核心。
- 自然到期、容量淘汰、雷触发和火触发竞争核心唯一终态。核心 State、Space Entity、到期工作、occurrence 和后续 Effect 使用版本化计划，容量从活动 State 工作投影派生，不新建 Pool Store。
- 绽放爆炸、超绽放和烈绽放在实际伤害准备时分别读取核心创建者、雷触发者和火触发者的当前等级与元素精通，并共享 `bloom_family` 30 帧两次伤害 Gate。
- 三种终止伤害各自保留 `reaction_damage.bloom_explosion`、`reaction_damage.hyperbloom` 和 `reaction_damage.burgeon` 分类；`bloom_family` 只作为共享 Gate family，不替代专属伤害分类。
- 正雷或正火草原核接触必须引用已经成功提交的元素 Impact，并在移除核心前校验帧、来源、元素和元素量一致；格式正确但不存在或不一致的引用不能成为触发证据。
- 普通目标只生成 `DamageResult`，不维护或扣减目标生命；当前场上角色受方复用既有角色受伤流程。第九版不增加目标 Health Store，不修改 `SimulationConfig`。
- 超绽放索敌数据确认为 `15,15`，并按距离就近选择目标。当前 Space 只提供 X/Z 平面圆形查询，因此运行时以核心位置为中心使用包含边界的 `15m` 半径，并按 `distance_xz, stable_subject_ref` 稳定选择最近合法敌方目标。
- 蔓生弹只实现锁定目标和 `ARRIVED | LOST` 窄结算，不声明真实运动调用方、飞行时间、轨迹或碰撞。
- 事实继续使用通用 Reaction、State、Damage 和既有角色 Health EventType，不新增绽放机制专属事件。

稳定字段、稳定 key、终态、伤害分类和失败边界以[绽放反应设计](../架构/系统/元素反应/反应/绽放反应设计.md)及[绽放反应契约](../契约/元素反应/反应/绽放反应契约.md)为准；生产 assembler 与 golden case 已落地。

### 3.32 月绽放独立反应契约冻结

- 月绽放是与普通绽放机制簇并列的独立反应，使用独立 `reaction.lunar_bloom` Definition、`reaction_handler.lunar_bloom` Handler、`lunar_incoming_*` 方向，`selection_priority = 100`。
- 候选要求 `reaction_capability:lunar_bloom`、角色触发来源和严格水草签名；不满足时回退到普通绽放。
- 水草消费关系、草原核 State 和 Space 创建与普通绽放共享，由中立草原核创建计划统一拥有。
- 月绽放反应本身不产生伤害；角色月绽放伤害由角色技能消费草露后通过 `CHARACTER_DIRECT` 月曜输入造成。
- `ReactionResourcePlanner.consume_lunar_bloom_dew` 提供整数草露原子消费接口。
- 月曜生产公式已注册：等级基数表 `{80: 1077.4, 90: 1446.9, 95: 1561.5, 100: 1674.8}`、精通系数 `6 × EM / (EM + 2000)`、角色月绽放倍率 `1.0`。
- 正式契约已迁移。

### 3.33 月感电独立反应契约冻结

- 月感电是与普通感电并列的独立反应，使用独立 `reaction.lunar_electro_charged` Definition、`reaction_handler.lunar_electro_charged` Handler、`lunar_incoming_*` 方向、`reaction_capability:lunar_electro_charged` capability 和 `selection_priority = 100`。
- 候选要求严格水雷签名、角色触发来源和队伍 capability；不满足时回退到普通感电。occurrence 本身不消费水雷，后手元素以标准 `20%` 损耗形成持久 Aura 保持水雷共存；月感电不产生直接伤害。
- Reaction 拥有 `LunarStormCloudState`（生命周期 `360` 帧、首次攻击 `15` 帧、攻击间隔 `15` 帧、`player_team` 作用域），Space 拥有 `REACTION_OBJECT` 位置投影；创建/刷新/云间排斥（`5` 米）和到期销毁通过跨领域计划原子完成。
- 雷暴云攻击使用唯一 `LunarStormCloudAttackRootWork` 与 scheduled root adapter；逐目标检查正水、正雷 Aura 与角色贡献，消费前冻结参与者，使用 `120` 帧每次 `1` 次的逐目标 Gate，并对水雷分别消费 `0.4 GU`。
- 攻击伤害使用 `damage_profile.reaction.lunar_electro_charged` 的 `LUNAR_REACTION` 复合月曜公式，反应倍率基线 `3.0`；组分独立结算后按 `0.60/0.30/0.05` 加权。
- 第十版生产 bootstrap、assembler 注入与纵向 golden case 已落地；生成锚点、攻击半径、云间排斥半径、周期与倍率的精确数值仍待人工确认，Space 实体生命周期投影刷新暂不延展。

稳定字段、稳定 key、攻击与失败边界以[月感电反应设计](../架构/系统/元素反应/反应/月感电反应设计.md)及[月感电反应契约](../契约/元素反应/反应/月感电反应契约.md)为准。

稳定字段、稳定 key、草露资源、消费接口和失败边界以[月绽放反应设计](../架构/系统/元素反应/反应/月绽放反应设计.md)及[月绽放反应契约](../契约/元素反应/反应/月绽放反应契约.md)为准。

### 3.34 月结晶独立反应契约冻结

- 月结晶是与普通结晶并列的独立反应，使用独立 `reaction.lunar_crystallize` Definition、`reaction_handler.lunar_crystallize` Handler、`lunar_incoming_geo_on_hydro` 方向、`reaction_capability:lunar_crystallize` capability 和 `selection_priority = 100`。
- 候选要求严格水岩签名（后手岩命中正水）、角色触发来源和队伍 capability；只替换水结晶方向，火、雷、冰结晶保持普通结晶。元素消费沿用普通结晶岩水 `2:1`，不使用成立 Gate，不创建水晶片。
- 水雷共存目标沿用公共水雷复合候选：雷步骤普通结晶正常成立，岩预算足够时水步骤继续按月结晶成立，同一批内同时产生雷晶片与月结晶月笼/累计记录；无 capability 时水步骤维持普通结晶并受成立 Gate 约束。
- 场上同时最多且常态只有 3 枚月笼：触发目标附近（半径 `12` 米、高 `5` 米圆柱）无月笼时生成 3 枚（目标周围 `3.25` 米圆周等距），有则不生成；月笼超过 `540` 帧未谐奏销毁。
- 共享累计器按 occurrence 顺序保存参与者记录，最多 `4` 层、第 5 层丢弃最旧；每 `3` 次月结晶触发一次谐奏，谐奏无独立冷却只按次数触发。
- 每枚月笼发射后进入 `21` 帧投射物飞行冷却（`0.35 秒 × 60`），冷却结束前不能再次攻击；受冷却或月笼销毁影响产生计数溢出，延迟触发后可能只再触发 `1~2` 次月结晶就再次谐奏。
- 谐奏目标为当前受角色攻击的一个目标，且必须同时处于三枚月笼索敌范围内；按距月笼集合最近选择，不要求等于触发目标。三枚月笼各自创建独立复合月曜伤害，组分独立暴击并按 `0.60/0.30/0.05` 加权。
- 月反应伤害统一不产生元素附着、不携带元素量；谐奏伤害立即结算，不模拟投射物命中延迟。
- 第十一版生产 bootstrap、assembler 注入与纵向 golden case 已落地；可回放随机协议、岩造物干扰与反应月结晶独立倍率（基线 `1.6`）记录为待确认项，不改变生产注册状态。

稳定字段、稳定 key、事务与失败边界以[月结晶反应设计](../架构/系统/元素反应/反应/月结晶反应设计.md)及[月结晶反应契约](../契约/元素反应/反应/月结晶反应契约.md)为准。

## 4. 待讨论事项

### 4.1 仿真配置契约

已确认初步方向：

- 使用 `SimulationConfig` 描述一次仿真。
- 顶层结构包含 `meta`、`team`、`scene`、`input_trace`、`rules`、`run_options`。
- 配置引用资产时统一使用 `asset_key`。
- `input_trace` 记录按键输入事实，不使用角色名称。
- 敌人目标信息直接写入 `scene`，不进入资产库。
- `scene` 可包含 `player` 初始位置/朝向；目标继续使用 `targets` 多目标列表，但运行时空间只把目标作为简单点位候选实体。
- `run_options` 不包含 `mode`。
- 所有仿真都保存完整结果数据。

详细方案见：[仿真配置契约与最小闭环](../契约/仿真配置契约与最小闭环.md)。

### 4.2 应用端 MVP

第一版 MVP 定为最短闭环：

- 创建或编辑一个 `SimulationConfig`。
- 队伍/角色构建配置。
- 按键输入轨迹编辑。
- 运行一次仿真。
- 保存完整仿真结果数据。
- 仿真结果摘要。

第一版暂不强制包含：

- 完整战斗过程复盘。
- 参数扫描。
- 多结果对比。
- 配置模板库。
- 复杂 UI 工作区。

### 4.3 CLI 与工具脚本

已确认第一版命令：

- `genshin-sim assets build`
- `genshin-sim assets fetch-source`
- `genshin-sim assets build-manifest`
- `genshin-sim assets audit-manifest`
- `genshin-sim assets validate`
- `genshin-sim assets info`
- `genshin-sim config validate path/to/config.json`
- `genshin-sim run path/to/config.json`
- `genshin-sim results list`
- `genshin-sim results inspect <session_id>`

原则：

- CLI 只作为开发、数据构建、调试和自动化入口。
- CLI 调用 `application/` 服务，不重复实现仿真组装逻辑。
- 第一版使用标准库 `argparse`。

详细方案见：[新项目模块边界设计](../架构/模块边界设计.md)。

### 4.4 测试与迁移策略

需要细化：

- `tests/unit/`、`tests/integration/`、`tests/golden/` 的职责。
- golden case 的保存格式。
- 数值可信度验证方式。

已确认原则：

- 测试不能直接照搬旧项目测试文件。
- 测试必须基于新项目架构、配置契约和模块边界重新编写。
- 旧项目测试只作为行为覆盖范围与数值预期参考。
- 旧项目能力覆盖见[旧项目能力盘点](../工程/旧项目能力盘点.md)，当前工作流、依赖门槛与任务选择方法见[迁移阶段安排](../工程/迁移阶段安排.md)。

### 4.5 UI 重设计

UI 需要大改，暂不做具体设计。

当前仅确认：

- UI 继续使用 Flet。
- UI 通过 `application/` 调用能力。
- UI 不直接访问 SQLite。
- UI 不直接组装仿真核心对象。

### 4.6 仿真任务执行模型

当前建议方向：

- 新增 `application/execution/` 保存同步执行原语，例如 `SynchronousSimulationExecutor`。
- 新增 `application/jobs/` 保存任务模型、状态和 `SimulationJobRunner` 调度协议。
- 当前已有内存版同步 `SimulationJobRunner`，用于验证任务接口；它不提供真正后台执行能力。
- `application/services/` 只作为 UI/CLI 对外服务门面，不保存单次同步运行原语。
- 仿真任务以进程隔离为主，异步只作为 UI 或主进程侧的调度外壳。
- worker 进程内部重新创建资产仓库、handler registry、结果写入器和同步执行器。
- 不将异步调度、进程池参数或运行模式写入 `SimulationConfig`。
- 不把 `core/` 改造成异步模拟器。

详细方案见：[仿真任务执行模型](../架构/仿真任务执行模型.md)。
