# 系统自治与跨系统协调

> 状态：已确认。
> 本文记录 `core/systems/` 的系统自治规则和 `core/coordination/` 的跨系统协调边界。
> 最后更新：2026-07-14

## 1. 背景

伤害、治疗、生命、护盾、能量和反应等领域会在同一次仿真流程中协作，但它们拥有不同的状态、公式、错误和审计事实。

如果一个系统直接依赖另一个系统的具体 Runtime 或 Store，容易产生以下问题：

- 状态没有唯一所有者。
- 一个系统替另一个系统实现公式或发布事实。
- 跨 Store 提交失败后留下部分状态。
- 领域模块之间形成循环依赖。
- 单元测试不得组装无关系统才能运行。
- Event 回调逐渐承担隐式调度和递归写入职责。

因此确认采用“系统自治，跨系统协调外置”的架构规则。

## 2. 决策

```text
core/systems/<domain>/
-> 只拥有本领域状态、公式、计划、写入口和领域事实

core/coordination/<flow>/
-> 只编排一个明确跨系统流程
```

`core/systems/` 不保存跨系统流程；`core/coordination/` 不实现领域规则。

## 3. 系统自治规则

每个 `core/systems/<domain>/` 模块必须满足：

- 领域状态只有该系统的 Store 拥有和提交。
- Resolver 或 Formula 只实现该领域计算。
- Runtime 只接受本领域请求并返回本领域结果或 MutationPlan。
- 系统只发布本领域已经提交的事实。
- 系统不能 import 其他领域系统的具体 Runtime 或 Store。
- 系统不能直接调用另一个系统的写入口。
- 系统不能通过 Event 回调间接修改另一个系统的当前结算。
- 有身份和生命周期的领域记录由对应系统直接拥有。
- 公共运行时原语只有在至少两个已实现领域证明相同不变量后才提取。

例如：

- ShieldRuntime 不调用 HealthRuntime，也不发布 `DAMAGE_APPLIED`。
- HealthRuntime 不查询 ShieldStore，也不计算元素吸收倍率。
- HealingRuntime 不直接修改 HealthState。
- DamageResolver 不创建或移除 Buff 实例。

## 4. 允许的系统间读取

系统自治不表示禁止所有依赖。只读依赖可以通过以下方式表达：

- `core/` 中立模块定义的稳定值对象。
- 最小只读 Protocol。
- 不产生副作用的查询服务。
- 上游已经结算完成的类型化输入。

依赖系统的具体类不是公共协议。若一个概念被多个系统使用，应优先判断它是否属于中立公共语汇。

例如：

- ShieldResolver 可以通过 `AttributeReader` 查询创建属性。
- ShieldRuntime 可以通过保护范围只读协议判断当前场上角色。
- 多个系统共同使用的元素、实体引用和来源引用应放在中立模块，不应因为历史位置而依赖 Damage 或 Attributes 内部模型。

只读协议也不能泄漏可变 Store、完整 Runtime 或任意查询上下文。

## 5. 跨系统协调层

跨系统流程放在：

```text
core/coordination/<flow>/
```

每个 coordinator 只负责一个有明确输入、输出和顺序的流程。协调流程分为两类：

- 写协调流程：组合多个领域计划，统一预校验并按固定顺序提交和发布事实。
- 只读条件协调流程：组合多个领域已经定义的只读条件，校验证据并形成不可变结果。

例如：

- `character_damage_taken`：角色伤害在护盾与血量之间的应用。
- `character_ability_condition`：组合冷却与标准元素能量公共条件，不执行资源写入。
- `elemental_reaction`：用三个限定用途 coordinator 分别处理 Aura/Reaction 帧同步、单个元素交互批次和同帧后续队列，不由任一领域直接调用其他系统。
- `resonance_reaction`：元素共鸣消费已提交的反应/伤害事实，为下一结算轮次生成能量与 Buff 强类型意图，不直接写入其他领域状态。
- 未来 `healing_application`：理论治疗结果与角色生命提交。
- 未来需要原子协作的其他明确结算流程。

协调器可以依赖多个领域系统的窄 Protocol，但不得依赖 application、content、assets、infrastructure 或 UI。

`core/coordination/` 与 `application/` 的编排层级不同：

- `core/coordination/` 编排仿真内部、需要确定帧顺序、状态提交语义或组合条件语义的跨系统流程。
- `application/` 编排加载配置、组装仿真、执行任务、保存结果等外部用例。

application 可以创建和注入 coordinator，但不能替代 coordinator 决定仿真帧内的领域提交顺序。

## 6. 协调器职责

### 6.1 写协调器

写协调器负责：

- 把上游请求适配为各领域强类型请求。
- 按契约顺序准备各领域不可变计划。
- 在写入前校验全部 Store version 和状态前值。
- 进入禁止外部回调的提交阶段。
- 提交各领域已经准备完成的状态变化。
- 形成跨系统应用记录。
- 在完整提交后按稳定顺序发布事实。

推荐流程：

```text
跨系统请求
-> prepare domain plan A
-> prepare domain plan B
-> validate all plans
-> commit without callbacks
-> build application record
-> publish domain facts
-> publish final flow fact
```

### 6.2 只读条件协调器

只读条件协调器负责：

- 接受一个明确场景的类型化查询。
- 通过窄只读 Protocol 查询各领域已经定义的条件结果。
- 校验主体、帧、能力类型和领域证据的一致性。
- 返回不可变组合结果、稳定阻塞原因和明确委托给上游的条件。
- 保持无副作用，不拥有或复制任何领域真值。

推荐流程：

```text
typed query
-> query domain condition A
-> query domain condition B when applicable
-> validate cross-domain identity and evidence
-> build immutable composite result
```

只读协调器不能推进领域时间、修改 Store、发布 Event、提供 reservation、返回 commit token，或把公共条件结果宣称为上游动作的最终准入结论。

## 7. 协调器禁止事项

协调器不能：

- 拥有长期领域状态或复制领域 Store。
- 实现伤害、治疗、护盾、生命或反应公式。
- 接受任意系统列表并按字符串优先级动态拼装 pipeline。
- 通过捕获宽泛异常把领域错误静默降级。
- 在 Event handler 中递归执行当前结算。
- 成为所有仿真流程共用的全局万能调度器。
- 在只读查询中隐式推进时间、写状态或发布“查询发生”事件。

协调器只有流程内临时计划、查询证据和审计记录，不成为新的领域真值来源；只读条件协调器不保存长期查询记录。

## 8. Event 边界

`EventEngine` 只发布和记录已经发生的事实，不承担跨系统协调。

规则：

- Event 不启动当前结算的同步写入。
- Event handler 不直接写领域 Store。
- 需要由事实触发后续行为时，handler 生成强类型后续命令。
- 后续命令进入明确的下一结算轮次或未来帧。
- 命令队列实现前，不接入依赖递归事件写入的正式 content。

事实顺序由对应 coordinator 或单领域 Runtime 的契约决定。

## 9. 依赖方向

```text
systems/<domain> -> shared models / read protocols       允许
systems/<domain> -> systems/<other> Runtime / Store      禁止
coordination/<flow> -> multiple system protocols         允许
application/assembly -> systems + coordination           允许
content -> domain requests / read protocols              允许
content -> systems Store / coordination internals        禁止
```

确有例外时必须先更新本决策与对应架构文档，不能只在代码中形成反向依赖。

## 10. 角色受伤示例

目标依赖：

```text
CharacterDamageTakenCoordinator
├── ShieldAbsorptionPort
├── CharacterHealthDamagePort
└── EventPublisher
```

流程：

```text
CharacterIncomingDamage
-> prepare ShieldAbsorptionPlan
-> prepare CharacterDamagePlan
-> validate both plans
-> commit both domains without callbacks
-> publish shield facts
-> publish health fact when effective damage > 0
-> publish DAMAGE_APPLIED when amount > 0
```

ShieldRuntime 不知道最终生命变化；HealthRuntime 不知道参与吸收的护盾。

协调器只影响 ShieldSystem 和 HealthSystem；DamageSystem 在上游完成计算，不属于协调器依赖或写入范围。详细设计见[角色受伤协调器设计](../架构/协调/角色受伤协调器设计.md)。

## 11. 治疗示例

理论治疗和生命应用是两个领域职责：

```text
HealingResolver / HealingRuntime
-> HealingResult
-> HealingApplicationCoordinator
-> CharacterHealingPlan
-> HealthRuntime
```

Healing 系统拥有倍率、治疗加成和理论治疗结果；Health 系统拥有当前生命、有效治疗量和溢出量；协调器只负责把两者按顺序连接。

## 12. 角色能力条件示例

目标依赖：

```text
CharacterAbilityConditionCoordinator
├── CooldownConditionReadPort
└── BurstEnergyConditionReadPort
```

流程：

```text
CharacterAbilityConditionQuery
-> query CooldownConditionResult
-> skill: build composite result
-> burst: query BurstEnergyConditionResult
-> validate character and ability evidence
-> return all blockers and delegated private-resource conditions
```

协调器不启动冷却、不扣除或预留能量，也不检查角色私有状态和 ActionManager 动作锁。详细设计见[角色能力条件协调器设计](../架构/协调/角色能力条件协调器设计.md)。

## 13. 对现有代码的影响

角色受伤流程已经迁移到 `core/coordination/character_damage_taken/`：ShieldRuntime 不再依赖 HealthRuntime，shield package 不再拥有 CharacterIncomingDamage、最终应用记录或 IncomingDamageHandler。

治疗流程仍由 HealingRequestHandler 编排理论治疗和生命提交，等待独立协调流程评审。角色能力条件协调器已完成文档设计但尚未实现。部分跨系统公共引用和枚举仍位于单一领域包中，继续按实际使用者逐项迁移。

## 14. 验证要求

后续代码检查至少覆盖：

- `core/systems/<domain>/` 不 import 其他领域的 Runtime 或 Store。
- coordinator 只依赖明确 Protocol。
- 单领域公式和 Store 测试不需要组装其他领域 Runtime。
- 跨系统失败注入不会留下部分状态。
- Event 回调不能递归写当前结算。
- 事实顺序与 application record 可稳定复现。
- 只读 coordinator 查询不改变 Store、revision、领域时间或 Event 记录。
- 只读组合结果保留全部适用领域证据，不把正常阻塞与查询错误混为一类。

必要时增加依赖边界测试或静态导入检查，不能只依赖人工约定。
