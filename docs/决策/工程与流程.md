### D-022 工程与交付

> 状态：生效

- 模拟输入契约：`SimulationInput` 顶层结构、`asset_key` 引用、`input_trace`、`scene` 目标、`run_options` 不含 `mode`、全量保存结果；详细见[模拟输入契约](../契约/模拟输入契约.md)。
- CLI：只作开发、数据构建、调试和自动化入口，调用 `application/` 公开能力，第一版使用 `argparse`；命令覆盖资产、配置、运行、结果与 handler 绑定维护。
- 测试策略：测试分层职责、golden case 保存格式与数值可信度验证方式由[测试规范](../工程/测试规范.md)承接；能力实现与数值来源约定见 D-008。
- 任务执行模型：同步原语在 `application/execution/`，任务模型与 runner 在 `application/jobs/`；仿真任务以进程隔离为主，worker 进程内部重建资产仓库、handler registry、结果写入器和同步执行器；不把异步调度或运行模式写入 `SimulationInput`，`core/` 不做成异步模拟器。详细见[批处理调度设计](../架构/批处理调度设计.md)。

### D-040 开发者模式与测试内容门控（2026-08-30）

> 状态：生效

- 引入开发者模式，供手动使用与 UI 开发期浏览 `content/test` 包下的测试内容；开关位于
  config.toml 的 `[developer] enabled`，**组装期**读取，CLI 与 server 共用，
  切换后重启进程生效。不做请求级开关，遵守"缺 handler 在组装阶段报错"的装配原则。
- 测试 `handler_key` 统一 `testing.*` 命名空间；`runtime_probe` 自
  `content/characters/testing/` 迁入 `content/test/characters/`，由
  `create_default_content_unit_registry(developer_mode=True)` 追加注册，
  正常模式不导入测试包。`generic.test_*` noop 占位键不门控（零行为、minimal
  静态库绑定目标）。
- 测试资产**不落库**：行数据由代码定义（`content/test/assets.py`），经内存
  `TestAssetRepository` 实现同一 `AssetRepository` 只读协议，开发者模式下用
  `CompositeAssetRepository`（主库优先、回退兜底、列表合并去重）叠加在正式
  资产库上；正常模式不构造组合仓库，测试资产不可见。批处理子进程经
  `SimulationWorkerPayload.developer_mode` 布尔透传。
- settings API 的 GET/PUT 携带 `developer` 节（`developer_enabled` 请求字段）。

风险标注：涉及装配链路与项目配置契约的行为变化；不改 `SimulationConfig`
契约、资产库 schema 与结果库结构。详见
[内容系统设计](../架构/内容系统设计.md) 8.1 与
[资产系统设计](../架构/资产系统设计.md) 7.1。

### D-044 测试内容不设测试用例（2026-08-31）

> 状态：生效

- `content/test` 包是测试脚手架与合成夹具，不是被测对象；不为该包代码设计单元、集成或 golden 测试用例，并移除已存在的直接针对测试内容的用例。
- 自动化代码测试不得 import `content/test`，也不得开启 developer_mode 注入该包；
  测试内容只供开发者模式手动/UI 使用。自动化测试需要合成资产或行为桩时，
  使用 `backend/tests/helpers/` 下的测试夹具，不使用源码测试包。
- 新增或调整测试内容时不要求配套测试；删除/迁移已有用例按[测试规范](../工程/测试规范.md) 6 的覆盖确认执行。

风险标注：纯测试策略调整，不改 `SimulationConfig` 契约、资产库 schema 与结果库结构。详见[内容系统设计](../架构/内容系统设计.md) 8.1 与[测试规范](../工程/测试规范.md) 3.3。

### D-059 自动化测试与 content/test 隔离（2026-09-04）

> 状态：生效

- `content/test` 是开发者模式的手动/UI 演示内容，不属于自动化测试依赖：
  后端测试不 import `genshin_sim.content.test`，不构造
  `create_default_content_unit_registry(developer_mode=True)`。
- 自动化测试的合成资产统一放 `backend/tests/helpers/`：`fixture_assets.py`
  提供零行为 noop 夹具（handler 使用默认注册表内置 `generic.test_*`）；
  需要输入/动作行为时，由测试文件或 helpers 内注册测试局部内容单元，
  不复用 `content/test` 的反应探针、词条探针武器/套装。
- `genshin_sim.content/__init__.py` 不再导出 `content/test` 的键与常量，
  普通 import 不触发测试包加载。
- 反应 golden/集成等原本用 test_a 的装配改为临时 SQLite 夹具资产 +
  默认注册表；芭芭拉切人、护盾等需要行为的场景使用测试本地 fixture。
- 删除 `backend/tests/helpers/barbara_assets.py`：芭芭拉集成测试不再复制
  真实倍率/效果参数；资产行收敛为 `backend/tests/helpers/barbara.py` 内的
  最小合成构造器（倍率统一 1.0、效果参数取简单合成值），只保留命座
  C1/C2/C4 与安可被动所需 payload。
- 芭芭拉元素战技集成只保留“施放元素战技对自身施加潮湿”的纵向用例；
  普攻、重击、下落、命中治疗、爆发治疗等不再作为内容集成测试覆盖，
  命座与被动集成用例保持现状。
- 新增自动化门禁用例扫描 `backend/tests`，禁止 `genshin_sim.content.test`
  import 与 `developer_mode=True`，防止回潮。

风险标注：测试策略与开发者内容边界调整；不改 `SimulationConfig` 契约、
资产库 schema 与结果库结构。详见[内容系统设计](../架构/内容系统设计.md) 8.1、
[资产系统设计](../架构/资产系统设计.md) 7.1 与[测试规范](../工程/测试规范.md) 3.3。

### D-062 决策记录整理机制（2026-09-06）

> 状态：生效（2026-09-06 确认）

- 整理由维护者主动触发（直接下达「整理决策记录」类任务），不定周期、不设自动指标。
- 整理定位为质量清理，不做替代链合并与历史归档：清理对象是**无用决策**（不再影响后续开发的条目，内容降级到架构/契约文档或 commit message 承载后删除）与**错误决策**（结论与代码、契约文档或已确认资料失真的条目，按情况修正表述或标记废弃）。带状态标记的被替代条目不属于清理对象。
- 流程固定提案先行：AI 扫描后产出整理提案（候选条目、处置建议、理由、引用影响清单），维护者确认后执行；执行后重建条目索引并校验状态行、编号引用与相对链接。
- 不变量：条目 ID 永不复用；除提案中明确列出并经维护者确认的处置外，整理不改写任何结论。结论本身的变化一律走正常决策流程（新条目 + 新旧指向）。
- AI 在日常任务中发现明显失真或明显不符门槛的条目时，在最终回复中提示，等待维护者触发整理，不自行清理。

原因：条目增长快（峰值约 15 条/周）且 UI 展示级条目占比高，长期不清理会稀释决策记录对后续开发的指引价值；触发时机由维护者掌握，避免自动指标造成不必要的整理动作。

### D-066 Git 与 GitHub 版本管理（2026-09-08）

> 状态：生效（2026-09-08 确认）

- 个人开发者定位，流程轻量：不启用分支保护、Issue 模板、预建 label 与 Milestone 等强制或仪式化管理；纪律性要求由 commit-workflow skill 约定承载，CI 是唯一强制兜底。
- CI 采用 GitHub Actions 双 job：backend（`uv sync --frozen` 后 ruff check、pyright、pytest 全量）、frontend（`pnpm install --frozen-lockfile` 后 lint、typecheck、test 全量），PR 与 main push 触发；本地按改动范围运行窄路径，本地求快、CI 求全。
- 提交流程：AI 参与的改动一律走 PR（留痕 + CI 验证）；人工改动尽量走 PR，允许直推 main，直推前自行运行相关检查。
- git tag 是项目唯一版本号，代码内不维护包版本常量（`pyproject.toml` 的 version 仅为打包样板，frontend 为私有应用不发布）；tag 与里程碑挂钩（M1 → `v0.1.0`、M2 → `v0.2.0`，依此类推），只在 main 上 CI 通过后打；Release notes 手动撰写，不引入自动生成工具。
- 旧项目历史保留在本地 `backup-old` 分支，不推送远程。

原因：单人 + AI 协作项目，管理收益来自机器自动化（CI）而非流程仪式；曾讨论的「包版本单一事实来源」方案因项目不发布 Python 包而作废，运行 provenance 若未来需要引擎版本，正确来源是 git tag 派生而非手写常量。

详细见 [commit-workflow skill](../../.codex/skills/commit-workflow/SKILL.md)。
