# 原神游戏机制实现规范

> 状态：正式规范（机制接入方向指导）。
> 本文给出新增或修改伤害、治疗、生命、护盾、能量、元素附着、ICD、反应等原神机制时的接入方向与纪律；具体实现规则、领域边界与代码形态由对应文档承载。
> 最后更新：2026-09-05。

## 1. 文档定位

本文是原神机制接入的方向总入口，不保存机制真值，也不重复领域运行态、系统自治、测试规范和各领域文档的实现细节。

## 2. 机制真值与证据

机制实现按以下优先级选择依据：

1. 当前版本游戏内描述、官方说明和可重复观测结果。
2. 维护良好且提供证据的机制资料库。
3. 当前版本 Wiki 或社区文档的交叉验证。
4. 明确标注的待确认假设，不得作为正式数值真值。

每个真实机制必须记录来源适用版本；角色倍率、持续时间、覆盖规则、反应系数和特殊例外在接入时按当前版本重新核对。旧版本资料只能用于证明模型需要具备某种表达能力，不能作为当前真值。

专题规范可以确认更严格的真值规则并优先于本文通用顺序；元素附着、ICD 与反应以[元素附着、ICD 与反应设计规范](./元素附着、ICD与反应设计规范.md)中的人工确认规则为准。

## 3. 接入前决策顺序

新机制进入编码前，按以下顺序逐项确认：

1. 行为目标与非目标。
2. 可信来源与适用版本。
3. 状态所有者与唯一写入口。
4. 使用创建时快照还是运行时动态查询。
5. 与属性、生命、Action、Impact、Event、Space 等系统的边界。
6. 需要同步的架构/契约/测试文档。
7. 测试矩阵与 golden 验收方式。

文档落位遵循：稳定字段、枚举、序列化和跨模块数据结构进 `docs/契约/`；长期职责与运行流程进 `docs/架构/`；阶段任务与未完成工作进 `docs/工程/`。

## 4. 实现方向

领域机制遵循“纯公式解析、状态提交、外层编排分离”的大方向：

- 内容只构造类型化请求，不拥有领域全局状态。
- 领域系统拥有本领域状态、公式与写入口；一次性结算不强制建立长期实例。
- 每个状态只有一个所有者和唯一写入口。
- 跨系统写流程放在限定用途协调器，不由领域直接调用其他系统的 Store/Runtime。
- 事件只表达已经提交的事实，不作为当前结算的可变 hook。
- 相同配置、资产版本、输入、帧顺序和随机种子必须得到相同结果。
- 可持久化模型使用强类型值对象并提供稳定序列化。
- 缺少可信数值来源或 golden case 时不得凭记忆补齐游戏规则。

具体职责分层、数值规则、错误模型、快照分类、确定性与原子性见[领域运行态实现规范](./领域运行态实现规范.md)第 9 节。

## 6. 通用纪律

- 不凭记忆实现版本敏感数值。
- 资产引用使用 `asset_key`，行为实现绑定使用 `handler_key`，显示名称不参与查询、冲突、覆盖或绑定；机制语义使用稳定 key。
- 不把所有领域状态塞进通用 dict。
- 不让 Resolver、modifier 查询或事件回调产生隐式副作用。
- 不让领域系统直接访问 SQLite、UI 或 application 服务。
- 不让 content 直接写领域 Store 或完整 `SimulationContext`。
- 不使用单一全局优先级替代明确的覆盖与冲突策略。
- 缺 handler、能力不匹配、JSON 格式错误和引用不存在尽量在组装阶段失败，不延迟到仿真运行。
- 不为尚未确认的未来能力提前建立万能框架。
- 测试 content 只能证明工程链路，不能冒充真实机制完成。
- 正式文档不长期保留“建议实现”与“实际实现差异”两套叙述；当前实现与正式契约不一致时，先评审并更新其中一方。
