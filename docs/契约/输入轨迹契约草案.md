# 输入轨迹契约草案

> 状态：草案。
> 本文档记录按键输入架构的阶段性讨论结果。尚未讨论完成的内容统一列入“待讨论事项”，不要视为最终契约。

最后更新：2026-07-05

## 1. 目标

新项目的仿真输入不应只抽象为线性动作序列。为了更接近游戏运行方式，第一版输入架构先记录“玩家在某一帧按下或松开了哪些键”，再由 `TeamActionController`、当前场上角色动作解释器和 `ActionManager` 解释这些输入。

核心原则：

- 输入层记录按键事实，不直接生成具体角色动作。
- `press` 与 `release` 都进入动作控制层，由角色逻辑判断点按、长按或特殊状态。
- “按键发生”和“动作成功发生”是两件事，后续应能分别审计。

## 2. 仿真假设

第一版输入轨迹只覆盖键盘和鼠标按钮：

- 不支持手柄输入。
- 不支持自定义键位映射。
- 不记录鼠标移动、镜头、视角或准星变化。
- 不实现移动键功能，默认角色无法通过 `W/A/S/D` 移动。
- 实际位移由后续角色动作、技能或空间系统解释，不由输入系统直接计算。

这些假设与旧项目文档中的简化空间模型保持一致：战场主要使用 `X/Z` 平面做范围判定，`Y` 轴只用于下落攻击等高度敏感动作；项目不模拟实体间刚体挤压。

## 3. 数据结构

输入轨迹按帧分组：

```text
InputTrace = list[KeyInputFrame]

KeyInputFrame
├── frame: int
└── events: list[KeyEvent]

KeyEvent
├── key: string
└── phase: "press" | "release"
```

示例：

```json
[
  {
    "frame": 120,
    "events": [
      {"key": "keyboard.e", "phase": "press"},
      {"key": "mouse.left", "phase": "press"}
    ]
  },
  {
    "frame": 145,
    "events": [
      {"key": "keyboard.e", "phase": "release"}
    ]
  }
]
```

## 4. 支持的按键

第一版只支持以下按键：

```text
keyboard.e
keyboard.q
keyboard.space
keyboard.1
keyboard.2
keyboard.3
keyboard.4
mouse.left
mouse.right
```

默认含义：

| 按键 | 默认控制含义 |
| --- | --- |
| `keyboard.e` | 战技按钮 |
| `keyboard.q` | 爆发按钮 |
| `keyboard.space` | 跳跃按钮 |
| `keyboard.1` ~ `keyboard.4` | 切换到对应队伍槽位 |
| `mouse.left` | 攻击按钮 |
| `mouse.right` | 冲刺按钮 |

注意：这里的默认控制含义不是最终动作。比如 `keyboard.e` 只表示玩家操作了战技按钮，具体是点按战技、长按战技、进入特殊状态还是输入无效，由当前角色和动作状态机解释。

## 5. 校验规则

已确认规则：

- 第一版模拟器骨架中，`frame` 必须是正整数。
- `KeyInputFrame` 按 `frame` 升序排列。
- 同一个 `InputTrace` 中 `frame` 不重复；同帧输入合并到同一个 `events` 列表。
- `phase` 只允许 `press` 或 `release`。
- `key` 只允许使用本文列出的第一版支持按键。
- 同一个 `KeyInputFrame.events` 中，同一个 `key` 不能重复出现。
- 同一帧多个事件按 `events` 列表顺序处理，不设置隐藏优先级。
- 遇到不支持的按键，应在配置校验阶段报错。
- 每一个 `press` 必须有且只有一个后续 `release`。
- 如果某个 `key` 尚未处于按下状态就出现 `release`，应在配置校验阶段报错。
- 如果某个 `key` 已经处于按下状态又出现新的 `press`，应在配置校验阶段报错。
- 仿真结束时不能存在仍处于按下状态且未释放的按键。

说明：`frame=0` 是仿真初始化帧，用于完成配置装配、运行时对象构造、初始场景和系统注册等运行前准备；它不进入有效输入配置，`input_trace` 从第 1 帧开始记录玩家输入事实。

## 6. 初步分发规则

输入事件先进入动作控制层：

```text
InputSystem
-> TeamActionController
-> CharacterActionInterpreter
-> ActionManager
-> SpaceRuntime
-> team / space 受控运行态接口
```

已确认规则：

- `keyboard.1` ~ `keyboard.4` 的 `press` 触发切换槽位请求。
- `keyboard.1` ~ `keyboard.4` 的 `release` 只更新输入状态，不触发切换逻辑。
- `keyboard.e`、`keyboard.q`、`keyboard.space`、`mouse.left`、`mouse.right` 的 `press` 与 `release` 都交给当前场上角色或对应控制逻辑处理。
- 输入状态负责计算按住帧数，例如 `held_frames = release_frame - press_frame`。
- 同一帧事件顺序只表示输入送达顺序，不保证后续输入一定产生动作。
- 当前 `TeamActionController` 使用 1-based 槽位编号，`keyboard.1` 对应 `active_slot=1`。
- 当前 `TeamActionController` 将切人输入翻译为 `team.switch` 动作时间轴，不直接更新 `TeamRuntimeState`。
- 当前 `SpaceRuntime` 消费被接受的 `team.switch` 动作实例，再由切人消费器更新队伍当前场上槽位并同步 `player:active.active_slot`。
- 当前 `TeamActionController` 会记录动作按钮输入事实；动作按钮 `press` 只创建输入会话，不立即生成 `ActionInstance`。
- 当前最小默认解释器在动作按钮 `release` 时生成 `ActionTimelineSpec`，再交给 `ActionManager` 调度。
- 当前 `ActionManager` 会为被接受的动作时间轴生成 `ActionInstance`，并生成默认 `ActionImpactPoint` 作为最小影响点；但它不生成普通攻击、战技、爆发、跳跃、冲刺或切人状态修改的具体执行结果。
- 当动作时间轴带空间查询且上下文挂载了 `SpaceRuntime` 时，动作实例会记录 X/Z 平面候选空间实体 id，并可通过 `SpaceRuntime` 解析出能关联到目标运行态的候选目标引用；这些候选不代表最终命中或造成伤害。
- 默认 `ActionImpactPoint` 发生在动作开始帧，携带同一组候选空间实体和候选目标引用，只表示动作时间轴上的候选影响点。
- 当前 `TeamActionController`、`ActionManager` 和 `SpaceRuntime` 都作为帧更新对象参与 `RuntimeWorld`；只要输入会话、动作、后摇 busy 窗口或空间实体运行态尚未结束，模拟器不会仅因输入轨迹消费完成而停止。
- 输入事实和动作决策如何进入事件流或结果库，等待事件系统契约重新设计后再确定。
- 如果前一个输入让角色进入后摇、输入锁定或其他不可接受状态，后续输入应被动作状态机拒绝并记录原因。
- 被拒绝的 `press` 不开启一次有效动作输入；对应 `release` 只关闭输入状态，不补触发点按或长按逻辑。

示例：

```json
{
  "frame": 120,
  "events": [
    {"key": "keyboard.2", "phase": "press"},
    {"key": "keyboard.e", "phase": "press"}
  ]
}
```

若 `keyboard.2` 切换成功并进入切人后摇，则同帧后续 `keyboard.e` 会被送达但可能因后摇被拒绝，不产生战技动作。

## 7. 帧内处理顺序

输入轨迹在每帧开始时处理：

```text
0. 第 0 帧完成仿真初始化、配置装配和运行时对象构造。
1. 进入第 N 帧。
2. 处理第 N 帧的 `input_trace` 事件。
3. 推进角色、动作、实体和系统的帧更新。
4. 完成第 N 帧边界处理。
```

因此，第 N 帧的输入在第 N 帧开始送达 `TeamActionController`，后续动作状态机和系统推进时可以看到本帧输入造成的状态变化。

## 8. 审计事件

事件系统正在重新设计中，当前不再保留旧的临时事件名。

后续需要重新确定：

- 输入事实是否作为事件记录。
- 动作请求、接受、拒绝是否拆成独立事件。
- 这些事件使用什么命名、payload 和持久化格式。

例如，同一帧内先 `keyboard.2 press` 再 `keyboard.e press` 时，`keyboard.e` 仍会被输入系统送达 `TeamActionController`；如果切人后摇 busy 窗口仍存在，该动作输入不会开启有效输入会话，后续 release 也不会补触发动作。至于这些过程如何记录到事件流，需要等待事件契约确定。

## 9. 待讨论事项

- 切人动作后摇和输入锁定的具体帧数来源。
- `ActionInstance` 如何从默认影响点扩展为具体角色时间轴、命中点、伤害点和取消窗口。
- 快照和结果库如何持久化输入事实与动作决策事件。
