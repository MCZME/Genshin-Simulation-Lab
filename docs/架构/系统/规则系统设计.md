# 规则系统设计

> 状态：正式规范。
> 本文固定规则系统的定位、模块结构、规则定义契约、规则类型路由与组装期接入方式。
> 最后更新：2026-09-07。

## 1. 定位

规则系统承载 `SimulationInput.rules` 中激活规则的语义：每条规则是一个独立定义、可注册的一等公民，负责把自己的激活参数解析为目标系统声明的协议实例。

规则系统是**纯装配期模块**：

- 不拥有帧期状态，不注册为仿真系统，不出现在 `SimulationContext` 与帧更新序列中。
- 不修改任何领域系统的状态；产物只在组装阶段被消费。
- 不发布事件、不产生快照。

## 2. 模块结构

```text
core/rules/
├── models.py        # RuleActivation、RuleResolutionContext
├── registry.py      # RuleDefinition 协议与 RuleRegistry
├── engine.py        # RuleEngine：解析激活 -> 规则类型束
├── errors.py        # 规则系统错误
└── definitions/     # 内置规则定义，每条规则一个文件
```

`core/rules/` 位于 `core/` 顶层，与 `systems/`、`coordination/` 平级：领域系统拥有帧期状态与写入口，协调器承载跨系统帧期流程，而规则系统只在组装期存在，生命周期与二者均不同。

## 3. 依赖边界

```text
core/rules/ ──(只读窄协议)──▶ core/systems/*/
application/assembly ──▶ core/rules/（引擎与注册表）
                     ──▶ core/systems/*/（构造时消费产物）
```

- 规则定义 import 目标系统的协议类型（如 `CriticalDecisionProvider`、`InitialEnergyPolicy`），只读依赖，落在系统自治规范允许的方向上。
- 目标系统不 import `core/rules/`，对规则的存在完全无感知。
- 协议定义留在拥有它的目标系统内，不在规则系统内中立化。

## 4. 规则定义契约

```python
class RuleDefinition(Protocol):
    rule_key: str    # 稳定标识，命名约定与 handler_key 一致
    rule_type: type  # 该规则产物的规则类型（目标系统协议）

    def validate_params(self, params) -> None: ...
    def resolve_activation(self, activation, context) -> Any: ...
```

- `rule_key` 是配置引用与注册查找的唯一标识。
- `rule_type` 用产物协议的 Python 类型本身作为标识，不引入字符串枚举；类型既是类别也是路由 key。
- `resolve_activation` 返回目标系统协议实例，产物必须通过 `isinstance(product, rule_type)` 校验（协议需 `@runtime_checkable`）。
- `RuleResolutionContext` 携带规则解析可读的仿真级输入（当前仅 `seed`），由应用层从 `RunOptions` 构造；`core/` 不依赖 `application/`。

`RuleRegistry` 拒绝重复 `rule_key`；`create_default_rule_registry()` 注册全部内置规则。新增规则的改动面：`definitions/` 增加一个文件并注册；目标系统零改动（除非需要新协议）；组装器仅在该规则类型首次出现时增加一行路由。

## 5. 规则类型束与冲突检测

`RuleEngine.resolve(activations, context)` 产出 `dict[type, Any]`：

- 同一规则重复激活：`RuleValidationError`。
- 未注册规则 key：`UnknownRuleKeyError`。
- 参数非法：`RuleValidationError`（由规则定义的 `validate_params` 抛出）。
- 同一规则类型出现两个产出者：`DuplicateRuleTypeError`。
- 产物不符合声明的规则类型：`RuleValidationError`。

以上错误都在组装阶段抛出，不延迟到仿真运行。

## 6. 组装期接入

`RuntimeAssembler` 持有 `RuleEngine`（`rule_registry` 可注入），在 `assemble()` 开头解析规则类型束，随后按类型机械路由：

- 能量初始值：`bundle.get(InitialEnergyPolicy, ZeroInitialEnergyPolicy())`，组装能量 Store 前写入角色 `EnergyState`。
- 暴击判定：`bundle.get(CriticalDecisionProvider)` 传入 `create_default_damage_formula_registry(critical_decision_provider=...)`；缺省回落固定不暴击。

接线规则：

- 组装器只出现「类型 → 构造参数」的机械路由，不出现任何 `rule_key` 判断；规则语义全部留在规则定义内。
- 束中缺省类型回落目标系统默认行为：不激活任何规则时，仿真行为与规则系统引入前逐位一致。
- 显式注入的构造参数（如 `damage_formula_registry`）优先于规则产物。

## 7. 内置规则

| rule_key | 规则类型 | 产物 |
| --- | --- | --- |
| `start_with_full_energy` | `InitialEnergyPolicy` | `FullInitialEnergyPolicy`：开局能量等于上限，容量为 0 保持 0。 |
| `crit_mode` | `CriticalDecisionProvider` | `off` → `FixedCriticalDecisionProvider(NON_CRITICAL)`；`random` → `SeededRandomCriticalDecisionProvider(seed)`，按 `run_options.seed` 确定性随机。 |
