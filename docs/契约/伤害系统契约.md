# 伤害系统契约

> 状态：正式规范。
> 本文固定伤害系统的稳定 key、数据模型、修饰阶段、数值公式、请求 / 解析 / 序列化契约、结构化错误与 application / content 装配边界。
> 最后更新：2026-10-01。

## 1. 适用范围

本契约适用于：

- `core/systems/damage/` 的请求、结果、修饰、事实容器、公式、resolver 与 handler 行为。
- `content` 的 Damage Impact 工厂、DamageProfile、伤害修饰 provider 与伤害事实容器接入。
- `application/assembly/` 的 provider 与事实容器收集、DamageProfile 注册与 handler 注入。
- 结果库、事件与分析层消费 `DAMAGE_RESOLVED` 载荷和伤害审计。

本契约不定义反应成立条件、Aura / ICD 行为、动作索敌与空间 AOE、护盾吸收或生命提交；这些边界分别由对应领域文档拥有。

## 2. 通用规则

- key 和枚举使用本文给出的稳定小写字符串值，不接受显示名称或自由字符串。
- 百分比使用小数倍率，例如 20% 保存为 `0.2`，200% 保存为 `2.0`。
- 数值统一使用 Python `float`；bool、NaN、正负无穷必须在模型边界拒绝。
- 所有加法使用 `math.fsum`，不依赖迭代顺序产生浮点差异。
- 结算器不使用全局随机数；暴击决策只通过注入式 `CriticalDecisionProvider` 进入。
- 结算器不进行显示舍入、整数化或 UI 格式化。
- 结算器对伤害事实只读不写：请求级事实由发射方在构造请求时绑定，会话级容器由内容侧
  状态逻辑推进；结算过程中任何写入都被禁止。
- 修饰项按稳定 key 排序；相同请求、相同属性查询结果、相同事实状态、相同暴击决策必须
  产生完全一致的 `DamageResult`。
- 显示名称（`damage_name`、`provider_display_name`）只进入审计展示，不作为仿真识别依据。

## 3. 稳定 key 与枚举

### 3.1 完整公式选择键（formula_key）

```text
damage_formula.general
damage_formula.transformative_reaction
damage_formula.lunar_reaction
damage_formula.stellar_reaction
```

`formula_key` 是 Damage 内部公式选择键，由主攻击标签经 `DamageProfileRegistry` 解析得到，不是上游请求变量。未注册主攻击标签一律默认 `damage_formula.general`，**不按标签命名空间区分**；反应伤害标签同样必须显式注册，其正确性由注册表内容与回归测试保证，不由标签前缀判定。

### 3.2 DamageModifierStage

阶段以 `DamageModifierStage` 枚举承载，语义如下：

| Stage | 作用 |
| --- | --- |
| `panel_attribute_value` | 公式读取来源主体面板属性，作为 scaling component 属性槽的基础贡献 |
| `panel_element_bonus` | 读取元素伤害加成属性，作为增伤槽的基础贡献 |
| `panel_crit_rate` | 读取面板暴击率，作为暴击率槽的基础贡献 |
| `panel_crit_damage` | 读取面板暴击伤害，作为暴击伤害槽的基础贡献 |
| `panel_resistance` | 读取目标抗性属性，作为抗性槽 R 的基础贡献 |
| `panel_elemental_mastery` | 读取元素精通，作为反应精通槽的基础贡献 |
| `component_coefficient_percent_add` | 对指定 scaling component 的原始倍率做百分比放大 |
| `component_coefficient_flat_add` | 对指定 scaling component 的倍率直接加值 |
| `base_damage_flat_add` | 基础伤害合计后、增伤区前加入固定伤害 |
| `damage_bonus_add` | 与元素伤害加成进入同一加法区 |
| `defense_reduction` | 作用于目标防御区的减防比例 |
| `defense_ignore` | 作用于本次伤害的无视防御比例 |
| `crit_rate_add` | 只参与本次伤害的暴击率调整 |
| `crit_damage_add` | 只参与本次伤害的暴击伤害调整 |
| `resistance_add` | 对目标抗性 R 直接加值，分段抗性区前生效；负值表示减抗 |
| `transformative_reaction_bonus_add` | 剧变公式专属：并入 `reaction_bonus`，与 `mastery_bonus` 同处精通区加算括号 |
| `stellar_base_multiplier_add` | 星烁基础系数（星烁公式专属）：`fsum` 汇总后加到冻结的 `stellar_base_multiplier`（乘数型基线，**加算**），不替换基线 |
| `stellar_base_bonus_add` | 星烁基础增伤（星烁公式专属）：并入 `(1 + Σ)` 括号内的 `stellar_base_bonus` |
| `stellar_reaction_bonus_add` | 星烁增伤位（星烁公式专属）：并入 `stellar_bonus`，与 `mastery` 同处精通区加算括号 |
| `stellar_authority_multiplier_add` | 星烁大权区（星烁公式专属）：直接加算到 `stellar_authority_multiplier`（大权区乘数），与增伤位分处不同乘区 |
| `stellar_feather_addition_add` | 直伤星烁羽毛区（星烁公式专属）：并入括号内末项 `direct_stellar_feather_addition`；该项**不被**星烁基础系数、基础增伤、精通增伤区与大权区乘算，因此不复用 `base_damage_flat_add` |
| `stellar_ascension_bonus_add` | 星烁擢升（星烁公式专属）：并入 `(1 + Σ)` 括号内的 `stellar_ascension_bonus`；多个擢升来源互相加算 |
| `lunar_base_damage_bonus_add` | 基础伤害提升（月曜公式专属）：并入 `(1 + Σ)` 括号内的 `base_damage_bonus`，乘算整个基础区 |
| `lunar_reaction_bonus_add` | 反应加成（月曜公式专属）：并入 `reaction_bonus`，与 `mastery_bonus` 同处精通区加算括号 |
| `lunar_additional_base_damage_add` | 附加基础伤害（月曜公式专属）：并入基础区括号内末项 `additional_base_damage`；该项**不被**反应倍率、基础伤害提升与精通增伤区乘算，只被暴击、擢升与抗性乘算 |
| `lunar_ascension_bonus_add` | 擢升乘数（月曜公式专属）：并入 `(1 + Σ)` 括号内的 `ascension_multiplier`；多个擢升来源互相加算 |

各公式的白名单：`GENERAL_ALLOWED_MODIFIER_STAGES` 只含直伤槽位阶段，不含任何反应专属阶段；`STELLAR_ALLOWED_MODIFIER_STAGES` = 6 个星烁专属 + 5 个共享通用阶段（倍率位 `component_coefficient_*`、暴击位 `crit_rate_add` / `crit_damage_add`、抗性位 `resistance_add`）；`LUNAR_ALLOWED_MODIFIER_STAGES` = 4 个月曜专属 + 暴击位与抗性位三个共享通用阶段；`TRANSFORMATIVE_ALLOWED_MODIFIER_STAGES` = 1 个剧变专属 + `resistance_add`。各公式的专属阶段两两互不重叠；共享通用阶段可在多个公式白名单中重叠，即同一位置复用。

面板读取词条由公式在属性读取点生成，不是 provider 写入的修饰；它们不参与 stacking 选择，也不进入 `rejected_terms`。四个公式都会产出面板账单，读取哪些面板值由各自已开放的位置决定：通用读取倍率、元素增伤、暴击与抗性（激化另读来源精通）；剧变读取目标抗性（元素精通在 occurrence 冻结、Damage 不查询来源属性）；星烁读取倍率、精通、暴击与抗性；月曜读取倍率（直伤模式）、精通、暴击与抗性。未开放的位置不产生面板词条。星烁/月曜复合模式的逐参与者账单落在各组分的 `modifier_terms` 与 `panel_terms`（随组分审计序列化），顶层账单为空。

星烁与月曜专有的阶段分别落在不同位置（星烁基础系数与基础增伤虽同处括号内，但一个是乘数型系数、一个是相对增伤，语义与审计入口都不同），互不替代。公式专属阶段**不可**用于其他公式；除共享的通用阶段外，普通阶段**不可**用于反应公式——任一越界都在入公式前由阶段校验拒绝，不做静默忽略。该校验由 `validate_formula_modifier_stages` 单一实现，resolver 与各公式体共用，越界一律抛 `DamageProviderViolationError`，不区分校验位置。

**星烁复合伤害的逐参与者收集**：星烁复合伤害对每个参与者独立结算，`formula_key` 与星烁输入沿用整次请求、只替换来源主体的组分查询会被重新收集一次修饰项。公式上下文的收集入口是必填项，不存在「缺入口就退化为整次请求」的分支。因此按 `source_ref` 自筛的 provider 只作用于该参与者自己的组分，不按来源过滤的 provider 对每个参与者各贡献一次。组分收集到的词条记录在该组分的审计字段中，并同样必须通过公式白名单校验。

调试倍率不属于 `DamageModifierStage`，只允许通过 `DebugDamageAdjustment` 构造注入；
生产组装固定使用默认 `1.0`。

### 3.3 其他稳定枚举

```text
Element（复用 core.elements）：
physical
pyro
hydro
electro
cryo
anemo
geo
dendro

CritOutcome：
not_applicable
non_critical
critical

DamageModifierStackingPolicy：
highest
lowest

LunarReactionDamageMode：
character_direct
reaction_composite

DamageReactionCapability：
secondary_amplifying
```

`Element.physical` 是伤害侧合法元素，但不参与元素交互；元素值用于选择 `bonus.damage.*` 与 `resistance.*` 属性。不接受 `none`、显示名称或自由字符串。

主攻击标签是攻击身份和 Profile 查找入口。标签值是各伤害来源自己声明的稳定字符串：直伤标签取自游戏数据，core 不维护公共标签常量表，也不建立标签词汇表或白名单。

主攻击标签是攻击身份字段本身，不是显示名称；跨内容判定（例如武器判定「元素战技命中敌人」）以该字段为准。附加攻击标签只参与条件和修饰，不能改变主攻击身份或绕过 Profile 注册。反应伤害的主攻击标签同样必须显式注册映射，未注册时静默回落通用公式，因此注册正确性由 `create_default_damage_profile_registry()` 的内容与回归测试承担。

**反应伤害主攻击标签**采用中文名称，与角色攻击标签同族；反应身份仍由 `reaction.*` 稳定键承担，两者是两组独立常量。本契约冻结的完整取值如下（这是契约冻结的标识清单，不由 core 维护为公共常量表）：

| 公式 | 标签 |
| --- | --- |
| 剧变 | `超载伤害`、`超导伤害`、`碎冰伤害`、`感电伤害`、`扩散火伤`、`扩散水伤`、`扩散雷伤`、`扩散冰伤`、`燃烧伤害`、`原绽放伤害`、`烈绽放伤害`、`超绽放伤害` |
| 月曜 | `月绽放`、`月感电`、`月结晶` |
| 星烁 | `星超导冰`、`星超导雷`、`星扩散风`、`星扩散冰` |

同一反应输出多元素时按元素拆标签（扩散由 1 个拆为火/水/雷/冰四个，直伤星超导由 1 个拆为冰/雷两个）；命名规则为星烁与月曜标签不带「伤害」后缀、其余反应标签带「伤害」后缀，不使用 `·` 等分隔符。标签与 `element` 是相互独立的字段——标签是攻击身份名称，`element` 是本次伤害的元素类型——两者不做一致性校验。

### 3.4 属性读取与面板词条 provider_key

面板读取词条的 `provider_key` 固定为 `panel.<attribute_key>`，例如 `panel.stat.crit_damage`、`panel.bonus.damage.pyro`、`panel.resistance.hydro`；`source_ref` 使用 `RuntimeSourceKind.SYSTEM`，`instance_id` 为属性主体 `entity_id`。属性系统内部的 `ModifierTerm` 不进入伤害系统，只有解析后的最终面板值进入账单。

### 3.5 伤害事实 key 命名空间

伤害事实的 key 由内容侧自行声明，不是本文维护的固定枚举；唯一的稳定约束是命名空间归属：

- 会话级容器通过 `DamageFactSpec.provider_key` 声明身份，它提供的全部事实 key 必须落在
  `<provider_key>.` 前缀下，例如 `sandrone.fageou.ray_index`。
- key 因此天然按容器分域，不同容器不可能声明同一个 key；`DamageFactIndex` 只需在装配期
  拒绝重复的 `provider_key`。
- 请求级事实由内容单元以 `damage_request_fact_keys` 声明，key 同样使用 `<域>.<key>` 的
  点分形式；同一 key 不得同时作为会话容器 key 与请求级 key（装配期拒绝），否则叠加顺序
  会静默改变取值来源。
- 事实 key 沿用本文第 2 节的小写稳定字符串口径，不接受显示名称或自由字符串。
- 事实 key 与属性读取词条的 `provider_key` 是两套独立标识：前者标识「暴露给伤害修饰的
  模拟事实」，后者标识「公式在属性读取点物化的面板词条」，不能混用。
- 每个事实 key 的语义表（语义、作用域、单位/词表、写入时机、预期消费者）由定义它的内容
  侧在自身文档中维护，参照[内容系统设计](../架构/内容系统设计.md)第 9 节。

## 4. 数据模型

### 4.1 DamageScalingTerm

```text
DamageScalingTerm
├── component_key: str
├── attribute_key: AttributeKey
└── coefficient: float
```

规则：

- `component_key` 是一次请求内稳定且唯一的审计标识。
- `attribute_key` 必须由属性注册表支持，通常为 `stat.atk.total`、`stat.hp.max`、
  `stat.def.total` 或 content 私有属性。
- `coefficient` 使用小数倍率，必须为非负有限数。
- bool、NaN 和无穷值必须拒绝。

多属性缩放通过多个 term 表达：`基础伤害 = fsum(属性值 × 对应 coefficient)`。

### 4.2 DamageProfile 与 DamageProfileRegistry

```text
DamageProfile
├── formula_key              # 完整公式选择键（见 3.1）
├── main_attack_tags: frozenset[str]
└── reaction_capabilities: frozenset[DamageReactionCapability]

DamageProfileRegistry
└── resolve_for_main_attack_tag(main_attack_tag) -> DamageProfile
```

规则：

- 主攻击标签是攻击身份和 Profile 查找入口；不能依赖附加标签或集合遍历顺序选择公式。
- 未注册主攻击标签一律默认使用通用公式，不按标签命名空间区分。
- 默认注册统一由 `application/assembly/damage_profiles.py::create_default_damage_profile_registry()`
  汇总，只注册非通用公式的显式映射；反应侧 Profile 由各反应 mechanic 模块的
  `*_damage_profile()` / `*_damage_profiles()` 工厂声明。
- `DamageReactionCapability.SECONDARY_AMPLIFYING` 只允许显式注册给扩散 Profile；
  handler 校验该 capability 后才接受二次增幅输入。
- 激化不新增 capability，不使用独立公式或合成标签；激化资格由雷/草元素、正倍率证据和
  强类型 `CatalyzeReactionInput` 共同决定，公式始终是通用公式。

### 4.3 DamageImpactSpec

```text
DamageImpactSpec
├── impact_ref
├── main_attack_tag
├── element
├── scaling_terms
├── flat_base_damage
├── can_crit
├── additional_attack_tags
├── strike_type
├── range_type
├── elemental_strength
├── elemental_amount
├── icd_tag_key / icd_sequence_key
├── area
└── display_name
```

规则：

- 一次 Damage Impact 完整声明攻击身份、元素、倍率、暴击资格、打击证据、元素施加、ICD
  绑定、AOE 与显示名。
- 物理伤害不能携带元素施加；`elemental_amount` 为正时必须提供 `elemental_strength`；
  ICD 标签与序列必须同时提供或省略。
- AOE、元素量和 ICD 字段在构造 `DamageRequest` 前已经由 Impact、ICD、Aura 与 Reaction
  消费；`DamageRequest` 通过 `impact_key` 关联完整 Impact 审计，不复制空间范围或 Aura 状态。

### 4.4 DamageRequest

```text
DamageRequest
├── request_id
├── frame
├── formula_key
├── main_attack_tag
├── impact_key
├── source_ref
├── target_ref
├── source_level
├── target_level
├── element
├── source_context
├── scaling_terms
├── flat_base_damage
├── tags
├── request_facts
├── can_crit
├── damage_name
├── reaction_capabilities
├── amplifying_reaction
├── secondary_amplifying_reaction
├── transformative_reaction
├── catalyze_reaction
├── lunar_reaction
└── stellar_reaction
```

规则：

- 来源必须是角色主体；目标可以是目标主体或角色主体。角色作为受方只允许绽放系列/月绽放
  攻击标签（`原绽放伤害`、`超绽放伤害`、`烈绽放伤害`、`月绽放`），由模型级白名单校验。
- `formula_key` 与 `main_attack_tag` 由 handler 从主攻击标签解析出的 DamageProfile 派生，
  不能由请求方绕过注册表自由填写；请求统一从 `DamageImpactSpec` 进入。
- `tags` 合并保存主攻击标签与附加攻击标签；主攻击身份通过 `main_attack_tag` 与审计保留。
- `request_facts` 是**请求级事实**：发射方构造请求时绑定的身份与快照值（如弹序、施放帧
  功率），随请求走到结算，对本次请求的全部目标结算一致。它承载「发射时刻就确定且沿途
  不变」的取值，定义时刻与结算时刻的错位对它无害。会话级状态（跨帧存活、由内容逻辑
  推进的模拟状态）不经请求携带，走内容侧事实容器在收集期读取（见 5.4）。
- `request_facts` 的 key 必须是非空字符串、按第 3.5 节的点分命名空间书写；取值限定为
  有限标量与文本（`DamageFactValue`），非法取值在请求构造期即拒绝。
- source/target level 必须来自组装后的运行态引用解析，不允许 content 用显示名称查找。
- `scaling_terms` 与 `flat_base_damage` 至少有一个能够产生基础伤害（通用与激化公式）；
  剧变请求不得携带普通倍率或 flat base，由强类型输入承载；月曜请求级同样不得携带
  倍率，倍率只能由参与者承载。
- `flat_base_damage` 是请求自身契约的一部分，不替代 Buff 提供的基础伤害加值。
- `can_crit=false` 时结果固定为 `not_applicable`，暴击乘数为 `1`。
- `damage_name` 来自 `DamageImpactSpec.display_name`，缺失时审计回退 action key；
  只作为审计展示。
- request 构造后不可变。

### 4.5 DamageQuery

```text
DamageQuery
├── request: DamageRequest
├── source_attribute_context: AttributeQueryContext
└── target_attribute_context: AttributeQueryContext
```

属性查询 context 至少携带：本次伤害的标签集合（主攻击标签与附加攻击标签合并）、本次
impact 的 `RuntimeSourceRef`、对方主体引用。来源属性查询的 `target_ref` 指向受击目标；
目标属性查询的 `target_ref` 指回伤害来源。

- `damage_formula.lunar_reaction`：必须携带 `LunarReactionDamageInput`；同时拒绝普通

  `StellarReactionDamageFormula` 注册进默认公式注册表，结算结果写入

### 4.7 DamageResult

```text
DamageResult
├── request_id
├── frame
├── formula_key
├── main_attack_tag
├── source_ref
├── target_ref
├── element
├── damage_name
├── base_damage
├── base_damage_additions
├── damage_bonus_multiplier
├── crit_outcome
├── crit_rate
├── crit_damage
├── crit_multiplier
├── reaction_multiplier
├── defense
├── resistance
├── official_damage
├── debug_multiplier
├── final_damage
├── reaction_details
├── secondary_amplifying_resolution
├── catalyze_reaction_resolution
├── lunar_reaction_resolution
├── stellar_reaction_resolution
├── component_results
├── applied_terms
├── rejected_terms
├── trace_level
├── trace_metadata
├── damage_bonus_zone
└── critical_zone
```

规则：

- `DamageResult` 是 `DamageRequest` 与本次收集期事实状态的函数：请求确定编译期固定的结算契约，请求级事实与会话级容器提供判定输入。同一请求在不同事实状态下的结果可以不同，因此审计必须**自洽**——所有实际影响结果的读取（面板属性值、事实取值、暴击决策）都必须能在结果或审计中复现，不允许依赖结算后不可回读的外部状态。请求级事实原样随结果携带（`request_facts`），会话级取值经 provider 产出的词条固化。
- `DamageResult` 构造后不可变，自洽且可独立验证，不依赖外部数据库回填。
- `DamageResult` 只承载伤害系统自身的审计。属性解析过程属于属性系统，不进入伤害结果，
  也不进入 `to_audit_dict()`；属性对伤害的贡献以面板读取词条（`panel_*` stage）的形式
  进入 `applied_terms`，随伤害词条账单呈现。
- `damage_bonus_zone` / `critical_zone` 是增伤区与暴击区的完整分区审计；通用与激化公式
  在组装结果时写入，星烁与月曜直伤模式从组分暴击区写入，剧变暴击区不适用，审计
  序列化不得从 `trace_metadata` 反推。
- `reaction_details` 保存通用反应区结果或剧变反应输入；`secondary_amplifying_resolution`、
  `catalyze_reaction_resolution`、`lunar_reaction_resolution` 保存对应强类型审计，互不覆盖。
- `official_damage` 是正式公式伤害；`final_damage = official_damage * debug_multiplier`。
  `final_multiplier` 属性兼容旧审计命名，当前等价于 `debug_multiplier`。
- 所有数值必须是有限数；最终伤害、正式伤害和调试倍率不得为负数。

## 5. 伤害修饰契约

### 5.1 DamageModifierTerm

```text
DamageModifierTerm
├── stage: DamageModifierStage
├── value: float
├── provider_key: str
├── source_ref: RuntimeSourceRef
├── component_key: str | None
├── stacking_group: str | None
├── audit_tags: tuple[str, ...]
└── provider_display_name: str | None
```

规则：

- component 阶段（`component_coefficient_percent_add`、`component_coefficient_flat_add`、
  `panel_attribute_value`）必须提供合法 `component_key`，且该 key 必须存在于当前请求的
  scaling terms。
- 其余阶段不得提供 `component_key`。
- 百分比统一使用小数。
- stacking group 支持 `highest` / `lowest` 两种选择策略，不支持依赖遍历顺序的 `latest`。
- term 不拥有持续时间、层数或刷新逻辑；这些生命周期属于提供 term 的领域实例。
- `provider_display_name` 由收集器从 provider 声明的 `display_name` 注入，只进入审计，
  不作为识别依据。

面板读取词条由公式在属性读取点通过 `DamageModifierTerm.panel_read()` 生成，`value` 是
属性系统解析后的最终面板值，`provider_key` 见 3.4；它们不是 provider 写入的修饰，
不参与 stacking 选择，也不进入 `rejected_terms`。四个公式都会产出面板账单，读取哪些
面板值由各自已开放的位置决定：通用读取倍率、元素增伤、暴击与抗性（激化另读来源精通）；
剧变读取目标抗性（元素精通在 occurrence 冻结、Damage 不查询来源属性）；星烁读取倍率、
精通、暴击与抗性；月曜读取倍率（直伤模式）、精通、暴击与抗性。未开放的位置不产生
面板词条。星烁/月曜复合模式的逐参与者账单落在各组分的 `modifier_terms` 与 `panel_terms`
（随组分审计序列化），顶层 `applied_terms` 为空。

### 5.2 DamageModifierProvider 与 Scope 访问边界

```text
DamageModifierProviderSpec
├── provider_key
├── reads: tuple[DamageAttributeRead, ...]
├── reads_facts: frozenset[str]
├── writes: frozenset[DamageModifierStage]
├── owner_ref: AttributeSubjectRef | None
└── display_name: str | None

DamageModifierProvider
├── provider_spec
└── contribute(query, scope) -> Sequence[DamageModifierTerm]
```

provider 必须：

- 无副作用。
- 显式声明可读取的属性（subject scope）、可能读取的伤害事实 key 和可能写入的伤害阶段；`writes` 不能为空。
- 不创建或移除机制实例。
- 不发布递归伤害请求。
- 不直接返回最终伤害。

`DamageResolutionScope` 向 provider 暴露受限的属性读取与事实读取能力。provider 只能通过
`resolve_for_provider` 读取声明过的属性、通过 `read_fact` 读取 `reads_facts` 声明过的伤害
事实；`read_fact` 按作用域叠加取值——先查请求级事实（`DamageRequest.request_facts`），
未命中再回落会话级事实索引。所有 provider 调用按稳定 key 排序、不嵌套，越权读取（属性
或事实）、返回其他 provider 的 term、写入未声明阶段或引用未知 component 都会抛出结构化
错误。结算过程中对事实的任何写入都被禁止：provider 无副作用，scope 不暴露写入口。

### 5.3 stacking group

`DamageModifierIndex` 注册并在收集后应用 stacking group：同一 group 内所有 term 必须
属于同一 stage，按 `highest` / `lowest` 选择一个生效项，其余进入 `rejected_terms`；
引用未注册 group 或 stage 不一致时抛出 `ConflictingDamageModifierError`。

### 5.4 伤害事实

伤害修饰的判定输入分两个作用域，与「编译期固定的 `DamageImpactSpec`」「修饰属性值的属性
通道」并列，共同构成伤害修饰的输入面：

- **请求级事实**：发射方构造请求时绑定、随请求走到结算的身份与快照值（如弹序、施放帧
  功率），承载「发射时刻就确定且沿途不变」的取值；存放在 `DamageRequest.request_facts`
  （见 4.4），不经过容器。
- **会话级事实容器**：内容侧定义并维护的**模拟状态视图**，为伤害修饰提供「结算当刻」的
  模拟状态（如解算功率、机制模式）。容器补齐的是「跨帧存活、由内容逻辑推进、只影响判定
  分支」的状态这一层。

**边界原则**：能表达为「修饰某个属性值」的状态走属性系统，不进事实；请求级取发射时绑定，
会话级读结算当刻。伤害系统绝不写入事实，provider 只能读自己声明过的 key。容器是**无状态
转发视图**：`read_fact` 直读底层状态 store（角色状态、领域 store），实现自身不得保存
变量、不得缓存、不得推进状态——推进、清零与快照都归底层状态所有者的既有链路。

```text
DamageFactValue = float | int | bool | str   # 两个作用域共用的取值域

DamageFactSpec                               # 会话级容器声明
├── provider_key          # 容器身份，也是事实 key 的命名空间前缀（见 3.5）
├── facts: frozenset[str] # 该容器暴露的事实 key，不能为空
├── owner_ref: AttributeSubjectRef | None
└── display_name: str | None

DamageFactProvider        # 内容侧实现（无状态转发）
├── fact_spec -> DamageFactSpec
└── read_fact(key) -> DamageFactValue | None

DamageFactIndex           # core 侧索引
├── provider_keys / fact_keys
├── owner_of(key) -> DamageFactSpec | None
├── provides(key) -> bool
└── read(key) -> DamageFactValue | None
```

规则：

- 容器是多个而非单一：`DamageFactIndex` 按稳定顺序注册多个 `DamageFactProvider`，只拒绝
  重复的 `provider_key`；key 归属由 3.5 的命名空间前缀强制。
- 取值域限定为有限标量与文本（`bool` / `int` / `float` / `str`）；`float` 必须有限，其余
  类型在读取点抛 `DamageValidationError`。容器不承载持续时间、层数或刷新语义，这些属于
  内容侧实例自己的生命周期。
- 容器只反映调用当刻的模拟状态，`read_fact` 必须是纯查询、无副作用；容器不持有状态，
  因此也不存在清零职责。
- 同一 key 不得同时由会话容器与请求级事实承载（装配期拒绝，见第 7 节）。

**provider 读取入口**：`DamageModifierProviderSpec.reads_facts` 与 `reads`、`writes` 同构，
是 provider 的读取声明，同时覆盖两个作用域。provider 只能通过
`DamageResolutionScope.read_fact(key)` 读取 `reads_facts` 声明过的 key，且必须处于该
provider 的活动执行区间内；未声明的 key 抛 `DamageProviderViolationError`。取值按作用域
叠加：请求级优先，未命中回落会话级。

**缺失语义**：请求未绑定该 key、或会话容器当刻不持有该 key，一律返回 `None`，表示
「条件不成立」，而不是错误。这样 provider 分支写成「读到 `None` 就不生效」，不必区分
「没有这个事实」与「事实当刻为空」。正因为缺失是静默的，装配期必须一次性检出「provider
声明读取、但既无容器提供也无比内容单元声明为请求级事实」的 key（见第 7、11 节），避免
拼错的 key 永远读到空值。

**审计自洽**：请求级事实原样进入 `DamageResult.request_facts` 并随审计载荷序列化；会话级
取值与属性贡献一样，通过 provider 产出的 `DamageModifierTerm` 固化——term 的 `value` 与
`audit_tags` 一旦写入即不可变，结果复现不依赖结算后回读任何容器（见 4.7）。

## 6. 数值公式

### 6.1 通用伤害公式

```text
倍率区 × 增伤区 × 暴击区 × 反应区 × 防御区 × 抗性区
```

倍率区：

```text
final_coefficient =
    original_coefficient * (1 + fsum(component_coefficient_percent_add))
    + fsum(component_coefficient_flat_add)

component_damage = resolved_attribute_value * final_coefficient

倍率区结果 =
    fsum(component_damage)
    + request.flat_base_damage
    + fsum(base_damage_flat_add)
```

增伤区：

```text
damage_bonus = resolved bonus.damage.{element} + fsum(damage_bonus_add)
damage_bonus_multiplier = 1 + damage_bonus
```

不允许隐式截断；若后续确认需要上下限，应由专用 policy 明确实现。

暴击区：

```text
crit_rate = resolved stat.crit_rate + fsum(crit_rate_add)
crit_damage = resolved stat.crit_damage + fsum(crit_damage_add)
effective_crit_rate = clamp(crit_rate, 0, 1)

crit_multiplier =
    critical: 1 + crit_damage
    non_critical: 1
```

暴击结果由注入式 `CriticalDecisionProvider.decide(query, effective_crit_rate)` 提供；
可暴击伤害不能返回 `not_applicable`。生产环境的带种子随机 provider 需要单独评审随机
种子和回放契约。

反应区（增幅反应）：

```text
mastery_bonus = 2.78 * EM / (EM + 1400)
reaction_multiplier = base_multiplier * (1 + mastery_bonus + reaction_bonus)
```

防御区：

```text
source_factor = source_level + 100
target_factor = (target_level + 100) * (1 - defense_ignore) * (1 - defense_reduction)
defense_multiplier = source_factor / (source_factor + target_factor)
```

- 防御减免与无视防御使用独立因子，各自必须为非负有限数。
- 不对组合结果做静默截断；分母非正时抛出结构化结算错误。
- 不通过构造虚拟目标 `stat.def.total` 重复表达等级防御公式。

抗性区：

```text
R < 0:          resistance_multiplier = 1 - R / 2
0 <= R <= 0.75: resistance_multiplier = 1 - R
R > 0.75:       resistance_multiplier = 1 / (1 + 4 * R)

effective_resistance = resolved resistance.{element} + fsum(resistance_add)
```

负的 `resistance_add` 表达减抗；减抗也可以继续通过目标 `resistance.*` 的运行时属性
modifier 实现，两条路径的加值合并后进入同一分段函数。抗性区不维护独立的
`resistance_shred` 状态。

最终聚合：

```text
official_damage =
    base_damage
    * damage_bonus_multiplier
    * crit_multiplier
    * reaction_multiplier
    * defense_multiplier
    * resistance_multiplier

final_damage = official_damage * debug_multiplier
```

结果必须是有限数字；出现 NaN、无穷值或不允许的负最终伤害时抛出结构化错误，不静默修正。

### 6.2 激化附加区

激化不选择独立公式，而是作为通用公式的可选附加区：

```text
mastery_bonus = 5 * EM / (1200 + EM)

base_damage_addition =
    level_multiplier
    * reaction_multiplier
    * (1 + mastery_bonus + reaction_bonus)
```

- 超激化 `reaction_multiplier = 1.15`，蔓激化 `reaction_multiplier = 1.25`；当前
  `reaction_bonus = 0.0`。稳定值由[激化反应契约](./元素反应/反应/激化反应契约.md)冻结。
- `source_level` 与 `stat.elemental_mastery` 从当前 `DamageQuery` 实时读取；等级系数复用
  已注册的共享等级系数表，并记录 table key 与元素精通面板读取词条。
- 激化附加值是独立公式区，不允许通过通用 `DamageModifierTerm` 伪造；结算结果作为命名来源
  进入 `DamageResult.base_damage_additions`，与普通倍率区结果相加后再经过增伤、暴击、防御
  和对应元素抗性。

### 6.3 剧变反应公式

```text
damage =
    level_multiplier
    * base_multiplier
    * (1 + mastery_bonus + reaction_bonus)
    * resistance_multiplier
```

- 等级系数、元素精通与精通加成在 occurrence 时由 `TransformativeReactionInput` 冻结；
  `mastery_bonus` 必须匹配 `16 * EM / (EM + 2000)`，Damage 不查询来源属性。
- 防御策略固定为 `approximate_unity`，防御乘区为 `1`；不接入普通倍率、增伤、暴击或
  防御区。
- 公式专属阶段 `transformative_reaction_bonus_add` 是增伤位的唯一入口：其数值以
  `fsum` 汇总后 **并入** `reaction_bonus` 进入上式精通区括号，不替换
  `TransformativeReactionInput` 冻结的基线值，也不改变防御策略与不暴击口径。
- 抗性位复用通用阶段 `resistance_add`：公式体先把「目标面板抗性 +
  Σ(`resistance_add`)」合并成有效抗性再传抗性策略，并把目标面板抗性读取词条写入
  面板账单；该位开放后剧变的 `applied_terms` 不再恒为空。

扩散 Profile 声明 `SECONDARY_AMPLIFYING` 时的二次增幅：

```text
基础剧变伤害
× [base_multiplier * (1 + 2.78 * captured_EM / (captured_EM + 1400) + reaction_bonus)]
× 对应元素抗性
```

基础剧变和二次增幅均使用扩散 occurrence 时捕获的数据；二次增幅不查询后续 round 的
来源属性，也不引入普通增伤、暴击或防御区。

### 6.4 月反应公式

组分公式：

```text
mastery_bonus = 6 * EM / (2000 + EM)

base_damage_after_reaction =
    core_base_damage
    * reaction_multiplier
    * (1 + base_damage_bonus)
    * (1 + mastery_bonus + reaction_bonus)
    + additional_base_damage

component_damage =
    base_damage_after_reaction
    * crit_multiplier
    * ascension_multiplier
    * resistance_multiplier
```

组分基础值来自参与者 `scaling_terms` / `flat_base_damage`（角色直接模式必须提供），或
已确认的等级基数表：

```text
80: 1077.4
90: 1446.9
95: 1561.5
100: 1674.8
```

复合聚合的稳定顺序和权重：

```text
按完整组分伤害从大到小排序（同值时按 participant_ref 稳定排序）
最高组分 × 0.60
第二组分 × 0.30
其余组分 × 0.05
```

- 组分结果和聚合结果分别进入 `LunarReactionComponentResolution` 与
  `LunarReactionDamageResolution`，通过 `DamageResult.lunar_reaction_resolution` 保留
  参与者、排序、暴击、抗性、权重、槽位三段审计及正式/调试伤害审计。
- 月曜不使用普通元素增伤区或普通防御区；每组分使用独立属性查询与注入式暴击决策。
  请求级不得携带 `scaling_terms` / `flat_base_damage`——倍率只能由参与者承载，
  公式体在入算前拒绝请求级倍率。
- **组分查询继承月曜公式键**：复合与直伤模式的组分查询都沿用整次请求的 `formula_key`
  （月曜），只替换来源主体、来源等级、`can_crit` 与参与者倍率，并把
  `reaction_profile_key` 并入标签。因此按 `formula_key` 自筛的 provider（如月兆的非月兆
  月曜增伤）能在组分收集里被识别；只对通用公式自筛的 provider 不会作用于月曜组分。
- **可修饰位置与当前开放度**：本公式的每个可修饰位置都以槽位账单承载，按「冻结基线 + Σ(该槽位修饰项)」合并；位置与开放度如下：

  | 位置 | 承载阶段 | 开放度 |
  | --- | --- | --- |
  | 组分基础值 `core_base_damage` | — | **不开放**：复合模式是机制冻结的等级基础伤害；直伤模式倍率由参与者承载，`component_key` 无法在请求级顶层收集里寻址 |
  | 反应系数 `reaction_multiplier` | — | **不开放**：机制侧冻结的反应口径，无内容侧来源 |
  | 基础伤害提升 `base_damage_bonus` | `lunar_base_damage_bonus_add` | 开放（专属阶段，乘算整个基础区） |
  | 精通 `mastery_bonus` | 面板读取 `panel_elemental_mastery` | 开放（面板读取派生，本身不可被效果词条修饰） |
  | 反应加成 `reaction_bonus` | `lunar_reaction_bonus_add` | 开放（专属阶段，并入精通区括号） |
  | 附加基础伤害 `additional_base_damage` | `lunar_additional_base_damage_add` | 开放（专属阶段，基础区括号内末项） |
  | 暴击区 | `crit_rate_add` / `crit_damage_add` | 开放（复用通用阶段；是否暴击由参与者 `can_crit` 与注入式决策决定） |
  | 擢升乘数 `ascension_multiplier` | `lunar_ascension_bonus_add` | 开放（专属阶段，多个来源互相加算） |
  | 抗性乘数 | `resistance_add` | 开放（复用通用阶段） |

  `core_base_damage` 与 `reaction_multiplier` 未开放的前置条件已记录在
  `LUNAR_ALLOWED_MODIFIER_STAGES` 的注释中；开放 `core_base_damage` 需要把直伤倍率
  从参与者挪到请求级，属契约变更，需单独评估后再改。
- 等级基数表、精通系数和分母默认使用已确认资料中的生产数值；调用方可以显式注入替代
  `lunar_formula` 用于测试或未来配置覆盖。

**反应系数与权重口径**（月感电 / 月结晶）：

- **未折入口径（本仓库）**：月感电 `reaction_multiplier = 3.0`、月结晶 `1.6`；与各自**直伤倍率同值**。同值不是代码复用错误，而是资料本身的定义方式——月曜体系里「反应系数」与「角色倍率」是同一个数。
- **折入口径**：把最高项权重折进系数后的写法，月感电 `1.8`、月结晶 `0.96`，配 `1 : 1/2 : 1/12` 分配。两套口径**逐组分等价**：`0.60 : 0.30 : 0.05 == 1 : 1/2 : 1/12`，且 `3.0 × 0.60 = 1.8`、`1.6 × 0.60 = 0.96`。
- **换口径必须同时改反应系数与分配权重**：只改一边会把 `0.60` 重复计入（改系数）或漏计（改权重），整体偏差恰为 `0.60` 倍。因此不得仅凭「资料写 1.8、代码是 3.0」判定代码错配。
- 权重在代码中单点定义（`core/systems/damage/lunar.py` 的 `LUNAR_COMPOSITE_WEIGHTS`），公式体按名次取值、超出表长沿用最后一项，不得在公式体里重复硬写 `0.60 / 0.30 / 0.05`。
- 月绽放不产生反应月曜伤害（反应本身无倍率），不涉及本口径；月感电与月结晶的反应复合路径共用同一条系数 + 权重聚合结构。
- 数值出处：米游社《元素反应（高等元素论）》(`article/25901063`)「直伤月反应倍率（月感电 3.0，月结晶倍率 1.6），反应月反应倍率（月感电 1.8，月结晶 0.96）」；米游社《月曜反应》(`article/77019346`) 分配系数「`0.6 × 第一高 + 0.3 × 第二高 + 0.05 × 其他`」；BWIKI《元素反应》页「反应倍率」表与《月结晶伤害公式》页。适用版本：月之八。

### 6.5 调试专用区

```text
最终输出 = 正式公式结果 × debug_multiplier
```

- `debug_multiplier` 默认固定为 `1.0`。
- 调试区不属于任何正式伤害公式或可由 content 使用的普通 modifier stage。
- 只有测试或显式调试入口可以注入非 `1.0` 的值，生产组装默认不得启用。
- 审计结果必须能够区分正式公式结果与应用调试区后的最终输出。

## 7. Resolver 契约

`DamageResolver.resolve(query, *, trace_level=TraceLevel.FULL) -> DamageResult`：

- 从 `DamageFormulaRegistry` 选择完整公式；公式必须已注册。
- 创建一次 `DamageResolutionScope`，携带本次结算的 query、trace level、事实索引与属性解析会话，按稳定 key 排序收集 `DamageModifierTerm`。
- 构造 resolver 时交叉校验：provider `reads_facts` 声明的每个 key 都必须有会话容器提供，
  或被某内容单元声明为请求级事实（`request_fact_keys`）；两者都不满足时抛
  `DamageValidationError`。请求级 key 与会话容器 key 撞名同样拒绝。
- 校验 provider 返回的 term 阶段属于公式允许集（`_validate_formula_stages`）。
- 公式按槽位账单计算（面板读取词条 + 效果词条），输出不可变 `DamageResult`。
- 同一次伤害观察到的机制实例集合必须在 resolution scope 内保持稳定；伤害查询期间
  不能添加、刷新、移除或过期领域实例，也不能改写任何事实。

trace level 只能改变审计数据量，不能改变数值结果：

- `none`：只保留最终乘区和值。
- `applied`：保留已应用 term（含面板读取词条）。
- `full`：额外保留被拒绝 term 和 policy 中间值。

## 8. 请求处理契约

`DamageRequestHandler` 把已经校验的 Damage Impact、目标解析、元素交互结果和 Damage
Profile 转换为逐目标 `DamageRequest`：

- 一次 Damage Impact 命中几个目标，就按稳定 `target_refs` 顺序产生几份独立
  `DamageRequest`；每个目标独立查询抗性、独立生成结果和审计。
- `formula_key` 由主攻击标签对应的 DamageProfile 派生；`can_crit=false` 的请求结果固定
  `not_applicable`。
- 模型级校验在动态运行时请求上执行：来源主体、目标白名单、scaling 存在性、反应输入
  组合、元素与 impact 一致性、强类型字段值域。
- Reaction 新产生的伤害只创建新的 Damage Impact，并在同帧下一 settlement round 进入
  流程；Reaction 不直接构造 `DamageRequest`。

## 9. 事件与序列化契约

### 9.1 DAMAGE_RESOLVED

`DAMAGE_RESOLVED` 由伤害系统在结算完成后发布：

- 不可取消、payload 不可变、默认记录、可以驱动后续机制。
- payload 持有不可变 `DamageResult`：`result` 保留摘要，`audit` 保存完整伤害公式审计。
- 事件类型加入需要同步[事件类型](../架构/事件系统/事件类型.md)。

### 9.3 DamageResult.to_audit_dict()

完整审计至少包含：

- `component_results`：倍率组件的属性值、原始/最终倍率与伤害贡献。通用/激化与星烁直伤
  取倍率区组件；月曜直伤取唯一组分的倍率区组件（该数值是反应前值，与 `base_damage` 的反应后
  加权值不同量纲）；星烁/月曜复合模式的倍率账本随各组分序列化，顶层为空；
- `base_damage_additions`：固定基础伤害加值；
- `damage_bonus`：元素增伤、修饰增伤与最终乘数（通用/激化来自 `damage_bonus_zone`）；
- `critical`：可暴击、暴击率、实际暴击率、暴击伤害、结果与乘数（通用/激化来自
  `critical_zone`）；
- `defense`：来源/目标等级、减防、无视防御与乘数；
- `resistance`：基础抗性、抗性修饰加值、有效抗性与乘数；
- `reaction`：带 `kind` 判别（`amplifying` / `transformative` / `catalyze` / `lunar` /
  `stellar`）的单一对象，二次增幅嵌套在 `transformative` 内；同一时刻只有一个判别值，
  判定顺序为月曜 → 星烁 → 激化 → 增幅/剧变，即激化存在时该字段承载激化、主反应载荷仍在
  摘要 `reaction`；
- `applied_terms`、`rejected_terms`：伤害槽位账单。通用/激化、星烁直伤与月曜直伤公式
  的 `applied_terms` 在效果词条后追加面板读取词条（`panel_*` stage，`provider_key` 为
  `panel.<attribute_key>`），构成“面板基础贡献 + 效果修饰”的完整账单；剧变公式同样
  计入面板抗性读取词条；星烁/月曜复合模式的逐参与者账单落在各组分审计
  （`components[].modifier_terms` 与 `components[].panel_terms`）内并随组分序列化，顶层为空；
- `request_facts`：本次结算读取的请求级事实快照（原样透传自 `DamageRequest`），使结果
  复现不依赖回读任何容器；会话级取值不在此列，经 provider 产出词条固化；
- `trace_metadata`：额外审计元数据。

审计不包含属性系统的内容：属性解析 trace 不出现在伤害审计中，需要属性侧审计时经由属性
系统自身的解析结果读取。

字段保持稳定只增不改；存储载荷见[结果库契约](./结果库契约.md)第 5.3 节，事件详情接口
形状见[UI API 契约](./ui/UI%20API%20契约.md)第 8 节。

## 11. Application 与 content 装配契约

- `ContentUnit` 通过 `damage_modifier_providers` 注册伤害修饰 provider，通过
  `damage_fact_providers` 注册会话级事实容器、通过 `damage_request_fact_keys` 声明本单元
  发射方可能写入的请求级事实 key；属性 provider、伤害 provider 与事实容器使用
  各自的类型化字段，新伤害实现不应根据 `scope` 字符串和自由 `object` query 猜测协议。
- 装配链路把各 `ContentUnit` 的 `damage_fact_providers` 聚合进 `RuntimeContentBundle`，
  由 `DamageFactIndex` 注册并注入 `DamageResolver`；`damage_request_fact_keys` 去重聚合后
  作为 `request_fact_keys` 传入 resolver 参与交叉校验。
- content impact factory 只负责展开 Damage Impact，不查询最终属性、不计算防御/抗性、
  不决定 Buff 是否生效、不直接生成最终伤害、不扣减生命、不选择公式。
- `application/assembly/damage_profiles.py` 是 DamageProfile 默认注册的唯一汇总入口。
- 以下错误应尽量在组装阶段暴露，不能把可提前发现的 content 错误延迟到战斗中：
  - 未注册 damage handler 或 provider；
  - scaling ref 不存在或倍率 payload 格式错误；
  - 不支持的元素、属性 key、主攻击标签、附加攻击标签、打击类型或远近类型；
  - `reaction.` 标签缺少显式映射、Profile 引用了未注册公式，或同一主标签重复注册；
  - provider 声明了非法属性读取或伤害阶段写入；
  - provider 声明的伤害事实读取既无容器提供、也未被内容单元声明为请求级事实（`DamageValidationError`）；
  - 请求级事实 key 与会话容器 key 撞名（`DamageValidationError`）；
  - 重复 provider key、重复事实容器 `provider_key`，或非法 stacking group。

## 12. 测试要求

`tests/unit/core/systems/damage/` 至少覆盖：

- 单属性缩放和多属性缩放。
- component 倍率百分比修饰与倍率加值。
- 固定基础伤害加值。
- 元素增伤与伤害专用增伤的聚合。
- 不可暴击、固定暴击和固定不暴击。
- 同等级无修饰防御区。
- 减防与无视防御的独立输入。
- 负抗性、普通抗性、`0.75` 边界和高抗性。
- 多个 final multiplier 的稳定顺序。
- stacking group 的 applied/rejected term。
- 面板读取词条进入槽位账单且不改变结算数值。
- 伤害事实：key 命名空间校验、重复 `provider_key` 拒绝、非法取值类型拒绝、缺失语义返回
  `None`、`reads_facts` 越权读取拒绝、请求级优先于会话级的叠加顺序、装配期对「声明读取
  但无来源」与「请求级 key 撞名会话容器」的交叉校验。
- bool、NaN、无穷、空 key、非法主体和未知元素。
- trace level 不改变最终数值。

浮点测试优先使用明确的绝对或相对容差；core 不为了让断言通过而提前舍入。测试组织与验收口径见[测试规范](../工程/测试规范.md)。

- 直接伤害回归 golden case 待正式契约来源重新建立。
