# 输入轨迹契约草案

> 状态：草案。
> 本文档记录按键输入架构的阶段性讨论结果。尚未讨论完成的内容统一列入“待讨论事项”，不要视为最终契约。

最后更新：2026-07-03

## 1. 目标

新项目的仿真输入不应只抽象为线性动作序列。为了更接近游戏运行方式，第一版输入架构先记录“玩家在某一帧按下或松开了哪些键”，再由队伍控制器、当前场上角色和动作状态机解释这些输入。

核心原则：

- 输入层记录按键事实，不直接生成具体角色动作。
- `press` 与 `release` 都进入控制器，由角色逻辑判断点按、长按或特殊状态。
- “按键发生”和“动作成功发生”是两件事，后续应能分别审计。

## 2. 仿真假设

第一版输入轨迹只覆盖键盘和鼠标按钮：

- 不支持手柄输入。
- 不支持自定义键位映射。
- 不记录鼠标移动、镜头、视角或准星变化。
- 不实现移动键功能，默认角色无法通过 `W/A/S/D` 移动。
- 实际位移由后续角色动作、技能或空间系统解释，不由输入系统直接计算。

这些假设与旧项目文档中的简化空间模型保持一致：战场主要使用 `X/Z` 平面做范围判定，`Y` 轴只用于下落攻击等高度敏感动作；项目不模拟实体间刚体挤压。

## 3. 数据结构

输入轨迹按帧分组：

```text
InputTrace = list[InputFrame]

InputFrame
├── frame: int
└── events: list[KeyEvent]

KeyEvent
├── key: string
└── phase: "press" | "release"
```

示例：

```json
[
  {
    "frame": 120,
    "events": [
      {"key": "keyboard.e", "phase": "press"},
      {"key": "mouse.left", "phase": "press"}
    ]
  },
  {
    "frame": 145,
    "events": [
      {"key": "keyboard.e", "phase": "release"}
    ]
  }
]
```

## 4. 支持的按键

第一版只支持以下按键：

```text
keyboard.e
keyboard.q
keyboard.space
keyboard.1
keyboard.2
keyboard.3
keyboard.4
mouse.left
mouse.right
```

默认含义：

| 按键 | 默认控制含义 |
| --- | --- |
| `keyboard.e` | 战技按钮 |
| `keyboard.q` | 爆发按钮 |
| `keyboard.space` | 跳跃按钮 |
| `keyboard.1` ~ `keyboard.4` | 切换到对应队伍槽位 |
| `mouse.left` | 攻击按钮 |
| `mouse.right` | 冲刺按钮 |

注意：这里的默认控制含义不是最终动作。比如 `keyboard.e` 只表示玩家操作了战技按钮，具体是点按战技、长按战技、进入特殊状态还是输入无效，由当前角色和动作状态机解释。

## 5. 校验规则

已确认规则：

- 第一版模拟器骨架中，`frame` 必须是正整数。
- `InputFrame` 按 `frame` 升序排列。
- 同一个 `InputTrace` 中 `frame` 不重复；同帧输入合并到同一个 `events` 列表。
- `phase` 只允许 `press` 或 `release`。
- `key` 只允许使用本文列出的第一版支持按键。
- 同一个 `InputFrame.events` 中，同一个 `key` 不能重复出现。
- 同一帧多个事件按 `events` 列表顺序处理，不设置隐藏优先级。
- 遇到不支持的按键，应在配置校验阶段报错。
- 每一个 `press` 必须有且只有一个后续 `release`。
- 如果某个 `key` 尚未处于按下状态就出现 `release`，应在配置校验阶段报错。
- 如果某个 `key` 已经处于按下状态又出现新的 `press`，应在配置校验阶段报错。
- 仿真结束时不能存在仍处于按下状态且未释放的按键。

说明：`frame=0` 的精确定义仍待讨论，当前先不进入有效配置。

## 6. 初步分发规则

输入事件先进入队伍控制器：

```text
InputSystem
-> TeamController
-> 当前场上角色控制器 / 队伍切换逻辑
```

已确认规则：

- `keyboard.1` ~ `keyboard.4` 的 `press` 触发切换槽位请求。
- `keyboard.1` ~ `keyboard.4` 的 `release` 只更新输入状态，不触发切换逻辑。
- `keyboard.e`、`keyboard.q`、`keyboard.space`、`mouse.left`、`mouse.right` 的 `press` 与 `release` 都交给当前场上角色或对应控制逻辑处理。
- 输入状态负责计算按住帧数，例如 `held_frames = release_frame - press_frame`。
- 同一帧事件顺序只表示输入送达顺序，不保证后续输入一定产生动作。
- 当前最小队伍控制器使用 1-based 槽位编号，`keyboard.1` 对应 `active_slot=1`。
- 当前最小队伍控制器在切换成功时更新当前场上槽位，发布 `AFTER_CHARACTER_SWITCH` 事件，并可向动作管理器登记切人后摇 busy 窗口。
- 当前最小队伍控制器会记录动作按钮输入事实；当连接动作管理器时，动作按钮 `press` 会形成动作请求，可能被接受或因 busy 等原因拒绝。
- 当前最小动作管理器会为被接受的动作请求生成 `ActionInstance`，但不生成普通攻击、战技、爆发、跳跃或冲刺的具体时间轴。
- 当动作请求带目标查询且上下文挂载了 `Space` 时，动作实例会记录 X/Z 平面候选目标 id；候选目标不代表最终命中或造成伤害。
- 当前最小动作管理器作为帧更新对象参与 `RuntimeWorld`；只要动作或后摇 busy 窗口尚未结束，模拟器不会仅因输入轨迹消费完成而停止。
- 输入系统会为每个已消费的按键事件发布 `INPUT_KEY_EVENT`，用于审计“按键确实发生过”。
- 动作管理器会为每个动作请求发布 `ACTION_DECISION`，用于审计请求是否被接受以及拒绝原因。
- 如果前一个输入让角色进入后摇、输入锁定或其他不可接受状态，后续输入应被动作状态机拒绝并记录原因。
- 被拒绝的 `press` 不开启一次有效动作输入；对应 `release` 只关闭输入状态，不补触发点按或长按逻辑。

示例：

```json
{
  "frame": 120,
  "events": [
    {"key": "keyboard.2", "phase": "press"},
    {"key": "keyboard.e", "phase": "press"}
  ]
}
```

若 `keyboard.2` 切换成功并进入切人后摇，则同帧后续 `keyboard.e` 会被送达但可能因后摇被拒绝，不产生战技动作。

## 7. 帧内处理顺序

输入轨迹在每帧开始时处理：

```text
1. 进入当前帧。
2. 处理当前帧的 `input_trace` 事件。
3. 推进角色、动作、实体和系统的帧更新。
4. 发布帧结束事件。
```

因此，第 N 帧的输入在第 N 帧开始送达控制器，后续动作状态机和系统推进时可以看到本帧输入造成的状态变化。

## 8. 审计事件

当前最小运行时使用两类事件区分输入事实和动作决策：

- `INPUT_KEY_EVENT`：记录 `key`、`phase` 和 `held_frames`。该事件只说明按键输入被消费，不说明动作成功。
- `ACTION_DECISION`：记录 `key`、`active_slot`、`accepted`、`reject_reason`、`occupied_until_frame`、`lock_source` 和 `target_ids`。该事件说明动作请求是否被动作管理器接受，以及接受时查询到的候选目标。

例如，同一帧内先 `keyboard.2 press` 再 `keyboard.e press` 时，`keyboard.e` 仍会有 `INPUT_KEY_EVENT`；如果切人后摇 busy 窗口仍存在，还会有一条 `accepted=false`、`reject_reason=busy` 的 `ACTION_DECISION`。

## 9. 待讨论事项

- `frame=0` 输入的精确定义。
- 切人动作后摇和输入锁定的具体帧数来源。
- `ActionInstance` 如何展开为具体时间轴、命中点、伤害点和取消窗口。
- 快照和结果库如何持久化输入事实与动作决策事件。
