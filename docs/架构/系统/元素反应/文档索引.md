## 1. 目录定位

本目录是 `core/systems/reaction/` 的唯一正式架构入口。文档分为两层：

- 目录根部保存所有反应共享的系统边界、领域模型、判定流程、事务与验证规则。
- `反应/` 保存单个反应或紧密机制簇的专门设计，不重复公共运行时。

跨领域编排不属于 Reaction 系统，见[元素反应协调器设计](../../协调/元素反应协调器设计.md)。稳定字段、key 和失败边界见[元素反应契约文档索引](../../../契约/元素反应/文档索引.md)。

## 4. 真值与适用规则

解释元素反应行为时按以下顺序：

1. 项目维护者确认的机制资料与对应正式契约。
2. 本目录公共架构和具体反应设计。
3. 生产代码及其单元测试、golden case，用于验证落地情况。
4. 项目决策记录，用于解释关键选择和历史原因。

历史评估和分版实施过程不属于当前运行时真值，已经迁移的内容不在当前正式文档之外重复维护。文档、代码和测试冲突时，必须根据已确认资料和 golden case 修正错误的一侧，不能同时保留两个对外语义。

## 5. 扩展规则

新增或修改反应时：

- 单反应规则优先进入自身机制目录、设计、契约和测试。
- 两个以上反应共享且由 Reaction Runtime 承担的稳定能力，才进入公共架构。
- 不同机制目录不得互相调用 Runtime、Store 或 handler。
- 复合候选的顺序、并行和排他关系由 Reaction 公共候选组件显式表达。
- 新字段必须明确所有者、默认值、校验、稳定身份、序列化和事务边界。
- 机制数值必须能追溯到人工确认资料和 golden case。
- 未确认或未实现内容必须放入明确标记的草案，不得混入正式架构。

月绽放、月感电、月结晶均已完成第一条纵向切片并拥有独立设计文档。具体机制仍未覆盖的内容必须直接记录在对应正式设计和契约的“当前边界/非目标”章节，不另设平行临时真值入口。
