# 结果存储系统设计

> 状态：已确认（2026-08-11 边界讨论定稿）。
> 本文定义结果存储系统（Results Store）的职责、数据分层、存储组织、还原与查询模型、模块边界和演进策略。SQLite 具体表结构与字段见[结果库契约](../契约/结果库契约.md)。
> 工程约定见[结果存储系统规范](../工程/结果存储系统规范.md)。
> 最后更新：2026-08-11

## 1. 定位

结果存储系统负责保存一次仿真运行产生的完整结果数据，支撑查询、分析、复盘与结果对比。

它回答三个问题：

- 这次运行是谁、什么时候跑的（运行记录）。
- 用了什么输入和什么版本的资产（输入快照与 provenance）。
- 运行过程中发生了什么、任意时刻状态如何（事件流与初始快照）。

明确不在范围内：

- 资产库（只读生成物，独立系统，位置不随 `data_dir` 搬迁）。
- 日志（工程运维数据，独立系统）。
- UI 工作区与工作流定义（未来 UI 系统所有）。
- 项目配置源文件（归工作区/文件存储）。
- 分析报告与导出物（归导出/文件存储）。

## 2. 结果数据的目的

- 结果数据服务于**分析与可视化**。
- 结果数据的第一职责是**还原模拟的整个过程**；只有保证可还原，才可以进行分析。
- 还原依靠**存储的事实**（事件流 + 初始快照），不依靠重跑。
- **复现不等于历史保真**：用当前引擎重跑旧输入得到的是新结果。重跑只能作为验证手段或显式“重新计算”动作（生成新的运行记录），不能作为查看历史的方式。

## 3. 真值层与派生层

真值层（存储，成功后不可变）：

- 运行记录：`session_id`、状态、时间、输入快照、provenance、运行元摘要。
- 事件流：过程事实，按 `ordinal` 有序。
- 初始快照：第 0 帧状态基线。

派生层（analysis 读取侧计算，不落库）：

- 分析摘要：总伤害、DPS、反应统计、覆盖率等。
- 时间序列：伤害曲线、HP/能量曲线、Buff 覆盖等。
- 任意帧状态视图。
- 跨运行对比数据。

物化（可选）：跳变表（jump track）等派生轨道，只在具体查询被证明慢或高频时建立；物化产物永远可重建，不进入真值 schema。

## 4. 数据类别边界

| 数据类别 | 边界结论 |
| --- | --- |
| 资产数据 | 独立系统；结果侧只记录 provenance。 |
| 模拟输入源文件 | 归工作区；扫描 `inputs/` 目录发现，`input_key` 定身份，平铺不嵌套。 |
| 项目配置 | `config.toml`（TOML + 注释，`tomlkit` 写入）；第一批配置项 `schema_version`、`workspace.data_dir`。 |
| 仿真会话/运行记录 | 运行前分配 `session_id`；成功后不可变；失败/取消留最小记录。 |
| 摘要数据 | 运行元摘要落结构化列；分析摘要读取时计算。 |
| 事件流 | 事实真值层；第一版存 SQLite 表；归档触发条件见第 7 节。 |
| 帧快照 | 不存全量逐帧快照；初始快照作为状态查询基线。 |
| 高频状态数据（HP/能量等） | 不按帧存数值；事件携带 `before/after`，基线 + 折叠还原。 |
| 投影数据 | 投影不是真值；归 analysis 读取侧；按性能物化。 |
| 任务状态 | 归任务系统；`job_id ↔ session_id` 单向关联。 |
| 日志 | 独立；仅通过关联 ID 关联。 |
| UI 工作区/工作流定义 | 独立；工作流定义文件保存于 `workflows/`，只引用 `session_id`，不拥有结果。 |
| 分析报告/导出物 | 归导出/文件存储；可再生成。 |

## 5. 术语

- **模拟输入**：一次仿真要模拟什么——队伍、场景、按键输入轨迹、规则、运行帧数，即当前 `SimulationInput` 的内容；源文件归工作区。
- **项目配置**：项目级 TOML 文件，保存 `schema_version`、`workspace.data_dir` 等设置。
- **结果存储系统**：本系统正式名称（Results Store）。
- **结果库**：SQLite 具体实现（`infrastructure/results_sqlite/`）。
- **输入快照**：进入仿真的不可变输入副本，随运行记录保存。
- **初始快照**：第 0 帧状态基线，随运行记录保存。
- 动词统一使用保存/写入/读取/投影/归档/清理；“持久化”不作为正式术语。

## 6. 运行生命周期

```text
运行开始前分配 session_id
-> 组装并运行仿真（core 发布事件、导出帧快照）
-> 执行器订阅事件并按记录规则收集
-> 成功：写入完整运行记录（输入快照、初始快照、元摘要、provenance）+ 事件流
-> 失败/取消：写入最小运行记录（状态、时间、输入快照、错误），不写事件流与元摘要
-> 运行记录不可变，同一 session_id 不允许覆盖
```

## 7. 存储组织

- 结果库位于 `<data_dir>/results/results.db`；`data_dir` 由项目配置 `workspace.data_dir` 指定，默认 `data/`。
- 第一版事件流存结果库 SQLite 表，与运行记录同库同事务。
- 事件流文件化归档（预留，第一版不实现）：
  - 触发类型：单次运行超限（写时判定）、结果库总体积超限（存量归档）、批量/长仿真模式（按模式判定）。
  - 阈值参数化，待实测校准。
  - 归档只移动事件流；文件不可变并带校验；读取透明；删除结果时联动清理。

## 8. 还原与查询模型

- **事件层面查询**：按 `(session_id, frame)` 或 `event_type` 过滤读取事件流。
- **状态层面查询**：任意帧值 = 初始快照基线 + 折叠该帧前的状态变化事件（依赖 `before/after` 证据）。
- **高频状态数据**（HP/能量等）：不按帧存数值；事件流本身即稀疏变化记录。
- **性能优化**：跳变表（jump track）物化“最后一次变化”索引，供任意帧状态查询和曲线渲染加速；可重建。

## 9. 模块边界与依赖

- `core/events/`、`core/snapshots/`：生成事实与快照，不负责存储。
- `application/execution/`：订阅事件、组装运行记录、调用写入协议。
- `infrastructure/results_sqlite/`：SQLite 实现（schema、writer、repository、归档预留）。
- `application/services/`：对外读取门面（`ResultsService` 等）。
- `analysis/`：派生层加工（摘要、序列、状态视图、对比），不写库、不直接访问 SQLite。

投影职责归 analysis 读取侧。

## 10. 事件契约要求

- `EventType.name` 冻结：只允许追加，不允许改名或复用。
- `payload.to_dict()` 只增字段、不改语义；破坏性变更走新事件类型。
- 状态变化事件必须携带 `before/after` 或稳定引用证据，保证可还原。
- 事件持久化不存 `source_type` 类名；来源语义由 payload 内稳定引用承担。
- 不冗余存储分类元信息（`record_by_default`、`result_committed` 等）。

## 11. schema 版本与数据演进

- 结果库 schema 版本（库级）与输入 schema 版本（运行级）语义分离。
- 开发阶段（未发布正式版）：不做自动迁移，版本不兼容时由用户显式重建结果库。
- 发布正式版后：设计逐级迁移，迁移前备份、单事务执行；第一版只允许兼容变更（加表、加列、加索引）。

## 12. 与任务系统的关系

- `job_id ↔ session_id` 单向关联：任务侧持有 `session_id`，结果库不存 `job_id`。
- 失败信息分工：结果库只留 `error_code` / `error_message` 摘要；完整堆栈与调度细节归任务系统与日志。

## 13. 后续演进

- 事件流文件化归档（触发条件见第 7 节）。
- 批量扫描：事件直写文件模式、结果与任务关联。
- 检查点快照：仅当“任意帧查询”性能需要时，作为可重建物化，不改变真值层。
- 任务状态持久化：由任务系统独立实现。

## 14. 参考实现

- **gcsim**：聚合统计与单次样本日志分离；种子记录于结果。它依赖重跑是因为不维护跨版本历史，我们因历史保真需求改为存事实。
- **Event Sourcing**（Martin Fowler）：事件日志为官方记录，状态可重建，快照/物化为可丢弃优化。
- **MLflow**：运行元数据入 SQL、大体积 artifact 走文件；`latest_metrics` 为物化查询优化。
- **游戏回放系统**（星际争霸 2 等）：输入 + 种子确定性重放依赖版本锁定，支持“以存事实为主、重跑作为新运行”的结论。
