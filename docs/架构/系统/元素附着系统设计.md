# 元素附着系统设计

> 状态：生效
> 实现覆盖：普通火、水、雷、冰、草附着，水雷与草冰共存，冻元素、燃元素、激元素，逐来源贡献、精确衰减、Reaction 管理型消费、复数状态 Link 和批量原子提交。

最后更新：2026-08-03

## 1. 系统定位

`core/systems/aura/` 是元素附着领域。它唯一拥有可持续 Aura Component、精确元素量、贡献归属、自然衰减、同元素更新和状态 Link 投影。

Aura 负责：

- 保存每个元素交互主体当前合法的 Aura Component 集合。
- 使用精确有理数计算附着、衰减和反应消费。
- 维护逐来源贡献和 Component 当前量投影。
- 执行普通附着、派生 Aura、Link 变更和精确消费计划。
- 提供不可变 View、MutationPlan、提交回执、事实和快照。

Aura 不负责：

- 判断异元素反应是否成立或决定候选顺序。
- 推进元素附着 ICD。
- 计算伤害、Buff、空间实体或 ReactionState。
- 直接读取 Reaction、Damage、Space 或 content 的 Runtime。

Reaction 决定元素交互语义，Aura 校验并执行精确元素量变化。跨领域一致性由元素反应协调器负责。

## 2. 代码组织与依赖

当前目录结构为：

```text
core/systems/aura/
├── __init__.py
├── enums.py
├── models.py
├── profiles.py
└── runtime.py
```

- `enums.py` 保存强度、损耗、衰减策略、结果和衰减模式。
- `profiles.py` 保存普通附着与激元素的精确衰减公式，以及派生施加 Profile Registry。
- `models.py` 保存不可变引用、贡献、Component、Record、请求、结果、计划和快照。
- `runtime.py` 保存 `AuraBatchPlanner`、`AuraRuntime` 和领域错误。

当前没有独立 `AuraStore`。`AuraRuntime` 内置 Record 索引、版本、规范化帧、稳定序列和幂等身份，是 Aura 状态唯一写入口。

Aura 只依赖 `core/elements/` 的中立元素语义和事件事实模型，不依赖其他领域 Runtime、数据库、application 或 content。

## 3. 中立元素语义

`core/elements/` 提供 Aura、ICD、Reaction 和协调器共享的值对象：

- `Element`：可以参与元素交互的火、水、雷、冰、风、岩、草。物理不属于 Element。
- `AuraKind`：当前可持续的火、水、雷、冰、草、冻元素、燃元素和激元素。
- `AuraAmount`：非负精确有理数，稳定序列化为分子、分母和十进制投影。
- `ElementalSubjectRef`：角色、目标或创建物的元素交互主体。
- `ElementalSourceRef`：元素施加者和 Aura 贡献者使用的中立来源。
- `ElementalStateLinkRef`：Aura Component 与 ReactionState 的稳定关系。

`aura_kind_for_element()` 只把可持续普通元素映射为 AuraKind。风和岩不会形成普通持久 Aura；`FROZEN`、`BURNING` 和 `QUICKEN` 只能由 Reaction 的强类型计划创建。

## 4. 精确元素量与衰减 Profile

所有元素量运算使用 `AuraAmount`，不能在领域内部退化为浮点近似。

普通附着的精确公式为：

```text
attached_amount = raw_amount * 4 / 5
duration_seconds = 7 + 5 / 2 * raw_amount
decay_per_second = attached_amount / duration_seconds
```

标准强度表：

| AuraStrength | 原始量 | 附着后量 | 持续帧数 |
| --- | ---: | ---: | ---: |
| `WEAK` | `1 GU` | `4/5 GU` | `570` |
| `MEDIUM` | `3/2 GU` | `6/5 GU` | `645` |
| `STRONG` | `2 GU` | `8/5 GU` | `720` |
| `SUPER_STRONG` | `4 GU` | `16/5 GU` | `1020` |

`AuraApplicationProfile` 冻结一次正元素施加使用的损耗和衰减档案策略。普通标准施加按 AuraStrength 取 Profile；扩散等派生普通施加可以使用已注册的 `REGULAR_FROM_RAW_AMOUNT`，根据精确原始量生成常规衰减档案，不能就近映射到某个标准强度。

激元素使用独立精确档案。设激元素量为 `Q`：

```text
duration_seconds = 6 + 5 * Q
decay_per_frame = Q / (360 + 300 * Q)
```

激元素不应用普通 `20%` 附着损耗。

## 5. 状态模型

Aura 状态结构为：

```text
AuraRuntime
└── AuraTargetRecord
    └── AuraComponent
        └── AuraContribution
```

### 5.1 AuraContribution

一条贡献至少保存：

- `contribution_ref`：稳定贡献身份。
- `contributor_ref`：贡献归属来源。
- `remaining_amount`：当前剩余精确元素量。
- `amount_origin`：当前元素量来源。
- 创建、最近有效施加和最近变化帧。

同一 Component 中，同一个 `contributor_ref` 最多保留一条贡献。重复施加时保留稳定 contribution ref，并在新量严格更大时更新该贡献。

### 5.2 AuraComponent

一个 Component 至少保存 Aura 实例身份、AuraKind、贡献集合、衰减档案、衰减来源、衰减模式、状态 Link 和时间审计。

当前元素量是贡献集合的只读投影：

```text
current_amount = max(contribution.remaining_amount)
```

显示量不能作为独立可写字段。即使最大值没有变化，新增或提高非主导贡献仍是实际状态变化，并推进 Record revision。

### 5.3 AuraTargetRecord

每个 `ElementalSubjectRef` 最多有一个 Record，每种 AuraKind 最多有一个 Component。Record 使用显式合法组合矩阵，不允许调用方任意拼装多 Aura。

当前支持的关键组合包括：

- 单一普通持久 Aura。
- 水与雷共存。
- 草与冰共存。
- 冻元素单独存在，或与一份藏水、藏冰共存。
- 燃元素与至少一个关联的普通草或激元素共存，并允许可选普通火。
- 激元素与当前已实现反应明确允许的普通水、火、草、雷、冰组合。

组合合法性由 Record 构造和 Planner 同时校验，不能使用“组件数量上限”替代明确规则。

### 5.4 贡献观察与审计

`AuraView` 是 Reaction 和协调器可以读取的不可变观察：

```text
AuraView
├── subject_ref
├── revision
└── components

AuraComponentView
├── instance_ref
├── aura_kind
├── current_amount
├── decay_profile
├── state_link_refs
└── contributions

AuraContributionView
├── contribution_ref
├── contributor_ref
└── remaining_amount
```

Reaction 可以读取消费前的贡献明细以冻结参与者或其他强类型证据，但不能获得 Aura Record、Store 或 MutationPlan。参与者快照属于 Reaction occurrence，不回写 Aura，也不改变贡献账本。

`AuraApplicationResult` 和 `AuraTransitionResult` 必须能够审计消费前后实际使用的 Component、贡献、元素量和 revision。至少区分：

- 新增贡献、提高非主导贡献、主导贡献变化和贡献归零；
- `current_amount` 未变化但贡献集合发生变化的情况；
- Component 级元素消费对全部贡献槽产生的前后值；
- Link、衰减模式和 Component 生命周期是否发生变化。

显示量不变不能把上述变化折叠为 `UNCHANGED`。完整 application 历史由交互事实保存，活动 Aura Store 只保存当前贡献真值和必要的状态审计。

## 6. 普通附着与同元素更新

`AuraApplicationRequest` 表达一次普通正元素施加，核心字段包括：

```text
request_id / application_id / impact_ref
frame / order
source_ref / target_ref
element / base_strength
application_coefficient
loss_policy
effective_raw_amount?
decay_profile?
```

规则：

- `application_coefficient` 来自 Aura ICD 决议；系数为零时协调器不得创建 Aura 请求。
- `impact_ref` 关联同一次 Impact 的伤害和元素施加，不承担请求幂等职责。
- 普通施加根据 base strength、系数和损耗策略得到附着量。
- 显式提供 `effective_raw_amount` 时，`decay_profile.raw_amount` 必须完全一致。
- 新 AuraKind 只有在当前 Record 的显式组合矩阵允许时才能加入。

同元素更新分别比较贡献量和 Component 衰减速率：

- 新来源创建独立贡献槽。
- 同来源只有新量严格更大时提高贡献量。
- 新 Profile 衰减速率严格更大时升级 Component 衰减档案和衰减来源。
- 数量与 Profile 都未变化时返回 `UNCHANGED`，但仍更新最近施加帧。

普通同元素更新不会重置已有贡献的创建身份，也不会把多个来源压缩成一个来源。

## 7. 派生 Aura、衰减模式与 Link

`AuraDecayMode` 分为：

| 模式 | 所有者与行为 |
| --- | --- |
| `STANDARD` | AuraRuntime 按 Component 的精确 Profile 自然衰减 |
| `STATE_LINKED` | 生命周期由关联 ReactionState 驱动，AuraRuntime 不执行自然衰减 |
| `REACTION_MANAGED` | 保留自身 Profile，但活动 ReactionState 暂时接管消费 |

当前派生 Aura 规则：

- 冻元素使用 `STATE_LINKED`，恰好携带一条 FrozenState Link，不保存自然衰减 Profile。
- 燃元素使用 `STATE_LINKED`，恰好携带一条 BurningState Link，不自然衰减。
- 普通草和激元素进入燃烧时使用 `REACTION_MANAGED`，分别按 `1/150 GU/frame` 消费。
- 激元素正常使用 `STANDARD` 和自身精确 Profile，至少携带 QuickenState Link；进入燃烧后可以同时携带 BurningState Link。

`AuraStateLinkMutationRequest` 只允许显式增加、删除 Link 或切换衰减模式。重复添加、不存在的删除和同一请求中同时增删同一 Link 都会失败。

派生 Aura 的精确建立、覆盖和终止规则见：

- [冻结反应设计](./元素反应/反应/冻结反应设计.md)
- [燃烧反应设计](./元素反应/反应/燃烧反应设计.md)
- [激化反应设计](./元素反应/反应/激化反应设计.md)

## 8. 时间模型

`AuraRuntime.update_frame()` 只接受不早于 `normalized_through_frame` 的帧。重复规范化同一帧无副作用，帧回退直接失败。

标准衰减对每条贡献扣除相同精确量：

```text
decay = decay_profile.decay_for_frames(elapsed_frames)
remaining = max(0, remaining - decay)
```

归零贡献从集合移除；贡献集合为空时删除 Component；Record 不再有 Component 时删除整个 Record。`STATE_LINKED` 和 `REACTION_MANAGED` 不由普通 `update_frame()` 衰减。

自然衰减按 elapsed frames 一次计算，因此逐帧推进和跨帧规范化必须得到相同结果。Component 归零时只发布一次 `AURA_DEPLETED`。

## 9. Planner、计划与提交

生产元素流程使用 `AuraBatchPlanner`：

```text
AuraRuntime.begin_batch(frame, batch_id)
-> Planner 在工作副本上 apply / consume / mutate links
-> Planner.seal()
-> AuraMutationPlan
-> AuraRuntime.validate(plan)
-> AuraRuntime.commit_prevalidated(plan)
```

Planner 捕获 batch 开始时的 Store version、稳定实例序列和贡献序列。后一个请求读取前一个请求形成的虚拟状态，但真实 Runtime 在 commit 前保持不变。

`AuraMutationPlan` 保存完整 Record 后值投影、删除主体、应用结果、精确消费结果、request/interaction identity 和稳定序列后值。提交使用完整投影替换 Runtime 内状态。

校验至少拒绝：

- stale Store version 或错误计划帧。
- 重复 operation、request、interaction 或 batch order。
- Planner seal 后继续写入。
- 事件事实发布期间同步写入。
- 非法 Aura 组合、悬空 Link 或不一致派生 Aura。

`AuraRuntime.apply()` 只是单请求便利入口，不建立第二套写逻辑，也不自行发布生产元素交互事实。

## 10. 与 Reaction 和协调器的边界

Reaction 负责决定：

- 候选、方向和决策顺序。
- 前后手消费语义。
- Component 保留、移除、共存或派生要求。
- 当前 Impact 调整、后续伤害、状态或实体 Effect。

Aura 负责：

- 校验 Reaction 声明的元素变化是否合法。
- 对所有贡献执行精确消费。
- 保存最终 Component、贡献、衰减和 Link 真值。
- 返回 `AuraApplicationResult` 与 `AuraTransitionResult`。

Reaction 不接收 Aura Record、MutationPlan 或 Runtime。Aura 不判断 reaction key，也不携带伤害倍率、精通公式或其他领域请求。

涉及 Aura 与 ReactionState Link 的建立、刷新和移除时，协调器必须在第一次写入前校验两侧完整投影，并在无回调阶段提交。任何一侧失败都不能留下悬空 Link。

完整流程见[元素反应判定与执行流程](./元素反应/判定与执行流程.md)和[元素反应协调器设计](../协调/元素反应协调器设计.md)。

## 11. 事实、快照与错误

Aura 领域事实包括：

- `AURA_APPLIED`：普通附着或同元素更新已经提交。
- `AURA_INTERACTION_RESOLVED`：Reaction 驱动的精确元素变化已经提交。
- `AURA_DEPLETED`：自然衰减使 Component 归零。

生产交互中的应用与消费事实由协调器根据提交回执发布；自然归零由 AuraRuntime 在帧更新后发布。事实发布期间启用写保护。

`AuraSnapshot` 保存规范化帧和稳定排序的完整 Record 树。主体按 kind 和 id 排序，Component、贡献和 Link 也使用稳定顺序。Snapshot 是只读投影，不拥有第二份状态。

非法输入、非法组合、精确档案不一致、帧回退、stale plan、重复身份和事实重入都必须显式失败。批量失败时 Runtime、版本和稳定序列保持不变。

## 12. 当前边界

当前正式实现不覆盖：

- 环境附着、自身附着和元素盾的专用持续时间、刷新与清理规则。
- 未经资料确认的派生 Aura 或特殊共存组合。
- Aura 结果库投影和完整 JSON 快照 schema。
- 全部角色、敌人和环境内容数据。
- 角色专属的月反应参与者、资源和伤害能力；这些能力由对应 Reaction、Damage 和 content 文档定义。

这些是内容与契约覆盖边界，不改变 Aura 当前的状态所有权和事务规则。新增机制必须先确认资料、合法组合、衰减所有者、Link 不变量和 golden case。
