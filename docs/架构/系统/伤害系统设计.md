# 伤害系统设计

> 状态：正式。
> 本文描述伤害系统的稳定架构边界、领域模型、完整公式结构与审计设计；稳定 key、数据结构、
> 数值公式、序列化与错误码以[伤害系统契约](../../契约/伤害系统契约.md)为准。
> 最后更新：2026-09-01

## 1. 设计目标

伤害系统负责：

1. 接收已经确定来源与目标的类型化伤害请求（`DamageImpactSpec` -> 逐目标 `DamageRequest`）。
2. 以主攻击标签经 `DamageProfileRegistry` 选择 `DamageProfile`，再由 `DamageProfile.formula_key` 选择完整公式。
3. 查询结算帧的来源属性和目标属性。
4. 收集纯查询、无副作用的伤害修饰项。
5. 按稳定完整公式结构计算伤害（通用公式含可选增幅/激化区，以及剧变、月曜）。
6. 输出不可变、可审计的 `DamageResult`，作为事实交给事件、结果记录和后续角色承伤接入层。

伤害系统不负责：

- 元素附着、ICD 与反应判定；只接收元素反应协调流程已经确认的强类型反应输入。
- 动作索敌与空间 AOE 目标解析；只按已经冻结的 `target_refs` 顺序逐目标结算。
- 目标当前生命、扣血、击败或死亡；角色目标由[角色受伤协调器](../协调/角色受伤协调器设计.md)适配为 `CharacterIncomingDamage` 后提交生命。
- 护盾吸收、减伤分摊或受击反馈。
- 治疗和能量。
- 随机种子配置与生产环境随机暴击策略；暴击决策只通过注入式 `CriticalDecisionProvider` 进入。
- UI 显示舍入和结果数据库 schema 扩展。
- 原激化判定、草/雷消耗、反应准入等 Reaction 领域事实。

## 2. 架构原则

### 2.1 伤害请求、属性和运行态分离

- Damage Impact 描述一次范围影响及其攻击、元素和 AOE 语义；伤害系统只接收目标已经解析后的单目标公式请求。
- `DamageRequest` 描述一次伤害的结算契约，不保存最终数值。
- `AttributeResolver` 是属性真值入口，伤害系统不维护第二份角色面板。
- `DamageModifierProvider` 只返回结构化修饰项，不直接修改请求、属性或世界状态。
- `DamageResult` 只描述已经完成的数值结算，不直接扣减生命。

### 2.2 默认实时查询

伤害在 `ImpactRequest` 被结算的当前帧查询属性。动作层的 `snapshot_on_emit` 当前只表示目标选择快照，不表示属性快照；伤害属性快照必须在未来通过独立、显式的伤害快照契约加入，不能复用目标选择字段产生隐式行为（见 15.5）。

### 2.3 确定性优先

- 所有加法使用 `math.fsum`。
- 修饰项按稳定 key 排序。
- 结算器不使用全局随机数。
- 结算器不进行显示舍入。
- 相同输入、相同属性查询结果、相同暴击决策必须产生完全一致的 `DamageResult`。

### 2.4 事件是结果事实，不是可变计算入口

伤害修饰通过 `DamageModifierProvider` 查询；动态机制实例的创建、刷新和过期由对应领域 Runtime 与 Store 管理；伤害结算完成后发布不可变事实事件。handler 不在事件调用栈内递归触发并修改同一次伤害结算。

不新增可变 `BEFORE_DAMAGE` / `BEFORE_CALCULATE` 事件作为修饰入口。如果未来确实需要拦截伤害请求，应设计独立 `INTERCEPT` 阶段和强类型决策结果，不能把共享 context 暴露给 handler 任意修改。

## 3. 模块边界

```text
core/systems/damage/
├── __init__.py
├── enums.py             # LunarReactionDamageMode、DamageReactionCapability、DamageModifierStage、CritOutcome、DamageModifierStackingPolicy
├── keys.py              # 完整公式稳定选择键（damage_formula.*）
├── models.py            # 输入、输出与审计值对象；各类反应强类型输入
├── profiles.py          # DamageProfileRegistry（主攻击标签 -> DamageProfile）
├── tags.py              # 公共主攻击标签常量
├── modifiers.py         # DamageModifierTerm、provider 协议、索引与 stacking group
├── policies.py          # 倍率区、增伤区、暴击区、反应区、防御区、抗性区公式族与暴击决策 provider
├── formulas.py          # DamageFormula 协议、DamageFormulaRegistry 与四种完整公式
├── level_multipliers.py # 剧变等级系数表与查询入口
├── resolver.py          # DamageResolutionSession、DamageResolver
├── handler.py           # Damage Impact 到逐目标 DamageRequest/Result 的请求处理入口
└── errors.py            # 结构化伤害错误
```

职责约束：

- `core/systems/damage/` 可以依赖 `core/attributes/` 和少量 core 值对象。
- `core/systems/damage/` 不能依赖 `assets`、`content`、`application`、`infrastructure` 或 UI。
- `content/` 提供 Damage Impact 工厂、DamageProfile 和修饰 provider，不实现全局伤害流水线。
- `application/assembly/` 负责收集 provider、构造索引并把 `DamageRequestHandler` 注入 `ImpactRequestDispatcher`；`application/assembly/damage_profiles.py` 是 DamageProfile 默认注册的唯一汇总入口。
- `infrastructure/results_sqlite/` 只持久化结果，不参与计算。
- 分析层可以消费审计结果做伤害构成和乘区分析，不重新计算真值。

## 4. 运行时流程

```text
Action / Reaction / 周期状态 / 空间实体
-> 产生 DamageImpactSpec（ImpactKind.DAMAGE）
-> Impact 使用 Action 索敌结果确定方向
-> Space 按 DamageImpactSpec.area 解析并冻结实际目标
-> 每个目标形成 TargetImpact
-> ICD、Aura 与 Reaction 处理元素、元素量、目标 Aura 和打击类型
-> DamageRequestHandler 以主攻击标签从 DamageProfileRegistry 取得 DamageProfile
-> 为每个目标构造单目标 DamageRequest
-> DamageResolver 创建一次 DamageResolutionSession
-> 收集 DamageModifierTerm
-> 按 DamageRequest.formula_key 从 DamageFormulaRegistry 选择完整公式
-> DamageFormula 编排对应计算区
-> 生成 DamageResult
-> 记录 DamageResolutionRecord
-> 发布 DAMAGE_RESOLVED 事实事件
-> 角色目标由角色受伤协调器适配为 CharacterIncomingDamage，经 HealthRuntime 产生生命变化
```

一次 Damage Impact 命中几个目标，就按稳定 `target_refs` 顺序产生几份独立 `DamageRequest`。每个目标独立查询抗性、独立生成结果和审计，不共享可变计算上下文。

Reaction 新产生的伤害只负责创建新的 Damage Impact，并在同帧下一 settlement round 进入上述流程；Reaction 不直接构造 `DamageRequest`，Damage 也不区分 Impact 来自 Action 还是 Reaction。

## 5. 领域模型总览

本节只描述模型职责与设计动机；字段、稳定值、校验规则与组合约束见[伤害系统契约](../../契约/伤害系统契约.md)第 3–4 节。

### 5.1 Element

元素语义统一使用 `core.elements.Element`，伤害领域不维护平行枚举；物理是伤害侧合法元素，但不参与元素交互。稳定值见契约 3.3。

### 5.2 DamageScalingTerm

`component_key` + `attribute_key` + `coefficient` 表达一个倍率分量；多属性缩放通过多个 term 表达，聚合为 `fsum(属性值 × coefficient)`。

### 5.3 DamageProfile 与 DamageProfileRegistry

DamageProfile 把稳定主攻击标签映射到完整公式和请求约束。设计要点：

- 主攻击标签是攻击身份和 Profile 查找入口；附加标签不能替代主标签，也不能依赖集合遍历顺序选择公式。
- 未注册的非 `reaction.` 命名空间主攻击标签默认使用通用公式（原神直伤统一走通用公式）；`reaction.` 前缀标签未注册显式映射时必须报错，防止反应标签笔误变成通用伤害。
- 默认注册统一由 `application/assembly/damage_profiles.py` 汇总；内容直伤不需要注册 Profile。
- 激化不新增 capability、独立公式或合成标签：资格由雷/草元素、正倍率证据和强类型 `CatalyzeReactionInput` 共同决定，公式始终是通用公式。

### 5.4 DamageImpactSpec

一次 Damage Impact 完整声明攻击身份、元素、倍率、暴击资格、打击证据、元素施加、ICD 绑定、AOE 与显示名。AOE、元素量和 ICD 字段在构造 `DamageRequest` 前已经由 Impact、ICD、Aura 与 Reaction 消费；`DamageRequest` 通过 `impact_key` 关联完整 Impact 审计。

### 5.5 DamageRequest

进入结算器前的单目标类型化请求：来源、目标、等级、元素、倍率、暴击资格与反应输入已解析完成，构造后不可变。角色作为受方只允许绽放系列/月绽放攻击标签，由模型级白名单校验。

### 5.6 DamageQuery

`DamageRequest` + 来源/目标属性查询 context。属性 context 携带标签集合、Impact 来源引用和对方主体引用，使 provider 可以声明“对特定目标增伤”或“来自特定来源时减抗”等条件。

### 5.7 DamageResult

不可变、可独立验证的结算结果与审计：摘要字段、分区审计（增伤/暴击/防御/抗性/反应）、组件结果、槽位账单（面板读取 + 效果词条）、属性 trace 与 trace level。`official_damage` 是正式公式伤害，`final_damage = official_damage * debug_multiplier`。

## 6. 伤害修饰设计

### 6.1 槽位账单模型

伤害计算采用“选公式 → 按槽位填 `DamageModifierTerm` → 计算”的统一模型：

```text
公式槽位 = 面板读取贡献（panel_*）+ 效果修饰贡献（其余 stage）
```

- 公式从属性系统读取面板值后，在读取点把最终值物化为面板读取词条，作为对应槽位的基础贡献；内容效果词条作为同一槽位的修饰贡献。
- 属性系统保持唯一真值，其内部 `ModifierTerm` 不进入伤害系统。
- 面板读取词条不是 provider 写入的修饰，不参与 stacking 选择，也不进入 `rejected_terms`。
- 通用与激化公式产出面板账单；剧变与月曜公式维持不接受普通伤害修饰的边界，不产出面板账单。

稳定 stage 清单、`DamageModifierTerm` 字段与 `panel_read()` 生成规则见契约 3.2、3.4 与 5.1。

### 6.2 provider 与生命周期

`DamageModifierProvider` 是无副作用查询入口，显式声明可读属性与可写阶段；`DamageResolutionSession` 只向 provider 暴露声明过的属性读取。静态效果在组装阶段直接注册 provider；BuffRuntime 等领域运行时中的活动实例未来向伤害索引暴露同一查询接口。两者生命周期来源不同，但查询契约相同。

### 6.3 stacking 与约束

`DamageModifierIndex` 按稳定 key 注册 stacking group，收集后在同一组内按 `highest` / `lowest` 选择一个生效项，其余进入 `rejected_terms`。引用未注册 group 或组内 stage 不一致时抛出结构化错误。

## 7. 完整公式架构

### 7.1 分层与公式选择

```text
DamageImpactSpec.main_attack_tag
-> DamageProfileRegistry
-> DamageProfile.formula_key
-> DamageFormulaRegistry
-> 对应 DamageFormula
-> DamageFormula 编排所需公式族
-> 生成 DamageResult
```

- 主攻击标签负责确定攻击身份并查找 Profile；Profile 负责选择完整公式和请求约束；完整公式负责乘区组成、计算顺序与审计结果；公式族负责可被多个完整公式复用的局部计算。
- 公式选择使用稳定主攻击标签与 Profile 映射，不根据元素、附加标签或最终属性值临时猜测。
- 未注册的非反应主攻击标签默认通用公式；`reaction.` 前缀标签未注册、或 Profile 指向未注册公式时必须报错。

当前注册三种完整公式，稳定键见契约 3.1：

```text
damage_formula.general                 -> GeneralDamageFormula
damage_formula.transformative_reaction -> TransformativeReactionDamageFormula
damage_formula.lunar_reaction          -> LunarReactionDamageFormula
```

### 7.2 通用伤害公式

```text
倍率区 × 增伤区 × 暴击区 × 反应区 × 防御区 × 抗性区
```

- 普通非反应伤害、增幅反应和激化参与的伤害都由 Profile 选择通用公式；无反应时反应区使用单位结果，增幅反应由反应区提供倍率，激化由激化附加区提供基础伤害增加值，不可暴击只改变暴击区输入或结果。
- 倍率区把“属性值”作为槽位基础贡献：`component_damage = 面板属性值 × 最终倍率`；原始倍率、百分比放大、倍率加值与基础伤害固定加值按各自 stage 汇总。
- 请求自带、角色、武器、圣遗物或其他机制提供的普通基础伤害固定加值使用同一种数据结构和聚合规则，来源差异只保留在 term 来源引用与审计信息中。
- 暴击结果由注入式 `CriticalDecisionProvider` 提供，结算器自己不调用随机数。
- 防御区与抗性区是独立 policy；抗性区按分段函数处理有效抗性，减抗也可以继续通过目标 `resistance.*` 运行时属性 modifier 实现，两条路径合并后进入同一分段函数，不维护独立的 `resistance_shred` 状态。

精确公式、稳定系数与边界规则见契约 6.1。

### 7.3 激化附加区

超激化和蔓激化不选择独立公式，而是作为通用公式的可选附加区：资格由关联伤害元素、正倍率证据与强类型 `CatalyzeReactionInput` 共同决定，不依赖攻击标签或独立 Profile。激化附加值是独立公式区，不允许通过通用 `DamageModifierTerm` 伪造；结果作为命名来源进入 `base_damage_additions`。

精确公式与稳定倍率见契约 6.2，反应侧完整设计见[激化反应设计](./元素反应/反应/激化反应设计.md)。

### 7.4 剧变反应公式

剧变使用独立公式（系数区 × 剧变提升区 × 抗性区），等级系数、元素精通与精通加成在 occurrence 时冻结，Damage 不查询来源属性；防御策略固定为 `approximate_unity`，不接入普通倍率、增伤、暴击或防御区，也不接受普通 Damage modifier stage。扩散 Profile 可声明 `SECONDARY_AMPLIFYING` 使用捕获式二次增幅。

精确公式见契约 6.3，反应侧数值见[剧变反应伤害契约](../../契约/元素反应/剧变反应伤害契约.md)。

### 7.5 月反应公式

月曜使用独立 `lunar_reaction` 公式：`CHARACTER_DIRECT` 只有一个角色参与者，`REACTION_COMPOSITE` 多个参与者各自完成完整组分伤害后按稳定权重聚合。组分独立读取属性、元素精通、暴击与目标抗性；等级基数表、精通系数和权重使用已确认生产数值，可显式注入替代用于测试。

精确公式、等级基数表与权重见契约 6.4，反应侧设计见[元素反应架构文档索引](./元素反应/文档索引.md)。

### 7.6 调试专用区

`final_damage = official_damage × debug_multiplier`。调试区不属于正式公式，也不属于 content 可用的普通 modifier stage；只有测试或显式调试入口可以注入非 `1.0` 的值。审计必须区分正式公式结果与应用调试区后的最终输出。

### 7.7 Profile、公式与其他维度

伤害元素、是否暴击、目标选择方式、倍率来源、场上/后台等维度都不直接作为公式选择键。普通攻击、重击、下落攻击、战技、爆发和具体反应等主攻击标签会选择 Profile，但不是公式实现本身；多个主标签可以映射到同一个公式。坠落、固定伤害等特殊伤害是否需要新增类型，留待有可信来源和验收案例后评审，不增加无明确公式语义的通用 `SPECIAL` 类型。

## 8. 事件边界

伤害相关事件：

| EventType | Category | 语义 |
| --- | --- | --- |
| `DAMAGE_RESOLVED` | `FACT` | 一次伤害数值已经完成结算，但尚不代表生命已扣减 |
| `DAMAGE_APPLIED` | `FACT` | 正伤害已经以角色为目标完成护盾与血量提交，不要求血量实际减少 |

`DAMAGE_RESOLVED` 由伤害系统在结算完成后发布，`DAMAGE_APPLIED` 由角色受伤协调器在护盾与血量提交后发布；两者都默认记录。

规则：

- `DAMAGE_RESOLVED` 不可取消、payload 不可变、默认记录、可以驱动后续机制。payload 持有不可变 `DamageResult`，其中 `result` 保留摘要，`audit` 保存完整伤害公式审计。
- `DAMAGE_APPLIED` 在 `CharacterIncomingDamage.amount > 0` 且目标是角色时发布，保存 `CharacterDamageTakenRecord`；完全吸收时仍发布，但不会产生 `CHARACTER_HEALTH_CHANGED`，零伤害不发布。
- 不新增可变 `BEFORE_DAMAGE` / `BEFORE_CALCULATE` 事件作为修饰入口。

事件类型的最终加入需要同步[事件类型](../事件系统/事件类型.md)；payload 与序列化形状见契约第 9 节。

## 9. 审计设计

`DamageResult` 本身自洽且可独立验证，不依赖外部数据库回填。它保存：

- 每个 scaling component 的属性值、原始倍率、修饰后倍率和贡献值。
- 元素增伤属性解析结果与增伤乘数。
- 暴击率、暴击伤害和暴击决策来源。
- 防御、抗性 policy 的输入和输出。
- 槽位账单：面板读取词条与已应用/被拒绝的伤害修饰项。
- 最终乘区的稳定应用顺序。
- 关联的属性 resolution trace。

trace level 复用属性系统的 `none`、`applied`、`full` 语义：`none` 只保留最终乘区和值；`applied` 保留已应用 term 和必要属性 trace；`full` 额外保留被拒绝 term、依赖链和 policy 中间值。trace level 只能改变审计数据量，不能改变数值结果。

序列化字段与存储载荷见契约第 9 节与[结果库契约](../../契约/结果库契约.md)第 5.3 节。

## 10. 与动态机制领域的关系

静态 provider 和测试 provider 已足以验证公式与链路；动态 provider 后续由对应领域 Store 提供只读 view：

```text
BuffStore / 其他领域 Store
-> 当前帧活动完整记录只读 view
-> 暴露 DamageModifierProvider / Attribute ModifierProvider
-> DamageResolver 在当前帧纯查询
```

边界：

- 伤害查询期间不能添加、刷新、移除或过期领域实例。
- 对应领域实例生命周期决定 provider 是否活动。
- provider 不保存独立持续时间。
- 同一次伤害观察到的机制实例集合必须在 resolution session 内保持稳定。

## 11. application 与 content 接入

### 11.1 content contribution

`ContentUnit` 提供类型化入口 `damage_modifier_providers`；内容包通过 `profiles.py` 声明 DamageProfile，通过该字段注册伤害修饰 provider。属性 provider 与伤害 provider 使用各自的类型化字段，新伤害实现不应根据 `scope` 字符串和自由 `object` query 猜测协议。

### 11.2 impact factory

content impact factory 负责把技能倍率引用、攻击身份、元素应用数据和动作上下文展开为 Damage Impact，例如 `impact_key -> DamageImpactSpec -> Space AOE 目标解析 -> 逐目标 DamageRequest`。impact factory 不负责查询最终攻击力、计算防御或抗性、决定 Buff 是否生效、直接生成最终伤害值、扣减目标生命或选择公式。

### 11.3 组装校验

以下错误应尽量在组装阶段暴露，不能把可提前发现的 content 错误延迟到战斗中：

- 未注册 damage handler 或 provider。
- scaling ref 不存在或倍率 payload 格式错误。
- 不支持的元素、属性 key、主攻击标签、附加攻击标签、打击类型或远近类型。
- `reaction.` 标签缺少显式映射、Profile 引用了未注册公式，或同一主标签重复注册；未注册的非反应标签默认通用公式。
- provider 声明了非法属性读取或伤害阶段写入。
- 重复 provider key 或非法 stacking group。

动态运行时请求仍需执行模型级校验。完整装配契约见[伤害系统契约](../../契约/伤害系统契约.md)第 11 节。

## 12. 错误模型

伤害系统使用结构化错误表达模型、公式、provider、暴击决策与结算失败边界；完整错误表与稳定 code 见[伤害系统契约](../../契约/伤害系统契约.md)第 10 节。application 组装层将资产和 content payload 错误转换为现有 assembly 错误或专用伤害装配错误。

## 13. 测试策略

### 13.1 单元测试

`tests/unit/core/systems/damage/` 至少覆盖：

- 单属性缩放和多属性缩放。
- component 倍率百分比修饰与倍率加值。
- 固定基础伤害加值。
- 元素增伤与伤害专用增伤的聚合。
- 不可暴击、固定暴击和固定不暴击。
- 同等级无修饰防御区。
- 减防与无视防御的独立输入。
- 负抗性、普通抗性、`0.75` 边界和高抗性。
- 多个 final multiplier 的稳定顺序。
- stacking group 的 applied/rejected term。
- 面板读取词条进入槽位账单且不改变结算数值。
- bool、NaN、无穷、空 key、非法主体和未知元素。
- trace level 不改变最终数值。

### 13.2 集成测试

至少跑通：

```text
测试角色 Action
-> ActionImpactPoint
-> DamageImpactSpec
-> Space AOE 目标解析
-> 目标级 ElementalImpactRequest
-> DamageProfile
-> DamageRequest
-> DamageResult
-> DAMAGE_RESOLVED
```

多目标案例必须验证实际 AOE 命中几个目标就产生几份 DamageRequest，结果顺序稳定且每个目标独立读取抗性。Reaction 生成的 Damage Impact 必须复用同一链路。

### 13.3 浮点与 golden

浮点测试优先使用明确的绝对或相对容差；core 不为了让断言通过而提前舍入。直接伤害回归 golden case 的来源与验收基线仍待正式契约来源建立（见 15.6）。

## 14. 测试探针与正式内容边界

`test_a` / `test_b`（`content/test/characters/reaction_probe`）是开发期测试内容，其攻击标签走默认通用公式，不再注册显式 DamageProfile。测试探针不代表真实角色机制完成；正式内容按“主攻击标签 -> 默认通用 / 显式反应映射”链路工作。

## 15. 未决与后续

> 状态：未决。以下事项不作为当前生产真值，完成对应契约或迁移后同步更新本文。

1. **`formula_key` 与默认通用兜底已落地**：`DamageProfile` 不再持有 `profile_key`，公式键为 `damage_formula.*` 字符串常量；未注册的非反应标签默认通用公式，`reaction.` 标签未注册报错。后续如需新增公式结构，只需扩展键常量与公式注册表。
2. **自由 `params.damage` 兼容入口已移除**：请求统一走 `DamageImpactSpec`，不再保留双入口。
3. **`DamageRequest.tags` 主/附加标签合并**：Impact 层已区分主攻击标签与附加攻击标签，request 层当前合并为单一 `tags`；恢复独立字段后再明确 request 层主次语义。
4. **`strike_type` / `range_type` 审计边界**：当前由 Impact 与 Reaction 消费，尚未复制到单目标请求与 `DAMAGE_RESOLVED` 审计；如需进入审计需显式增加字段。
5. **伤害属性快照契约**：当前默认实时查询；独立、显式的伤害属性快照尚未设计，不能复用目标选择快照字段。
6. **直接伤害 golden case**：旧项目迁移基线因来源不满足 golden 可信要求已删除；直接伤害回归待正式契约来源重新建立。
8. **随机暴击**：生产环境带种子随机 `CriticalDecisionProvider` 与回放契约尚未确认；当前仅注入式固定决策。
9. **目标生命**：当前角色对场景目标伤害以 `DAMAGE_RESOLVED` 结束，不作用于目标生命。
