# 冷却系统设计

> 状态：正式规范。
> 本文说明 `core/systems/cooldown/` 冷却领域的结构设计：适用范围、核心结论、模块边界、状态所有权与跨系统协作。
> 最后更新：2026-09-05。

稳定模型字段、时长解析规则、查询与写入语义、错误码、事实与快照见[冷却系统契约](../../契约/冷却系统契约.md)，本文不重复维护。

## 1. 定位与范围

冷却领域负责角色元素战技与元素爆发的冷却次数状态、串行恢复链、时长解析、条件查询、缩减、重置、事实与快照。

冷却领域不负责：

- 判断技能何时发生：外部在确定帧提交 `StartCooldownRequest`，Runtime 校验并消费一次次数。
- 判断技能是否可以释放：冷却条件只回答“指定冷却键的 CD 条件是否满足”，公共条件组合由角色能力条件协调器承担。
- 计算动态基础时长的业务公式：动态时长由调用方在请求前确定并提交。
- 状态效果自身触发冷却、武器 / 圣遗物被动触发冷却、元素附着 ICD、元素反应 ICD、协同攻击间隔、产球间隔及其他效果内部计时。

## 2. 核心结论

1. `CooldownStore` 是冷却状态的唯一所有者，`CooldownRuntime` 是唯一业务写入口。
2. 冷却真值使用整数帧与绝对 `ready_frame`，不逐帧递减浮点秒数。
3. 单次与多充能使用同一串行恢复模型：同一时刻只有一个活动恢复计时，其余已消费次数排队。
4. 固定 CD 从 `CooldownDefinition` 读取；动态基础 CD 由请求显式提供。
5. 时长 modifier term 在恢复链从空变为非空时解析并快照；恢复链未清空时，后续排队次数沿用同一 interval。
6. 百分比时长修正、固定减秒、重置活动计时、直接恢复次数和临时无视 CD 是不同语义，不合并为万能写接口。
7. 所有写入采用 prepare / commit：提交前校验 Store revision 与完整前值，提交后生成不可变领域事实。
8. 冷却领域不 import 或查询其他领域 Runtime / Store，不通过全局上下文寻找外部状态。

## 3. 资料与可信度

通用建模方向与多充能行为参考 KQM 冷却资料及固定快照；动态、离散基础 CD 参考达达利亚等角色页面证据；本地原始数据（Project Amber / Yatta）只用于确认基础 CD 字段与样本值，不作为冷却领域契约真值。具体角色接入前仍需按[原神游戏机制实现规范](../../工程/原神游戏机制实现规范.md)建立当前版本 golden case。

实测建模结论：

- 多充能技能使用串行恢复，而不是每个次数独立并行恢复。
- 多充能技能在第一项进入恢复链时快照 CDR；链持续存在时后续恢复沿用该快照。
- 祭礼类重置对多充能技能作用于当前活动计时，不一次恢复全部排队次数。
- 部分技能的基础 CD 是外部状态决定的离散值，冷却系统不能只保存一个固定资产秒数。
- 不同来源的百分比调整可能引用不同中间阶段，因此 resolver 必须使用有序、可审计的 term，而不是把百分比全部相加。

## 4. 模块边界

```text
src/genshin_sim/core/systems/cooldown/
├── __init__.py
├── enums.py         # 领域稳定枚举
├── errors.py        # 结构化错误
├── models.py        # 身份、definition、record、请求、计划、结果、事实模型
├── policies.py      # 时长 term 阶段与操作策略
├── resolver.py      # 基础时长与 term 解析
├── store.py         # definition registry、record、revision 与原子提交
├── runtime.py       # 查询、规范化、prepare/commit 与 mutation 入口
├── snapshots.py     # 稳定运行时快照
└── ports.py         # CooldownDurationTermPort（内容侧 term 通道）
```

允许依赖：

- Python 标准库。
- `core/` 中已经确认的中立 JSON 值、帧值与 source context 值对象；若无合适中立模型，冷却领域先定义自己的窄类型。

禁止依赖：

- `core/actions`、`core/coordination`。
- 另一个 `core/systems/<domain>` 的 Runtime、Store 或具体模型。
- `content`、`assets`、`application`、`infrastructure`、`ui` 或 `cli`。
- `SimulationContext.get_system()` 或其他服务定位方式。

冷却系统不提供 callback、事件监听器、通用 hook registry 或外部对象引用。

## 5. 状态所有权

`CooldownStore` 直接拥有每个冷却键的完整 `CooldownRecord`：可用次数、活动恢复与排队次数之和恒等于 `max_charges`。`CooldownRuntime` 是唯一业务写入口，提供：

- 帧规范化（按 ready frame 自然恢复）。
- 条件查询（`CooldownConditionReadPort`）。
- 开始冷却、固定减秒、重置当前活动计时。
- 单键与多键批量 mutation 的 prepare / commit。

`remaining_frames` 是查询投影，不进入 Store 状态。外部只能获得不可变视图、条件结果与类型化请求入口，不能直接修改 record。

## 6. 时长解析

冷却时长由 `CooldownDurationResolver` 解析：固定模式从 definition 读取，请求提供模式使用请求的基础时长，随后按固定阶段应用有序 `CooldownDurationTerm`。不同来源的百分比修正可能引用不同已完成阶段，因此 term 按阶段与稳定顺序逐步计算并保留每阶段审计；最终结果使用整数 / Decimal 运算并向上取整。

内容侧通过 `ContentUnit.cooldown_duration_terms` 按 `CooldownKey` 声明 term，编译期绑定到定时动作，动作在冷却开始帧原样提交。

## 7. 帧语义与确定性

- 活动恢复区间为半开区间：`started_frame <= frame < ready_frame`。
- Runtime 维护 `normalized_through_frame`：查询与写入只接受已规范化到请求帧的状态；帧回退报错，查询不隐式推进时间。
- 自然恢复按实际 ready frame 逐点产生事实；跨多个 interval 的一次规范化不会把事实伪装成查询帧。
- definition、record、batch item 与 fact 使用稳定排序，不依赖 dict / set / 对象地址 / 注册顺序。
- prepare / commit 期间设置重入保护；领域事实只是数据，不在 Runtime 内同步执行外部 handler。

## 8. 跨系统协作

- 冷却与标准元素能量的公共条件组合由 `CharacterAbilityConditionCoordinator` 只读组合，协调器只能消费 `CooldownConditionResult`，不能进入本系统读取 Store 或重复计算。
- 冷却写请求由动作在注册的冷却开始帧提交：`TimedActionSpec.cooldown_start_frame` + `cooldown_ability_key`，`TimedImpactAction` 在指定帧提交 `StartCooldownRequest`。
- 角色专属状态与私有资源仍由 content 判断；动作锁与中断仍由 `ActionManager` 判断。
- 冷却 Runtime 在整帧中先于 `ActionManager` 规范化，保证同帧动作查询看到已恢复状态。

## 9. 事实、事件与快照

冷却领域事实描述已提交状态（开始、恢复、缩减、重置、链完成），由 Runtime 返回；经 `COOLDOWN_CHANGED` 事件发布，载荷包含事实字段与前后 `CooldownRecordSnapshot`。快照保存规范化帧、稳定排序的完整记录视图，不保存 resolver、provider 或调用方对象。载荷与快照字段见[冷却系统契约](../../契约/冷却系统契约.md)。

## 10. 暂不泛化

真实机制与 golden 出现前，不增加直接恢复指定次数、临时免费消费或无视 CD、暂停 / 加速 / 倒放、运行时修改 `max_charges`、复制 / 交换 key 的剩余 CD，以及任意调用方直接 mutation。

## 11. 禁止的简化

- 不把 CD 做成 `dict[action_key, float_seconds_left]`。
- 不每帧对所有记录执行 `remaining -= 1 / fps`。
- 不用显示名称作为 key。
- 不把多个 charge 建模为并行计时器。
- 不在恢复链中途重新解析 interval。
- 不把 reset 解释为填满全部 charge。
- 不把 fixed reduction 溢出到下一排队项。
- 不让查询隐式推进时间或发布事实。
- 不用 callback 或全局 service locator 获取外部状态。
- 不提供调用方可直接覆盖 record 的 setter。
- 不把效果内部 CD、ICD、协同攻击间隔或产球间隔塞进本 Store。
- 不在冷却领域内部实现 Action、Energy、Buff、Impact、Event 或 coordination 逻辑。
