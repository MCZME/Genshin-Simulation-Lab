# 事件系统设计

> 状态：已定案。
> 本文档描述项目事件系统的职责、边界、运行模型和扩展规则。具体事件清单见：[事件类型](./事件类型.md)。

最后更新：2026-07-06

## 1. 定位

事件系统位于 `core/events/`，是仿真核心内部的运行时通信、观察和记录入口。

它负责：

- 表达仿真过程中发生的关键节点。
- 为机制扩展提供明确的拦截点。
- 向快照、结果记录和复盘分析提供结构化事件数据。
- 支持系统、实体、效果等运行时对象订阅事件并响应。

它不负责：

- 持久化事件到数据库。
- 定义 UI 展示格式。
- 从资产库或配置文件读取数据。
- 代替 `Simulator` 或 `RuntimeWorld` 执行主循环。
- 隐式保存全部运行时状态。

事件系统是“发生了什么”的结构化通道，不是所有状态的唯一真相来源。生命值、动作状态、队伍状态、空间对象等状态仍由对应系统或运行时对象持有。

## 2. 模块结构

`core/events/` 当前按职责拆分：

```text
core/events/
├── categories.py   # 事件分类与分类默认规则
├── types.py        # EventType 枚举
├── specs.py        # EventSpec 与 EventType 元信息表
├── payloads.py     # 事件载荷协议和基础载荷
├── models.py       # GameEvent 运行时事件对象
├── handlers.py     # EventHandler 协议
├── engine.py       # EventEngine 分发器
└── __init__.py     # 对外统一导出
```

核心概念：

| 概念 | 职责 |
| --- | --- |
| `EventType` | 事件身份，描述“发生了什么”。 |
| `EventCategory` | 事件语义分类，描述事件在运行时中的作用。 |
| `EventCategorySpec` | 分类默认规则。 |
| `EventSpec` | 具体事件类型的运行时元信息。 |
| `EventPayload` | 事件载荷协议。 |
| `GameEvent` | 一次实际发生的运行时事件。 |
| `EventHandler` | 对象式事件处理器协议。 |
| `EventEngine` | 事件订阅、发布和帧事件缓冲。 |

## 3. 运行流程

事件发布流程：

```text
运行时对象构造 GameEvent
-> GameEvent 校验 payload 类型
-> EventEngine.publish(event)
-> 根据 event.should_record 写入当前帧事件缓冲
-> 按 EventType 查找订阅者
-> 按订阅顺序调用 handler
-> 如果 event.cancelled 为 true，停止后续 handler
```

事件缓冲规则：

- `EventEngine.frame_events` 只保存当前帧中需要记录的事件。
- `SimulationContext.advance_frame()` 会清空上一帧事件缓冲。
- 长期持久化不由 `EventEngine` 负责，而由应用层订阅事件后写入结果模型。

异常规则：

- `EventEngine` 不捕获 handler 异常。
- handler 抛错应直接让仿真失败，避免错误被静默吞掉。

订阅规则：

- 当前只支持按 `EventType` 订阅。
- 当前不支持按分类订阅或全局订阅。
- 当前不引入 handler 优先级；订阅顺序就是分发顺序。

## 4. 与其他模块的关系

### 4.1 `simulation`

`Simulator` 发布基础生命周期事件，例如仿真开始、帧开始、帧结束、仿真结束。

`TraceInputSystem` 发布输入消费事件，用于记录输入事实。

第 0 帧是初始化帧，仿真开始事件可发生在当前帧；`run()` 推进后才进入实际运行帧。

### 4.2 `snapshots`

快照系统从 `SimulationContext.events.frame_events` 读取当前帧事件。

快照导出时使用：

```text
event.event_type.name
event.frame
event.payload.to_dict()
source_type
```

快照只生成结构化对象，不负责写数据库。

### 4.3 `application` 与 `infrastructure`

应用层运行服务可以订阅 `EventType`，将运行时事件转换为结果模型中的 `RecordedEvent`。

结果模型和结果库仍使用 `data` 字段保存 `payload.to_dict()` 的结果。这里的 `data` 是持久化和投影格式，不是核心事件对象内部的载荷模型。

具体数据库写入属于 `infrastructure/results_sqlite/`，不属于 `core/events/`。

## 5. 事件分类

事件分类按运行时语义划分，而不是按伤害、治疗、反应、动作等业务领域划分。

| 分类 | 中文名 | 核心含义 |
| --- | --- | --- |
| `BOUNDARY` | 边界事件 | 仿真或帧循环的生命周期边界。 |
| `INTENT` | 意图事件 | 某个输入、请求或指令进入系统，但不代表成功。 |
| `INTERCEPT` | 拦截事件 | 某件事即将提交，允许机制修改或取消。 |
| `FACT` | 事实事件 | 某件事已经发生，结果已经成立。 |
| `STATE_CHANGE` | 状态变化事件 | 某个运行时状态已经改变。 |
| `AUDIT` | 审计事件 | 用于调试、复盘和解释，不直接参与机制。 |

周期性结算暂不作为一级分类。燃烧 tick、空间实体行为 tick 或效果 tick 应按语义归入事实事件、状态变化事件或拦截事件。

## 6. 分类默认规则

| 分类 | 可取消 | 载荷可修改 | 默认记录 | 结果已成立 | 可驱动机制 |
| --- | --- | --- | --- | --- | --- |
| `BOUNDARY` | 否 | 否 | 否 | 是 | 否 |
| `INTENT` | 否 | 否 | 是 | 否 | 否 |
| `INTERCEPT` | 是 | 是 | 否 | 否 | 是 |
| `FACT` | 否 | 否 | 是 | 是 | 是 |
| `STATE_CHANGE` | 否 | 否 | 是 | 是 | 是 |
| `AUDIT` | 否 | 否 | 否 | 是 | 否 |

规则说明：

- `INTERCEPT` 是唯一默认允许取消和修改载荷的分类。
- `FACT` 和 `STATE_CHANGE` 表示结果已经成立，默认进入记录，不允许回头修改事实。
- `INTENT` 默认记录请求进入系统的事实，但不代表请求成功，也不应直接驱动状态落地。
- `AUDIT` 用于解释过程，默认不记录，不应作为核心机制驱动来源。
- `BOUNDARY` 表示生命周期边界，默认不记录；具体边界事件可通过 `EventSpec` 覆盖默认记录规则。

## 7. 事件元信息

每个 `EventType` 必须在 `EVENT_SPECS` 中注册对应 `EventSpec`。

`EventSpec` 字段：

| 字段 | 含义 |
| --- | --- |
| `category` | 事件分类。 |
| `payload_type` | 事件载荷类型。 |
| `cancelable` | 是否可取消；为 `None` 时继承分类默认规则。 |
| `mutable_payload` | 载荷是否可修改；为 `None` 时继承分类默认规则。 |
| `record_by_default` | 是否默认记录；为 `None` 时继承分类默认规则。 |
| `result_committed` | 是否表示结果已经成立；为 `None` 时继承分类默认规则。 |
| `mechanic_driver` | 是否可作为机制驱动来源；为 `None` 时继承分类默认规则。 |

设计原则：

- `category` 和 `payload_type` 必填。
- 具体事件默认继承分类规则。
- 只有少数事件需要覆盖分类默认规则。
- `EventSpec` 不包含 handler 优先级、展示文本、数据库表名或 UI 信息。

## 8. 载荷规则

核心事件对象使用 `payload` 字段承载结构化载荷。

载荷规则：

- 载荷对象必须提供 `to_dict()`。
- `GameEvent.frame` 表达事件发生帧，payload 不重复记录当前帧。
- payload 不直接引用运行时复杂对象，只放可序列化数据。
- `GameEvent` 创建时会校验 payload 类型必须匹配 `EventSpec.payload_type`。
- 外部快照和结果库使用 `payload.to_dict()` 生成可持久化数据。

取消规则：

- `GameEvent.cancel()` 只允许用于 `EventSpec` 判定为可取消的事件。
- 当前已确认事件中没有可取消事件。
- 后续 `INTERCEPT` 事件需要配套可变 payload 或明确的修改接口。

记录规则：

- `GameEvent.record` 为 `None` 时使用 `EventSpec` 的默认记录规则。
- 显式传入布尔值时，作为单次事件的记录覆盖。
- `EventEngine` 可通过 `record_filter` 覆盖记录判断，用于调试或测试。

## 9. 扩展规则

新增事件类型时必须同步：

- 在 `EventType` 中添加事件成员。
- 定义对应 payload 类型。
- 在 `EVENT_SPECS` 中注册 `EventSpec`。
- 更新 [事件类型](./事件类型.md)。
- 补充事件发布点或订阅处理测试。

新增事件时应优先确认：

- 它属于哪一类事件。
- 是否表示结果已经成立。
- 是否允许取消。
- 是否允许 payload 修改。
- 是否默认记录。
- 机制逻辑是否可以依赖它驱动状态。
