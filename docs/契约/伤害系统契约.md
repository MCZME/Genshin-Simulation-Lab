# 伤害系统契约

> 状态：第一版已确认。
> 本文档固定伤害系统的稳定 key、数据模型、修饰阶段、数值公式、请求/解析/序列化契约、结构化错误与 application/content 装配边界。架构背景与设计动机见[伤害系统设计](../架构/系统/伤害系统设计.md)。
> 最后更新：2026-09-01

## 1. 适用范围

本契约适用于：

- `core/systems/damage/` 的请求、结果、修饰、公式、resolver 与 handler 行为。
- `content` 的 Damage Impact 工厂、DamageProfile 与伤害修饰 provider 接入。
- `application/assembly/` 的 provider 收集、DamageProfile 注册与 handler 注入。
- 结果库、事件与分析层消费 `DAMAGE_RESOLVED` 载荷和伤害审计。

本契约不定义反应成立条件、Aura/ICD 行为、动作索敌与空间 AOE、护盾吸收或生命提交；
这些边界分别由对应领域文档拥有。

## 2. 通用规则

- key 和枚举使用本文给出的稳定小写字符串值，不接受显示名称或自由字符串。
- 百分比使用小数倍率，例如 20% 保存为 `0.2`，200% 保存为 `2.0`。
- 数值统一使用 Python `float`；bool、NaN、正负无穷必须在模型边界拒绝。
- 所有加法使用 `math.fsum`，不依赖迭代顺序产生浮点差异。
- 结算器不使用全局随机数；暴击决策只通过注入式 `CriticalDecisionProvider` 进入。
- 结算器不进行显示舍入、整数化或 UI 格式化。
- 修饰项按稳定 key 排序；相同输入、相同属性查询结果、相同暴击决策必须产生完全一致的 `DamageResult`。
- 显示名称（`damage_name`、`provider_display_name`）只进入审计展示，不作为仿真识别依据。

## 3. 稳定 key 与枚举

### 3.1 完整公式选择键（formula_key）

```text
damage_formula.general
damage_formula.transformative_reaction
damage_formula.lunar_reaction
```

`formula_key` 是 Damage 内部公式选择键，由主攻击标签经 `DamageProfileRegistry` 解析得到，
不是上游请求变量。未注册的非 `reaction.` 命名空间标签默认 `damage_formula.general`；
`reaction.` 前缀标签未注册显式映射时必须报错，不能静默降级。

### 3.2 DamageModifierStage

```text
panel_attribute_value
panel_element_bonus
panel_crit_rate
panel_crit_damage
panel_resistance
panel_elemental_mastery
component_coefficient_percent_add
component_coefficient_flat_add
base_damage_flat_add
damage_bonus_add
defense_reduction
defense_ignore
crit_rate_add
crit_damage_add
resistance_add
```

语义：

| Stage | 作用 |
| --- | --- |
| `panel_attribute_value` | 公式读取来源主体面板属性，作为 scaling component 属性槽的基础贡献 |
| `panel_element_bonus` | 读取元素伤害加成属性，作为增伤槽的基础贡献 |
| `panel_crit_rate` | 读取面板暴击率，作为暴击率槽的基础贡献 |
| `panel_crit_damage` | 读取面板暴击伤害，作为暴击伤害槽的基础贡献 |
| `panel_resistance` | 读取目标抗性属性，作为抗性槽 R 的基础贡献 |
| `panel_elemental_mastery` | 读取元素精通，作为反应精通槽的基础贡献 |
| `component_coefficient_percent_add` | 对指定 scaling component 的原始倍率做百分比放大 |
| `component_coefficient_flat_add` | 对指定 scaling component 的倍率直接加值 |
| `base_damage_flat_add` | 基础伤害合计后、增伤区前加入固定伤害 |
| `damage_bonus_add` | 与元素伤害加成进入同一加法区 |
| `defense_reduction` | 作用于目标防御区的减防比例 |
| `defense_ignore` | 作用于本次伤害的无视防御比例 |
| `crit_rate_add` | 只参与本次伤害的暴击率调整 |
| `crit_damage_add` | 只参与本次伤害的暴击伤害调整 |
| `resistance_add` | 对目标抗性 R 直接加值，分段抗性区前生效；负值表示减抗 |

面板读取词条由公式在属性读取点生成，不是 provider 写入的修饰；它们不参与 stacking
选择，也不进入 `rejected_terms`。通用与激化公式产出面板账单；剧变与月曜公式不接受
普通伤害修饰，不产出面板账单。

调试倍率不属于 `DamageModifierStage`，只允许通过 `DebugDamageAdjustment` 构造注入；
生产组装固定使用默认 `1.0`。

### 3.3 其他稳定枚举

```text
Element（复用 core.elements）：
physical
pyro
hydro
electro
cryo
anemo
geo
dendro

CritOutcome：
not_applicable
non_critical
critical

DamageModifierStackingPolicy：
highest
lowest

LunarReactionDamageMode：
character_direct
reaction_composite

DamageReactionCapability：
secondary_amplifying
```

`Element.physical` 是伤害侧合法元素，但不参与元素交互；元素值用于选择 `bonus.damage.*`
与 `resistance.*` 属性。不接受 `none`、显示名称或自由字符串。

公共主攻击标签（`core/systems/damage/tags.py`）：

```text
normal_attack
charged_attack
plunging_attack
elemental_skill
elemental_burst
direct_damage
```

主攻击标签是攻击身份和 Profile 查找入口；附加攻击标签只参与条件和修饰，不能改变主攻击
身份或绕过 Profile 注册。`reaction.` 前缀标签必须显式注册映射。

### 3.4 属性读取与面板词条 provider_key

面板读取词条的 `provider_key` 固定为 `panel.<attribute_key>`，例如
`panel.stat.crit_damage`、`panel.bonus.damage.pyro`、`panel.resistance.hydro`；
`source_ref` 使用 `RuntimeSourceKind.SYSTEM`，`instance_id` 为属性主体 `entity_id`。
属性系统内部的 `ModifierTerm` 不进入伤害系统，只有解析后的最终面板值进入账单。

## 4. 数据模型

### 4.1 DamageScalingTerm

```text
DamageScalingTerm
├── component_key: str
├── attribute_key: AttributeKey
└── coefficient: float
```

规则：

- `component_key` 是一次请求内稳定且唯一的审计标识。
- `attribute_key` 必须由属性注册表支持，通常为 `stat.atk.total`、`stat.hp.max`、
  `stat.def.total` 或 content 私有属性。
- `coefficient` 使用小数倍率，必须为非负有限数。
- bool、NaN 和无穷值必须拒绝。

多属性缩放通过多个 term 表达：`基础伤害 = fsum(属性值 × 对应 coefficient)`。

### 4.2 DamageProfile 与 DamageProfileRegistry

```text
DamageProfile
├── formula_key              # 完整公式选择键（见 3.1）
├── main_attack_tags: frozenset[str]
└── reaction_capabilities: frozenset[DamageReactionCapability]

DamageProfileRegistry
└── resolve_for_main_attack_tag(main_attack_tag) -> DamageProfile
```

规则：

- 主攻击标签是攻击身份和 Profile 查找入口；不能依赖附加标签或集合遍历顺序选择公式。
- 未注册的非 `reaction.` 命名空间主攻击标签默认使用通用公式；`reaction.` 前缀标签
  未注册显式映射时必须报错。
- 默认注册统一由 `application/assembly/damage_profiles.py::create_default_damage_profile_registry()`
  汇总，只注册非通用公式的显式映射；反应侧 Profile 由各反应 mechanic 模块的
  `*_damage_profile()` / `*_damage_profiles()` 工厂声明。
- `DamageReactionCapability.SECONDARY_AMPLIFYING` 只允许显式注册给扩散 Profile；
  handler 校验该 capability 后才接受二次增幅输入。
- 激化不新增 capability，不使用独立公式或合成标签；激化资格由雷/草元素、正倍率证据和
  强类型 `CatalyzeReactionInput` 共同决定，公式始终是通用公式。

### 4.3 DamageImpactSpec

```text
DamageImpactSpec
├── impact_ref
├── main_attack_tag
├── element
├── scaling_terms
├── flat_base_damage
├── can_crit
├── additional_attack_tags
├── strike_type
├── range_type
├── elemental_strength
├── elemental_amount
├── icd_tag_key / icd_sequence_key
├── area
└── display_name
```

规则：

- 一次 Damage Impact 完整声明攻击身份、元素、倍率、暴击资格、打击证据、元素施加、ICD
  绑定、AOE 与显示名。
- 物理伤害不能携带元素施加；`elemental_amount` 为正时必须提供 `elemental_strength`；
  ICD 标签与序列必须同时提供或省略。
- AOE、元素量和 ICD 字段在构造 `DamageRequest` 前已经由 Impact、ICD、Aura 与 Reaction
  消费；`DamageRequest` 通过 `impact_key` 关联完整 Impact 审计，不复制空间范围或 Aura 状态。

### 4.4 DamageRequest

```text
DamageRequest
├── request_id
├── frame
├── formula_key
├── main_attack_tag
├── impact_key
├── source_ref
├── target_ref
├── source_level
├── target_level
├── element
├── source_context
├── scaling_terms
├── flat_base_damage
├── tags
├── can_crit
├── damage_name
├── reaction_capabilities
├── amplifying_reaction
├── secondary_amplifying_reaction
├── transformative_reaction
├── catalyze_reaction
└── lunar_reaction
```

规则：

- 来源必须是角色主体；目标可以是目标主体或角色主体。角色作为受方只允许绽放系列/月绽放
  攻击标签（`reaction.bloom_explosion`、`reaction.hyperbloom`、`reaction.burgeon`、
  `reaction.lunar_bloom`），由模型级白名单校验。
- `formula_key` 与 `main_attack_tag` 由 handler 从主攻击标签解析出的 DamageProfile 派生，
  不能由请求方绕过注册表自由填写；请求统一从 `DamageImpactSpec` 进入。
- `tags` 合并保存主攻击标签与附加攻击标签；主攻击身份通过 `main_attack_tag` 与审计保留。
- source/target level 必须来自组装后的运行态引用解析，不允许 content 用显示名称查找。
- `scaling_terms` 与 `flat_base_damage` 至少有一个能够产生基础伤害（通用与激化公式）；
  剧变与月曜请求不得携带普通倍率或 flat base，由各自强类型输入承载。
- `flat_base_damage` 是请求自身契约的一部分，不替代 Buff 提供的基础伤害加值。
- `can_crit=false` 时结果固定为 `not_applicable`，暴击乘数为 `1`。
- `damage_name` 来自 `DamageImpactSpec.display_name`，缺失时审计回退 action key；
  只作为审计展示。
- request 构造后不可变。

### 4.5 DamageQuery

```text
DamageQuery
├── request: DamageRequest
├── source_attribute_context: AttributeQueryContext
└── target_attribute_context: AttributeQueryContext
```

属性查询 context 至少携带：本次伤害的标签集合（主攻击标签与附加攻击标签合并）、本次
impact 的 `RuntimeSourceRef`、对方主体引用。来源属性查询的 `target_ref` 指向受击目标；
目标属性查询的 `target_ref` 指回伤害来源。

### 4.6 反应强类型输入与组合校验

通用公式可携带以下强类型输入（由 Reaction 协调流程转换，content 不能直接填写）：

```text
AmplifyingReactionInput
├── occurrence_ref
├── reaction_profile_key
├── trigger_element: Element
├── base_multiplier: float（> 0）
└── reaction_bonus: float（1 + reaction_bonus > 0）

CatalyzeReactionInput
├── target_impact_ref（必须等于 {impact_ref}:target:{target_ref}）
├── occurrence_ref
├── reaction_profile_key
├── trigger_element: Element（必须匹配当前伤害元素）
├── reaction_multiplier: float（> 0；超激化 1.15、蔓激化 1.25）
└── reaction_bonus: float
```

剧变公式必须携带：

```text
TransformativeReactionInput
├── occurrence_ref / cause_ref（至少一个非空）
├── reaction_profile_key
├── source_kind: TransformativeReactionSourceKind
├── source_level: int
├── level_multiplier_table_key
├── level_multiplier: float（> 0）
├── elemental_mastery: float（>= 0）
├── mastery_bonus（必须匹配 16 * EM / (EM + 2000)）
├── reaction_bonus
├── base_multiplier: float（> 0）
├── defense_policy（固定 "approximate_unity"）
└── cause_ref
```

扩散 Profile 可额外携带 `SecondaryAmplifyingReactionInput`（捕获式增幅），要求 Profile
已注册 `SECONDARY_AMPLIFYING` capability、`target_impact_ref` 与当前 Impact 一致：

```text
SecondaryAmplifyingReactionInput
├── target_impact_ref
├── occurrence_ref
├── reaction_profile_key
├── trigger_element: Element
├── base_multiplier: float（> 0）
├── captured_elemental_mastery: float（>= 0）
└── reaction_bonus: float
```

月曜公式必须携带 `LunarReactionDamageInput`：

```text
LunarReactionDamageInput
├── reaction_profile_key
├── mode: character_direct | reaction_composite
├── participants（角色不重复；character_direct 必须恰好一个）
├── reaction_multiplier: float（> 0）
├── base_damage_bonus: float（1 + base_damage_bonus > 0）
├── reaction_bonus: float
└── occurrence_ref: str | None
```

`LunarReactionParticipantInput` 字段：

```text
participant_ref（必须是角色主体）
source_level（正整数）
scaling_terms（component_key 不重复）
flat_base_damage
additional_base_damage（>= 0）
can_crit
ascension_multiplier（> 0）
```

按 `formula_key` 校验输入组合：

- `damage_formula.general`：可携带 `AmplifyingReactionInput` 或 `CatalyzeReactionInput`，
  两者互斥；不得携带剧变、月曜或二次增幅输入。
- `damage_formula.transformative_reaction`：必须携带 `TransformativeReactionInput`；
  同时拒绝普通倍率、flat base 和暴击能力；二次增幅仅按上述 capability 限制允许。
- `damage_formula.lunar_reaction`：必须携带 `LunarReactionDamageInput`；同时拒绝普通
  倍率、flat base 与全部其他反应输入。

```text
DamageResult

├── frame
├── formula_key
├── main_attack_tag
├── source_ref
├── target_ref
├── element
├── damage_name
├── base_damage
├── base_damage_additions
├── damage_bonus_multiplier
├── crit_outcome
├── crit_rate
├── crit_damage
├── crit_multiplier
├── reaction_multiplier
├── defense
├── resistance
├── official_damage
├── debug_multiplier
├── final_damage
├── reaction_details
├── secondary_amplifying_resolution
├── catalyze_reaction_resolution
├── lunar_reaction_resolution
├── component_results
├── source_attribute_trace
├── target_attribute_trace
├── applied_terms
├── rejected_terms
├── trace_level
├── trace_metadata
├── damage_bonus_zone
└── critical_zone
```

规则：

- `DamageResult` 构造后不可变，自洽且可独立验证，不依赖外部数据库回填。
- `damage_bonus_zone` / `critical_zone` 是增伤区与暴击区的完整分区审计；通用与激化公式
  在组装结果时写入，剧变与月曜审计从既有 reaction 明细派生，审计序列化不得从
  `trace_metadata` 反推。
- `reaction_details` 保存通用反应区结果或剧变反应输入；`secondary_amplifying_resolution`、
  `catalyze_reaction_resolution`、`lunar_reaction_resolution` 保存对应强类型审计，互不覆盖。
- `official_damage` 是正式公式伤害；`final_damage = official_damage * debug_multiplier`。
  `final_multiplier` 属性兼容旧审计命名，当前等价于 `debug_multiplier`。
- 所有数值必须是有限数；最终伤害、正式伤害和调试倍率不得为负数。

## 5. 伤害修饰契约

### 5.1 DamageModifierTerm

```text
DamageModifierTerm
├── stage: DamageModifierStage
├── value: float
├── provider_key: str
├── source_ref: RuntimeSourceRef
├── component_key: str | None
├── stacking_group: str | None
├── audit_tags: tuple[str, ...]
└── provider_display_name: str | None
```

规则：

- component 阶段（`component_coefficient_percent_add`、`component_coefficient_flat_add`、
  `panel_attribute_value`）必须提供合法 `component_key`，且该 key 必须存在于当前请求的
  scaling terms。
- 其余阶段不得提供 `component_key`。
- 百分比统一使用小数。
- stacking group 支持 `highest` / `lowest` 两种选择策略，不支持依赖遍历顺序的 `latest`。
- term 不拥有持续时间、层数或刷新逻辑；这些生命周期属于提供 term 的领域实例。
- `provider_display_name` 由收集器从 provider 声明的 `display_name` 注入，只进入审计，
  不作为识别依据。

面板读取词条由公式在属性读取点通过 `DamageModifierTerm.panel_read()` 生成，`value` 是
属性系统解析后的最终面板值，`provider_key` 见 3.4；它们不是 provider 写入的修饰，
不参与 stacking 选择，也不进入 `rejected_terms`。通用与激化公式产出面板账单；剧变与
月曜公式不产出面板账单。

### 5.2 DamageModifierProvider 与 Session 访问边界

```text
DamageModifierProviderSpec
├── provider_key
├── reads: tuple[DamageAttributeRead, ...]
├── writes: frozenset[DamageModifierStage]
├── owner_ref: AttributeSubjectRef | None
└── display_name: str | None

DamageModifierProvider
├── provider_spec
└── contribute(query, session) -> Sequence[DamageModifierTerm]
```

provider 必须：

- 无副作用。
- 显式声明可读取的属性（subject scope）和可能写入的伤害阶段；`writes` 不能为空。
- 不创建或移除机制实例。
- 不发布递归伤害请求。
- 不直接返回最终伤害。

`DamageResolutionSession` 向 provider 暴露受限属性读取能力。provider 只能通过
`resolve_for_provider` 读取声明过的属性；所有 provider 调用按稳定 key 排序、不嵌套，
越权读取、返回其他 provider 的 term、写入未声明阶段或引用未知 component 都会抛出
结构化错误。

### 5.3 stacking group

`DamageModifierIndex` 注册并在收集后应用 stacking group：同一 group 内所有 term 必须
属于同一 stage，按 `highest` / `lowest` 选择一个生效项，其余进入 `rejected_terms`；
引用未注册 group 或 stage 不一致时抛出 `ConflictingDamageModifierError`。

## 6. 数值公式

### 6.1 通用伤害公式

```text
倍率区 × 增伤区 × 暴击区 × 反应区 × 防御区 × 抗性区
```

倍率区：

```text
final_coefficient =
    original_coefficient * (1 + fsum(component_coefficient_percent_add))
    + fsum(component_coefficient_flat_add)

component_damage = resolved_attribute_value * final_coefficient

倍率区结果 =
    fsum(component_damage)
    + request.flat_base_damage
    + fsum(base_damage_flat_add)
```

增伤区：

```text
damage_bonus = resolved bonus.damage.{element} + fsum(damage_bonus_add)
damage_bonus_multiplier = 1 + damage_bonus
```

不允许隐式截断；若后续确认需要上下限，应由专用 policy 明确实现。

暴击区：

```text
crit_rate = resolved stat.crit_rate + fsum(crit_rate_add)
crit_damage = resolved stat.crit_damage + fsum(crit_damage_add)
effective_crit_rate = clamp(crit_rate, 0, 1)

crit_multiplier =
    critical: 1 + crit_damage
    non_critical: 1
```

暴击结果由注入式 `CriticalDecisionProvider.decide(query, effective_crit_rate)` 提供；
可暴击伤害不能返回 `not_applicable`。生产环境的带种子随机 provider 需要单独评审随机
种子和回放契约。

反应区（增幅反应）：

```text
mastery_bonus = 2.78 * EM / (EM + 1400)
reaction_multiplier = base_multiplier * (1 + mastery_bonus + reaction_bonus)
```

防御区：

```text
source_factor = source_level + 100
target_factor = (target_level + 100) * (1 - defense_ignore) * (1 - defense_reduction)
defense_multiplier = source_factor / (source_factor + target_factor)
```

- 防御减免与无视防御使用独立因子，各自必须为非负有限数。
- 不对组合结果做静默截断；分母非正时抛出结构化结算错误。
- 不通过构造虚拟目标 `stat.def.total` 重复表达等级防御公式。

抗性区：

```text
R < 0:          resistance_multiplier = 1 - R / 2
0 <= R <= 0.75: resistance_multiplier = 1 - R
R > 0.75:       resistance_multiplier = 1 / (1 + 4 * R)

effective_resistance = resolved resistance.{element} + fsum(resistance_add)
```

负的 `resistance_add` 表达减抗；减抗也可以继续通过目标 `resistance.*` 的运行时属性
modifier 实现，两条路径的加值合并后进入同一分段函数。抗性区不维护独立的
`resistance_shred` 状态。

最终聚合：

```text
official_damage =
    base_damage
    * damage_bonus_multiplier
    * crit_multiplier
    * reaction_multiplier
    * defense_multiplier
    * resistance_multiplier

final_damage = official_damage * debug_multiplier
```

结果必须是有限数字；出现 NaN、无穷值或不允许的负最终伤害时抛出结构化错误，不静默修正。

### 6.2 激化附加区

激化不选择独立公式，而是作为通用公式的可选附加区：

```text
mastery_bonus = 5 * EM / (1200 + EM)

base_damage_addition =
    level_multiplier
    * reaction_multiplier
    * (1 + mastery_bonus + reaction_bonus)
```

- 超激化 `reaction_multiplier = 1.15`，蔓激化 `reaction_multiplier = 1.25`；当前
  `reaction_bonus = 0.0`。稳定值由[激化反应契约](./元素反应/反应/激化反应契约.md)冻结。
- `source_level` 与 `stat.elemental_mastery` 从当前 `DamageQuery` 实时读取；等级系数复用
  已注册的共享等级系数表，并记录 table key 与属性 trace。
- 激化附加值是独立公式区，不允许通过通用 `DamageModifierTerm` 伪造；结算结果作为命名来源
  进入 `DamageResult.base_damage_additions`，与普通倍率区结果相加后再经过增伤、暴击、防御
  和对应元素抗性。

### 6.3 剧变反应公式

```text
damage =
    level_multiplier
    * base_multiplier
    * (1 + mastery_bonus + reaction_bonus)
    * resistance_multiplier
```

- 等级系数、元素精通与精通加成在 occurrence 时由 `TransformativeReactionInput` 冻结；
  `mastery_bonus` 必须匹配 `16 * EM / (EM + 2000)`，Damage 不查询来源属性。
- 防御策略固定为 `approximate_unity`，防御乘区为 `1`；不接入普通倍率、增伤、暴击或
  防御区，不接受普通 Damage modifier stage。

扩散 Profile 声明 `SECONDARY_AMPLIFYING` 时的二次增幅：

```text
基础剧变伤害
× [base_multiplier * (1 + 2.78 * captured_EM / (captured_EM + 1400) + reaction_bonus)]
× 对应元素抗性
```

基础剧变和二次增幅均使用扩散 occurrence 时捕获的数据；二次增幅不查询后续 round 的
来源属性，也不引入普通增伤、暴击或防御区。

### 6.4 月反应公式

组分公式：

```text
mastery_bonus = 6 * EM / (2000 + EM)

base_damage_after_reaction =
    core_base_damage
    * reaction_multiplier
    * (1 + base_damage_bonus)
    * (1 + mastery_bonus + reaction_bonus)
    + additional_base_damage

component_damage =
    base_damage_after_reaction
    * crit_multiplier
    * ascension_multiplier
    * resistance_multiplier
```

组分基础值来自参与者 `scaling_terms` / `flat_base_damage`（角色直接模式必须提供），或
已确认的等级基数表：

```text
80: 1077.4
90: 1446.9
95: 1561.5
100: 1674.8
```

复合聚合的稳定顺序和权重：

```text
按完整组分伤害从大到小排序（同值时按 participant_ref 稳定排序）
最高组分 × 0.60
第二组分 × 0.30
其余组分 × 0.05
```

- 组分结果和聚合结果分别进入 `LunarReactionComponentResolution` 与
  `LunarReactionDamageResolution`，通过 `DamageResult.lunar_reaction_resolution` 保留
  参与者、排序、暴击、抗性、权重及正式/调试伤害审计。
- 月曜公式暂不接受普通 Damage modifier stage，也不使用普通元素增伤区或普通防御区；
  每组分使用独立属性查询与注入式暴击决策。
- 等级基数表、精通系数和分母默认使用已确认资料中的生产数值；调用方可以显式注入替代
  `lunar_formula` 用于测试或未来配置覆盖。

### 6.5 调试专用区

```text
最终输出 = 正式公式结果 × debug_multiplier
```

- `debug_multiplier` 默认固定为 `1.0`。
- 调试区不属于任何正式伤害公式或可由 content 使用的普通 modifier stage。
- 只有测试或显式调试入口可以注入非 `1.0` 的值，生产组装默认不得启用。
- 审计结果必须能够区分正式公式结果与应用调试区后的最终输出。

## 7. Resolver 契约

`DamageResolver.resolve(query, *, trace_level=TraceLevel.FULL) -> DamageResult`：

- 从 `DamageFormulaRegistry` 选择完整公式；公式必须已注册。
- 创建一次 `DamageResolutionSession`，按稳定 key 排序收集 `DamageModifierTerm`。
- 校验 provider 返回的 term 阶段属于公式允许集（`_validate_formula_stages`）。
- 公式按槽位账单计算（面板读取词条 + 效果词条），输出不可变 `DamageResult`。
- 同一次伤害观察到的机制实例集合必须在 resolution session 内保持稳定；伤害查询期间
  不能添加、刷新、移除或过期领域实例。

trace level 只能改变审计数据量，不能改变数值结果：

- `none`：只保留最终乘区和值。
- `applied`：保留已应用 term 和必要属性 trace。
- `full`：额外保留被拒绝 term、依赖链和 policy 中间值。

## 8. 请求处理契约

`DamageRequestHandler` 把已经校验的 Damage Impact、目标解析、元素交互结果和 Damage
Profile 转换为逐目标 `DamageRequest`：

- 一次 Damage Impact 命中几个目标，就按稳定 `target_refs` 顺序产生几份独立
  `DamageRequest`；每个目标独立查询抗性、独立生成结果和审计。
- `formula_key` 由主攻击标签对应的 DamageProfile 派生；`can_crit=false` 的请求结果固定
  `not_applicable`。
- 模型级校验在动态运行时请求上执行：来源主体、目标白名单、scaling 存在性、反应输入
  组合、元素与 impact 一致性、强类型字段值域。
- Reaction 新产生的伤害只创建新的 Damage Impact，并在同帧下一 settlement round 进入
  流程；Reaction 不直接构造 `DamageRequest`。

## 9. 事件与序列化契约

### 9.1 DAMAGE_RESOLVED

`DAMAGE_RESOLVED` 由伤害系统在结算完成后发布：

- 不可取消、payload 不可变、默认记录、可以驱动后续机制。
- payload 持有不可变 `DamageResult`：`result` 保留摘要，`audit` 保存完整伤害公式审计。
- 事件类型加入需要同步[事件类型](../架构/事件系统/事件类型.md)。

### 9.2 DamageResult.to_dict()

摘要形状保持稳定，字段语义不得改变：

```text
request_id
frame
formula_key
main_attack_tag
source_ref
target_ref
element
damage_name
base_damage
damage_bonus_multiplier
crit_outcome
crit_rate
crit_damage
crit_multiplier
reaction_multiplier
reaction
secondary_amplifying_reaction
catalyze_reaction
lunar_reaction
defense_multiplier
resistance_multiplier
final_multiplier
official_damage
debug_multiplier
final_damage
```

摘要不再输出 `damage_type`。

### 9.3 DamageResult.to_audit_dict()

完整审计至少包含：

- `component_results`：倍率组件的属性值、原始/最终倍率与伤害贡献；
- `base_damage_additions`：固定基础伤害加值；
- `damage_bonus`：元素增伤、修饰增伤与最终乘数（通用/激化来自 `damage_bonus_zone`）；
- `critical`：可暴击、暴击率、实际暴击率、暴击伤害、结果与乘数（通用/激化来自
  `critical_zone`）；
- `defense`：来源/目标等级、减防、无视防御与乘数；
- `resistance`：基础抗性、抗性修饰加值、有效抗性与乘数；
- `reaction`：带 `kind` 判别（`transformative` / `catalyze` / `lunar`）的单一对象，
  二次增幅嵌套在 `transformative` 内；
- `applied_terms`、`rejected_terms`：伤害槽位账单。通用/激化公式的 `applied_terms` 在
  效果词条后追加面板读取词条（`panel_*` stage，`provider_key` 为 `panel.<attribute_key>`），
  构成“面板基础贡献 + 效果修饰”的完整账单；剧变/月曜路径保持空账单；
- `source_attribute_trace`、`target_attribute_trace`：属性解析 trace，递归依赖完整保存，
  不截断；
- `trace_metadata`：额外审计元数据。

字段保持稳定只增不改；存储载荷见[结果库契约](./结果库契约.md)第 5.3 节，事件详情接口
形状见[UI API 契约](./ui/UI%20API%20契约.md)第 8 节。

## 10. 结构化错误

| Error | code | 场景 |
| --- | --- | --- |
| `DamageValidationError` | `damage_validation_error` | 请求、term 或结果模型字段非法 |
| `UnsupportedDamageElementError` | `unsupported_damage_element` | 元素不受支持 |
| `DuplicateDamageFormulaError` | `duplicate_damage_formula` | 同一种伤害类型重复注册完整公式 |
| `UnsupportedDamageFormulaError` | `unsupported_damage_formula` | 标签或请求选择的公式没有已注册实现 |
| `DamageFormulaInputError` | `damage_formula_input_error` | 请求不满足当前公式的输入契约 |
| `DamageSourceNotFoundError` | `damage_source_not_found` | 来源运行态不存在 |
| `DamageTargetNotFoundError` | `damage_target_not_found` | 目标运行态不存在 |
| `InvalidDamageScalingError` | `invalid_damage_scaling` | 倍率或 scaling 属性非法 |
| `DamageProviderViolationError` | `damage_provider_violation` | provider 越权读取、写入或返回非法 term |
| `ConflictingDamageModifierError` | `conflicting_damage_modifier` | stacking 组未注册或组内冲突 |
| `CriticalDecisionError` | `critical_decision_error` | 暴击决策无效或与请求不兼容 |
| `DamageResolutionError` | `damage_resolution_error` | 结果非有限数等结算失败 |

application 组装层将资产和 content payload 错误转换为现有 assembly 错误或专用伤害装配错误。

## 11. Application 与 content 装配契约

- `ContentUnit` 通过 `damage_modifier_providers` 注册伤害修饰 provider；属性 provider 与
  伤害 provider 使用各自的类型化字段，新伤害实现不应根据 `scope` 字符串和自由 `object`
  query 猜测协议。
- content impact factory 只负责展开 Damage Impact，不查询最终属性、不计算防御/抗性、
  不决定 Buff 是否生效、不直接生成最终伤害、不扣减生命、不选择公式。
- `application/assembly/damage_profiles.py` 是 DamageProfile 默认注册的唯一汇总入口。
- 以下错误应尽量在组装阶段暴露，不能把可提前发现的 content 错误延迟到战斗中：
  - 未注册 damage handler 或 provider；
  - scaling ref 不存在或倍率 payload 格式错误；
  - 不支持的元素、属性 key、主攻击标签、附加攻击标签、打击类型或远近类型；
  - `reaction.` 标签缺少显式映射、Profile 引用了未注册公式，或同一主标签重复注册；
  - provider 声明了非法属性读取或伤害阶段写入；
  - 重复 provider key 或非法 stacking group。

## 12. 测试要求

`tests/unit/core/systems/damage/` 至少覆盖：

- 单属性缩放和多属性缩放。
- component 倍率百分比修饰与倍率加值。
- 固定基础伤害加值。
- 元素增伤与伤害专用增伤的聚合。
- 不可暴击、固定暴击和固定不暴击。
- 同等级无修饰防御区。
- 减防与无视防御的独立输入。
- 负抗性、普通抗性、`0.75` 边界和高抗性。
- 多个 final multiplier 的稳定顺序。
- stacking group 的 applied/rejected term。
- 面板读取词条进入槽位账单且不改变结算数值。
- bool、NaN、无穷、空 key、非法主体和未知元素。
- trace level 不改变最终数值。

浮点测试优先使用明确的绝对或相对容差；core 不为了让断言通过而提前舍入。完整测试策略
见[伤害系统设计](../架构/系统/伤害系统设计.md)第 13 节与[测试规范](../工程/测试规范.md)。

## 13. 暂缓范围

- 生产环境带种子随机 `CriticalDecisionProvider` 与回放契约尚未确认；当前仅注入式固定决策。
- `DamageRequest.tags` 当前合并主/附加攻击标签；恢复独立字段后再明确 request 层主次语义。
- `strike_type` / `range_type` 当前由 Impact 与 Reaction 消费，尚未复制到单目标请求与
  `DAMAGE_RESOLVED` 审计。
- 独立、显式的伤害属性快照契约尚未设计；当前默认实时查询。
- 直接伤害回归 golden case 待正式契约来源重新建立。
