# 状态效果（Buff）系统设计

> 状态：正式。
> 本文描述状态效果（Buff）系统的当前职责、领域边界、状态所有权、运行流程与跨系统接入方式。
> 稳定模型、枚举、策略、事件、错误和序列化规则以[状态效果系统契约](../../契约/状态效果系统契约.md)为准。
> 最后更新：2026-09-04

## 1. 定位

状态效果系统为「具有运行时身份和有限生命周期、附着于角色或目标主体、以无回调记录表达的状态效果」提供唯一状态所有者。系统中的 `Buff` 是中性技术名，不表示有利、有害或中性：例如限时属性提升、目标减抗和纯存在标记都属于同一领域模型。

本系统承担：

- 定义、实例、Store、应用策略与生命周期的领域模型。
- 创建、刷新、叠层、替换、共存、过期和显式移除的确定性语义。
- 活动 Buff 到属性修饰 term 的无副作用投影。
- `ImpactKind.APPLY_STATUS` 与统一意图队列中的 `buff` 意图接入。
- 状态提交后的事实发布与快照导出。

本系统不承担：

- 伤害、治疗、护盾、生命、能量、冷却、元素附着、元素反应或元素附魔的领域公式。
- 空间实体、召唤物、场地物或范围索敌。
- 角色专属计数器、模式状态或不可泛化的状态机；这类状态归 owner content state。
- 事件触发回调或每帧 content 回调；跨领域后续行为由统一意图队列和结算轮次承载。
- 资产参数解释、SQLite 访问、配置解析、UI 展示或结果库写入。

## 2. 归属判断

一个机制是否进入 `BuffStore`，按以下条件判断：

- 需要稳定运行时身份。
- 具有有限生命周期。
- 附着于固定角色或目标属性主体。
- 需要刷新、叠层、替换、共存或显式移除中的至少一种状态语义。
- 状态可用无回调记录完整表达。

常见归属：

| 能力 | 归属 | 原因 |
| --- | --- | --- |
| 无条件常驻武器副属性 | 静态 `ModifierProvider` | 没有运行时生命周期 |
| 限时攻击力提升 | `BuffRuntime` | 有生命周期并向属性提供 term |
| 限时目标减抗 | `BuffRuntime` | 目标状态与属性 provider 协作 |
| 纯「已激活」标记 | `BuffRuntime` | 有身份、有限生命周期且只需存在性查询 |
| 气氛值、模式、专属计数器 | owner content state | 是单个 handler 的复杂私有状态 |
| 护盾容量与吸收 | `ShieldRuntime` | 有独立公式、容量与受伤流程 |
| 冷却 | `CooldownRuntime` | 更适合 key 到 ready frame |
| 元素附着与 ICD | 对应领域运行时 | 有附着量、衰减、计数和窗口规则 |
| 周期伤害或周期治疗 | 调度命令 + 对应领域系统 | Buff 不执行 tick 公式 |
| 元素附魔 | `InfusionRuntime` | 不是普通属性 term |
| 场地物、召唤物 | `Space` / CreatedObject | 有空间身份与行为 |
| 一次伤害、治疗或能量变化 | 对应领域请求 | 没有长期实例 |

不能因为某项能力在游戏描述中称为「效果」就放入 Buff 系统。

## 3. 核心决策

- Buff 定义与运行实例分离：`BuffDefinition` 在组装期编译且运行期只读，`BuffRecord` 是 Store 中完整不可变实例。
- `BuffStore` 是活动记录与历史记录的唯一真值来源；不把 Buff 可变状态挂在角色或实体上。
- 生命周期使用半开区间：`created_frame <= frame < expires_at_frame`。
- 冲突身份固定为 `(target_ref, definition.conflict_key)`，不使用显示名、类名、注册顺序或 priority。
- 属性 provider 固定注册，查询无副作用；Buff 不动态注册/注销 provider。
- 状态先完整计划、原子提交、后发布事实；提交阶段不查询属性、不调用 content、不发布事件。
- BuffRuntime 不订阅事件、不执行回调；事实驱动的后续状态变化经统一意图队列进入下一结算轮次。
- 跨系统原子流程（例如超导减抗）通过 `prepare_apply` / `validate` / `commit_prevalidated` / `publish_committed_facts` 由协调器编排。
- 数值修饰在应用帧解析并保存在记录中；属性查询时只按层数、标签和有效期投影。

```text
core/systems/buff/
├── __init__.py      # 稳定公共导出
├── enums.py         # 生命周期、应用策略、结果、移除原因、数值策略与层数缩放
├── errors.py        # 结构化领域错误与错误详情
├── definitions.py   # BuffDefinition、BuffAttributeModifierTemplate、BuffDefinitionRegistry
├── models.py        # 请求、记录、结果、计划和值对象
├── resolver.py      # 纯应用策略解析
├── store.py         # BuffStore 与 BuffStoreReader
├── protocols.py     # BuffReader 窄只读协议
├── providers.py     # BuffAttributeModifierProvider
├── runtime.py       # 计划、提交、生命周期、事实发布与重入保护
├── handler.py       # APPLY_STATUS 到 ApplyBuffRequest 的适配
└── snapshots.py     # BuffInstanceSnapshot / BuffSnapshot
```

组件职责：

| 组件 | 职责 |
| --- | --- |
| `BuffDefinitionRegistry` | 保存组装期已编译、运行期只读的 Buff 定义 |
| `BuffResolver` | 根据定义、请求和冲突记录纯计算应用结果与替换集合 |
| `BuffStore` | 原子拥有全部完整记录、实例序列、版本和已提交操作 |
| `BuffStoreReader` | 向 provider 暴露活动记录查询的只读适配器 |
| `BuffRuntime` | 直接应用、过期清理、显式移除、计划/提交和事实发布入口 |
| `BuffReader` | provider 与 content 依赖的窄只读协议，不暴露 Store 写入口 |
| `BuffAttributeModifierProvider` | 把活动记录转换为属性 `ModifierTerm` |
| `BuffImpactRequestHandler` | 校验 `ImpactKind.APPLY_STATUS` 结构并适配目标 |
| `BuffInstanceSnapshot` / `BuffSnapshot` | 指定帧活动实例的不可变展示/持久化投影 |

## 5. 定义、实例与身份

### 5.1 BuffDefinition

`BuffDefinition` 是组装期从资产参数和 content 行为编译出的不可变运行时定义。它声明：

- 稳定定义 key、机制 key、handler key 和冲突 key。
- 允许附着的属性主体种类。
- 应用策略、数值刷新策略和最大层数。
- 属性 modifier 模板或纯标记模式。
- 可选显示名 `display_name`。

定义不是资产数据库对象。`effect_payloads` 只保存参数和 `handler_key`；content factory 负责把参数编译为 `BuffDefinition`，application 负责注册与交叉校验。

定义 key 在一次组装中全局唯一。`mechanic_key` 表达跨运行期稳定的机制语义；`definition_key` 承载本次组装中不同槽位、精炼或参数版本的唯一绑定；`handler_key` 绑定 content 实现；`conflict_key` 决定哪些活动记录参与冲突判断。显示名不进入任何身份 key。

### 5.2 BuffRecord

`BuffRecord` 是运行时真值，单条记录即可判断实例是否合法。它直接包含不可变 `BuffDefinition`、目标、来源、层数、已解析 modifier、生命周期和移除审计，不要求跨 Store 拼接元数据。

```text
BuffStore
└── BuffRecord
    ├── instance_ref
    ├── definition
    ├── created_frame
    ├── last_applied_frame
    ├── expires_at_frame
    ├── lifecycle_state
    ├── state: BuffState
    ├── removed_frame?
    └── removal_reason?
```

### 5.3 身份语义

以下概念必须分开：

- `BuffInstanceRef`：一次运行中的具体 Buff 实例身份。
- `definition_key`：本次组装中使用哪份已编译定义。
- `mechanic_key`：稳定机制语义和分析聚合 key。
- `handler_key`：哪段 content 代码负责编译定义。
- `conflict_key`：哪些活动记录参与应用策略冲突判断。
- `target_ref`：Buff 附着并影响谁。
- `applier_ref`：哪个角色或目标施加了 Buff，可为空。
- `source_context`：可跨重复施放保持一致的稳定来源绑定；单次动作/Impact 的发生身份进入 request id，不把瞬时 instance id 当成来源身份。

如果同名机制允许不同来源分别存在，content 必须把稳定来源身份编入 `conflict_key`；如果不同来源不应叠加，则使用相同 `conflict_key`。

## 6. 目标与作用域

每条 `BuffRecord` 只附着于一个 `AttributeSubjectRef`：

- `character`：固定战斗角色身份，例如 `character:slot_1`。
- `target`：固定目标身份，例如 `target:target_1`。

每个 `BuffDefinition` 必须显式声明允许的 target kinds；application 会把它与属性定义 owner kinds 交叉校验，错误目标在组装阶段失败。

队伍 Buff 在应用时展开为每个固定角色一个请求。以多目标 `ImpactKind.APPLY_STATUS` 施放时，全部请求经 `apply_many()` 在一个 Buff Store 计划中原子提交；content hook 逐个入队时不承诺跨请求原子性。固定角色展开可以让每个角色的覆盖率、刷新和移除独立可审计，并避免 Buff 系统依赖队伍动态作用域。

「始终跟随当前场上角色」的动态作用域不是固定角色 Buff；需要该语义时先评审窄的 active-character scope reader，或在切换事实后按稳定规则迁移状态。

## 7. 应用策略与生命周期

系统固定四种应用策略：

| 策略 | 无冲突记录 | 有冲突记录 |
| --- | --- | --- |
| `replace` | 创建新实例 | 原子移除全部冲突记录并创建新实例 |
| `refresh` | 创建新实例 | 保留同一兼容实例，刷新期限和值 |
| `stack_refresh` | 创建新实例 | 保留同一兼容实例，加层至上限并刷新期限 |
| `coexist` | 创建新实例 | 忽略冲突集合，始终创建独立实例 |

兼容记录要求定义、目标、施加者和稳定来源上下文完全一致。`refresh` / `stack_refresh` 遇到多个冲突记录、其他定义或不同来源时抛结构化冲突错误，不隐式选择赢家。

统一刷新规则：

```text
candidate_expires_at = request.frame + request.duration_frames
expires_at_after = max(existing.expires_at_frame, candidate_expires_at)
```

刷新不会缩短仍在活动的期限。需要以新实例强制替换并缩短期限时使用 `replace`。

`stack_refresh` 使用单记录、统一期限模型：

```text
stacks_after = min(max_stacks, stacks_before + stack_delta)
```

同一 Buff 的每层独立计时不属于本系统当前模型；这类机制需要独立栈记录或专用领域状态。

生命周期：

- 活动：`lifecycle_state == active` 且 `created_frame <= frame < expires_at_frame`。
- 过期：帧开始的时间推进阶段把 `expires_at_frame <= frame` 的活动记录统一提交为 `expired`。
- 移除：替换、驱散、消费或显式请求把记录提交为 `removed`。

即使过期清理尚未运行，provider 也必须按查询帧判断有效性，不能把 `lifecycle_state=active` 单独视为生效。

## 8. 数值与属性协作

Buff 系统不实现任意表达式语言，也不在属性查询期间修改自身状态。

当前值模型是「应用前解析、记录中保存」：

```text
content / adapter 查询所需属性或读取资产常量
-> 构造 BuffModifierValue(term_key, value)
-> BuffRuntime 按 BuffDefinition 校验并解析为 BuffResolvedAttributeModifier
-> BuffRecord 保存 BuffResolvedAttributeModifier
-> provider 在查询时只应用层数和标签条件
```

每个模板声明 `constant`（无论层数只贡献一次 value）或 `linear`（贡献 `value * stack_count`）。重新应用时由 `value_refresh_policy` 决定保留首次值（`keep_initial`）或替换为本次值（`replace_latest`）。

`BuffAttributeModifierProvider` 在组装期从定义生成并固定注册。查询时：

```text
AttributeQuery(frame, subject, key, context)
-> provider 通过 BuffReader 查询活动记录
-> 过滤 target、definition_key 和半开生命周期
-> 检查 required/excluded query tags
-> 计算 constant / linear 值
-> 生成 ModifierTerm
-> AttributeResolver 应用 stacking group 与 policy
```

关键规则：

- 不为每个运行时实例动态注册或注销 provider。
- provider 查询无副作用，不触发过期提交、不发布事件、不改变层数。
- 已过期但尚未物理清理的记录不贡献 term。
- `conflict_key` 处理实例共存；属性 `stacking_group` 处理多个有效 term 的数值择优；两者不能互相替代。
- `ModifierTerm.source_ref` 使用 `RuntimeSourceKind.MECHANIC`、`mechanic_key` 和稳定 Buff instance key；原始 `source_context` 保留在 Buff 记录、事件与快照中。
- `BuffDefinition.display_name` 进入 provider 的 `ModifierProviderSpec.display_name`，最终由属性解析注入词条审计 `provider_display_name`，不参与任何解析。

需要每次查询时动态读取施加者属性、目标生命比例等复杂条件的 Buff 不通过通用模板表达。这类能力由 content 提供声明 reads/writes 的专用 provider，并通过窄只读协议读取 Buff 和其他领域状态。

## 9. 动态最大生命边界

动态修改 `stat.hp.base`、`stat.hp.max` 或其传递依赖会要求 Health 系统按旧最大生命比例同步当前生命。仅提交 Buff 记录会让属性真值与当前生命短暂不一致，因此组装阶段拒绝这类 Buff 定义。

拒绝范围覆盖属性定义依赖图和已注册属性 provider 的 `reads -> writes` 依赖边。启用动态最大生命 Buff 前必须新增限定协调流程：

```text
BuffMaxHpChangeCoordinator
-> 准备 BuffMutationPlan
-> 用计划投影视图解析 old/new stat.hp.max
-> 准备 CharacterMaxHpReconcilePlan
-> 统一校验 BuffStore 与 HealthStore
-> 无回调提交两个领域
-> 按契约发布 Buff 与最大生命事实
```

在计划投影与协调器落地前，application 必须拒绝直接或经依赖图间接影响 `stat.hp.max` 的动态 Buff。

## 10. 与其他系统和跨系统协作

### 10.1 属性与伤害

减抗通过目标 `resistance.*` 属性 modifier 表达，普通元素伤害加成通过 `bonus.damage.*` 表达。需要伤害专用阶段、component 或复杂 DamageQuery 条件的 Buff 不让 `core/systems/buff` import Damage Runtime 或 Store；content 可以声明类型化 `DamageModifierProvider` 并读取 `BuffReader`。

### 10.2 治疗、护盾、能量与附着

Buff 系统不直接调用这些系统的写入口，也不在记录中保存它们的可变状态。若某个 Buff 应触发治疗、授盾、能量变化或附着，由内容 EventHook 或协调器生成强类型命令/请求，经统一意图队列进入后续结算轮次。

### 10.3 内容状态

`BuffRecord` 只保存通用层数、期限、已解析 modifier 值和稳定来源。角色专属累计量、模式、计数或状态机由 owner content state 保存，不在两个 Store 中复制同一计数。

### 10.4 空间与队伍

Buff 目标使用稳定战斗主体，不使用空间实体显示名或位置。范围选取和候选目标解析在 Impact / Space 层完成，`BuffRuntime` 只接受已确定的目标引用。

### 10.5 事实响应与统一意图

内容 EventHook 经 `HookDispatcher` 挂在 `FACT_RESPONSE` 阶段，消费已发布事实并产出下一结算轮次的 `ApplyBuffRequest`；这些请求以 `IntentKind.BUFF` 入队，由 `BuffIntentHandler` 在下一轮转发到 `BuffRuntime.apply`。BuffRuntime 自身不订阅 `EventEngine`。

元素共鸣的 `ResonanceReactionStage` 同样在 `FACT_RESPONSE` 阶段消费反应/伤害事实，为下一结算轮次入队能量与 Buff 意图。

### 10.6 跨系统原子协调

当 Buff 变化必须与反应 Gate、Aura、Reaction State 等其他领域状态在同一原子计划中提交时（例如超导物理减抗），协调器使用：

```text
BuffRuntime.prepare_apply(requests) -> BuffMutationPlan
-> 协调器统一 validate 全部领域计划
-> 各领域 commit_prevalidated()
-> BuffRuntime.publish_committed_facts(receipt)
```

`prepare_apply` 只生成计划，不提交任何状态；`commit_prevalidated` 无回调；事件只能在全部领域提交后由调用方发布。

## 11. 帧顺序与结算路径

每帧由 `Simulator` 驱动 `FramePipeline`。Buff 相关挂载与顺序：

| 阶段 | Buff 行为 |
| --- | --- |
| `TIME_ADVANCE` | `BuffRuntime.update_frame` 清理到期记录，先于动作推进 |
| `ACTION_ADVANCE` | 动作与影响点产生 `ImpactRequest` |
| `SETTLEMENT` | 排空意图；`ImpactRequestDispatcher` 的 APPLY_STATUS 与 `buff` 意图在此应用 |
| `FACT_RESPONSE` | content hooks / 共鸣阶段响应事实并产出下一轮意图 |
| `SNAPSHOT` | 属性面板同步；帧末导出 Buff 快照 |

帧内一个 Buff 的典型路径：

```text
动作 -> ImpactRequest(apply_status) 或 HookDispatcher 产出的 BUFF 意图
-> BuffRuntime.apply / apply_many
-> 计划 -> 校验 -> 提交 -> BUFF_APPLIED / BUFF_REMOVED 事实
-> 后续轮次属性查询可见
```

帧 0 只发布 `SIMULATION_STARTED` 并导出初始快照，不跑阶段管线。同一帧多轮结算有最大轮数上限，超过上限按确定性错误处理。

简单属性 Buff 和状态标记本身不产生未来工作，因此 `BuffRuntime.is_idle()` 固定返回 `True`。未来周期命令由对应调度器决定是否阻止仿真结束。

## 12. 计划、原子性与重入

单个或批量应用流程：

```text
请求与定义校验
-> 冻结同一批次请求顺序
-> 查询全部冲突前值
-> BuffResolver 纯计算所有结果
-> 生成一个 BuffMutationPlan
-> 校验 Store version、全部记录前值和 operation id
-> 一次提交 replacement_records
-> 生成 receipt
-> 按请求顺序发布关联移除事实与应用事实
```

规则：

- `apply_many()` 要求同批请求 frame 一致、order 唯一、request id 唯一，并按显式 `order` 处理。
- 任一请求失败，整批记录不变化。
- 替换多个旧实例与创建新实例属于一个 Store 提交。
- commit 阶段不查询属性、不调用 content、不发布事件。
- 记录按 instance ref 稳定排序，事实按请求 order、目标和 instance ref 稳定排序。
- 状态提交或事实发布期间再次调用 Buff 写入口抛重入错误。
- 事件 handler 不能在当前发布调用栈中直接 apply/remove Buff。

## 13. 事件与快照

两个事实事件：

- `BUFF_APPLIED`：一次创建、替换、刷新、叠层或到顶刷新已经提交；载荷 `result.instance_after` 携带提交后的完整实例快照。
- `BUFF_REMOVED`：一个实例因过期、替换、驱散、消费或显式原因离开活动状态。

两者都是 `STATE_CHANGE`、默认记录、不可取消、载荷不可修改。替换时先按旧 instance ref 发布 `BUFF_REMOVED`，再发布 `BUFF_APPLIED`。

`BuffSnapshot` 只包含指定帧活动的记录，按 instance ref 排序，是不可变投影。快照携带 `display_name`（来自定义）用于展示，但显示名不参与身份、冲突或生命周期。

结果持久化使用通用事件 JSON + 初始快照：初始 `buff` provider 保存第 0 帧实例；`BUFF_APPLIED` 的 `instance_after` 与 `BUFF_REMOVED` 提供折叠还原证据。事件与初始快照构成覆盖分析输入，覆盖区间按以下边界重建：

```text
开始或刷新边界 = BUFF_APPLIED.frame
计划结束边界 = BUFF_APPLIED.expires_at_after
提前结束边界 = BUFF_REMOVED.frame
会话裁剪边界 = SIMULATION_ENDED.end_frame + 1
```

同一实例刷新时更新计划结束边界；替换时旧实例结束、新实例开始。实现覆盖投影时必须按半开区间并集计算，不能简单相加重叠实例时长。

## 14. 确定性、错误边界与验证

- 所有 key、目标、请求 order、记录和事件使用稳定排序。
- modifier 数值先拒绝 `bool`，再校验有限数；百分比使用小数倍率。
- 不依赖 dict、set、handler 注册或 Event 订阅的偶然顺序。
- 不使用 priority 解决 Buff 冲突。
- 不静默忽略未知 definition、非法 target、缺失 modifier value 或不兼容冲突。
- application 把资产/content/定义错误转换为 assembly 错误；运行中的合法状态冲突保留 Buff 领域错误。
- `BuffMutationPlan` 的 operation id 与 request id 由 Runtime 确定性生成并防止重复提交。

错误层级与稳定 code 见契约第 26 节。模型、策略、生命周期、provider、Impact、事件与快照的测试要求见契约第 29 节。

## 15. 当前实现边界

当前已落地：

- 定义注册表、Store、Resolver、Runtime、快照与结构化错误。
- 四种应用策略、半开生命周期、批量原子提交和重入保护。
- `BUFF_APPLIED` / `BUFF_REMOVED` 与 `instance_after` 事件载荷。
- `BuffAttributeModifierProvider` 与属性系统接入。
- `APPLY_STATUS` Impact 适配、`buff` 意图与内容 EventHook 产出链路。
- 元素反应协调器（超导减抗）与元素共鸣动态 Buff 的跨系统接入。
- 被怜爱的少女 4 件套等真实 content 通过统一 Buff 定义和 EventHook 接入。

当前不覆盖：

- 无限持续时间。
- 每层独立期限与部分层消费。
- 驱散类别、不可驱散和免疫规则。
- 动态最大生命 Buff（组装拒绝；需要未来协调器）。
- 通用事件触发型 Buff 模板；事实触发由 content hook / 协调器承载。
- 动态场上角色或队伍作用域记录。
- Buff 专用结果库投影表。
