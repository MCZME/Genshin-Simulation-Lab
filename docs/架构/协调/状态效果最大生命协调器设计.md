# 状态效果最大生命协调器设计

> 状态：正式规范。
> 本文定义影响 `stat.hp.max` 的 Buff 变更如何与生命值系统统一计划、预校验、提交并按契约发布事实。
> 最后更新：2026-09-06。

## 1. 定位

状态效果最大生命协调器是 Buff 系统和生命值系统之间的一条固定跨领域流程，不属于其中任何一方。

目标结构：

```text
ApplyBuffRequest / RemoveBuffRequest / 帧过期
-> BuffRuntime.prepare_apply / prepare_remove / prepare_expiry
-> BuffMaxHpChangeCoordinator
   ├── BuffMutationPort
   ├── HealthReconcilePort
   ├── MaxHpProjectionPort（计划投影视图解析 old/new stat.hp.max）
   ├── 统一校验 Buff 计划与最大生命 reconcile 计划
   ├── 无回调、不得产生业务失败的提交阶段
   └── 按契约顺序发布 Buff 事实与 CHARACTER_MAX_HP_CHANGED
-> BuffMaxHpChangeRecord
```

`BuffMaxHpChangeCoordinator` 位于 `core/coordination/buff_max_hp_change/`。它只编排 Buff 计划与生命值系统受控同步入口 `HealthRuntime.prepare_max_hp_reconcile()`，不计算任何属性值或生命公式。

## 2. 处理范围

以下 Buff 变更入口统一经过协调器：

- `IntentKind.BUFF` 意图结算路径（`BuffIntentHandler`）。
- `APPLY_STATUS` Impact 路径（`BuffImpactRequestHandler`）。
- 帧过期路径（TIME_ADVANCE 阶段的 `update_frame`）。
- 显式移除路径（`dispelled` / `consumed` / `explicit`）。

计划的 definition_key 集合与组装期计算的“影响 `stat.hp.max` 依赖闭包的 Buff definition key 集合”无交集时，协调器透明透传：校验、提交与事实发布行为和直接调用 `BuffRuntime` 完全一致，不解析投影，不发布最大生命事实。

以下路径不经过本协调器：

- 元素反应结算协调器对内置反应状态 Buff 的直接计划提交。内置反应状态定义不得影响 `stat.hp.max`；未来若有需要，单独评审该路径接入。
- 静态（组装期固定）provider 对 `stat.hp.max` 的贡献，由 frame 0 初始解析覆盖。
- 目标（TARGET）主体的 `stat.hp.max` 变化：目标没有生命运行态，无需同步。

## 3. 设计目标

- Buff 系统只拥有 Buff 记录、生命周期与领域事实；生命值系统只拥有当前生命与比例同步规则。
- 动态最大生命的生效与失效同步发生在明确的生命周期边界（应用、刷新、替换、叠层、过期、移除），不逐帧轮询 `stat.hp.max` 猜测变化。
- 在任何状态提交前完成 Buff Store 与 Health Store 的版本与前值校验。
- 防止 Buff 已提交而当前生命未同步的部分成功。
- 新旧最大生命使用同一套属性解析算法，通过计划投影视图保证确定性。

## 4. 非目标

- 计算属性 modifier、解析策略或生命比例公式。
- 解释 Buff 的业务语义（来源、驱散规则、触发条件）。
- 同步目标主体或场景实体的任何状态。
- 覆盖元素反应结算协调器的内置反应状态路径。
- 处理静态 provider 的 frame 0 之外贡献（当前不存在该能力）。

## 5. 输入边界

协调器不定义新的请求模型，直接复用 Buff 领域的 `ApplyBuffRequest`、`RemoveBuffRequest` 与 `BuffMutationPlan`。最大生命同步的数值输入由投影视图解析产生：

- 提交前边界视图（`BuffProjectionMode.BEFORE`）：保持真实 Store 记录，并把计划 `expected_records` 视为在边界帧仍然活动。过期记录在边界帧的自然半开区间查询已经不贡献属性，只有显式回看边界前状态才能得到当前生命实际对齐的旧最大生命。
- 提交后视图（`BuffProjectionMode.AFTER`）：在真实 Store 记录上叠加计划 `replacement_records`。

两视图使用同一 `AttributeResolver` 定义、基础属性与非 Buff provider，仅把 `BuffAttributeModifierProvider` 的 reader 换成投影视图，保证 old/new 解析结果 bit 级确定且可比。

## 6. 受影响系统

### 6.1 BuffSystem

Buff 系统提供计划入口：`prepare_apply` / `prepare_expiry` / `prepare_remove` / `validate` / `commit_prevalidated` / `publish_committed_facts`。协调器不直接操作 `BuffStore`。

### 6.2 HealthSystem

生命值系统提供受控同步计划入口：`prepare_max_hp_reconcile` / `validate_max_hp_reconcile` / `commit_max_hp_reconcile_prevalidated` / `reconcile_events_for`。同步按 `hp_after = hp_before / old_max_hp * new_max_hp` 比例调整当前生命，只发布 `CHARACTER_MAX_HP_CHANGED`，不产生治疗或普通生命变化事实。

健康侧校验只覆盖 Store 版本、当前生命前值与结果数值范围（`hp_after <= new_max_hp`）；旧最大生命的真值由协调器的边界视图负责，健康侧不重解析（过期边界帧的自然属性查询已不含到期记录，重解析必然与边界前视图冲突）。

## 7. 准备阶段

协调器入口（`apply_many` / `remove` / `update_frame`）持有重入保护。准备阶段只查询和计算，不修改任何 Store，也不发布事件：

1. 通过 Buff 端口获得 `BuffMutationPlan`。
2. 判断计划是否触及影响 `stat.hp.max` 的 definition key；未触及则进入透传路径。
3. 对计划涉及的角色主体（`replacement_records` 的目标去重后按主体稳定排序）解析 `(old, new)` 最大生命对。
4. `old != new` 的主体逐个准备 `CharacterMaxHpReconcilePlan`，operation_id 为 `buff-max-hp:{buff operation_id}:{entity_id}`。

## 8. 统一预校验

所有计划准备完成后，在任何写入之前校验：

- Buff Store version 与全部计划前值未变化。
- 每个角色的 HealthStore version 与当前生命前值未变化。
- 各计划尚未提交。

任一校验失败时，两个 Store 均不提交，也不发布任何事实。

## 9. 提交原子性

统一预校验通过后进入无回调提交阶段：

```text
BuffStore.commit_prevalidated(buff_plan)
-> HealthStore.commit_reconcile_prevalidated(reconcile_plan)（按主体稳定顺序）
-> 形成 BuffMaxHpChangeRecord
```

与[角色受伤协调器](./角色受伤协调器设计.md)相同：第一次写入之前已经排除所有正常业务失败；一旦开始提交，两个领域提交必须完成。预校验后的提交违反“不得失败”契约时包装为 `BuffMaxHpChangeCommitError` 上抛。

## 10. 事实语义与顺序

完整提交后按以下顺序发布：

```text
BUFF_APPLIED / BUFF_REMOVED（由 BuffRuntime.events_for 按现有契约）
-> CHARACTER_MAX_HP_CHANGED（按主体稳定顺序，仅 old != new）
```

语义要点：

- 比例同步不是治疗，不发布 `CHARACTER_HEALTH_CHANGED`。
- `old == new` 的主体不发布最大生命事实。
- 事实只在两个 Store 完整提交后发布；观察者在 `BUFF_APPLIED` 时即可看到已同步的生命状态。
- 该事件类别为 AUDIT，不驱动普通当前生命变化机制（见事件类型登记）。

## 11. 领域事实所有权

- Buff 事实由 Buff 系统按已提交计划构造。
- `CHARACTER_MAX_HP_CHANGED` 由生命值系统按已提交的 `CharacterMaxHpReconcilePlan` 构造。
- 协调器只决定发布顺序，构造跨领域观测记录 `BuffMaxHpChangeRecord`（不参与结果持久化）。

## 12. 边界语义

- **半开区间**：过期帧 N 的属性查询在提交前已经不含到期记录（`is_active_at(N)` 为假）。失效同步固定发生在 TIME_ADVANCE(N)（帧首阶段），帧内后续结算看到一致状态；`FRAME_STARTED` 钩子在帧 N 前段查询到“新最大生命 + 旧比例当前生命”属于既有区间语义，随 TIME_ADVANCE 提交消失。
- **空闲停止**：活动 Buff 不阻止仿真按空闲规则结束；若仿真在 Buff 到期前停止，属性真值与当前生命保持同尺度一致，无需补同步。
- **浮点比较**：新旧最大生命使用精确相等判断；同一解析算法对同一状态的结果确定，不产生虚假同步。

## 13. 错误模型

```text
BuffMaxHpChangeError
├── BuffMaxHpChangeCommitError
└── BuffMaxHpChangeReentrancyError
```

- `BuffMaxHpChangeCommitError`：预校验后的领域提交违反不得失败契约。
- `BuffMaxHpChangeReentrancyError`：事件回调同步重入协调器。

领域校验错误（Buff 前值冲突、生命前值冲突、非法最大生命或当前生命越界等）直接上抛领域异常，不静默退化；当前生命越过投影旧最大生命时，比例结果 `hp_after` 越界由生命值领域校验（`InvalidCurrentHealthError`）拦截，两个 Store 均不提交。

## 14. 验证要求

- 生效同步：应用后最大生命更新、当前生命按比例缩放，事件顺序为 `BUFF_APPLIED` -> `CHARACTER_MAX_HP_CHANGED`。
- 失效同步：过期与显式移除后比例还原，事件顺序为 `BUFF_REMOVED` -> `CHARACTER_MAX_HP_CHANGED`。
- 刷新替换值与叠层变化产生正确的增量同步。
- 非最大生命 Buff 透传：无额外事件、无投影解析。
- 混合批次：单次 reconcile，逐主体稳定排序。
- 校验失败时两个 Store 均不提交、不发布事件。
- 事件回调同步重入协调器抛 `BuffMaxHpChangeReentrancyError`。
- 预校验后提交失败包装为 `BuffMaxHpChangeCommitError`；已提交部分不回滚，事实不发布。
- 多角色主体：逐主体按 `(kind, entity_id)` 稳定排序，operation_id 含实体 id。
- 当前生命越过投影旧最大生命时，比例结果越界由生命值领域校验拦截（`InvalidCurrentHealthError` 原样上抛），两个 Store 均不提交。
- 目标主体 Buff 不触发同步。
- 投影视图单元语义：BEFORE 保持前值活动、AFTER 叠加 replacement、真实 Store 不受影响。

## 15. 当前实现

代码位于 `core/coordination/buff_max_hp_change/`。组装阶段不再拒绝影响 `stat.hp.max` 的动态 Buff（D-014 第一版拒绝已被 D-064 修订）；`application/assembly/buffs.py` 的 `build_max_hp_affected_buff_keys()` 计算受影响 definition key 集合，`runtime_assembler` 把协调器接入意图、Impact、TIME_ADVANCE 与显式移除四个入口，并暴露在 `AssembledSimulation.buff_max_hp_coordinator`。

机制出处：最大生命变化时当前生命按比例同步、且不视为治疗，见[生命值系统设计](../系统/生命值系统设计.md)第 9 节引用的 KQM 夜兰 C4 证据。真实角色 golden case 仍按[后续实现计划](../../工程/后续实现计划.md)后置。
