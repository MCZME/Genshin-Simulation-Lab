## 2. 普通绽放输入与元素量

Reaction 输入使用协调器构造的实际后手预算：

```text
interaction_id
target_ref
frame / order
source_ref
incoming_element
incoming_amount
observed_aura
observed_quicken_state?
```

设先手可用量为 `A`、实际预算为 `T`：

```text
incoming_hydro_on_dendro / incoming_hydro_on_quicken:
hydro_used = min(T, 2 * A)
dendro_like_used = hydro_used / 2

incoming_dendro_on_hydro:
dendro_used = min(T, A / 2)
hydro_used = dendro_used * 2
```

只有双方消费量都大于零才返回普通绽放 occurrence。正水/正草/正激元素的无伤害施加也适用；普通绽放不产生 Damage Effect。`incoming_amount` 不得使用初始 ICD 请求量或再次扣除普通附着损耗。

同一 interaction 的后续候选必须消费前一步的逻辑后值。未被计划持久化的剩余预算不能自动重入 Reaction 或形成隐式 Aura。

## 3. 草原核契约

### 3.1 State 与生命周期

正普通绽放 occurrence 必须创建一枚 `DendroCoreState`，字段为：

```text
instance_ref
subject_ref
space_entity_ref
created_by_occurrence_ref
core_creator_ref
dynamic_scaling_basis
pool_scope = player_team
created_frame
expires_at_frame = created_frame + 360
creation_sequence
revision = 1
```

State 不得保存 Aura、元素量、生命值、来源等级、EM 或伤害快照。生命周期为 `[created_frame, expires_at_frame)`，到期任务的 `next_required_frame` 为 `expires_at_frame`。状态终态由 receipt/fact 表达，活动 State 不增加自由文本 lifecycle 字段。

确定性引用格式：

```text
reaction-state:dendro-core:<created_by_occurrence_ref>
reaction_object:dendro_core:<created_by_occurrence_ref>
```

### 3.2 容量与终态

`player_team` 活动核心容量为 `5`。创建第六枚时淘汰排序最小的活动核心：

```text
(creation_sequence, instance_ref)
```

终态枚举固定为：

```text
EXPIRED
CAPACITY_EVICTED
HYPERBLOOM_TRIGGERED
BURGEON_TRIGGERED
```

终态提交必须原子移除 State、容量索引、到期工作和 Space binding，并保留原因、来源、帧、occurrence 和 Effect 关联。请求重放、非活动核心和已终结核心不得产生第二个终态或 Effect。

## 4. 核心接触请求与证据

```text
BloomCoreTriggerRequest
├── operation_id
├── frame
├── source_ref
├── incoming_element
├── incoming_amount
├── contacted_core_refs
├── associated_impact_ref
└── source_context
```

`incoming_amount <= 0` 或 incoming element 不是雷/火时返回稳定空决议，可省略 `associated_impact_ref`。正雷/正火请求必须满足：

1. `associated_impact_ref` 存在且指向已提交的元素 Impact；
2. 已提交证据的 `frame`、`source_ref`、`incoming_element` 和 `incoming_amount` 分别与请求完全一致；
3. 所有 `contacted_core_refs` 都能解析到活动 State，并与对应 `REACTION_OBJECT` Space binding 一致。

缺失、未知、帧/来源/元素/元素量不一致，以及 State/Space 版本 stale，必须在计划提交前抛出稳定错误。Reaction 不接受位置替代 core ref，也不由核心数量重复扣除 incoming Aura。

同一 `operation_id` 幂等；一次请求可以按稳定 ref 顺序终结多个活动核心。非活动引用被跳过，不阻止其他活动核心提交。同帧雷火竞争不设置额外元素优先级，按稳定影响顺序由先成功请求取得终态。

## 5. 终结伤害契约

三种伤害都使用 `GeneratedDamageImpactEffect`、`TRANSFORMATIVE_REACTION`、草元素、元素量 `0`、不可暴击和近似单位防御。共享公式：

```text
mastery_bonus = 16 * EM / (EM + 2000)
damage_before_resistance =
    level_multiplier * reaction_multiplier
    * (1 + mastery_bonus + reaction_bonus)
```

第九版 `reaction_bonus = 0.0`，实际受方草抗性独立结算。稳定 Profile 如下：

| 伤害 | 来源 | 怪物倍率 | 角色倍率 | 范围 |
| --- | --- | ---: | ---: | ---: |
| 绽放爆炸 | `core_creator_ref` | `2.0` | `0.1` | `5m` |
| 超绽放 | 雷触发来源 | `3.0` | `0.15` | `1m` |
| 烈绽放 | 火触发来源 | `3.0` | `0.15` | `5m` |

来源等级和 EM 在实际伤害准备时读取：绽放爆炸读取核心创建者，超绽放在蔓生弹 `ARRIVED` 时读取雷触发者，烈绽放读取火触发者。普通目标只保存 `DamageResult`；当前场上角色通过既有角色受伤流程应用生命/护盾，Reaction 不直接修改生命。

三种 Effect 必须分别写入专属 `reaction_damage.*` key；不能统一写成 `bloom_family`。`bloom_family` 只表示 Gate 的共享计数槽。

## 6. 超绽放锁敌与蔓生弹

雷接触核心成功后，以核心终结位置为锚点查询最近合法敌方目标：

```text
search_range = 15,15
radius_xz = 15m
order = distance, stable_subject_ref
limit = 1
```

边界包含，查询使用当前 Space 的 X/Z 平面投影。无合法目标时仍提交 occurrence 和核心终态，不创建蔓生弹或伤害。

有目标时创建 `SprawlingShotState`：

```text
instance_ref
space_entity_ref
source_core_ref
trigger_occurrence_ref
trigger_source_ref
dynamic_scaling_basis
selected_target_ref
created_frame
revision = 1
```

`selected_target_ref` 创建后不可替换。`SprawlingShotResolutionPort` 只接受：

```text
ARRIVED | LOST
```

`ARRIVED` 必须使用调用方提供的命中位置，生成锁定目标半径 `1m` 的超绽放伤害；`LOST` 只终结 State 和 Space，不换目标、不造成伤害。两者由 `operation_id` 幂等处理；契约不声明真实飞行时间、速度、轨迹、转向或碰撞算法。

## 7. 共享 Gate

```text
gate = reaction_gate.bloom_family.damage
scope = damage_source_ref + target_ref + bloom_family
window_frames = 30
max_damage_instances = 2
```

绽放爆炸、超绽放、烈绽放共享同一个 `bloom_family` 计数；同一来源/目标/窗口内最多通过两次伤害，不同来源互不占用。Gate 在每个候选目标实际准备 Damage 时检查，阻止只影响该目标的 Damage Effect，不回滚 Reaction occurrence、核心终态、Space 移除或蔓生弹创建。

## 8. 事务、事实与错误边界

普通绽放、核心接触和蔓生弹结算均使用 `prepare -> validate -> commit`。Aura、ReactionState、Space、到期工作、Effect、Gate 和事实的前值/版本任一 stale 时，整批失败且不得部分提交。Commit 不重新查询 Attribute、Space 或调用 handler。

必须记录通用 `REACTION_OCCURRED`、`REACTION_STATE_CHANGED`、`DAMAGE_RESOLVED` 和 `ELEMENTAL_INTERACTION_RESOLVED`，并保存 occurrence、来源、目标、核心/蔓生弹、终态原因、Effect、帧和 Gate 结果。

组装阶段缺少 Definition、Handler、Profile、State/Space adapter、Damage kind、Gate 或目标策略时失败；运行时的关联 Impact 证据、核心 binding 和版本冲突也必须显式失败，不能降级为空反应。

## 9. 当前非目标与验收入口

契约不包含丰穰之核、角色专属强制引爆、草原核移动/聚集/碰撞/阻挡、蔓生弹真实运动、特殊目标索敌、联机受方、非零绽放专属反应加成、特殊暴击、削韧、硬直、击退和空间位移。月绽放见[月绽放反应契约](./月绽放反应契约.md)。

长期验收入口：

- `tests/unit/core/systems/reaction/test_bloom_mechanic.py`
- `tests/golden/reactions/test_quicken_and_bloom.py`

第九版实现规划与临时记录仅作为历史资料，不再定义本契约之外的稳定字段。
