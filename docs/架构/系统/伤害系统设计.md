# 伤害系统设计

> 状态：正式。
> 本文描述当前伤害系统的稳定架构边界、领域模型、完整公式结构与审计契约；具体游戏公式以已确认资料和 golden case 为验收来源。
> 最后更新：2026-08-31。

## 1. 设计目标

伤害系统负责：

1. 接收已经确定来源与目标的类型化伤害请求（`DamageImpactSpec` -> 逐目标 `DamageRequest`）。
2. 以主攻击标签经 `DamageProfileRegistry` 选择 `DamageProfile`，再由 `DamageProfile.formula_key` 选择完整公式。
3. 查询结算帧的来源属性和目标属性。
4. 收集纯查询、无副作用的伤害修饰项。
5. 按稳定完整公式结构计算伤害（通用公式含可选增幅/激化区，以及剧变、月曜）。
6. 输出不可变、可审计的 `DamageResult`，作为事实交给事件、结果记录和后续角色承伤接入层。

伤害系统不负责：

- 元素附着、ICD 与反应判定；只接收元素反应协调流程已经确认的强类型反应输入。
- 动作索敌与空间 AOE 目标解析；只按已经冻结的 `target_refs` 顺序逐目标结算。
- 目标当前生命、扣血、击败或死亡；角色目标由[角色受伤协调器](../协调/角色受伤协调器设计.md)适配为 `CharacterIncomingDamage` 后提交生命。
- 护盾吸收、减伤分摊或受击反馈。
- 治疗和能量。
- 随机种子配置与生产环境随机暴击策略；暴击决策只通过注入式 `CriticalDecisionProvider` 进入。
- UI 显示舍入和结果数据库 schema 扩展。
- 原激化判定、草/雷消耗、反应准入等 Reaction 领域事实。

## 2. 架构原则

### 2.1 伤害请求、属性和运行态分离

- Damage Impact 描述一次范围影响及其攻击、元素和 AOE 语义；伤害系统只接收目标已经解析后的单目标公式请求。
- `DamageRequest` 描述一次伤害的结算契约，不保存最终数值。
- `AttributeResolver` 是属性真值入口，伤害系统不维护第二份角色面板。
- `DamageModifierProvider` 只返回结构化修饰项，不直接修改请求、属性或世界状态。
- `DamageResult` 只描述已经完成的数值结算，不直接扣减生命。

### 2.2 默认实时查询

伤害在 `ImpactRequest` 被结算的当前帧查询属性。动作层的 `snapshot_on_emit` 当前只表示目标选择快照，不表示属性快照；伤害属性快照必须在未来通过独立、显式的伤害快照契约加入，不能复用目标选择字段产生隐式行为（见 15.5）。

### 2.3 确定性优先

- 所有加法使用 `math.fsum`。
- 修饰项按稳定 key 排序。
- 结算器不使用全局随机数。
- 结算器不进行显示舍入。
- 相同输入、相同属性查询结果、相同暴击决策必须产生完全一致的 `DamageResult`。

### 2.4 事件是结果事实，不是可变计算入口

伤害修饰通过 `DamageModifierProvider` 查询；动态机制实例的创建、刷新和过期由对应领域 Runtime 与 Store 管理；伤害结算完成后发布不可变事实事件。handler 不在事件调用栈内递归触发并修改同一次伤害结算。

不新增可变 `BEFORE_DAMAGE` / `BEFORE_CALCULATE` 事件作为修饰入口。如果未来确实需要拦截伤害请求，应设计独立 `INTERCEPT` 阶段和强类型决策结果，不能把共享 context 暴露给 handler 任意修改。

## 3. 模块边界

```text
core/systems/damage/
├── __init__.py
├── enums.py             # LunarReactionDamageMode、DamageReactionCapability、DamageModifierStage、CritOutcome、DamageModifierStackingPolicy
├── keys.py              # 完整公式稳定选择键（damage_formula.*）
├── models.py            # 输入、输出与审计值对象；各类反应强类型输入
├── profiles.py          # DamageProfileRegistry（主攻击标签 -> DamageProfile）
├── tags.py              # 公共主攻击标签常量
├── modifiers.py         # DamageModifierTerm、provider 协议、索引与 stacking group
├── policies.py          # 倍率区、增伤区、暴击区、反应区、防御区、抗性区公式族与暴击决策 provider
├── formulas.py          # DamageFormula 协议、DamageFormulaRegistry 与四种完整公式
├── level_multipliers.py # 剧变等级系数表与查询入口
├── resolver.py          # DamageResolutionSession、DamageResolver
├── handler.py           # Damage Impact 到逐目标 DamageRequest/Result 的请求处理入口
└── errors.py            # 结构化伤害错误
```

职责约束：

- `core/systems/damage/` 可以依赖 `core/attributes/` 和少量 core 值对象。
- `core/systems/damage/` 不能依赖 `assets`、`content`、`application`、`infrastructure` 或 UI。
- `content/` 提供 Damage Impact 工厂、DamageProfile 和修饰 provider，不实现全局伤害流水线。
- `application/assembly/` 负责收集 provider、构造索引并把 `DamageRequestHandler` 注入 `ImpactRequestDispatcher`；`application/assembly/damage_profiles.py` 是 DamageProfile 默认注册的唯一汇总入口。
- `infrastructure/results_sqlite/` 只持久化结果，不参与计算。
- 分析层可以消费审计结果做伤害构成和乘区分析，不重新计算真值。

## 4. 运行时流程

```text
Action / Reaction / 周期状态 / 空间实体
-> 产生 DamageImpactSpec（ImpactKind.DAMAGE）
-> Impact 使用 Action 索敌结果确定方向
-> Space 按 DamageImpactSpec.area 解析并冻结实际目标
-> 每个目标形成 TargetImpact
-> ICD、Aura 与 Reaction 处理元素、元素量、目标 Aura 和打击类型
-> DamageRequestHandler 以主攻击标签从 DamageProfileRegistry 取得 DamageProfile
-> 为每个目标构造单目标 DamageRequest
-> DamageResolver 创建一次 DamageResolutionSession
-> 收集 DamageModifierTerm
-> 按 DamageRequest.formula_key 从 DamageFormulaRegistry 选择完整公式
-> DamageFormula 编排对应计算区
-> 生成 DamageResult
-> 记录 DamageResolutionRecord
-> 发布 DAMAGE_RESOLVED 事实事件
-> 角色目标由角色受伤协调器适配为 CharacterIncomingDamage，经 HealthRuntime 产生生命变化
```

一次 Damage Impact 命中几个目标，就按稳定 `target_refs` 顺序产生几份独立 `DamageRequest`。每个目标独立查询抗性、独立生成结果和审计，不共享可变计算上下文。

Reaction 新产生的伤害只负责创建新的 Damage Impact，并在同帧下一 settlement round 进入上述流程；Reaction 不直接构造 `DamageRequest`，Damage 也不区分 Impact 来自 Action 还是 Reaction。

## 5. 核心模型

### 5.1 Element（统一元素枚举）

元素语义统一使用 `core.elements.Element`，伤害领域不再维护平行枚举。稳定值：

```text
physical
pyro
hydro
electro
cryo
anemo
geo
dendro
```

物理是伤害侧合法元素，但不参与元素交互；`aura_kind_for_element` 对物理返回 None。元素值用于选择 `bonus.damage.*` 和 `resistance.*` 属性。不接受 `none`、显示名称或自由字符串。

### 5.2 DamageScalingTerm

```text
DamageScalingTerm
├── component_key: str
├── attribute_key: AttributeKey
└── coefficient: float
```

规则：

- `component_key` 是一次请求内稳定且唯一的审计标识。
- `attribute_key` 必须由属性注册表支持，通常为 `stat.atk.total`、`stat.hp.max`、`stat.def.total` 或 content 私有属性。
- `coefficient` 使用小数倍率，例如 200% 保存为 `2.0`。
- bool、NaN 和无穷值必须拒绝。
- coefficient 必须为非负有限数；负倍率由专用 policy 或输入契约另行处理。

多属性缩放通过多个 term 表达：

```text
基础伤害 = fsum(属性值 × 对应 coefficient)
```

### 5.3 DamageProfile 与 DamageProfileRegistry

Damage Profile 把稳定主攻击标签映射到完整公式和请求约束：

```text
DamageProfile
├── formula_key              # 完整公式选择键（见 7.1）
├── main_attack_tags: frozenset[str]
└── reaction_capabilities: frozenset[DamageReactionCapability]
```

```text
DamageProfileRegistry
└── resolve_for_main_attack_tag(main_attack_tag) -> DamageProfile
```

规则：

- 主攻击标签是攻击身份和 Profile 查找入口；附加攻击标签不能替代主标签，也不能依赖集合遍历顺序选择公式。
- `formula_key` 标识 Damage 内部完整公式结构，取值见 7.1。它由注册表按主攻击标签解析，不是上游请求变量。
- 未注册的非 `reaction.` 命名空间主攻击标签默认使用通用公式（原神直伤统一走通用公式）；`reaction.` 前缀标签未注册显式映射时必须报错，不能静默降级，防止反应标签笔误变成通用伤害。
- 默认注册统一由 `application/assembly/damage_profiles.py::create_default_damage_profile_registry()` 汇总，只注册非通用公式的显式映射：反应侧 profile 由各反应 mechanic 模块的 `*_damage_profile()` / `*_damage_profiles()` 工厂声明。内容直伤不需要注册 Profile，芭芭拉与测试探针的显式注册已随默认兜底移除。
- `DamageReactionCapability.SECONDARY_AMPLIFYING` 只允许显式注册给扩散 Profile；handler 校验该 capability 后才接受二次增幅输入，不能由上游自由声明。
- 激化不新增 `DamageReactionCapability.CATALYZE_ADDITIVE`，也不再使用独立公式或合成标签：激化资格由雷/草元素、正倍率证据和强类型 `CatalyzeReactionInput` 共同决定，公式始终是通用公式。

### 5.4 DamageImpactSpec

```text
DamageImpactSpec
├── impact_ref
├── main_attack_tag
├── element
├── scaling_terms
├── flat_base_damage
├── can_crit
├── additional_attack_tags
├── strike_type
├── range_type
├── elemental_strength
├── elemental_amount
├── icd_tag_key / icd_sequence_key
├── area
└── display_name
```

规则：

- 一次 Damage Impact 完整声明攻击身份、元素、倍率、暴击资格、打击证据、元素施加、ICD 绑定、AOE 与显示名。
- 物理伤害不能携带元素施加；`elemental_amount` 为正时必须提供 `elemental_strength`；ICD 标签与序列必须同时提供或省略。
- AOE、元素量和 ICD 字段在构造 `DamageRequest` 前已经由 Impact、ICD、Aura 与 Reaction 消费；`DamageRequest` 通过 `impact_key` 关联完整 Impact 审计，不复制空间范围或 Aura 状态。
- 芭芭拉普攻已按该链路落地：`DamageImpactSpec` 同时携带 `area`（球 -> 当前 X/Z 模型的同半径圆）与 `strike_type` / `range_type` / ICD 绑定；AOE 以索敌选中的最近目标为锚点，由 Impact/Space 解析实际受击目标后再构造逐目标 `DamageRequest`。

### 5.5 DamageRequest

```text
DamageRequest
├── request_id
├── frame
├── formula_key
├── main_attack_tag
├── impact_key
├── source_ref
├── target_ref
├── source_level
├── target_level
├── element
├── source_context
├── scaling_terms
├── flat_base_damage
├── tags
├── can_crit
├── damage_name
├── reaction_capabilities
├── amplifying_reaction
├── secondary_amplifying_reaction
├── transformative_reaction
├── catalyze_reaction
└── lunar_reaction
```

规则：

- 来源必须是角色主体；目标可以是目标主体或角色主体。角色作为受方只允许绽放系列/月绽放攻击标签（`reaction.bloom_explosion`、`reaction.hyperbloom`、`reaction.burgeon`、`reaction.lunar_bloom`），由模型级白名单校验。
- `formula_key` 与 `main_attack_tag` 由 handler 从主攻击标签解析出的 DamageProfile 派生，不能由请求方绕过注册表自由填写；请求入口统一为 `DamageImpactSpec`，自由 `params.damage` 路径已移除。
- `tags` 当前合并保存主攻击标签与附加攻击标签；主攻击身份通过 `main_attack_tag` 与审计保留。附加攻击标签只参与条件和修饰，不能改变主攻击身份或绕过 Profile 注册。Damage Impact 层仍区分 `main_attack_tag` / `additional_attack_tags`；request 层恢复独立字段是未决事项（见 15.3）。
- source/target level 必须来自组装后的运行态引用解析，不允许 content 用显示名称查找。
- `scaling_terms` 与 `flat_base_damage` 至少有一个能够产生基础伤害（通用与激化公式）；剧变与月曜请求不得携带普通倍率或 flat base，由各自强类型输入承载。
- `flat_base_damage` 是请求自身契约的一部分，不替代 Buff 提供的基础伤害加值。
- `can_crit=false` 时结果固定为 `not_applicable`，暴击乘数为 `1`。
- `damage_name` 来自 `DamageImpactSpec.display_name`，缺失时审计回退 action key；只作为审计展示，不作为仿真识别依据。
- request 构造后不可变。
- 强类型反应输入由 Reaction 协调流程转换，content 不能直接填写；输入组合按 `formula_key` 校验：
  - `damage_formula.general`：可携带 `AmplifyingReactionInput` 或 `CatalyzeReactionInput`，两者互斥；不得携带剧变、月曜或二次增幅输入。
  - `damage_formula.transformative_reaction`：必须携带 `TransformativeReactionInput`；同时拒绝普通倍率、flat base 和暴击能力。`SecondaryAmplifyingReactionInput` 仅当 Profile 已注册扩散 Profile 且声明 `SECONDARY_AMPLIFYING` capability、且 `target_impact_ref` 与当前 Impact 一致时允许。
  - `damage_formula.lunar_reaction`：必须携带 `LunarReactionDamageInput`；同时拒绝普通倍率、flat base 与全部其他反应输入。`CHARACTER_DIRECT` 只能有一个角色参与者，`REACTION_COMPOSITE` 至少一个参与者且角色不重复。

`CatalyzeReactionInput` 只能进入通用公式：`trigger_element` 必须匹配当前伤害元素，`target_impact_ref` 必须等于 `{impact_ref}:target:{target_ref}`；无该输入时请求按普通直伤结算。

### 5.6 DamageQuery

```text
DamageQuery
├── request: DamageRequest
├── source_attribute_context: AttributeQueryContext
└── target_attribute_context: AttributeQueryContext
```

属性查询 context 至少携带：

- 本次伤害的标签集合（主攻击标签与附加攻击标签合并）。
- 本次 impact 的 `RuntimeSourceRef`。
- 对方主体引用。

来源属性查询的 `target_ref` 指向受击目标；目标属性查询的 `target_ref` 指回伤害来源。这样 provider 可以在声明依赖后实现“对特定目标增伤”或“来自特定来源时减抗”等条件。

### 5.7 DamageResult

```text
DamageResult
├── request_id
├── frame
├── formula_key
├── main_attack_tag
├── source_ref
├── target_ref
├── element
├── damage_name
├── base_damage
├── base_damage_additions
├── damage_bonus_multiplier
├── crit_outcome
├── crit_rate
├── crit_damage
├── crit_multiplier
├── reaction_multiplier
├── defense
├── resistance
├── official_damage
├── debug_multiplier
├── final_damage
├── reaction_details
├── secondary_amplifying_resolution
├── catalyze_reaction_resolution
├── lunar_reaction_resolution
├── component_results
├── source_attribute_trace
├── target_attribute_trace
├── applied_terms
├── rejected_terms
├── trace_level
├── trace_metadata
├── damage_bonus_zone
└── critical_zone
```

`DamageResult` 必须不可变并包含足够信息，使测试和分析层能够解释最终值，而不是只保存一个 float。

规则：

- `damage_bonus_zone` / `critical_zone` 是增伤区与暴击区的完整分区审计；通用与激化公式在组装结果时写入，剧变与月曜审计从既有 reaction 明细派生，审计序列化不得从 `trace_metadata` 反推。
- `reaction_details` 保存通用反应区结果或剧变反应输入；`secondary_amplifying_resolution`、`catalyze_reaction_resolution`、`lunar_reaction_resolution` 保存对应强类型审计，互不覆盖。
- `official_damage` 是正式公式伤害；`final_damage = official_damage * debug_multiplier`。`final_multiplier` 属性兼容旧审计命名，当前等价于 `debug_multiplier`。
- 所有数值必须是有限数；最终伤害、正式伤害和调试倍率不得为负数。显示舍入、整数化或 UI 格式化不在 core 中进行。

## 6. 伤害修饰契约

属性 `ModifierTerm` 只修改属性，不能承担伤害专用乘区。伤害系统定义独立的 `DamageModifierTerm`。

### 6.1 DamageModifierStage

```text
component_coefficient_percent_add
component_coefficient_flat_add
base_damage_flat_add
damage_bonus_add
defense_reduction
defense_ignore
crit_rate_add
crit_damage_add
resistance_add
```

语义：

| Stage | 作用 |
| --- | --- |
| `component_coefficient_percent_add` | 对指定 scaling component 的原始倍率做百分比放大 |
| `component_coefficient_flat_add` | 对指定 scaling component 的倍率直接加值 |
| `base_damage_flat_add` | 基础伤害合计后、增伤区前加入固定伤害 |
| `damage_bonus_add` | 与元素伤害加成进入同一加法区 |
| `defense_reduction` | 作用于目标防御区的减防比例 |
| `defense_ignore` | 作用于本次伤害的无视防御比例 |
| `crit_rate_add` | 只参与本次伤害的暴击率调整 |
| `crit_damage_add` | 只参与本次伤害的暴击伤害调整 |
| `resistance_add` | 对目标抗性 R 直接加值，分段抗性区前生效；负值表示减抗 |

调试倍率不属于 `DamageModifierStage`，只允许通过 `DebugDamageAdjustment` 构造注入；生产组装固定使用默认 `1.0`。

### 6.2 DamageModifierTerm

```text
DamageModifierTerm
├── stage: DamageModifierStage
├── value: float
├── provider_key: str
├── source_ref: RuntimeSourceRef
├── component_key: str | None
├── stacking_group: str | None
├── audit_tags: tuple[str, ...]
└── provider_display_name: str | None
```

规则：

- component 阶段必须提供合法 `component_key`，且该 key 必须存在于当前请求的 scaling terms。
- 非 component 阶段不得提供 `component_key`。
- 百分比统一使用小数，例如 20% 保存为 `0.2`。
- stacking group 支持 `highest` / `lowest` 两种选择策略，不支持依赖遍历顺序的 `latest`。
- term 不拥有持续时间、层数或刷新逻辑；这些生命周期属于提供 term 的领域实例。
- `provider_display_name` 由收集器从 provider 声明的 `display_name` 注入，只进入审计，不作为识别依据。

### 6.3 DamageModifierProvider

```text
DamageModifierProviderSpec
├── provider_key
├── reads: tuple[DamageAttributeRead, ...]
├── writes: frozenset[DamageModifierStage]
├── owner_ref: AttributeSubjectRef | None
└── display_name: str | None

DamageModifierProvider
├── provider_spec
└── contribute(query, session) -> Sequence[DamageModifierTerm]
```

provider 必须：

- 无副作用。
- 显式声明可读取的属性（subject scope）和可能写入的伤害阶段；`writes` 不能为空。
- 不创建或移除机制实例。
- 不发布递归伤害请求。
- 不直接返回最终伤害。

`DamageResolutionSession` 向 provider 暴露受限的属性读取能力。provider 只能通过 `resolve_for_provider` 读取声明过的属性；所有 provider 调用按稳定 key 排序、不嵌套，越权读取、返回其他 provider 的 term、写入未声明阶段或引用未知 component 都会抛出结构化错误。

stacking group 由 `DamageModifierIndex` 注册并在收集后应用：同一 group 内所有 term 必须属于同一 stage，按 `highest` / `lowest` 选择一个生效项，其余进入 `rejected_terms`；引用未注册 group 或 stage 不一致时抛出 `ConflictingDamageModifierError`。

静态效果可以在组装阶段直接注册 provider；未来 BuffRuntime 等领域运行时中的活动实例可以向伤害索引暴露 provider。两者使用同一个查询接口，但生命周期来源不同。

## 7. 完整公式架构

### 7.1 分层与公式选择

伤害处理采用以下固定分层：

```text
DamageImpactSpec.main_attack_tag
-> DamageProfileRegistry
-> DamageProfile.formula_key
-> DamageFormulaRegistry
-> 对应 DamageFormula
-> DamageFormula 编排所需公式族
-> 生成 DamageResult
```

其中：

- 主攻击标签负责确定本次攻击身份并查找 Damage Profile。
- Damage Profile 负责选择完整公式和请求约束。
- 完整公式负责确定乘区组成、计算顺序和审计结果。
- 公式族负责防御区、抗性区、暴击区等可被多个完整公式复用的局部计算。
- 公式选择使用稳定主攻击标签与 Profile 映射，不根据元素、附加标签或最终属性值临时猜测。
- 未注册的非反应主攻击标签默认通用公式；`reaction.` 前缀标签未注册、或 Profile 指向未注册公式时必须报错，不能静默降级。

当前已注册三种完整公式：

```text
formula_key=damage_formula.general                 -> GeneralDamageFormula
formula_key=damage_formula.transformative_reaction -> TransformativeReactionDamageFormula
formula_key=damage_formula.lunar_reaction          -> LunarReactionDamageFormula
```

`formula_key` 是 Damage 内部公式选择键，不是上游请求变量。Action、Reaction、周期状态和空间实体都只产生带稳定主攻击标签的 Damage Impact；组装阶段只需为剧变、月曜等非通用公式注册显式映射，直伤标签默认通用。原激化本身不产生伤害，因此不创建 Damage Impact。

### 7.2 通用伤害公式

通用伤害公式由以下计算区组成：

```text
倍率区
× 增伤区
× 暴击区
× 反应区
× 防御区
× 抗性区
```

普通非反应伤害、增幅反应和激化参与的伤害由 Profile 选择通用公式：

- 无反应时，反应区使用通用公式规定的单位结果。
- 增幅反应由反应区提供对应倍率。
- 激化由激化附加区提供基础伤害增加值（见 7.3）。
- 不可暴击等规则只改变暴击区输入或结果，不改变所选 Profile 与公式。

倍率区统一按以下结构聚合：

```text
final_coefficient =
    original_coefficient * (1 + fsum(component_coefficient_percent_add))
    + fsum(component_coefficient_flat_add)

component_damage = resolved_attribute_value * final_coefficient

倍率区结果 =
    fsum(component_damage)
    + request.flat_base_damage
    + fsum(base_damage_flat_add)
```

请求自带、角色、武器、圣遗物或其他机制提供的普通基础伤害固定加值使用同一种数据结构和聚合规则，来源差异只保留在 term 的来源引用和审计信息中。

增伤区：

```text
damage_bonus = resolved bonus.damage.{element} + fsum(damage_bonus_add)
damage_bonus_multiplier = 1 + damage_bonus
```

不允许增伤区隐式截断；若后续确认某些规则需要上下限，应由专用 policy 明确实现。

暴击区：

```text
crit_rate = resolved stat.crit_rate + fsum(crit_rate_add)
crit_damage = resolved stat.crit_damage + fsum(crit_damage_add)
effective_crit_rate = clamp(crit_rate, 0, 1)

crit_multiplier =
    critical: 1 + crit_damage
    non_critical: 1
```

结算器自己不调用随机数。暴击结果由注入式 `CriticalDecisionProvider.decide(query, effective_crit_rate)` 提供；可暴击伤害不能返回 `not_applicable`。测试使用固定返回 `critical` 或 `non_critical` 的 provider；生产环境的带种子随机 provider 需要单独评审随机种子和回放契约（见 15.8）。

反应区（增幅反应）：

```text
mastery_bonus = 2.78 * EM / (EM + 1400)
reaction_multiplier = base_multiplier * (1 + mastery_bonus + reaction_bonus)
```

防御区：

```text
source_factor = source_level + 100
target_factor = (target_level + 100) * (1 - defense_ignore) * (1 - defense_reduction)
defense_multiplier = source_factor / (source_factor + target_factor)
```

- 防御减免与无视防御使用独立因子，各自必须为非负有限数。
- 不对组合结果做静默截断；分母非正时抛出结构化结算错误。
- resolver 不通过构造虚拟目标 `stat.def.total` 重复表达等级防御公式。

抗性区：

```text
R < 0:          resistance_multiplier = 1 - R / 2
0 <= R <= 0.75: resistance_multiplier = 1 - R
R > 0.75:       resistance_multiplier = 1 / (1 + 4 * R)
```

目标抗性从 `resistance.{element}` 实时查询，使用小数表示。伤害专用修饰阶段 `resistance_add` 在分段函数前直接作用于 R：

```text
effective_resistance = resolved resistance.{element} + fsum(resistance_add)
```

负的 `resistance_add` 表达减抗；减抗也可以继续通过目标 `resistance.*` 的运行时属性 modifier 实现，两条路径的加值合并后进入同一分段函数。抗性区不维护独立的 `resistance_shred` 状态。

最终聚合：

```text
official_damage =
    base_damage
    * damage_bonus_multiplier
    * crit_multiplier
    * reaction_multiplier
    * defense_multiplier
    * resistance_multiplier

final_damage = official_damage * debug_multiplier
```

结果必须是有限数字；出现 NaN、无穷值或不允许的负最终伤害时抛出结构化错误，不静默修正。

### 7.3 激化附加区

超激化和蔓激化不选择独立公式，而是作为通用公式的可选激化附加区：

```text
(倍率区 + 激化附加区)
× 增伤区
× 暴击区
× 防御区
× 抗性区
```

激化资格不依赖攻击标签或独立 Profile：关联伤害元素为雷/草、`scaling_terms` 存在正系数倍率项，且反应协调流程提供强类型 `CatalyzeReactionInput` 时，通用公式在倍率区后追加激化附加区。该附加值不并入普通基础伤害固定加值，也不通过通用反应区处理。

```text
mastery_bonus = 5 * EM / (1200 + EM)

base_damage_addition =
    level_multiplier
    * reaction_multiplier
    * (1 + mastery_bonus + reaction_bonus)
```

- 超激化 `reaction_multiplier = 1.15`，蔓激化 `reaction_multiplier = 1.25`；稳定值由激化反应契约冻结，当前 `reaction_bonus = 0.0`。
- `source_level` 与 `stat.elemental_mastery` 从当前 `DamageQuery` 实时读取；不读取原激化创建者，不快照 EM。等级系数复用已注册的共享等级系数表，并记录 table key 与属性 trace。
- 激化附加值是独立公式区，不允许通过通用 `DamageModifierTerm` 伪造；结算结果作为命名来源进入 `DamageResult.base_damage_additions`，与普通倍率区结果相加后再经过增伤、暴击、防御和对应元素抗性。
- Damage 输入必须是强类型 `CatalyzeReactionInput`，且只能进入通用公式。输入与当前 Impact/元素不一致、增幅与激化输入同时出现，或非通用公式收到该输入，都稳定失败；无输入时请求按普通直伤结算。
- 完整稳定 key、调整模型和测试矩阵见[激化反应设计](./元素反应/反应/激化反应设计.md)与[激化反应契约](../../契约/元素反应/反应/激化反应契约.md)。

### 7.4 剧变反应公式

剧变反应使用独立公式结构：

```text
系数区
× 剧变提升区
× 抗性区
```

```text
damage =
    level_multiplier
    * base_multiplier
    * (1 + mastery_bonus + reaction_bonus)
    * resistance_multiplier
```

- 等级系数、元素精通与精通加成在 occurrence 时由 `TransformativeReactionInput` 冻结；`mastery_bonus` 必须匹配 `16 * EM / (EM + 2000)`，Damage 不查询来源属性。
- 防御策略固定为 `approximate_unity`，防御乘区为 `1`；剧变公式不接入普通倍率、增伤、暴击或防御区，也不接受普通 Damage modifier stage。
- 抗性区在输入、分段规则和审计语义与公共抗性公式族一致时复用。

扩散 Profile 可额外声明 `SECONDARY_AMPLIFYING`。当且仅当该 capability、同一 target Impact ref 和 `SecondaryAmplifyingReactionInput` 全部成立时，剧变公式使用：

```text
基础剧变伤害
× [base_multiplier * (1 + 2.78 * captured_EM / (captured_EM + 1400) + reaction_bonus)]
× 对应元素抗性
```

基础剧变和二次增幅均使用扩散 occurrence 时捕获的数据；二次增幅不查询后续 round 的来源属性，也不引入普通增伤、暴击或防御区。其他剧变 Profile 仍拒绝该输入。

### 7.5 月反应公式

月反应使用独立 `lunar_reaction` 公式并由 `LunarReactionDamageFormula` 处理。当前代码冻结两种 Damage 侧模式：

- `CHARACTER_DIRECT` 只允许一个角色参与者，使用该角色的属性倍率或固定基础伤害作为组分基础值。
- `REACTION_COMPOSITE` 保存多个角色参与者；每个参与者独立读取属性、元素精通、暴击和目标抗性，完成完整组分伤害后才排序和加权。

组分基础值来自参与者 `scaling_terms` / `flat_base_damage`（角色直接模式必须提供），或已确认的等级基数表（生产默认 `80: 1077.4`、`90: 1446.9`、`95: 1561.5`、`100: 1674.8`）。组分公式：

```text
mastery_bonus = 6 * EM / (2000 + EM)

base_damage_after_reaction =
    core_base_damage
    * reaction_multiplier
    * (1 + base_damage_bonus)
    * (1 + mastery_bonus + reaction_bonus)
    + additional_base_damage

component_damage =
    base_damage_after_reaction
    * crit_multiplier
    * ascension_multiplier
    * resistance_multiplier
```

复合聚合的稳定顺序和权重为：

```text
按完整组分伤害从大到小排序（同值时按 participant_ref 稳定排序）
最高组分 × 0.60
第二组分 × 0.30
其余组分 × 0.05
```

- 组分结果和聚合结果分别进入 `LunarReactionComponentResolution` 与 `LunarReactionDamageResolution`，通过 `DamageResult.lunar_reaction_resolution` 保留参与者、排序、暴击、抗性、权重及正式/调试伤害审计。
- 月曜公式暂不接受普通 Damage modifier stage，也不使用普通元素增伤区或普通防御区；每组分使用独立属性查询与注入式暴击决策。
- 等级基数表、精通系数和分母默认使用已确认资料中的生产数值，已注册进默认 `DamageFormulaRegistry`；调用方可以显式注入替代 `lunar_formula` 用于测试或未来配置覆盖。
- 月绽放反应本身不产生伤害，不声明 `LunarReactionDamageImpactEffect`。角色月绽放伤害由角色技能消费草露后构造 `LunarReactionDamageInput(mode=CHARACTER_DIRECT)` 进入统一 Damage Impact；`LunarReactionDamageImpactEffect` 类型保留给未来确实存在反应月曜伤害的机制。
- 月反应是否成立不由 Damage 判断。队伍角色提供的准入能力、严格元素签名、普通/月变体选择和草露状态均属于 Reaction 与元素反应协调流程；正式 Reaction 边界见[元素反应架构文档索引](./元素反应/文档索引.md)。

### 7.6 调试专用区

```text
最终输出 = 正式公式结果 × debug_multiplier
```

- `debug_multiplier` 默认固定为 `1.0`。
- 调试区不属于任何正式伤害公式或可由 content 使用的普通 modifier stage。
- 只有测试或显式调试入口可以注入非 `1.0` 的值，生产组装默认不得启用。
- 审计结果必须能够区分正式公式结果与应用调试区后的最终输出。

### 7.7 Profile、公式与其他维度

以下维度不直接作为公式选择键：

- 物理、火、水等伤害元素。
- 是否暴击、是否可暴击和暴击结果。
- 单体、范围、持续伤害等目标选择或发生方式。
- 攻击力、生命值、防御力等倍率来源。
- 场上角色、后台角色、武器或内容创建对象等伤害来源。

普通攻击、重击、下落攻击、战技、爆发和具体反应等主攻击标签会选择 Damage Profile，但不是公式实现本身；多个主标签可以映射到同一个公式。附加攻击标签只参与条件和修饰，不能改变主攻击身份或绕过 Profile 注册。

坠落、固定伤害及其他特殊伤害是否需要新增类型，留待对应机制有可信来源和验收案例后评审；当前不增加无明确公式语义的通用 `SPECIAL` 类型。

## 8. 事件边界

伤害相关事件：

| EventType | Category | 语义 |
| --- | --- | --- |
| `DAMAGE_RESOLVED` | `FACT` | 一次伤害数值已经完成结算，但尚不代表生命已扣减 |
| `DAMAGE_APPLIED` | `FACT` | 正伤害已经以角色为目标完成护盾与血量提交，不要求血量实际减少 |

`DAMAGE_RESOLVED` 由伤害系统在结算完成后发布，`DAMAGE_APPLIED` 由角色受伤协调器在护盾与血量提交后发布；两者都默认记录。

规则：

- `DAMAGE_RESOLVED` 不可取消、payload 不可变、默认记录、可以驱动后续机制。payload 持有不可变 `DamageResult`，其中 `result` 保留摘要，`audit` 保存完整伤害公式审计。
- `DAMAGE_APPLIED` 在 `CharacterIncomingDamage.amount > 0` 且目标是角色时发布，保存 `CharacterDamageTakenRecord`；完全吸收时仍发布，但不会产生 `CHARACTER_HEALTH_CHANGED`，零伤害不发布。
- 不新增可变 `BEFORE_DAMAGE` / `BEFORE_CALCULATE` 事件作为修饰入口。

事件类型的最终加入需要同步[事件类型](../事件系统/事件类型.md)。

## 9. 审计与序列化

`DamageResult` 本身自洽且可独立验证，不依赖外部数据库回填。它保存：

- 每个 scaling component 的属性值、原始倍率、修饰后倍率和贡献值。
- 元素增伤属性解析结果与增伤乘数。
- 暴击率、暴击伤害和暴击决策来源。
- 防御、抗性 policy 的输入和输出。
- 已应用与被拒绝的伤害修饰项。
- 最终乘区的稳定应用顺序。
- 关联的属性 resolution trace。

trace level 复用属性系统的 `none`、`applied`、`full` 语义：

- `none`：只保留最终乘区和值。
- `applied`：保留已应用 term 和必要属性 trace。
- `full`：额外保留被拒绝 term、依赖链和 policy 中间值。

trace level 只能改变审计数据量，不能改变数值结果。

### 9.1 `DamageResult` 序列化契约

- `to_dict()` 保持现有摘要形状，字段语义不得改变；摘要包含 `formula_key` 与 `main_attack_tag`，不再输出 `damage_type`。
- `to_audit_dict()` 输出完整审计，供 `DAMAGE_RESOLVED` 的 `audit` 载荷序列化。
- `to_audit_dict()` 至少包含：
  - `component_results`：倍率组件的属性值、原始/最终倍率与伤害贡献；
  - `base_damage_additions`：固定基础伤害加值；
  - `damage_bonus`：元素增伤、修饰增伤与最终乘数（通用/激化来自 `damage_bonus_zone`）；
  - `critical`：可暴击、暴击率、实际暴击率、暴击伤害、结果与乘数（通用/激化来自 `critical_zone`）；
  - `defense`：来源/目标等级、减防、无视防御与乘数；
  - `resistance`：基础抗性、抗性修饰加值、有效抗性与乘数；
  - `reaction`：带 `kind` 判别（`transformative` / `catalyze` / `lunar`）的单一对象，二次增幅嵌套在 `transformative` 内；
  - `applied_terms`、`rejected_terms`：已应用与被拒绝伤害修饰项；
  - `source_attribute_trace`、`target_attribute_trace`：属性解析 trace，递归依赖完整保存；
  - `trace_metadata`：额外审计元数据。
- 字段保持稳定只增不改；存储载荷见[结果库契约](../../契约/结果库契约.md)第 5.3 节，事件详情接口形状见[UI API 契约](../../契约/ui/UI%20API%20契约.md)第 8 节。

## 10. 与动态机制领域的关系

静态 provider 和测试 provider 已足以验证公式与链路；动态 provider 后续由对应领域 Store 提供只读 view：

```text
BuffStore / 其他领域 Store
-> 当前帧活动完整记录只读 view
-> 暴露 DamageModifierProvider / Attribute ModifierProvider
-> DamageResolver 在当前帧纯查询
```

边界：

- 伤害查询期间不能添加、刷新、移除或过期领域实例。
- 对应领域实例生命周期决定 provider 是否活动。
- provider 不保存独立持续时间。
- 同一次伤害观察到的机制实例集合必须在 resolution session 内保持稳定。

## 11. application 与 content 接入

### 11.1 content contribution

`ContentUnit` 提供类型化入口：

```text
damage_modifier_providers: Sequence[DamageModifierProvider]
```

内容包通过 `profiles.py` 声明 DamageProfile，通过 `damage_modifier_providers` 注册伤害修饰 provider。现有泛化 `modifiers` 入口可作短期兼容，但新伤害实现不应根据 `scope` 字符串和自由 `object` query 猜测协议；属性 provider 与伤害 provider 使用各自的类型化字段。

### 11.2 impact factory

content impact factory 负责把技能倍率引用、攻击身份、元素应用数据和动作上下文展开为 Damage Impact，例如：

```text
impact_key="barbara.normal.hit_1"
-> DamageImpactSpec(
       main_attack_tag="普通攻击1",
       element="hydro",
       elemental_amount=1,
       icd_sequence_key="默认",
       icd_tag_key="普通攻击",
       scaling_terms=(DamageScalingTerm(component_key, stat.atk.total, coefficient), ...),
   )
-> Space 解析实际 AOE 目标
-> 每个目标构造 DamageRequest
```

impact factory 不负责：

- 查询最终攻击力。
- 计算防御或抗性。
- 决定 Buff 是否生效。
- 直接生成最终伤害值。
- 扣减目标生命。
- 直接选择或构造公式；公式由主攻击标签对应 Profile 决定。

`DamageRequestHandler` 根据已经校验的 Damage Impact、目标解析、元素交互结果和 Damage Profile 创建类型化 `DamageRequest`，并通过 `ImpactRequestDispatcher` 进入统一结算。

### 11.3 组装校验

以下错误应尽量在组装阶段暴露：

- 未注册 damage handler 或 provider。
- scaling ref 不存在或倍率 payload 格式错误。
- 不支持的元素、属性 key、主攻击标签、附加攻击标签、打击类型或远近类型。
- `reaction.` 标签缺少显式映射、Profile 引用了未注册公式，或同一主标签重复注册；未注册的非反应标签默认通用公式。
- provider 声明了非法属性读取或伤害阶段写入。
- 重复 provider key 或非法 stacking group。

动态运行时请求仍需执行模型级校验，但不能把可提前发现的 content 错误延迟到战斗中。

## 12. 错误模型

| Error | code | 场景 |
| --- | --- | --- |
| `DamageValidationError` | `damage_validation_error` | 请求、term 或结果模型字段非法 |
| `UnsupportedDamageElementError` | `unsupported_damage_element` | 元素不受支持 |
| `DuplicateDamageFormulaError` | `duplicate_damage_formula` | 同一种伤害类型重复注册完整公式 |
| `UnsupportedDamageFormulaError` | `unsupported_damage_formula` | 标签或请求选择的公式没有已注册实现 |
| `DamageFormulaInputError` | `damage_formula_input_error` | 请求不满足当前公式的输入契约 |
| `DamageSourceNotFoundError` | `damage_source_not_found` | 来源运行态不存在 |
| `DamageTargetNotFoundError` | `damage_target_not_found` | 目标运行态不存在 |
| `InvalidDamageScalingError` | `invalid_damage_scaling` | 倍率或 scaling 属性非法 |
| `DamageProviderViolationError` | `damage_provider_violation` | provider 越权读取、写入或返回非法 term |
| `ConflictingDamageModifierError` | `conflicting_damage_modifier` | stacking 组未注册或组内冲突 |
| `CriticalDecisionError` | `critical_decision_error` | 暴击决策无效或与请求不兼容 |
| `DamageResolutionError` | `damage_resolution_error` | 结果非有限数等结算失败 |

application 组装层将资产和 content payload 错误转换为现有 assembly 错误或专用伤害装配错误。

## 13. 测试策略

### 13.1 单元测试

`tests/unit/core/systems/damage/` 至少覆盖：

- 单属性缩放和多属性缩放。
- component 倍率百分比修饰与倍率加值。
- 固定基础伤害加值。
- 元素增伤与伤害专用增伤的聚合。
- 不可暴击、固定暴击和固定不暴击。
- 同等级无修饰防御区。
- 减防与无视防御的独立输入。
- 负抗性、普通抗性、`0.75` 边界和高抗性。
- 多个 final multiplier 的稳定顺序。
- stacking group 的 applied/rejected term。
- bool、NaN、无穷、空 key、非法主体和未知元素。
- trace level 不改变最终数值。

### 13.2 集成测试

至少跑通：

```text
测试角色 Action
-> ActionImpactPoint
-> DamageImpactSpec
-> Space AOE 目标解析
-> 目标级 ElementalImpactRequest
-> DamageProfile
-> DamageRequest
-> DamageResult
-> DAMAGE_RESOLVED
```

多目标案例必须验证实际 AOE 命中几个目标就产生几份 DamageRequest，结果顺序稳定且每个目标独立读取抗性。Reaction 生成的 Damage Impact 必须复用同一链路。

### 13.3 浮点与 golden

浮点测试优先使用明确的绝对或相对容差；core 不为了让断言通过而提前舍入。直接伤害回归 golden case 的来源与验收基线仍待正式契约来源建立（见 15.6）。

## 14. 测试探针与正式内容边界

`test_a` / `test_b`（`content/test/characters/reaction_probe`）是开发期测试内容，其攻击标签走默认通用公式，不再注册显式 DamageProfile。测试探针不代表真实角色机制完成；正式内容按“主攻击标签 -> 默认通用 / 显式反应映射”链路工作。

## 15. 未决与后续

> 状态：未决。以下事项不作为当前生产真值，完成对应契约或迁移后同步更新本文。

1. **`formula_key` 与默认通用兜底已落地**：`DamageProfile` 不再持有 `profile_key`，公式键为 `damage_formula.*` 字符串常量；未注册的非反应标签默认通用公式，`reaction.` 标签未注册报错。后续如需新增公式结构，只需扩展键常量与公式注册表。
2. **自由 `params.damage` 兼容入口已移除**：请求统一走 `DamageImpactSpec`，不再保留双入口。
3. **`DamageRequest.tags` 主/附加标签合并**：Impact 层已区分主攻击标签与附加攻击标签，request 层当前合并为单一 `tags`；恢复独立字段后再明确 request 层主次语义。
4. **`strike_type` / `range_type` 审计边界**：当前由 Impact 与 Reaction 消费，尚未复制到单目标请求与 `DAMAGE_RESOLVED` 审计；如需进入审计需显式增加字段。
5. **伤害属性快照契约**：当前默认实时查询；独立、显式的伤害属性快照尚未设计，不能复用目标选择快照字段。
6. **直接伤害 golden case**：旧项目迁移基线因来源不满足 golden 可信要求已删除；直接伤害回归待正式契约来源重新建立。
8. **随机暴击**：生产环境带种子随机 `CriticalDecisionProvider` 与回放契约尚未确认；当前仅注入式固定决策。
9. **目标生命**：当前角色对场景目标伤害以 `DAMAGE_RESOLVED` 结束，不作用于目标生命。
