## 当前协调能力

当前 `ElementalStateFrameCoordinator` 可同步 Aura、ICD 与注入的 ReactionState，且在 Store 声明必需处理帧时拒绝跨越。它会在 Aura 自然衰减后移除失效感电，并把 due `ElectroChargedState` 物化为稳定 `ScheduledReactionRootWork`；同帧重复规范化复用既有 Frame Record。`FrozenStateLinkBatchCoordinator` 只在 Aura 与 ReactionState 计划、主体和 Link 前值均完整匹配后提交二者；它不拥有冻结时长、衰减或刷新公式。

`GeneratedDamageImpactEffect` 已使用统一 `Element`（含物理）。感电使用专用的 13 米 X/Z 传播选择：Space 只返回候选，协调器冻结目标顺序并组合关系、伤害能力和正水 Aura 条件；已感电目标仅在 Gate 允许后消费水雷、接管来源并同步未来周期。周期 root 先于同帧 Action/Impact，由 `ElementalSettlementCoordinator` 作为唯一帧入口耗尽。目标生命周期通过 `end_reaction_subject_lifecycle()` 的窄入口移除感电状态；主目标在周期结算时失去伤害资格也会停止后续调度。

`ElementalSettlementWorkQueue` 以已提交 root 为边界，按 work id 去重，冻结当前 round，并只接受严格更大的子 round。生产固定 `maximum_settlement_round = 64`，允许后续 round `1` 至 `64`；child batch 固定按父 work 的下一 round 入队，入队 round `65` 抛出稳定超限错误。`SimultaneousElementApplicationBatch` 在 batch 级保存共同 `source_ref`；策略 Registry 只接受归属当前策略的强类型结果。生产支持无 Aura、恰好一水一雷的共存和无 Aura 等量水冰整体冻结，已有 Aura、重复元素或未注册输入稳定失败，不把任一元素伪造成先手。

`ElementalInteractionCoordinator` 会把 `ReactionResolution.generated_impact_batches` 保留给后续队列。协调器冻结 `SwirlEmissionSelection` 的 6 米目标，并在一个跨目标原子 batch 中执行单元素或已注册的同帧多元素施加：水雷使用各自常规 Aura Profile 形成共存，等量水冰以完整原始预算形成冻结 Aura/State Link；范围锚点排除，关系、Damage capability 和 Aura capability 分别判定，缺少一种能力只阻止对应分量。无伤害组件的单元素生成施加会进入既有 Aura、Reaction 与 State planner；多元素 batch 中的 Damage component 同样独立准备 Gate 和 Damage，不删除元素施加。

`Damage component` 通过 `ReactionGeneratedImpactDamageInputAdapter` 取得由 Reaction 机制声明的 `TransformativeReactionInput`，协调器不持有伤害倍率。中心 `GeneratedDamageImpactEffect` 必须显式携带正的 `transformative_base_multiplier`，协调器不按 reaction key 推导或补全。它在同一个派生 batch 内准备 Gate、Aura、Reaction、State 与 Damage；Gate 只条件化 Damage，二次蒸发/融化只为同一 `generated_impact_ref` 创建 `SecondaryAmplifyingReactionInput`，其元素精通取自 batch 的捕获来源。普通超载 Effect 声明 `StrikeType.BLUNT`，Effect group 协调事务以此观察冻结状态并产生碎冰子 Effect，不实现击退、硬直、削韧或位移。扩散 Definition、Damage Profile、Gate、Aura Profile 与适配器均由生产 assembler 显式注册。

燃烧与感电周期使用 `ScheduledReactionRootWork` 判别联合和显式 adapter registry；公共协调器不按 burning key、state key 或目录顺序增加具名分支。燃烧的状态计划、草特殊消费、周期伤害与施火、双 Aura 并行消费及失效清理由机制侧强类型适配器声明，具体边界见[燃烧反应设计](../系统/元素反应/反应/燃烧反应设计.md)及[燃烧反应契约](../../契约/元素反应/反应/燃烧反应契约.md)。

激化通过显式 adapter registry 接入 Quicken 建立、覆盖、终止和当前 Impact 调整。协调器只编排步骤、转换强类型模型和封存计划，不按 reaction key 实现激化公式、覆盖规则或燃烧类草消费；稳定边界见[激化反应设计](../系统/元素反应/反应/激化反应设计.md)及[激化反应契约](../../契约/元素反应/反应/激化反应契约.md)。

绽放通过显式 Bloom adapter 接入草原核和蔓生弹流程。协调器只负责把上游已经解析的 `contacted_core_refs`、`associated_impact_ref` 与已提交 Impact 证据组合成原子终态计划，并校验 State/Space binding；Reaction 机制拥有终态、容量、锁敌和 Damage Effect 声明。正雷或正火请求缺少证据、证据帧/来源/元素/元素量不一致，或引用不是活动核心时以 `BloomCoreTriggerError` 在提交前失败。超绽放只接收 `ARRIVED | LOST` 窄结算，不在公共协调器中实现投射物运动。

## 1. 定位

元素反应协调包位于：

```text
core/coordination/elemental_reaction/
```

它连接元素附着 ICD、Aura、Reaction、Damage、Space 和状态等领域，但不拥有任何长期领域状态，不实现任何反应、元素量、伤害或空间公式。

目标结构：

```text
ElementalStateFrameCoordinator
-> 同步规范化 Aura 与 Reaction
-> 生成本帧周期根工作

ElementalInteractionCoordinator
-> 解析一个具有共同因果来源的 ElementalInteractionBatch
-> 统一准备、校验和提交领域计划

ElementalSettlementCoordinator
-> 驱动本帧工作队列
-> 依次执行周期根、原始 Impact 和同源后续轮次
```

三个 coordinator 各自只处理一个明确流程：

- Frame coordinator 处理跨域时间一致性。
- Interaction coordinator 处理一个原子元素交互批次。
- Settlement coordinator 只处理同帧工作排序、去重、轮次和因果链。

## 2. 设计目标

- Reaction 不依赖其他领域的 Runtime、Store、Request 或 Plan。
- 所有跨系统类型转换集中在协调包。
- 同一批次内后一个交互能看到前一个交互准备出的虚拟状态。
- 多目标、ICD、Aura、Reaction 和必须内联的外部状态变化保持原子。
- 当前 Impact 的关联伤害修正必须在 Damage 解析前确定。
- 传播、周期、实体触发和二次反应使用同帧工作队列，不使用 Event 递归。
- 帧顺序、目标顺序、反应 ordinal 和事实顺序可以稳定复现。
- 正常效果阻止与技术性失败明确分开。

## 3. 非目标

协调包不负责：

- 实现 Reaction Rule、选择优先级或元素量消耗公式。
- 实现 Aura 衰减、同元素叠加或精确元素量计算。
- 实现 ICD 序列、窗口或共享身份。
- 实现 Damage 公式、防御、抗性、暴击或精通收益。
- 保存冻结、激化、燃烧、感电、草露或反应实体机制状态。
- 保存 Space 索引、Buff Record、护盾或生命状态。
- 通过字符串动态拼装任意系统 pipeline。
- 将 EventEngine 作为当前结算入口。

## 5. 稳定输入

### 5.1 ElementalImpactRequest

```text
ElementalImpactRequest
├── impact_ref
├── frame
├── impact_order
├── source_ref
├── target_refs
├── damage_intent?
├── element
├── elemental_amount
├── icd_sequence_key?
├── icd_tag_key?
├── attack_tag_key
├── additional_attack_tag_keys
├── strike_type
├── range_type
└── source_context
```

规则：

- `impact_ref` 标识一次已经完成 AOE 目标解析的 Impact；同一次多目标 Impact 共享该引用。
- 每个目标派生唯一 interaction request id 和 target order。
- `damage_intent` 表示 Impact 携带的伤害公式参数；元素施加由 `element`、`elemental_amount` 和 ICD 标签/序列直接表达，不设置“是否允许 Reaction”开关。
- 第八版激化资格证据由协调器从类型化 `DamageImpactSpec.scaling_terms` 派生：至少一个倍率项的 `coefficient > 0`。仅有 `flat_base_damage`、零系数项或稍后加入的基础伤害固定加值都不能伪造该证据；无 `damage_intent` 时证据固定为否。
- `elemental_amount=0` 时仍可结算对应元素伤害，但不产生 Aura 应用或普通元素反应。
- 正元素量经过 ICD 后，与目标当前 Aura 决定普通元素反应；`strike_type=BLUNT` 与冻结状态共同提供碎冰候选。
- `attack_tag_key` 是主攻击身份，必须与附加攻击标签分开保存；Damage Profile 由主标签选择。
- 附魔和元素转换必须在构造最终 ElementalImpactRequest 前完成；ICD key 不包含最终元素。

### 5.2 无伤害元素 Impact

没有伤害的元素施加继续使用同一个 `ElementalImpactRequest`：

```text
damage_intent = None
elemental_amount > 0
```

是否经过 Aura ICD 由 ICD 标签/序列是否存在以及对应 ICD 定义决定。只要 ICD 后实际元素量为正，就正常与目标 Aura 交互；传播、环境附着和反应生成的元素施加不使用来源类别或布尔开关阻止 Reaction。

## 6. 工作项与因果身份

```text
ElementalWorkItem =
    ImpactInteractionWork
  | ReactionPulseWork
  | ReactionEntityTriggerWork
  | ReactionGeneratedImpactWork
```

周期根进一步使用判别联合：

```text
ScheduledReactionRootWork =
    ElectroChargedTickRootWork
  | BurningCycleRootWork
```

`ScheduledReactionRootAdapterRegistry` 按工作变体类型和稳定 adapter key 显式注册。Frame coordinator 只接收 Reaction 已物化的不可变工作，Settlement coordinator 只通过注册 adapter 转换该工作；两者都不根据 reaction key 或 state key 推断机制。`BurningCycleRootWork` 可以同时携带 damage tick 与 pyro application 序号，但至少一个存在。

`BurningCycleRootWork` 保存 `work_id`、`frame`、`root_order`、`state_instance_ref`、`subject_ref` 以及可空的 `damage_tick_index`、`pyro_application_index`；两个 index 至少一个为正整数。其 work id 由 frame、state instance 与两个 index 确定性派生。

公共身份：

```text
work_id
root_work_id
parent_occurrence_id?
parent_effect_id?
scheduled_state_tick_cause?
frame
root_order
settlement_round
emission_order
target_order
```

稳定派生规则：

- root work id 来自原始 Impact、周期状态或实体触发身份。
- child work id 由 parent effect id、目标引用和 child ordinal 派生。
- 相同 work id 在同一次仿真中只能处理一次。
- 因果身份不使用随机 UUID；相同输入必须生成相同排序与审计引用。
- 即时 occurrence 与 scheduled state tick 使用判别式 cause；周期根不伪造 `parent_occurrence_id`。

## 7. 帧顺序

每帧元素流程固定为：

```text
1. ELEMENTAL_STATE_NORMALIZATION
2. SCHEDULED_REACTION_ROOTS
3. ROOT_ELEMENTAL_IMPACTS
4. ELEMENTAL_FRAME_FINALIZATION
```

具体顺序：

1. `ElementalStateFrameCoordinator` 把 Aura 与 Reaction 同步规范化到帧 `F`。
2. 按 `scheduled_frame -> scheduled root kind order -> state slot -> cycle index` 处理本帧周期根工作。
3. 每个周期根工作提交后，先耗尽其同源后续轮次，再处理下一个周期根工作。
4. 按 `impact_order` 处理原始 Impact。
5. 每个原始 Impact 提交后，先耗尽该 root 的同源后续轮次，再处理下一个 impact order。
6. 队列为空后完成本帧元素结算。

因此前一个完整因果链的状态对后一个根工作可见；同一次范围命中的全部直接目标仍在同一个 batch 中原子处理。

Aura 已确认的端点规则保持不变：

- 帧 `F` 的已有 Aura 先衰减，再处理本帧周期和命中。
- 在帧 `F` 归零的 Aura 对本帧后续工作不可见。
- 帧 `F` 新建的 Aura 从 `F+1` 开始自然衰减。
- 同帧工作之间不发生自然衰减。

Reaction 默认有限状态使用半开区间；到期帧先失效，默认不再产生同帧周期。经人工确认的具体反应例外必须由 StateReactionBehavior 明确表达并有 golden case。

燃烧在状态帧内固定先执行草特殊消费，再根据计划后草、燃元素投影判断状态是否继续；只有仍成立时才物化本帧 `BurningCycleRootWork`。该 root 内部先结算伤害，再生成周期火施加；因此草在本帧归零时不会留下本帧伤害或施火工作。

## 8. ElementalStateFrameCoordinator

### 8.1 输入与端口

```text
ElementalStateFrameCoordinator.normalize(context, frame)
```

```text
AuraFramePort
AuraIcdFramePort
ReactionStateInteractionPort（可选）
ReactionBoundEntityExpiryPort（可选）
DendroCoreExpiryCoordinator（可选）
```

协调器缓存每个已经完成的 `ElementalStateFrameRecord`，同帧重复调用直接返回原记录。推进前读取 Reaction 的 `next_required_frame`；请求帧跨过该必需帧时显式失败。

### 8.2 当前规范化流程

```text
检查 frame record cache 与 Reaction next_required_frame
-> 记录 Aura previous_normalized_frame
-> ReactionRuntime.update_frame(context, F)
-> AuraRuntime.update_frame(context, F)
-> AuraIcdRuntime.update_frame(context, F)
-> Space.update_frame(context, F)
-> 清理到期 FrozenState 与关联冻元素 Aura
-> 清理普通自然衰减后已经失去 QUICKEN Aura 的 QuickenState
-> BurningStateFrameAdapter 消费 REACTION_MANAGED 类草 Aura 并准备周期 root
-> 清理或推进 ElectroChargedState，并准备本帧周期 root
-> 处理到期绑定实体与草露生命周期 work
-> 建立并缓存 ElementalStateFrameRecord
```

普通 `STANDARD` Aura 衰减由 `AuraRuntime.update_frame()` 直接物化并提交；它跳过 `STATE_LINKED` 和 `REACTION_MANAGED` Component。Reaction 管理的 Aura 消费、Link 增删以及关联 State 的创建或删除继续通过专用 Aura/Reaction BatchPlanner 准备。

### 8.3 提交边界

当前帧规范化不是一份覆盖所有领域的统一 FramePlan。Reaction、Aura、ICD 与 Space 的普通时间推进按固定顺序调用各领域 `update_frame()`；需要同时维持 Aura/ReactionState Link 的步骤使用 `FrozenStateLinkBatchCoordinator`、`BurningStateLinkBatchCoordinator` 或 `QuickenStateLinkBatchCoordinator`：先校验两份计划及最终 Link 投影，再进入无回调提交阶段依次提交。

提交后：

- Aura、ICD 与已注入 Reaction 的 `normalized_through_frame` 都等于 `F`。
- linked component 和 state 不存在悬空关系。
- 感电等周期游标在对应 ReactionState 计划提交时推进，生成的 root 随后写入本帧 `ElementalStateFrameRecord`；后续规范化步骤失败会终止仿真，不执行补偿回滚。
- `next_required_frame` 指向下一个必须访问的帧。

Aura 对 `REACTION_MANAGED` Component 不执行普通衰减。`BurningStateFrameAdapter` 使用上一 Aura 规范化帧计算 elapsed frames，在 Aura 工作副本中执行精确类草消费，并与 ReactionState 计划统一校验和提交。燃烧的 `next_required_frame` 是下一伤害帧、下一施火帧和预计草耗尽帧的最小值，ReactionRuntime 不为计算该值反向查询 Aura 运行态。

### 8.4 跳帧

- Aura 自然衰减可以精确计算跨帧结果。
- Reaction 没有主动工作时可以随 Aura 一起跨帧规范化。
- 若区间内存在 Reaction `next_required_frame`，调度器必须先访问该帧。
- 跨过未处理 due frame 是结构化错误。
- 只有未来必须执行的工作延长仿真；被动存在的 Aura 或 Reaction 状态不延长仿真。

## 9. ElementalInteractionBatch

原子单位是具有共同因果来源的批次：

```text
ElementalInteractionBatch
├── batch_id
├── root_work_id
├── frame
├── root_order
├── settlement_round
└── ordered_interactions
```

批次划分：

- 一次原始 Impact 对全部直接目标形成一个 batch。
- 一次传播 effect 选中的全部目标形成一个 batch。
- 一次周期触发形成一个 batch。
- 一次实体触发及其直接目标形成一个 batch。

任一请求非法时整个 batch 不提交。不同 root 或不同 follow-up effect 不合并成同一事务。

## 10. 临时 Batch Planner

协调器为每个 batch 创建：

```text
AuraIcdBatchPlanner
AuraBatchPlanner
ReactionBatchPlanner
InlineEffectPlannerSet
```

Planner：

- 捕获各自 Store version 和前值。
- 只修改本 batch 的虚拟投影。
- 不写真实 Store、不发布事实、不调用外部回调。
- 后一个 interaction 读取前一个 interaction 准备后的虚拟状态。
- 只能 seal 一次；seal 后不可继续使用。
- 任一阶段失败时整体丢弃。

该模型同时满足批量原子性和同批次顺序，不需要协调器读取或复制领域 Record。

## 11. 单个 interaction 的准备顺序

按 interaction order 执行：

```text
1. AuraIcdBatchPlanner.prepare_impact()
   -> IcdResolution

2. AuraBatchPlanner.observe_application_or_state()
   -> 有 application 时使用基础强度和 ICD 系数计算实际施加观察值
   -> 始终返回当前虚拟 Aura 的中立观察

3. ReactionBatchPlanner.prepare_interaction()
   -> ReactionDraft
   -> 返回候选、步骤、元素变化语义和 required inline preflight

4. Coordinator 将元素变化语义转换为 Aura planner 输入

5. AuraBatchPlanner.apply_reaction_transition()
   -> ElementalTransitionResult
   -> 更新 Aura 虚拟投影

6. Coordinator 准备 Draft 声明的 required inline effects
   -> 转换为 ReactionInlineEffectObservation

7. Coordinator 将 Aura 实际变化转换为 Reaction observation

8. ReactionBatchPlanner.finalize_interaction(
       draft,
       observed_transition,
       inline_effect_observations,
   )
   -> ReactionResolution
   -> 更新 Reaction State/Gate 虚拟投影
   -> 形成 occurrence 与 effects

9. Coordinator 准备剩余 CURRENT_TRANSACTION effects

10. DamageImpactPlanningPort 使用当前 Impact 调整准备 DamageResult
```

`ReactionDecisionStep.state_planning_intents` 由显式注册的状态计划 adapter 在同一个 Reaction planner 虚拟投影中消费。它可表达无 occurrence 的燃烧维护，但不得由协调器根据具体 reaction key 临时构造。对于普通火与燃元素同时存在的目标，Reaction 输出共享输入预算的 `ParallelAuraConsumption`；Aura planner 在一个 transition 中并行准备两个分支，Reaction 仍只形成一个 occurrence 和一组效果。

第八版在 `ReactionDraft` 创建时冻结交互开始时的 Quicken 存在证据，供超激化或蔓激化候选读取；同一交互后续新建或覆盖的激元素不能反向触发当前 Impact 的附加反应。`QUICKEN + ELECTRO` 受草与 `QUICKEN + DENDRO` 受雷使用两个顺序 Step；`QUICKEN + CRYO` 受雷使用一个包含超导和超激化的并行 Step；`DENDRO + CRYO` 受雷先结算超导，再把剩余预算交给原激化。协调器保留 Reaction 已冻结的 step/occurrence ordinal，不自行重排。

特殊分支：

- ICD 系数为 `0`：提交 ICD 游标，不产生元素施加；若 `strike_type` 等稳定 Impact 字段可以触发现有 ReactionState，仍进入 Reaction 解析。
- `elemental_amount=0`：不产生普通元素施加；若打击类型可以触发现有 ReactionState，仍读取 Aura/Reaction 状态并解析非元素触发。
- 无现存 Aura 且无匹配 Reaction：Aura 处理普通新附着。
- 同元素施加：Reaction 返回无反应，Aura 执行同元素叠加。
- 无 damage intent 的元素施加：不调用 DamageImpactPlanningPort，但仍可产生 Reaction。
- Damage intent 存在但实际元素量为 `0`：不能获得元素施加型反应修正，但仍可能由打击类型触发碎冰等已注册规则。

## 12. Reaction 与 Aura 类型转换

协调器只做结构化适配：

```text
Reaction.ElementalTransitionEffect
-> AuraReactionTransitionRequest

Aura.ElementalTransitionResult
-> Reaction.ObservedElementalTransition
```

禁止：

- 在 adapter 中实现反应系数、消耗优先级或残留公式。
- 在 adapter 中修正 Reaction Rule 的候选选择。
- 把 Aura Store、Record 或 MutationPlan 传入 Reaction。
- 把 Reaction StateRecord 传入 Aura。

adapter 必须保留 interaction id、component link、前后量、来源和 step ordinal，不能只传最终元素列表。

## 13. 队伍准入

```text
ReactionEligibilityReadPort
└── evidence_for(frame, team_ref) -> ReactionEligibilityView
```

当前临时实现的核心观察模型为：

```text
ReactionCapabilityEvidence
├── capability_key
└── provider_ref: ElementalSubjectRef(character)

ReactionEligibilityView
├── team_ref
├── frame
└── evidence: tuple[ReactionCapabilityEvidence, ...]
```

`application/assembly` 从角色 `ContentUnit.reaction_capabilities` 生成静态 `ReactionEligibilityReadPort`。Reaction 只读取 key 和 provider ref，不读取 TeamRuntime、角色资产或 content handler。

规则：

- 端口返回静态队伍组成提供的 capability 和 provider ref。
- Reaction 不获得 TeamRuntime、角色资产或 content handler。
- 月绽放只有存在 `reaction_capability:lunar_bloom` 且触发来源属于协调器提供的角色来源集合时进入严格水草候选；月感电仍只有存在 `reaction_capability:lunar_electro_charged` 时进入候选。
- capability provider 不自动成为 trigger source 或 effect owner，也不会仅因提供准入而进入反应角色参与者集合。
- capability view 在同一个 batch 内固定，不能因目标顺序变化。

元素交互协调器把同一帧的角色来源集合和 capability key 集合注入 `ReactionEvaluationRequest`。月绽放命中后，协调器在同一批次创建草露资源计划；该计划与 ReactionState、Damage Gate 使用共同 Store version 校验，再和 Aura、Space 计划一起进入无回调提交阶段。

## 14. 来源观察与快照

```text
ReactionSourceObservationPort
└── observe(requirement) -> ReactionSourceObservation
```

流程：

```text
ReactionDraft 声明 source read requirements
-> Coordinator 查询窄端口
-> 转换为 Reaction 自己的强类型 observation
-> Reaction finalize 保存动态引用或 captured basis
```

协调器不决定创建快照、触发快照或动态读取。它只执行 Rule 已声明的读取时点。读取结果的主体、frame、profile 和 requirement id 必须一致。

## 15. CURRENT_TRANSACTION Effect

必须内联准备的效果包括：

- 当前 Impact 关联伤害修正。
- 反应成立所必需的 linked Aura 与 Reaction 状态。
- 必须与反应同时创建的空间实体。
- 失败时应使反应整体不成立的状态或控制效果。

对应端口返回不可变计划或纯解析结果。任一内联计划非法时整个 ElementalInteractionBatch 回滚。

正常免疫或不适用必须返回类型化 preflight observation。Rule 可以声明：

- 正常阻止不影响 Reaction 成立。
- 正常阻止使该候选不成立。

第二种情况必须在 Reaction finalize 前反馈，不能先形成 occurrence 再补偿。未被最终 occurrence 采用的 provisional inline plan 由对应 planner 丢弃，不进入 seal。

## 16. Damage 边界

### 16.1 当前 Impact 的关联伤害

Reaction 输出：

```text
CurrentImpactDamageAdjustment
├── target_impact_ref
└── amplifying_reaction_input

CatalyzeCurrentImpactDamageAdjustment
├── adjustment_ref
├── target_impact_ref
├── occurrence_ref
├── reaction_profile_key
├── trigger_element
├── reaction_multiplier
└── reaction_bonus
```

`DamageImpactPlanningPort` 负责把它转换为 Damage 领域输入：

- 增幅性质的调整进入当前 Damage Profile 所选公式的反应区。
- `CatalyzeCurrentImpactDamageAdjustment` 由专用 adapter 转换为同字段身份的 `CatalyzeReactionInput`，进入当前 Damage Profile 所选 `damage_formula.catalyze_additive`。协调器不读取等级、元素精通或等级系数，也不计算基础伤害附加值。
- 无反应时保持原 Damage intent。
- Reaction 不选择 Damage Profile 或公式，Damage 不重新判断反应是否成立。

Damage 解析是纯准备步骤；若输入非法，在任何 Store 提交前失败。`DamageResult` 在元素状态完整提交后才作为事实发布。

### 16.2 反应生成的新伤害 Impact

Reaction 在处理当前 Impact 时新产生的伤害统一输出 Reaction-owned Damage Effect，由协调器转换为普通 Damage Impact，并使用 `NEXT_SETTLEMENT_ROUND`。普通剧变伤害使用 `GeneratedDamageImpactEffect`；反应月曜伤害（月感电雷暴云攻击、月结晶月笼谐奏）使用 `LunarReactionDamageImpactEffect` 或专用攻击 Effect。月绽放不使用该路径：

```text
GeneratedDamageImpactEffect
-> ReactionGeneratedImpactWork
-> 同帧下一 settlement round
-> Impact / Space 解析实际目标
-> 每个目标进入相同 ElementalImpactRequest 与 DamageRequest 流程
```

月绽放反应本身不产生伤害；角色月绽放伤害由角色技能消费草露后以 `LunarReactionDamageInput(mode=CHARACTER_DIRECT)` 进入统一 Damage Handler。`LunarReactionDamageImpactEffect` 已由月结晶谐奏路径使用：三枚月笼各自声明独立复合伤害 Effect，元素量恒为 `0`，不产生元素附着。

月曜 Effect 只携带稳定角色来源、父 occurrence、反应 Profile 和效果输入；协调器读取队伍角色等级并构造 Damage 侧参与者输入，不能计算最终伤害。当前月曜 Damage Profile 已接入 assembler，生产公式已按资料注册（等级基数表、`6 × EM / (EM + 2000)` 以及月绽放 `1.0`、月感电 `3.0`、月结晶 `1.6` 基线倍率）；测试覆盖仍可显式注入替代数值。月绽放不产生反应伤害，因此没有反应伤害 Gate；角色技能伤害走技能自身的伤害规则。

Reaction 不直接构造 `DamageRequest`，也不存在 `ReactionDamagePort` 专用公式入口。反应伤害通过稳定主攻击标签选择 Damage Profile；其 `elemental_amount` 与普通 Action Impact 语义相同，`0` 表示只有元素伤害而无元素施加。

### 16.3 伤害应用

Damage 解析完成后：

- 角色目标进入现有角色受伤协调器。
- 目标生命系统在实现后使用对应的类型化应用流程。
- 护盾、生命和死亡结果不反向修改已经成立的 Reaction occurrence。
- 伤害导致主体失效时，生成新的 ReactionLifecycleNotice 工作，不通过 Event handler 直接清理。

第七版提供通用 `ReactionSubjectUnavailableNotice` 的计划入口及 Burning adapter：同一事务移除 `BurningState`、燃元素和相关 Link，并停止未来根工作。目标 Health/Lifecycle 生产运行时尚不存在，因此本版不增加虚假的死亡检测调用者；未来由真实上游生命周期能力生成该通知。

## 17. 状态、控制与空间适配

### 17.1 状态与控制

```text
ReactionStatusEffect -> ReactionStatusPort
ControlEffect        -> ReactionControlPort
```

adapter 负责映射到对应领域请求。Reaction 自身持续状态不经过该端口，直接进入 ReactionMutationPlan。

### 17.2 空间实体

```text
SpatialEntityCreationEffect -> ReactionSpatialPlanningPort.prepare_create()
```

Space 拥有位置、空间实体和空间生命周期；Reaction 拥有实体的反应机制状态。需要两边绑定时必须在同一 CURRENT_TRANSACTION 中准备和提交，并通过稳定 binding ref 关联。

第六版普通结晶使用此入口创建 `REACTION_OBJECT`。Reaction 先形成未提交的 occurrence、成立 Gate、`CrystallizeShardState` 与确定性空间创建声明；协调器冻结目标锚点的位置和朝向后，通过 Space 的无副作用计划接口准备实体创建。Aura、ICD、Reaction 与 Space 的所有计划须在第一次写入前完成 binding、完整前值与版本校验，任何技术冲突都终止整个 batch，不做补偿写入。

晶片到期由 `ReactionBoundEntityExpiryCoordinator` 处理“Reaction State 终态 + 已绑定 Space Entity 删除”的单一流程。`CrystallizeShardPickupCoordinator` 由生产组装暴露，按 `operation_id` 幂等协调 Reaction、Space 与 Shield：在第一次写入前统一预校验 `picked` 终态、实体删除和 `ShieldGrantPlan`，再无回调提交三方并发布事实。它不读取距离、碰撞或物理拾取资格；默认保护范围为 active team。发布事实时协调器同时保护 Reaction、Space 与 Shield，订阅者不能反向修改当前批次领域状态。

普通结晶的完整候选顺序、状态生命周期和拾取授盾契约见[结晶反应设计](../系统/元素反应/反应/结晶反应设计.md)与[结晶反应契约](../../契约/元素反应/反应/结晶反应契约.md)。

### 17.3 范围查询

ReactionTargetSelection 由 adapter 转换为空间查询：

- 查询只返回候选主体。
- 结果按距离、稳定实体 id 和明确 tie-break 排序。
- 命中资格、Reaction 匹配和最终效果仍由后续 batch 决定。
- Reaction 不维护第二份空间索引。

范围参数来自 Reaction 的强类型选择，不在协调器内固定为 5 米。第七版燃烧使用 X/Z Circle 半径 `1.0`、包含锚点，并按距离与稳定主体引用排序；Effect group 计划时一次冻结全部合法敌对且具备 Damage capability 的目标。

## 18. 同帧 Settlement Queue

### 18.1 排序

队列使用：

```text
frame
-> phase
-> root_order
-> settlement_round
-> cause ordinal
-> emission_order
-> target_order
-> work_id
```

每个 root 的 follow-up chain 在进入下一个 root order 前耗尽。一个范围 effect 的多目标仍作为一个 batch，而不是按队列拆成多个独立事务。

`cause ordinal` 对 occurrence 使用 occurrence ordinal，对 scheduled state tick 使用 `state slot -> tick kind -> tick index`。两者不互相冒充；相同 cause 必须导出相同 work identity。

Reaction Damage Gate 的请求、解析和 Record 同样保存该 `ReactionEffectCause`。协调器只能透传 cause 与 effect identity；不得为周期工作构造假的 parent occurrence。结晶成立 Gate 继续只接受真实 occurrence。

### 18.2 轮次

```text
root batch                  -> round 0
root 的直接 follow-up       -> round 1
follow-up 产生的新工作      -> round 2
...
```

`NEXT_SETTLEMENT_ROUND` 表示同帧下一轮，不表示下一帧。

### 18.3 循环保护

- work id 全局去重。
- parent/child 因果链完整保存。
- 单个 root 最大同帧轮次固定为 `64`，不进入 SimulationInput。
- 已提交 batch 产生的事实不可回滚；后续轮次失败只终止本次仿真，不补偿撤销已经发布的 Aura、Reaction、Damage 或跨领域事实。
- 超过上限抛出 `ElementalSettlementRoundLimitError` 并终止本次仿真，不静默截断。
- 队列不接受 Event callback 直接写入。
- 只有已提交 batch 产生的 Effect 才能进入下一轮。

### 18.4 第二版 round 1 Effect group

第二版一个 `ReactionEffectGroup` 对应一个原子 batch。协调器只执行一次范围查询，冻结关系、capability 和 `target_order`；Damage 与 Status Effect 共享候选，但按 capability 形成各自子集。Damage Effect 声明 `strike_type` 时，同一事务还为具备 Aura capability 的候选准备状态型 Reaction、Aura 和 State 计划；超载钝击命中冻结目标产生碎冰，碎冰 Damage Effect 只进入父 work 的下一 settlement round。

准备顺序：

```text
work / parent / effect identity
-> anchor 与范围候选
-> 目标资格与稳定排序
-> strike Reaction / Aura / State plan
-> Reaction Damage Gate plan
-> Buff plan
-> Damage records
-> batch record 草案
-> 全部 seal / validate
```

固定提交顺序：

```text
enter ElementalSettlementCoordinator mutation guard
-> ReactionPort.commit_prevalidated(reaction_plan)
-> AuraPort.commit_prevalidated(aura_plan)
-> ReactionPort.commit_prevalidated_store_mutation(gate_plan, state_plan)
-> BuffPort.commit_prevalidated(buff_plan)
-> DamagePort.commit_prepared_records(damage_records)
-> build ElementalInteractionBatchRecord
exit mutation phase
```

目标关系不适用、缺少目标级 capability 和 Gate blocked 是类型化正常阻止。缺少系统端口、Definition、Profile、adapter，或 capability Provider 声明支持后仍无法准备领域计划，是技术错误。Gate 只阻止对应反应 Damage；超导 Status Effect 独立准备，超载钝击命中语义及其碎冰判定也不由超载 Damage Gate 撤销。

## 19. Batch seal、校验与提交

全部 interaction 完成后：

```text
IcdPlan = IcdPlanner.seal()
AuraPlan = AuraPlanner.seal()
ReactionPlan = ReactionPlanner.seal()
InlinePlans = InlineEffectPlannerSet.seal()
DamageResults = DamageImpactPlanningPort.seal()
```

统一校验：

- batch、frame、root 和 interaction identity 一致。
- request id、application id、occurrence id、effect id 和 order 唯一。
- Icd、Aura、Reaction Store version 与完整前值有效。
- Reaction expected transition 与 Aura actual transition 一致。
- linked Aura、Reaction state 和 Space entity 不会悬空。
- CurrentImpactDamageAdjustment 指向本 batch 的真实目标级 Impact 和关联伤害。
- inline external plan 与 effect identity 一致。
- DamageResult 引用已完成的 Reaction resolution。

固定提交顺序：

```text
enter ElementalInteractionCoordinator mutation guard
-> IcdPort.commit_prevalidated()
-> AuraPort.commit_prevalidated()
-> ReactionPort.commit_prevalidated()
-> Inline ports commit_prevalidated()（稳定端口顺序）
-> build ElementalInteractionBatchRecord
-> exit mutation phase
```

第一次写入前必须排除所有正常业务失败。commit 期间禁止属性查询、空间查询、handler、重新计算、Event 和同步重入。

若某个端口不能保证预校验后无业务失败，必须改为 copy-on-write 计划或从 CURRENT_TRANSACTION 移出，不能依赖补偿写入。

上述通用顺序用于 round 0 和未来 current-transaction Effect。第二版 round 1 Effect group 使用第 18.4 节的 Reaction Gate、Buff、Damage 顺序；两者都必须在第一次写入前排除全部技术错误。

## 20. 事实顺序

完整提交后按以下顺序发布：

```text
1. AURA_ICD_RESOLVED（interaction order）
2. Aura 领域事实（interaction order、component 稳定顺序）
3. REACTION_STATE_CHANGED（slot 稳定顺序）
4. REACTION_RESOURCE_CHANGED（resource key 稳定顺序）
5. REACTION_OCCURRED（occurrence ordinal）
6. CURRENT_TRANSACTION 外部领域事实（固定端口顺序）
7. DAMAGE_RESOLVED（Impact 与 target order）
8. ELEMENTAL_INTERACTION_RESOLVED
```

规则：

- 事实内容由领域根据已提交回执构造；协调器只决定跨领域顺序。
- `ELEMENTAL_INTERACTION_RESOLVED` 保存 batch 关联记录，不复制完整领域状态。
- follow-up work 在 batch commit 时已经冻结，但只在当前事实发布完成后开始处理。
- Event handler 不能修改当前队列、planner 或 Store。
- 下游需要响应事实时只能产生明确的下一轮命令，并由相应调度入口接收。

第二版 round 1 不发布 Gate 专属事实。普通路径固定发布 `BUFF_REMOVED`、`BUFF_APPLIED`、`DAMAGE_RESOLVED`、`ELEMENTAL_INTERACTION_RESOLVED`；超载钝击产生碎冰时，在 Buff 与 Damage 事实之前依次发布 Aura 交互、`REACTION_OCCURRED` 和 ReactionState 变化事实。没有对应领域变化时跳过该类事实；所有目标正常阻止时仍发布最终元素交互记录。

`current_impact_adjustment_refs` 必须按稳定 adjustment ref 升序保存；没有当前 Impact 调整时序列化为空 tuple。第八版不为激化增加另一条平行批次记录字段。

## 22. 正常结果与失败

正常结果：

- 无 Reaction，只有 Aura 附着或同元素叠加。
- ICD 系数为零。
- 没有 application intent，只有 Damage。
- 月反应准入不满足而普通候选继续匹配。
- Effect 因免疫、目标为空或不适用被正常阻止。
- 第二版目标关系不是 hostile、目标缺少对应 capability 或 Damage Gate blocked。
- 独立伤害为零或被护盾完全吸收。

错误：

- 任一 planner、plan、adapter 或 identity 不一致。
- 未规范化帧、帧回退或跳过 required frame。
- Reaction candidate 歧义。
- Aura 实际变化与 Reaction Draft 不一致。
- 缺少系统 capability 端口、profile、definition 或 effect adapter 的组装契约。
- capability Provider 声明支持目标后，对应领域仍不能准备计划。
- stale plan、重复 operation、重复 work id 或悬空 link。
- commit 阶段出现领域业务错误。
- settlement round 超限。
- coordinator 同步重入。
- Quicken Aura/State/Link 投影冲突：`QuickenStateLinkConflictError` 或 `QuickenAuraCoverageConflictError`。
- 同一目标 Impact 存在重复、冲突或不匹配的激化调整：`CatalyzeImpactAdjustmentConflictError`。
- 绽放核心接触缺少已提交 Impact、Impact 证据不一致、State/Space binding 冲突或蔓生弹结算非法：`BloomCoreTriggerError`；这些错误发生在任何计划提交前。

协调器不能捕获宽泛异常并降级成无反应、无 Aura 或无效果。

## 23. 组装

目标顺序：

```text
创建 AuraIcdRuntime
-> 创建 AuraRuntime
-> 创建 ReactionRuntime 与 Registry
-> 创建 Reaction eligibility/source read ports
-> 创建 Damage、Status、Control、Space、state planning 与 scheduled root adapters
-> 创建 ElementalStateFrameCoordinator
-> 创建 ElementalInteractionCoordinator
-> 创建 ElementalSettlementCoordinator
-> 注入整帧 Simulator/World
```

组装阶段校验：

- Aura、Reaction 使用一致的 `ElementalSubjectRef` 和 link 类型。
- 所有 ReactionEffect 变体存在明确 adapter。
- 所有 `state_planning_intents` 和 `ScheduledReactionRootWork` 变体存在唯一明确 adapter。
- reaction profile 到 Damage 公式输入的映射完整。
- 月反应 capability 存在 content provider。
- Source observation profile 存在读取 schema。
- 空间实体 profile、状态 profile 和控制 profile 可解析。
- `MAX_SAME_FRAME_SETTLEMENT_ROUNDS` 使用引擎固定值，不从资产或配置覆盖。
- Quicken establishment、coverage、termination 三种 intent 各有唯一 adapter，Quicken Link validator 已注册；不得使用一个通用 Aura-state transition adapter 兜底。
- `CatalyzeCurrentImpactDamageAdjustment` 存在唯一 Damage adapter，且目标主攻击标签可唯一解析到 `damage_formula.catalyze_additive`；不注册 `DamageReactionCapability.CATALYZE_ADDITIVE`。

## 24. 验证矩阵

### 24.1 帧与时间

- Aura 与 Reaction 同步规范化。
- Aura 在帧开始归零后，本帧周期和命中均看不到该 component。
- 周期根完整因果链先于 root impacts。
- 前一 root 的完整连锁先于下一 impact order。
- 不能跨过 Reaction next required frame。
- 到期帧默认不触发周期；Gate 在 ready frame 可用。

### 24.2 批量事务

- 同一多目标 Impact 共享 impact ref、每个目标使用不同 interaction id。
- batch 后项看到前项虚拟 ICD、Aura 和 Reaction 状态。
- 任一目标计划失败时三个 Store 和 inline Store 都不变。
- stale plan 与重复 work 被拒绝。
- commit 阶段无查询、计算、回调和业务错误。

### 24.3 Reaction 与 Damage

- 元素伤害但 ICD 为零时没有元素施加型 Reaction；`strike_type=BLUNT` 等已确认 Impact 字段仍可触发对应状态型 Reaction。
- 无伤害元素施加可以触发 Reaction。
- 当前 Impact 修正进入关联 DamageResult。
- 激化只在交互开始已有 Quicken、正元素施加成功、关联 scaling term 至少一项系数为正且 Profile 选择激化公式时进入 `CatalyzeReactionInput`；无伤害、仅 flat、零倍率和通用公式路径均稳定拒绝或不产 occurrence。
- `CatalyzeReactionResolution.base_damage_addition` 与 `DamageResult.base_damage_additions` 中对应值一致，实时 EM trace 可审计。
- 独立伤害进入下一轮且默认不附着。
- 角色受伤应用不反向修改 occurrence。

### 24.4 持续、传播与实体

- linked Aura 和 Reaction state 同帧创建、刷新和移除。
- 周期游标与 due work 原子推进。
- 燃烧同帧先草消费与继续性判断，后伤害，再周期施火；草耗尽帧不遗留周期工作。
- 周期火使用 scheduled cause 与捕获式来源，不伪造 occurrence 或实时观察。
- 普通火与燃元素并行消费共享输入预算，只形成一个 occurrence。
- 激元素独立自然衰减，覆盖保留 Aura/State/Link/贡献身份；激元素与普通草进入同一 BurningState 后分别消费，并在 Link 集合变化时原子更新。
- 扩散类多目标传播形成新 batch。
- 实体创建与 ReactionEntityState 原子绑定。
- work 去重、稳定排序和 64 轮上限。

### 24.5 月反应

- 月感电有、无伊涅芙 capability evidence。
- provider、trigger source、state owner、effect owner 分离。
- 水岩可以进入月结晶候选，其他岩元素组合不进入。
- 月候选满足时排他替代对应普通候选。
- 月结晶无成立 Gate 与谐奏 Gate，只按共享累计次数触发；月笼飞行冷却由月笼 State 保存。
- 月结晶谐奏立即结算、零元素量，三枚月笼各自独立复合月曜伤害。
- 月绽放草露产生和当前代码已实现的连续恢复刷新均通过 Reaction resource plan；角色技能消费仍待后续角色机制切片。

### 24.6 事实与审计

- 事实只在全部 Store 提交后发布。
- 跨领域事实顺序固定。
- batch record、frame record 和 parent/child 因果链稳定序列化。
- Event 回调不能递归进入 coordinator 或队列。

## 25. 维护与扩展要求

- 新增协调流程前先确认它确实跨越两个以上领域，并具有明确的顺序、证据或事务需求。
- 新的 Effect、状态计划和 scheduled root 变体必须具有唯一强类型 adapter。
- 公共协调器不得根据 reaction key、state key 或目录顺序增加机制分支。
- 所有写入必须在第一次 commit 前完成目标冻结、版本、身份、前值、Link 和 adapter 校验。
- 新流程必须覆盖正常阻止、技术失败零提交、事实顺序、幂等和同帧轮次边界。
- 月绽放、月感电、月结晶均已注册 capability/严格签名/资源或状态 adapter；月感电还注册了雷暴云 `LunarStormCloudScheduledRootAdapter` 与逐目标 Gate，月结晶注册了月笼集合生成/复用、累计器与到期协调器。正式角色 Content、角色技能草露消费与角色月曜伤害入口仍待后续。
