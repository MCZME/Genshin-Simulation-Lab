# 伤害系统设计

> 状态：第一版非反应直接伤害、统一 Damage Impact、攻击标签到 Damage Profile 和增幅反应输入均已实现。第五版已把 `SecondaryAmplifyingReactionInput` 接入剧变公式：仅声明 capability 的扩散 Profile 可以使用捕获元素精通的二次蒸发/融化乘区，且完整审计已序列化并注册到生产组装。第八版激化完整公式、实时元素精通读取与强类型审计已进入生产组装；月曜伤害的单/复合输入、组分结算与审计已实现，生产公式已按已确认资料注册。月绽放反应不产生伤害，角色月绽放伤害由角色技能触发。
> 本文档同时记录当前公式实现和迁移后的稳定边界。具体游戏公式以旧项目回归用例和后续确认的 golden case 为验收来源，不以本文单独作为游戏机制真值来源。

最后更新：2026-08-07

## 1. 设计背景

当前项目已经具备：

- `core/attributes/` 的确定性属性查询、修饰项、依赖解析、审计和快照能力。
- `Action -> ActionImpactPoint -> ImpactRequest` 的影响请求链路。
- 角色等级、目标等级、目标抗性和多目标空间引用。
- content handler、impact factory 和 application 组装边界。

第一版已经把带结构化 `params.damage` 契约的 `ImpactKind.DAMAGE` 接入统一伤害结算入口。尚未提供真实倍率契约的测试或内容占位请求会保留明确的 ignored record，不会伪造伤害数值。

旧项目 `core/systems/damage/` 可以提供以下迁移参考：

- 多属性倍率组成基础伤害。
- 增伤、暴击、防御、抗性和最终聚合的分阶段计算。
- 每次伤害保存可追踪审计数据。
- `tests/unit/systems/test_damage_pipeline.py` 中的最小回归案例。

旧实现不直接迁移以下设计：

- 不复用可任意修改字符串字典的 `DamageContext.stats`。
- 不通过可变 `BEFORE_CALCULATE` 事件向计算上下文写入 Buff。
- 不使用全局 `random` 或未注入的随机状态决定暴击。
- 不让伤害系统负责空间广播、元素附着、生命扣减或日志持久化。
- 不继续使用显示名称作为属性、元素、攻击类型或乘区标识。

## 2. 第一版目标

第一版伤害系统负责：

1. 接收已经确定来源与目标的类型化伤害请求。
2. 查询结算帧的来源属性和目标属性。
3. 收集纯查询、无副作用的伤害修饰项。
4. 按稳定阶段计算非反应直接伤害。
5. 输出不可变、可审计的伤害结果。
6. 把伤害结果作为事实交给事件、结果记录和后续角色承伤接入层。

第一版明确不负责：

- 元素附着、元素反应和反应倍率。
- 目标当前生命、扣血、击败或死亡。
- 护盾吸收、减伤分摊或受击反馈。
- 治疗和能量。
- 月曜伤害、剧变反应等特殊伤害公式。
- 随机种子配置和生产环境随机暴击策略。
- UI 显示舍入和结果数据库 schema 扩展。

这些能力以后消费 `DamageResult` 或扩展独立结算 policy，不塞入第一版通用流水线。

## 3. 架构原则

### 3.1 伤害请求、属性和运行态分离

- Damage Impact 描述一次范围影响及其攻击、元素和 AOE 语义；Damage 系统只接收目标已经解析后的单目标公式请求。
- `DamageRequest` 描述一次伤害的结算契约，不保存最终数值。
- `AttributeResolver` 是属性真值入口，伤害系统不维护第二份角色面板。
- `DamageModifierProvider` 只返回结构化修饰项，不直接修改请求、属性或世界状态。
- `DamageResult` 只描述已经完成的数值结算，不直接扣减生命。

### 3.2 默认实时查询

第一版在 `ImpactRequest` 被结算的当前帧查询属性。

动作层的 `snapshot_on_emit` 当前只表示目标选择快照，不表示属性快照。伤害属性快照必须在未来通过独立、显式的伤害快照契约加入，不能复用目标选择字段产生隐式行为。

### 3.3 确定性优先

- 所有加法使用 `math.fsum`。
- 修饰项按稳定 key 排序。
- 结算器不使用全局随机数。
- 结算器不进行显示舍入。
- 相同输入、相同属性查询结果、相同暴击决策必须产生完全一致的 `DamageResult`。

### 3.4 事件是结果事实，不是可变计算入口

旧项目的 `BEFORE_CALCULATE` 允许 handler 直接修改共享 `DamageContext`，会使顺序、状态所有权和审计边界变得不稳定。

新设计中：

- 伤害修饰通过 `DamageModifierProvider` 查询。
- 动态机制实例的创建、刷新和过期由对应领域 Runtime 与 Store 管理。
- 伤害结算完成后发布不可变事实事件。
- handler 不在事件调用栈内递归触发并修改同一次伤害结算。

## 4. 模块边界

建议新增：

```text
core/systems/damage/
├── __init__.py
├── enums.py        # 元素、修饰阶段、暴击结果等稳定枚举
├── models.py       # DamageRequest、DamageQuery、DamageResult 等值对象
├── profiles.py     # 主攻击标签到 DamageProfile/完整公式的稳定映射
├── modifiers.py    # DamageModifierTerm、provider 协议和索引
├── policies.py     # 倍率区、增伤区、暴击区、防御、抗性等公式族 policy
├── formulas.py     # DamageFormula 协议、注册表和 GeneralDamageFormula
├── resolver.py     # session、modifier、公式选择和公共结果组装入口
├── handler.py      # 目标级 Damage Impact 到 DamageRequest/Result 的同步请求处理入口
└── errors.py       # 结构化伤害错误
```

职责约束：

- `core/systems/damage/` 可以依赖 `core/attributes/` 和少量 core 值对象。
- `core/systems/damage/` 不能依赖 `assets`、`content`、`application`、`infrastructure` 或 UI。
- `content/` 提供伤害请求工厂和修饰 provider，不实现全局伤害流水线。
- `application/assembly/` 负责收集 provider、构造索引并把 `DamageRequestHandler` 注入 `ImpactRequestDispatcher`。
- `infrastructure/results_sqlite/` 未来只持久化结果，不参与计算。
- 分析层可以消费审计结果做伤害构成和乘区分析，不重新计算真值。

不建议把实现放入泛化的 `core/systems/` 基类体系。当前项目没有统一 `GameSystem` 生命周期需求，伤害更适合作为明确协议和纯 resolver 组成的独立领域包。

## 5. 运行时流程

```text
Action / Reaction / 周期状态 / 空间实体
-> 产生 DamageImpactWork
-> Impact 使用 Action 索敌结果确定方向
-> Space 按 DamageImpactSpec.area 解析并冻结实际目标
-> 每个目标形成 TargetImpact
-> ICD、Aura 与 Reaction 处理元素、元素量、目标 Aura 和打击类型
-> 主攻击标签从 DamageProfileRegistry 取得 DamageProfile
-> 为每个目标构造单目标 DamageRequest
-> DamageResolver 创建一次 DamageResolutionSession
-> 收集 DamageModifierTerm
-> 按 DamageProfile.formula_key 从 DamageFormulaRegistry 选择完整公式
-> DamageFormula 编排对应计算区
-> 生成 DamageResult
-> 记录 DamageResolutionRecord
-> 发布 DAMAGE_RESOLVED 事实事件
-> 后续角色承伤 adapter 可交给 HealthRuntime 产生生命变化
```

一次 Damage Impact 命中几个目标，就按稳定 `target_refs` 顺序产生几份独立 `DamageRequest`。每个目标独立查询抗性、独立生成结果和审计，不共享可变计算上下文。

Reaction 新产生的伤害只负责创建新的 Damage Impact，并在同帧下一 settlement round 进入上述流程；Reaction 不直接构造 `DamageRequest`，Damage 也不区分 Impact 来自 Action 还是 Reaction。

## 6. 核心模型

### 6.1 Element（统一元素枚举）

元素语义统一使用 `core.elements.Element`，伤害领域不再维护平行枚举。第一版稳定值：

```text
physical
pyro
hydro
electro
cryo
anemo
geo
dendro
```

物理是伤害侧合法元素，但不参与元素交互；`aura_kind_for_element` 对物理返回 None。
元素值用于选择 `bonus.damage.*` 和 `resistance.*` 属性。第一版不接受 `none`、显示名称或自由字符串。

### 6.2 DamageScalingTerm

```text
DamageScalingTerm
├── component_key: str
├── attribute_key: AttributeKey
└── coefficient: float
```

规则：

- `component_key` 是一次请求内稳定且唯一的审计标识。
- `attribute_key` 必须由属性注册表支持，通常为 `stat.atk.total`、`stat.hp.max`、`stat.def.total` 或 content 私有属性。
- `coefficient` 使用小数倍率，例如 200% 保存为 `2.0`。
- bool、NaN 和无穷值必须拒绝。
- coefficient 是否允许负数由 damage policy 决定；第一版普通直伤要求非负。

多属性缩放通过多个 term 表达：

```text
基础伤害 = fsum(属性值 × 对应 coefficient)
```

### 6.3 DamageProfile

Damage Profile 把稳定主攻击标签映射到完整公式和请求约束：

```text
DamageProfile
├── profile_key
├── attack_tag_key
├── formula_key
├── allowed_modifier_stages
├── reaction_capabilities
└── input_policy
```

```text
DamageProfileRegistry
└── require_by_attack_tag(attack_tag_key) -> DamageProfile
```

规则：

- 主攻击标签是攻击身份和 Profile 查找入口；附加攻击标签不能替代主标签，也不能依赖集合遍历顺序选择公式。
- `formula_key` 只标识 Damage 内部完整公式结构，例如通用、激化、剧变或月反应公式。
- content 和 Reaction 不显式填写 `DamageType`；未注册主攻击标签或公式必须报错，不能静默降级。
- Profile 注册和攻击标签规范化在组装阶段校验，不使用显示名称作为运行时 key。
- `DamageReactionCapability.SECONDARY_AMPLIFYING` 只允许显式注册给扩散 Profile；handler 将该 capability 冻结到已构造的 `DamageRequest`，不能由上游自由声明。
- 第八版激化不新增 `DamageReactionCapability.CATALYZE_ADDITIVE`。主攻击标签唯一选中的 `DamageProfile.formula_key = damage_formula.catalyze_additive` 是激化资格的唯一 Damage 侧声明；公式与 capability 两套并行开关会形成可矛盾的重复真值。

### 6.4 DamageRequest

```text
DamageRequest
├── request_id: str
├── impact_ref: str
├── frame: int
├── damage_profile_key: str
├── formula_key: str
├── impact_key: str
├── attack_tag_key: str
├── additional_attack_tag_keys: frozenset[str]
├── strike_type
├── range_type
├── source_ref: AttributeSubjectRef
├── target_ref: AttributeSubjectRef
├── source_level: int
├── target_level: int
├── element: Element
├── scaling_terms: tuple[DamageScalingTerm, ...]
├── flat_base_damage: float
├── catalyze_reaction_input: CatalyzeReactionInput?
├── can_crit: bool
└── source_context: RuntimeSourceRef
```

规则：

- 来源第一版必须是角色主体，目标必须是目标主体。
- `damage_profile_key` 与 `formula_key` 必须来自主攻击标签解析出的已注册 Damage Profile，不能由请求方绕过注册表自由填写。
- `attack_tag_key` 保存主攻击身份；`additional_attack_tag_keys` 保存 Buff、被动、公式修饰和机制条件所需的附加身份。
- `strike_type` 和 `range_type` 从 Damage Impact 保留到单目标请求与审计；钝击是碎冰的稳定攻击侧证据。
- source/target level 必须来自组装后的运行态引用解析，不允许 content 用显示名称查找。
- `scaling_terms` 和 `flat_base_damage` 至少有一个能够产生基础伤害。
- `flat_base_damage` 是请求自身契约的一部分，不替代 Buff 提供的基础伤害加值。
- 主攻击标签和附加攻击标签用于普通攻击、重击、下落攻击、战技、爆发及 content 私有条件匹配；二者不得压平成无法区分主次的单一集合。
- request 构造后不可变。
- `TRANSFORMATIVE_REACTION` 仍拒绝普通 `AmplifyingReactionInput`。只有同时拥有 `secondary_amplifying_reaction`、已注册 Profile 和 `SECONDARY_AMPLIFYING` capability 的剧变请求可进入二次增幅；该输入的 `target_impact_ref` 必须与当前 `DamageImpactSpec.impact_ref` 一致。
- `CatalyzeReactionInput` 保存 `target_impact_ref`、`occurrence_ref`、`reaction_profile_key`、`trigger_element`、`reaction_multiplier` 与 `reaction_bonus`。它只能由协调器从 `CatalyzeCurrentImpactDamageAdjustment` 转换，content、自由 payload 和普通 Damage 请求不能直接填写。
- 关联伤害具备激化资格的结构化证据是 `DamageImpactSpec.scaling_terms` 至少存在一个 `coefficient > 0` 的倍率项。仅有 `flat_base_damage`、只有零系数项，或稍后由 `BASE_DAMAGE_FLAT_ADD` 修饰产生数值，都不满足该资格。
- 激化公式还必须校验 `CatalyzeReactionInput.target_impact_ref` 等于当前 Impact、触发元素等于当前伤害元素，且 Profile 选择了 `damage_formula.catalyze_additive`；任一不一致稳定失败。

Damage Impact 中的 AOE、元素量和 ICD 标签/序列字段在构造 `DamageRequest` 前已经由 Impact、ICD、Aura 与 Reaction 消费；DamageRequest 通过 `impact_ref` 关联完整 Impact 审计，不复制空间范围或 Aura 状态。

现有 `ImpactRequest.params` 只是待迁移的通用传输边界。进入伤害系统后必须转换成 `DamageRequest`，后续计算不得反复读取自由结构的 params。

### 6.5 DamageQuery

```text
DamageQuery
├── request: DamageRequest
├── source_attribute_context: AttributeQueryContext
└── target_attribute_context: AttributeQueryContext
```

属性查询 context 至少携带：

- 主攻击标签和附加攻击标签。
- 打击类型与远近类型。
- 本次 impact 的 `RuntimeSourceRef`。
- 对方主体引用。

来源属性查询的 `target_ref` 指向受击目标；目标属性查询的 `target_ref` 可以指回伤害来源。这样 provider 可以在声明依赖后实现“对特定目标增伤”或“来自特定来源时减抗”等条件。

### 6.6 DamageResult

```text
DamageResult
├── request_id: str
├── impact_ref: str
├── frame: int
├── damage_profile_key: str
├── formula_key: str
├── attack_tag_key: str
├── additional_attack_tag_keys: frozenset[str]
├── strike_type
├── range_type
├── source_ref: AttributeSubjectRef
├── target_ref: AttributeSubjectRef
├── element: Element
├── base_damage: float
├── base_damage_additions: tuple[BaseDamageAdditionResolution, ...]
├── damage_bonus_multiplier: float
├── crit_outcome: CritOutcome
├── crit_multiplier: float
├── reaction_multiplier: float
├── defense_multiplier: float
├── resistance_multiplier: float
├── official_damage: float
├── debug_multiplier: float
├── final_damage: float
├── component_results: tuple[DamageComponentResult, ...]
├── source_attribute_trace: tuple[AttributeResolution, ...]
├── target_attribute_trace: tuple[AttributeResolution, ...]
├── applied_terms: tuple[DamageModifierTerm, ...]
├── rejected_terms: tuple[DamageModifierTerm, ...]
├── catalyze_reaction_resolution: CatalyzeReactionResolution?
└── trace_metadata: Mapping[str, object]
```

`DamageResult` 必须不可变并包含足够信息，使测试和分析层能够解释最终值，而不是只保存一个 float。

二次增幅剧变额外保存 `SecondaryAmplifyingReactionResolution`，其中包含 Base Hit 的 target impact、二次 occurrence/profile、捕获 EM、精通加成、反应加成和最终二次倍率；基础剧变输入仍保留在 `reaction_details`，两者不互相覆盖。

第八版激化额外保存强类型 `CatalyzeReactionResolution`：`target_impact_ref`、`occurrence_ref`、`reaction_profile_key`、`trigger_element`、`source_level`、`level_multiplier_table_key`、`level_multiplier`、`elemental_mastery`、`mastery_bonus`、`reaction_multiplier`、`reaction_bonus`、`base_damage_addition` 与 `elemental_mastery_trace`。同一 `base_damage_addition` 还进入 `base_damage_additions` 审计投影，两处数值必须完全一致；本版不改变结果库 schema。

`final_damage` 仍是浮点真值。显示舍入、整数化或 UI 格式化不在 core 中进行。

## 7. 伤害修饰契约

属性 `ModifierTerm` 只修改属性，不能承担伤害专用乘区。伤害系统定义独立的 `DamageModifierTerm`。

### 7.1 DamageModifierStage

当前正式伤害 modifier 阶段：

```text
component_coefficient_percent_add
component_coefficient_flat_add
base_damage_flat_add
damage_bonus_add
defense_reduction
defense_ignore
crit_rate_add
crit_damage_add
```

语义：

| Stage | 作用 |
| --- | --- |
| `component_coefficient_percent_add` | 对指定 scaling component 的原始倍率做百分比放大 |
| `component_coefficient_flat_add` | 对指定 scaling component 的倍率直接加值 |
| `base_damage_flat_add` | 基础伤害合计后、增伤区前加入固定伤害 |
| `damage_bonus_add` | 与元素伤害加成进入同一加法区 |
| `defense_reduction` | 作用于目标防御区的减防比例 |
| `defense_ignore` | 作用于本次伤害的无视防御比例 |
| `crit_rate_add` | 只参与本次伤害的暴击率调整 |
| `crit_damage_add` | 只参与本次伤害的暴击伤害调整 |

调试倍率不属于 `DamageModifierStage`，只允许通过 `DebugDamageAdjustment` 构造注入；生产组装固定使用默认 `1.0`。

### 7.2 DamageModifierTerm

```text
DamageModifierTerm
├── stage: DamageModifierStage
├── value: float
├── provider_key: str
├── source_ref: RuntimeSourceRef
├── component_key: str | None
├── stacking_group: str | None
└── audit_tags: tuple[str, ...]
```

规则：

- component 阶段必须提供合法 `component_key`。
- 非 component 阶段不得提供 `component_key`。
- 百分比统一使用小数，例如 20% 保存为 `0.2`。
- stacking group 第一版沿用 `highest` / `lowest`，不支持依赖遍历顺序的 `latest`。
- term 不拥有持续时间、层数或刷新逻辑；这些生命周期属于提供 term 的领域实例。

### 7.3 DamageModifierProvider

```text
DamageModifierProvider
├── provider_spec
└── contribute(query, session) -> Sequence[DamageModifierTerm]
```

provider 必须：

- 无副作用。
- 显式声明可读取的属性和可能写入的伤害阶段。
- 不创建或移除机制实例。
- 不发布递归伤害请求。
- 不直接返回最终伤害。

`DamageResolutionSession` 向 provider 暴露受限的属性读取能力。provider 只能读取声明过的属性，违规行为在组装或运行时抛结构化错误。

未来 BuffRuntime 等领域运行时中的活动实例可以向伤害索引暴露 provider。静态武器或圣遗物效果也可以在组装阶段直接注册 provider。两者使用同一个查询接口，但生命周期来源不同。

## 8. 第一版普通直伤公式

本节定义实现结构和迁移基线。具体游戏数值仍需用 golden case 确认。

### 8.1 组件倍率

对每个 scaling component：

```text
final_coefficient =
    original_coefficient
    * (1 + fsum(component_coefficient_percent_add))
    + fsum(component_coefficient_flat_add)

component_damage = resolved_attribute_value * final_coefficient
```

### 8.2 基础伤害

```text
base_damage =
    fsum(all component_damage)
    + request.flat_base_damage
    + fsum(base_damage_flat_add)
```

### 8.3 增伤区

```text
damage_bonus =
    resolved bonus.damage.{element}
    + fsum(damage_bonus_add)

damage_bonus_multiplier = 1 + damage_bonus
```

第一版不允许增伤区隐式截断。若后续确认某些规则需要上下限，应由专用 policy 明确实现。

### 8.4 暴击区

```text
crit_rate = resolved stat.crit_rate + fsum(crit_rate_add)
crit_damage = resolved stat.crit_damage + fsum(crit_damage_add)

crit_multiplier =
    critical: 1 + crit_damage
    non_critical: 1
```

第一版不允许 `DamageResolver` 自己调用随机数。暴击结果由注入的 `CriticalDecisionProvider` 提供：

```text
CriticalDecisionProvider.decide(query, final_crit_rate) -> CritOutcome
```

测试使用固定返回 `critical` 或 `non_critical` 的 provider。生产环境的带种子随机 provider 需要单独评审随机种子和回放契约，在此之前不得使用全局 `random`。

当 `can_crit=false` 时，resolver 不调用 decision provider，结果固定为 `not_applicable`，暴击乘数为 `1`。

### 8.5 防御区

当前场景契约保存来源等级和目标等级，不保存敌人面板防御力。普通直伤防御 policy 应以双方等级为基础，并接收减防与无视防御修饰。

建议第一版 policy 接口：

```text
DefensePolicy.resolve(
    source_level,
    target_level,
    defense_reduction,
    defense_ignore,
) -> DefenseResolution
```

第一版确认公式：

```text
source_factor = source_level + 100
defense_change_factor = 1 - defense_reduction
defense_ignore_factor = 1 - defense_ignore
target_factor = (target_level + 100) * defense_ignore_factor * defense_change_factor

defense_multiplier = source_factor / (source_factor + target_factor)
```

注意：

- 旧项目无修饰时的等级 90 对等级 90 回归值为 `0.5`，可以作为第一条迁移 golden case。
- 防御减免与无视防御使用独立因子：`(1 - 无视防御) * (1 - 防御减免)`。
- 第一版要求减防与无视防御各自为非负有限数，不对组合结果做静默截断；若最终分母无效则抛出结构化结算错误。
- resolver 不应通过构造虚拟目标 `stat.def.total` 来重复表达等级防御公式。

### 8.6 抗性区

目标抗性从 `resistance.{element}` 实时查询，使用小数表示。

候选迁移分段函数：

```text
R < 0:
    resistance_multiplier = 1 - R / 2

0 <= R <= 0.75:
    resistance_multiplier = 1 - R

R > 0.75:
    resistance_multiplier = 1 / (1 + 4 * R)
```

该分段函数来自旧项目伤害流水线与审计系数实现，第一版至少需要覆盖负抗性、普通抗性、边界 `0.75` 和高抗性测试。

减抗应优先表现为目标 `resistance.*` 的运行时属性 modifier，而不是再在伤害系统中维护一套 `resistance_shred` 状态。

### 8.7 最终聚合

```text
result =
    base_damage
    * damage_bonus_multiplier
    * crit_multiplier
    * reaction_multiplier
    * defense_multiplier
    * resistance_multiplier

final_damage = result * debug_multiplier
```

其中 `result` 是正式公式伤害，会作为 `official_damage` 进入审计；`debug_multiplier` 默认为 `1.0`，不从 content provider、资产 payload 或 `SimulationInput` 读取。

结果必须是有限数字。出现 NaN、无穷值或不允许的负最终伤害时抛出结构化错误，不静默修正。

## 9. 审计与快照

旧项目区分 `[R]` 静态检索数据和 `[S]` 动态审计数据，但新项目第一版不应让结果完整性依赖外部数据库回填。

建议 `DamageResult` 本身保存：

- 每个 scaling component 的属性值、原始倍率、修饰后倍率和贡献值。
- 元素增伤属性解析结果。
- 暴击率、暴击伤害和暴击决策来源。
- 防御、抗性 policy 的输入和输出。
- 已应用与被拒绝的伤害修饰项。
- 最终乘区的稳定应用顺序。
- 关联的属性 resolution trace。

后续结果持久化可以对 trace 做投影或去重优化，但 core 产生的 `DamageResult` 必须先是自洽且可独立验证的。

第一版 trace level 可以复用属性系统的 `none`、`applied`、`full` 语义：

- `none`：只保留最终乘区和值。
- `applied`：保留已应用 term 和必要属性 trace。
- `full`：额外保留被拒绝 term、依赖链和 policy 中间值。

trace level 只能改变审计数据量，不能改变数值结果。

## 10. 事件边界

建议新增以下事件：

| EventType | Category | 语义 |
| --- | --- | --- |
| `DAMAGE_RESOLVED` | `FACT` | 一次伤害数值已经完成结算，但尚不代表生命已扣减 |
| `DAMAGE_APPLIED` | `FACT` | 正伤害已经以角色为目标完成护盾与血量提交，不要求血量实际减少 |

第一版伤害系统只实现 `DAMAGE_RESOLVED`。

规则：

- `DAMAGE_RESOLVED` 不可取消、payload 不可变、默认记录、可以驱动后续机制。
- payload 持有 `DamageResult` 或稳定结果引用。
- 不新增可变 `BEFORE_DAMAGE` / `BEFORE_CALCULATE` 事件作为修饰入口。
- 如果未来确实需要拦截伤害请求，应设计独立 `INTERCEPT` 阶段和强类型决策结果，不能把共享 context 暴露给 handler 任意修改。

事件类型的最终加入需要同步[事件类型](../事件系统/事件类型.md)。

## 11. 与动态机制领域的关系

静态 provider 和测试 provider 已足以验证公式与链路；动态 provider 后续由对应领域 Store 提供只读 view。

后续接入方式：

```text
BuffStore / 其他领域 Store
-> 当前帧活动完整记录只读 view
-> 暴露 DamageModifierProvider / Attribute ModifierProvider
-> DamageResolver 在当前帧纯查询
```

边界：

- 伤害查询期间不能添加、刷新、移除或过期领域实例。
- 对应领域实例生命周期决定 provider 是否活动。
- provider 不保存独立持续时间。
- 同一次伤害观察到的机制实例集合必须在 resolution session 内保持稳定。

## 12. application 与 content 接入

### 12.1 content contribution

建议在 `ContentUnit` 增加类型化入口：

```text
damage_modifier_providers: Sequence[DamageModifierProvider]
```

现有泛化 `modifiers` 可作为短期兼容入口，但新伤害实现不应根据 `scope` 字符串和自由 `object` query 猜测协议。属性 provider 与伤害 provider 应分别使用类型化字段。

### 12.2 impact factory

content impact factory 负责把技能倍率引用、攻击身份、元素应用数据和动作上下文展开为 Damage Impact，例如：

```text
impact_key="barbara.normal.hit_1"
-> DamageImpactSpec(
       attack_tag_key="普通攻击1",
       element="hydro",
       elemental_amount=1,
       icd_sequence_key="默认",
       icd_tag_key="普通攻击",
       damage_parameters_ref="barbara.normal.hit_1",
   )
-> Space 解析实际 AOE 目标
-> 每个目标构造 DamageRequest
```

芭芭拉普攻已按该链路落地：`DamageImpactSpec` 同时携带 `area`（球 -> 当前
X/Z 模型的同半径圆）与 `strike_type`/`range_type`/ICD 绑定；AOE 以索敌
选中的最近目标为锚点，由 Impact/Space 解析实际受击目标后再构造逐目标
`DamageRequest`。

impact factory 不负责：

- 查询最终攻击力。
- 计算防御或抗性。
- 决定 Buff 是否生效。
- 直接生成最终伤害值。
- 扣减目标生命。
- 直接选择或构造 `DamageType`。

`ImpactRequestDispatcher` 或专用 adapter 根据已经校验的 Damage Impact、目标解析、元素交互结果和 Damage Profile 创建类型化 `DamageRequest`。

### 12.3 组装校验

以下错误应尽量在组装阶段暴露：

- 未注册 damage handler 或 provider。
- scaling ref 不存在或倍率 payload 格式错误。
- 不支持的元素、属性 key、主攻击标签、附加攻击标签、打击类型或远近类型。
- 主攻击标签缺少 Damage Profile、Profile 引用了未注册公式，或同一主标签重复注册。
- provider 声明了非法属性读取或伤害阶段写入。
- 重复 provider key 或非法 stacking group。

动态运行时请求仍需执行模型级校验，但不能把可提前发现的 content 错误延迟到战斗中。

## 13. 错误模型

建议结构化错误：

| Error | code | 场景 |
| --- | --- | --- |
| `DamageValidationError` | `damage_validation_error` | 请求或 term 字段非法 |
| `UnsupportedDamageElementError` | `unsupported_damage_element` | 元素不受支持 |
| `UnsupportedDamageProfileError` | `unsupported_damage_profile` | 主攻击标签没有已注册 Damage Profile |

application 组装层将资产和 content payload 错误转换为现有 assembly 错误或专用伤害装配错误。

## 17. 多公式架构

> 状态：第一轮 `GENERAL`、剧变与第八版激化完整公式基础设施已实现；激化通过独立 Profile、实时元素精通读取和 `CatalyzeReactionResolution` 审计接入生产；月曜伤害公式与审计已进入生产注册，数值来源为已确认资料。

后续公式不按元素或来源拆分，而是按完整伤害公式的结构分类。伤害处理采用以下固定分层：

```text
DamageImpactSpec.attack_tag_key
-> DamageProfileRegistry
-> DamageProfile.formula_key
-> DamageFormulaRegistry
-> 对应 DamageFormula
-> DamageFormula 编排所需公式族
-> 生成 DamageResult
```

其中：

- 主攻击标签负责确定本次攻击身份并查找 Damage Profile。
- Damage Profile 负责选择完整公式和请求约束。
- 完整公式负责确定乘区组成、计算顺序和审计结果。
- 公式族负责防御区、抗性区、暴击区等可被多个完整公式复用的局部计算。
- 公式选择使用稳定主攻击标签与 Profile 显式映射，不根据元素、附加标签或最终属性值临时猜测。
- 未注册主攻击标签、Profile 或公式必须报错，不能静默降级为通用伤害。

### 17.1 已确认完整公式结构

第一阶段确认四种完整公式结构：

```text
general
damage_formula.catalyze_additive
transformative_reaction
lunar_reaction
```

它们是 Damage 内部 `formula_key`，不是上游请求变量。Profile 与公式的固定关系为：

```text
formula_key=general                            -> GeneralDamageFormula
formula_key=damage_formula.catalyze_additive  -> CatalyzeReactionDamageFormula
formula_key=transformative_reaction            -> TransformativeReactionDamageFormula
formula_key=lunar_reaction                     -> LunarReactionDamageFormula
```

Action、Reaction、周期状态和空间实体都只产生带稳定主攻击标签的 Damage Impact。组装阶段把普通攻击、反应伤害和月反应等主标签注册到对应 Profile；运行时不再由上游直接声明公式类别。原激化本身不产生伤害，因此不创建 Damage Impact。

### 17.2 通用伤害公式

通用伤害公式由以下计算区组成：

```text
倍率区
× 增伤区
× 暴击区
× 反应区
× 防御区
× 抗性区
```

普通非反应伤害和增幅反应参与的伤害由 Profile 选择 `general` 公式：

- 无反应时，反应区使用通用公式规定的单位结果。
- 增幅反应由反应区提供对应倍率。
- 不可暴击等规则只改变暴击区输入或结果，不改变所选 Profile 与公式。

倍率区统一按以下结构聚合：

```text
倍率区结果 = Σ(属性值 × 最终倍率) + Σ(基础伤害固定加值)
```

请求自带、角色、武器、圣遗物或其他机制提供的普通基础伤害固定加值，在公式中使用同一种数据结构和聚合规则，不按来源拆成“固定基础伤害”“基础伤害附加值”等多个数值字段；来源差异只保留在 term 的来源引用和审计信息中。

通用公式可以组合倍率区、增伤区、暴击区、反应区、防御区和抗性区公式族。具体接口名称待实现时确定。

### 17.3 激化反应公式

超激化和蔓激化伤害使用独立完整公式：

```text
(倍率区 + 激化附加区)
× 增伤区
× 暴击区
× 防御区
× 抗性区
```

激化公式可以复用通用公式的倍率区、增伤区、暴击区、防御区和抗性区公式族，但必须使用独立的激化附加区计算激化反应提供的附加值。该附加值不并入通用公式的普通基础伤害固定加值，也不通过通用反应区处理。

第八版固定：

```text
mastery_bonus = 5 * EM / (1200 + EM)

base_damage_addition =
    level_multiplier
    * reaction_multiplier
    * (1 + mastery_bonus + reaction_bonus)
```

- 超激化 `reaction_multiplier = 1.15`，蔓激化 `reaction_multiplier = 1.25`，第八版 `reaction_bonus = 0.0`。
- `source_level` 与 `stat.elemental_mastery` 从当前 `DamageQuery` 实时读取；不读取原激化创建者，不快照 EM。等级系数复用已注册的共享等级系数表，并记录 table key 与属性 trace。
- 激化附加值是独立公式区，不允许通过通用 `DamageModifierTerm` 伪造；但其结算结果必须作为命名来源进入 `DamageResult.base_damage_additions`，与普通倍率区结果相加后再经过增伤、暴击、防御和对应元素抗性。
- Damage 输入必须是强类型 `CatalyzeReactionInput`。没有输入、输入与当前 Impact/元素不一致，或通用公式收到该输入都稳定失败，不能静默退化。
- 迁移期间 `DamageType.CATALYZE_REACTION` 只可作为 Damage 内部公式实现键；content 和自由 payload 禁止填写。完成 `formula_key` 迁移后移除该公开枚举输入，不保留双入口。

完整稳定 key、调整模型和测试矩阵见[激化反应设计](./元素反应/反应/激化反应设计.md)与[激化反应契约](../../契约/元素反应/反应/激化反应契约.md)；第八版规划仅保留历史交付记录。

### 17.4 剧变反应公式

剧变反应使用独立公式结构：

```text
系数区
× 剧变增伤区
× 抗性区
```

剧变增伤区与通用伤害的增伤区语义和数据来源不同，必须使用独立公式族，不能复用通用增伤区实现。抗性区只有在输入、分段规则和审计语义完全一致时才复用公共抗性公式族。

第五版预生产的扩散 Profile 可额外声明 `SECONDARY_AMPLIFYING`。当且仅当该 capability、同一 target Impact ref 和 `SecondaryAmplifyingReactionInput` 全部成立时，剧变公式使用：

```text
基础剧变伤害
× [base_multiplier * (1 + 2.78 * captured_EM / (captured_EM + 1400) + reaction_bonus)]
× 对应元素抗性
```

基础剧变和二次增幅均使用扩散 occurrence 时捕获的数据；二次增幅不查询后续 round 的来源属性，也不引入普通增伤、暴击或防御区。其他剧变 Profile 仍拒绝该输入。

### 17.5 月反应公式

月反应使用独立 `lunar_reaction` 公式并由 `LunarReactionDamageFormula` 处理。当前代码已冻结两种 Damage 侧模式：

- `CHARACTER_DIRECT` 只允许一个角色参与者，使用该角色的属性倍率或固定基础伤害作为组分基础值。
- `REACTION_COMPOSITE` 保存多个角色参与者；每个参与者独立读取属性、元素精通、暴击和目标抗性，完成完整组分伤害后才排序和加权。

复合聚合的稳定顺序和权重为：

```text
按完整组分伤害从大到小排序
最高组分 × 0.60
第二组分 × 0.30
其余组分 × 0.05
```

组分结果和聚合结果分别进入 `LunarReactionComponentResolution` 与 `LunarReactionDamageResolution`，并通过 `DamageResult.lunar_reaction_resolution` 和 `DamageResult.to_dict()` 保留参与者、排序、暴击、抗性、权重及正式/调试伤害审计。月曜公式暂不接受普通 Damage modifier stage，也不使用普通元素增伤区或普通防御区。

`LunarReactionDamageFormula` 的等级基数表、精通系数和分母默认使用已确认资料中的生产数值，已注册进默认 `DamageFormulaRegistry`；调用方仍可显式注入替代公式用于测试或未来配置覆盖。

月绽放反应本身不产生伤害，不声明 `LunarReactionDamageImpactEffect`。角色月绽放伤害由角色技能消费草露后构造 `LunarReactionDamageInput(mode=CHARACTER_DIRECT)` 进入统一 Damage Impact；Damage Handler 通过 `damage_profile.reaction.lunar_bloom` 选择 `LUNAR_REACTION`，并将完整审计写入 `DamageResult.lunar_reaction_resolution`。`LunarReactionDamageImpactEffect` 类型保留给未来确实存在反应月曜伤害的机制。

月反应是否成立不由 Damage 判断。队伍角色提供的准入能力、严格元素签名、普通/月变体选择和草露状态均属于 Reaction 与元素反应协调流程；Damage 只接收已由主攻击标签对应 Profile 选定的月反应公式输入。正式 Reaction 边界见[元素反应架构文档索引](./元素反应/文档索引.md)。月曜公式使用注入式 `CriticalDecisionProvider`；可回放随机输入、角色专属倍率和追加攻击规则必须通过 Damage/仿真随机正式契约进入，不能由某个月反应机制自行定义全局随机语义。

### 17.6 调试专用区

`final_multiplier` 已从伤害 modifier stage 移除，调试倍率作为正式游戏公式之外的显式注入区：

```text
最终输出 = 正式公式结果 × debug_multiplier
```

- `debug_multiplier` 默认固定为 `1.0`。
- 调试区不属于任何正式伤害公式或可由 content 使用的普通 modifier stage。
- 只有测试或显式调试入口可以注入非 `1.0` 的值，生产组装默认不得启用。
- 审计结果必须能够区分正式公式结果与应用调试区后的最终输出。

### 17.7 Profile、公式与其他维度

以下维度不直接作为 `formula_key`：

- 物理、火、水等伤害元素。
- 是否暴击、是否可暴击和暴击结果。
- 单体、范围、持续伤害等目标选择或发生方式。
- 攻击力、生命值、防御力等倍率来源。
- 场上角色、后台角色、武器或内容创建对象等伤害来源。

普通攻击、重击、下落攻击、战技、爆发和具体反应等主攻击标签会选择 Damage Profile，但不是公式实现本身；多个主标签可以映射到同一个 `formula_key`。附加攻击标签只参与条件和修饰，不能改变主攻击身份或绕过 Profile 注册。

坠落、固定伤害及其他特殊伤害是否需要新增类型，留待对应机制有可信来源和验收案例后评审；当前不增加无明确公式语义的通用 `SPECIAL` 类型。
