# 伤害多公式实现规划

> 状态：第一轮基础设施已实施；仅 `GENERAL` 已注册，后续公式和结果 envelope 仍待可信来源、golden case 与单独评审。
> 最后更新：2026-07-12。
> 架构结论以[伤害系统设计](../架构/伤害系统设计.md)和[项目决策记录](../决策/项目决策记录.md)为准。

## 1. 目标

把当前只支持非反应直接伤害的单体 `DamageResolver`，渐进迁移为以下结构：

```text
DamageRequest.damage_type
-> DamageFormulaRegistry
-> 对应 DamageFormula
-> DamageFormula 编排公式族
-> DamageResult
```

第一轮实现只完成并注册 `GENERAL`，并保证现有直接伤害数值、稳定顺序和审计能力不回退。后续公式必须分别取得可信机制来源和 golden case 后再实现：

```text
GENERAL                 -> GeneralDamageFormula
CATALYZE_REACTION       -> CatalyzeReactionDamageFormula
TRANSFORMATIVE_REACTION -> TransformativeReactionDamageFormula
LUNAR_REACTION          -> LunarReactionDamageFormula
```

## 2. 非目标

本规划不同时实现以下内容：

- 元素附着、反应触发和反应归属判断。
- 激化、剧变或月反应的具体数值。
- 随机暴击和随机种子契约。
- 生命扣减、护盾、受击反馈和 `DAMAGE_APPLIED`。
- 结果数据库 schema 扩展。
- UI、CLI 或资产数据库的新配置入口。
- 无可信公式的 `SPECIAL` 万能伤害类型。

## 3. 当前实现与目标差距

当前代码集中在 `core/systems/damage/`：

- `DamageRequest` 默认承载普通直伤的倍率、固定基础伤害和暴击资格。
- `DamageResolver.resolve()` 同时负责 modifier 收集、全部乘区计算和结果组装。
- `policies.py` 已经包含可复用的暴击决策、防御区和抗性区实现。
- `DamageResult` 字段固定为通用直伤结构，尚不能表达公式类型和不同公式的专属审计。
- `DamageModifierStage.FINAL_MULTIPLIER` 当前可由普通 provider 写入，与“仅调试使用”的新结论不一致。
- `ImpactRequest.params.damage` 尚未显式携带伤害类型。

迁移原则：先把现有算法原样抽进 `GeneralDamageFormula`，再改变公共结果结构；数值重构与模型破坏性变更不得混在同一步中。

## 4. 目标职责

### 4.1 DamageResolver

`DamageResolver` 保留为统一入口，只负责：

1. 创建一次 `DamageResolutionSession`。
2. 根据 `DamageRequest.damage_type` 获取完整公式。
3. 收集并稳定排序 `DamageModifierTerm`。
4. 校验本次公式是否允许 provider 返回的 modifier stage。
5. 调用公式并组装公共结果、trace 和 applied/rejected term。

它不再直接实现倍率区、增伤区、暴击区、防御区或抗性区公式。

### 4.2 DamageFormula

完整公式负责：

- 声明自身对应的 `DamageType`。
- 声明允许的 modifier stage。
- 校验该公式所需请求输入。
- 编排公式族和计算区顺序。
- 返回公式专属、不可变的审计结果。

### 4.3 公式族

公式族负责一个可复用的局部计算，例如倍率区、增伤区、暴击区、防御区或抗性区。公式族应满足：

- 输入和输出强类型。
- 无世界状态写入。
- 不选择完整伤害公式。
- 不自行创建、移除或刷新机制实例。
- 结果保留足够的审计字段。

现有 `StandardDefensePolicy`、`StandardResistancePolicy` 和 `CriticalDecisionProvider` 先原位保留并作为公式族使用，不为目录整齐立即拆文件。

### 4.4 DamageFormulaRegistry

注册表按 `DamageType` 保存公式，负责拒绝重复注册和未实现类型。第一轮只注册 `GENERAL`；其他枚举值存在不代表已有可用公式。

## 5. 关键类型草案

以下代码用于冻结职责和数据流，正式实现应遵守项目格式、类型检查和错误体系。

### 5.1 伤害类型

```python
class DamageType(StrEnum):
    GENERAL = "general"
    CATALYZE_REACTION = "catalyze_reaction"
    TRANSFORMATIVE_REACTION = "transformative_reaction"
    LUNAR_REACTION = "lunar_reaction"
```

`DamageRequest` 增加显式字段：

```python
@dataclass(frozen=True, slots=True)
class DamageRequest:
    request_id: str
    frame: int
    damage_type: DamageType
    impact_key: str
    # 其余现有公共字段保持不变
```

第一轮不提前创建未知公式的空 payload 类型。当前倍率字段仍作为 `GENERAL` 输入；实现第二种公式前，再根据已确认输入评审是否引入判别联合的 formula input。

### 5.2 公式声明与协议

```python
@dataclass(frozen=True, slots=True)
class DamageFormulaSpec:
    damage_type: DamageType
    allowed_modifier_stages: frozenset[DamageModifierStage]


class DamageFormula(Protocol):
    @property
    def formula_spec(self) -> DamageFormulaSpec: ...

    def resolve(
        self,
        context: DamageFormulaContext,
    ) -> DamageFormulaResolution: ...
```

公式上下文由 resolver 创建，不向公式暴露完整可变 `SimulationContext`：

```python
@dataclass(frozen=True, slots=True)
class DamageFormulaContext:
    query: DamageQuery
    session: DamageResolutionSession
    modifiers: DamageModifierCollection
    trace_level: TraceLevel
```

若 `DamageResolutionSession` 与公式协议出现循环 import，应把公式需要的属性读取能力收窄为 `DamageAttributeAccess` Protocol，而不是通过 `Any` 或把完整 resolver 传入公式。

### 5.3 注册表

```python
class DamageFormulaRegistry:
    def __init__(self, formulas: Sequence[DamageFormula]) -> None:
        self._formulas: dict[DamageType, DamageFormula] = {}
        for formula in formulas:
            damage_type = formula.formula_spec.damage_type
            if damage_type in self._formulas:
                raise DuplicateDamageFormulaError(damage_type)
            self._formulas[damage_type] = formula

    def require(self, damage_type: DamageType) -> DamageFormula:
        try:
            return self._formulas[damage_type]
        except KeyError as exc:
            raise UnsupportedDamageTypeError(damage_type) from exc
```

不提供回退到 `GENERAL` 的逻辑。

### 5.4 Resolver 目标形态

```python
@dataclass(frozen=True, slots=True)
class DamageResolver:
    attribute_resolver: AttributeResolver
    formula_registry: DamageFormulaRegistry
    modifier_index: DamageModifierIndex = field(default_factory=DamageModifierIndex)

    def resolve(self, query: DamageQuery, *, trace_level: TraceLevel) -> DamageResult:
        formula = self.formula_registry.require(query.request.damage_type)
        session = DamageResolutionSession(self.attribute_resolver, query, trace_level)
        modifiers = self.modifier_index.collect(query, session)
        _validate_formula_stages(formula.formula_spec, modifiers.applied_terms)
        resolution = formula.resolve(
            DamageFormulaContext(query, session, modifiers, trace_level)
        )
        return _build_damage_result(query, resolution, modifiers, trace_level)
```

公式 stage 校验只检查 provider 实际返回的 term。provider 可以声明支持多个公式的 stage，但对当前公式返回不支持的 term 必须报 `DamageProviderViolationError`，不能静默忽略。

## 6. 通用公式设计

### 6.1 正式公式

```text
正式伤害 =
    倍率区
    × 增伤区
    × 暴击区
    × 反应区
    × 防御区
    × 抗性区
```

`GeneralDamageFormula` 固定编排六个公式族：

```python
@dataclass(frozen=True, slots=True)
class GeneralDamageFormula:
    scaling_policy: ScalingZonePolicy
    damage_bonus_policy: DamageBonusZonePolicy
    critical_policy: CriticalZonePolicy
    reaction_policy: GeneralReactionZonePolicy
    defense_policy: DefenseZonePolicy
    resistance_policy: ResistanceZonePolicy
    debug_adjustment: DebugDamageAdjustment = DebugDamageAdjustment()
```

第一轮反应区使用恒等实现并返回 `1.0`，只代表“当前请求没有增幅反应”，不伪造尚未实现的增幅反应数值。

### 6.2 倍率区

```text
倍率区结果 = Σ(属性值 × 最终倍率) + Σ(基础伤害固定加值)
```

请求自带的 `flat_base_damage` 与 `BASE_DAMAGE_FLAT_ADD` term 在进入倍率区时统一规范化为一种内部审计对象：

```python
@dataclass(frozen=True, slots=True)
class BaseDamageAddition:
    addition_key: str
    value: float
    source_ref: RuntimeSourceRef
    audit_tags: tuple[str, ...] = ()
```

倍率区结果只保留一组 additions，不按“固定基础伤害”“基础伤害附加值”或来源模块拆字段：

```python
@dataclass(frozen=True, slots=True)
class ScalingZoneResolution:
    component_results: tuple[DamageComponentResult, ...]
    additions: tuple[BaseDamageAddition, ...]
    value: float
```

为控制首轮改动，`ImpactRequest.params.damage.flat_base_damage` 可以暂时保持现有标量契约，由 handler/formula adapter 转换为 `BaseDamageAddition`。是否直接修改外部 payload 字段留到后续契约评审。

### 6.3 增伤区

第一轮保持现有行为：元素伤害加成与 `DAMAGE_BONUS_ADD` 相加，形成一个乘数。目标伤害减免尚未形成确认契约，本轮不新增未经验证的字段。

```python
@dataclass(frozen=True, slots=True)
class DamageBonusZoneResolution:
    element_bonus: float
    modifier_bonus: float
    multiplier: float
```

### 6.4 暴击区

暴击区复用注入式 `CriticalDecisionProvider`，并完整保存暴击资格、有效暴击率、暴击伤害、决策结果和乘数：

```python
@dataclass(frozen=True, slots=True)
class CriticalZoneResolution:
    can_crit: bool
    crit_rate: float
    effective_crit_rate: float
    crit_damage: float
    outcome: CritOutcome
    multiplier: float
```

随机暴击 provider 不在本轮实现。

### 6.5 反应区

通用公式的反应区只负责增幅性质的乘数：

```python
@dataclass(frozen=True, slots=True)
class GeneralReactionZoneResolution:
    multiplier: float
```

第一轮使用 `multiplier=1.0`。增幅反应输入、精通收益和反应加成等契约必须在反应系统与 golden case 确认后增加。

### 6.6 防御区与抗性区

第一轮直接复用现有 `StandardDefensePolicy`、`DefenseResolution`、`StandardResistancePolicy` 和 `ResistanceResolution`。迁移时必须保证：

- 防御区继续使用已经确认的 `(1 - 无视防御) * (1 - 防御减免)` 结构。
- 抗性区继续覆盖负抗性、`0.75` 边界和高抗性分段。
- 抽取公式族前后 golden case 数值完全一致。

### 6.7 调试专用区

`FINAL_MULTIPLIER` 从 `DamageModifierStage` 移除，不再允许 content provider 声明或返回。调试倍率通过构造注入：

```python
@dataclass(frozen=True, slots=True)
class DebugDamageAdjustment:
    multiplier: float = 1.0
```

```text
final_damage = official_damage × debug_multiplier
```

规则：

- 生产 assembler 只注入默认 `1.0`。
- 单元测试可以显式注入其他有限非负值。
- `official_damage` 与 `final_damage` 都进入审计；正常运行时二者相同。
- 不从 `SimulationConfig`、资产 payload 或 content contribution 读取调试倍率。

## 7. 结果模型迁移

第一轮抽取通用公式时，`DamageResult.to_dict()` 保持现有关键字段，避免同时破坏事件和结果投影：

```text
request_id
frame
source_ref
target_ref
element
base_damage
damage_bonus_multiplier
crit_outcome
defense_multiplier
resistance_multiplier
final_damage
```

同时增加：

```text
damage_type
official_damage
debug_multiplier
```

在实现第二种完整公式前，必须单独评审并迁移为公共 envelope 加公式专属 resolution：

```python
@dataclass(frozen=True, slots=True)
class DamageResult:
    request_id: str
    frame: int
    damage_type: DamageType
    source_ref: AttributeSubjectRef
    target_ref: AttributeSubjectRef
    element: DamageElement
    official_damage: float
    debug_multiplier: float
    final_damage: float
    resolution: DamageFormulaResolution
    # 公共 trace 与 modifier 审计
```

```python
type DamageFormulaResolution = (
    GeneralDamageResolution
    | CatalyzeReactionDamageResolution
    | TransformativeReactionDamageResolution
    | LunarReactionDamageResolution
)
```

未实现公式不提前创建空 resolution 类。结果 envelope 的落地属于核心结果模型变更，实施前需要再次人工确认，并同步检查事件 JSON 与结果库投影兼容性。

## 9. 实施阶段

### 阶段 A：冻结基线

1. 运行完整 `pytest`、`ruff`、`pyright`，记录现有状态。
2. 补足当前通用公式六区的直接断言。
3. 确认没有真实 content 使用 `FINAL_MULTIPLIER`。

验收：未修改实现前，现有 golden case 和纵向集成测试全部可复现。

### 阶段 B：加入类型和公式注册表

1. 增加 `DamageType`、公式错误、`DamageFormulaSpec` 和 registry。
2. `DamageRequest` 与 `params.damage` 显式携带 `general`。
3. assembler 只注册 `GeneralDamageFormula`。
4. 添加重复注册、缺公式、非法类型和不回退测试。

验收：所有现有伤害都明确走 `GENERAL`；请求其他类型得到结构化错误。

### 阶段 C：抽取通用公式族

按以下顺序小步抽取，每一步保持最终数值不变：

1. 倍率区和统一基础伤害 addition。
2. 增伤区。
3. 暴击区。
4. 恒等通用反应区。
5. 防御区和抗性区接线。
6. `GeneralDamageFormula` 最终聚合。

验收：旧 resolver 公式代码全部移出统一入口；golden case 数值和审计顺序不变。

### 阶段 D：收紧调试区

1. 移除 `DamageModifierStage.FINAL_MULTIPLIER`。
2. 删除普通 provider 对该 stage 的写入能力。
3. 增加构造注入的 `DebugDamageAdjustment`。
4. 将原 final multiplier 单元测试改为显式调试注入测试。
5. 断言 assembler 的运行态结果 `debug_multiplier == 1.0`。

验收：content 无法影响调试区；测试仍可显式验证最终乘算路径。

### 阶段 E：结果模型评审

1. 统计 `DamageResult`、事件 payload 和结果投影的全部消费者。
2. 决定 envelope 与判别联合的最终字段。
3. 保持或迁移现有 `to_dict()` 扁平摘要。
4. 同步结果模型文档和兼容测试。

此阶段属于核心结果结构变更，实施前必须人工确认。

### 阶段 F：后续公式

每种公式独立进入一个实现批次：

1. 明确可信来源和公式。
2. 确认输入契约、可复用公式族和专属公式族。
3. 增加类型化 resolution。
4. 增加 unit、integration 和 golden case。
5. 最后注册到生产 `DamageFormulaRegistry`。

推荐顺序：激化反应 -> 剧变反应 -> 月反应。没有 golden case 时只保留枚举，不添加空实现或测试占位公式。

## 10. 测试矩阵

### 10.1 Registry 与选择

- 四个 `DamageType` 能稳定序列化。
- 第一轮只注册 `GENERAL`。
- 重复注册同一类型报错。
- 未注册类型报错且不回退。
- `params.damage.damage_type` 缺失、类型错误或未知值报错。

### 10.2 通用公式族

- 单 component、多 component 和仅固定基础伤害。
- component 倍率百分比与倍率直接加值。
- 多个普通基础伤害 addition 使用 `math.fsum` 聚合并保留来源。
- 元素增伤与伤害专用增伤。
- 不可暴击、固定暴击和固定不暴击。
- 无反应时反应区固定为 `1.0`。
- 已确认防御公式和抗性分段边界。
- 非法负数、NaN、无穷和未知 component。

### 10.3 Modifier 权限

- provider 返回当前公式不支持的 stage 时失败。
- stacking group 的 applied/rejected 审计不变。
- content 无法声明调试区写入。
- trace level 只改变审计量，不改变 official/final damage。

### 10.4 调试区

- 默认 `debug_multiplier == 1.0`。
- 非 `1.0` 只能通过测试构造注入。
- `official_damage` 不受调试区影响。
- `final_damage == official_damage * debug_multiplier`。
- 非有限或负调试倍率被拒绝。

### 10.5 集成与 golden

- `ActionImpactPoint -> ImpactRequest -> GENERAL -> DamageResult`。
- 多目标顺序和独立抗性查询保持稳定。
- `DAMAGE_RESOLVED` 事件包含伤害类型和最终伤害。
- 结果持久化仍能读取事件摘要。
- 现有 54000 golden case 不变。

## 12. 风险与人工确认点

- `DamageResult` envelope 会影响事件 JSON 和结果消费者，必须单独确认。
- `DamageRequest` 的 formula input 是否改为判别联合，应等第二种公式输入确定后评审。
- 增幅反应输入和反应区算法尚未确认，不得凭记忆实现。
- 激化、剧变和月反应数值必须有可信来源及 golden case。
- 调试倍率不得进入 `SimulationConfig` 或资产数据，否则会污染可复现契约。
- 任何新增伤害类型必须对应明确的完整公式，不能只因为来源、元素或攻击标签不同而扩枚举。

## 13. 完成标准

第一轮多公式基础设施完成时应满足：

- 所有伤害请求显式携带 `DamageType.GENERAL`。
- resolver 通过 registry 选择 `GeneralDamageFormula`。
- 通用六区由明确公式族计算，resolver 不再内联公式。
- 普通基础伤害固定加值统一聚合并可审计。
- 正式公式结果与调试后结果明确分离。
- content 无法写入调试区。
- 未实现伤害类型明确失败且不降级。
- 现有单元、集成和 golden 数值全部保持通过。
- 相关架构、决策和工程文档与实现一致。
