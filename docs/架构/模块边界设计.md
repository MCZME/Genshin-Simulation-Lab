# 模块边界设计

> 状态：正式规范。
> 本文从结构设计角度说明项目的仓库布局、后端顶层模块划分、职责与依赖方向。
> 最后更新：2026-09-05。

本文是项目结构的导航入口，不描述具体代码文件、运行流程或实现细节。领域自治与跨系统协调的规则见[领域运行态实现规范](../工程/领域运行态实现规范.md)与[系统自治与跨系统协调规范](../工程/系统自治与跨系统协调规范.md)；测试规则见[测试规范](../工程/测试规范.md)；工作区目录与文件组织见[结果存储系统规范](../工程/结果存储系统规范.md)。

## 1. 仓库顶层结构

单仓库双工程：

```text
<project-root>/
├── README.md
├── AGENTS.md
├── docs/                      # 架构、契约、决策与工程文档
├── backend/                   # Python 后端（uv + src 布局）
│   ├── pyproject.toml
│   ├── uv.lock
│   ├── config.example.toml    # 提交到仓库的配置模板
│   ├── config.toml            # 本地生成，不入库
│   ├── data/                  # 本地数据目录（不入库）
│   │   ├── assets/            # 资产库与 manifest
│   │   ├── inputs/            # 模拟输入
│   │   ├── results/           # 结果库
│   │   ├── exports/
│   │   ├── templates/
│   │   ├── workflows/
│   │   └── logs/
│   ├── src/genshin_sim/       # Python 包
│   └── tests/
└── frontend/                  # Web 前端工程（pnpm + Vite）
```

工作区目录的推导与文件组织约定见[结果存储系统规范](../工程/结果存储系统规范.md)。

## 2. 后端顶层模块

`backend/src/genshin_sim/` 固定为以下七个顶层模块：

| 模块 | 定位 |
| --- | --- |
| `core/` | 纯仿真运行时核心：帧循环、事件、动作、影响、领域系统与跨系统协调。 |
| `content/` | 具体游戏内容实现：角色、武器、圣遗物、通用内容与队伍内容。 |
| `assets/` | 资产数据对象、仓库协议与相关错误。 |
| `infrastructure/` | 具体技术实现：SQLite、文件存储、日志、进程任务等。 |
| `application/` | 用例编排与组装，Python 后端唯一公开能力出口。 |
| `cli/` | 命令行入口适配。 |
| `server/` | HTTP 服务入口适配。 |

## 3. 依赖方向

总体依赖：

```text
frontend
  -> server（HTTP API）
      -> application（唯一公开能力出口）
          -> core / assets / content
          -> 仓库与写入协议
              <- infrastructure 实现
cli
  -> application
      -> core / assets / content
      -> 仓库与写入协议
          <- infrastructure 实现
```

硬规则：

- `core/` 是纯仿真运行时核心，不依赖 `assets/`、`infrastructure/`、`application/`、`ui/` 或 `content/`。
- `assets/` 只保存资产数据对象、仓库协议与相关错误，不实现 SQLite 访问。
- `content/` 保存具体内容实现，可以依赖 `core/` 与 `assets/` 数据对象。
- `application/` 负责用例编排与组装，不直接编写具体 SQLite 查询；SQLite 实现通过构造注入。
- `infrastructure/` 保存 SQLite、文件存储、日志、进程任务等具体技术实现，不依赖上层业务。
- `application/` 是 Python 后端唯一公开能力出口；`cli/` 与 `server/` 只能通过 `genshin_sim.application` 的公开接口调用能力。
- `frontend/` 只通过 `server/` 提供的 HTTP API 调用 application 能力，不 import Python 代码、不直接访问 SQLite、不组装仿真核心对象。
- 唯一出口约束面向外部入口（`cli/`、`server/`、`frontend/`），不要求内部模块之间的调用都经过 `application/`；`core/` 不反向依赖 `application/`。
- `cli/` 与 `server/` 不得导入具体 repository、writer、job runner、`SimulationAssembler`、`Simulator`、content registry 或查询计划执行器；新增入口能力时，先在 `application/` 定义稳定用例与模型，再做入口适配。
- `application/` 公开出口不暴露可变 Store、数据库连接或具体基础设施对象。

## 4. `core/`：纯仿真运行时

`core/` 负责“怎么模拟”：不负责数据来源、结果存储、UI 展示或具体游戏内容实现。内部按职责划分为以下子模块：

```text
core/
├── simulation/      # 仿真上下文、帧循环、Simulator、统一意图队列与结算
├── events/          # EventType、payload、EventSpec 与 EventEngine
├── actions/         # 输入会话、ActionManager 与动作实例
├── impacts/         # 影响点、ImpactFactory 与请求分发
├── entity_states/   # 角色/目标运行态、生命周期与内容状态挂载
├── attributes/      # 属性解析与属性面板快照
├── elements/        # 元素中立值对象与引用
├── contracts/       # 意图、帧阶段等跨系统中立契约
├── systems/         # 领域自治系统（damage、health、healing、shield、buff、cooldown、energy、infusion、aura、aura_icd、reaction、resonance、moonsign、movement）
├── coordination/    # 限定用途的跨系统协调器
├── space/           # 空间实体、范围查询与空间运行态
└── snapshots/       # 帧快照导出
```

领域系统互不 import 对方的 Runtime 或 Store；跨系统写流程统一放在 `coordination/`。系统自治与协调外置的完整规则见[领域运行态实现规范](../工程/领域运行态实现规范.md)与[系统自治与跨系统协调规范](../工程/系统自治与跨系统协调规范.md)。

## 5. `content/`：具体游戏内容实现

`content/` 是具体游戏内容的行为实现层，按内容类型组织：

```text
content/
├── characters/      # 正式角色（按地区/角色组织）
├── weapons/         # 正式武器（按武器类型组织）
├── artifacts/       # 正式圣遗物
├── generic/         # 可复用通用内容
├── team/            # 队伍级内容（元素共鸣、月兆地区效果）
├── test/            # 测试内容（仅开发者模式注册）
└── definitions/     # ContentUnit 等内容单元模型
```

内容通过 `handler_key` 与资产绑定，编译期产出 `ContentUnit`，由 `application/assembly` 注入运行时。内容包结构与 `version` 约定见[内容包结构约定](../工程/内容/内容包结构约定.md)与[内容版本约定](../工程/内容/内容版本约定.md)。

## 6. `assets/`：资产数据层

`assets/` 保存资产数据对象、仓库协议与资产相关错误，定义 `AssetRepository` 协议与角色、武器、圣遗物等数据对象。它不负责 SQLite 查询、数据导入、具体角色行为或 UI 展示。资产系统的分层与构建链路见[资产系统设计](./资产系统设计.md)，资产数据库字段与 manifest 契约见[资产数据库契约](../契约/资产数据库契约.md)。

## 7. `application/`：用例编排与唯一出口

`application/` 是用例编排层，是 CLI 与 HTTP API 唯一能调用的公开出口。内部按用途划分为：

```text
application/
├── input/           # 模拟输入契约与校验
├── config/          # 项目配置与工作区路径
├── assembly/        # 仿真组装（SimulationAssembler 与分阶段组装）
├── execution/       # 同步仿真执行与运行记录
├── jobs/            # 任务模型与执行器协议
├── batch/           # 批级调度用例
├── services/        # 对外用例门面（资产、输入、项目、结果、分析等）
└── models.py        # 用例层共享契约模型
```

它连接资产库、content 注册表、core 运行时、结果库与基础设施实现，但自身不直接编写 SQLite 查询，也不依赖任何 UI 框架。

分析能力横跨三处：查询计划编译执行器在 `infrastructure/results_sqlite/`，用例门面在 `application/services/`，HTTP 端点由 `server/` 提供。完整说明见[分析系统设计](./分析系统设计.md)与[分析系统契约](../契约/分析系统契约.md)。

## 8. `infrastructure/`：技术实现层

`infrastructure/` 提供具体技术实现，按技术域组织：

```text
infrastructure/
├── assets_sqlite/           # 资产库 SQLite 实现
├── assets_project_amber/    # Project Amber / Yatta 源站抓取与 manifest 构建
├── results_sqlite/          # 结果库与查询计划编译执行器
├── file_storage/            # 项目配置与工作流文件读写
├── jobs/                    # 进程任务执行
└── logging/                 # 日志配置与 JSONL 输出
```

它以协议实现身份从外侧注入，不属于任何入口或核心模块。

## 9. `cli/`、`server/` 与 `frontend/`

- `cli/`：命令行入口，只做参数解析与用例调用，不启动 HTTP 服务。
- `server/`：HTTP 服务入口，负责托管前端静态文件、路由、DTO、错误映射与访问控制；与 `cli/` 同级，不直接访问 `core/`、`content/`、`assets/` 或 `infrastructure/` 的具体实现。
- `frontend/`：仓库根目录下的独立 Web 前端工程（React + React Flow）。它是纯客户端，只调用 HTTP API；工作流图语义（定义校验、变体展开、成员预览）由前端持有，CLI 不运行工作流。

产品形态、状态设计与工程规范见[前端工程规范](../工程/前端工程规范.md)。
