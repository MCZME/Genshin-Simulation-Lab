# 游戏机制运行时架构规范

> 状态：总体架构已确认，具体协议名称、字段和序列化结构待实现评审。
> 本文档约束 Buff、状态、角色被动、命座、武器效果、圣遗物效果、元素附着、ICD、冷却、层数和其他持续机制的运行时架构。伤害、治疗与反应的具体数值规则不在本文范围内。

最后更新：2026-07-11

## 1. 设计目标

游戏机制层需要同时支持：

- 简单静态修饰与复杂内容专属行为。
- 持续时间、层数、刷新、替换、共存和过期。
- 基于运行时事实触发后续机制。
- 稳定、可复现的同帧执行顺序。
- 快照、事件记录、结果审计和问题复现。
- 角色、武器、圣遗物等内容通过 `handler_key` 扩展，而不让 `core/` 依赖具体内容实现。

本设计不追求把所有游戏规则数据化，也不允许具体内容绕过通用运行时直接修改世界状态。

## 2. 总体架构决策

机制层采用以下混合模式：

```text
ECS-like 数据组织
+ Protocol 能力行为
+ Command Buffer 状态变更
+ Event 事实记录
+ Registry 内容绑定
```

正式表述为：

```text
协议驱动运行时 + 局部组件化机制状态
```

各部分职责：

| 模式 | 职责 |
| --- | --- |
| ECS-like 数据组织 | 表达机制实例的身份、归属、生命周期和可组合能力 |
| Protocol | 表达具体机制具备的行为能力 |
| Command Buffer | 收集、排序、校验并统一提交状态变更 |
| Event | 记录已经发生的运行时事实，供触发、审计和分析使用 |
| Registry | 通过稳定 `handler_key` 将机制声明绑定到具体行为实现 |

该方案不是全局 ECS。项目不建立一个允许任意模块查询和修改所有组件的通用 `ECSWorld`。

## 3. 为什么不采用单一模式

### 3.1 不采用纯 ECS

原神机制中存在大量内容专属条件、计数、刷新和转换规则。若所有行为都实现为扫描组件的 System，容易演变为每个角色、武器或圣遗物各有一个专用 System，导致：

- 具体内容行为泄漏进 `core/`。
- 系统执行顺序难以维护。
- 机制状态与内容实现的绑定不清晰。
- 复杂行为被迫拆成过多通用组件或专用系统。

因此 ECS 思想只用于机制实例的数据组织、组合、索引和序列化，不作为整个机制行为模型。

### 3.2 不采用纯对象行为模型

若每个 Buff 或被动都是可以直接修改世界的长期对象，会导致：

- 生命周期和叠层规则分散在具体 handler 中。
- 同帧修改顺序依赖回调调用顺序。
- 事件递归触发难以控制。
- 快照、恢复和审计需要理解任意对象内部状态。
- 不同内容容易绕过统一机制入口。

因此具体行为对象只能读取受限运行时视图并返回结果或命令，不能直接修改运行态。

### 3.3 不采用事件总线作为业务主线

事件只表达已经发生的事实。事件系统不负责直接决定机制状态如何变化，也不允许监听器在回调中递归修改世界。

机制变化必须显式转换为命令，再由机制运行时统一提交。

## 4. 核心概念

### 4.1 MechanicInstance

`MechanicInstance` 表示一次实际存在于运行时中的机制实例。它只保存身份和状态，不直接拥有任意世界修改能力。

概念结构：

```text
MechanicInstance
├── instance_id
├── mechanic_key
├── handler_key
├── owner_ref
├── source_ref
├── target_ref?
├── start_frame
├── lifecycle
├── tags
├── params
└── local_state
```

字段语义：

- `instance_id`：本次运行中的唯一实例身份。
- `mechanic_key`：稳定的机制语义身份，不使用显示名称。
- `handler_key`：行为实现绑定入口。
- `owner_ref`：机制归属，例如角色槽位、队伍或目标。
- `source_ref`：机制来源，例如角色天赋、命座、武器或圣遗物效果。
- `target_ref`：可选的作用目标。
- `lifecycle`：机制的活动、过期、移除等状态。
- `params`：不可变组装参数。
- `local_state`：本次实例的可变内容专属状态，必须可快照和校验。

第一版不要求把所有字段拆成真实 ECS Component。实现可以使用强类型数据类和索引表，只要保持组件化组合思想。

### 4.2 机制能力

机制能力表示一个实例可以参与哪些运行时流程，例如：

```text
Duration
Stackable
EventReactive
AttributeModifier
ImpactModifier
Periodic
Aura
Cooldown
```

能力是运行时调度和索引依据，不要求所有能力都映射成统一通用组件。

### 4.3 MechanicBehavior

具体角色、武器、圣遗物和通用机制行为由 `content/` 提供，并通过 `handler_key` 注册。

行为实现不采用单个巨大的基类或万能协议，而采用小型能力协议。候选能力协议包括：

```text
EventReactive
ModifierProvider
PeriodicBehavior
LifecyclePolicy
ImpactTransformer
SnapshotProvider
```

上述名称是架构示意，具体 Python 协议名称待实现评审。

同一个 handler 可以实现一个或多个能力协议。组装阶段根据能力建立索引，运行时不应反复扫描所有 handler 判断能力。

### 4.4 MechanicRuntimeView

行为实现只能接收只读运行时视图。视图按最小权限暴露查询能力，例如：

```text
MechanicRuntimeView
├── frame
├── instance
├── owner_state_reader
├── mechanic_state_reader
├── attribute_reader
└── event_context
```

禁止把完整可变 `SimulationContext`、状态存储或系统实现直接交给 content handler。

### 4.5 MechanicCommand

所有机制状态变化通过强类型命令表达。候选命令包括：

```text
ApplyMechanic
RefreshMechanic
ReplaceMechanic
RemoveMechanic
PatchMechanicState
AddStack
ConsumeStack
StartCooldown
ConsumeCooldown
AddModifierInstance
RemoveModifierInstance
```

具体内容行为只能返回命令，不能直接执行命令对应的修改。

通用运行时负责：

- 校验命令来源和目标。
- 解析刷新、替换、共存和叠层规则。
- 稳定排序。
- 原子提交。
- 生成对应事实事件。

## 5. 状态所有权

机制运行时必须拥有机制实例和通用生命周期状态。具体 content 不持有独立的全局机制容器。

推荐所有权：

```text
MechanicRuntime
├── MechanicInstanceStore
├── BehaviorRegistry
├── CapabilityIndex
├── SubscriptionIndex
├── ModifierIndex
├── CommandBuffer
└── EventRecorder
```

### 5.1 MechanicInstanceStore

`MechanicInstanceStore` 使用 ECS-like 方式组织和索引机制实例，但不向外暴露任意组件修改 API。

外部应使用领域化接口：

```text
find_active(owner_ref, mechanic_key)
find_by_tag(owner_ref, tag)
apply(command)
remove(instance_id)
snapshot()
```

不建议向 content 暴露：

```text
add_component(entity, component)
remove_component(entity, component_type)
query_all(component_types)
```

### 5.2 ContentStateStore 的边界

现有 `ContentStateStore` 与机制实例存储职责不同：

- `ContentStateStore` 保存角色、武器、圣遗物 handler 自身的长期内容运行态，例如计数器、模式和动作相关专属状态。
- `MechanicInstanceStore` 保存已施加到运行时中的 Buff、状态、冷却、附着、临时修饰和其他可独立管理生命周期的机制实例。

同一状态不得同时在两个存储中维护。能够被通用地添加、刷新、移除或过期的状态，优先建模为机制实例。

## 6. Protocol 使用规则

### 6.1 小能力协议

协议按实际能力拆分，不建立包含全部钩子的 `BaseMechanic` 大接口。

系统只依赖所需协议，例如：

```text
事件调度只依赖 EventReactive
属性查询只依赖 ModifierProvider
逐帧推进只依赖 PeriodicBehavior
应用冲突只依赖 LifecyclePolicy
```

### 6.2 协议不负责状态所有权

协议实现解释规则，但不拥有通用实例生命周期，也不持有对全局运行时的可变引用。

### 6.3 协议返回结构化结果

协议方法返回以下一种或多种结构化数据：

- `MechanicCommand`。
- modifier term。
- 生命周期决策。
- 内容专属状态 patch。
- 审计说明。

不得依赖返回前已经完成的隐式副作用。

### 6.4 组装阶段校验

组装阶段必须校验：

- `handler_key` 非空且唯一绑定。
- 机制声明需要的能力均由 handler 提供。
- 事件订阅和 modifier target 合法。
- handler 不使用测试实现作为真实内容降级。
- 需要快照的 `local_state` 存在明确序列化方式。

## 7. 事件与命令模型

### 7.1 事件是事实

事件表达已经发生的事实，例如：

```text
MechanicApplied
MechanicRefreshed
MechanicRemoved
MechanicExpired
StackChanged
CooldownStarted
CooldownConsumed
```

具体伤害、治疗和反应事件由对应系统设计决定，不在本文冻结。

### 7.2 命令是意图

机制行为观察事实后可以产生命令，但事件本身不直接修改状态。

```text
事实事件
-> 选择订阅实例
-> 调用行为协议
-> 收集机制命令
-> 排序与校验
-> 提交命令
-> 记录新的事实事件
```

### 7.3 禁止立即递归修改

事件处理期间产生的命令不能立即在当前 handler 调用栈中修改运行态并递归发布事件。

推荐使用同帧分阶段队列：

```text
1. 冻结当前阶段输入事实
2. 基于只读状态调用相关行为
3. 收集命令
4. 稳定排序并提交
5. 生成下一阶段事实
6. 由后续阶段继续处理
```

同帧允许多少轮机制级联、如何检测循环以及超过上限时如何报错，待运行时实现评审，但必须有显式边界，不能无限递归。

## 8. 确定性顺序

机制运行时必须保证相同配置、资产版本、输入和随机种子产生相同结果。

命令和行为调用至少需要稳定排序键。建议包含：

```text
phase
priority
owner_ref
source_ref
instance_id
emission_index
```

具体排序字段待实现评审，但必须满足：

- 不依赖 Python 容器的偶然遍历顺序。
- 同帧新增实例不改变已经冻结阶段的订阅集合。
- 同帧移除实例是否仍处理当前阶段事件必须有统一规则。
- `priority` 只用于稳定排序，不作为任意机制冲突的万能仲裁值。
- 刷新、替换、共存和拒绝由显式生命周期策略决定。

## 9. 生命周期与冲突策略

通用运行时负责提供有限、明确的生命周期决策：

```text
apply_new
refresh_existing
replace_existing
coexist
reject_new
```

叠层行为应从有限策略开始，例如：

```text
independent_instances
shared_duration_shared_stack
refresh_duration
replace_by_stronger
```

无法由通用策略表达的内容可以通过 `LifecyclePolicy` 提供决策，但该协议仍只返回决策，不直接修改实例存储。

机制分组、唯一性和冲突判断必须使用稳定 key、owner/source 引用和显式标签，不使用显示名称。

## 10. 属性与修饰查询的关系

属性和其他数值修饰使用查询模式，不把最终属性保存为可任意写入的共享面板。

活动机制实例可以通过 `ModifierProvider` 提供纯修饰项：

```text
AttributeQuery
-> ModifierIndex 选择相关活动实例
-> 调用 ModifierProvider
-> 收集 ModifierTerm
-> 对应解析器统一聚合
```

规则：

- modifier 查询必须无副作用。
- 查询期间不得创建、刷新或移除机制实例。
- modifier 生命周期由其所属机制实例决定。
- modifier term 必须保留来源和实例身份，支持审计。
- 属性层职责见[属性系统架构](./属性系统设计.md)；属性聚合顺序、查询依赖和快照规则以[属性系统契约](../契约/属性系统契约.md)为准。

伤害、治疗、反应等系统未来可以消费相同的机制查询能力，但本文不规定其具体结算公式。

## 11. content 层接入方式

角色、武器、圣遗物和通用内容通过 `ContentRuntimeContribution` 或后续等价贡献模型提供：

- 机制行为 handler。
- 事件订阅声明。
- modifier target 声明。
- 机制初始参数或工厂。
- 必要的内容专属状态定义。

`content/` 不负责：

- 创建全局机制运行时。
- 保存所有活动机制实例。
- 决定全局执行顺序。
- 在事件 hook 中直接修改运行态。
- 绕过命令入口直接添加 Buff、附着或冷却。

真实内容机制仍通过 `handler_key` 显式注册。缺 handler、能力不匹配或状态 schema 不合法应在组装阶段报错。

## 12. 与其他运行时的关系

### 12.1 ActionManager

机制层不解释输入，也不改变动作时间轴。动作可以通过 impact、事件或显式机制命令创建机制实例。

机制若需要影响动作准入或动作解释，必须通过后续专门评审的只读查询边界表达，不能直接控制 `ActionManager`。

### 12.2 ImpactRuntime

`ImpactRequest` 表达机制意图。机制系统接收对应 request 后，可以产生机制命令；content impact factory 不直接修改机制实例存储。

### 12.3 EventEngine

`EventEngine` 负责事实发布与记录。`MechanicRuntime` 负责把相关事实转为受控的机制行为调用和命令提交。

### 12.4 SpaceRuntime

有空间位置的创建物继续由 `CreatedObjectRuntime` 与 `SpaceRuntime` 管理。无空间位置的 Buff、被动、冷却和持续效果归机制运行时管理。

空间对象可以通过稳定引用成为机制 owner、source 或 target，但机制实例不自动成为空间实体。

## 13. 建议模块边界

具体文件结构待实现时调整，职责建议如下：

```text
core/mechanics/
├── models.py       # 机制实例、引用、生命周期和值对象
├── protocols.py    # 小能力协议
├── commands.py     # 强类型机制命令
├── decisions.py    # 生命周期与冲突决策
├── store.py        # 实例存储和索引
├── runtime.py      # 调度、命令提交和阶段推进
├── ordering.py     # 稳定排序规则
└── snapshots.py    # 机制快照模型
```

若属性查询形成独立系统，应放在 `core/attributes/`，通过协议读取活动机制提供的 modifier，不把属性逻辑并入机制实例存储。

## 14. 测试规范

机制层测试至少分为：

- 纯行为单元测试：给定只读视图，协议实现返回确定命令或 modifier term。
- 生命周期单元测试：应用、刷新、替换、共存、叠层和过期。
- 顺序测试：同帧多事件、多实例和多命令结果稳定。
- 集成测试：content contribution 到机制实例运行时的完整链路。
- golden case：真实角色、武器、圣遗物、附着、ICD 和复杂触发行为。

测试必须断言结构化结果和事件，不依赖工程日志。

真实游戏机制的数值、持续时间、触发条件和覆盖规则必须有可信来源或旧项目 golden case 支撑。

## 15. 禁止事项

- 不建立允许所有模块任意访问的全局 ECS 世界。
- 不让具体机制 handler 直接修改 `SimulationContext` 或其他系统状态。
- 不在事件回调中立即递归发布并结算新的机制事件。
- 不使用显示名称作为机制身份、分组或冲突依据。
- 不使用单一全局优先级解决所有覆盖和冲突问题。
- 不把所有具体角色机制迁入 `core/` System。
- 不把可通用管理的临时机制状态重复保存在 `ContentStateStore`。
- 不让 modifier 查询产生副作用。
- 不以通用 `dict[str, object]` 作为所有机制状态的长期唯一模型；稳定结构应逐步收紧为强类型值对象。

## 16. 已确认与待评审事项

### 16.1 已确认

- 机制层采用“协议驱动运行时 + 局部组件化机制状态”。
- ECS-like 模式只用于机制实例的数据组织、组合、索引和序列化。
- 具体内容行为通过小型能力 Protocol 提供。
- 机制运行时统一拥有实例、生命周期、排序和命令提交。
- content handler 只能读取受限视图并返回结构化结果或命令。
- 事件表达事实，命令表达状态变更意图。
- 机制事件采用分阶段处理，不允许立即递归修改。
- 属性和其他 modifier 查询保持纯查询、无副作用。
- `ContentStateStore` 与机制实例存储职责分离。

### 16.2 待实现评审

- 具体 Protocol、Command 和生命周期枚举名称。
- `MechanicInstance` 的正式字段和强类型引用模型。
- ECS-like 能力采用独立组件、标签还是预编译能力描述。
- 同帧机制级联轮次、循环检测和错误类型。
- modifier 索引、查询上下文和最终聚合顺序。
- 机制快照与恢复的数据契约。
- 事件类型和 payload 的正式定义。
- 首个用于验证架构的真实机制切片。
