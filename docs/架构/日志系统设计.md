# 日志系统设计

> 状态：正式规范。
> 本文是项目工程日志的唯一规范：定义日志定位与服务对象、使用边界、消息与 `extra` 字段、级别语义、JSONL 文件输出、存储清理与异常记录策略。
> 最后更新：2026-09-08。

## 1. 定位

日志系统用于记录项目运行过程中的工程诊断信息。

它负责：

- 记录 CLI、UI、应用服务和基础设施的运行边界。
- 记录失败原因、异常栈和关键诊断上下文。
- 辅助开发、测试、用户反馈和本地问题排查。
- 为未来桌面 UI 提供可导出的本地诊断日志。

它不负责：

- 保存仿真事件流。
- 替代快照、结果库或分析数据。
- 作为机制逻辑的驱动来源。
- 作为配置契约、资产契约或结果契约的一部分。
- 在导入模块时自动修改全局日志配置。

仿真过程中“发生了什么”由 `core/events/` 的结构化事件表达；工程日志只表达“系统如何运行、哪里失败、如何诊断”。

## 2. 服务对象

- 主读者是开发者：本地排错、收到反馈后远程排查。
- UI 用户通过“导出诊断日志”间接参与，不直接阅读日志文本。
- 自动化日志分析不纳入设计；文件采用 JSONL 与稳定字段仅为将来保留可行性。
- 测试与 CI 不是运行时日志系统的读者，测试使用 `caplog` 或自定义 handler。

## 3. 边界原则

- `infrastructure/logging/` 负责日志配置、handler、formatter、输出路径和清理策略，并提供 `logging_context`（基于 `ContextVar`）供入口注入日志上下文字段。
- `cli/` 和 `server/` 作为入口负责调用日志初始化（`configure_logging`），并用 `logging_context` 注入入口级上下文（command、operation_id 等）。
- `application/`、`assets/`、`content/`、`core/` 使用标准库 `logging.getLogger(__name__)` 获取 logger。
- 非基础设施模块不依赖 `genshin_sim.infrastructure.logging`；模块内字段（session_id、job_id 等）通过 `extra` 显式传递，入口级上下文字段由入口通过 `logging_context` 注入，handler 侧自动补齐。
- `core/` 不把工程日志当作仿真记录通道；仿真事实、输入事实、动作事实和结算事实仍通过事件系统、快照和结果模型表达。
- 日志配置不写入 `SimulationInput`，也不影响仿真结果的可复现性。

## 4. 与事件、快照和结果库的区别

| 类型 | 所属模块 | 主要用途 | 是否作为仿真数据 |
| --- | --- | --- | --- |
| 工程日志 | `infrastructure/logging` 配置，各模块使用标准 logger | 诊断、排错、运行观测 | 否 |
| 事件流 | `core/events` | 表达仿真过程中的结构化事实和拦截点 | 是 |
| 快照 | `core/snapshots` | 导出运行时状态与当前帧事件 | 是 |
| 结果库 | `infrastructure/results_sqlite` | 持久化完整仿真结果、事件和投影数据 | 是 |

日志文件可以记录某次仿真开始、结束、失败、保存到哪个 `session_id`，但不记录完整事件流、完整配置快照或逐帧状态。

## 5. 使用边界（谁在什么边界记录什么）

各模块使用模块级 logger：

```python
import logging

logger = logging.getLogger(__name__)
```

使用边界与必带字段：

| 边界 | 级别 | 必带字段 | 记录什么 |
| --- | --- | --- | --- |
| 命令/操作入口 | INFO / ERROR | command, operation_id | 命令开始、结束（exit_code）、未处理异常 |
| 项目配置 | INFO / DEBUG / WARNING | project_root | init 成功；load 调试；配置缺省/降级时警告 |
| 资产库维护 | INFO / DEBUG | asset_db, asset_key | init/build/validate/fetch 结果；查询类 DEBUG |
| 输入校验 | INFO / ERROR | input_path, input_name | 校验通过；失败原因摘要 |
| 组装 | INFO / ERROR | config_name, session_id | 组装开始；组装完成汇总（team_size、target_count、rule_count）；缺资产、缺 handler、JSON 格式错误 |
| 仿真运行生命周期 | INFO / ERROR | session_id, config_name | 运行开始/完成/失败/保存；失败带完整栈 |
| 任务生命周期 | INFO / WARNING | job_id, session_id | 提交/取消/完成/失败；取消受限等可恢复问题 |
| 基础设施技术操作 | INFO / ERROR / WARNING | result_db, asset_db, session_id | 数据库初始化、写入失败、文件路径不可用、清理失败 |
| 结果读取 | DEBUG / ERROR | session_id | 查询轨迹；ResultNotFound、JSON 损坏等读侧错误 |
| content 注册诊断 | DEBUG / WARNING / INFO | asset_key, handler_key | 占位 handler 是常态用 DEBUG；注册冲突用 WARNING；启动汇总可选 INFO |
| core | 默认不打，异常时 ERROR/DEBUG | — | 只在确定性异常或极少量调试信息 |

不记录：

- 帧循环、事件发布、伤害/属性计算等高频率路径。
- 完整 `SimulationInput`、完整事件 payload、完整快照、大型查询结果。
- 日志中最多记录摘要、计数或截断内容。

## 6. 级别语义

| 级别 | 使用场景 |
| --- | --- |
| DEBUG | 开发诊断、查询轨迹、占位 handler 绑定等常态细节 |
| INFO | 重要运行边界：命令开始/结束、数据库初始化、仿真完成、结果保存 |
| WARNING | 可恢复但需要注意：任务取消受限、日志清理失败、配置降级、注册冲突 |
| ERROR | 当前命令或用例失败，但进程仍可返回可控错误码 |
| CRITICAL | 进程级不可恢复故障，很少使用 |

仿真机制中的拒绝、命中、伤害、输入消费等事实不因“重要”而进入工程日志。

## 7. 关联维度

- `operation_id`：一次入口操作，由 CLI/UI 入口在调用上下文生成。
- `session_id`：一次仿真运行，由执行器生成；关键日志点必须通过 `extra` 携带。
- `job_id`：一次任务，由任务层生成；任务完成时串联 `session_id`。
- 资源路径：`asset_db`、`result_db` 在日志上下文中写最终解析后的路径。

关联约定：

- `application` 不依赖 `infrastructure/logging`；`session_id` 通过 `extra` 显式传递。
- 测试钉住执行器的四个关键日志点（组装开始、运行开始、运行完成、结果保存/失败），断言 logger 名、级别与 `extra.session_id`，不依赖消息文本。
- 失败栈只在承担完整栈的层次记录（执行器负责仿真失败栈，任务层只记 `job_id + session_id + error_code` 摘要），避免重复打印。

## 8. 消息规范

- 消息统一使用中文（CLI 入口消息一并遵守）。
- 消息只描述“发生了什么”，结构化数据一律走 `extra`，不拼进文本。
- 使用 `%s` 占位符，不写 f-string，保持标准 logging 惰性求值。
- 消息简短、一事一记，沿用“仿真组装开始”“仿真结果已保存”风格。
- 组装失败与运行失败在消息上区分（“仿真组装失败”/“仿真运行失败”），级别均为 ERROR。
- 不记录完整 `SimulationInput`、事件 payload、快照、大型查询结果；DEBUG 需要时只记摘要或计数。

## 9. `extra` 字段列表

字段名稳定、小写 snake_case；新增字段先补入本表再使用：

`command`、`operation_id`、`session_id`、`job_id`、`config_name`、`input_path`、`input_name`、`project_root`、`asset_db`、`asset_key`、`handler_key`、`result_db`、`exit_code`、`error_code`、`frames_run`、`stop_reason`、`team_size`、`target_count`、`rule_count`、`limit`、`state`

## 10. 输出策略

两类输出：

- 控制台：面向开发者，使用文本格式，默认写入 `stderr`。
- 文件：面向排错与导出，固定使用 JSONL，不使用文本格式。

默认配置：

- CLI 普通模式：控制台只输出 WARNING 及以上；命令结果仍使用 `stdout`。
- CLI 调试模式（`--debug`）：控制台输出 DEBUG 及以上，并在顶层异常处记录异常栈。
- 项目模式（存在 `config.toml`）：命令默认启用文件日志，写入 `<data_dir>/logs/`；进程仿真 worker 同样启用文件日志。
- `project init` 与帮助类入口不启用默认文件日志；显式 `--log-file` 仍可用。
- `--log-file` 显式指定 > `GENSHIN_SIM_LOG_FILE` 环境变量 > 项目默认路径。
- server 常驻进程：启动即启用文件日志，固定写入 `<data_dir>/logs/server.jsonl` 并使用大小轮转；控制台输出 WARNING 及以上。uvicorn 自身的 access/error 日志独立配置，不与本项目日志合并。
- server 的进程仿真 worker 始终启用文件日志，写入同一 logs 目录；CLI 非项目模式（显式指定资产/结果库路径）不启用 worker 文件日志。
- 测试：不在包导入时自动配置日志，测试使用 `caplog` 或自定义 handler。

`config.toml` 是项目模式的前置条件：除 `project init` 与帮助类入口外，缺失或无效时命令直接报错，不静默回退。

## 11. JSONL 记录结构

文件日志每条记录一行一个 JSON 对象：

```json
{
  "ts": "2026-08-11T14:33:22.123+08:00",
  "level": "INFO",
  "logger": "genshin_sim.application.execution.executor",
  "message": "仿真运行完成",
  "fields": {
    "command": "run",
    "operation_id": "9f2c...",
    "session_id": "a1b2...",
    "config_name": "demo",
    "frames_run": 1200,
    "stop_reason": "RUN_LIMIT_REACHED"
  },
  "exception": null
}
```

规则：

- 顶层固定键：`ts`、`level`、`logger`、`message`、`fields`、`exception`。
- `ts` 使用 ISO 8601，带毫秒和时区。
- `fields` 包含全部上下文字段与 `extra`；空值字段不写，保持单行紧凑。
- `exception` 只在有异常栈时填 `traceback` 文本，否则为 `null`。
- 序列化使用 `ensure_ascii=False`、紧凑分隔符；不可序列化值兜底转字符串，日志格式化自身不得抛异常。
- 文件不设版本号；字段名稳定是兼容性约定。

## 12. 存储组织与保留

- 日志目录为 `<data_dir>/logs/`，由 `workspace.data_dir` 推导，不逐个配置；`ProjectConfig.logs_dir()` 提供路径，无 `config.toml` 时回落 `<project_root>/data/logs/`（`application.resolve_logs_dir` 统一承载该规则）。
- 每次打开（CLI 每次调用）创建一个独立文件，命名格式：

```text
genshin-sim-2026-08-11T14-33-22.123-4821.jsonl
```

- 时间戳带毫秒，后缀为进程号，避免并发冲突；文件名不使用冒号。
- 进程仿真 worker 通过进程池 initializer 启用文件日志：每个 worker 进程一个文件，命名规则同上，文件名中的进程号天然区分 worker 与主进程日志。
- server 主进程使用固定文件 `server.jsonl` 加大小轮转（默认 5MB × 5 份）；常驻进程不适用"每次打开建文件"。
- CLI 默认文件日志不轮转：一个进程只写一个文件，进程退出即关闭。
- 显式 `--log-file` 仍使用用户给定路径和大小轮转，属于用户主动控制行为。
- 清理在启用文件日志时执行，只作用于 `logs/` 目录内 `genshin-sim-*.jsonl`：
  - 删除超过 30 天的文件。
  - 文件数超过 200 个时删除最旧文件。
  - 清理失败记录 WARNING，不阻断日志写入。
- 日志清理绝不联动结果库；结果数据不可变，日志可随时删除。

## 13. 异常记录策略

- 入口层负责记录未处理异常，例如 CLI `main()` 或 server HTTP 错误处理边界。
- 应用服务可以在用例边界记录失败摘要，但不重复记录完整异常栈。
- 需要保留异常栈时使用 `logger.exception()`，并继续让异常按既有错误模型传播。
- 执行器负责仿真失败完整栈；任务层只记摘要。
- `EventEngine` 不捕获 handler 异常，保持事件系统当前失败语义。
- 日志不改变错误暴露层级；缺资产、缺 handler、JSON 格式错误仍应在组装或校验阶段抛出明确异常。

目标是“一次失败有一个清晰异常栈”，避免每层都重复打印同一栈。

## 14. 验收标准

- 不新增第三方依赖。
- 导入 `genshin_sim` 不会自动创建日志文件或修改 root logger。
- CLI 正常输出不被日志污染。
- `--debug` 或等价配置可以看到异常栈和关键诊断信息。
- 项目模式下每次命令产生一个 JSONL 文件，字段结构与本文一致。
- server 启动即产生 `server.jsonl`，进程仿真 worker 各产生一个 JSONL 文件；执行器关键日志点在 worker 日志中可见。
- 日志实现不破坏既有模块依赖方向；`application` 不依赖 `infrastructure/logging`。
- 仿真事件、快照和结果库职责不被日志替代。
- 执行器关键日志点带 `session_id`，并有测试钉住。
- 测试覆盖日志初始化、JSONL 序列化、按次建文件、清理和 handler 去重。
