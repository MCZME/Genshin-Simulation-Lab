# 状态效果最大生命协调器契约

> 状态：正式规范。
> 本文冻结 Buff 计划投影、最大生命同步计划、跨领域提交与事件边界。
> 最后更新：2026-09-06。

## 1. 处理对象

协调器不定义新的请求模型，直接复用 Buff 领域类型：

```text
ApplyBuffRequest（应用 / 刷新 / 叠层 / 替换）
RemoveBuffRequest（reason ∈ dispelled | consumed | explicit）
BuffMutationPlan（含帧过期计划）
```

同步只作用于 `AttributeSubjectKind.CHARACTER` 目标；TARGET 主体没有生命运行态，其 `stat.hp.max` 变化不同步。

## 2. 计划投影视图

`ProjectedBuffReader` 实现 `BuffReader.active()`，以未提交 `BuffMutationPlan` 为叠加层：

```text
BuffProjectionMode.BEFORE
    真实 Store 记录 + 计划 expected_records 视为在边界帧仍然活动
    （解析当前生命实际对齐的旧最大生命）

BuffProjectionMode.AFTER
    真实 Store 记录 + 叠加计划 replacement_records
    （解析统一提交完成后的新最大生命）
```

约束：

- 视图只读，不推进状态、不提交计划、不发布事件、不改层数。
- 除 `expected_records` 的边界回看外，两种模式都按真实半开区间规则（`created_frame <= frame < expires_at_frame`）过滤。
- 结果按 `instance_ref` 稳定排序。

`ProjectedBuffMaxHpResolver.resolve_max_hp_pair(subject_ref, frame, plan)` 返回 `(old, new)`：

- 复用真实 `AttributeResolver` 的定义、基础属性与全部非 Buff provider。
- 仅把 `BuffAttributeModifierProvider` 的 reader 换成投影视图等价实例。
- 同一算法保证 old/new 结果确定可比；`old == new` 的主体不产生同步计划。

## 3. CharacterMaxHpReconcilePlan

计划由 `HealthReconcilePort.prepare_max_hp_reconcile()` 准备：

```text
operation_id: str            # buff-max-hp:{buff operation_id}:{entity_id}
frame: int
target_ref: AttributeSubjectRef(character)
old_max_hp: float
new_max_hp: float
expected_store_version: int
expected_current_hp: float
result: CharacterMaxHpReconcileResult
```

约束：

- `old_max_hp`、`new_max_hp` 必须是有限正数。
- 提交前当前生命必须位于 `[0, old_max_hp]`。
- `result` 满足 `hp_after = hp_before / old_max_hp * new_max_hp`，`-0.0` 规范化为 `0.0`。
- `result` 的主体、帧与最大生命必须与计划一致。
- 计划不可变；Store version 或当前生命前值变化时统一预校验失败。

## 4. 领域端口

```text
BuffMutationPort
├── definition_registry: BuffDefinitionRegistry
├── prepare_apply(requests) -> BuffMutationPlan
├── prepare_expiry(frame) -> BuffMutationPlan | None
├── prepare_remove(request) -> BuffMutationPlan
├── validate(plan) -> None
├── commit_prevalidated(plan) -> BuffCommitReceipt
└── publish_committed_facts(receipt) -> None

HealthReconcilePort
├── prepare_max_hp_reconcile(ref, old, new, frame, *, operation_id)
│       -> CharacterMaxHpReconcilePlan
├── validate_max_hp_reconcile(plan) -> None
├── commit_max_hp_reconcile_prevalidated(plan) -> MaxHpReconcileReceipt
└── reconcile_events_for(receipt) -> tuple[GameEvent, ...]

MaxHpProjectionPort
└── resolve_max_hp_pair(subject_ref, frame, plan) -> tuple[float, float]
```

健康侧校验只覆盖 Store 版本、当前生命前值与结果数值范围（`hp_after <= new_max_hp`）；旧最大生命真值由协调器的边界视图负责。

## 5. 协调器提交契约

```text
apply_many(requests) -> tuple[BuffApplicationResult, ...]
apply(request) -> BuffApplicationResult
remove(request) -> BuffRemovalResult
update_frame(context, frame) -> None
is_idle() -> True
```

统一流程：

```text
判断计划是否触及影响 stat.hp.max 的 definition key
-> 未触及：透传（validate -> commit_prevalidated -> publish_committed_facts）
-> 触及：投影解析逐主体 (old, new) -> 准备 reconcile 计划
   -> 统一预校验（Buff Store + HealthStore 版本与前值）
   -> BuffStore.commit_prevalidated
   -> HealthStore.commit_reconcile_prevalidated（按主体稳定排序）
   -> 发布 Buff 事实 -> 逐主体发布 CHARACTER_MAX_HP_CHANGED
```

- 预校验后的提交不得产生业务失败；违反时包装为 `BuffMaxHpChangeCommitError`。
- 重入（事件回调同步进入协调器）抛 `BuffMaxHpChangeReentrancyError`。
- 主体排序键为 `(kind.value, entity_id)`；operation_id 含 Buff 计划 operation_id 与实体 id，可幂等去重。

## 6. 事件契约

同步只复用既有事件，不新增事件类型：

| 事件 | 类别 | 发布条件 |
| --- | --- | --- |
| `BUFF_APPLIED` / `BUFF_REMOVED` | STATE_CHANGE | 由 Buff 系统按已提交计划发布，顺序不变 |
| `CHARACTER_MAX_HP_CHANGED` | AUDIT | `old_max_hp != new_max_hp` 的角色主体，每主体至多一条 |

事实只在两个 Store 完整提交后发布；`CHARACTER_MAX_HP_CHANGED` 载荷为 `CharacterMaxHpChangedPayload(result)`，`result.hp_before / hp_after` 记录比例同步前后当前生命。

## 7. 数值不变量

- `old_max_hp > 0`、`new_max_hp > 0`、`0 <= hp_before <= old_max_hp`。
- 比例同步不产生治疗、伤害或直接扣血语义。
- 所有输入与结果为有限数，`bool` 不作为数值接受。
- Buff 记录本身不因同步发生变化（层数、期限、值不变）。

## 8. 错误类型

| 错误 | 场景 |
| --- | --- |
| `BuffMaxHpChangeCommitError` | 预校验后的领域提交违反不得失败契约 |
| `BuffMaxHpChangeReentrancyError` | 协调器同步重入 |

领域校验错误（`BuffPlanConflictError`、`HealthPlanConflictError`、`InvalidMaxHealthError`、`InvalidCurrentHealthError` 等）原样上抛；当前生命越过投影旧最大生命时，比例结果 `hp_after` 越界由 `InvalidCurrentHealthError` 拦截。

## 9. 组装与接线

- `build_max_hp_affected_buff_keys()` 在组装期沿属性依赖闭包与 provider `reads -> writes` 边计算受影响 definition key 集合，组装阶段不再直接拒绝这类 Buff。
- 协调器接入四个入口：`IntentKind.BUFF` 意图处理器、`BuffImpactRequestHandler`、TIME_ADVANCE 帧过期、显式移除。
- 元素反应结算协调器的内置反应状态路径不经本协调器，其内置定义不得影响 `stat.hp.max`。
- 协调器暴露在 `AssembledSimulation.buff_max_hp_coordinator`。
