# 冷却系统契约

> 状态：正式规范。
> 本文固定 `core/systems/cooldown/` 冷却领域的稳定 key、模型字段、恢复模式、时长解析规则、查询与写入语义、错误码、事实与快照。
> 最后更新：2026-10-10。

设计背景、模块边界与跨系统协作见[冷却系统设计](../架构/系统/冷却系统设计.md)，本文不重复展开。

## 1. 适用范围

本契约适用于角色元素战技与元素爆发的冷却次数状态、恢复模式（串行 / 独立）、恢复链、时长解析、条件查询、缩减、重置、批量提交、事实与快照。

不覆盖：

- 跨系统组合逻辑和 Action 接入的具体实现。
- 状态效果自身触发冷却、武器 / 圣遗物被动触发冷却。
- 元素附着 ICD、元素反应 ICD、协同攻击间隔、产球间隔及其他效果内部计时。
- 冷却与标准元素能量的公共条件组合（见[角色能力条件协调器契约](./角色能力条件协调器契约.md)）。

## 2. 通用规则

- 冷却真值使用整数帧和绝对 `ready_frame`，不逐帧递减浮点秒数。
- 活动恢复有效区间为半开区间：`started_frame <= frame < ready_frame`。
- `frame`、时长、次数等整数域拒绝 `bool` 与负数；数值域拒绝非有限值。
- 多充能恢复语义由 definition 的 `recovery_mode` 决定：`SERIAL`（默认，既有行为）同一时刻只有一个在途恢复计时、其余已消费次数排队；`INDEPENDENT` 每次消费各自独立计时，互不影响、不排队。
- `max_charges == 1` 时两种模式的存储形态与事实序列完全一致。
- 冷却领域只回答指定冷却键的 CD 条件是否满足，不回答技能是否可以释放。
- 冷却领域不 import 或查询其他领域 Runtime / Store，不通过全局上下文寻找外部状态。

## 4. 身份与定义

### 4.1 CooldownSubjectRef

```text
CooldownSubjectRef
├── subject_type: CooldownSubjectType
└── subject_id: str
```

- 只支持 `character` 主体。
- `subject_id` 是本次仿真内稳定、非空的角色主体 id；不使用显示名称、队伍槽位文本或 Python 对象地址。

### 4.2 CooldownKey

```text
CooldownKey
├── subject: CooldownSubjectRef
└── ability_key: str
```

- `ability_key` 表示共享同一冷却状态的能力身份；共享 CD 的多个释放变体必须使用同一 key。
- 推荐核心能力 key：`elemental_skill`、`elemental_burst`。
- 稳定排序键为 `(subject_type, subject_id, ability_key)`。

### 4.3 CooldownDefinition

```text
CooldownDefinition
├── key: CooldownKey
├── ability_kind: AbilityKind
├── base_duration_frames: int
├── max_charges: int
├── duration_mode: CooldownDurationMode
├── source_ref: str
├── tags: tuple[str, ...]
└── recovery_mode: CooldownRecoveryMode = serial
```

校验：

- `base_duration_frames` 是非负整数。
- `max_charges` 是正整数。
- `source_ref` 是非空且无首尾空白的稳定来源标识。
- `tags` 非空字符串、去重后按字典序冻结。
- `recovery_mode` 必须是 `CooldownRecoveryMode`；缺省为 `serial`，既有内容不受影响。
- `FIXED` 请求不得覆盖基础时长；`REQUEST_PROVIDED` 请求必须提供非负整数基础时长，definition 的 `base_duration_frames` 只作审计参考。

### 4.4 DefinitionRegistry

- 运行开始前完成注册并冻结；冻结后拒绝注册。
- 重复 key 报 `DuplicateCooldownDefinitionError`。
- 未注册 key 报 `CooldownDefinitionNotFoundError`。
- Runtime 运行后不能替换 definition 或修改 `max_charges`、`recovery_mode`。

## 5. 运行态模型

### 5.1 CooldownRecord

```text
CooldownRecord
├── key: CooldownKey
├── ability_kind: AbilityKind
├── max_charges: int
├── available_charges: int
├── recovery_mode: CooldownRecoveryMode
├── recoveries: tuple[ActiveRecovery, ...]      # 在途恢复项，按 (ready_frame, started_frame, chain_id) 稳定排序
├── queued_recoveries: int                      # 仅 serial
├── revision: int
└── last_changed_frame: int
```

`active_recovery` 与 `pending_recoveries` 是只读投影，不是存储字段：

```text
active_recovery      = recoveries[0] if recoveries else None   # 最早到期的在途项
pending_recoveries   = len(recoveries)
```

不变量：

```text
0 <= available_charges <= max_charges
0 <= queued_recoveries
len(recoveries) <= max_charges
recovery_mode == serial      -> len(recoveries) <= 1
recovery_mode == independent -> queued_recoveries == 0
available_charges + len(recoveries) + queued_recoveries == max_charges
revision >= 0
last_changed_frame >= 0
```

- 每项恢复项必须是 `ActiveRecovery`；构造时按稳定排序键规范化顺序，使取值相等的记录必然相等。
- 存储不变量只有一条守恒式：`available_charges + len(recoveries) + queued_recoveries == max_charges`；`serial` 的模式约束把「至多一个在途项」写成额外条件，`independent` 的模式约束把排队计数固定为 0。

初始化：`available_charges = max_charges`、`recoveries` 为空、无排队项、`revision = 0`、`last_changed_frame = 0`、`recovery_mode` 取自 definition。

### 5.2 ActiveRecovery

```text
ActiveRecovery
├── started_frame: int
├── ready_frame: int
├── interval_frames: int
├── chain_id: str
├── start_source_ref: str
└── duration_audit: CooldownDurationResolution
```

不变量：

```text
started_frame >= 0
interval_frames >= 0
ready_frame == started_frame + interval_frames
chain_id 非空
start_source_ref 非空
```

稳定排序键为 `(ready_frame, started_frame, chain_id)`。

### 5.3 串行恢复（`serial`，默认）

- 已消费但尚未恢复的次数组成串行恢复链；排队项只有在前一项恢复后才开始完整 interval。
- 同一时刻至多一个在途恢复项，第二次消费不会创建并行计时器。
- 链身份在链从空变为非空时创建，链未清空期间的所有消费沿用同一 `chain_id`。

最大 2 次、interval 900 帧示例：

```text
初始：available=2, recoveries=[], queued=0
frame 100 开始一次：available=1, recoveries=[ready=1000], queued=0
frame 120 再开始一次：available=0, recoveries=[ready=1000], queued=1
frame 1000 规范化：available=1, recoveries=[ready=1900], queued=0
frame 1900 规范化：available=2, recoveries=[], queued=0
```

### 5.4 独立恢复（`independent`）

- 每次消费创建自己的在途恢复项，`ready_frame = 消费帧 + 自身 interval`；各项互不影响、不排队、不互相续链。
- 每个在途恢复项各自构成一条单元素链，`chain_id` 取自身 `request_id`；因此 `reused_chain_resolution` 恒为 `false`，每次消费都按当刻的 terms 重新解析 interval。
- 缩减 / 重置作用于**最早到期的在途恢复项**（见 §7.4 / §7.5），其余在途项不受影响。
- 不引入「恢复项暂停 / 排序重排 / 跨项结转」语义。

最大 2 次、interval 900 帧示例：

```text
初始：available=2, recoveries=[], queued=0
frame 100 开始一次：available=1, recoveries=[ready=1000]
frame 200 再开始一次：available=0, recoveries=[ready=1000, ready=1100]
frame 1000 规范化：available=1, recoveries=[ready=1100]
frame 1100 规范化：available=2, recoveries=[]
```

### 5.5 剩余帧是投影

```text
remaining_frames = max(0, active_recovery.ready_frame - query_frame)
```

`active_recovery` 是最早到期的在途恢复项；无在途项时 `remaining_frames = 0`。Store 不保存 `remaining_frames`，避免每帧写状态、累计误差和快照前后不一致。

## 6. 冷却时长解析

### 6.1 基础时长

```text
FIXED            -> definition.base_duration_frames
REQUEST_PROVIDED -> requested_base_duration_frames
```

Runtime 不计算动态基础时长的业务公式；调用方必须在请求前得到确定整数帧并保留可审计 `source_ref`。

### 6.2 CooldownDurationTerm

```text
CooldownDurationTerm
├── term_key: str
├── source_ref: str
├── stage: CooldownDurationStage
├── operation: CooldownDurationOperation
├── value: Decimal | float | int
├── reference_stage: CooldownDurationStage | None
└── priority: int
```

策略：

- `MULTIPLY_CURRENT`：当前阶段值乘非负有限倍率；不能提供 `reference_stage`。
- `ADD_REFERENCE_PERCENT` / `SUBTRACT_REFERENCE_PERCENT`：增加 / 减少指定已完成阶段值的一定比例；必须提供 `reference_stage`，且 `reference_stage` 必须早于当前阶段。
- 同阶段按 `(priority, term_key, source_ref)` 稳定排序。
- 重复 `(term_key, source_ref)` 报错，不静默叠加。

固定阶段顺序为 `BASE -> OWNER_ADJUSTMENT -> DURATION_INCREASE -> EXTERNAL_ADJUSTMENT -> FINALIZE`。

### 6.3 解析结果

```text
CooldownDurationResolution
├── base_duration_frames: int
├── resolved_duration_frames: int
├── terms: tuple[CooldownDurationTerm, ...]
├── stage_totals: tuple[(CooldownDurationStage, Decimal), ...]
├── rounded_from: Decimal | None
└── source_refs: tuple[str, ...]
```

规则：

- 运算使用整数或 Decimal，不使用二进制 float 作为真值。
- 最终结果小于 0 时截断为 0；最终分数帧向上取整。
- `resolved_duration_frames >= 0`。
- 每个阶段保存输入、操作和输出，供审计，分析层不重新计算。

### 6.4 多充能快照

`serial`：

- 恢复链为空时，第一次 `StartCooldownRequest` 解析 terms 并创建 interval。
- 恢复链非空时，后续 `StartCooldownRequest` 不重新解析 terms，沿用活动链 interval；请求仍可携带 terms，但 Runtime 必须忽略其数值并在结果中记录 `reused_chain_resolution=True`。
- 恢复链清空后，下一次开始重新解析。

`independent`：

- 每次 `StartCooldownRequest` 都以当刻的 terms 解析 interval，并立即记录 `reused_chain_resolution=False`。
- 不产生 `queued_recoveries`；后续消费不会改动已有在途项的 interval 或 `ready_frame`。

## 7. 查询与写入

### 7.1 规范化

`CooldownRuntime` 维护 `normalized_through_frame`：

- `normalize(frame)` 拒绝帧回退；`frame == normalized_through_frame` 时无副作用。
- 按 `CooldownKey` 稳定顺序处理到期记录。
- 每个在途恢复项在 `frame >= ready_frame` 时恢复一次；已到期项按稳定排序键逐个处理，每处理一项后重新取集合（串行排队项会在该项完成时被建为新的在途项，可能同帧继续到期）。
- `serial`：有排队项时下一活动项从前一项的自然 `ready_frame` 开始，而不是从查询帧开始。
- `independent`：处理一项不影响其余项的 `ready_frame`；同帧多项到期时按稳定排序键依次恢复。
- 跨多个 interval 时循环恢复所有已到期项；每个实际恢复点生成独立事实，事实帧使用对应自然 ready frame。
- 查询和 mutation 只接受已规范化到请求帧的 Runtime：`frame > normalized_through_frame` 报未规范化错误，不隐式推进。

### 7.2 条件查询

```text
CooldownQuery
├── key: CooldownKey
└── frame: int

CooldownConditionResult
├── query: CooldownQuery
├── satisfied: bool
├── reason: CooldownConditionReason
└── view: CooldownView
```

条件：

```text
satisfied = available_charges > 0
reason = charge_available | no_available_charge
```

`CooldownView` 至少提供 `key`、`ability_kind`、`max_charges`、`available_charges`、`active_ready_frame`、`remaining_frames`、`queued_recoveries`、`chain_id`、`revision`、`pending_recoveries`、`recovery_mode`。

- `active_ready_frame` / `remaining_frames` / `chain_id` 描述**最早到期的在途恢复项**（与 §5.1 的 `active_recovery` 投影一致）。
- `pending_recoveries` 是在途恢复项总数；`serial` 下为 0 或 1，`independent` 下可大于 1。
- `queued_recoveries` 只在 `serial` 下可能非零。

查询无副作用、不产生领域事实；结果不代表技能整体可释放。

### 7.3 StartCooldownRequest

```text
StartCooldownRequest
├── request_id: str
├── key: CooldownKey
├── frame: int
├── requested_base_duration_frames: int | None
├── duration_terms: tuple[CooldownDurationTerm, ...]
└── source_ref: str
```

prepare 流程：

1. 校验 request、definition、frame 与幂等 id。
2. 确认记录已规范化到 frame。
3. 查询冷却条件；条件不满足时返回 `plan=None`，不替调用方决定下一步。
4. 按 `recovery_mode` 分派：
   - `serial` + 链为空：解析 duration、创建新链、`available_charges -= 1`。
   - `serial` + 链非空：复用链 interval、`available_charges -= 1`、`queued_recoveries += 1`，结果记录 `reused_chain_resolution=True`。
   - `independent`：解析 duration、创建独立的在途恢复项、`available_charges -= 1`，`queued_recoveries` 不变。
5. 构造完整后值和事实，不修改 Store。

commit 流程：

1. 校验 `expected_store_revision`、完整 before 与 request id 未提交。
2. 原子写入 after、revision 与已提交 request id。
3. 返回不可变 result 与事实。

0 帧时长允许：Start plan 先记录消费，再在同一事务结果中立即恢复；最终 record 不留下 0 帧 active recovery；同一 request id 只能提交一次。

### 7.4 ReduceRemainingCooldownRequest

```text
ReduceRemainingCooldownRequest
├── request_id: str
├── key: CooldownKey
├── frame: int
├── reduction_frames: int
└── source_ref: str
```

规则：

- `reduction_frames` 是非负整数。
- 只作用于最早到期的在途恢复项 `active_recovery`；`new_ready_frame = max(frame, old_ready_frame - reduction_frames)`，同时把该项 `interval_frames` 记为 `new_ready_frame - started_frame`；其余在途项（`independent` 下可能有）不受影响。
- 本帧完成时恢复一个次数；`serial` 有排队项时从命令生效帧开始下一个完整 interval。
- 超出当前 remaining 的减量不结转到下一项。
- 无在途计时返回 `ignored(no_active_recovery)`；`reduction_frames == 0` 返回 `ignored(no_effect)`。

### 7.5 ResetActiveCooldownRequest

```text
ResetActiveCooldownRequest
├── request_id: str
├── key: CooldownKey
├── frame: int
└── source_ref: str
```

规则：

- 让最早到期的在途恢复项在本帧完成；不一次填满全部 `max_charges`，也不改动其余在途项。
- `serial` 有排队项时从本帧开始下一完整 interval。
- 无在途计时返回 `ignored(no_active_recovery)`。
- 不提供无来源的 `reset_all`。

### 7.6 批量 mutation

```text
CooldownMutationBatchRequest
├── batch_id: str
├── frame: int
└── requests: tuple[CooldownMutationRequest, ...]
```

规则：

- requests 按 `(CooldownKey.sort_key, request_id)` 稳定排序。
- 同一个 key 在一个 batch 中最多出现一次；同一 batch 不能使用重复 request_id。
- 所有请求必须使用 batch frame。
- 先验证全部 key、frame、数值、revision 与完整前值，再提交任何状态；任一 item 非法时整批失败。
- 合法 ignored item 不导致整批失败，但必须保留结果。
- commit 一次更新 Store revision，再按稳定顺序返回 item result 与 facts。

### 7.7 暂不泛化的命令

真实机制和 golden 出现前，不增加：

- 直接恢复指定数量 charge。
- 临时免费消费或无视 CD。
- 暂停、加速或倒放冷却时间。
- 运行时修改 `max_charges`。
- 复制或交换两个 key 的剩余 CD。
- 任意 `set_record()` / `set_ready_frame()` 或调用方直接 mutation。

## 8. Store 与提交

`CooldownStore` 拥有 definition registry、完整 record、version 与已提交 operation id：

- `commit_prevalidated` 只接受完整记录替换；任一 key 冲突或 version 不匹配时不得提交任何替换。
- 同一 operation / request id 只能提交一次。
- 只有记录实际变化时 Store version 才增加；ignored 项仍登记幂等身份。
- 提交和事实构造期间再次调用写入口报 `CooldownReentrancyError`。

## 9. 事实与快照

### 9.1 CooldownFact

```text
CooldownFact
├── fact_id: str
├── fact_kind: CooldownFactKind
├── frame: int
├── key: CooldownKey
├── operation_id: str
├── chain_id: str | None
├── before_available_charges: int
├── after_available_charges: int
├── active_ready_frame: int | None
├── queued_recoveries: int
├── source_ref: str
├── duration_audit: CooldownDurationResolution | None
├── before_record: CooldownRecord | None
└── after_record: CooldownRecord | None
```

- 事实只描述已提交状态。
- 事实稳定排序键为 `(frame, key.sort_key, fact_kind_order, operation_id)`，其中 fact_kind 顺序为 `started → reduced → reset → charge_recovered → chain_completed`。
- 自然恢复使用实际 ready frame，不伪装成规范化查询帧。
- `chain_id` 取本次操作作用的链：`started` / `reduced` / `reset` / `charge_recovered` 在 `serial` 下取操作后在途项的链（链已清空时为 `null`）；`independent` 下取本次操作针对项的链；`chain_completed` 取被清空链的身份。
- `active_ready_frame` 与 `queued_recoveries` 是操作后记录的最早到期投影与排队计数。`independent` 下 `queued_recoveries` 恒为 0，完整在途集合以 `after_record.recoveries` 为准。
- `independent` 下每个在途项各自成链，因此每次恢复产生一组 `charge_recovered` + `chain_completed` 事实；`serial` 下一组事实只在链清空时出现。

### 9.2 事件

冷却事实经 `COOLDOWN_CHANGED`（`STATE_CHANGE`）发布，payload 固定为：

```text
CooldownChangedPayload
├── fact_id
├── fact_kind
├── frame
├── subject_ref: { subject_type, subject_id }
├── ability_key
├── operation_id
├── chain_id
├── before_available_charges
├── after_available_charges
├── active_ready_frame
├── queued_recoveries
├── source_ref
├── before_record: CooldownRecordSnapshot | null
└── after_record: CooldownRecordSnapshot | null
```

载荷字段本身未随恢复模式变化；`before_record` / `after_record` 按 §9.3 携带 `recovery_mode` 与完整 `recoveries`，独立模式下的在途集合由这里观察。

### 9.3 快照

```text
CooldownSnapshot
├── schema_version: int = 2
├── frame: int
├── normalized_through_frame: int
└── records: tuple[CooldownRecordSnapshot, ...]

CooldownRecordSnapshot
├── subject_type / subject_id / ability_key / ability_kind
├── max_charges / available_charges
├── active_started_frame / active_ready_frame / interval_frames
├── queued_recoveries / chain_id
├── revision
├── recovery_mode: str
└── recoveries: tuple[CooldownRecoverySnapshot, ...]

CooldownRecoverySnapshot
├── started_frame / ready_frame / interval_frames
└── chain_id / start_source_ref
```

- `schema_version = 2` 起记录快照携带 `recovery_mode` 与完整 `recoveries` 列表。
- `active_started_frame` / `active_ready_frame` / `interval_frames` / `chain_id` 保留为**最早到期在途项**的便捷投影（与 §5.1 一致），`independent` 下必须与 `recoveries[0]` 一致。
- 快照按 `CooldownKey` 稳定排序，`recoveries` 按 §5.2 稳定排序键排序；不保存 resolver、外部 provider、callback 或调用方对象。definition 来源通过独立运行元数据或事实审计关联，不重复写入每帧 record。

## 11. 内容接入

- `ContentUnit.cooldown_definitions` 提供强类型 `CooldownDefinition` 切片。
- `ContentUnit.cooldown_duration_terms` 按 `CooldownKey` 声明冷却时长修正 term，内容编译期绑定到定时动作，动作在冷却开始帧原样提交给 `StartCooldownRequest.duration_terms`。
- `CooldownDurationTermPort` 供内容 / 队伍规则（如双风共鸣 ×0.95）提供 term；冷却领域只验证和解析已经提供的 term。
- 冷却与标准元素能量的公共条件组合由[角色能力条件协调器契约](./角色能力条件协调器契约.md)消费 `CooldownConditionResult`，不得直接读取 Store。

## 12. 测试要求

至少覆盖：

- subject、key、definition、duration mode、recovery mode、source ref 与 tags 的合法 / 非法值。
- Store 不变量：初始化、`available + len(recoveries) + queued` 总数守恒、单次与多充能转换、跨模式非法状态（串行两个在途项、独立非零排队）被拒绝、在途项构造时按稳定排序键规范化。
- 帧边界：`ready_frame - 1` 不满足、`ready_frame` 规范化后满足；0 帧、1 帧与分数秒向上取整；帧回退与未规范化查询。
- 串行回归：串行而非并行恢复、链存在时复用 interval、链清空后重算、reset 只完成当前活动项、fixed reduction 不向排队项结转、事实序列与 `chain_id` 投影逐位不变。
- 独立恢复：各次消费独立计时、同帧多项到期时按稳定排序键依次恢复、每次消费重新解析 terms 且 `queued_recoveries` 恒为 0、reduce / reset 只作用于最早到期项且不影响其余项、全部恢复后 reduce 返回 ignored。
- 时长 resolver：三种 operation、固定阶段、reference 只能指向已完成阶段、稳定排序、重复 term 拒绝、负结果截断、链内忽略新 term。
- mutation 与 batch：applied / ignored / 非法分支、稳定排序、整批原子性、同 key 重复拒绝、同步重入拒绝。
- 事实与快照：started / recovered / reduced / reset / chain completed 顺序、0 帧 start/recover 顺序、稳定排序与 JSON 往返；独立模式下快照与事件的 `recoveries` 列表完整。

## 13. golden 断言

领域实现至少需要以下可复现用例：

1. 固定 32 秒单次 CD 边界（`ready_frame - 1` 不满足、`ready_frame` 规范化后满足）。
2. 双充能串行恢复。
3. 多充能 CDR 快照（链存在时沿用 interval，链清空后重算）。
4. 当前活动项 reset（不填满全部次数，排队项从请求帧开始）。
5. fixed reduction 不向排队项结转。
6. request-provided 动态基础时长。
7. 不同 reference stage 的 CDR 计算审计。
8. 双充能独立恢复（两次消费各自计时，分别在自身 ready frame 恢复）。
9. 独立恢复下 reduce / reset 只作用于最早到期项。

真实角色 golden 的取证与外部调用时点属于内容 / 协调专题；领域真值使用上述明确输入验证。
