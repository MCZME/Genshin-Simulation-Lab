# 按键输入系统设计

> 状态：核心运行链路已确认。本文档说明按键输入契约在运行时如何协作，以及输入系统与动作系统之间的职责边界。

最后更新：2026-07-11

## 1. 目标与边界

本文档回答：“`SimulationInput.input_trace` 编译后的输入会话在运行时怎么协作，边界为什么这么划。”

稳定数据契约见：[按键输入契约](../契约/按键输入契约.md)。动作实例、锁、中断和影响点的完整设计见：[动作系统设计](./动作系统设计.md)。

本文档关注：

- 输入事实如何在组装阶段编译。
- `ActionManager` 如何按帧处理 PRESS、RELEASE 和派生 HOLD。
- binding 为什么在 PRESS 时固定。
- `detached/canceled` 的运行语义。
- 与 `ActionInterpreterRegistry`、队伍解释器、角色解释器的职责边界。
- 与事件系统、结果库、快照的关系。
- 后续扩展入口。

本文档不定义：

- 具体动作如何解释。
- 角色动作帧数、动作锁、中断窗口和资源规则。
- 伤害、命中、索敌、元素附着、反应或其他机制结算。

## 2. 总体流程

按键输入进入运行时的目标链路：

```text
SimulationInput.input_trace
-> InputTraceCompiler
-> InputSessionTrace
-> ActionManager.update_frame
-> ActionInterpreterRegistry
-> InterpreterBinding
-> ActionInterpretationResult
-> ActionManager 动作准入
```

更完整的动作链路会继续进入 `ActionRegistry`、`ActionInstance`、`ActionImpactPoint` 和 `ImpactRuntime`，详见动作系统文档。

核心原则：

- 配置层只记录按键事实。
- 按键事实在组装阶段配对为输入会话计划，并编译为 `InputSessionTrace`。
- `ActionManager` 是运行时输入会话的拥有者。
- 动作是否发生、动作类型和开始帧由对应解释器决定。
- 完整输入计划中的未来 release 不向解释器提前暴露。

## 3. 组装阶段编译

组装阶段处理顺序：

```text
SimulationInput
-> application/input 结构校验
-> InputTraceCompiler.compile()
-> InputSessionTrace
-> SimulationAssembler 注入 ActionManager
```

`InputTraceCompiler` 只在组装阶段运行。它负责把配置中的 `press/release` 事实配对为不可变输入会话计划，并生成帧边界索引。

组装阶段还应校验：

- 所有允许出现在配置中的输入键必须存在 selector。
- 同一个键不能重复注册 selector。
- 真实角色槽位必须存在角色动作解释器。
- 真实角色解释器声明的 Action 必须存在于 `ActionRegistry`。
- 缺资产、缺 handler、缺解释器或缺 Action 时应在组装阶段报错。

`InputTraceCompiler` 不作为每帧运行对象，也不直接调用动作解释器。

## 4. 每帧处理顺序

第 N 帧的输入处理属于 `ActionManager.update_frame` 的一部分：

```text
1. 启动此前预约在第 N 帧开始的动作
2. 按原始 order 处理第 N 帧 PRESS / RELEASE
3. 每次解释后立即应用结果
4. 处理仍为 held/listening 的 HOLD
5. 推进运行中的动作实例
6. 处理本帧 impact
```

规则：

- 同帧输入顺序会影响后续解释结果。
- 输入边界先于 HOLD，保持“显式输入先处理、运行态随后推进”的帧语义。
- 新 press 当帧不再调用 HOLD。
- release 当帧不再调用 HOLD。
- 当前帧接受并开始的动作应立即执行 `on_start()`，使同帧后续输入看到其状态变化。
- HOLD 不写入 `input_trace`，而是由 `ActionManager` 根据运行时会话状态逐帧派生。

## 5. 运行时会话状态

运行时输入会话同时保存物理状态和动作控制状态。

物理状态：

```text
held
released
```

动作控制状态：

```text
listening
detached
canceled
```

语义：

- `listening`：后续 HOLD、RELEASE 或未来启用的 CANCEL 继续调用原解释器。
- `detached`：动作已不再需要输入控制；物理按键仍可保持按下。
- `canceled`：动作控制因切人或其他规则失效；未来 release 仍作为物理事实处理。

`detached/canceled` 不会删除或改写未来 release 输入事实。它们只影响运行时是否继续调用解释器。

触发类型：

```text
press
hold
release
cancel（保留）
```

- PRESS 来自输入会话开始边界。
- RELEASE 来自输入会话结束边界。
- HOLD 由 `ActionManager` 对仍为 `held/listening` 的会话逐帧派生。
- CANCEL 保留给动作系统内部的会话控制取消回调；当前实现只把会话控制状态置为 `canceled`，不调用解释器。

HOLD 和 CANCEL 都不是新的外部按键事实，因此不写入 `input_trace`。

## 6. PRESS 时固定 binding

`ActionManager` 使用 `ActionInterpreterRegistry` 解析输入会话：

```text
key
-> selector
-> InterpreterBinding
```

第一版 selector：

- 队伍级 selector。
- 当前场上角色 selector。

binding 在 PRESS 时解析并写入运行时会话。后续 HOLD、RELEASE 和未来可能启用的 CANCEL 始终使用同一 binding，不因当前 `active_slot` 改变而重新路由。

示例：

```text
frame 100: active_slot=1, keyboard.e press
frame 110: 切到 slot 2
frame 130: keyboard.e release
```

该 E 会话仍归属 press 时的 slot 1。切人成功后可以取消它的动作控制，但不能把 release 路由给 slot 2。

这样做的原因：

- 输入会话的 owner 在开始时就应稳定。
- 长按类动作需要同一个解释器连续观察 PRESS、HOLD 和 RELEASE。
- 切人、状态变化或其他动作不能把已经开始的物理按键会话改写为另一个角色的输入。
- 完整输入计划不能被运行时 active slot 变化重新解释为不同事实。

## 7. 解释器职责边界

`ActionInterpreterRegistry` 只负责从按键和运行时上下文得到 `InterpreterBinding`。

队伍解释器负责：

- 队伍级按键解释，例如切换到指定槽位。
- 返回语义化动作请求，例如 `team.switch`。
- 不直接修改队伍运行态。

角色解释器负责：

- 当前 owner 角色的按键解释。
- 根据输入会话、角色状态、资源和动作状态返回解释结果。
- 判断继续等待、拒绝、启动动作或控制已有动作。

解释器不负责：

- 创建 `ActionInstance`。
- 获取或释放动作锁。
- 直接修改动作实例或动作状态。
- 执行动作逻辑。
- 产生伤害、治疗或状态变化。
- 读取未来 release 信息。

解释器只返回 `ActionInterpretationResult`、`PreparedAction` 或语义化控制命令。`ActionManager` 负责最终动作准入、锁冲突检查、实例创建、旧实例取消和生命周期推进。

## 8. 事件、结果库与快照

输入事实、会话边界和动作判断是不同层级：

```text
KeyEvent
InputSessionBoundary
ActionInterpretationResult
ActionDecision
ActionInstance lifecycle
```

`ActionManager` 在处理输入边界时发布两类输入事件：

```text
INPUT_KEY_RECEIVED
INPUT_SESSION_BOUNDARY_REACHED
```

发布顺序：

```text
1. 发布 INPUT_KEY_RECEIVED。
2. 创建或读取 RuntimeInputSession，并更新 physical_state。
3. 发布 INPUT_SESSION_BOUNDARY_REACHED。
4. 如果 will_interpret=true，调用解释器。
5. 后续由动作解释、动作决策和动作生命周期事件记录结果。
```

这些输入事件只用于复盘、审计和结果记录，不作为动作机制的驱动来源。

与其他系统的边界：

- `core/events` 定义事件类型、payload 和分发，不写数据库。
- 结果库可以持久化输入事实、会话边界和后续动作事件；具体 SQLite schema 属于 `infrastructure/results_sqlite`。
- 快照可以暴露当前运行时输入会话状态，但快照模型与结果库持久化格式仍需后续细化。
- `analysis/` 只基于结果数据加工复盘或统计，不反向驱动动作系统。

## 9. 当前实现状态

当前已经落地：

- `application/input` 对 `input_trace` 执行结构和生命周期校验。
- `InputTraceCompiler` 在组装阶段把按键事实编译为 `InputSessionTrace`。
- `SimulationAssembler` 把配置中的按键输入轨迹编译后注入 `ActionManager`。
- `ActionManager` 按帧读取会话边界，处理 PRESS、RELEASE、派生 HOLD，并调用固定 binding 的解释器。
- `ActionManager` 发布 `INPUT_KEY_RECEIVED` 与 `INPUT_SESSION_BOUNDARY_REACHED` 事件，用于复盘、审计和结果记录。

后续仍需细化：

- 输入会话在快照和结果库中的持久化格式。
- CANCEL 回调是否调用解释器，以及 payload 与审计规则。
- 动作解释结果、动作决策和动作生命周期事件的最终 payload。

## 10. 后续扩展入口

后续扩展应优先保持当前边界：

- 自定义键位：在配置或用户设置层把物理输入映射到稳定 key；`InputTraceCompiler` 仍只接收规范化 key。
- 手柄：新增手柄 key 命名空间，并在契约层定义按钮和轴输入是否进入同一会话模型。
- 移动：移动键若需要连续方向输入，应先确认是否属于按键会话、运动控制状态，或独立移动意图流。
- 镜头：鼠标移动、视角和准星不应伪装成 `press/release`，需要单独的输入事实契约。
- CANCEL 回调：只有当真实角色或机制需要取消通知时，再启用解释器 CANCEL 触发，并补充事件与测试。
- 结果库与快照：先稳定事件 payload，再确定 SQLite 投影表和快照字段。
