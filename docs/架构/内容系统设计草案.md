# 内容系统设计草案

> 状态：草案。
> 本文档记录 `content/` 层的设计方向，用于支撑角色、武器、圣遗物、通用影响、状态和修饰行为的实现。尚未确认的接口命名、运行态字段和具体角色机制不视为最终契约。
> 具有稳定身份和生命周期的运行态由[领域运行态设计](./领域运行态设计.md)约束；伤害、治疗、护盾、反应等领域规则的实现与验证要求见[原神游戏机制实现规范](../工程/原神游戏机制实现规范.md)。
> 属性层职责与 content 协作边界见[属性系统架构](./属性系统设计.md)；属性定义、查询上下文、modifier 阶段、依赖解析和快照规则以[属性系统契约](../契约/属性系统契约.md)为准。

最后更新：2026-07-08

## 1. 设计目标

`content/` 是具体游戏内容实现层，用于把资产数据和核心通用运行时接口连接起来。

目标：

- 通过 `handler_key` 绑定具体内容实现。
- 保存角色、武器、圣遗物、通用影响、状态和修饰行为代码。
- 为动作系统提供角色动作解释器。
- 为对应领域系统提供影响展开、修饰器和触发器。
- 在组装阶段产出可注入运行时的内容贡献。

非目标：

- 不读取 SQLite。
- 不解析用户配置文件。
- 不创建 `SimulationAssembler`。
- 不直接控制模拟器帧循环。
- 不直接写结果库或 UI。
- 不把具体内容逻辑放进 `core/`。

## 2. 核心理解

`content/` 不应只是散落的 handler 函数集合，而应按资产 `handler_key` 创建“运行时贡献”。

推荐链路：

```text
SimulationConfig
-> AssetRepository 读取资产数据
-> handler_key 查找 content factory
-> content factory 创建 ContentRuntimeContribution
-> application/assembly 注入运行时
-> core 通过通用协议调用
```

`assets` 保存静态数据，`content` 保存行为代码，`core` 保存通用协议和运行时容器，`application/assembly` 负责装配。

### 2.1 当前验证阶段范围

当前阶段优先验证装配链路：

```text
资产
-> handler_key
-> content factory
-> ContentRuntimeContribution
-> runtime 注入
```

当前阶段已经使用测试专用 content 验证最小直接伤害链路，但仍不把测试倍率视为真实角色机制。治疗、Buff、反应和真实内容数值继续要求独立契约或 golden case。`content/` 可以保留 `generic.noop`、`generic.test_*` 或测试专用 content，用于证明资产、配置、注册表、组装器和机制运行时可以正确连接。

真实资产如果对应行为尚未实现，资产库中的 `handler_key` 默认保持为空；只有测试资产、占位资产或已经有真实实现的内容才填写 `handler_key`。占位 handler 不代表真实游戏机制已经实现。

## 3. 内容类型

### 3.1 CharacterContent

角色内容负责角色主行为。

典型贡献：

- 动作解释器。
- 角色专属运行态扩展。
- 角色技能影响工厂。
- 内容创建对象行为。
- 天赋、命座和角色专属触发器。
- 角色专属修饰器。

角色内容不负责：

- 读取资产库。
- 直接修改模拟器帧循环。
- 直接写结果库。
- 绕过通用动作和伤害领域系统直接结算伤害。

### 3.2 WeaponContent

武器内容负责武器被动和相关行为。

典型贡献：

- 静态或条件属性修饰器。
- 触发器。
- 影响请求修饰器。
- 特定武器影响工厂。

武器内容不提供角色动作解释器，第一版不贡献内容创建对象行为，也不能通过修饰器或触发器改变动作解释结果。武器只影响属性、事件响应、影响请求和后续机制结算。

### 3.3 ArtifactContent

圣遗物内容负责套装行为和参数化机制。

典型贡献：

- 套装属性修饰器。
- 条件 Buff。
- 触发器。
- 影响请求修饰器。

圣遗物内容不提供角色动作解释器，第一版不贡献内容创建对象行为，也不能通过修饰器或触发器改变动作解释结果。圣遗物只影响属性、事件响应、影响请求和后续机制结算。

### 3.4 GenericContent

通用内容用于实现可复用的基础影响、状态或修饰行为。

典型贡献：

- 通用静态修饰器。
- 测试用 NoOp handler。
- 通用 Buff/Status 逻辑或影响展开逻辑。

## 4. 运行时贡献模型

建议用统一的运行时贡献对象表达内容产物。

已确认方向：`ContentRuntimeContribution` 放在 `content/models.py`。它是内容层 factory 的装配返回模型，不放进 `core/`，也不放进 `application/`。

概念结构：

```text
ContentRuntimeContribution
├── owner_type
├── owner_key
├── handler_key
├── slot?
├── action_interpreter?
├── state_extension?
├── impact_factories
├── created_object_behaviors
├── event_hooks
├── modifiers
├── attribute_definitions
├── attribute_providers
├── damage_modifier_providers
├── damage_modifier_stacking_groups
└── metadata
```

说明：

- `owner_type` 表示角色、武器、圣遗物、套装、通用影响或状态来源。
- `owner_key` 对应资产 `asset_key` 或内容来源 key。
- `handler_key` 是代码绑定入口。
- `slot` 用于绑定到队伍槽位。
- `action_interpreter` 主要由角色内容贡献。
- `actions` 保存内容贡献的不可变 Action 定义，统一使用稳定 `action_key` 注册。
- `state_extension` 保存内容专属运行态。
- `impact_factories` 把 `impact_key` 展开为机制请求。
- `created_object_behaviors` 定义内容创建空间实体的后续 tick 行为入口，仅由角色内容贡献。
- `event_hooks` 响应核心事件或机制事件。
- `modifiers` 是现有泛化兼容入口；新属性和伤害实现优先使用类型化 provider 字段。
- `attribute_definitions` 和 `attribute_providers` 提供属性定义与属性修饰。
- `damage_modifier_providers` 和 `damage_modifier_stacking_groups` 提供伤害专用纯查询修饰与冲突策略。

边界规则：

- `core/` 定义通用协议和运行时数据，例如 `ActionInterpreter`、`Action`、`ActionInstance`、`ImpactFactory`、`ImpactRequest`、空间实体创建请求、实体生命周期模型、`Modifier` 和 `EventHook`。
- `content/models.py` 定义 `ContentRuntimeContribution`、`CharacterContentRuntime` 等内容层装配产物。
- `application/assembly` 调用 content factory，收集 `ContentRuntimeContribution`，再拆分构造 `ActionInterpreterRegistry`、`ActionRegistry`、`ImpactDispatcher`、`ImpactRequestDispatcher`、`ImpactRuntime`、`CreatedObjectRuntime`、`HookRegistry`、`ModifierRegistry` 等运行时对象。
- `core/` 不接触完整 `ContentRuntimeContribution`，只接收拆分后的通用协议实现。
- `content` 不依赖 `application`。

调整后的目标装配模型：

- `SimulationAssembler` 按角色、武器、圣遗物和资产 payload 分别创建专用 runtime request。
- content registry 返回 `ContentRuntimeContribution | None`。
- `application/assembly` 收集贡献物并构造 `RuntimeContentBundle`。
- `RuntimeContentBundle` 拆分出 `action_interpreters`、`actions`、`impact_factories`、`created_object_behaviors`、`event_hooks`、属性 provider、伤害 provider、`modifiers` 和 `ContentStateStore`。
- `ActionInterpreterRegistry` 接收队伍级 selector 和按队伍槽位拆出的角色动作解释器。
- `ActionRegistry` 接收 `action_key -> Action`，并在组装阶段校验解释器声明的动作 key。
- `ImpactDispatcher` 只接收 `impact_key -> ImpactFactory`。
- `ImpactRuntime` 负责把动作影响点展开为 `ImpactRequest`；具体请求由 `ImpactRequestDispatcher` 转交对应领域系统或 `CreatedObjectRuntime`。
- `CreatedObjectRuntime` 接收内容创建空间实体所需的通用行为协议或创建请求。
- `core/` 不 import `content`，也不认识 `RuntimeContentBundle`。

## 5. 角色内容运行时

角色内容可产出角色运行时对象。

概念结构：

```text
CharacterContentRuntime
├── slot
├── character_key
├── handler_key
├── action_interpreter
├── state_extension?
├── impact_factories
├── created_object_behaviors
├── passive_hooks
└── metadata
```

### 5.1 action_interpreter

`action_interpreter` 负责解释输入会话和动作控制状态。

它可以返回：

```text
defer
defer_until
reject
enter_control_state
schedule_timeline
cancel_session
```

解释器只生成通用动作语义，不直接创建 `ActionInstance`，不直接计算伤害。

### 5.2 state_extension

`state_extension` 保存角色专属运行态。它不直接挂在 `CharacterRuntimeState` 字段上，而是由统一 `ContentStateStore` 管理。

示例：

```text
furina_state
├── salon_members
├── arkhe_state
├── fanfare?
└── custom_flags
```

这些状态不应塞进通用 `CharacterRuntimeState`。通用角色运行态只保存所有角色共有的字段，角色专属字段由内容层扩展管理。

推荐统一容器：

```text
ContentStateStore
├── character_states
│   └── slot -> handler_key -> state
├── weapon_states
│   └── slot -> handler_key -> state
├── artifact_states
│   └── slot -> handler_key -> state
└── generic_states
    └── owner_ref -> handler_key -> state
```

角色专属 state 第一版索引：

```text
(slot, character_handler_key)
```

不要用显示名称，也不要只用 `asset_key`。`slot` 表示队伍运行时归属，`handler_key` 表示具体 content 实现归属；同一个 handler 也可能被不同 slot 使用，不能按 handler 全局单例存。

推荐访问方式：

```text
state = content_state_store.get_character_state(
    slot=1,
    handler_key="character.furina",
    expected_type=FurinaState,
)
```

规则：

- `CharacterRuntimeState` 只保存通用字段。
- 角色专属字段全部放在 content state extension。
- 只有对应 owner 的 content handler 能读写自己的 state。
- hook 的 `state_patches` 只能 patch 自己 owner 的 state。
- `ActionInterpreter` 可以读取自己角色的 state extension。
- 武器、圣遗物不能直接读取或修改角色专属 state；第一版不开放跨 owner state 访问。
- state extension 不直接保存数据库对象、UI 对象、文件句柄或不可序列化运行时对象。

快照协议：

```text
ContentStateSnapshotProvider
└── snapshot_state(frame, state) -> ContentStateSnapshot
```

快照模型：

```text
ContentStateSnapshot
├── owner_ref
├── handler_key
├── schema_version
├── frame
└── payload
```

`payload` 必须是 JSON-compatible 数据，例如 dict、list、str、number、bool 或 null。

### 5.3 impact_factories

`impact_factories` 把动作影响点或 `impact_key` 展开为 `ImpactRequest`。

示例：

```text
impact_key="furina.skill.press.hit_1"
-> ImpactRequest(kind=damage, element=hydro, scaling_ref="skill.e.hit_1")
```

影响工厂不负责最终伤害计算。最终结算仍由伤害领域系统完成。

### 5.4 created_object_behaviors

`created_object_behaviors` 定义内容创建空间实体在创建后的 tick 行为入口。

示例：

```text
impact_key="furina.skill.create_salon_member"
-> ImpactRequest(kind=create_entity, params.object_key="furina.salon_member")
-> CreatedObjectRuntime 创建 CreatedObjectRuntimeState
-> Space 登记对应 SpatialEntity
-> 后续机制、事件或实体行为按明确规则生成 damage / heal 等 ImpactRequest
```

内容创建空间实体的对象运行态和实体登记由 `core/space` 管理，并复用 `core/entity_states/lifecycle.py` 中的通用生命周期值对象。content 负责提供创建规格、刷新策略、空间参数和后续行为入口，不直接推进全局帧循环。

无空间位置、不参与空间查询的持续逻辑不应放进 `created_object_behaviors`；这类逻辑应作为机制、状态或 hook 处理。

### 5.5 event_hooks

`event_hooks` 用于表达“已提交事实发生后产生什么后续命令”。它可以由角色、武器、圣遗物或通用内容贡献，但不能直接修改 `RuntimeWorld` 或领域 Store，也不能改写动作解释结果。

最小协议：

```text
EventHook
├── hook_key
├── owner_ref
├── subscriptions
├── priority
└── handle(event, context) -> HookResult
```

`HookResult` 最小包含：

```text
HookResult
├── impact_requests
├── modifier_commands
├── state_patches
└── audit_notes
```

规则：

- hook 只能监听已经发生的运行时事件。
- hook 不能监听或改写输入解释过程。
- hook 不能直接修改 `RuntimeWorld`。
- `state_patches` 只能描述自己 owner 的 content state 变更，并由下一结算轮次提交。
- hook 产生的伤害、治疗、创建空间实体等后续行为仍走 `ImpactRequest` 或对应领域强类型命令。
- `priority` 只用于稳定排序，不作为复杂机制仲裁入口。
- 在通用命令队列实现前，真实触发型 hook 不进入正式 content。

### 5.6 modifiers

`modifiers` 用于表达“结算时如何修饰数值”。它应是纯查询、无副作用。

最小协议：

```text
Modifier
├── modifier_key
├── owner_ref
├── targets
├── scope
├── priority
└── evaluate(query, context) -> ModifierTerm[]
```

`ModifierTerm` 最小包含：

```text
ModifierTerm
├── target
├── operation
├── value
├── source
└── tags
```

`operation` 第一版控制在：

```text
flat_add
percent_add
final_multiplier
override
```

规则：

- modifier 不直接改属性、伤害结果或世界状态。
- modifier 只返回修饰项，由对应领域系统统一聚合。
- modifier 不能改变动作解释器、动作时间轴、取消窗口或输入会话。
- 临时 Buff、层数、持续时间等不由 modifier 自己维护；由 BuffRuntime 等领域运行时处理 hook 产生的强类型命令。
- 结算系统负责审计每个 modifier term 的来源和贡献。

### 5.7 passive_hooks

`passive_hooks` 用于表达天赋、命座和角色专属触发逻辑。

第一版可先保留协议位置，不急于实现复杂事件订阅系统。

## 6. handler_key 与 factory

`handler_key` 是内容代码绑定入口，不等同于 `asset_key`。

示例：

```text
asset_key   = character:75
handler_key = character.furina
```

当前阶段按三档理解 `handler_key`：

- 空值：资产存在，但没有行为实现；组装阶段不创建 content。
- `generic.noop` 或 `generic.test_*`：测试或占位用途，只验证装配链路。
- `character.*`、`weapon.*` 或 `artifact.*`：真实 content 实现，需要对应测试或 golden case 支撑。

不保留泛化 `RuntimeHandlerRequest` 作为长期设计。内容注册表按内容类型提供明确注册与创建入口。

第一版 factory 协议：

```text
CharacterHandlerFactory
-> CharacterRuntimeRequest
-> ContentRuntimeContribution

WeaponHandlerFactory
-> WeaponRuntimeRequest
-> ContentRuntimeContribution

ArtifactHandlerFactory
-> ArtifactRuntimeRequest
-> ContentRuntimeContribution

ImpactHandlerFactory
-> ImpactRuntimeRequest
-> ContentRuntimeContribution
```

第一版 request 模型：

```text
CharacterRuntimeRequest
├── handler_key
├── character_key
├── slot
├── params
└── asset?

WeaponRuntimeRequest
├── handler_key
├── weapon_key
├── slot
├── params
└── asset?

ArtifactRuntimeRequest
├── handler_key
├── artifact_key
├── slot
├── artifact_kind
├── piece_count?
├── params
└── asset?

ImpactRuntimeRequest
├── handler_key
├── slot?
├── owner_type
├── owner_key
├── impact_key
├── impact_kind
├── unlock_key?
└── params
```

第一版注册入口：

```text
registry.register_character_factory("character.furina", create_furina_content)
registry.register_weapon_factory("weapon.sword.splendor_of_tranquil_waters", create_weapon_content)
registry.register_artifact_factory("artifact.golden_troupe", create_artifact_content)
registry.register_impact_factory("impact.generic.damage", create_generic_damage_impact)
```

第一版创建入口：

```text
registry.create_character(request)
registry.create_weapon(request)
registry.create_artifact(request)
registry.create_impact(request)
```

规则：

- `handler_key` 仍保持全局唯一，即使注册入口按内容类型区分。
- 组装阶段按资产类型调用对应入口并做强校验。
- 角色 handler 不接收武器 request，武器 handler 不接收角色 request。
- impact handler 只接收影响展开相关上下文，不通过泛化 `asset` 或 `params` 字段猜测内容类型。

推荐注册方式：

```text
content/characters/fontaine/furina/content.py
-> register(registry)
-> registry.register_character_factory("character.furina", create_furina_content)
```

factory 输入由对应 request 模型提供，通常包含：

- 资产对象。
- 队伍槽位。
- 等级、天赋等级、命座等配置。
- impact payload、资产 effect payload 或 params。
- 组装阶段可用的只读上下文。

factory 输出应是 `ContentRuntimeContribution` 或更具体的角色、武器、圣遗物贡献对象。

## 7. 推荐目录

```text
content/
├── __init__.py
├── bootstrap.py
├── registry.py
├── models.py
├── characters/
│   └── fontaine/
│       └── furina/
│           ├── __init__.py
│           ├── content.py
│           ├── actions.py
│           ├── impacts.py
│           ├── state.py
│           └── hooks.py
├── weapons/
│   └── sword/
│       └── splendor_of_tranquil_waters/
│           ├── __init__.py
│           ├── content.py
│           ├── impacts.py
│           └── hooks.py
├── artifacts/
└── generic/
```

说明：

- `characters/` 按地区分组，再按角色目录分组，例如 `characters/fontaine/furina/`。
- `weapons/` 按武器类型分组，再按武器目录分组，例如 `weapons/sword/splendor_of_tranquil_waters/`。
- `content.py` 保存注册入口和 factory。
- `actions.py` 保存动作解释器和时间轴规格构造。
- `impacts.py` 保存 impact factory。
- `state.py` 保存角色专属运行态。
- `hooks.py` 保存天赋、命座和触发器。
- 圣遗物目录后续可按套装或区域再细分，当前暂不展开。

## 8. 装配关系

推荐装配流程：

```text
SimulationAssembler
-> 读取队伍槽位资产
-> 查找 character.handler_key
-> 创建 CharacterContentRuntime
-> 查找 weapon.handler_key
-> 创建 WeaponContent contribution
-> 查找 artifact / impact handler_key
-> 创建 ArtifactContent / GenericContent contribution
-> 汇总 RuntimeContentBundle
-> 构造 ActionInterpreterRegistry、ActionRegistry、ImpactDispatcher、ImpactRequestDispatcher
-> 注入 ActionManager、ImpactRuntime、HookRegistry、ModifierRegistry 等运行时对象
```

缺资产、缺 handler、JSON 格式错误或 handler 参数不合法，应在组装阶段报错。

## 9. 与 core 的边界

`content/` 可以依赖 `core/` 的通用协议、数据类和运行时接口。

`core/` 不能依赖 `content/`。

推荐方向：

```text
core 定义协议：
ActionInterpreter
Action
ImpactFactory
CreatedObjectBehavior
EventHook
Modifier

content 实现协议：
FurinaActionInterpreter
FurinaNormalAttackAction
FurinaImpactFactory
FurinaSalonMemberFactory
GoldenTroupeModifier

application/assembly 注入实现：
ActionInterpreterRegistry(key -> selector -> ActionInterpreter)
ActionRegistry(action_key -> Action)
ImpactDispatcher(impact_key -> ImpactFactory)
ImpactRequestDispatcher(kind -> mechanic handler)
CreatedObjectRuntime(behavior_key -> CreatedObjectBehavior)
```

`core/` 不保留独立的 `SummonSystem`、`SummonSpec`、`SummonInstance` 或 `SummonFactory`。内容创建的场上对象应作为带生命周期的空间实体处理；无空间持续逻辑归机制、状态或 hook。

## 10. 与动作系统的关系

角色动作解释器和具体角色 Action 都属于角色内容。

链路：

```text
ActionManager
-> 根据 InputSession 的固定 binding 找到 CharacterActionInterpreter
-> 解释 InputSessionView
-> 获得 ActionInterpretationResult
-> 根据 PreparedAction.action_key 查询 ActionRegistry
-> 创建并管理 ActionInstance(Action)
```

角色解释器负责输入判断和动作准备；角色 Action 负责具体动作运行、控制命令、取消与影响点生成；`ActionManager` 统一拥有输入会话、动作准入、锁、实例和生命周期。

## 11. 与影响结算的关系

动作影响点到期后，需要展开为 `ImpactRequest`。

推荐方向：

```text
ActionImpactPoint
-> ImpactDispatcher
-> content impact factory
-> ImpactRequest[]
-> ImpactRequestDispatcher
-> DamageSystem / HealSystem / AuraSystem / BuffSystem
```

`content` 可以根据角色、武器、圣遗物和 params 生成影响请求，但不负责最终数值结算。

内容创建空间实体也走影响请求：

```text
ActionImpactPoint
-> ImpactRequest(kind=create_entity)
-> ImpactRequestDispatcher 转交 CreatedObjectRuntime
-> CreatedObjectRuntime 创建 CreatedObjectRuntimeState
-> Space 登记 SpatialEntity
-> 后续 ImpactRequest[]
-> 对应领域系统结算
```

`content` 定义空间实体创建规格和后续行为入口，`core/space` 管理内容创建空间对象运行态和实体登记，并复用 `core/entity_states/lifecycle.py` 的通用生命周期值对象。

## 12. 已确认方向

- `content/` 是行为实现层，不是资产读取层。
- `handler_key` 是唯一代码绑定入口。
- 内容实现应产出运行时贡献，而不是在组装阶段随意修改世界。
- `ContentRuntimeContribution` 放在 `content/models.py`，由 `application/assembly` 拆包注入运行时系统；`core` 不接触整包贡献对象。
- 不保留泛化 `RuntimeHandlerRequest` 作为长期设计；角色、武器、圣遗物和 impact 使用专用 request、factory、注册入口和创建入口。
- `handler_key` 保持全局唯一，即使注册入口按内容类型区分。
- 角色内容主要贡献动作解释器、专属状态、影响工厂、内容创建对象行为和角色 hooks。
- 内容创建空间实体第一版只能由角色内容贡献；武器、圣遗物和 generic content 不贡献内容创建对象行为，因此第一版不设计跨内容类型空间实体创建优先级。
- 内容创建空间实体由动作影响创建，角色 content 定义创建规格、空间参数和后续行为入口；对象运行态和实体登记由 `core/space` 管理，生命周期值对象复用 `core/entity_states/lifecycle.py`。
- `core/` 不保留独立 `core/summons` 模块；无空间持续逻辑归机制、状态或 hook，不命名为召唤物。
- 武器和圣遗物主要贡献修饰器、触发器和影响工厂。
- 武器和圣遗物不提供动作解释器，不影响角色动作解释结果，也不能改变动作本身；它们只能影响属性、事件响应、影响请求和后续机制结算。
- `event_hooks` 用于在运行时事实发生后产生下一结算轮次的 `ImpactRequest`、领域命令或 owner state patch，不直接修改 `RuntimeWorld` 或领域 Store。
- `modifiers` 用于结算时提供纯修饰项，由对应领域系统统一聚合；modifier 本身无副作用。
- 新伤害实现使用类型化 `damage_modifier_providers`，不通过 `scope` 字符串猜测伤害协议。
- hook 和 modifier 都不能改写输入解释、动作时间轴、取消窗口或输入会话。
- 动作影响链路使用 `ImpactRequest`、`ImpactDispatcher`、`ImpactFactory` 等术语；`effect` 预留给 Buff/Status/Modifier 等状态或修饰语义。
- `ImpactRequest`、`ImpactDispatcher` 和 `ImpactFactory` 建议放在独立 `core/impacts/` 模块。
- 角色专属状态不塞进通用 `CharacterRuntimeState`，统一由 `ContentStateStore` 按 `(slot, handler_key)` 管理。
- 角色专属 state 只能由 owner content 读写；武器、圣遗物第一版不能直接读取或修改角色专属 state。
- content state 快照通过 `ContentStateSnapshotProvider` 输出，payload 必须是 JSON-compatible 数据。
- 具体角色、武器、圣遗物机制需要可信来源或 golden case 支撑。
- 当前验证阶段已经验证最小测试伤害链路；真实角色、武器、圣遗物和反应数值仍必须有可信来源或 golden case。
- 真实资产在行为未实现前默认不填 `handler_key`；`generic.noop` 与 `generic.test_*` 只用于测试或占位，不作为真实实现标记。
