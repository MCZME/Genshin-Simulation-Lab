### D-017 元素反应契约冻结

> 状态：生效

- 普通反应由本次元素、ICD 后实际元素量和目标 Aura 决定；碎冰额外读取稳定 `strike_type=BLUNT` 证据，来源种类、武器显示类型和布尔“允许反应”开关不参与。
- 反应处理当前 Impact 时只能调整该 Impact 已携带的关联伤害；新增伤害一律成为同帧下一 settlement round 的子 Damage Impact。
- 增幅/剧变：Profile 拆为 `AmplifyingReactionProfile | TransformativeReactionProfile` 强类型联合；超载、超导使用独立稳定 key 与 Gate，effect group 在下一 settlement round 执行。
- 燃烧：普通燃烧火草建立时创建 `2 GU` 燃元素与 `BurningState`；周期火每 `15` 帧造成 `0.25` 倍率火元素剧变伤害，普通火每 `120` 帧施加 `1 GU`，不进入 Aura ICD。
- 激化：原激化按草雷 `1:1` 实际消费创建 `QUICKEN`；超激化/蔓激化不消费激元素，在通用公式的激化附加区结算（`CatalyzeReactionInput`），倍率 `1.15/1.25`，精通公式已固定。
- 绽放：普通绽放/绽放爆炸/超绽放/烈绽放，水与类草 `2:1` 消费；草原核持续 `360` 帧、每队最多五枚，容量淘汰引爆最老核心；`bloom_family` 共享 `30` 帧两次 Gate，三种伤害分类独立。

各反应稳定字段、key 和验收入口见对应反应契约与[元素反应公共模型契约](../契约/元素反应/公共模型契约.md)。

### D-018 月反应独立契约冻结

> 状态：生效

- 月绽放：独立 `ReactionKey`、handler 与方向，capability 准入加严格水草签名，与普通绽放互斥（触发时独占）；反应本身不产生伤害，草露由 ReactionStore 拥有，角色月曜伤害走 `CHARACTER_DIRECT`；生产公式已注册。
- 月感电：独立 key 与严格水雷签名，与普通感电互斥（触发时独占）；occurrence 不消费水雷（后手按 `20%` 损耗保持共存）；`LunarStormCloudState` 生命周期 `360` 帧、每 `15` 帧攻击、逐目标 Gate 并消费 `0.4 GU`；复合月曜伤害按 `0.60/0.30/0.05` 加权。
- 月结晶：独立 key 与严格水岩签名，只替换水结晶方向；场上最多三枚月笼、共享累计器、每三次月结晶触发一次谐奏；谐奏复合月曜伤害不产生元素附着。
- 三条月反应均已有生产 bootstrap 与 golden case；未确认项（可回放随机、岩造物干扰、精确倍率等）记录在正式契约，不改变生产注册状态。

### D-068 星超导契约冻结

> 状态：生效

- 独立 key 集合：`reaction.stellar_conduct`、`reaction_handler.stellar_conduct`、`reaction_capability:stellar_conduct`、`reaction_state.polestar_field`、`reaction_state.stellar_conduct_counter`、`reaction_spatial_profile.polestar_field`、`damage_formula.stellar_reaction`；命名采用官方英文 `Stellar-Conduct` / `Polestar Field` 的 snake_case，不使用社区俗称 `star_superconduct`，不复用 `lunar_*`。
- 星超导候选 `selection_priority=110`：capability 与角色来源齐备时排他替代普通超导，否则回退普通超导；冰雷按 `min(incoming, aura)` `1:1` 消费，两个方向签名与普通超导一致。
- 星超导没有公共反应伤害：occurrence 只声明极星辉域计划。领域 State/Space binding 与雷暴云一致；域内重触发（X/Z `<= 12`，忽略 Y 轴）只刷新生命周期、保留实例与圆心，域外重触发替换旧领域；同一队伍至多一个领域。
- 附着计数按队伍共享，不绑定 Field 实例；`240` 帧窗口到期结算快照层数、清空窗口并推进；新领域生成时排除触发攻击身份，只影响当前窗口；不建立"前 4 秒"预热窗口，`0` 层直伤星烁基础系数为 `1`。
- 星烁伤害使用独立 `damage_formula.stellar_reaction` 与强类型 `StellarReactionDamageInput`/`StellarReactionDamageResolution`，首期 `character_direct`，`reaction_composite` 留待星扩散；修饰只接受星烁专属阶段与共享的倍率/暴击/抗性通用阶段，不接受增伤、防御等其余普通槽位阶段，也不与通用反应输入混用（位置与白名单见 D-075、D-082 与[伤害系统契约](../契约/伤害系统契约.md)第 3.2 / 6 节）。
- 数值冻结状态：领域持续 `420` 帧（约 7 秒）、计数窗口 `240` 帧、领域半径 `12` 为当前实现基线，未作正式数值冻结；冻结状态与验收见[星超导反应契约](../契约/元素反应/反应/星超导反应契约.md)。
- 角色直伤星超导 content 技能模组（角色资产接入）为后续切片；未确认项记录在正式契约非目标。

原因：把星超导建为独立 Definition 而非普通超导 Rule 的条件分支，可复用月相反应的选择优先级与回退模式，并保持普通超导语义不变；早期"星超导周期结算产生公共反应伤害"的规划已被资料修正（星超导不存在反应星烁伤害），周期结算的公共结果改为层数快照与系数可查询性；星烁公式独立于通用反应区，是因为直伤星烁的星烁基础增伤、大权区、羽毛区等区间无法由普通 `DamageModifierTerm` 表达。

### D-069 星扩散契约冻结

> 状态：生效

- 独立 key 集合：`reaction.stellar_swirl`、`reaction_handler.stellar_swirl`、`reaction_capability:stellar_swirl`、`reaction_state.stellar_swirl_vortex`、`reaction_spatial_profile.stellar_swirl_vortex`、`buff.reaction.stellar_swirl.radiance`、伤害标签 `星扩散风` / `星扩散冰`、damage kind `reaction_damage.stellar_swirl_wind` / `reaction_damage.stellar_swirl_ice`、去重 Gate `reaction_gate.stellar_swirl.wind`；复用 `damage_formula.stellar_reaction` 并启用 `reaction_composite` 模式。命名采用官方英文 `Stellar-Swirl` 的 snake_case，不使用社区俗称 `star_swirl`，不复用 `lunar_*`。
- 候选 `selection_priority=110`：capability 与角色来源齐备时排他替代普通扩散，否则回退；本期只注册风命中冰一个方向，消费与普通扩散一致（`incoming_consumed = min(incoming, aura×2)`、aura 侧减半）；风元素自附着方向依赖 `AuraKind` 扩展 ANEMO，明确后置，反向方向 key 仅预留不注册。
- 星辉风旋为 `battle` 作用域全场唯一的 State/Space binding 对象：锚定首个反应目标位置、等级 `1~6`、`180` 帧自动爆炸、6 级立即爆炸、升级不移动锚点也不刷新爆炸计时；6 级爆炸后同帧后序目标创建等级 `1` 新风旋，账本与伤害源窗口无跨风旋继承。
- 伤害源与参与者分层：星扩散·风伤害源 = 触发者，参与者 = 触发者 + 冰贡献在反应发生时活跃且被本次反应消费的角色（集合语义、不要求参与者持有 capability）；星扩散·冰无反应触发者，伤害源 = 生命周期内最后一次星扩散·风的触发者（含被去重挡掉与 6 级同帧事件），参与者 = 各风参与者并集；伤害源必在参与者集合内；结构性至多 4 名，兜底按首次参与帧升序保留。
- 风伤害去重是伤害结算层规则：去重只拦截伤害实例（Gate 窗口 `30` 帧基线、至多 1 次），不影响反应发生、元素消费、风旋等级累加、参与者计入与伤害源认定。
- 星扩散·风单体、星烁基础系数 `0.75`、可暴击、不附着元素；星扩散·冰爆炸按等级使用圆柱 AOE（半径 `6/8`、高度 `4` 仅作强类型记录）、系数 `2/3`、可暴击、对命中目标附着 `1U` 冰元素并归因于伤害源，后续反应触发者随之。
- 反应星烁复合公式：逐参与者以自身等级的 `reaction_base_value` 替换 `scaling_value` 结算，按折前伤害稳定排序取前 `4` 名，权重按名次固定 `0.60/0.30/0.05/0.05` 且不按参与人数重归一化（与月曜复合实现同构），逐参与者独立暴击决策；聚合与组分审计写入 `StellarReactionDamageResolution`。
- 辉映·星扩散 Buff：`480` 帧基线、每次风触发统一刷新，直伤星扩散基础系数词条固定 `1.0`；目标集合由辉映资格证据决定，角色与 key 粒度在角色资产接入阶段定案；与辉映·星超导可共存，同一角色同时满足两种状态条件时星超导优先（能力层读取优先级执行，Buff 层不互斥）。

### D-070 状态效果队伍作用域主体

> 状态：生效

- `AttributeSubjectKind` 增加两个队伍作用域 kind：

  | kind | 作用范围 | 挂载身份 |
  | --- | --- | --- |
  | `team` | 队伍全部角色 | `AttributeSubjectRef.team(team_ref)` |
  | `active_character` | 只作用于当前场上角色 | `AttributeSubjectRef.active_character(team_ref)` |

- 两个 kind 的 `entity_id` 都是队伍稳定作用域 id（例如 `player_team`），不是角色战斗实体 id，也不是空间实体 id；作用范围差异只由 kind 表达。属性主体 kind `active_character` 与空间实体 kind 同名但不同域，不互相推导。
- 队伍作用域 kind 在定义规则上与 character / target 完全一致，不附加额外限制：`marker_only` 与 attribute modifiers 的互斥规则照旧，带 attribute modifiers 的定义照常产出 `BuffAttributeModifierProvider`。
- 队伍作用域词条经属性侧投影可见：公共属性定义全部接受 `team` / `active_character` 为 `owner_kinds`，角色侧属性（如 `stat.atk.*`、`bonus.shield.strength`）同样接受队伍作用域主体，只是不接受 `target`；`BuffAttributeModifierProvider` 在查询角色主体时除精确匹配外，追加该角色所属队伍的 `team` 记录与（当该角色为当前场上角色时）`active_character` 记录；投影是只读展开，`target` 主体与角色主体之间不互相投影，不引入主体继承或下钻。
- 投影所需的队伍归属与场上判定由装配期注入的窄只读端口 `TeamScopeProjectionPort` 提供（适配 `TeamRuntimeState`），不在属性或 Buff 领域硬编码队伍作用域 id；未注入端口时不投影。
- 冲突仍以 `(target_ref, conflict_key)` 判定：同一 conflict key 在 `team`、`active_character`、角色与目标主体之间互不冲突；同一主体上的刷新兼容性照旧要求 definition、target、applier 与 source context 一致。
- 消耗型效果使用既有 `BuffRemovalReason.CONSUMED` 的显式移除请求表达，不新增生命周期状态。
- 消费方按对应主体精确查询后，再自行与"该角色是否符合该 kind 的作用范围"组合；Buff 领域不感知场上角色，也不做主体迁移。唯一例外是属性 provider 的队伍作用域投影：它按装配期注入的端口把队伍作用域记录展开到角色面板，仍是属性侧只读行为，不改变 Buff 领域读取语义。

原因：队伍级效果此前只能展开成每个角色一份（元素共鸣与辉映 Buff 均为 `target_kinds={CHARACTER}`），而"作用于整队"与"只作用于当前场上角色"是两种不同语义——前者与场上是谁无关，后者是位置级效果、切人后应由新前台接管；逐角色复制这两种语义都会引出"切人后效果归属谁"的迁移问题。把槽位做在队伍系统（`TeamRuntimeState`）会形成与 `BuffRuntime` 并行的第二套生命周期、审计与结果库投影机制，并违反"不得为了复用把不同机制塞进通用 Store"的硬规则，因此改为在 Buff 系统内增加两个队伍作用域主体，复用既有全部机制。

### D-071 星扩散跳跃能力 Buff 的形态与消耗链路

> 状态：生效

- 风旋爆炸命中角色后的跳跃能力 Buff（`buff.reaction.stellar_swirl.jump_boost`）挂**位置级队伍作用域主体** `AttributeSubjectKind.ACTIVE_CHARACTER`（`entity_id` 为队伍稳定作用域 id `player_team`），**不挂**精确角色主体 `CHARACTER`：跳跃只有前台角色能执行，位置级语义天然表达"谁在前台谁享受、切人后由新前台接管"，且不引出"命中时是谁就锁死给谁"的迁移问题。
- Buff 形态为 `marker_only`，不声明任何属性词条；`REFRESH` + `REPLACE_LATEST`、至多 `1` 层、存续 `360` 帧（约 6 秒基线）。"提高跳跃能力"没有任何来源化的量化口径（跳跃高度、倍率、体力消耗、二段跳均无数值），位移设施也没有跳跃能力模型可写，因此**不冻结任何数值**，只做存在标记。
- 命中判定与挂载身份分离：爆炸 selection 显式声明 `reaction_target.hostile_effect` 资格策略，不继承 `bloom_damage` 默认值；范围内角色在 Effect 循环内按 `SELF` 关系被挡下（不受冰伤害、不被附着），跳跃 Buff 改由协调器在 Effect 循环**外**的独立通道申请。这样"爆炸不自伤"由资格意图表达，而不是依赖 `StellarReactionDamageImpactEffect` 恰好不在 bloom 自伤白名单的 Effect 类型联合里。
- 消耗时机为**起跳那一刻**而非落地：Buff 在起跳当帧仍可被读取（用于提高本次跳跃），由跳跃动作自身在解析时以 `BuffRemovalReason.CONSUMED` 显式移除，不新增生命周期状态（归属修订见 D-072）。
- 位移设施（`core/movement`）只提供位移入口：`movement` impact 的 `jump.upward_velocity` → `start_jump` 置入向上初速度并推进运动，初速度由调用方给出，设施不内置任何角色跳跃数值；设施不认识 Buff，也不发布起跳事实。
- 本期**不接线**：角色跳跃的速度/高度资料缺失，接内容必然引入无来源数值；角色跳跃动作与其 impact factory 未建，位移入口只由单元测试驱动。读写通道本身已具备（D-073）。

原因：资料只给出"风旋爆炸命中角色后，提高其未来 6 秒跳跃能力；完成一次跳跃后该效果消失"这一句话，命中范围、精确帧数与"跳跃能力"的口径全部未来源化；过早冻结数值会让后续 golden case 建立在猜测上。选位置级主体而非精确角色，是因为空间侧只有 `SpatialEntityKind.ACTIVE_CHARACTER` 一种角色实体（后台角色没有空间实体），"爆炸命中角色"必然是前台角色，与位置级挂载自洽；精确角色主体还会引出"Buff 给谁、切人后归谁"的迁移问题。起跳即消耗而非落地才消耗，是因为 Buff 的语义是"提高本次跳跃"，必须在起跳那一帧仍可读取；同时"完成一次跳跃"在没有连续跳跃状态模型时可判定的最小单位就是那次跳跃动作本身。Movement 不认识 Buff、Buff 不认识 Movement 是系统自治的硬规则，而跳跃动作本身就是消费方，因此消耗由动作侧自持，不再另加协调器（见 D-072）。

- **粒度按位置切分**：公式里每个可被修饰的位置对应一个阶段；**通用公式已有对应位置的一律复用通用阶段**，不另设同名阶段——星烁的倍率位复用 `component_coefficient_percent_add` / `component_coefficient_flat_add`（需绑定 `component_key`），暴击位复用 `crit_rate_add` / `crit_damage_add`，抗性位复用 `resistance_add`；月曜的暴击位与抗性位、剧变的抗性位同样复用。各反应公式**专有**位置才使用专属阶段，一位置一阶段，互不替代。不采用"反应类共用一个阶段"的方案——按公式切分语义边界清晰，各白名单互不牵连，新增反应类型时不会误放行。
- 各公式白名单：星烁 `STELLAR_ALLOWED_MODIFIER_STAGES` = 「6 个星烁专属 + 5 个共享通用阶段」；月曜 `LUNAR_ALLOWED_MODIFIER_STAGES` = 「4 个月曜专属 + 暴击位与抗性位三个共享通用阶段」；剧变 `TRANSFORMATIVE_ALLOWED_MODIFIER_STAGES` = 「1 个剧变专属 + 抗性位（`resistance_add`）」；`GENERAL_ALLOWED_MODIFIER_STAGES` **不含**任何反应专属阶段。**各公式的专属阶段两两互不重叠**；共享通用阶段允许重叠，这正是"同位置复用"的本意。月曜的倍率位与反应系数位不开放（前者的 component_key 无法在请求级顶层收集里寻址，后者是机制冻结的反应口径，无内容侧来源），详见[伤害系统契约](../契约/伤害系统契约.md)第 3.2 与 6.4 节。
- 专属阶段以 `fsum` 汇总后**并入**对应基线，**不替换**调用方冻结的基线值；改动不触及防御策略（剧变仍 `approximate_unity`）、不暴击口径与其余乘区顺序。**位置 3（基础系数）取加算口径**：若写成 `base × Π(1 + x)`，它与位置 4（基础增伤）在数学上等价，两个位置将失去分设意义，因此取 `base + Σ`。
- **星烁暴伤不设专属阶段**：暴伤槽位 `crit_damage_add` 由星烁与通用公式共享（`STELLAR_ALLOWED_MODIFIER_STAGES` 含之），剧变公式仍拒绝它（剧变不暴击）。星烁伤害的暴击区本来就读取面板暴伤，专属阶段不带来额外语义，只会要求公式把专属词条再折算回通用槽位；作用范围因此改由 provider 自筛 `formula_key` 决定，与 `crit_rate_add` 的处理方式一致。
- **星烁复合伤害的修饰按参与者收集**：星烁复合伤害对每个参与者独立结算，组分查询只替换来源主体并沿用整次请求的 `formula_key` 与星烁输入，由公式经 resolver 注入的收集入口重新收集一次修饰项。按 `source_ref` 自筛的 provider 只作用于该参与者自己的组分；不按来源过滤的 provider（队伍级效果）对每个参与者各贡献一次，既有语义不变。组分收集的词条同样必须通过星烁白名单校验。
- 越界一律拒绝：普通阶段进入反应公式、任一反应专属阶段进入通用公式或其他反应公式（共享通用阶段除外），都在入公式前由 `validate_formula_modifier_stages` 抛出 `DamageProviderViolationError`，不做静默忽略。公式体内原有的 `raise` 退化为防御性兜底。

原因：内容侧需要表达"装备者对某类反应伤害提升固定比例"的常驻加成（本批两套圣遗物均涉及）。这类效果作用于**反应伤害**而非角色直伤，因此不能走直伤槽位词条；而反应公式的反应加成位此前只能由机制常量或调用方冻结值写入，内容侧无贡献入口。改为属性通道会与剧变契约"等级系数、元素精通与精通加成在 occurrence 时冻结，Damage 不查询来源属性"直接冲突；新增通用修饰项传递框架则成本远高于收益。补专属阶段复用现成的 `allowed_modifier_stages` 白名单、`_validate_formula_stages` 校验、`_sum_terms` 汇总与 `DamageModifierProvider` 协议，无新概念，且内容侧与既有 `CRIT_RATE_ADD` 用法完全同形。

### D-082 槽位账单是伤害公式的唯一修饰通道

> 状态：生效

- **任一伤害公式的可修饰位置都必须开成槽位账单通道。** 位置指公式里一个独立的基线来源与消费点；槽位值一律按 `基线 + Σ(该槽位修饰项)` 合并，基线只有两种合法来源：
  - 面板读取（`DamageModifierTerm.panel_read()`，`provider_key = panel.<attribute_key>`）；
  - 机制侧冻结值（机制层在 occurrence 或组装时按资料算出的机制常量）。
- **效果进入数值的唯一入口是 `DamageModifierProvider` 产出的 `DamageModifierTerm`**，由伤害系统收集、署名、叠加、消费与审计。判定标准：

  | | 做法 | 判定 |
  | --- | --- | --- |
  | ✅ | 内容侧声明攻击身份：倍率、属性、元素、主攻击标签 | 允许——这是攻击定义，不是效果 |
  | ✅ | 机制侧冻结反应基线（等级系数、元素精通、权重、基础系数） | 允许——这是机制事实 |
  | ✅ | 效果以 `DamageModifierProvider` 在结算时产出词条 | **唯一允许的效果落地方式** |
  | ❌ | 在 Impact / Action / 内容组装阶段把效果算进区间值（写入强类型字段、预乘属性、合并成单标量） | 禁止——数值与署名同时脱离账本 |
  | ❌ | 内容侧把证据（层数、标签、Buff 投影）换算成最终加成数值后写入字段 | 禁止——换算与审计属伤害侧职责 |

- **强类型输入只承载反应身份、结构与冻结基线**，不再是区间值的唯一来源。输入字段可以被专属阶段的贡献叠加，但不得被内容侧预乘或预换算写入。
- **开放度不足是缺口，不是合法的设计分支。** 一个位置不开放修饰，落到该位置的效果只能在别处把数值算好再塞进来，审计链条在此断开。四个公式共用同一账本结构（面板词条 / 效果词条 / 收集叠加 / 分区审计），差异只在已开放的槽位数量。
- **但白名单不得出现没有消费点的阶段。** 开槽位时必须在公式体内接上消费点——例如抗性位要求公式体先按 `面板抗性 + Σ resistance_add` 合并有效抗性再传给抗性策略，只把阶段加进白名单而不消费会是零效果阶段。同理，不为没有已知来源的位置臆造阶段。
- **合并值必须同时进入实算与审计。** 每个位置保留「冻结基线 / Σ修饰项 / 合并值」三段，使 `to_dict()` 能直接回答"这个值里有哪一部分是谁给的"；provider 署名沿用 `applied_terms` 既有机制，不新增字段。
- 本条目生效时的已知开放度缺口，随 2026-09-29 月曜槽位化收窄为：月曜不开放位置 ①（组分基础值）与位置 ②（反应系数）——前者受"直伤倍率由参与者承载、`component_key` 只能在请求级收集里寻址"的机制限制，开放它需把直伤倍率挪到请求级（契约变更，另行评估）；后者是机制冻结的反应口径，无内容侧来源。剧变不开放倍率位、基础系数位、精通位与二次增幅位。位置边界与开放度表见[伤害系统契约](../契约/伤害系统契约.md)第 6.4 节与[剧变反应伤害契约](../契约/元素反应/剧变反应伤害契约.md)第 5.1 节。**除上述已定案的不开放位置外，不得为没有已知来源的位置臆造阶段。**

原因：伤害系统的审计能力建立在槽位账单之上——「面板读取贡献 + 效果修饰贡献」是唯一能让每个乘区值可回源的结构。此前星烁公式把十个位置压缩成 `StellarReactionDamageInput` 的强类型字段，倍率与属性在输入边界被合并成单标量 `scaling_value`，效果无法落在具体位置上，只能在内容侧算好后塞入；公式内部甚至保留了"先把所有区间装配进输入、再调纯函数"的同构体。结果是数值与署名一起脱离账本：审计里看不到是谁贡献的，也无法把倍率与属性分别修饰。替代方案有两条，都被否决：一是保留强类型字段、另开若干"额外加成"字段，那只是把内容侧换算搬到更窄的字段上，审计链条仍然断开；二是让内容侧继续预乘，代价是任何"提高倍率 X%"的效果都会连带放大属性。改按位置切分槽位后，复用既有的白名单校验、`_sum_terms` 汇总与 provider 协议，无新概念。

### D-083 月曜反应系数与分配权重口径

> 状态：生效

- 资料对月曜反应伤害给出**两套等价写法**，本仓库采用「未折入」写法，并把两者的换算关系固定为契约：

  | 口径 | 月感电 | 月结晶 | 分配权重 | 最高组分实际系数 |
  | --- | ---: | ---: | --- | ---: |
  | 未折入（本仓库） | `3.0` | `1.6` | `0.60 : 0.30 : 0.05`（其余组分沿用 `0.05`） | `3.0 × 0.60 = 1.8`、`1.6 × 0.60 = 0.96` |
  | 折入 | `1.8` | `0.96` | `1 : 1/2 : 1/12` | 同上 |

- 两套口径逐组分等价：`0.60 : 0.30 : 0.05 == 1 : 1/2 : 1/12`，且 `3.0 × 0.60 = 1.8`、`1.6 × 0.60 = 0.96`。因此**换口径必须同时改反应系数与分配权重**，只改一边会把 `0.60` 重复计入（改系数）或漏计（改权重），整体偏差恰为 `0.60` 倍。
- 反应系数（未折入口径）取值为 `3.0`（月感电）/ `1.6`（月结晶），与对应反应的**直伤倍率同值**；两者同值不是代码复用错误，而是资料本身的定义方式（`反应系数` 与 `角色倍率` 在月曜体系里是同一个数）。
- 权重在代码中单点定义（`core/systems/damage/lunar.py` 的 `LUNAR_COMPOSITE_WEIGHTS`），公式体按名次取值、超出表长沿用最后一项，不得在公式体里重复硬写 `0.60 / 0.30 / 0.05`。
- 月绽放不产生反应月曜伤害（反应本身无倍率），不涉及本口径；月感电与月结晶的反应复合路径共用同一条系数 + 权重聚合结构。
- 数值出处：米游社《元素反应(高等元素论)》(`article/25901063`)：「直伤月反应倍率(月感电 3.0, 月结晶倍率 1.6)，反应月反应倍率(月感电 1.8, 月结晶 0.96)」；米游社《月曜反应》(`article/77019346`)：分配系数「`0.6 × 第一高 + 0.3 × 第二高 + 0.05 × 其他`」；BWIKI《元素反应》页「反应倍率」表与《月结晶伤害公式》页。适用版本：月之八。
- 本节冻结的是**口径与换算关系**，不是新增数值；`3.0 / 1.6` 与 `0.60 / 0.30 / 0.05` 在本次定案前已是生产实现值。

原因：整理月曜位置开放度时曾把资料里的「反应倍率 1.8 / 0.96」判为代码 `3.0 / 1.6` 的错配，并计划把常量改为 `1.8 / 0.96`。复核一手资料后确认这是**两套等价口径**而非错配：`1.8 / 0.96` 正是把权重表里的最高项 `0.60` 折进系数后的写法，配 `1 : 1/2 : 1/12` 分配；代码采用的 `3.0 / 1.6` 配 `0.60 : 0.30 : 0.05`，逐组分结果完全相同。若按原判断只改系数，整体会偏小 `0.60` 倍。两套写法在社区资料里混用（同为 BWIKI 体系的「反应倍率」表给 `3 / 1.6`，「伊涅芙/攻略」正文写「反应基础倍率为 1.8」），因此把口径与换算关系冻结成契约正文，避免后续再按单边数值判断"错配"。

### D-084 公开属性绝对值口径与游戏规则基础面板

> 状态：生效

- 公开属性一律存储**绝对值**，不是"相对基底的加成量"。三项由游戏全局规则给定、每个角色都具备的基础面板值按此口径以**基础贡献**注入角色主体，不写成 `AttributeDefinition.default_value`（属性系统契约第 7.1 节禁止用 `default_value` 承载游戏规则默认面板）：

  | Key | 基础面板值 | 来源引用 |
  | --- | ---: | --- |
  | `stat.crit_rate` | `0.05` | `system` / `base.stat.crit_rate` |
  | `stat.crit_damage` | `0.5` | `system` / `base.stat.crit_damage` |
  | `stat.energy_recharge` | `1.0` | `system` / `base.stat.energy_recharge` |

- 下游公式不再补基底：伤害侧暴击乘数 = `1 + crit_damage`（暴击判定命中时）；能量侧 `recharge_multiplier` 直接返回 `stat.energy_recharge` 本身，原 `1 + recharge_bonus` 作废。
- 属性语义随之统一：能量结算事件 `EnergyRecipientResolution.recharge_bonus` 改名 `energy_recharge`，因为它现在承载效率绝对值而非加成。
- 基础面板只注入**角色主体**：目标主体的这三项仍取解析代数默认值 `0.0`，目标不获得角色基础面板。其余加法属性（元素精通、各类伤害加成、抗性等）没有游戏规则基础值，未注入时同样取 `0.0`。
- 常量单点定义在 `core/attributes/base_stats.py`，装配期在 `application/assembly/attributes.py` 的角色主体上注入；来源类型 `system`，使基础面板值在属性来源链里可署名。

原因：这三项基础值此前**全仓没有设置**——`CharacterLevelStats` 只承载 `base_hp/base_atk/base_def`，`_iter_base_contributions` 不播种这三项，additive 定义统一 `default_value=0.0`，内容侧从不引用 `stat.crit_rate` / `stat.crit_damage`，前端只按百分比格式化原值。而暴击侧是按**绝对值**消费的（`crit_rate = 面板值 + Σ`、`multiplier = 1 + crit_damage`），因此任何可暴击伤害都少 5% 暴击率与 50% 暴击伤害：以实测 `DAMAGE_RESOLVED` 事件为例，面板暴击率 19.2%（应为 24.2%）、暴击伤害 44.1%（应为 94.1%），暴击命中时乘数 `1.441` 而非 `1.941`。与此同时，元素充能效率的基础 100% 此前以 `recharge_multiplier = 1 + recharge_bonus` 的隐式 `1.0` 承载：属性语义是"加成"，UI 却按「元素充能效率」显示百分比，于是面板显示比实际效率少 100%。两条路径因此混用两套相反口径——本次统一为「属性存绝对值」：暴击补齐基础面板，充能去掉隐式基底并把属性语义改为绝对值（充能效率实算结果不变，只是基底从公式挪进属性）。

### D-087 辉映直伤系数经 Buff 载荷词条与窄端口承载（2026-10-05）

> 状态：生效

- 辉映·星超导 / 辉映·星扩散 Buff 携带的直伤星烁基础系数**不再进入属性系统**：原公共属性键 `stellar.conduct.direct_base_multiplier` 与 `stellar.swirl.direct_base_multiplier` 从 `core/attributes/keys.py` 的公共键注册表移除；系数改以 Buff **载荷词条**（`BuffPayloadTermTemplate` / `BuffResolvedPayloadTerm`，随 `buff.reaction.stellar_conduct.radiance` 的 `stellar.conduct.radiance.direct_base_multiplier` 与 `buff.reaction.stellar_swirl.radiance` 的 `stellar.swirl.radiance.direct_base_multiplier` 留存）承载。
- 内容侧经**星烁辉映证据窄端口**读取：协议 `StellarRadianceEvidencePort`（`core/systems/reaction/radiance.py`，含 `RadianceVariant` / `RadianceEvidence`），实现 `StellarRadianceEvidenceReader` 在元素反应协调层（`core/coordination/elemental_reaction/radiance_evidence.py`，包装 Buff 只读端口），装配期注册为仿真系统。变体优先级口径不变：两种辉映并存时星超导优先（D-069），由端口读取顺序执行，Buff 层不做互斥。
- 公共属性键准入判据同步冻结进[属性系统契约](../契约/属性系统契约.md)第 3 节：公共属性键只承载主体作用域、可被属性修饰系统修饰、参与面板解析与审计的战斗数值；机制证据、反应系数等非面板数值不得注册为公共属性键，新增公共键必须先修订属性系统契约。

原因：通用公式家族中所有反应系数（增幅、激化、剧变、月曜、星烁复合）均由机制侧持有、经请求边界注入，不占用属性键；星烁直伤是唯一"持续状态把角色攻击持续转化为机制伤害"的场景，其请求由角色内容端在能力帧构建、协调器不在链路内，因此需要内容端可读载体。此前把证据投影为属性键让属性系统承担了"机制证据总线"角色，与面板语义混同且有键集无序扩张风险；本次收敛为"属性系统保持面板语义 + Buff 载荷词条承载随生命周期留存的机制数值 + 领域窄端口读取"，与 D-070"随 Buff 生命周期的投影归 Buff 系统、不建并行机制"的定案一致。
