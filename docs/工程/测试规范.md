# 测试规范

> 状态：生效，持续维护。
> 最后更新：2026-08-22。

## 1. 文档定位

测试代码与生产代码同等对待：可读、可审、可维护，并接受同一套质量工具检查。本文的职责是定义 `tests/` 的组织方式、命名、脚手架复用、参数化与断言、golden case 的代码形态以及质量门禁。

本文不保存具体机制、公式或数值真值。机制与数值以 `docs/契约/`、`docs/架构/` 和已确认的 golden case 为准；各系统的测试矩阵与验收入口由对应架构/契约文档拥有。

本文落实[项目决策记录](../决策/项目决策记录.md)中“测试与迁移策略”的已确认结论，并与以下文档分工：

- [迁移阶段安排](./迁移阶段安排.md)：测试分层职责与 golden case 最小记录（工作流要求）。
- [系统自治与跨系统协调](../决策/系统自治与跨系统协调.md)：单元测试的组装边界。
- [原神游戏机制实现规范](./原神游戏机制实现规范.md)：数值可信度与机制实现要求。

## 2. 分层职责

| 层级 | 目录 | 验证对象 | 典型内容 | 不应包含 |
| --- | --- | --- | --- | --- |
| 单元测试 | `tests/unit/` | 单一模块、单一系统、公式、状态提交与错误分支 | 领域 Store、resolver、公式、handler、纯模型、边界与异常 | 组装无关系统、访问 SQLite、启动 UI、依赖具体角色/武器内容（除非测试内容本身） |
| 集成测试 | `tests/integration/` | 组装到运行闭环、跨模块事件流、仓库、持久化与任务执行 | 资产 -> handler -> 装配 -> 运行、纵向内容切片、错误暴露时机 | 代替单元测试逐分支验证公式；把多个无关纵向关注点堆进一个文件 |
| golden case | `tests/golden/` | 有可信输入与预期结果的机制或数值基准 | 伤害、治疗、反应、Buff 覆盖率、时间轴等冻结基线 | 未确认数值；以版本/交付批分类；承担普适单元覆盖 |

归类规则：先问“这个测试要锁定什么”。公式与状态提交进 `tests/unit/`；跨模块闭环进 `tests/integration/`；有可信来源且预期值需要冻结的机制/数值进 `tests/golden/`。同一行为不应为凑层级而在 unit 和 golden 各复制一份；两种层级同时存在时，应确认它们锁定的真值确实不同（例如单元锁公式分支、golden 锁完整输入下的最终数值）。

### 2.1 跨层覆盖归属与重复检测

每个行为只允许一个“真值持有层”：同一输入场景，unit 与 golden 不得同时持有相同的断言目标。归属约定如下：

| 真值类型 | 持有层 | 示例 |
| --- | --- | --- |
| 完整输入下的最终数值、事件顺序、状态与附着副作用 | golden | 蒸发/融化倍率与剩余附着、剧变最终伤害、扩散批量结果 |
| 公式分支、精确消耗份额、内部契约记录、错误分支、状态机不变式 | unit | 精确消耗分数、Gate 决策枚举、打击类型、Store 版本与提交顺序 |
| 资产 -> handler -> 装配 -> 运行的纵向闭环 | integration | 内容切片数值闭环、错误暴露时机 |

新增测试前的检查顺序：

1. 先在 `tests/golden/` 与同领域 unit 目录检索同名或同参数化场景（用 `rg` 搜索测试名与输入常量，或 `pytest --collect-only` 比对参数化 ID）。
2. 若场景已存在于另一层：
   - 断言目标相同 → 不新增用例，把断言补进既有用例；
   - 断言目标不同 → 允许并存，但必须在用例注释中标注另一层对应用例与本层额外锁定的真值，格式：
     `# 与 golden（<相对路径>::<用例名>）共存；本用例只锁定 <真值>。`
3. unit 测试禁止复制 golden 场景的输入构造（相同的 aura 注入序列、消耗批次、frame 布局）来“等价重演”；确需相同输入时，从共享构造器或 fixture 取用，并声明锁定的真值不同。
4. 每个机制在领域收敛清单（如[元素反应收敛切片](./元素反应收敛切片.md)）的覆盖矩阵中登记：机制 -> golden 用例 -> unit 用例 -> 两者关系；矩阵随测试变更同步更新。

以下信号视为重复覆盖，需按上表收敛：

- 同一参数化组合（aura 元素/强度、incoming、数量、frame）在两个层级文件出现，且断言表达式相同；
- unit 测试名含 “golden” 或注释直接引用另一层用例的输入构造；
- unit 用例的输入 ID/请求 ID 复制了 golden 场景命名（如 `*-golden-case-*`）。

### 2.2 资产数据库数据验证边界

资产库（SQLite）与标准 manifest 是只读生成产物，其中的资产绑定（`handler_key`）、
等级数值、效果参数等属于数据内容，**不在测试中验证**：

- 测试不读取本地资产库或 manifest 的固定路径，不断言具体数据库数值，不验证
  “某个资产绑定了哪个 handler”。
- 测试只验证代码行为：内容工厂、注册表、装配、运行时、repository 接口、
  审计规则和错误分支。需要资产数据作为测试输入时，使用内联合成数据或
  `tests/helpers/` 共享构造器，不固定真实资产数值。
- 真实数据内容的正确性由资产构建与校验链路承担：
  `assets fetch-source` → `build-manifest` → `audit-manifest` → `build` →
  `validate`（见[资产数据库设计](../契约/资产数据库设计.md)）。数据库层测试只验证
  读取/写入代码的行为契约，不充当数据审计。
- golden case 的“可信输入与预期输出”指机制或公式基准；资产库数值基线不写入测试，
  需要固定时由数据版本与 audit 规则承载。

## 3. 内容切片测试预算

内容层（角色、武器、圣遗物、效果等具体实现）是测试最容易膨胀的地方：它主要是数据与接线，不是共享算法。测试预算按“收集用例数”计算（`pytest --collect-only` 展开参数化后的数量），防止每个内容单元都获得完整测试。

每个内容切片的默认预算为 5～10 个收集用例，按以下顺序分配：

- 内容单元注册与校验：1～2 个。验证能注册、缺资产条目或非法参数会报错；同类错误用参数化合并。
- 数值闭环：每个机制 1 个。走纵向集成，断言最终数值与关键事件/状态副作用；同一机制不重复覆盖。
- 特殊逻辑：只有真正独立的逻辑才单独测（去重、上限、跟随切人、解锁门槛等），每类 1 个。
- 接线代表：同类能力只保留 1 个代表（例如普攻选一个、战技选一个），证明资产 -> handler -> 运行时链路可用。

不默认测试的内容：

- 实现细节：逐帧衔接矩阵、动作编译字段、修饰器内部贡献步骤、每个命座的编译细节。
- 内容数据本身：范围半径、tick 次数、天赋等级加成表；数值由对应的数值闭环间接验证。
- 引擎已覆盖的重复行为：面积查询、创建物 tick 等 core 层已有测试的机制，内容层不再重复。

预算以外的内容切片（超过约 10 个收集用例）必须说明理由：机制确实复杂、跨系统交互多或承载契约真值；审查确认后才能超预算。

参考示例：芭芭拉切片按本预算收敛到 29 个收集用例（含参数化展开），保留数值闭环、装配代表与特殊逻辑。

## 4. 目录与文件组织

- `tests/unit/` 按 `unit/<顶层模块>/<子路径>/test_<关注点>.py` 镜像 `src/genshin_sim/` 结构；`tests/integration/` 按纵向关注点或基础设施模块组织；`tests/golden/` 按稳定业务领域组织（当前为 `damage/`、`reactions/`）。
- 测试文件名与测试函数名描述行为或关注点，不使用版本时间线作为分类依据。
- 一个文件只承担一个关注点，这是硬规则，与行数无关：文件内出现多个独立行为组（例如普攻、战技、命座各自成组）时必须拆分，即使总行数没有超限。
- 单文件默认不超过 500 行，作为触发检查的软信号：超限时优先按关注点拆文件或参数化；确实无法拆分的，在文件头注释说明该文件的单一关注点与超限理由。
- 一个测试函数只验证一个行为主题。准备步骤进 fixture 或 helper，断言集中在本次行为的输入与结果上；同一行为可以有多条断言（例如一次伤害结算后的数值、事件类型与顺序）。
- 测试内禁止真实网络、真实时钟与未固定种子的随机；随机路径必须显式固定种子。

## 5. 脚手架与复用

- 禁止跨文件复制私有构造/装配 helper（例如配置 payload、`_assemble`、`_apply_aura` 这类）。同一脚手架出现第二份时立即提取。
- 提取位置按复用范围：
- 跨领域/跨目录共享：`tests/conftest.py` 或 `tests/helpers/` 包（纯函数与数据构造器通过 `from tests.helpers... import ...` 导入）；
- 单领域内共享：该领域目录的 `conftest.py`（例如 `tests/golden/reactions/conftest.py`）；
- 单文件内私有 helper：允许，但不得被其他文件复制。
- fixture 优先使用工厂形态（返回构造器而不是固定实例），避免测试间共享可变状态；scope 默认 `function`，只读、不可变或重量级资源才使用 `module`/`session`。
- 临时资产库、结果库、缓存一律使用 `tmp_path`，不使用固定路径或共享文件；需要预置资产时通过共享构造器生成，不复制数据库文件。
- 测试之间必须隔离：不依赖执行顺序、模块级可变状态或上一个测试留下的副作用。
- 跨文件共享的 key、常量与基线数值放在 helpers 或 conftest，不逐文件复制。
- 落位按“使用范围的最小共同目录”：
- 跨目录、跨领域共享：fixture 放 `tests/conftest.py`，纯函数与数据构造器放 `tests/helpers/`；
- 单领域内部共享：放该领域目录的 `conftest.py`；
- 单一角色或内容单元：测试文件放入镜像 src 结构的角色目录（例如 `tests/unit/content/characters/mondstadt/barbara/`），其私有脚手架放同目录 `conftest.py`。
- `tests/helpers/` 是显式包：`tests/` 必须提供 `__init__.py`，helper 通过 `from tests.helpers... import ...` 导入；禁止隐式依赖测试目录被加入 `sys.path` 后直接 `import helpers`。
- 与 pytest 生命周期相关的共享能力（临时路径、装配完成的运行时、事件捕获、清理）一律做成 fixture，不进 `tests/helpers/`；`tests/helpers/` 只放无副作用的纯构造器、常量与工具函数。

## 6. 参数化与断言

- 两个及以上同构测试函数（相同断言体、仅输入不同）优先合并为 `@pytest.mark.parametrize`；参数化用例使用稳定、可读的 `ids`。
- 断言行为优先于实现：优先断言公开结果、事件、快照与数值；仅当内部记录本身就是被验证的契约（例如分发记录、提交计划）时才断言内部对象。
- 浮点数值统一使用 `pytest.approx`；golden 的允许误差随用例记录。
- 错误分支使用 `pytest.raises` 断言异常类型与关键信息，不复制堆栈。
- 测试必须包含有效断言；仅“能跑通”不能作为测试。
- 数值预期不得从实现推导后自我验证：golden 预期值必须先有资料或旧项目复核，再写入测试。

## 7. Golden case 代码形态

- 目录与命名：`tests/golden/<稳定业务领域>/test_<机制或流程>.py`；领域契约入口与状态在领域 README 或收敛清单维护（元素反应见[元素反应收敛切片](./元素反应收敛切片.md)）。
- 一个 golden 文件聚焦一个机制或跨机制流程，不写成该目录下所有功能的集合。
- 数据格式：默认使用 Python 内联数据并通过参数化表达同构矩阵；只有数据量大到影响可读性时才使用同目录 `data/` 下的 JSON 文件，并声明键约定与 schema；引入新数据格式时同步更新本文档。
- 每个 golden case 至少满足[迁移阶段安排](./迁移阶段安排.md) 11.2 的最小记录：验证能力、资料来源及适用版本、旧项目参考、完整输入条件、预期输出与允许误差、不覆盖的行为。记录放在用例 docstring 或数据记录中。
- 未确认的机制数值不得写成 golden 预期；只能以草案/待确认状态留在文档或契约中。
- golden 用例标识不使用版本时间线；资料来源中的“版本”只描述游戏版本或数据来源，不描述本项目交付批次。

## 8. 质量门禁

- 测试代码与生产代码使用同一套工具：`ruff check`、`ruff format --check`、`pyright`（`pyproject.toml` 已包含 `tests`）；`pytest` 保持 `--strict-config` 与 `--strict-markers`。
- 提交前运行与改动相关的测试路径；涉及数值或机制必须运行对应 golden case。完整检查命令见 [AGENTS.md](../../AGENTS.md)。
- 覆盖率只作为线索，不设统一阈值；关键分支（边界、错误、提交顺序、确定性）必须有覆盖。
- 纯文档改动可以不运行代码检查，但必须在交付说明中明确。

## 9. 重构与演进

- 测试重构是独立主题：按仓库提交工作流，一个 PR 只处理一个主题，测试规范化不与功能提交混入。
- 存量测试按领域分批套用本文规则，不做一次性大范围重排；每个迁移切片在完成实现时顺带清理本领域脚手架。
- 删除或合并测试的标准是覆盖密度而非数量：不降低契约覆盖；若断言承载契约真值，先迁入对应持有层（按 §2.1）再删除；删除前确认没有唯一覆盖，并同步领域覆盖矩阵。
- 行为变更的顺序：先确认并更新契约与 golden 真值，再改实现与测试，避免用测试反推实现。
