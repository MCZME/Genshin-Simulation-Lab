## 1. 文档定位

本文记录批处理工作流画布原型开发中已经暴露的经验、教训和正式实现建议，目的是减少正式开发时重复试错。

- 产品形态、区域模型和工作流语义以[批处理工作流画布设计](../架构/UI/批处理画布设计.md)为准。
- 模块边界与分层要求以[模块边界设计](../架构/模块边界设计.md)和[UI 结构与状态设计](../架构/UI/UI结构与状态设计.md)为准；前端工程细节见[前端工程规范](./前端工程规范.md)。
- 本文不是工作流定义、节点类型或持久化格式契约，不把原型代码提升为生产真值。
- 原型使用原生 HTML、CSS 和 JavaScript 验证交互；正式 UI 仍沿用项目确认的技术栈，不能直接复制原型实现。

## 2. 原型已经验证的方向

### 2.1 单画布端到端链路有辨识度

把“配置 → 模拟 → 分析”放在同一画布中，用户可以同时看到输入如何展开成批、模拟如何逐成员执行，以及结果如何进入指标与视图。相比拆成多个页面，这种形态更适合参数扫描、批次比较和结果追溯。

正式实现应优先交付一条可运行的纵向链路，而不是先追求节点类型覆盖率。第一条链路至少包含：

1. 根节点与一个配置节点。
2. 一个批量变体节点。
3. 配置区域边界输出。
4. 模拟桥节点及成员级状态。
5. 分析区域边界输入、一个指标节点和一个视图节点。

### 2.2 区域必须是可见的语义边界

区域不仅是视觉分组，还决定节点库内容、节点归属、数据语言和合法连线。原型表明，以下反馈必须在拖拽过程中或结束后立即出现：

- 当前节点将进入哪个区域。
- 节点与区域类型是否兼容。
- 节点移到空白处后已成为游离草稿。
- 游离草稿不能继续保留有效连线或参与运行。
- 同类节点不能跨区域直接连接，跨阶段数据必须经过模拟桥节点。

只在点击“运行”后统一报错会让区域看起来像装饰。正式实现应把区域归属和连线许可作为编辑器模型的一等状态。

后续讨论进一步确认，区域必须拥有显式数据边界，而不只是通过节点空间位置推断跨阶段关系：

- 配置区域固定提供一个边界输出，区域内节点先汇入该边界，再连接模拟桥。
- 分析区域固定提供一个边界输入，模拟桥只能连接该边界，不能直接连接区域内节点。
- 配置区域输出承担最终输入数量、校验和预览；分析区域输入承担外部连接状态和会话数量。
- 原“输入输出节点”和“会话数据源节点”与区域边界职责重复，应从节点类型中移除。
- 分析区域内的数据提供节点仍可作为独立来源提供历史结果，不要求区域边界输入必须连接。

边界端口使区域移动、调整尺寸和缩放后的连线关系保持稳定，也避免外部长连线穿入区域内部。正式实现必须在模型层校验边界，不能只依靠绘制层遮挡非法连线。

画布对象面板的筛选不能由鼠标所在区域或悬停节点驱动。用户移动、拖拽和编辑节点时必然频繁跨越区域，使用瞬时指针位置切换面板会造成内容跳变，并让用户失去刚才浏览或搜索的对象。原型确认采用以下规则：

- 面板提供“全部 / 配置 / 分析”显式筛选。
- 点击区域或区域内节点属于明确意图，可以切换到对应类型。
- 点击空白、选择模拟桥节点、移动鼠标或拖拽现有节点时保持当前筛选。
- 配置与分析分别记住最近明确选择的区域，作为点击创建节点的稳定添加目标。
- 拖入创建仍以实际落点校验区域兼容性，添加目标不替代落点判断。

这条经验可以推广到其他持久工具面板：瞬时指针状态适合显示预览和放置反馈，不适合改变工具内容、筛选条件或后续命令目标。

### 2.3 节点内编辑适合短闭环配置

角色选择、等级、命座、目标路径、指标口径等短配置直接放在节点内，能够保留上下文，避免频繁切换侧栏或弹窗。节点标题、状态和关键摘要必须在缩放后仍可扫描。

但节点内编辑不等于把完整表单塞进卡片。正式实现需要为每类节点明确：

- 默认展开的最小编辑字段。
- 收起时保留的摘要。
- 字段错误显示位置。
- 节点最小、默认和最大宽度。
- 内容过长时采用节点内滚动、分组展开还是独立编辑面板。

原型中的通用占位节点只能验证“新增、移动、连接”流程，不能作为正式节点编辑器模板。

节点编辑器还必须守住用户认知边界：用户熟悉的是原神中的角色、武器、圣遗物和战斗概念，不是项目的数据结构。内部稳定键、绑定键、JSON 路径和会话标识可以存在于模型和契约中，但常规界面必须翻译为名称、状态和任务动作，不能要求用户先理解项目实现才能完成配置或分析。

### 2.4 组输出与独立输出必须分开建模

原型最初只在枚举节点上提供一个输出端口，用 `×4` 表示它产生四个成员。这表达的是“一个组端口”，用户却容易把它理解成节点已经支持四个可独立连接的输出。端口数量与端口基数必须使用不同的视觉和数据模型表达。

枚举节点的改进方案同时提供完整组主端口和可展开的成员投影端口：主端口继续触发批量展开，成员端口只输出一个指定值。成员使用稳定 `item_id`，不能使用显示值或当前数组下标作为连线身份。

正式实现还要避免两个陷阱：

- 动态成员全部常驻为端口会使区间、大型枚举节点失控，因此成员端口应按需展开，并为大集合另行设计选择或投影节点。
- 多个成员分支重新进入同一节点时，不能自动推断为拼接、片段合并或叉乘；汇入语义必须显式并可预览最终输入数量。

### 2.5 图形编辑必须保留精确输入

按键轨迹同时提供滑块拖动和开始帧、结束帧、轨道选择，明显优于只提供拖动。图形操作适合快速调整，数值输入适合精确修改和无障碍操作。

正式轨迹编辑器还需要补齐：

- 滑块两端分别调整 press/release，而不只是整体平移。
- 未闭合事件、重叠冲突和越界的字段级提示。
- 横向缩放、帧/秒刻度和网格吸附状态。
- 轨道新增、重命名、排序与删除。
- 键盘微调以及撤销、重做。

### 2.6 批次状态要贴近成员

只显示一个总进度无法解释部分失败、排队和取消。模拟节点内的成员列表能够直接表达“排队、运行中、成功、失败、取消”，并为错误原因提供稳定位置。

正式实现应由前端 `WorkflowRuntime` 提交已展开成员，并消费应用层批次/任务状态，不应让 UI 用定时器推测进度。整批取消是第一版必要能力；成员级取消可以后置。

### 2.7 视图节点应直接显示结果

运行完成后在视图节点内切换时间轴和表格，能保持数据来源、指标口径和最终结果之间的空间关系。正式实现应保留这一点，同时把复杂分析计算留在 `analysis/` 与应用服务，UI 只消费结果模型。

### 2.8 具体 UI 原型的共同先决条件

进入具体 UI 骨架验证前，已经确认以下前提。后续原型以这些结论为输入，不在每轮中重复讨论；视觉主题、颜色、密度、尺寸和精确布局仍需通过具体原型验证。

- 目标用户熟悉原神中的角色、武器、圣遗物、队伍、目标、伤害和战斗过程，不假定其理解项目代码、数据契约或存储标识。
- 常规界面使用原神语义与任务语义，不要求用户识别 `asset_key`、`handler_key`、JSON 路径或 `session_id`。
- 产品以画布为中心，配置、模拟和分析在同一工作空间内完成；工作流管理位于顶部栏，不设置脱离画布上下文的独立运行历史页面。
- 历史结果通过分析区域的数据提供节点进入当前工作流。
- 采用有边界的弹性布局：允许工具区收起、画布伸缩和常见桌面视口适配，不支持任意停靠、插件化面板、用户自定义工作区或移动端布局。
- 面向桌面鼠标与键盘，最低内容视口为 `1280 × 720`。
- 节点是画布内所见即所得的编辑器，节点整体不折叠；只有内部次要分组可以折叠，并在折叠后保留摘要。
- 局部问题反馈与集中问题导航同时存在，分别承担解释和汇总跳转职责。
- 保存是明确动作，运行不隐式保存；运行期间只锁定会改变工作流含义的编辑，查看与导航仍可使用。
- 原型应尽量使用真实资产名称和图片；代表性占位数值不作为游戏机制或数值真值。

### 2.9 工作空间骨架原型结论

第一轮具体 UI 原型只比较左侧工具区组织方式，顶部栏、状态栏与画布内容保持一致，配置、模拟和分析阶段只使用色块占位。节点编辑、端口、连线、运行和结果状态均未在本轮验证。

已确认结论如下：

- 左侧使用常驻窄工具轨，节点和问题共享一个按需展开的工具面板。
- 工具面板收起后，工具轨仍提供稳定入口；工具内容只由明确点击切换，不随鼠标移动、悬停或拖拽变化。
- 不设置“大纲”工具。大量节点的查找与定位留待后续结合搜索、筛选和画布导航单独验证。
- 本轮没有确认工具轨宽度、面板宽度、图标、颜色、间距和内部列表样式，这些仍是后续具体 UI 原型的验证对象。

### 2.10 节点卡原型结论

视觉规范原型把节点卡从单一状态扩展为完整状态组，结构固定为“头部 + 内容区 + 底部”，并确认以下内容：

- 头部承载节点图标、节点类型、区域/槽位上下文和当前状态徽标；状态必须同时使用颜色、图标和文本，不依赖颜色单独表达。
- 内容区使用稳定行高承载直接编辑字段；运行中的模拟节点显示成员进度条，错误节点在字段旁给出修复提示。
- 底部固定承载路径与端口点，路径使用等宽字体并允许省略；端口点只表达连接状态，不替代端口命中区域。
- 原型层确认尺寸：节点宽度 260px、头部 40px、内容行 24px、底部 32px、图标按钮 24px、端口点 8px；后续统一使用舒适密度，不再提供紧凑密度。
- 状态组覆盖等待、选中、运行中、成功、失败、结果过期、覆盖警告和草稿；失败与警告分别贴近字段位置，避免只靠整卡颜色判断。
- 数值字段使用等宽和表格数字特性，避免状态变化时宽度跳动；路径、时间、计数和 ID 保持同一字体规则。

节点宽度、图标按钮尺寸和内部行高仍需要真实画布交互验证，重点确认拖拽、缩放、选择、节点内编辑和舒适密度下的可读性，再回写正式 UI 结构设计。

### 2.11 设置入口与居中弹窗原型结论

- 设置入口放在工具轨底部，使用 24px 设置图标按钮，不用色板图标表达设置。
- 主题设置从顶部栏移入设置弹窗，顶部栏只保留工作流主操作，避免同一职责出现两个入口。
- 设置弹窗采用居中模态，带遮罩；支持点击遮罩、Esc 和关闭按钮关闭。
- 动效使用淡入加轻微缩放，视觉与主题 token 保持一致。
- 设置弹窗宽度 400px，采用单列分组表单：分组标题在上，设置项标签左、控件右。
- 视觉规范原型可展开完整排版示例（外观/编辑器/应用、segmented/只读/开关/下拉/输入框），应用壳第一版只启用主题；规范示例不等于已启用设置项。
- 设置内容第一版只包含主题；不提供密度设置（统一舒适），不提供背景开关（动态背景常开）。

### 2.12 工具栏基本交互原型结论

- 工具栏采用状态驱动：画布对象面板和问题列表共用同一个展开面板，同一时间只激活一个工具。
- 点击节点/问题工具会切换面板；点击当前已激活的工具会收起面板。
- 区域不单独占用工具轨入口，统一作为画布对象面板中的可拖拽项。
- 面板项采用“一个项、一次创建”的可拖拽列表，不采用表单或独立弹窗；画布对象面板按区域/配置/模拟分组展示。
- 拖拽区域项到画布空白处创建区域；拖拽节点项到区域内创建区域内节点，拖到空白画布创建游离草稿；当前只生成视觉占位，不接真实数据。
- 画布对象面板搜索框使用“搜索对象”，不再使用“搜索节点”。
- 问题面板采用筛选（全部/错误/警告/提示）和两行问题项：严重程度图标、标题、定位信息、定位箭头；点击问题项进入选中态。
- 问题筛选按钮按严重程度着色：错误使用 danger、警告使用 warning、提示使用 info；全部保持中性。
- 设置属于临时浮层工具，打开期间按钮保持激活态，关闭后恢复普通态。
- Esc 优先关闭当前浮层，其次收起面板；工具切换只由明确点击触发，不随鼠标移动或悬停变化。

### 2.13 顶部栏、区域运行与细边优化原型结论

- 顶部栏左侧为品牌 mark、工作流切换器和未保存状态；品牌 mark 独立于切换器选中态，切换器只包住当前工作流名称与下拉箭头。
- 工作流切换器提供切换、新建和重命名入口；重命名正式实现不使用系统 prompt。
- 顶部栏右侧为保存和全部运行；保存按钮保持普通样式，未保存状态由徽标承担。
- 顶部栏不提供运行模式菜单；区域头部提供区域运行按钮，只运行该区域内容，当前仅做视觉占位。
- 细边优化：图标描边统一为 2px 并启用 geometricPrecision；语义边框不透明度提升到 0.72；关键 1px 分隔线使用 border-strong。

### 2.14 画布导航与小地图原型结论

- 画布网格使用单层 24px 点阵，深浅主题统一；曾尝试主点 + 强调点，浅色下效果不佳，已取消强调点。
- 动态背景固定为氛围层，不随画布平移或缩放。
- 空画布状态使用“拖入区域开始”，创建首个区域或节点后消失。
- 画布世界使用 translate + scale 坐标；参考 workflow-canvas 实现滚轮以鼠标位置为中心缩放、中键平移、点击选择和对象拖拽。
- 鼠标中键平移仅作为设计规则，本轮浏览器原型不验证具体中键手感；空白画布左键拖拽留给框选。
- 缩放范围 25% ~ 400%；右下角为“小地图 + 左侧图标按钮”结构，百分比放在小地图右上角，状态栏不显示缩放百分比。
- 小地图定位为结构总览：显示区域、节点、连线、模拟桥与当前视口；项目内容较少时直接展示完整结构，不提前聚合。
- 每种节点类型有独立颜色；连线带淡箭头表达数据流向。
- 小地图视觉：直角、外边框加粗、无阴影；收起按钮位于左侧最上方，图标向下；折叠时面板向下位移并淡出，展开时反向恢复。
- 缩到 50% 以下时隐藏文字待节点/区域实现后验证。

## 3. 原型暴露的主要教训

### 3.1 DOM 不能成为正式状态真值

原型为快速补齐撤销、重做，使用页面结构快照恢复节点、区域、表单和轨迹。这能验证交互预期，但不适合作为正式实现：

- 页面结构与业务状态强耦合，组件重构会破坏历史记录。
- 运行态、编辑态和持久化数据容易被一起快照。
- 大画布的完整快照会带来明显的内存和性能成本。
- 无法稳定生成可测试、可迁移的工作流定义。

正式实现应以 `WorkflowDefinition` 和 `WorkflowEditorState` 为真值。撤销、重做记录可逆命令或结构化状态差异，不能保存控件树或序列化后的页面。

### 3.2 原型全局变量不能演化成万能画布对象

原型把节点、连线、选择、缩放、运行定时器和校验状态集中在一个脚本中，适合短期实验，但正式实现必须保持四个职责独立：

| 职责 | 落位 | 拥有内容 | 不应拥有 |
| --- | --- | --- | --- |
| `WorkflowDefinition` | `frontend/` 模型；后端只做不透明 JSON 存档 | 节点、端口、连线、参数、区域与持久化布局 | 当前选择、悬停、运行进度 |
| `WorkflowEditorState` | `frontend/src/state/` | 选择、已提交节点位置与连线、区域归属、撤销历史 | 视口、拖拽与草稿连线瞬态、仿真结果、数据库访问 |
| `WorkflowValidator` | `frontend/src/workflow/` | 诊断项、严重级别、定位、运行阻断结论 | 控件状态修改、执行任务 |
| `WorkflowRuntime` | `frontend/src/workflow/` | 展开、向批次 API 提交已展开成员、跟踪成员与节点执行状态 | 画布布局、编辑手势、进程调度 |

不要为了复用把四者重新包装成一个全局 Store。UI 可以有组合视图模型，但状态所有权仍需清晰。

### 3.3 校验必须返回结构化诊断

原型用状态栏和短提示表达 handler 缺失、游离节点、跨区域连线、环路与运行链缺失，证明了校验反馈的必要性，也暴露了字符串式校验的局限。

正式前端 `WorkflowValidator` 至少应返回：

- 稳定诊断代码。
- `error` 或 `warning` 严重级别。
- 节点、端口、连线或字段定位。
- 面向用户的短消息与可选修复建议。
- 是否阻止保存、运行或仅影响当前分支。

编辑期间运行轻量增量校验；点击检查或运行时执行完整校验。警告不能和阻断错误使用相同视觉状态。

### 3.4 模拟动画不能代替运行状态机

原型使用定时器依次更新节点和批次成员，适合演示视觉反馈，但无法覆盖任务乱序完成、部分失败、取消竞争、窗口重开和结果恢复。

正式运行状态必须来自应用层任务模型，并满足：

- 状态转换有明确枚举和终态。
- 成员完成顺序不影响结果归属。
- 取消后迟到的任务回调不能把批次改回运行中。
- 工作流关闭再打开时，运行态与已保存定义不会混淆。
- 节点结果过期由输入版本或运行标识判断，不靠颜色残留判断。

### 3.5 删除、区域操作和危险动作要设计完整

原型补充删除和区域菜单后发现，单个动作会牵涉节点归属、连线、运行链完整性和撤销历史。正式实现不能只删除画面元素。

- 删除节点必须同时处理关联连线，并作为一个原子编辑命令进入历史。
- 删除非空区域需要明确采用“阻止删除”“节点转为游离草稿”或“连同节点删除”，不能临时决定。
- 删除运行必需节点后应立即产生定位明确的诊断。
- 重命名应使用画布内编辑，不使用系统 `prompt`。
- 连线本身需要可选择、删除和调整输入顺序。

### 3.6 视口与世界坐标要集中处理

拖拽、缩放、连线和轨迹编辑同时存在时，屏幕坐标与世界坐标换算很容易分散到各控件。正式实现应提供单一坐标转换入口，并统一处理缩放中心、命中测试、吸附和区域边界。

“适应全部”只根据区域计算仍不够，还需要覆盖游离节点、桥节点、连线控制点和“适应选中”。视口属于编辑期状态，默认不写入工作流定义。

## 4. 正式实现建议

### 4.1 先定义最小模型，再搭控件

进入正式实现时，先创建工作流定义契约和节点类型契约，再实现画布控件。首版模型只覆盖已经准备交付的纵向链路，不提前建立万能节点系统。

建议的最小编辑操作包括：

- 创建、移动、调整区域大小和重命名区域。
- 创建、移动、配置和删除节点。
- 建立、选择、排序和删除连线。
- 设置节点归属或转为游离草稿。
- 撤销、重做以及保存脏状态判断。

每个操作都应可以脱离 UI 控件进行单元测试。

### 4.2 分阶段接入真实能力

1. 编辑器骨架：结构化定义、区域、视口、选择、连线、历史和校验诊断。
2. 配置闭环：根节点、角色、按键轨迹、枚举、配置区域输出以及最终文档预览。
3. 模拟闭环：应用服务提交、成员状态、失败原因和整批取消。
4. 分析闭环：分析区域边界输入、指标和表格/时间轴视图。
5. 持久化：保存、加载、schema 版本迁移和脏状态比较。

每一阶段都应保留可运行的端到端场景，不以“控件已经画出来”作为完成标准。

### 4.3 保留桌面工具的操作效率

工作流画布是高信息密度桌面工具，不以移动端为第一目标。正式实现仍应保证常见窗口宽度下内容不重叠，并提供：

- 鼠标拖拽与键盘操作的等价入口。
- 撤销、重做、删除、取消和适应视图快捷键。
- 图标按钮的工具提示和明确的禁用状态。
- 焦点可见、合理的 Tab 顺序和状态文本，不只依赖颜色。
- 运行期间禁用编辑，但仍允许查看、平移和取消。

## 5. 正式开发前验收清单

- [ ] 已确定第一条纵向工作流及其真实应用服务入口。
- [ ] 已创建最小 `WorkflowDefinition` 契约，并明确 schema 版本。
- [ ] 已区分持久化布局、编辑期视口和运行态。
- [ ] 节点、端口和连线使用稳定 ID，不依赖显示名称或控件引用。
- [ ] 节点类型声明输入、输出、区域类型和编辑器配置。
- [ ] 校验器可检测游离参与运行、区域不匹配、端口类型、环路、覆盖和路径错误。
- [ ] 撤销、重做基于模型操作，覆盖批量动作和关联连线。
- [ ] 模拟状态来自应用服务，支持乱序完成、失败和取消。
- [ ] 模型使用 `asset_key` 引用资产，缺少 `handler_key` 在组装或运行前被阻断；常规界面只展示用户可识别的资产信息和状态说明。
- [ ] 轨迹编辑同时支持图形调整与精确数值输入。
- [ ] 已建立节点规模与连线规模的性能基准。
- [ ] 已有至少一个端到端交互测试覆盖配置、运行和结果查看。

## 6. 后续原型应继续回答的问题

原型后续迭代应服务于尚未确认的问题，不继续堆积无法进入正式实现的占位节点：

- 节点库采用点击创建、拖入创建，还是两者并存。
- 多输入端口的顺序如何直接调整并清晰展示覆盖关系。
- 连线选择、删除和手动路径调整是否足够易用。
- 按键轨迹在常见事件数量下的缩放、选择和冲突提示是否可读。
- 多少节点和连线开始需要性能优化或局部渲染。
- React Flow 在区域语义、节点内表单、中文输入法与高频拖拽下的真实表现如何落到正式组件。
- 枚举/区间节点在成员端口按需展开、大集合性能与叉乘预览下的交互是否可用。

这些问题形成明确结论后，应分别回写产品设计、工程规范或正式契约；本文只保留跨阶段可复用的实施经验。
