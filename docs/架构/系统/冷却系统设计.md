# 元素战技与元素爆发冷却系统设计

> 状态：正式。第一版冷却领域 Runtime、时长解析、条件查询、修改命令、批量提交、事实和快照已经实现，并已接入真实内容链路。
>
> 适用范围：角色元素战技与元素爆发的冷却次数状态、恢复链、时长解析、条件查询、缩减、重置、事实、快照与审计。
>
> 明确排除：跨系统组合逻辑和 Action 接入的具体实现、状态效果自身触发冷却、武器/圣遗物被动触发冷却、元素附着 ICD、元素反应 ICD、协同攻击间隔、产球间隔及其他效果内部计时。冷却与标准元素能量的公共条件组合见独立协调器设计。

最后更新：2026-08-08

## 1. 文档目标

本文只冻结 `core/systems/cooldown/` 内部设计，使后续实现不再需要重新讨论：

- 冷却状态由谁拥有。
- 冷却保存剩余秒数还是绝对 ready frame。
- 单次技能与多充能技能如何统一建模。
- 固定时长和外部提供的动态基础时长如何进入同一解析流程。
- 百分比时长修正、固定减秒、重置和恢复次数如何区分。
- 冷却条件查询返回什么，以及它不代表什么。
- 自然恢复、同帧修改、计划提交和批量修改如何保持确定性与原子性。
- 冷却领域需要哪些事实、快照、错误和测试。

本文不在冷却领域内部实现 `core/coordination/`、Action、Energy、Buff、Impact、Event、application 或 content 逻辑。冷却与标准元素能量的只读公共条件组合已经由[角色能力条件协调器设计](../协调/角色能力条件协调器设计.md)独立定案；其他写入连接继续按专题讨论。

## 2. 核心结论

1. `CooldownStore` 是元素战技与元素爆发冷却状态的唯一所有者，`CooldownRuntime` 是唯一业务写入口。
2. 冷却真值使用整数帧和绝对 `ready_frame`，不逐帧递减浮点秒数。
3. 单次和多充能使用同一串行恢复模型；同一时刻只有一个活动恢复计时，其余已消费次数排队。
4. 冷却领域不自行判断技能何时发生。外部只在确定的帧提交 `StartCooldownRequest`，Runtime 负责校验、消费一次冷却次数并启动或排队恢复。
5. 冷却领域只回答“指定冷却键的 CD 条件是否满足”，不回答“战技或爆发是否可以释放”。
6. 固定 CD 从 `CooldownDefinition` 读取；动态基础 CD 由请求显式提供。动态时长如何从角色状态或动作持续时间计算不属于本系统。
7. 时长 modifier term 在恢复链从空变为非空时解析并快照；恢复链未清空时，后续排队次数沿用同一 interval。
8. 百分比时长修正、固定减少当前剩余 CD、重置当前活动计时、直接恢复次数和临时无视 CD 是不同语义，不合并为万能写接口。
9. 所有写入采用 prepare/commit；提交前校验 revision 和完整前值，提交后生成不可变领域事实。
10. 冷却领域不 import 或查询其他领域 Runtime/Store，也不通过全局上下文寻找外部状态。

### 3.4 实测建模结论

- 多充能技能使用串行恢复，而不是每个次数独立并行恢复。
- 多充能技能在第一项进入恢复链时快照 CDR；链持续存在时后续恢复沿用该快照。
- 祭礼类重置对多充能技能作用于当前活动计时，不一次恢复全部排队次数。
- 部分技能的基础 CD 是外部状态决定的离散值，冷却系统不能只保存一个固定资产秒数。
- 不同来源的百分比调整可能引用不同中间阶段，因此 resolver 必须使用有序、可审计的 term，而不是把百分比全部相加。

上述证据主要来自旧版本。具体角色内容接入前仍需按[原神游戏机制实现规范](../../工程/原神游戏机制实现规范.md)重新建立当前版本 golden case。

## 4. 范围与延期事项

### 4.1 第一版正式范围

- `CooldownSubjectRef`、`CooldownKey` 和 `CooldownDefinition`。
- 固定与请求提供的动态基础时长。
- 单次与多充能串行恢复。
- 整数帧、ready frame 和自然恢复规范化。
- 有序时长 modifier term、解析结果和审计。
- 冷却条件查询。
- 开始冷却、固定减秒、重置当前活动计时。
- 单键和多键批量 mutation 的 prepare/commit。
- 领域事实、快照、错误、ignored 结果和确定性测试。

### 4.2 外部连接状态

- 哪个系统决定何时提交 `StartCooldownRequest`：已由定时动作支持
  （`TimedActionSpec.cooldown_start_frame` + `cooldown_ability_key`，
  `TimedImpactAction` 在指定帧提交）。
- Action、输入解释器或具体角色状态机如何提交冷却写请求：解释器经
  `ActionInterpretationContext.ability_condition_port` 只读查询公共条件，
  冷却写请求由动作在注册的冷却开始帧提交。
- 冷却与标准元素能量的只读公共条件组合已确定，由 `CharacterAbilityConditionCoordinator` 负责。
- 角色专属状态和私有资源仍由 content 判断，动作锁与中断仍由 `ActionManager` 判断。
- Buff、共鸣、命座或场域如何生成 `CooldownDurationTerm`：已落地——内容单元
  `cooldown_duration_terms` 在内容编译期按解锁过滤收集，随
  `TimedImpactAction.cooldown_duration_terms` 进入
  `StartCooldownRequest.duration_terms`。
- Impact、Event 或后续命令队列如何适配冷却 mutation。
- 冷却 Runtime 在整帧 world 中的具体调用顺序。
- 剩余冷却是否影响整体仿真停止条件。
- `CooldownDefinition` 如何从 SQLite、manifest、content 或其他来源组装：
  内容切片已落地（`ContentUnit.cooldown_definitions` 强类型定义）。
- 冷却事实如何映射到公共 EventType 或结果数据库。

本文只保证冷却领域提供稳定、强类型、可协调的输入输出；公共条件协调器只能消费 `CooldownConditionResult`，不能进入本系统读取 Store 或重复计算冷却条件。

### 4.3 明确不属于技能冷却领域

- Buff、武器、圣遗物、命座或被动效果自己的触发 CD。
- 雷电将军元素战技协同攻击 `0.9s` 间隔。
- 断流·斩、产球、治疗 tick 等效果内部间隔。
- 元素附着 ICD、反应 ICD、攻击命中 ICD。
- 元素能量、体力、生命或专属资源。
- 输入 HOLD 窗口、动作锁、姿态持续时间和动画时长。

## 5. 稳定身份与术语

### 5.1 CooldownSubjectRef

```text
CooldownSubjectRef
├── subject_type
└── subject_id
```

第一版只注册：

```text
subject_type = character
```

规则：

- `subject_id` 是本次仿真内稳定、非空的角色主体 id。
- 不使用角色显示名称、队伍槽位文本或 Python 对象地址。
- 外部系统如何把自己的角色引用映射为 `CooldownSubjectRef` 留到协调专题。

### 5.2 CooldownKey

```text
CooldownKey
├── subject: CooldownSubjectRef
└── ability_key: str
```

推荐核心能力 key：

```text
elemental_skill
elemental_burst
```

`ability_key` 表示共享同一冷却状态的能力身份。某个角色有多个释放变体时，只要它们共享 CD，就必须使用同一个 key。如何从具体动作映射到该 key 不属于本文。

### 5.3 Charge

`charge` 表示技能冷却系统中的可使用次数。它不表示元素能量，也不代表技能整体可以释放。

### 5.4 Recovery chain

已消费但尚未恢复的次数组成串行恢复链。同一时间只有一个 `ActiveRecovery`，其余次数由 `queued_recoveries` 计数表示。

### 5.5 Cooldown condition

冷却条件只定义为：

```text
available_charges > 0
```

条件满足不包含任何外部资源、状态或动作判断。

## 6. 模块边界

目标目录只包含：

```text
src/genshin_sim/core/systems/cooldown/
├── __init__.py
├── enums.py
├── errors.py
├── models.py
├── policies.py
├── resolver.py
├── store.py
├── runtime.py
└── snapshots.py
```

职责：

- `models.py`：主体引用、key、definition、record、请求、计划、结果、事实与审计模型。
- `policies.py`：有限的时长 term 阶段和操作规则。
- `resolver.py`：解析基础时长和 term，不读取外部系统。
- `store.py`：拥有 definition registry、record、revision 和原子提交。
- `runtime.py`：领域查询、规范化、prepare/commit 和 mutation 入口。
- `snapshots.py`：稳定运行时快照。
- `errors.py`：领域验证、查找、计划冲突和重入错误。

允许依赖：

- Python 标准库。
- `core/` 中已经确认的中立 JSON 值、帧值和 source context 值对象；若尚无合适中立模型，冷却领域先定义自己的窄类型。

禁止依赖：

- `core/actions`。
- `core/coordination`。
- 另一个 `core/systems/<domain>` 的 Runtime、Store 或具体模型。
- `content`、`assets`、`application`、`infrastructure`、`ui` 或 `cli`。
- `SimulationContext.get_system()` 或其他服务定位方式。

冷却系统不提供 callback、事件监听器、通用 hook registry 或外部对象引用。

## 7. 静态领域定义

### 7.1 CooldownDefinition

```text
CooldownDefinition
├── key: CooldownKey
├── ability_kind: AbilityKind
├── base_duration_frames: int
├── max_charges: int
├── duration_mode: CooldownDurationMode
├── source_ref: str
└── tags: tuple[str, ...]
```

枚举：

```text
AbilityKind
├── ELEMENTAL_SKILL
└── ELEMENTAL_BURST

CooldownDurationMode
├── FIXED
└── REQUEST_PROVIDED
```

校验：

- `key` 合法且唯一。
- `base_duration_frames` 是非负整数。
- `max_charges` 是正整数。
- `source_ref` 是非空稳定来源标识。
- tags 非空、唯一并按字典序冻结。
- `FIXED` 请求不得覆盖基础时长。
- `REQUEST_PROVIDED` 请求必须提供非负整数基础时长；definition 中的 `base_duration_frames` 只作为审计参考，不作为运行值。

### 7.2 DefinitionRegistry

```text
CooldownDefinitionRegistry
├── register(definition)
├── get(key)
├── contains(key)
└── definitions
```

规则：

- 运行开始前完成注册并冻结。
- 重复 key 报 `DuplicateCooldownDefinitionError`。
- 未注册 key 报 `CooldownDefinitionNotFoundError`。
- Runtime 运行后不能替换 definition 或修改 `max_charges`。
- definition 来源和构建过程不属于冷却领域；Runtime 只信任已经通过校验的不可变 definition。

## 8. 运行态模型

### 8.1 CooldownRecord

```text
CooldownRecord
├── key: CooldownKey
├── ability_kind: AbilityKind
├── max_charges: int
├── available_charges: int
├── active_recovery: ActiveRecovery | None
├── queued_recoveries: int
├── revision: int
└── last_changed_frame: int
```

不变量：

```text
0 <= available_charges <= max_charges
0 <= queued_recoveries
available_charges
  + queued_recoveries
  + (1 if active_recovery else 0)
  == max_charges
revision >= 0
last_changed_frame >= 0
```

初始化：

```text
available_charges = max_charges
active_recovery = None
queued_recoveries = 0
revision = 0
last_changed_frame = 0
```

### 8.2 ActiveRecovery

```text
ActiveRecovery
├── started_frame
├── ready_frame
├── interval_frames
├── chain_id
├── start_source_ref
└── duration_audit
```

不变量：

```text
started_frame >= 0
interval_frames >= 0
ready_frame = started_frame + interval_frames
chain_id 非空
start_source_ref 非空
```

### 8.3 串行恢复

最大 2 次、interval 900 帧：

```text
初始：available=2, active=None, queued=0
frame 100 开始一次：available=1, active.ready=1000, queued=0
frame 120 再开始一次：available=0, active.ready=1000, queued=1
frame 1000 规范化：available=1, active.ready=1900, queued=0
frame 1900 规范化：available=2, active=None, queued=0
```

第二次消费不会创建并行的 `ready_frame=1020`。排队项只有在前一项恢复后才开始完整 interval。

### 8.4 为什么不保存 remaining

`remaining_frames` 是查询投影：

```text
remaining_frames = max(0, ready_frame - query_frame)
```

Store 不保存它，避免每帧写状态、累计误差和快照前后不一致。

## 9. 冷却时长解析

### 9.1 基础时长

```text
CooldownDurationInput
├── definition
├── start_frame
├── requested_base_duration_frames?
├── terms
└── source_ref
```

选择规则：

```text
FIXED            -> definition.base_duration_frames
REQUEST_PROVIDED -> requested_base_duration_frames
```

Runtime 不计算动态基础时长的业务公式。调用方必须在请求前得到确定整数帧，并保留可审计 `source_ref`。

### 9.2 CooldownDurationTerm

```text
CooldownDurationTerm
├── term_key
├── source_ref
├── stage
├── operation
├── value
├── reference_stage?
└── priority
```

固定阶段：

```text
BASE
-> OWNER_ADJUSTMENT
-> DURATION_INCREASE
-> EXTERNAL_ADJUSTMENT
-> FINALIZE
```

允许操作：

```text
CooldownDurationOperation
├── MULTIPLY_CURRENT
├── ADD_REFERENCE_PERCENT
└── SUBTRACT_REFERENCE_PERCENT
```

含义：

- `MULTIPLY_CURRENT`：当前阶段值乘非负有限倍率。
- `ADD_REFERENCE_PERCENT`：增加指定已完成阶段值的一定比例。
- `SUBTRACT_REFERENCE_PERCENT`：减少指定已完成阶段值的一定比例。
- reference 不得指向当前或未来阶段。
- 同阶段按 `(priority, term_key, source_ref)` 稳定排序。
- 重复 `(term_key, source_ref)` 报错，不静默叠加。
- 最终结果小于 0 时截断为 0。

内容侧通道已落地：`ContentUnit.cooldown_duration_terms`（按 `CooldownKey`
声明 terms）在编译期绑定到定时动作，动作开始冷却时原样提交给
`StartCooldownRequest.duration_terms`。term 的数值来源由内容层决定；冷却系统
只验证和解析已经提供的 term。

### 9.3 Resolution

```text
CooldownDurationResolution
├── base_duration_frames
├── resolved_duration_frames
├── terms
├── stage_totals
├── rounded_from?
└── source_refs
```

规则：

- 外部数值先拒绝 `bool`，再校验为有限非负数。
- 运算使用整数或 Decimal，不使用二进制 float 作为真值。
- 最终分数帧向上取整。
- `resolved_duration_frames >= 0`。
- 每个阶段保存输入、操作和输出，分析层不重新计算。

### 9.4 多充能快照

- 恢复链为空时，第一次 `StartCooldownRequest` 解析 terms 并创建 interval。
- 恢复链非空时，后续 `StartCooldownRequest` 不重新解析 terms，沿用活动链 interval。
- 请求仍可携带 terms 用于外部统一调用，但 Runtime 必须忽略其数值并在结果中记录 `reused_chain_resolution=True`。
- 恢复链清空后，下一次开始重新解析。

## 10. 领域查询与命令

### 10.1 规范化到目标帧

```text
NormalizeCooldownsRequest
└── frame

NormalizeCooldownsResult
├── frame
├── changed_records
└── facts
```

规则：

- frame 必须不小于 Runtime 已处理的最后帧。
- 按 `CooldownKey` 稳定顺序处理到期记录。
- 活动项在 `frame >= ready_frame` 时恢复一次。
- 若存在排队项，下一活动项从前一项的自然 `ready_frame` 开始，而不是从查询帧开始。
- 如果调用方跨越多个 interval，Runtime 循环恢复所有已经到期的项。
- 每个实际恢复点生成独立事实，事实帧使用对应自然 ready frame。

外部何时调用 normalize 不在本文规定；冷却查询和 mutation 只接受已规范化到请求帧的 Runtime。

### 10.2 条件查询

```text
CooldownQuery
├── key
└── frame

CooldownView
├── key
├── ability_kind
├── max_charges
├── available_charges
├── active_ready_frame?
├── remaining_frames
├── queued_recoveries
├── chain_id?
└── revision

CooldownConditionResult
├── query
├── satisfied
├── reason
└── view
```

条件：

```text
satisfied = available_charges > 0
reason = charge_available | no_available_charge
```

`query` 原样保存本次 `CooldownQuery`，使协调器和审计调用方可以验证 key 与查询帧；它不表示查询产生了领域事实。

它不代表技能整体可以释放，也不产生拒绝、异常或写入。

### 10.3 开始冷却

```text
StartCooldownRequest
├── request_id
├── key
├── frame
├── requested_base_duration_frames?
├── duration_terms
└── source_ref

PrepareStartCooldownResult
├── condition
└── plan?

StartCooldownPlan
├── request_id
├── key
├── expected_revision
├── before
├── after
├── resolution
└── facts
```

prepare：

1. 校验 request、definition、frame 和幂等 id。
2. 确认记录已规范化到 frame。
3. 查询冷却条件。
4. 条件不满足时返回 `plan=None`，不替调用方决定下一步。
5. 链为空时解析 duration；链非空时复用 interval。
6. 构造完整后值和事实，不修改 Store。

commit：

1. 校验 `expected_revision`、完整 before 和 request id 未提交。
2. 原子写入 after、revision 和已提交 request id。
3. 返回不可变 result 与事实。

### 10.4 固定减少当前剩余 CD

```text
ReduceRemainingCooldownRequest
├── request_id
├── key
├── frame
├── reduction_frames
└── source_ref
```

规则：

- `reduction_frames` 是非负整数。
- 只作用于当前 `active_recovery`。
- `new_ready_frame = max(frame, old_ready_frame - reduction_frames)`。
- 若本帧完成，恢复一个次数；有排队项时从当前帧开始下一个完整 interval。
- 超出当前 remaining 的减量不结转到下一项。
- 无活动计时返回 `ignored(no_active_recovery)`。

减秒导致的完成与自然跨帧规范化不同：下一项从命令生效帧开始，因为当前活动项被提前完成。

### 10.5 重置当前活动 CD

```text
ResetActiveCooldownRequest
├── request_id
├── key
├── frame
└── source_ref
```

规则：

- 让当前活动计时在本帧完成。
- 不一次填满全部 `max_charges`。
- 有排队项时从本帧开始下一完整 interval。
- 无活动计时返回 `ignored(no_active_recovery)`。
- 不提供无来源的 `reset_all`。

### 10.6 批量 mutation

```text
CooldownMutationBatchRequest
├── batch_id
├── frame
└── requests

CooldownMutationBatchPlan
├── batch_id
├── frame
├── expected_store_revision
├── item_plans
└── facts
```

规则：

- requests 按 `(CooldownKey, request_id)` 稳定排序。
- 同一个 key 在一个 batch 中第一版最多出现一次。
- 先验证全部 key、frame、数值、revision 和前值，再提交任何状态。
- 任一 item 非法时整批失败。
- 合法 ignored item 不导致整批失败，但必须保留结果。
- commit 一次更新 Store revision，再按稳定顺序返回 item result 和 facts。

调用方为何需要多目标修改不属于冷却领域。

### 10.7 暂不泛化的命令

真实机制和 golden 出现前，不增加：

- 直接恢复指定数量 charge。
- 临时免费消费或无视 CD。
- 暂停、加速或倒放冷却时间。
- 运行时修改 `max_charges`。
- 复制或交换两个 key 的剩余 CD。
- 任意 `set_record()`、`set_ready_frame()` 或调用方直接 mutation。

## 11. 帧语义与确定性

### 11.1 半开边界

活动恢复有效区间：

```text
started_frame <= frame < ready_frame
```

在 `frame == ready_frame` 完成规范化后，该次数已恢复，冷却条件可能变为 satisfied。

### 11.2 0 帧时长

- 0 帧 definition 合法但必须有明确来源。
- Start plan 可以先记录消费，再在同一个事务结果中立即恢复。
- 最终 record 不留下 0 帧 active recovery。
- 同一 request id 仍只能提交一次，不能利用 0 帧重复消费。
- result 与 facts 必须同时记录 started 和 recovered，顺序固定。

### 11.3 帧单调性

- Runtime 维护 `normalized_through_frame`。
- 查询和 mutation frame 小于该值时报 `CooldownFrameRegressionError`。
- 查询 frame 大于该值时不隐式推进；调用方必须先显式 normalize。
- 该规则让读取保持无副作用，并避免查询顺序改变事实。

### 11.4 稳定排序

- definition 和 record 快照按 `CooldownKey` 排序。
- batch item 按 `(CooldownKey, request_id)` 排序。
- facts 按 `(frame, CooldownKey, fact_kind, operation_id)` 排序。
- 不依赖 dict、set、对象地址或注册顺序。

### 11.5 重入

Runtime 在 prepare/commit 事务中设置领域重入保护。提交和事实构造期间再次调用写入口时报 `CooldownReentrancyError`。领域事实只是数据，不在 Runtime 内同步执行外部 handler。

## 12. 条件、错误与 ignored

### 12.1 冷却条件不是动作结论

稳定条件结果：

```text
CooldownConditionResult(
    query=CooldownQuery(key=..., frame=...),
    satisfied=False,
    reason=no_available_charge,
    view=CooldownView(...),
)
```

冷却系统不把它映射为输入拒绝、ActionDecision、UI 提示或异常。映射属于后续调用方契约。

`CharacterAbilityConditionCoordinator` 可以把该结果与元素能量领域条件组合为公共条件证据，但不能改变 `satisfied`、推进冷却时间或把组合结果宣称为 Action 最终准入。精确映射见[角色能力条件协调器契约](../../契约/角色能力条件协调器契约.md)。

### 12.2 错误模型

```text
CooldownError
├── CooldownValidationError
├── CooldownDefinitionNotFoundError
├── DuplicateCooldownDefinitionError
├── CooldownRecordNotFoundError
├── CooldownFrameRegressionError
├── CooldownNotNormalizedError
├── StaleCooldownPlanError
├── DuplicateCooldownRequestError
├── CooldownDurationResolutionError
├── CooldownInvariantError
└── CooldownReentrancyError
```

| 错误 | 典型场景 |
| --- | --- |
| `CooldownValidationError` | key、帧、数值、tag、source ref 或 request id 非法 |
| `CooldownDefinitionNotFoundError` | 请求未知 key |
| `DuplicateCooldownDefinitionError` | 重复注册 definition |
| `CooldownRecordNotFoundError` | definition 存在但运行态未初始化 |
| `CooldownFrameRegressionError` | 请求帧早于已规范化帧 |
| `CooldownNotNormalizedError` | 请求帧晚于当前规范化边界 |
| `StaleCooldownPlanError` | record/store revision 或 before 已变化 |
| `DuplicateCooldownRequestError` | 相同 request/batch id 重复提交 |
| `CooldownDurationResolutionError` | term 阶段、引用、倍率或结果非法 |
| `CooldownInvariantError` | available、active、queued 总数不守恒 |
| `CooldownReentrancyError` | 当前事务尚未完成时再次写入 |

错误消息包含 key、frame、request id 和 source ref，不能只包含显示名称。

### 12.3 ignored

```text
CooldownMutationResult
├── applied
├── reason
├── before
├── after
└── facts
```

ignored reason：

```text
no_active_recovery
no_effect
```

未知 key、非法数值、stale plan 或重复 id 不是 ignored，必须报错。

## 13. 领域事实与快照

### 13.1 CooldownFact

```text
CooldownFactKind
├── STARTED
├── CHARGE_RECOVERED
├── REDUCED
├── RESET
└── CHAIN_COMPLETED

CooldownFact
├── fact_id
├── fact_kind
├── frame
├── key
├── operation_id
├── chain_id?
├── before_available_charges
├── after_available_charges
├── active_ready_frame?
├── queued_recoveries
├── source_ref
└── duration_audit?
```

规则：

- 事实只描述已提交状态。
- `fact_id` 可由 `(operation_id, index)` 确定生成。
- 自然恢复使用实际 ready frame。
- facts 由领域 result 返回；如何发布或持久化不在本文讨论。

### 13.2 CooldownSnapshot

```text
CooldownSnapshot
├── schema_version
├── frame
├── normalized_through_frame
└── records

CooldownRecordSnapshot
├── subject_type
├── subject_id
├── ability_key
├── ability_kind
├── max_charges
├── available_charges
├── active_started_frame?
├── active_ready_frame?
├── interval_frames?
├── queued_recoveries
├── chain_id?
└── revision
```

快照不保存 resolver、外部 provider、callback 或调用方对象。definition 来源通过独立运行元数据或事实审计关联，不重复写入每帧 record。

## 14. 关键领域案例

### 14.1 固定单次冷却

定义：基础 32 秒，60 FPS 转换后为 1920 帧。frame 100 收到开始请求：

```text
started_frame = 100
ready_frame = 2020
frame 2019：冷却条件不满足
frame 2020 规范化后：冷却条件满足
```

该案例不对技能是否可释放做断言。

### 14.2 多充能与快照

定义：最大 2 次，基础 600 帧。第一次请求携带 15% CDR term：

```text
interval = ceil(600 * 0.85) = 510
frame 100 start：available=1, active.ready=610
frame 120 start：available=0, active.ready=610, queued=1
frame 610 normalize：available=1, active.ready=1120
frame 1120 normalize：available=2, active=None
```

frame 120 请求携带的不同 term 不改变 interval。链清空后下一次 start 才重新解析。

### 14.3 重置多充能当前计时

前值：

```text
available=0
active.ready=610
queued=1
interval=510
```

frame 600 reset：

```text
available=1
active.started=600
active.ready=1110
queued=0
```

不是 `available=2`，也不继续使用自然恢复时的 1120。

### 14.4 固定减秒不结转

前值 remaining 为 30 帧、queued 为 1，收到 `reduction_frames=60`：

```text
当前项在请求帧完成
下一项从请求帧开始完整 interval
多出的 30 帧不作用于下一项
```

### 14.5 请求提供动态基础时长

定义为 `REQUEST_PROVIDED`，请求在 frame 500 提供 `requested_base_duration_frames=420`：

```text
base = 420
-> 解析请求携带 terms
-> 得到 interval
-> ready_frame = 500 + interval
```

冷却系统不询问 420 的角色机制原因，只校验 definition 模式、非负整数和 source ref。

### 14.6 跨帧规范化

最大 3 次，available=0，active.ready=100，queued=2，interval=50。直接 normalize 到 frame 220：

```text
frame 100 恢复一次
frame 150 恢复一次
frame 200 恢复一次并结束 chain
最终 available=3
```

事实帧为 100、150、200，不统一伪装成查询帧 220。

## 15. 测试规范

### 15.1 模型与 definition

- subject、key、ability kind、duration mode、source ref 和 tags。
- bool、负值、NaN、Infinity、空字符串和重复 key。
- fixed/request-provided 模式字段互斥。
- definition registry 冻结后拒绝修改。

### 15.2 Store 不变量

- 初始化 `available_charges == max_charges`。
- available、active、queued 总数守恒。
- 单次与多充能状态转换。
- record revision 与 store revision。
- stale plan 和重复 request id 不修改状态。

### 15.3 帧边界

- `ready_frame - 1` 条件不满足，`ready_frame` 规范化后满足。
- 0 帧、1 帧、整数秒和分数秒向上取整。
- frame regression 与未 normalize 查询。
- 跨多个 interval 的一次 normalize。
- 自然恢复事实使用真实 ready frame。

### 15.4 多充能

- 连续消费到 0。
- 串行而非并行恢复。
- 恢复一次后再次消费。
- 链存在时复用 interval，链清空后重算。
- reset 只完成当前活动项。
- fixed reduction 不向排队项结转。

### 15.5 时长 resolver

- 三种 operation 和固定阶段。
- reference 只能指向已完成阶段。
- 稳定 term 排序和重复 term 拒绝。
- 每阶段 audit 完整。
- 负结果截断 0，最终分数帧向上取整。
- 链内忽略新 term 并记录 `reused_chain_resolution`。

### 15.6 Mutation 与 batch

- reduce/reset 的 applied、ignored 和非法分支。
- batch 稳定排序。
- 任一 item 失败时不部分提交。
- ignored item 不阻止其他合法 item。
- 同 key 重复 item 第一版拒绝。
- 提交期间同步重入被拒绝。

### 15.7 事实与快照

- started、recovered、reduced、reset、chain completed 顺序。
- 0 帧 start/recover 顺序。
- snapshot 稳定排序和 JSON 兼容。
- snapshot 不包含外部对象或 callback。

### 15.8 Golden cases

领域实现至少需要：

1. 固定 32 秒单次 CD 边界。
2. 双充能串行恢复。
3. 多充能 CDR 快照。
4. 当前活动项 reset。
5. fixed reduction 不结转。
6. request-provided 动态基础时长。
7. 不同 reference stage 的 CDR 计算审计。

真实角色 golden 的取证和外部调用时点属于后续内容/协调专题；本阶段先用明确输入验证领域真值。

## 16. 领域实施顺序

### 阶段 A：模型、definition 与 Store

1. 实现 enums、errors、subject/key、definition registry。
2. 实现 record、active recovery 和 Store 不变量。
3. 实现 revision、request id 幂等和快照基础。

完成门槛：不接任何外部系统即可构造、查询和验证所有合法/非法状态。

### 阶段 B：固定时长最小闭环

1. 实现 normalize。
2. 实现 condition query。
3. 实现固定时长 start prepare/commit。
4. 实现单次与多充能串行恢复。
5. 实现基础 facts。

完成门槛：固定单次、多充能和跨帧规范化案例通过。

### 阶段 C：时长 resolver

1. 实现 term 阶段、operation 和稳定排序。
2. 实现 Decimal/整数运算与向上取整。
3. 实现 resolution audit。
4. 实现恢复链快照和 request-provided 基础时长。

完成门槛：多充能快照和不同 reference stage 审计通过。

### 阶段 D：修改命令与 batch

1. 实现 reduce remaining。
2. 实现 reset active。
3. 实现 ignored result。
4. 实现 batch prepare/commit 和重入保护。

完成门槛：单键与多键 mutation 原子性测试通过。

### 阶段 E：领域稳定化

1. 完成 facts、snapshot schema 和序列化。
2. 完成全部领域 golden cases。
3. 冻结公共导出和错误层级。
4. 单独发起跨系统协调设计讨论。

## 17. 验收标准

- `core/systems/cooldown/` 可以在不导入其他领域或应用模块的情况下独立测试。
- 冷却系统只返回冷却条件，不提供或推导整体技能可释放性。
- 单次、多充能、串行恢复、快照 interval 和 ready frame 行为有完整测试。
- fixed 与 request-provided 基础时长均有封闭校验。
- 时长 term 使用有限操作集合、固定阶段、稳定排序和完整 audit。
- start、normalize、reduce、reset 和 batch 全部采用 prepare/commit。
- stale plan、重复 id、帧回退和同步重入不会留下部分状态。
- facts 与 snapshots 足以解释每次开始、恢复和修改。
- 领域 API 不包含 Action、Energy、Buff、Impact、Event 或 coordination 专用模型。
- `pytest`、`ruff check`、`ruff format --check`、`pyright` 通过。

## 18. 禁止的简化

- 不把 CD 做成 `dict[action_key, float_seconds_left]`。
- 不每帧对所有记录执行 `remaining -= 1 / fps`。
- 不用显示名称作为 key。
- 不把多个 charge 建模为并行计时器。
- 不在恢复链中途重新解析 interval。
- 不把 reset 解释为填满全部 charge。
- 不把 fixed reduction 溢出到下一排队项。
- 不让查询隐式推进时间或发布事实。
- 不用 callback 或全局 service locator 获取外部状态。
- 不提供调用方可直接覆盖 record 的 setter。
- 不把效果内部 CD、ICD、协同攻击间隔或产球间隔塞进本 Store。
- 不在冷却领域内部实现 Action、Energy、Buff、Impact、Event 或 coordination 逻辑。
