# 元素反应运行时与事务契约

> 状态：已实现。本文冻结 Reaction Planner、主元素交互和同帧后续 Effect Group 的事务语义。

最后更新：2026-08-01

## 1. Registry

`ReactionRegistry` 提供：

```text
register(definition) -> None
definitions -> tuple[ReactionDefinition, ...]
definition_for(reaction_key) -> ReactionDefinition
```

约束：

- 重复 `reaction_key` 在注册时失败；
- 缺失 Definition 在查询时失败；
- `definitions` 按 `reaction_key` 稳定排序；
- 生产 Definition 由 bootstrap 显式注册。

生产只提供 `create_default_reaction_bootstrap()`。它一次返回字段固定的 `ReactionBootstrap`，统一携带当前完整 `reaction_registry`、`damage_gate_definitions` 与 `establishment_gate_definitions`，并通过 `create_runtime()` 原子构造配置一致的 `ReactionRuntime`。

bootstrap 不提供按历史交付版本裁剪的 Registry 或 Gate 集合。需要隔离机制的单元测试直接用明确的 Definition 构造最小 `ReactionRegistry`，不得用版本号间接表达依赖集合。

## 2. ReactionBatchPlanner

稳定调用流程：

```text
planner = runtime.begin_batch(frame, batch_id)
resolution = planner.prepare(request)
plan = planner.seal()
runtime.validate(plan)
receipt = runtime.commit_prevalidated(plan)
```

约束：

- `prepare()` 请求帧必须等于 Planner 帧；
- 同一 Planner 中 `interaction_id` 和 `order` 不得重复；
- `seal()` 只能执行一次；
- seal 后不得继续 prepare；
- plan 中 resolutions 按请求 `order` 排序；
- 当前稳定 API 不使用 `prepare_interaction()/finalize_interaction()`。

## 3. ReactionMutationPlan

稳定字段：

```text
operation_id: str
frame: int
interaction_ids: tuple[str, ...]
expected_store_version: int
resolutions: tuple[ReactionResolution, ...]
establishment_gate_plan: ReactionEstablishmentGateMutationPlan | None
```

普通蒸发、融化的 `establishment_gate_plan` 为空。

## 4. 校验与幂等

`ReactionRuntime.validate(plan)` 必须拒绝：

- `expected_store_version` 与当前 version 不同；
- 已提交的 `operation_id`；
- 任一已提交的 `interaction_id`；
- 非法或过期的成立 Gate 计划。

`commit_prevalidated()` 仍会再次执行校验，然后冻结 operation/interaction 身份并返回 `ReactionCommitReceipt`。

普通蒸发、融化不创建 ReactionState，因此 occurrence 提交不增加 version；stale version 校验仍然生效。

### 4.1 ReactionState 计划

`ReactionStatePlanner` 以 `ReactionStateSlotKey(subject_ref, slot, scope)` 管理强类型完整记录，只允许创建、完整替换和移除。计划至少冻结：

```text
expected_store_version
expected_records
replacement_records
removed_slot_keys
changes
```

活动 `FrozenState` 使用共享 `FROZEN` slot；惰性 `FreezeRecoveryState` 使用共享 `FREEZE_RECOVERY` slot。两者不能并存，且恢复状态的 `next_required_frame` 固定为 `None`。

## 5. ICD 与 Reaction 的输入边界

- 带 Binding 的命中进入 ICD Planner；即使没有元素施加，Binding 仍可以推进 ICD。
- 只有正元素施加意图才计算 Reaction 后手预算。
- `incoming_amount = elemental_amount * icd_coefficient`。
- `icd_coefficient = 0` 时不创建元素施加型 Reaction 请求。
- Reaction 不读取或修改 ICD 窗口、游标和 Binding。

## 6. 主交互预检

单个 `ElementalInteractionBatch` 在首次提交前完成：

```text
ICD plan validate
-> Aura plan validate
-> Reaction plan validate
-> Reaction Store plan validate
-> Aura / ReactionState Link validate
-> 可选 Space plan validate
-> Damage prepare
```

任一步失败时，ICD、Aura、Reaction、ReactionState、Space 与 Damage 均不得提交。

## 7. 主交互提交顺序

当前生产实现顺序固定为：

```text
ICD commit
-> Reaction occurrence commit
-> Aura commit
-> Reaction Store commit
-> 可选 Space commit
-> Damage record commit
```

提交方法只应用已准备变更，不查询其他系统、不调用 handler、不发布事实。

## 8. 主交互事实顺序

提交后按以下相对顺序发布：

```text
AURA_ICD_RESOLVED
-> AURA_APPLIED（若有）
-> AURA_INTERACTION_RESOLVED（若有）
-> REACTION_OCCURRED（若有，按决策步骤顺序）
-> ReactionState 事实（若有）
-> DAMAGE_RESOLVED（若有）
-> ELEMENTAL_INTERACTION_RESOLVED
```

事实发布期间不能通过事件回调重入 Aura 写入口或当前元素结算。

## 9. Follow-up Queue 与 Effect Group

已提交 occurrence 可以冻结 `ReactionEffectGroup`。`ElementalSettlementCoordinator` 在 round 0 事实发布完成后，将 group 放入严格更大的 settlement round；Event callback 不参与入队。

目标资格使用：

```text
ReactionTargetEligibility
├── subject_ref
├── spatial_entity_id
├── distance_xz
├── relation: self | ally | hostile | neutral_or_unknown
└── capabilities: aura | damage | attribute_status
```

Space 只提供几何候选。协调器冻结 relation、capability 和稳定目标顺序；单个 Effect 被正常阻止不撤销同组其他合法 Effect。

一个 Effect Group 是独立原子 batch。当前准备与提交边界为：

```text
freeze targets
-> optional strike Reaction / Aura / State plans
-> Damage Gate plan
-> optional Buff plan
-> Damage and character-damage plans
-> validate all plans
-> Reaction occurrence commit（若有状态型子反应）
-> Aura commit（若有）
-> Reaction Store commit（Gate + State）
-> Buff commit（若有）
-> Damage commit
```

round 1 失败不回滚已提交的 round 0。已提交 batch 产生的子 Effect 只能进入下一 round；单 root 最大同帧轮次为 `64`。

## 10. Reaction Damage Gate

Gate slot：

```text
gate_definition_key
trigger_source_ref
damage_target_ref
damage_kind_key
```

Definition 拥有 `window_frames` 与 `max_damage_instances`；Record 保存窗口起点、ready frame、已接受次数、最近接受帧、cause/effect 引用和 revision。

- 窗口使用半开区间；`frame >= ready_frame` 时建立新窗口；
- 窗口内计数未满则允许并推进 Record；
- 计数已满则 blocked，Record、revision 和 Store version 不变化；
- 允许后最终伤害为零不撤销 Gate 推进；
- blocked 只阻止对应 Damage，不撤销 occurrence、元素变化、超导 Status Effect 或超载钝击语义。

普通超载注册 `30/1`，普通超导注册 `30/2`。具体 key 见各反应专门契约。

普通碎冰注册 `30/2`。Gate blocked 不撤销碎冰 occurrence、linked Aura/State 移除、恢复历史或同一命中的后续元素候选。

## 11. 正常空结果与错误

正常空结果：

- 无匹配 Definition 或签名；
- 后手预算为零；
- 无匹配 Aura；
- 当前伤害不具备增幅资格，但反应本身仍可成立。

必须终止 batch 的错误：

- Definition、Profile、handler 或稳定引用缺失；
- 请求身份或顺序重复；
- stale plan；
- Aura/ReactionState/Space 绑定不一致；
- Damage Profile、属性输入、反应乘数或最终结果预检非法。

## 12. 记录要求

每个成功 batch 必须可从记录恢复：

- work、ICD、Aura、Reaction 和 Damage 请求之间的稳定关联；
- 每个决策步骤选择的候选 key；
- occurrence 与元素变化引用；
- 是否存在当前 Impact 伤害调整；
- 最终事实顺序和 settlement round。

Effect Group batch 还必须保存 parent work/occurrence、effect group/effect、目标结果、Gate、Buff 和 follow-up work 引用。集合使用稳定 tuple，不用自由 Mapping 保存机制结果。

## 13. 耦合 Aura/State Link 与周期生命周期

冻结相关 batch 必须在首次写入前验证 Aura 与 ReactionState 的完整最终投影：

- 活动 `FrozenState` 必须且只能关联同主体的一个正 `FROZEN` Aura；
- 两侧 `ElementalStateLinkRef` 必须相等；
- `FreezeRecoveryState` 不得持有 Aura Link，也不得被活动冻结查询返回；
- 创建、刷新、自然到期和碎冰移除不能只修改一侧；
- `next_required_frame` 存在时，帧协调器不得跨过该帧。

自然到期是状态生命周期工作，不创建伪 occurrence。Aura 与 State 移除全部提交完成后，当前路径发布已提交的 ReactionState 事实。

普通感电周期遵守相同的跨系统边界：帧协调器先提交状态游标和 scheduled root，后续 Effect Group 再准备目标 Gate、条件水雷 Aura 消费、状态来源接管和 Damage。周期 Effect 使用 `ScheduledStateTickCause`，不得伪造 occurrence；Gate blocked 是目标级正常结果，不回退周期游标。

感电的目标选择、`30/1` Gate、`0.4 GU` 条件消费和 13 米传播稳定字段见[感电反应契约](./反应/感电反应契约.md)。
