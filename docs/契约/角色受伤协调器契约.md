# 角色受伤协调器契约

> 状态：第一版已实现。
> 本文冻结角色伤害输入、护盾与血量计划、最终受伤记录和事件边界。

最后更新：2026-07-13

## 1. CharacterIncomingDamage

```text
damage_id: str
frame: int
target_ref: AttributeSubjectRef(character)
amount: float
element: DamageElement
source_ref: AttributeSubjectRef | None
source_context: RuntimeSourceRef | None
tags: frozenset[str]
```

约束：

- `damage_id` 非空，frame 为非负整数。
- target 必须是角色主体。
- `amount` 为有限非负数。
- `amount` 是伤害系统已经完成伤害计算、但尚未应用角色护盾和血量的伤害值。
- 请求不包含 `protection_ref` 或 `ignore_shield`；护盾系统根据目标解析适用保护范围。
- tags 归一化为稳定集合并按排序顺序序列化。

所有正式角色伤害使用该请求；直接扣血和按生命流失建模的流血不使用该请求。

## 2. ShieldAbsorptionPlan

计划由 ShieldAbsorptionPort 准备，至少保存：

```text
damage_id
frame
target_ref
operation_id
expected_store_version
expected_instance_records
replacement_instance_records
result: ShieldAbsorptionResult
fact_data
```

计划不可变。`expected_instance_records` 与 replacements 按完整 instance ref 稳定排序。计划创建后 Store version 或任一记录前值变化时，统一预校验必须失败。

## 3. CharacterDamagePlan

计划由 CharacterHealthDamagePort 准备，至少保存：

```text
application: CharacterDamageApplication
operation_id
expected_store_version
expected_health
expected_max_hp
result: CharacterHealthChangeResult
fact_data
```

`application.amount` 必须等于护盾结果的 `health_bound_damage`。提交不得重新决定伤害量、最大生命或有效血量变化。

## 4. CharacterDamageTakenRecord

```text
incoming_damage: CharacterIncomingDamage
shield_result: ShieldAbsorptionResult
health_application: CharacterDamageApplication
health_result: CharacterHealthChangeResult
```

不变量：

```text
incoming_damage.amount
== shield_result.protected_damage + shield_result.health_bound_damage

health_application.amount
== shield_result.health_bound_damage
```

完全吸收、无盾和零伤害均形成完整记录。

## 5. 领域端口

协调器只依赖两个写端口：

```text
ShieldAbsorptionPort
├── prepare_absorption(request) -> ShieldAbsorptionPlan
├── validate(plan) -> None
└── commit_prevalidated(plan) -> ShieldCommitReceipt

CharacterHealthDamagePort
├── prepare_damage(application) -> CharacterDamagePlan
├── validate(plan) -> None
└── commit_prevalidated(plan) -> HealthCommitReceipt
```

端口不得暴露可变 Store。DamageSystem 不属于协调器端口；上游只负责构造 `CharacterIncomingDamage`。

## 6. CharacterDamageTakenCoordinator

公共入口：

```text
apply(request: CharacterIncomingDamage) -> CharacterDamageTakenRecord
records -> tuple[CharacterDamageTakenRecord, ...]
```

内部顺序：

```text
enter reentrancy guard
-> prepare shield plan
-> prepare health plan
-> validate both plans and cross-plan invariants
-> commit both plans without callbacks
-> build CharacterDamageTakenRecord
-> publish ordered facts
-> leave reentrancy guard
```

调用方不能分别提交同一次角色受伤的 shield plan 和 health plan。

## 7. 提交契约

统一预校验必须发生在任一 Store 写入之前。校验失败时两个 Store 都不改变。

`commit_prevalidated()` 必须满足：

- 只应用计划中已经构造的完整替换值。
- 不查询属性、content 或其他领域状态。
- 不重新计算或执行业务分支。
- 不发布事件或同步回调。
- 不产生正常领域验证错误。
- 同一个计划不能重复提交。

若实现不能满足上述约束，协调器必须使用 copy-on-write 或正式事务边界，不能允许部分提交后再补偿。

## 8. 事件契约

| EventType | 发布条件 |
| --- | --- |
| `SHIELD_CAPACITY_CHANGED` | 匹配护盾的原生容量发生变化 |
| `SHIELD_REMOVED` | 匹配护盾在本次伤害中耗尽 |
| `SHIELD_ABSORPTION_RESOLVED` | `incoming_damage.amount > 0` 且至少有一个匹配护盾 |
| `CHARACTER_HEALTH_CHANGED` | 角色当前生命真实减少 |
| `DAMAGE_APPLIED` | `incoming_damage.amount > 0` 且目标是角色 |

`DAMAGE_APPLIED` 使用 `FACT` 分类，表示角色成为一份正伤害的应用目标，不表示血量一定减少。其 payload 保存完整 `CharacterDamageTakenRecord`。

## 9. 数值与序列化

- 数值接受 `int | float`，拒绝 `bool`，并要求有限。
- 容量和伤害残差的零值归一化由对应领域契约规定。
- 枚举使用稳定字符串 value。
- 主体引用和来源上下文使用结构化对象。
- 新增或删除字段属于契约变化，必须同步持久化测试和本文。

## 10. 错误类型

目标错误层级至少包括：

```text
CharacterDamageTakenError
├── CharacterDamageTakenValidationError
├── CharacterDamageTakenTargetError
├── CharacterDamageTakenPlanConflictError
├── CharacterDamageTakenCommitError
└── CharacterDamageTakenReentrancyError
```

ShieldSystemError 和 HealthSystemError 保留各自领域语义，由协调器附加 damage id 和 target ref 后传播。预校验之后出现领域业务错误属于提交契约违反，必须作为 CharacterDamageTakenCommitError 报告。

## 11. 当前实现

契约已由 `core/coordination/character_damage_taken/` 实现。请求使用 `amount` 且不携带 protection ref；`DAMAGE_APPLIED` 使用 `FACT` 分类并保存完整 `CharacterDamageTakenRecord`。

当前提交原子性建立在单线程内存运行时约束上：两个领域在任何写入前完成统一预校验，真实 `commit_prevalidated()` 只执行已准备值的确定性内存替换，不查询、不计算且不发布事件。
