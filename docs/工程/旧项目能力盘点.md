# 旧项目能力盘点

> 状态：阶段 0 收束稿。
> 最后更新：2026-07-04。
> 本文档用于阶段 0 的迁移盘点。它不是实现说明，而是把旧项目能力按“重设计 / 直迁 / 待确认”分类，方便后续逐项迁移。

## 1. 盘点目标

- 梳理旧项目中仍然有价值的能力。
- 区分需要重新设计的部分与可以直接迁移的部分。
- 给每个能力指定新项目归属模块。
- 为第一批迁移任务准备验收方式和 golden case 入口。

## 2. 阶段 0 收束结论

- 输入与动作核心架构已经重新定案。`input_trace` 继续记录按键事实，并在组装阶段编译为输入会话计划；运行时统一由 `ActionManager` 管理解释器、Action、动作实例、具名锁和影响点。后续迁移以[按键输入契约](../契约/按键输入契约.md)、[按键输入系统设计](../架构/按键输入系统设计.md)与[动作系统设计草案](../架构/动作系统设计草案.md)为准。
- 资产数据库重设计讨论已结束。第一版以[资产数据库设计](../契约/资产数据库设计.md)为准，基础资产库使用 SQLite、结构化索引表与 JSON payload 混合模型，`asset_key` 与 `handler_key` 分离。
- UI 仍属于完全重设计范围。本轮 MVP 只保留 Flet 入口壳和应用服务边界验证，不迁移旧 UI 工作流。
- 第一批实现只使用测试资产与 generic NoOp handler，不迁移真实角色、武器、圣遗物、伤害或反应数值。
- 高风险数值能力暂不凭记忆实现，只登记旧项目测试和文档作为后续 golden case 来源。

## 3. 处理方式分类

### 3.1 需要重新设计

- 资产数据导入流程与真实数据源接入；第一版资产库 schema 已冻结。
- 具体 Action、动作状态、控制命令、锁、中断窗口与 Impact 机制接入；输入数据契约和动作核心边界已确认，代码待迁移。
- UI 与交互工作流。

动作序列单独成专题，不纳入第一批直迁范围。

### 3.2 优先直迁

- 运行时骨架：事件、上下文、模拟器。
- 核心数值与规则处理：伤害、反应、生命、护盾、能量、共鸣、规则。
- 纯机制工具：附着、ICD、附魔、元素转换等。
- 内容实现：角色、武器、圣遗物、通用 handler。
- 分析与批处理：结果加工、批量模型、结果摘要。
- 只要不依赖旧 UI 形态、旧数据库结构或旧动作序列契约，就优先直迁。

### 3.3 待确认

- 依赖旧 UI 形态的逻辑。
- 依赖旧数据库结构的逻辑。
- 依赖旧动作序列契约且无法映射到新 `input_trace` / 动作状态机的逻辑。
- 暂无可信来源或 golden case 的机制数值。

## 6. 第一批直迁顺序

建议阶段 0 先冻结以下直迁顺序：

1. 事件系统与上下文骨架。
2. 模拟器骨架与帧推进。
3. 伤害、反应、生命、护盾、能量等核心系统。
4. 共鸣、规则、月曜、纳塔等附加规则系统。
5. 机制工具：附着、ICD、附魔等纯算法。
6. 结果持久化与分析加工的数据模型。
7. 一个最小内容切片：一名角色、对应武器、对应圣遗物效果。

## 7. 填写规则

- 每个能力只写一个主归属模块。
- 如果同一能力同时涉及重设计和直迁，以更高风险的一侧为准。
- 直迁不等于照搬，必须重新检查模块边界和依赖方向。
- 数值相关内容必须标注来源或 golden case。
- 迁移完成后，备注栏应记录对应测试文件或验收文档。
