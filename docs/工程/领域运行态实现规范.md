# 领域运行态实现规范

> 状态：生效。
> 本规范定义有身份、状态或生命周期的领域运行态如何归属、计划和提交；新增或修改领域系统时按本文执行。不记录具体系统的实施顺序。
> 最后更新：2026-09-05（补充领域实现的通用数值、错误与确定性规则；机制接入方向见[原神游戏机制实现规范](./原神游戏机制实现规范.md)）。

## 1. 核心结论

伤害、治疗、护盾、Buff、冷却、元素附着、元素附着 ICD 和元素反应都是游戏机制，但不共享同一种状态模型。每个 `core/systems/<domain>/` 直接拥有本领域的完整运行态，并在真实复用关系形成后再提取最小公共原语。

禁止为了字段相似预先建立统一机制 Store、通用运行态基类或可选组件容器。一个领域实例是否合法，必须能够由该领域自己的完整记录和不变量判断。

## 2. 领域运行态的判定

满足以下任一条件的对象通常属于领域运行态：

- 具有跨帧稳定身份。
- 保存会被后续请求读取或修改的领域状态。
- 具有创建、刷新、消费、到期、移除或互斥终态。
- 需要版本、幂等身份、快照或事实审计。
- 必须与同领域其他记录共同满足不变量。

一次性请求、纯公式解析和不可持久化的结果通常不需要建立长期记录。例如伤害与治疗可以通过 Resolver 或 Runtime 产生一次性结果；护盾、Buff、Aura 和 ReactionState 则需要领域记录。

## 3. 状态所有权

每个领域直接拥有：

- 领域实例引用和稳定排序、序列化规则。
- 完整领域记录和全部合法性约束。
- 领域查询索引和只读 View。
- 创建、刷新、替换、消费和移除语义。
- 不可变 MutationPlan、版本校验和幂等身份。
- 提交回执、领域事实和快照。

不得把一个合法实例拆成必须跨多个领域 Store 才能拼出的半成品。跨领域 Link 只表达关系，不转移任何一方的状态真值。

当前常见所有权示例：

| 领域 | 状态所有者 | 说明 |
| --- | --- | --- |
| 护盾 | `ShieldStore` | 完整拥有护盾身份、容量、冲突与生命周期 |
| Buff | `BuffStore` | 完整拥有 Buff 实例、应用策略和有效期 |
| 冷却 | `CooldownStore` | 按角色和 ability key 保存次数与恢复状态 |
| 元素附着 ICD | `AuraIcdRuntime` 内置记录 | 拥有窗口、序列游标、版本和幂等身份 |
| 元素附着 | `AuraRuntime` 内置记录 | 拥有 Aura Component、贡献量、衰减和 Link |
| 元素反应 | `ReactionRuntime` 内置记录 | 拥有 ReactionState、Gate、资源和计划 |
| 元素能量 | `CharacterEnergyStore` 与在途队列 | 分别拥有角色当前能量与微粒、晶球调度 |
| 空间创建物 | Space 及对应创建物 Runtime | 分别拥有空间投影和具体机制状态 |

是否使用独立 Store 类属于领域内部实现选择，不改变状态所有权。Runtime 内置记录索引时，Runtime 仍是该领域唯一写入口。

## 4. 身份与来源语义

不同语义必须使用不同字段或强类型引用：

- `instance_ref`：领域实例自身身份。
- `source_context` 或领域专用来源引用：产生本次请求的动作、内容或上游机制。
- `creator_ref`：创建时读取属性的主体。
- `target_ref`、`protection_ref` 等领域影响范围。
- `link_ref`：跨领域对象之间的稳定关系。

不得恢复含义模糊的通用 `owner_ref`，也不要求所有领域继承统一运行态引用。跨领域协调器负责显式转换不同领域引用，并校验来源、目标和 Link 是否指向同一因果对象。

## 5. 生命周期

生命周期属于领域记录和领域规则。常见模型包括：

- 半开时间区间 `created_frame <= frame < expires_at_frame`。
- 无固定到期帧，由消费或显式命令结束。
- key 到 ready frame 的专用时间模型。
- 时间窗口与计数游标组合的状态机。
- 由其他领域状态 Link 决定连续性的耦合生命周期。

领域 Runtime 负责声明下一必需处理帧、规范化规则和到期行为。活动记录是否延长仿真，也必须由领域明确决定，不能由通用生命周期框架猜测。

## 6. 请求、计划与提交

content 和 application 只能构造领域请求，不能构造或直接写领域记录。单领域写入遵循：

```text
领域请求
-> 纯计算与只读观察
-> 不可变 MutationPlan
-> 校验版本、身份和完整前值
-> 无回调提交
-> 生成提交回执与领域事实
```

MutationPlan 应保存足以证明计划仍然有效的信息，包括计划帧、Store version、operation identity、request identity 和必要的前值投影。提交阶段不得重新查询外部状态、调用业务 handler、执行公式或发布事件。

如果多个领域需要共同提交，由限定用途协调器在第一次写入前准备并校验全部计划。提交开始后不得再出现可预期的业务失败，也不使用补偿写入模拟原子性。

## 7. 跨领域协调

需要多个领域共同提交时，由限定用途协调器统一编排；领域只准备自己的计划并参与固定顺序的无回调提交。协调器职责、禁止事项、依赖方向与示例见[系统自治与跨系统协调规范](./系统自治与跨系统协调规范.md)。

## 8. Event 与后续工作

领域遵循“状态先提交、事件后发布”：事件只表达已经提交的事实，事件 handler 不能在当前结算中递归修改领域状态。需要由事实触发后续行为时，转换为强类型领域命令并进入明确的下一结算轮次或未来帧；`EventEngine` 边界与跨系统事件规则见[系统自治与跨系统协调规范](./系统自治与跨系统协调规范.md)。

## 9. 领域实现的通用规则

本节是新增或修改领域实现时的通用工程规则，具体机制接入方向见[原神游戏机制实现规范](./原神游戏机制实现规范.md)。

### 9.1 职责分层

领域实现按以下方向分层，但不为目录完整创建空抽象：

```text
类型化请求
-> 纯 Resolver / Formula
-> 不可变 Resolution / Result
-> Runtime / Store 原子提交
-> Handler / Adapter 编排
-> 事实事件与快照
```

- 请求描述结算意图和所需上下文，不保存已推导的最终值；使用稳定引用、强类型枚举和有限数值。
- Resolver/Formula 只做纯查询和纯计算：不写 Store、不修改状态、不发布事件、不读取 UI/数据库/文件，返回中间量足够完整的不可变结果。
- Runtime 拥有领域状态提交顺序；Store 拥有具体状态。涉及多个实例或多个字段时先计算完整更新集并校验前值，再一次提交。
- Handler/Adapter 把上游通用请求转换为领域强类型请求并编排多个明确写入口，不重复实现领域公式，也不通过字符串重新解释已类型化的结果。

### 9.2 数值与错误规则

- 所有外部数值先拒绝 `bool`，再校验为有限 `int | float`；对非负、正数、比例或上下限使用显式验证。
- 浮点求和优先使用稳定顺序和 `math.fsum()`；接近零归一化必须有明确容差和领域理由；不使用无文档的 clamp 掩盖非法状态；中间乘数和最终结果都校验有限性。
- 结果保存参与审计所需的公式分量、倍率、来源和上下文。
- 错误至少区分：输入或模型验证错误、属性或依赖查询错误、状态或实例不存在、生命周期或策略冲突、原子提交冲突、不支持的枚举/公式/handler。
- 错误消息包含稳定 key、instance id、主体引用或字段路径，不只输出显示名称；非法输入不得静默忽略，除非上游契约明确把该请求定义为可审计的 ignored request。

### 9.3 快照与查询输入分类

每个公式输入必须明确属于：创建时快照、结算帧动态查询、运行态累计状态、上游已经结算完成的输入之一。不得把动态属性提前乘入实例真值，也不得在结果分析阶段重新决定运行时真值；快照发生帧和查询主体必须进入契约或结果记录。

### 9.4 确定性与原子性

- 多实例查询和提交使用稳定排序键；不依赖 `set`、普通 dict 构造来源或注册顺序的偶然遍历结果。
- 同帧输入集合在处理阶段开始前冻结。
- 多对象状态变化先完整校验再提交；提交失败不留下部分更新。
- 事件、快照和结果记录只能观察到提交前或提交后的完整状态。

## 10. 与其他模块的边界

- `content/` 声明具体角色、武器、圣遗物和机制行为，构造类型化请求，不访问领域内部 Store。
- `application/assembly/` 创建领域 Runtime、Registry、adapter 和 coordinator，并在组装阶段校验绑定完整性。
- `attributes/` 可以读取领域提供的只读 ModifierProvider，但不拥有领域生命周期，也不能在属性查询时修改状态。
- `snapshots/` 只导出各领域快照，不成为第二份状态真值。
- `infrastructure/` 和资产数据库不进入 `core/systems/`。

## 11. 公共提取门槛

只有同时满足以下条件，才评审提取中立公共原语：

- 至少两个已经实现并通过领域测试的真实使用者。
- 共享的是行为和不变量，而不是同名字段。
- 提取后不需要领域类型开关、可选组件表或通用 patch API。
- 各领域仍原子拥有自己的完整记录。
- 公共 API 可以独立测试，且不迫使新领域采用不合适的生命周期。

优先提取精确值对象、稳定引用或小型技术工具。新增公共运行态模块前必须同步更新[模块边界设计](../架构/模块边界设计.md)和[架构与运行时决策](../决策/架构与运行时.md)。
