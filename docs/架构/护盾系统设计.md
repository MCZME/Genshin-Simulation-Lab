# 护盾系统设计

> 状态：核心运行时已实现；真实角色护盾 content 与结晶反应尚未接入。
> 本文冻结角色侧护盾的游戏行为、状态所有权、运行流程和跨系统边界。精确字段与序列化见[护盾系统契约](../契约/护盾系统契约.md)。

最后更新：2026-07-13

## 1. 范围

护盾系统负责：

- 在创建帧解析护盾原生吸收量。
- 管理护盾授予、刷新、替换、叠加、共存和移除。
- 保存每个活动护盾的原生最大与剩余吸收量。
- 在角色来伤进入生命系统前并行结算全部活动护盾。
- 在承伤帧动态读取当前受保护角色的护盾强效。
- 发布授予、容量变化、移除、吸收和最终来伤应用事实。
- 提供结构化结果、快照和通用事件持久化输入。

护盾系统不负责：

- 敌方元素盾、敌人护盾条或破盾元素量。
- 敌人对角色的完整伤害公式。
- 伤害减免、无敌、格挡、闪避和免疫本身。
- 韧性、抗打断和击退的完整结算。
- 元素附着、反应触发、结晶晶片生成和拾取。
- 侵蚀、生命流失或其他直接扣血机制。
- UI、分析图表或专用结果数据库投影。

## 2. 依据与可信度

当前通用行为参考：

- [KQM 护盾机制](https://library.keqingmains.com/combat-mechanics/damage/shields)：基础吸收量、护盾强效、元素倍率、多盾同时承伤和创建属性快照。
- [KQM 护盾证据库](https://library.keqingmains.com/evidence/combat-mechanics/damage/shields)：伤害减免顺序、同元素倍率和快照证据。
- [Genshin Impact Wiki - Shield](https://genshin-impact.fandom.com/wiki/Shield)：溢出伤害、多盾并行、岩盾倍率和当前场上角色护盾强效的交叉核对。

这些资料只冻结通用系统的表达能力。具体角色、武器、圣遗物或反应的倍率、固定值、持续时间、叠加上限和特殊例外必须在接入时重新核对当前版本，并提供 golden case。

## 3. 核心决策

- 护盾不是额外生命，不进入 `HealthState`。
- 护盾实例复用[机制系统设计](./机制系统设计.md)中的通用身份和生命周期。
- 护盾元素、容量、保护对象和冲突键由 `ShieldComponentStore` 独立拥有。
- 创建者属性在创建帧解析；动态护盾强效在每次承伤帧查询。
- 活动实例保存未乘动态护盾强效的原生容量。
- 多个不同护盾同时承受同一份来伤，不把容量相加。
- 同名或同冲突组的刷新行为由请求携带显式策略决定。
- 直接扣血继续使用生命系统的直接扣血入口并绕过护盾。
- 第一版不修改 `SimulationConfig`、资产库 schema 或结果库 schema。

## 4. 系统结构

```text
ShieldImpactRequestHandler
-> ShieldGrantRequest
-> ShieldResolver
-> ShieldGrantResolution
-> ShieldRuntime
   ├── MechanicRuntime / MechanicInstanceStore
   ├── ShieldComponentStore
   ├── AttributeResolver
   ├── HealthRuntime
   ├── TeamRuntimeState
   └── EventEngine
```

角色来伤链路：

```text
护盾前减免后的 CharacterIncomingDamage
-> ShieldRuntime 并行吸收
-> 原子提交全部护盾容量变化和耗尽移除
-> CharacterDamageApplication(health_bound_damage)
-> HealthRuntime.apply_damage()
-> IncomingDamageApplicationRecord
```

## 5. 模块边界

### 5.1 ShieldResolver

`ShieldResolver` 只负责创建时纯计算：

- 使用同一属性解析 session 查询创建者属性。
- 计算公式分量、固定值和护盾自身原生倍率。
- 可选地计算叠加上限。
- 返回包含中间量和属性 trace 的不可变结果。

它不读取当前生命，不发布事件，不访问 Store，也不修改机制实例。

### 5.2 ShieldRuntime

`ShieldRuntime` 负责领域规则和状态提交：

- 选择冲突实例。
- 应用授予策略。
- 同步通用机制实例和护盾组件。
- 计算多盾并行吸收更新集。
- 调用生命系统提交穿透伤害。
- 发布已经提交的事实事件。

它不重新计算敌方伤害公式，也不直接修改 `HealthState`。

### 5.3 HealthRuntime

`HealthRuntime` 只接收护盾处理后的 `CharacterDamageApplication`，不读取护盾列表，不计算元素倍率或护盾强效。

### 5.4 content 与 application

`content/` 构造护盾请求和显式授予策略，不写护盾容量。`application/assembly/` 组装 Resolver、Runtime、Handler、Store、属性系统和 dispatcher。

## 6. 状态所有权

```text
MechanicInstanceStore
└── instance_id、能力 key、语义 key、handler key、owner、生命周期

ShieldComponentStore
└── protection、creator、source、element、maximum、remaining、conflict、tags
```

两个 Store 通过相同 `instance_id` 建立一对一关联。活动护盾必须同时具有活动 `MechanicInstance` 和 `ShieldComponent`。实例到期、替换或显式移除后，机制 removal 通知负责清理组件并发布领域移除事实。

护盾组件不保存当前角色护盾强效，也不保存已经乘元素倍率的“有效盾量”。

## 7. 保护对象

### 7.1 active_team

普通角色护盾默认保护玩家队伍当前场上角色，而不是固定保护创建者：

```text
kind = active_team
protection_id = team:player
```

每次承伤时通过 `TeamRuntimeState.current_character` 解析真实生命目标和护盾强效查询主体。来伤目标不是当前场上角色时必须返回目标不匹配错误。

### 7.2 character

`character` 保护类型为未来固定角色保护、联机或场景规则预留。使用时，来伤目标 entity id 必须与 protection id 一致。

## 8. 创建公式

基础公式：

```text
BaseAbsorption = fsum(CreatorAttribute[i] * Coefficient[i]) + FlatAbsorption
NativeAbsorption = BaseAbsorption * product(NativeMultiplier[i])
```

规则：

- 创建者属性在 `request.frame` 查询并冻结。
- coefficient、固定值和原生倍率必须为有限非负数。
- base absorption 和最终 native absorption 必须为有限正数。
- `NativeMultiplier` 表示护盾自身描述中的额外吸收效果，不是角色公共护盾强效。
- 可叠加护盾可以使用同结构的独立公式计算容量上限。
- 公式结果保存全部分量和来源，支持审计。

## 9. 动态护盾强效

护盾强效使用公共属性：

```text
bonus.shield.strength
```

承伤帧查询：

```text
subject_ref = 当前受保护角色
frame = incoming.frame
shield_strength_multiplier = 1 + bonus.shield.strength
```

乘数必须为有限正数。切换当前场上角色后，同一个队伍护盾立即使用新角色在该帧的护盾强效。

属性的正式定义、owner 范围和聚合规则以[属性系统契约](../契约/属性系统契约.md)为准。

## 10. 元素吸收倍率

| 护盾类型 | 来伤类型 | 倍率 |
| --- | --- | ---: |
| 岩元素护盾 | 任意伤害 | 1.5 |
| 非岩元素护盾 | 同元素伤害 | 2.5 |
| 其他组合 | 任意伤害 | 1.0 |

单盾有效倍率：

```text
EffectiveMultiplier = ElementMultiplier * ShieldStrengthMultiplier
```

原生容量消耗：

```text
NativeCost = min(RemainingNative, IncomingDamage / EffectiveMultiplier)
NativeAfter = RemainingNative - NativeCost
AbsorbableDamage = min(IncomingDamage, RemainingNative * EffectiveMultiplier)
```

接近零的浮点残差按护盾契约规定归一化为零。

## 11. 多盾并行吸收

同一次来伤对全部活动护盾使用同一份输入独立计算：

```text
ShieldHitResult[i] = resolve(active_shield[i], incoming_damage)
```

禁止把多个护盾容量相加或按顺序逐盾抵扣。每个护盾都按完整来伤计算自身消耗；最终保护量取所有护盾本次可保护伤害的最大值：

```text
ProtectedDamage = max(AbsorbableDamage[i], default=0)
HealthBoundDamage = IncomingDamage - ProtectedDamage
```

所有 `ShieldHitResult` 先完成计算，再通过版本号和前值校验一次提交。耗尽组件在同一结算中离开活动状态。

## 12. 授予策略

### 12.1 replace

- 同 protection ref 和 conflict key 的现有实例先替换移除。
- 新建 instance id。
- 新容量使用本次授予量。
- 事件顺序为旧实例移除后新实例授予。

### 12.2 refresh_replace

- 保留 instance id。
- 容量替换为本次授予量。
- 过期帧刷新为 `frame + duration_frames`。

### 12.3 add_capped_refresh

- 保留 instance id。
- `remaining_after = min(remaining_before + granted, capacity_limit)`。
- maximum 更新为本次解析的 capacity limit。
- 同时刷新持续时间。

### 12.4 keep_stronger_refresh

- 保留 instance id。
- 剩余量和最大量分别保留旧值与新授予量中的较大值。
- 无论是否采用新容量都刷新持续时间。

### 12.5 coexist

- 不与不同 conflict key 合并。
- 同一 protection ref 上不同 conflict key 的护盾可以并存。
- 当前同一 conflict key 最多一个活动实例，重复授予返回冲突错误。

## 13. 生命周期

护盾沿用机制系统半开区间：

```text
created_frame <= frame < expires_at_frame
```

帧内运行顺序：

```text
MechanicRuntime 过期到期实例
-> ActionManager
-> ImpactRuntime
-> SpaceRuntime
```

所有护盾公共入口都必须按请求帧过滤活动实例，不能依赖稍后清理。显式移除只能发生在活动区间；耗尽、替换、过期和 owner 移除保存明确 reason。

## 14. 来伤与生命提交

护盾入口消费已经完成防御、抗性和伤害减免处理的 `mitigated_amount`。它不重复应用这些公式。

完全吸收时仍构造：

```text
CharacterDamageApplication(amount=0)
IncomingDamageApplicationRecord
DAMAGE_APPLIED
```

生命系统返回零有效变化且不发布虚假 `CHARACTER_HEALTH_CHANGED`。部分穿透时只有 `health_bound_damage` 进入生命写入口。

直接扣血使用 `CharacterHpDeduction`，默认绕过护盾，不增加通用 `ignore_shield` 字段。

## 15. 事件顺序

### 15.1 授予

```text
SHIELD_REMOVED(reason=replaced)   # 仅替换
-> SHIELD_CAPACITY_CHANGED        # 仅刷新导致容量变化
-> SHIELD_GRANTED
```

不同策略的创建、替换、刷新、叠加和保留旧值通过 `ShieldGrantResult.outcome` 区分。

### 15.2 承伤

```text
提交全部护盾变化和耗尽移除
-> SHIELD_CAPACITY_CHANGED（instance_id 顺序）
-> SHIELD_REMOVED(depleted，instance_id 顺序）
-> SHIELD_ABSORPTION_RESOLVED
-> CharacterDamageApplication
-> CHARACTER_HEALTH_CHANGED（仅真实减少时）
-> DAMAGE_APPLIED
```

零来伤不消耗护盾，不发布容量变化或吸收事件。无活动护盾时不发布吸收事件，但仍形成普通 `DAMAGE_APPLIED` 记录。

### 15.3 事务与重入

护盾授予、显式移除和吸收在状态提交期间缓存护盾事实事件，完整提交后按稳定顺序发布。事实事件发布期间同步发起的护盾写操作返回 `ShieldStateConflictError`，不能改变当前结算或制造重复冲突实例。

## 16. Impact 与组装

护盾使用专用 `ImpactKind.SHIELD`。`ShieldImpactRequestHandler` 要求结构化 `params.shield`，解析创建者、保护对象、公式、策略和来源上下文后构造 `ShieldGrantRequest`。

装配结果暴露：

- `MechanicRuntime`。
- `ShieldComponentStore`。
- `ShieldResolver`。
- `ShieldRuntime`。
- `ShieldImpactRequestHandler`。
- `IncomingDamageHandler`。

缺少 SpaceRuntime、owner slot、创建者、公式或必填字段时返回结构化错误。完整 payload 见[护盾系统契约](../契约/护盾系统契约.md)。

## 17. 快照、持久化与分析

护盾快照保存：

- 稳定 instance id 和机制 key。
- protection、creator 和 source context。
- 护盾元素。
- 原生最大与剩余吸收量。
- 创建帧和过期帧。
- tags。

快照不保存某个角色和某种来伤元素下推导出的有效盾量作为真值。

当前结果持久化复用通用事件 JSON，不增加专用护盾表或升级结果库 schema。未来只有在真实数据证明事件扫描成本过高后才评审专用投影。

analysis 可以从事件派生覆盖率、来源吸收量、耗尽/过期/替换次数、穿透伤害和多盾冗余，但不能回写运行态或重新决定真值。

## 18. 错误边界

护盾系统区分：

- 输入和值对象验证错误。
- 创建公式或动态属性查询错误。
- 容量和乘数错误。
- 保护对象不存在或目标不匹配。
- 授予策略和冲突错误。
- 组件、实例或批量前值冲突。

非法状态不能 clamp 后继续运行，也不能静默把领域错误降级为无盾。

## 19. 验证基线

核心运行时至少覆盖：

- 过量伤害穿透。
- 同元素 2.5 倍与岩盾 1.5 倍。
- 动态护盾强效与切换场上角色。
- 多盾并行且不相加。
- 减免后输入和直接扣血绕过。
- 容量叠加到上限。
- 过期帧不参与吸收。
- 全部授予策略。
- 批量提交失败无部分状态。
- 事件顺序和事件回调重入。
- 快照与结果库 JSON 往返。
- ActionImpactPoint 到护盾授予的纵向链路。

真实角色护盾和结晶的验证要求见[护盾系统后续实现计划](../工程/护盾系统后续实现计划.md)。
