# AI 协作规范

本文档定义本项目中人类开发者与 AI 助手的协作方式。它不是替代测试、文档或代码审查的信任声明，而是让 AI 的工作可限定、可复查、可持续。

## 1. 协作目标

AI 主要用于提高项目重建效率：

- 梳理旧项目能力与新项目模块的映射关系。
- 编写项目骨架、数据模型、接口协议和测试。
- 迁移明确边界内的旧代码能力。
- 补充文档、示例、CLI 和校验工具。
- 执行代码审查、依赖边界检查和回归风险分析。

AI 不应成为游戏机制、数值可信度或产品方向的唯一来源。

## 2. 适合交给 AI 的任务

- 创建或调整项目骨架。
- 根据已有文档实现接口、数据类、协议和服务骨架。
- 为明确算法补充单元测试。
- 为迁移能力整理 checklist 和 golden case 草案。
- 编写 CLI 参数解析、配置校验、数据库 schema 初始化等工程代码。
- 对变更做风险审查。
- 根据已确认结论同步文档。

## 3. 需要人工确认的任务

以下任务在实现前应由人工确认范围或验收标准：

- 顶层架构和模块边界变化。
- `SimulationConfig`、资产库 schema、结果库 schema 的破坏性调整。
- 原神角色、武器、圣遗物、反应和敌人机制的具体数值与规则。
- 新增外部数据源、抓取流程、依赖库或服务。
- 删除旧项目逻辑、删除数据文件或重写大范围模块。
- UI 产品形态和核心交互模式。

## 4. AI 开工前输入

给 AI 派发任务时，优先包含：

```text
目标：
范围：
参考文档：
相关旧项目位置：
验收标准：
禁止事项：
```

示例：

```text
目标：实现 SimulationConfig 的第一版校验模型。
范围：只改 application/config 和测试。
参考文档：docs/契约/仿真配置契约与最小闭环.md。
验收标准：能校验 schema_version、team、scene、sequence 的基本结构。
禁止事项：不要引入 UI，不要访问 SQLite。
```

## 5. AI 输出验收标准

AI 完成任务时，至少说明：

- 修改了哪些文件。
- 实现了什么行为。
- 是否同步了相关文档。
- 运行了哪些检查。
- 是否存在未解决风险或需要人工确认的点。

对于代码任务，优先满足：

- 改动范围与任务一致。
- 不破坏既定模块依赖边界。
- 有必要的测试或可复现验证。
- 错误在合适层级暴露。
- 文档与实现保持一致。

## 6. 数值与机制可信度

仿真项目的核心风险是数值和行为可信度。

规则：

- AI 不能仅凭记忆实现游戏数值。
- 复杂机制迁移前应记录来源、旧项目参考、预期行为和验证方式。
- 伤害、治疗、反应、Buff 覆盖率、时间轴等核心逻辑应优先沉淀 golden case。
- 如果来源不明确，AI 应标注不确定性，并请求人工确认。

## 7. 文档同步规则

以下变更必须同步文档：

- 模块职责或依赖方向变化。
- 配置契约、资产库结构、结果数据结构变化。
- CLI 命令、测试策略、迁移策略变化。
- 影响 AI 后续协作方式的规则变化。

`docs/` 下文件夹和文件名使用中文，文档引用使用相对链接。

## 8. 审查方式

AI 可以作为第一轮审查者，重点检查：

- 依赖是否越界。
- 是否把 UI、SQLite、具体内容逻辑泄漏进 `core/`。
- 配置和资产身份是否使用稳定 key。
- 错误是否过晚暴露。
- 测试是否覆盖关键行为。

人工审查重点放在：

- 架构选择是否符合项目目标。
- 数值与机制是否可信。
- 迁移优先级是否正确。
- UI 和分析产品形态是否符合预期。
