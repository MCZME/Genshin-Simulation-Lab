# UI 原型验证规范

> 状态：生效
> 最后更新：2026-08-13

## 1. 定位

本文定义 UI 原型的验证边界、工作流程、交付物和结论收敛方式。UI 原型是可操作的设计载体，只用于回答界面与交互问题；原型代码是一次性实现，不作为正式 UI 的代码、架构、组件或状态管理参考。

相关文档职责如下：

- 产品形态与已确认交互规则由 `docs/架构/UI/` 下对应设计文档维护。
- UI 正式实现的模块边界由[模块边界设计](../架构/模块边界设计.md)维护，前端工程要求由[前端工程规范](./前端工程规范.md)维护。
- 原型过程中形成的可复用经验与教训由[UI 原型开发经验](./UI原型开发经验.md)维护。
- 本文只维护原型如何立项、验证和收敛，不定义具体产品界面。

## 2. 原型类型

### 2.1 想法可行性原型

用于快速判断某个交互概念是否能被表达和操作，例如无限画布、区域归属、节点内编辑、组输出与成员输出。

特点：

- 只覆盖待验证机制的最短路径。
- 允许使用占位内容和简化状态。
- 结论是“该交互方向是否成立”，不是最终视觉方案。
- 验证结束后冻结，不继续累积无关能力。

### 2.2 具体 UI 原型

用于验证已经选定的产品方向如何落实为具体界面，包括信息层级、布局、组件形态、操作路径和完整状态反馈。

特点：

- 使用真实或具有代表性的名称、图片、数值和错误文案。
- 围绕明确用户任务覆盖完整状态，而不是罗列全部功能。
- 关注用户能否理解和完成任务，不讨论界面如何编码。
- 产出可回写正式设计的视觉与交互结论。

想法可行性原型通过后才能进入对应的具体 UI 原型；具体 UI 原型不得反向把原型代码提升为正式实现基础。

## 3. 验证范围

### 3.1 必须验证

- 信息架构：用户是否理解页面区域、工作阶段与导航关系。
- 视觉层级：主要任务、当前上下文和次要信息是否有清晰优先级。
- 信息密度：内容是否足够完整，同时保持可扫描且不拥挤。
- 操作路径：用户能否发现入口并以合理步骤完成任务。
- 交互可预测性：选择、拖拽、连接、展开和切换是否符合预期。
- 状态反馈：空、编辑、校验、运行、失败、完成和结果过期等状态是否清晰。
- 错误恢复：用户是否能定位问题、理解原因并知道如何修正。
- 数据追溯：结果是否能追溯到对应输入、批次成员和参数。
- 桌面视口适配：常见窗口尺寸下是否存在遮挡、溢出或信息过散。
- 基础可访问性：焦点、键盘入口、工具提示、禁用状态和非颜色提示是否完整。

### 3.2 不纳入验证

- 原型源码的模块划分、代码质量和复用价值。
- 正式 UI 的技术栈、组件框架和状态管理方案。
- 工作流、节点、端口和持久化数据的正式契约。
- 后端接口、数据库访问和真实仿真执行。
- 真实并发、性能上限和大规模节点承载能力。
- 原型代码向正式 UI 的迁移方案。

原型只需稳定支撑本轮 UI 验证。除保证原型能够运行和复现状态外，不以生产代码标准评价或扩展原型实现。

## 4. 原型代码不提交原则

原型代码只存在于本地工作区，不进入 Git 历史、分支、提交或 PR。仓库通过 `.gitignore` 忽略 `prototypes/`，降低原型代码被误提交的风险。

具体规则如下：

- 不暂存、不提交 `prototypes/` 下的源码、依赖声明、锁文件、构建产物、本地资源和生成数据。
- 不使用强制添加绕过 `.gitignore`，也不以“后续再删除”的方式临时提交原型。
- 提交前检查 `git status`，确认原型目录没有进入暂存区；如果误暂存，只从暂存区移除，保留本地原型文件继续验证。
- 需要长期保留的产品结论写入正式 UI 设计文档；可复用经验写入[UI 原型开发经验](./UI原型开发经验.md)。
- 需要纳入评审记录的关键截图应复制到对应文档资源目录，并由文档明确引用；不得为了保留截图而提交整个原型目录。
- 正式实现必须在 `ui/` 等正式模块内根据已确认文档重新设计和编码，不移动、复制或演化原型源码。

本原则不设常规例外。如果未来确实需要把某类可执行原型作为仓库资产，必须先形成明确项目决策、修改本规范和忽略规则，再按正式代码要求独立评审；不能在普通 UI 任务中临时破例。

## 5. 立项要求

每轮原型开始前必须形成简短验证说明，至少包含：

1. 目标用户及其已有知识。
2. 一条明确的核心任务。
3. 本轮需要回答的 UI 问题。
4. 必须覆盖的界面状态。
5. 主要桌面视口。
6. 明确不验证的内容。
7. 原型结束和结论收敛条件。

同一轮原型不应同时验证多个无关产品方向。新问题超出当前任务时，记录为后续轮次，不顺手扩展当前原型。

## 6. 验证流程

### 6.1 定义场景

使用“用户为了什么，在什么起始状态下，要完成什么任务”的形式描述场景。场景必须包含可观察的完成结果，不能使用“体验整个界面”之类的开放目标。

### 6.2 建立状态矩阵

先列出状态，再制作界面。每个状态至少记录：

- 用户当前目标。
- 页面主操作。
- 必须可见的信息。
- 禁用或不可用操作。
- 错误或进度反馈位置。
- 进入下一状态的动作。

状态应由固定数据稳定复现，不要求接入真实业务能力。

### 6.3 制作具体界面

- 使用接近真实业务的内容，避免使用无意义占位文本。
- 固定格式组件必须有稳定尺寸，状态变化不能造成无意义布局跳动。
- 交互入口、选中状态、悬停状态、禁用状态和错误状态必须完整。
- 同一操作在不同状态下的行为应一致；无法执行时明确禁用并给出原因。
- 不在界面中加入解释原型功能、视觉设计或使用方法的说明文字。

### 6.4 执行任务评审

评审以任务为单位，不以“是否好看”为唯一判断。每项任务记录：

- 是否完成。
- 完成路径和操作次数。
- 发生的误操作。
- 用户停顿或寻找入口的位置。
- 对状态、术语或结果产生的误解。
- 建议保留、修改或放弃的设计。

### 6.5 视口检查

具体 UI 原型默认检查以下桌面视口：

- `1280 × 720`：最低内容视口，核心操作不得被遮挡或挤出。
- `1440 × 900`：主要设计尺寸。
- `1920 × 1080`：宽屏信息密度检查。

如果产品另有最低窗口要求，以正式产品设计为准。移动端不自动纳入桌面分析工具的原型范围。

### 6.6 收敛结论

每个验证问题必须标记为：

- 已确认：形成稳定 UI 规则并回写正式设计。
- 需修改：记录问题和下一轮验证目标。
- 已放弃：记录放弃原因，避免重复试验。
- 未覆盖：明确留待后续，不以当前原型推断结论。

## 7. 原型交付物

一轮完整的具体 UI 原型至少产出：

- 验证场景与范围。
- 状态矩阵。
- 可操作原型。
- 主要视口与关键状态截图。
- 任务评审记录。
- UI 问题与决策清单。
- 正式设计文档修订。
- 新增或修正的原型经验。

原型源码不属于正式实现交付物，也不作为后续实现评审的依据。正式实现评审应引用确认后的架构、交互、契约和工程文档。

## 8. 文档收敛规则

- 产品布局、组件行为和交互规则回写 `docs/架构/UI/`。
- 跨原型可复用的经验、失败模式和评审方法回写[UI 原型开发经验](./UI原型开发经验.md)。
- 原型流程与验收规则变更回写本文。
- 进入正式实现后需要稳定的数据结构和失败边界，再创建 `docs/契约/` 下的契约文档。
- 原型代码中的名称、对象、事件和状态不能直接成为正式契约；必须根据已确认设计重新定义。
- 原型与正式文档冲突时，以已确认的正式文档为准，或先完成设计修订后再实施。
