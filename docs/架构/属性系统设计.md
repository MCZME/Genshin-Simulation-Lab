# 属性系统设计

> 状态：正式规范。
> 本文描述属性系统：它回答“某一主体在指定帧的某个属性有效值是多少、来源是什么”，是只读、可审计的查询解析引擎；包括属性与机制状态的边界、来源分层与模块结构。
> 最后更新：2026-09-05。

稳定 key、模型字段、枚举、解析公式、错误语义、快照与装配规则以[属性系统契约](../契约/属性系统契约.md)为真值，本文不重复维护。

## 1. 定位

属性系统是 `core/` 内的确定性查询与解析能力，用于回答：

```text
在指定帧、主体和查询上下文下，某个属性的有效值是多少，来源是什么？
```

属性系统不是可写角色面板，也不是保存全部战斗状态的通用容器。

核心原则：

- 原始属性在组装阶段生成并冻结。
- 派生属性在查询时解析，不写回角色或目标运行态。
- modifier 只贡献结构化修饰项，不直接修改属性值。
- 动态 modifier 的生命周期由机制运行时管理。
- 属性查询和 modifier provider 必须无副作用。
- 缓存只能优化查询，不能成为属性真值来源。
- 完整解析结果必须可审计、可快照、可测试。

设计目标：

- 为动作、机制和后续结算系统提供统一只读属性入口。
- 区分资产基础值、配置静态贡献、运行时机制修饰和派生属性。
- 支持条件 modifier、属性依赖和跨主体读取。
- 保证相同输入和运行态得到相同结果。
- 允许 content 扩展私有属性与 provider，但不允许覆盖公共属性。
- 保持 `core/attributes` 不依赖资产库、配置、content 或基础设施。

## 2. 非目标

属性系统不负责：

- 当前生命、当前能量等资源状态。
- Buff、Debuff、冷却、层数、持续时间和元素附着。
- 输入解释、动作时间轴和 impact 调度。
- 伤害、治疗和反应的最终结算。
- UI 面板缓存和显示格式。
- 结果库具体表结构。

## 3. 属性与机制状态的边界

适合作为属性的内容：

- 基础与最终生命、攻击、防御。
- 暴击率、暴击伤害、元素精通、元素充能效率。
- 治疗加成、受治疗加成和元素伤害加成。
- 目标抗性等需要统一读取和修饰的稳定数值。

不适合作为属性的内容：

| 内容 | 归属 |
| --- | --- |
| 当前生命 | 生命值系统运行态 |
| 当前能量 | 元素能量系统运行态 |
| Buff、被动激活状态 | 状态效果（Buff）系统 |
| 持续时间、层数、冷却 | 领域机制实例或专用运行态 |
| 元素附着、ICD | 元素附着 / ICD 运行时 |
| 护盾实例 | 护盾系统 |
| 元素附魔 | 元素附魔系统 |
| 技能倍率 | 资产数据或动作参数 |
| 一次性保证暴击等效果 | 触发机制 |
| content 专属计数器和模式 | `ContentStateMount` 或机制实例状态 |

判断原则：

- 需要被多个来源数值修饰并统一查询的稳定量，适合建模为属性。
- 具有生命周期、触发、消耗、层数或离散模式的内容，优先建模为机制状态。
- 只服务于一个 handler 的内部数据，优先保存在内容状态中。

## 4. 总体结构

```text
资产数据 + SimulationInput + content contribution
                    |
                    v
        application/assembly
                    |
        +-----------+------------+
        |                        |
        v                        v
BaseAttributeSet        ModifierProviderIndex
        |                        |
        +------------+-----------+
                     |
                     v
        AttributeDefinitionRegistry
                     |
                     v
            AttributeResolver
                     |
                     v
           AttributeResolution
```

主要组件：

- `AttributeDefinitionRegistry`：保存公共与私有属性定义、解析策略引用和叠加组定义。
- `BaseAttributeSet`：按主体和属性保存不可变基础贡献。
- `ModifierProviderIndex`：按写入属性索引静态和动态 provider。
- `AttributeResolver`：统一解析依赖、收集 term、执行 policy 并生成审计结果。
- `AttributeResolutionSession`：管理单次顶层查询内的依赖栈、memo 和 provider 读取校验。
- `AttributeSnapshot`：保存调用者明确请求的历史属性事实。
- `AttributePanelSynchronizer`：逐帧解析当前面板并发布有差异的 `ATTRIBUTE_PANEL_CHANGED` 事实。

## 5. 身份模型

属性主体只支持角色和目标。

- 角色使用稳定战斗实体身份，不使用 `player:active` 空间实体。
- 目标使用稳定目标运行态身份，不使用显示名称。
- 队伍、空间创建物和机制实例不作为属性主体；创建物需要属性时，显式读取其来源角色或目标。

属性归属主体和属性贡献来源使用不同引用类型：subject/target ref 表达“查询谁的数值”，source ref 表达“该基础值或 modifier 来自哪里”。这样避免把资产、动作、机制实例和角色身份混入一个万能引用类型。

## 6. 属性空间

属性空间分为两部分：

```text
公共属性：由 core 定义，封闭且稳定
content 私有属性：由 handler 在自身命名空间内扩展
```

公共属性可以被核心系统和多个内容实现依赖，content 不得覆盖其定义或解析策略。私有属性必须位于对应 `handler_key` 命名空间，默认只供对应 content 或明确协作者使用，不得成为核心系统的隐式依赖，通过 `ContentUnit` 在组装阶段注册。若实际是计数器、模式或临时状态，应改用内容状态或机制实例。

## 7. 属性来源分层

属性采用“原始值预组装，派生值延迟查询”：

- **Primitive Base**：来自资产和配置的不可变原始值，由 application 读取并转换为 core 基础贡献；`core/attributes` 不读取 SQLite，也不解析配置 JSON。
- **Static Modifier**：本次仿真中始终存在的修饰，必须绑定明确属性主体，不能跨队伍槽位泄漏。
- **Runtime Modifier**：来自活动领域实例的动态修饰；对应领域 Store 拥有完整实例与生命周期，属性系统只读取当前有效 provider。
- **Derived Attribute**：根据基础属性、依赖属性和 modifier 延迟解析的最终属性，不写回角色或目标运行态。

条件 provider 可能需要在运行期读取其他领域运行态（队伍场上身份、创建物活动状态）。这类 provider 由装配器在创建对应运行态后调用 `bind_runtime_ports` 注入只读端口；属性运行时在装配前已经引用同一 provider 实例，原位绑定即可，无需重建。绑定只发生在装配期，未绑定或运行期 `contribute` 仍保持只读无副作用。

## 8. 查询与解析

```text
AttributeQuery
-> 校验属性定义与主体类型
-> 解析 definition dependencies
-> 读取 BaseAttributeSet
-> 从 ModifierProviderIndex 选择 provider
-> provider 基于只读 query/session 返回 ModifierTerm
-> 校验 reads/writes、私有命名空间和 stage
-> 应用 stacking group
-> 执行 ResolutionPolicy
-> 应用 override 与 bounds
-> 生成 AttributeResolution
```

属性查询上下文只保存会影响数值语义的结构化信息（tags、source、target）。审计明细级别与数值查询语义分离：切换 trace level 不得改变 final value。

## 9. 稳定规则

以下规则是属性系统的长期方向，具体字段、枚举与公式见[属性系统契约](../契约/属性系统契约.md)：

- **协议边界**：属性层使用小型 Protocol（`ModifierProvider` / `AttributeReader` / `ResolutionPolicy`），不建立可修改所有属性的万能接口；provider 只能经当前 resolution session 读取依赖，不得直接修改状态、绕过 session 或访问其他 content 的私有属性。
- **依赖与循环**：明确的同主体静态循环在组装阶段拒绝，跨主体依赖按完整查询身份在运行时检测；不通过 priority 或执行顺序掩盖循环。memo 只属于单次 session，不形成跨帧或跨查询真值缓存。
- **叠加与覆盖**：同组互斥使用显式 stacking group，不使用全局 priority；override 必须由属性定义显式允许，多个有效 override 不隐式仲裁。
- **快照与审计**：属性默认实时查询，需要固定值时由调用者显式创建局部快照；快照只保存明确请求的 query，不可变，不随后续运行态变化。
- **确定性与数值**：相同 query、基础值和 provider 状态必须得到相同结果；聚合不依赖偶然遍历顺序，核心解析不做显示舍入，真实游戏需要的取整由明确 policy 或机制实现并配 golden case。

## 10. 与其他模块的关系

### 10.1 application / assembly

读取资产与配置、创建基础贡献、注册 content 私有定义和 provider，并构造属性运行时。对需要延迟绑定的 provider，先构造队伍与创建物运行态，再调用 `bind_runtime_ports` 原位注入只读端口；初始最大生命解析发生在绑定前，未绑定 provider 返回空，避免条件 provider 影响 HP 装配。

### 10.2 content

可以贡献私有属性定义、自身命名空间内的 stacking group、原生 `ModifierProvider` 与 legacy modifier 兼容入口；content 不得覆盖公共定义或直接写最终属性。

### 10.3 领域机制 Store

对应领域 Runtime 和 Store 拥有动态实例及其生命周期。活动实例可以提供 modifier provider，属性 resolver 不创建、刷新或移除领域实例。

### 10.4 SimulationContext

组装器将 `AttributeResolver` 注册为只读运行时系统，其他系统通过协议获取属性，不依赖 application 或资产对象。`HealthRuntime` 通过 `AttributeResolver` 查询 `stat.hp.max`，但角色当前生命仍保存在生命运行态中，不注册为公共属性。

### 10.5 infrastructure / results

属性快照与审计结果的持久化由结果基础设施承接，属性系统不定义结果库 schema。

## 11. 模块组织

```text
core/attributes/
├── keys.py           # 公共与私有属性 key 常量
├── definitions.py    # 属性定义、注册表、叠加组定义
├── models.py         # 查询、解析、快照与引用模型
├── protocols.py      # ModifierProvider / AttributeReader / ResolutionPolicy
├── policies.py       # base_sum / total_stat / additive 解析策略
├── indexes.py        # BaseAttributeSet / ModifierProviderIndex
├── resolver.py       # AttributeResolver
├── session.py        # AttributeResolutionSession
├── panel.py          # AttributePanelSynchronizer：面板解析与差异发布
└── errors.py         # 结构化错误

application/assembly/
└── attributes.py     # 资产、配置与 content 装配
```

`core/attributes` 不能 import `assets`、`content`、`application` 或 `infrastructure`。
