# 生命值系统设计

> 状态：第一版已确认并实现。
> 本文档冻结角色生命值运行态、状态提交、事件与系统边界。治疗和护盾公式由独立系统负责；本文只固定它们进入唯一生命写入口的边界。

最后更新：2026-07-13

## 1. 设计目标

生命值系统负责保存角色当前生命，并把已经完成上游数值计算的生命变化提交为可验证、可审计的运行时状态变化。

第一版需要支持：

- 角色承受已经结算的伤害量。
- 角色接受已经结算的生命恢复量。
- 技能或机制产生的直接扣血、生命消耗和生命流失。
- 查询角色当前生命、最大生命和生命比例。
- 最大生命变化时按原生命比例同步当前生命。

生命值系统不负责：

- 计算伤害、防御、抗性、暴击或反应。
- 计算治疗量、治疗加成或受治疗加成。
- 护盾吸收、减伤、生命之契或其他承伤前处理。
- 死亡、击败、复活、免死、动作取消或仿真停止。
- 目标生命、目标移除或索敌过滤。

## 2. 核心决策

第一版冻结以下架构结论：

1. 可变生命运行态只属于角色，不属于场景目标。
2. `CharacterRuntimeState.health` 保存角色当前生命；`TargetRuntimeState` 不增加生命字段。
3. 最大生命是公共派生属性，通过 `AttributeResolver` 查询 `stat.hp.max`；当前生命不是属性系统中的公共属性。
4. 组装器在 frame 0 解析最终最大生命，并以满血创建角色生命状态。
5. `CharacterHealthStore` 和 `HealthRuntime` 只接受 `AttributeSubjectKind.CHARACTER`。
6. 伤害、生命恢复和直接扣血保留不同领域语义，但统一通过 `HealthRuntime` 提交当前生命。
7. 生命值允许降到 `0`；`0` 只是数值下界，不等价于死亡或击败。
8. 最大生命同比同步不是治疗、伤害或直接扣血，不发布普通生命变化事件。
9. 当前角色对场景目标的伤害仍以 `DAMAGE_RESOLVED` 结束，不作用于目标生命。
10. 结果库继续复用通用事件 JSON，不增加生命值专用表或结果库 schema 版本。

## 3. 模块边界

生命值能力分布在三个稳定位置：

```text
core/entity_states/health.py
    HealthState：角色当前生命的最小可变状态

core/systems/health/
    请求、结果、索引、校验、查询和受控提交

application/assembly/assembler.py
    解析初始最大生命并组装 HealthRuntime
```

依赖方向为：

```text
application/assembly
    -> core/attributes
    -> core/entity_states
    -> core/systems/health

core/systems/health
    -> core/attributes
    -> core/entity_states
    -> core/events
```

`core/systems/health` 不依赖 `assets`、`content`、`application`、`infrastructure` 或 `ui`。具体角色、武器、圣遗物和机制只能构造类型化请求，不能绕过运行时直接实现另一套生命结算。

## 4. 状态所有权

### 4.1 当前生命

`HealthState` 只保存：

```text
HealthState
└── current_hp: float
```

规则：

- 接受有限非负数，允许 `0.0`。
- 拒绝 `bool`、NaN、正负无穷和负数。
- 提供 `is_zero` 作为纯数值查询。
- 不保存最大生命、生命比例、生存状态、护盾量或来源信息。
- 运行时语义上的生命写入必须通过 `HealthRuntime`；`HealthState` 自身不解释伤害、治疗或扣血。

### 4.2 最大生命

最大生命始终通过属性系统解析：

```text
CharacterLevelStats.base_hp
-> stat.hp.base
-> static/runtime modifier
-> stat.hp.max
```

生命值系统不复制 `max_hp` 到 `HealthState`，避免形成属性真值和运行态副本两套来源。每次普通生命提交按请求帧查询 `stat.hp.max`。

### 4.3 角色身份索引

`CharacterHealthStore` 建立以下映射：

```text
AttributeSubjectRef.character(combat_entity_id)
-> CharacterRuntimeState.health
```

store 保存原 `HealthState` 引用，不复制状态。构造时拒绝重复角色引用；查询目标主体时抛出 `UnsupportedHealthSubjectError`；缺少已登记角色时抛出 `CharacterHealthNotFoundError`。

## 5. 生命变化模型

### 5.1 变化类型

`HealthChangeKind` 只包含：

| 类型 | 语义 | 当前生命方向 |
| --- | --- | --- |
| `DAMAGE` | 已结算伤害作用于角色生命 | 减少 |
| `HEALING` | 已结算恢复量作用于角色生命 | 增加 |
| `HP_DEDUCTION` | 技能或机制直接扣除生命 | 减少 |

最大生命同步不属于 `HealthChangeKind`，使用独立结果和事件表达。

### 5.2 强类型请求

正式写入口不接受任意正负 delta，而是接受三个强类型请求：

```text
CharacterDamageApplication
CharacterHealingApplication
CharacterHpDeduction
```

共有字段：

```text
change_id
frame
target_ref
amount
source_ref
source_context
tags
```

其中：

- `change_id` 是稳定、非空的上游关联标识。
- `frame` 是非负整数。
- `target_ref` 必须是角色主体。
- `amount` 是有限非负数，方向由请求类型决定。
- `source_ref` 表达属性主体来源，可为空。
- `source_context` 表达内容或运行时来源，可为空。
- `tags` 是无空字符串的不可变标签集合。
- `CharacterHpDeduction` 额外要求 `minimum_remaining_hp`。

分离请求类型可以防止负数方向约定、把直接扣血伪装成伤害，以及调用方遗漏最低生命限制。

### 5.3 统一结果

三个写入口都返回不可变 `CharacterHealthChangeResult`：

```text
change_id
frame
change_kind
target_ref
source_ref
source_context
requested_amount
effective_amount
unapplied_amount
hp_before
hp_after
max_hp
minimum_remaining_hp
tags
```

语义：

- `requested_amount` 是上游请求应用的数值。
- `effective_amount` 是实际改变当前生命的数值。
- `unapplied_amount` 是受当前生命、最大生命或最低生命限制而未应用的部分。
- `minimum_remaining_hp` 只对直接扣血有意义，其余类型为 `None`。
- 不使用 `overkill_damage`，因为第一版没有死亡或击败语义。

结果始终满足：

```text
requested_amount = effective_amount + unapplied_amount
```

## 6. `HealthRuntime`

### 6.1 依赖

```text
HealthRuntime(
    attribute_resolver,
    character_health_store,
    event_engine,
)
```

- `attribute_resolver` 提供请求帧的 `stat.hp.max` 真值。
- `character_health_store` 提供角色当前生命状态引用。
- `event_engine` 发布已提交的生命变化和最大生命同步事件。

第一版 `HealthRuntime` 没有逐帧更新行为，不进入 `BasicRuntimeWorld.updatables`。

### 6.2 查询接口

```text
get_current_hp(character_ref) -> float
get_max_hp(character_ref, frame) -> float
get_hp_ratio(character_ref, frame) -> float
is_zero(character_ref) -> bool
```

查询规则：

- 所有接口只接受已登记角色主体。
- `get_max_hp()` 要求解析结果是有限正数。
- `get_hp_ratio()` 在返回前校验 `0 <= current_hp <= max_hp`。
- `is_zero()` 不推导死亡、击败或复活状态。

### 6.3 写接口

```text
apply_damage(request) -> CharacterHealthChangeResult
apply_healing(request) -> CharacterHealthChangeResult
deduct_hp(request) -> CharacterHealthChangeResult
reconcile_max_hp(character_ref, old_max_hp, new_max_hp, frame)
    -> CharacterMaxHpReconcileResult
```

除 `reconcile_max_hp()` 外，所有普通写入口都在请求帧重新查询最大生命。

## 7. 提交规则

### 7.1 伤害应用

```text
effective_amount = min(requested_amount, hp_before)
hp_after = hp_before - effective_amount
unapplied_amount = requested_amount - effective_amount
```

- 当前生命最低为 `0`。
- 超出当前生命的部分进入 `unapplied_amount`。
- `HealthRuntime` 不重新计算伤害公式。
- 降到 `0` 不产生死亡或击败事件。

### 7.2 生命恢复应用

```text
missing_hp = max_hp - hp_before
effective_amount = min(requested_amount, missing_hp)
hp_after = hp_before + effective_amount
unapplied_amount = requested_amount - effective_amount
```

- 当前生命最高为请求帧的 `max_hp`。
- 超出生命上限的部分进入 `unapplied_amount`，上游治疗系统可以将其解释为溢出治疗。
- 当前生命为 `0` 时仍按数值规则恢复，因为第一版没有死亡状态限制。
- 本入口只应用已结算恢复量，不计算治疗公式。

### 7.3 直接扣血

```text
available = max(0, hp_before - minimum_remaining_hp)
effective_amount = min(requested_amount, available)
hp_after = hp_before - effective_amount
unapplied_amount = requested_amount - effective_amount
```

- `minimum_remaining_hp` 必须位于 `[0, max_hp]`。
- 允许扣到零的机制显式传 `0`；至少保留 1 点生命的机制显式传 `1`。
- 当前生命百分比、最大生命百分比、固定值和周期性流失只是上游 amount 的计算方式，不形成新的生命写入口。
- 直接扣血不经过伤害公式，不发布伤害事件，默认不被护盾处理。

### 7.4 受控提交顺序

普通生命写入统一遵循：

```text
校验请求
-> 查找角色 HealthState
-> 查询请求帧 stat.hp.max
-> 校验当前生命与最大生命
-> 纯计算 CharacterHealthChangeResult
-> 一次性写入 current_hp
-> 按有效变化发布事件
-> 返回结果
```

请求、主体、属性或当前状态校验失败时，不得修改状态，也不得发布生命变化事件。状态写入发生在事件发布之前，因此事件处理器观察到的是已提交状态；当前实现不承诺在事件处理器抛错时回滚状态。

## 8. 数值不变量

生命值系统提交前后必须保持：

```text
max_hp > 0
0 <= current_hp <= max_hp
requested_amount >= 0
effective_amount >= 0
unapplied_amount >= 0
requested_amount = effective_amount + unapplied_amount
```

另外：

- 所有输入和结果必须是有限数。
- `bool` 不作为数值接受。
- `-0.0` 规范化为 `0.0`。
- core 不提前舍入。
- 只有明确的生命上下限规则可以截断数值；非法输入不能通过静默 clamp 掩盖。

## 9. 最大生命同步

动态最大生命从 `old_max_hp` 变为 `new_max_hp` 时，当前生命保持原比例：

```text
hp_after = (hp_before / old_max_hp) * new_max_hp
```

`reconcile_max_hp()` 的边界：

- 调用方必须显式提供旧最大生命、新最大生命和发生帧。
- 两个最大生命都必须是有限正数。
- 提交前当前生命必须位于 `[0, old_max_hp]`。
- 同步结果使用 `CharacterMaxHpReconcileResult` 表达。
- 旧值与新值不同时发布 `CHARACTER_MAX_HP_CHANGED`。
- 不发布 `CHARACTER_HEALTH_CHANGED`，也不把增加部分计为治疗。

当前接口只作为受控同步入口。未来由动态 modifier 生命周期在明确的生效或失效边界调用，不通过逐帧轮询 `stat.hp.max` 猜测变化。

## 10. 组装与运行时挂接

组装器按以下顺序创建角色生命状态：

```text
加载资产与 content contribution
-> 构建 AttributeRuntime
-> 按角色 combat_entity_id 构造 AttributeSubjectRef
-> 在 frame 0 查询 stat.hp.max
-> 创建 HealthState(current_hp=max_hp)
-> 创建 CharacterRuntimeState
-> 创建 CharacterHealthStore
-> 创建 HealthRuntime
-> 注册到 SimulationContext 并暴露在 AssembledSimulation
```

组装阶段拒绝无法解析、非有限或非正的初始最大生命。第一版不修改 `SimulationInput`，也不支持角色初始残血配置。

`AssembledSimulation.health_runtime` 是集成测试、后续系统 adapter 和应用层只读诊断的稳定入口。目标组装流程保持无生命状态。

## 11. 事件契约

### 11.1 `CHARACTER_HEALTH_CHANGED`

```text
category = STATE_CHANGE
payload = CharacterHealthChangedPayload(result)
record_by_default = true
result_committed = true
mechanic_driver = true
```

发布条件：

- `effective_amount > 0`。
- 角色当前生命已经提交为 `hp_after`。

以下情况返回结果但不发布事件：

- 零伤害。
- 满血角色接受恢复量。
- 当前生命为零时继续承伤。
- 被 `minimum_remaining_hp` 完全阻止的直接扣血。

### 11.2 `CHARACTER_MAX_HP_CHANGED`

```text
category = AUDIT
payload = CharacterMaxHpChangedPayload(result)
record_by_default = false
result_committed = true
mechanic_driver = false
```

该事件只审计最大生命同比同步，不驱动普通当前生命变化机制。

### 11.3 与上游事实的顺序

上游数值结算事实和生命状态变化必须分离：

```text
上游伤害或恢复量完成结算
-> 可选的承伤前处理或 adapter
-> HealthRuntime 提交状态
-> CHARACTER_HEALTH_CHANGED
```

需要同时观察“数值已经结算”和“当前生命真实变化”的机制，应分别订阅上游 resolved 事件与生命变化事件。

## 12. 与其他系统的关系

### 12.1 属性系统

- 属性系统拥有 `stat.hp.max` 真值。
- 当前生命不注册为公共属性，也不通过 modifier term 直接修改。
- 依赖生命比例的 content 应通过受限运行时视图查询当前生命和最大生命，不能把当前生命缓存为属性。

### 12.2 伤害系统

当前已实现的伤害链路是角色对场景目标：

```text
ImpactRequest(kind=damage)
-> DamageRequest(CHARACTER -> TARGET)
-> DamageResult
-> DAMAGE_RESOLVED
```

该结果不进入 `HealthRuntime`，因为场景目标没有生命状态。

未来角色承伤接入必须通过显式 adapter：

```text
IncomingDamageResult
-> ShieldRuntime / mitigation（若存在）
-> CharacterDamageApplication
-> HealthRuntime.apply_damage()
```

`HealthRuntime` 不依赖具体伤害公式族，也不把任意 `DamageResult` 自动应用为扣血。

### 12.3 治疗系统

治疗系统负责倍率、固定值、治疗加成、受治疗加成和 `HEALING_RESOLVED` 等上游语义。生命值系统只消费其已经结算完成的非负恢复量：

```text
HealingResult
-> CharacterHealingApplication
-> HealthRuntime.apply_healing()
```

治疗系统阶段 A-C 已实现类型化单目标闭环，见[治疗系统设计](./治疗系统设计.md)、[治疗系统契约](../../契约/治疗系统契约.md)和[治疗系统实现规划](../../工程/治疗系统实现规划.md)。

### 12.4 护盾与角色受伤应用

护盾不是额外生命，不进入 `HealthState`。护盾、减伤和其他承伤前处理只能决定最终交给 `CharacterDamageApplication.amount` 的数值，不能直接修改角色当前生命。

当前代码已经验证以下行为链路，目标架构由独立角色受伤协调器负责编排：

```text
伤害系统已经完成计算的 amount
-> CharacterIncomingDamage
-> CharacterDamageTakenCoordinator 准备护盾与血量计划
-> ShieldRuntime 提交并行吸收计划
-> CharacterDamageApplication(amount=health_bound_damage)
-> HealthRuntime 提交生命计划
```

伤害公式、防御、抗性、暴击、反应和伤害 modifier 均由伤害系统在协调器之前完成。完全吸收时仍构造 `CharacterDamageApplication(amount=0)` 和完整受伤记录，`HealthRuntime` 返回零有效变化且不发布 `CHARACTER_HEALTH_CHANGED`；只要输入 `amount > 0`，外层仍发布表示角色成为正伤害目标的 `DAMAGE_APPLIED`。

直接扣血和按生命流失建模的流血继续使用血量系统独立入口，不经过护盾，也不增加通用 `ignore_shield` 字段。周期性效果如果每次结算的是正式伤害，仍进入角色受伤协调器。

`HealthRuntime` 不导入或查询护盾系统。护盾完整实例由 `ShieldStore` 拥有，不进入 `HealthState`；CharacterDamageTakenCoordinator 只通过护盾和血量两个领域端口协调，不依赖 DamageSystem。

目标迁移中，HealthRuntime 增加不可变 `CharacterDamagePlan`：`prepare_damage()` 完成最大生命查询和前值校验，`commit_prevalidated()` 只应用已经统一预校验的结果，不查询、不计算且不在无回调提交阶段发布事件。现有 `apply_damage()` 可以保留为单领域便捷入口，在内部完成 prepare、validate、commit 和事实发布。

护盾的正式行为和字段分别见[护盾系统设计](./护盾系统设计.md)与[护盾系统契约](../../契约/护盾系统契约.md)，跨领域提交见[角色受伤协调器设计](../协调/角色受伤协调器设计.md)。

### 12.5 生存状态

第一版没有角色生存状态机。未来只有在动作准入、切换、复活、目标移除或战斗结束确实需要生存语义时，才单独设计状态和事件；不得把 `current_hp == 0` 直接扩展为隐式死亡行为。

## 13. 错误模型

```text
HealthSystemError
├── HealthValidationError
├── CharacterHealthNotFoundError
├── InvalidMaxHealthError
├── InvalidCurrentHealthError
└── UnsupportedHealthSubjectError
```

| 错误 | code | 典型场景 |
| --- | --- | --- |
| `HealthSystemError` | `health_error` | 生命值系统错误基类 |
| `HealthValidationError` | `health_validation_error` | 请求字段、帧、数值或最低生命非法 |
| `CharacterHealthNotFoundError` | `character_health_not_found` | 角色没有登记生命状态 |
| `InvalidMaxHealthError` | `invalid_max_health` | 最大生命无法解析、非有限或非正 |
| `InvalidCurrentHealthError` | `invalid_current_health` | 当前生命不在合法区间 |
| `UnsupportedHealthSubjectError` | `unsupported_health_subject` | 向生命值系统传入非角色主体 |

可在组装阶段发现的最大生命和角色登记错误应尽早转换为 application assembly 错误，不延迟到仿真运行中。

## 14. 扩展规则

后续扩展必须保持以下约束：

- 新的生命变化来源优先复用三类现有请求；只有语义无法归入伤害、恢复或直接扣血时才评审新类型。
- content 不得直接修改 `HealthState.current_hp`。
- 目标生命若未来确有分析需求，必须独立评审目标状态、击败语义、索敌和停止条件，不能放宽当前角色专用接口后顺手接入。
- 护盾、生命之契和生存状态使用独立状态与运行时，不向 `HealthState` 堆叠字段。
- 动态最大生命接入使用明确生命周期边界，不使用逐帧轮询。
- 新增事件时继续遵守“上游结算事实”和“已提交状态变化”分离原则。
- 任何具体角色生命消耗比例、最低生命限制或特殊恢复规则都需要可信来源或 golden case。

## 15. 验证策略

### 15.1 单元测试

至少覆盖：

- `HealthState` 对零、正数和非法数值的校验。
- `CharacterHealthStore` 的角色索引、缺失、重复和目标主体拒绝。
- 普通伤害、超量伤害、零伤害和零生命承伤。
- 普通恢复、溢出恢复、满血恢复和零生命恢复。
- 可扣到零、最低保留 1 点和完全受限的直接扣血。
- 当前生命或最大生命非法时不修改状态、不发布事件。
- 最大生命增加和减少时保持生命比例。
- 有效变化与 `CHARACTER_HEALTH_CHANGED` 一一对应。

### 15.2 组装与回归测试

至少保证：

- 每个组装角色初始当前生命等于 frame 0 的最终 `stat.hp.max`。
- 所有角色进入 `CharacterHealthStore`，目标不进入生命系统。
- `HealthRuntime` 注册到 `SimulationContext` 并暴露在 `AssembledSimulation`。
- 通用事件 JSON 可以持久化角色生命变化，无需升级结果库 schema。
- 现有角色对目标伤害仍只产生 `DAMAGE_RESOLVED`，直接伤害 golden case 不增加目标剩余生命断言。
