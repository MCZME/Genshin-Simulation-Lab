# 状态效果（Buff）系统契约

> 状态：正式。
> 本文冻结状态效果系统的公共模型、枚举、应用策略、生命周期、Store/计划、事件、快照、错误、序列化、装配与验证规则。
> 职责背景、归属判断与运行流程见[状态效果系统设计](../架构/系统/状态效果系统设计.md)。
> 最后更新：2026-09-04

## 1. 适用范围

本契约覆盖：

- `core/systems/buff/` 的定义、请求、记录、结果、计划、Store、Resolver、Runtime、provider 与快照。
- `ImpactKind.APPLY_STATUS` 到 `ApplyBuffRequest` 的适配。
- `buff` 意图与 content EventHook / 共鸣响应阶段产出的 Buff 请求接入。
- Buff 变化参与跨系统协调器计划时的准备、提交与事实发布边界。
- `ContentUnit.buff_definitions` 的组装边界。
- Buff 属性 modifier 接入 `core/attributes` 的行为。
- `BUFF_APPLIED` / `BUFF_REMOVED` 事件、通用结果 JSON 与 coverage 分析输入。

不覆盖：

- 无限持续时间、每层独立期限、部分层消费。
- 驱散类别、不可驱散和免疫规则。
- 动态最大生命 Buff（组装阶段拒绝）。
- 通用事件触发型 Buff 模板；触发行为由 content hook / 协调器承载。
- 动态场上角色、队伍光环或范围作用域记录。
- 伤害/治疗专用 modifier、附魔、冷却、附着或 ICD 状态。
- Buff 专用结果库投影表与 UI 展示模型。

## 2. 通用规则

- `Buff` 是中性技术名，不根据有利、有害或中性分类改变核心行为。
- key 使用非空稳定字符串；`display_name` 不得参与身份、冲突、绑定或解析。
- 百分比使用小数倍率，例如 20% 保存为 `0.2`。
- 数值先拒绝 `bool`，再接受有限 `int | float` 并规范为 `float`。
- 帧号是非负整数；duration 和 stack delta 是正整数。
- 所有公共运行时模型不可变并使用 `slots`。
- 序列化枚举使用稳定小写字符串 value。
- tuple 按契约顺序序列化；frozenset 按字典序输出。
- Runtime 不读取 SQLite、配置 JSON、UI 或显示文本。

## 3. 稳定枚举

### 3.1 BuffLifecycleState

```text
active
expired
removed
```

- `active`：记录尚未提交离场状态；是否在查询帧有效仍由半开区间判断。
- `expired`：因到达 `expires_at_frame` 离场。
- `removed`：因替换、驱散、消费或显式请求离场。

### 3.2 BuffApplicationPolicy

```text
replace
refresh
stack_refresh
coexist
```

### 3.3 BuffApplicationOutcome

```text
created
replaced
refreshed
stacked
stack_capped_refreshed
```

### 3.4 BuffRemovalReason

```text
expired
replaced
dispelled
consumed
explicit
```

`expired` 和 `replaced` 只能由 BuffRuntime 对应流程产生。外部显式移除请求只允许 `dispelled`、`consumed` 或 `explicit`。

### 3.5 BuffValueRefreshPolicy

```text
keep_initial
replace_latest
```

### 3.6 BuffStackScaling

```text
constant
linear
```

## 4. BuffInstanceRef

```text
BuffInstanceRef
├── sequence: int
└── domain_key: str = "buff"
```

规则：

- `sequence` 必须是正整数。
- `domain_key` 固定为 `buff`。
- 排序先按 domain key，再按 sequence；同一 Store 中实际等价于 sequence 升序。
- 稳定字符串形式为 `buff:{sequence}`。

序列化：

```json
{
  "domain_key": "buff",
  "sequence": 12
}
```

## 5. BuffAttributeModifierTemplate

```text
BuffAttributeModifierTemplate
├── term_key: str
├── target_key: AttributeKey
├── stage: ModifierStage
├── stack_scaling: BuffStackScaling = constant
├── stacking_group: str | None
├── required_query_tags: frozenset[str]
├── excluded_query_tags: frozenset[str]
└── audit_tags: tuple[str, ...]
```

规则：

- `term_key` 在同一 BuffDefinition 中唯一。
- target key 必须已注册，stage 必须被目标属性 policy 允许。
- stacking group 提供时必须存在，且 target/stage 与属性 stacking group 定义一致。
- required 与 excluded tags 必须是非空字符串集合，二者不能相交。
- audit tags 保持定义顺序，值必须是非空字符串。
- 模板不保存数值表达式、函数、condition 回调、priority 或 emission index。

查询匹配：

```text
required_query_tags <= query.context.tags
and
excluded_query_tags 与 query.context.tags 无交集
```

不匹配时该模板不产生 term，也不作为 rejected term 进入属性解析；它在 provider 阶段即不适用。

## 6. BuffDefinition

```text
BuffDefinition
├── definition_key: str
├── mechanic_key: str
├── handler_key: str
├── conflict_key: str
├── target_kinds: frozenset[AttributeSubjectKind]
├── application_policy: BuffApplicationPolicy
├── value_refresh_policy: BuffValueRefreshPolicy
├── max_stacks: int
├── attribute_modifiers: tuple[BuffAttributeModifierTemplate, ...]
├── marker_only: bool = false
├── tags: frozenset[str]
└── display_name: str | None
```

规则：

- 四个 key 都必须是非空稳定字符串。
- target kinds 不能为空，只允许 character 和 target。
- `max_stacks` 必须是正整数。
- `refresh`、`replace`、`coexist` 要求 `max_stacks == 1`。
- `stack_refresh` 允许 `max_stacks >= 1`。
- `marker_only=false` 时 attribute modifiers 不能为空。
- `marker_only=true` 时 attribute modifiers 必须为空。
- modifier term key 不能重复。
- tags 只用于查询、审计和分析，不驱动应用策略。
- 定义本身不可包含 Store、Runtime、content 对象、数据库对象或可调用回调。
- `display_name` 提供时必须是非空字符串，未提供时为 `None`；它经 provider 的 `ModifierProviderSpec.display_name` 进入属性词条审计（`provider_display_name`），并随 Buff 实例快照与 `BUFF_APPLIED` 载荷中的 `instance_after` 下发，不参与身份、冲突或生命周期判断。

定义序列化不输出 `display_name`（见第 27 节）。

## 7. BuffDefinitionRegistry

```text
BuffDefinitionRegistry
├── register(definition)
├── get(definition_key)
├── contains(definition_key)
└── definitions
```

规则：

- 注册只发生在组装阶段。
- definition key 全局唯一，重复注册抛 `BuffDefinitionConflictError`。
- `definitions` 按 definition key 字典序返回不可变 tuple。
- 运行开始后按只读方式使用。
- 未知 definition key 抛 `BuffDefinitionNotFoundError`。

## 8. BuffModifierValue 与 BuffResolvedAttributeModifier

### 8.1 BuffModifierValue

```text
BuffModifierValue
├── term_key: str
└── value: float
```

规则：

- term key 必须非空。
- value 必须是有限数字。
- 一个 ApplyBuffRequest 中 term key 不能重复。
- 对非 marker 定义，请求提供的 term key 集合必须与定义模板 key 集合完全一致。
- marker 定义要求 modifier values 为空。

### 8.2 BuffResolvedAttributeModifier

```text
BuffResolvedAttributeModifier
├── template: BuffAttributeModifierTemplate
└── value: float
```

`value` 是应用帧已经解析的单次或每层基础值。provider 的有效值：

```text
constant -> value
linear   -> value * record.state.stack_count
```

乘法结果必须再次校验有限性。Buff 系统不做显示舍入。

## 9. ApplyBuffRequest

```text
ApplyBuffRequest
├── request_id: str
├── frame: int
├── order: int
├── definition_key: str
├── target_ref: AttributeSubjectRef
├── source_context: RuntimeSourceRef
├── duration_frames: int
├── stack_delta: int = 1
├── modifier_values: tuple[BuffModifierValue, ...]
└── applier_ref: AttributeSubjectRef | None
```

规则：

- request id 和 definition key 必须非空。
- request id 在一次仿真内必须唯一；同一外部事实重放必须生成相同 id，不同应用意图不能复用 id。
- frame 和 order 是非负整数。
- target 只支持 character 或 target。
- duration 和 stack delta 必须是正整数。
- applier 可以为空；提供时只支持 character 或 target。
- source context 必须表示可跨重复施放保持一致的来源绑定，例如资产 key + 槽位或稳定机制来源；单次 action/impact instance 只进入 request id。需要不同来源各自刷新时，definition/conflict key 也必须按来源稳定区分。
- modifier values 按 term key 排序后冻结。
- definition 解析与 modifier value 完整性由 BuffRuntime 在准备阶段校验。
- `refresh`、`replace`、`coexist` 要求 `stack_delta == 1`。
- `stack_refresh` 允许任意正 stack delta，并按 max stacks 截断。

请求不包含：

- 显示名称。
- lifecycle state 或 instance ref。
- 已推导 expires at frame。
- 任意 params dict。
- Event 或回调对象。

BuffRuntime 和 BuffImpactRequestHandler 不负责从属性查询推导 modifier value。`modifier_values` 始终是命令生产者已经解析完成的输入。

## 10. BuffState

```text
BuffState
├── target_ref: AttributeSubjectRef
├── applier_ref: AttributeSubjectRef | None
├── source_context: RuntimeSourceRef
├── stack_count: int
├── max_stacks: int
├── resolved_modifiers: tuple[BuffResolvedAttributeModifier, ...]
└── tags: frozenset[str]
```

不变量：

```text
1 <= stack_count <= max_stacks
max_stacks == record.definition.max_stacks
resolved modifier keys == definition template keys
tags == definition.tags
```

marker definition 要求 resolved modifiers 为空；非 marker 定义要求一一对应。

## 11. BuffRecord

```text
BuffRecord
├── instance_ref: BuffInstanceRef
├── definition: BuffDefinition
├── created_frame: int
├── last_applied_frame: int
├── expires_at_frame: int
├── lifecycle_state: BuffLifecycleState
├── state: BuffState
├── removed_frame: int | None
└── removal_reason: BuffRemovalReason | None
```

通用不变量：

```text
created_frame <= last_applied_frame < expires_at_frame
state.max_stacks == definition.max_stacks
state.tags == definition.tags
```

活动记录：

- lifecycle state 为 `active`。
- removed frame 和 removal reason 必须为空。
- stack count 必须为正且不超过上限。

非活动记录：

- lifecycle state 为 `expired` 或 `removed`。
- removed frame 和 removal reason 必须同时存在。
- `expired` 必须对应 reason `expired`。
- `removed` 不能对应 reason `expired`。
- removed frame 不能早于 created frame。

活动判断：

```text
is_active_at(frame) =
    lifecycle_state == active
    and created_frame <= frame < expires_at_frame
```

`lifecycle_state == active` 但查询帧已经到达 expires at 的记录不生效，等待 Runtime 在时间推进阶段提交过期状态。

## 12. BuffApplicationResult

```text
BuffApplicationResult
├── request_id: str
├── frame: int
├── order: int
├── outcome: BuffApplicationOutcome
├── instance_ref: BuffInstanceRef
├── definition_key: str
├── mechanic_key: str
├── target_ref: AttributeSubjectRef
├── applier_ref: AttributeSubjectRef | None
├── source_context: RuntimeSourceRef
├── stacks_before: int
├── stacks_after: int
├── expires_at_before: int | None
├── expires_at_after: int
├── replaced_instance_refs: tuple[BuffInstanceRef, ...]
├── resolved_modifiers_after: tuple[BuffResolvedAttributeModifier, ...]
└── instance_after: BuffInstanceSnapshot | None
```

结果规则：

- 新建或替换时 stacks before 为 `0`。
- created 的 replaced refs 为空。
- replaced 的 replaced refs 非空，并按 instance ref 排序。
- refreshed 的 stacks before 等于 stacks after。
- stacked 的 stacks after 大于 stacks before。
- stack capped refreshed 的 stacks before 等于 stacks after 等于 max stacks。
- expires at after 必须大于 frame。
- target、applier 和 source context 表示提交后活动记录的有效归属与来源。
- 结果完整保留属性审计所需的已解析值。
- `instance_after` 默认不参与计划解析；`BUFF_APPLIED` 事件由 Runtime 在提交后为载荷填充完整实例快照。直接 `apply*()` 返回的普通结果不保证携带该字段。

```text
RemoveBuffRequest

├── instance_ref: BuffInstanceRef
```

外部请求 reason 只允许：

### 13.2 BuffRemovalResult

```text
BuffRemovalResult
├── frame: int
├── instance_ref: BuffInstanceRef
```

## 14. BuffMutationPlan

```text
BuffMutationPlan
├── operation_id: str
├── frame: int
├── expected_store_version: int
├── request_ids: tuple[str, ...]
├── expected_records: tuple[BuffRecord, ...]
├── replacement_records: tuple[BuffRecord, ...]
├── application_results: tuple[BuffApplicationResult, ...]
└── removal_results: tuple[BuffRemovalResult, ...]
```

规则：

- operation id 必须非空。
- expected store version 是非负整数。
- request ids 按本计划语义顺序冻结且不能重复；纯到期计划使用空 tuple。
- expected 和 replacement records 都按 instance ref 排序，不能有重复引用。
- expected records 只保存批次开始前的 Store 前值；同一记录在批次内被连续刷新或叠层时只出现一次。
- replacement records 只保存批次全部请求处理后的最终记录；中间计划状态不作为重复 replacement record 保存。
- application results 按 `(order, target kind, target id, instance ref)` 排序。
- removal results 按 `(frame, instance ref)` 排序；批量替换时旧实例移除顺序稳定。
- replacement records 是提交后的完整记录，包括新建、刷新、叠层和离场记录。
- plan 不保存可调用对象或 Store 引用。

operation id 由 Runtime 集中、确定性生成：

```text
批量应用：buff-apply:{frame}:{len(request_id_1)}:{request_id_1}:...
显式移除：buff-remove:{len(request_id)}:{request_id}
到期批次：buff-expire:{frame}:{len(seq_1)}:{seq_1}:...
```

实现必须使用无歧义的长度前缀编码，不能直接用分隔符拼接任意 request id 后假设不会碰撞。

## 15. BuffCommitReceipt 与 BuffStore

### 15.1 BuffCommitReceipt

```text
BuffCommitReceipt
└── plan: BuffMutationPlan
```

receipt 只能由成功的 `commit_prevalidated()` 创建。事件从 receipt 生成，不能在提交前从临时结果发布。

### 15.2 BuffStore

```text
BuffStore
├── version
├── records
├── active_records
├── allocate_ref()
├── add(record)
├── get(instance_ref)
├── require(instance_ref)
├── active(frame, target_ref?, definition_key?, mechanic_key?)
├── due_at(frame)
├── conflicts(target_ref, conflict_key, frame)
├── validate(plan)
└── commit_prevalidated(plan)
```

Store 规则：

- 只保存完整 BuffRecord，不保存 definition key 到可变组件的拆分表。
- records 按 instance ref 返回，包括历史离场记录。
- active 查询必须同时调用 `is_active_at(frame)`。
- conflicts 使用 `(target_ref, definition.conflict_key)`，只返回查询帧活动记录。
- version 在 replacement records 非空的一次提交后只增加一次。
- operation id 成功提交后进入已提交集合；重复提交抛 `BuffPlanConflictError`。
- Store 同时保存已经成功提交的外部 request id；任一非空 plan request id 已提交时，validate 抛 `BuffPlanConflictError`。
- validate 检查 Store version 和 expected records 完整前值。
- commit prevalidated 不再查询、计算、调用 handler 或发布事件。
- commit prevalidated 不重新调用 `validate()`；调用方必须先显式完成全部可失败检查。
- commit prevalidated 把非空 plan request ids 一并登记为已提交。
- 实例 sequence 单调增加但不保证连续；准备失败允许留下未使用序号。
- `add(record)` 只用于受控初始记录装载，不允许绕过计划和版本校验在运行期写入。

### 15.3 BuffStoreReader

`BuffStoreReader` 是 `BuffStore` 的只读适配器，向 `BuffAttributeModifierProvider` 与窄只读协议暴露 `active(...)`，不暴露 allocate、validate、commit 或内部版本。

## 16. BuffResolver

### 16.1 BuffApplicationResolution

```text
BuffApplicationResolution
├── definition: BuffDefinition
├── request: ApplyBuffRequest
├── expected_records: tuple[BuffRecord, ...]
├── replacement_records: tuple[BuffRecord, ...]
├── result: BuffApplicationResult
└── removals: tuple[BuffRemovalResult, ...]
```

expected records 和 replacement records 都按 instance ref 排序。该模型只描述单个请求的纯解析结果；BuffRuntime 负责把有顺序依赖的一批 resolution 归并为一个 BuffMutationPlan，并消除中间记录的重复前值与重复最终值。

### 16.2 解析入口

BuffResolver 是纯对象，不持有 Store 或 EventEngine。

```text
resolve_apply(definition, request, conflicts, allocated_ref_or_none)
-> BuffApplicationResolution
```

Resolver 规则：

- 不分配实例引用；allocated ref 由 Runtime 在创建分支传入。
- 创建、替换或共存分支要求 allocated ref；复用现有实例的刷新/叠层分支要求该参数为空。
- 不读取属性、content state 或其他领域 Runtime。
- 不写 Store。
- 不发布事件。
- 相同输入必须产生相同输出。

## 17. 应用策略精确定义

### 17.1 兼容记录

`refresh` 和 `stack_refresh` 的唯一冲突记录必须同时满足：

```text
record.definition.definition_key == request.definition_key
record.state.target_ref == request.target_ref
record.state.applier_ref == request.applier_ref
record.state.source_context == request.source_context
record.is_active_at(request.frame)
```

request target kind 还必须位于 definition.target_kinds。上述任一条件不满足时抛 `BuffApplicationConflictError`。

### 17.2 create

所有策略在没有需要复用的记录时创建：

```text
created_frame = frame
last_applied_frame = frame
expires_at_frame = frame + duration_frames
stack_count = min(stack_delta, max_stacks)
```

非 stack refresh 策略的 stack delta 已被约束为 1。

### 17.3 replace

- 查询全部活动冲突记录。
- 把冲突记录原子改为 removed/replaced。
- 分配新 instance ref 并创建新记录。
- outcome 为 `replaced`；无冲突时为 `created`。
- 旧实例 created/last applied/values 不转移到新实例。

### 17.4 refresh

- 无冲突时创建。
- 有且只有一个兼容冲突时保留 instance ref 和 created frame。
- last applied frame 更新为请求 frame。
- expires at 使用 `max(old, frame + duration)`。
- stack count 保持 1。
- value refresh policy 决定保留旧 resolved values 或使用新请求值。
- outcome 为 `refreshed`。

### 17.5 stack_refresh

- 无冲突时创建，初始层数按上限截断。
- 有且只有一个兼容冲突时保留 instance ref 和 created frame。
- last applied 和 expires at 按 refresh 规则更新。
- stack after 使用 `min(max_stacks, before + delta)`。
- 未到上限且增加时 outcome 为 `stacked`。
- 已到上限或本次增加被完全截断时 outcome 为 `stack_capped_refreshed`。
- resolved values 按 value refresh policy 处理；所有层共享一组 value 和期限。

### 17.6 coexist

- 不复用冲突记录。
- 每个请求始终创建独立 instance ref。
- 每个实例独立期限和 resolved values。
- outcome 始终为 `created`。

## 18. BuffReader

```text
BuffReader
└── active(
        frame,
        target_ref=None,
        definition_key=None,
        mechanic_key=None,
    ) -> tuple[BuffRecord, ...]
```

规则：

- 返回不可变记录 tuple，按 instance ref 排序。
- 不暴露 Store version、allocate、validate 或 commit。
- 查询没有匹配项时返回空 tuple。
- query 不提交过期状态，不发布事件。
- content 或其他领域只能依赖此类窄只读协议，不能拿到 BuffStore。

不提供按显示名称、前缀、Python 类型、任意 predicate 或宽泛 tags dict 查询。

## 19. BuffAttributeModifierProvider

每个包含属性模板的 BuffDefinition 在组装时生成一个 provider：

```text
provider_key = "buff.attribute:" + definition_key
writes = definition 中所有 target_key
private_namespace = handler_key
owner_ref = None
reads = ()
display_name = definition.display_name
```

`contribute(query, session)`：

1. 忽略 session，不读取其他属性。
2. 通过 BuffReader 查询相同 definition key、query subject 和 query frame 的活动记录。
3. 按 instance ref 遍历记录，按定义模板顺序处理。
4. 检查 query tags。
5. 计算 constant 或 linear value。
6. 生成 ModifierTerm。

term 字段：

```text
target_key = template.target_key
stage = template.stage
value = resolved value 或 resolved value * stack count
provider_key = 上述稳定 provider key
source_ref = RuntimeSourceRef(
    kind=mechanic,
    source_key=record.definition.mechanic_key,
    instance_id=record.instance_ref.to_key(),
)
stacking_group = template.stacking_group
audit_tags = template.audit_tags + (
    "buff",
    "definition:" + definition_key,
    "stacks:" + stack_count,
)
```

`provider_display_name` 由 AttributeResolver 从 `ModifierProviderSpec.display_name` 注入；term 自身可以不预填。内容未提供显示名时为 `None`，前端回退 `provider_key`。

provider 不得：

- 写 Buff Store。
- 把过期提交作为查询副作用。
- 调用 EventEngine。
- 返回未声明属性或 stage。
- 使用注册顺序决定 term 顺序。

## 20. BuffRuntime

```text
BuffRuntime
├── apply(request) -> BuffApplicationResult
├── apply_many(requests) -> tuple[BuffApplicationResult, ...]
├── remove(request) -> BuffRemovalResult
├── prepare_apply(requests) -> BuffMutationPlan
├── validate(plan)
├── commit_prevalidated(plan) -> BuffCommitReceipt
├── publish_committed_facts(receipt)
├── events_for(receipt) -> tuple[GameEvent, ...]
├── update_frame(context, frame)
├── snapshot(frame)
└── is_idle() -> bool
```

### 20.1 apply / apply_many

- requests 不能为空。
- 同一批次 frame 必须相同。
- order 在批次内唯一，request id 在批次内唯一。
- 按 order 冻结处理顺序。
- 后一个请求在纯计划阶段看到前一个请求的计划后记录，保证同批冲突语义确定。
- 整批只生成一个 Store plan 和 operation id。
- `apply()` 是单请求便捷入口，等价于 `apply_many((request,))`。
- 直接调用时在提交后立即发布本批事实。

### 20.2 remove

- 校验实例在 request frame 活动。
- 生成 removed record、removal result 和单 plan。
- 提交后发布 `BUFF_REMOVED`。

### 20.3 prepare / validate / commit / publish

跨系统协调器使用：

```text
plan = runtime.prepare_apply(requests)      # 只准备，不提交、不发布
domain 协调器统一 validate
receipt = runtime.commit_prevalidated(plan) # 无回调提交
runtime.publish_committed_facts(receipt)    # 全部领域提交后发布
```

- `prepare_apply` 只做纯解析并冻结计划，不进入 mutation 提交范围。
- `commit_prevalidated` 不重新调用 validate，也不发布事件。
- `publish_committed_facts` 保留事件期写入保护，只能在 receipt 对应计划提交后调用。
- `events_for(receipt)` 返回本计划应发布的事件，供调用方检查或统一发布。

### 20.4 update_frame

- 查找 `expires_at_frame <= frame` 且 lifecycle active 的记录。
- 按 instance ref 生成 expired records 和 removal results。
- 同一帧到期记录在一个 plan 中原子提交。
- 提交后按 instance ref 发布 `BUFF_REMOVED`。

### 20.5 snapshot / idle

- `snapshot(frame)` 返回 BuffSnapshot，只含指定帧活动实例。
- `is_idle()` 固定返回 `True`。简单 Buff 不因未来过期边界单独延长仿真。

### 20.6 reentrancy

Runtime 维护 mutation 和 event publishing guard：

- mutation/commit 范围内再次写入抛 `BuffReentrancyError`。
- 事实发布调用栈内再次写入也抛 `BuffReentrancyError`。
- 直接入口先缓存事件，退出 mutation scope 后发布。
- EventEngine 不捕获 handler 异常；异常使仿真失败，但已提交事实不回滚。

## 21. 接入契约

### 21.1 ImpactKind.APPLY_STATUS

ImpactRequest：

```text
kind = apply_status
target_refs = 一个或多个 character:/target: 稳定主体 id
params = {
  "buff": {
    "definition_key": str,
    "duration_frames": int,
    "stack_delta": int,
    "modifier_values": [
      {"term_key": str, "value": number}
    ],
    "applier_ref": {
      "kind": "character" | "target",
      "entity_id": str
    } | null
  }
}
```

规则：

- `params.buff` 必须存在且是 object。
- 未声明字段拒绝，不默许拼写错误。
- target refs 不能为空，重复目标拒绝。
- 目标按输入 tuple 顺序映射为 request order；handler 生成稳定 request id。
- source context 使用 `RuntimeSourceRef(MECHANIC, definition.mechanic_key, "slot:{owner_slot}" 或 None)`；单次发生身份只用于 request id。
- 同一 ImpactRequest 的全部目标通过 `apply_many()` 原子提交。
- 缺 handler、未知 definition 或非法值属于结构化仿真错误，不静默忽略。

APPLY_STATUS 适配后的 request id 固定使用长度前缀编码：

```text
source_occurrence_id = source_impact_point_id ?? impact_request.request_id
impact_request_id = impact_request.request_id ?? ""
definition_key = params.buff.definition_key

buff-impact:{len(source_occurrence_id)}:{source_occurrence_id}:{len(impact_request_id)}:{impact_request_id}:{len(definition_key)}:{definition_key}:{len(target_kind)}:{target_kind}:{len(target_entity_id)}:{target_entity_id}:{order}
```

`source_impact_point_id` 与 `ImpactRequest.request_id` 至少一个必须存在，否则适配失败。长度按字符串 Unicode code point 数计算。

`BuffImpactRequestHandler` 为每次成功处理记录 `BuffApplicationRecord`：

```text
BuffApplicationRecord
├── frame
├── impact_request
├── buff_requests
└── results
```

### 21.2 BUFF 意图

统一意图队列的 `buff` 意图载荷必须是 `ApplyBuffRequest`：

```text
IntentKind.BUFF
payload = ApplyBuffRequest
处理器 = BuffIntentHandler -> BuffRuntime.apply(request)
```

content EventHook 的 `HookResult.buff_requests` 由 HookDispatcher 转为下一结算轮次的 BUFF 意图；每个请求单独入队并按统一排序结算。共鸣响应阶段为动态双草精通 / 双岩减抗生成的 Buff 请求也走同一入口。多请求在此路径不承诺跨请求原子性；需要原子性的能力应使用 `apply_many` 或协调器计划。

### 21.3 跨系统协调器

Buff 作为协调器端口时必须满足：

- 协调器在准备阶段调用 `prepare_apply` 并冻结全部领域计划。
- 提交前统一 `validate`；任一领域失败则整批不提交。
- 提交阶段只调用 `commit_prevalidated`，不触发业务失败。
- Buff 事实在相关领域全部提交后经 `publish_committed_facts` 发布。
- 超导减抗等反应状态到 Buff 的映射使用显式 adapter，不接受未注册状态 profile。

## 22. 事件契约

### 22.1 BUFF_APPLIED

```text
EventType.BUFF_APPLIED
category = STATE_CHANGE
payload_type = BuffAppliedPayload
record_by_default = true
result_committed = true
mechanic_driver = true
cancelable = false
mutable_payload = false
```

```text
BuffAppliedPayload
└── result: BuffApplicationResult
```

每个成功请求发布一次，包括 stack capped refreshed。事件载荷的 `result.instance_after` 在提交后填充完整实例快照，供结果库折叠还原与展示。

### 22.2 BUFF_REMOVED

```text
EventType.BUFF_REMOVED
category = STATE_CHANGE
payload_type = BuffRemovedPayload
record_by_default = true
result_committed = true
mechanic_driver = true
cancelable = false
mutable_payload = false
```

```text
BuffRemovedPayload
└── result: BuffRemovalResult
```

### 22.3 顺序

- replace：全部 `BUFF_REMOVED` 随后对应 `BUFF_APPLIED`。
- refresh/stack：只发布 `BUFF_APPLIED`。
- expire batch：按 instance ref 发布 `BUFF_REMOVED`。
- apply many：按 request order 发布；每个 replace 的 removal 紧邻并先于自己的 applied 事件。
- 所有事件只能观察完整提交后的 Store。

```text
BuffInstanceSnapshot
├── instance_ref
├── definition_key
├── mechanic_key
├── handler_key
├── conflict_key
├── display_name: str | None
├── target_ref
```

```text
BuffSnapshot
├── frame: int
└── instances: tuple[BuffInstanceSnapshot, ...]
```

只包含 snapshot frame 活动的实例，按 instance ref 排序。快照不可变，不随后续刷新或移除改变。

## 24. application 装配契约

`ContentUnit` 支持：

```text
buff_definitions: tuple[BuffDefinition, ...] = ()
```

组装时把 content 贡献的 Buff 定义与内置定义一起注册：

```text
content_bundle.buff_definitions
+ superconduct_buff_definition()
+ create_resonance_buff_definitions()
-> BuffDefinitionRegistry
```

目标组装顺序：

1. content factory 根据 asset params 构造 BuffDefinition。
2. application 校验 definition handler key 必须等于 unit handler key。
3. 收集全部定义并创建 `BuffDefinitionRegistry`。
4. 校验 Buff definition 的属性、stage、target kinds、私有命名空间、stacking group 和动态最大生命依赖闭包。
   动态最大生命依赖闭包包含属性定义依赖和 provider `reads -> writes` 依赖。
5. 创建 `BuffStore`，为非 marker definition 创建 `BuffAttributeModifierProvider`。
6. 构建最终 `AttributeRuntime`（静态 provider + content provider + Buff provider）。
7. 创建 `BuffResolver`、`BuffRuntime` 和 `BuffImpactRequestHandler`。
8. 注册到 `SimulationContext` 和 `AssembledSimulation`。
9. 把 BuffRuntime 挂到 `TIME_ADVANCE` 阶段，把 BUFF 意图处理器注册到结算运行时。
10. 把 APPLY_STATUS 接入 ImpactRequestDispatcher，把 HookDispatcher 挂到 `FACT_RESPONSE`。

`AssembledSimulation` 暴露：

```text
buff_definitions
buff_store
buff_resolver
buff_runtime
buff_handler
```

组装错误包括：

- 重复 definition key。
- handler key 与 contribution 不一致。
- 未知或非法属性 target/stage。
- 私有属性命名空间越界。
- modifier term key 重复。
- marker 与 modifier 配置冲突。
- stacking group 未知或与模板不一致。
- 动态最大生命依赖。
- 非法 max stacks 或策略组合。

这些错误转换为 `InvalidRuntimePayloadError`，不延迟到第一次属性查询。

目标层级：

```text
BuffSystemError
├── BuffValidationError
├── BuffDefinitionError
│   ├── BuffDefinitionNotFoundError
│   └── BuffDefinitionConflictError
├── BuffModifierBindingError
├── BuffApplicationConflictError
├── BuffInstanceNotFoundError
├── BuffPlanConflictError
├── BuffReentrancyError
└── BuffImpactContractError
```

稳定 code：

| 错误 | code |
| --- | --- |
| `BuffValidationError` | `buff_validation_error` |
| `BuffDefinitionNotFoundError` | `buff_definition_not_found` |
| `BuffDefinitionConflictError` | `buff_definition_conflict` |
| `BuffModifierBindingError` | `buff_modifier_binding_error` |
| `BuffApplicationConflictError` | `buff_application_conflict` |
| `BuffInstanceNotFoundError` | `buff_instance_not_found` |
| `BuffPlanConflictError` | `buff_plan_conflict` |
| `BuffReentrancyError` | `buff_reentrancy_error` |
| `BuffImpactContractError` | `buff_impact_contract_error` |

错误消息必须包含相关 definition key、instance ref、target ref、request id 或字段路径。

## 27. 序列化规则

- BuffInstanceRef 使用结构化 domain key 和 sequence。
- AttributeSubjectRef 保存 kind 和 entity id。
- RuntimeSourceRef 保存 kind、source key 和 instance id。
- definition、mechanic、handler 和 conflict key 全部保留，不能只保存一个通用 key。
- modifier 模板保存 target key、stage、stack scaling、stacking group 和标签条件。
- resolved modifier 保存模板身份和有限 value。
- enums 使用本文小写 value。
- tags 输出排序 tuple；audit tags 保持定义顺序。
- removed frame/reason 同为空或同时存在。
- `BuffDefinition` 内嵌序列化不输出 `display_name`；`BuffInstanceSnapshot` 与 `BUFF_APPLIED.result.instance_after` 输出 `display_name`。旧数据缺失该字段时为 `null`。
- 不序列化 Python 类名、对象地址或 callable。
- 新增、删除或重命名公共字段属于契约变化，必须同步事件、快照和 JSON 往返测试。

## 28. 确定性规则

- definition registry 按 definition key 排序。
- Store records 和快照按 instance ref 排序。
- apply many 要求 order 和 request id 分别唯一，并按 order 处理。
- conflicts 和 due records 按 instance ref 排序。
- modifier values 按 term key 排序。
- provider records 按 instance ref、templates 按定义顺序处理；最终 term 仍由 AttributeResolver 稳定排序。
- 同一 request order 重复时直接报错，不使用输入集合偶然顺序打破平局。
- operation id / request id 使用长度前缀编码，不允许分隔符碰撞。
- 不使用显示名称、对象 hash、dict 插入来源或 Event 订阅顺序决定结果。

## 29. 测试与验证要求

### 29.1 模型与定义

- key、帧、duration、stack、有限数值和 bool 拒绝。
- instance ref、definition、record 和结果不可变。
- marker/modifier、policy/max stack 和 term key 组合校验。
- 活动/离场记录不变量与稳定序列化。

### 29.2 Store 与计划

- 分配、查询、conflicts、due 和历史记录保留。
- Store version、完整前值、重复 operation、重复 ref 冲突。
- 批量 replacement 一次 version 增长。
- plan 任一错误不修改记录。

### 29.3 策略

- replace 无冲突/单冲突/多冲突。
- refresh 创建、刷新、不缩短期限、keep initial 与 replace latest。
- stack refresh 初始多层、正常加层、到顶刷新和大 delta 截断。
- coexist 多实例独立期限。
- refresh/stack 遇到不同 definition、source 或 applier 明确失败。

### 29.4 生命周期与顺序

- `created <= frame < expires` 的每个边界。
- 到期帧 provider 已失效，清理事件随后提交。
- 同帧 apply 后的后续查询可见。
- replace removal 先于 applied。
- 批量 apply order 稳定。
- mutation 和事件发布期间同步重入失败。

### 29.5 属性 provider

- character/target 隔离。
- constant 与 linear stack scaling。
- required/excluded query tags。
- stacking group 交给属性 resolver 选择。
- source ref 包含 mechanic 与 instance id。
- `display_name` 进入 provider spec，属性词条得到 `provider_display_name`。
- 过期/移除记录不贡献 term。
- 查询不改变 Store version、记录或事件缓冲。
- 动态最大生命直接和传递依赖在组装阶段拒绝。

### 29.6 Impact、意图、组装与结果

- APPLY_STATUS params 严格字段校验。
- 多目标一次计划，任一非法目标整批失败。
- definition/handler/私有命名空间装配错误前移。
- BUFF 意图只接受 ApplyBuffRequest；内容 hook 与共鸣响应产物进入下一轮。
- 跨系统协调器准备/统一提交/事实发布顺序正确。
- BUFF_APPLIED/REMOVED payload JSON 往返，`instance_after` 保留展示字段。
- BuffSnapshot 只包含查询帧活动实例。
- 覆盖投影（如后续实现）必须按半开区间并集合并，不能简单相加重叠实例时长。

### 29.7 当前验证状态

当前实现已有：

- `tests/unit/core/systems/buff/test_buff_runtime.py`：模型、Store/计划、策略、生命周期、provider、Impact、事件 JSON、重入与 display_name。
- `tests/unit/content/artifacts/test_maiden_beloved.py`：真实圣遗物 content 的多穿戴者 Buff 定义与独立实例。
- `tests/golden/resonance/test_elemental_resonance_dynamic.py`：双草/双岩共鸣经反应事实生成的 Buff 请求数值与来源基线。
- 内容 hook、意图处理器、共鸣阶段、装配错误与反应协调器边界测试。

验证缺口：

- 尚未建立从真实资产出发、覆盖「真实 Buff 全生命周期 + 属性查询 + 事件 + 覆盖区间」的独立 golden case；现有真实 content（被怜爱的少女）以单元验证为主，动态共鸣 golden 覆盖请求生成层。测试夹具与开发者测试内容不代替真实机制的 golden 覆盖。
