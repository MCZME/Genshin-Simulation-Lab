## 2. 已确认决策

### 2.1 产品方向

- 新项目核心是仿真引擎。
- 应用端从简单伤害计算器扩展为更广义的分析工具。
- 分析能力围绕仿真结果、战斗复盘、参数扫描和结果对比逐步展开。
- 第一版 MVP 定为最短闭环：创建或编辑 `SimulationInput`、队伍/角色构建配置、按键输入轨迹编辑、运行一次仿真、保存完整仿真结果数据（指标展示后置，见 2.29）。
- 第一版暂不强制包含：完整战斗过程复盘、多结果对比、配置模板库、复杂 UI 工作区；参数扫描能力随枚举/区间节点提前进入 MVP（见 2.27）；分析区域不进入 MVP，也不预建数据结构（节点模型见[分析区域设计](../架构/UI/分析区域设计.md)）。

### 2.2 技术与项目管理

- UI 采用 Python + Web 前端（React + React Flow），见 2.27；选型过程与探索结论见该节。
- 新项目采用单仓库单包。
- Python 包名暂定 `genshin_sim`。
- 使用 `src/` 布局。
- 使用 `uv` 管理项目。
- `pyproject.toml` 作为项目配置入口。
- 质量工具确定为 `ruff`、`pyright`、`pytest`。

### 2.3 数据源

- 新项目数据库统一使用本地 SQLite。
- 静态资产库使用 SQLite，作为正式运行时携带的只读生成产物。
- 运行期结果库使用 SQLite，并与基础资产库职责分离。
- 基础资产数据来源确定为 Project Amber / Yatta 当前默认数据。
- 已实现 `infrastructure/assets_project_amber/` 源站适配层，用于抓取开发期 raw JSON cache 并转换为标准资产 manifest。
- 资产数据构建流程确定为 `genshin-sim assets fetch-source` -> `genshin-sim assets build-manifest` -> `genshin-sim assets audit-manifest` -> `genshin-sim assets build --manifest` -> `genshin-sim assets validate`。
- 项目不依赖远程数据库服务，数据库统一为本地 SQLite。

### 2.4 基础资产数据库

- 资产库作为只读生成产物存在。
- 不设置 `raw_assets` 表。
- 采用结构化索引表与 JSON Payload 混合模型。
- `asset_key` 使用 `{asset_type}:{source_id}` 格式。
- `handler_key` 与 `asset_key` 分离，用于绑定仿真代码实现。
- 真实资产若尚无行为实现，`handler_key` 默认保持为空；`generic.noop` 与 `generic.test_*` 只用于测试或占位，不代表真实机制已经实现。
- 技能倍率使用 `scaling_json`。
- 武器、天赋、命座、圣遗物等复杂效果使用 `params_json`。
- `sim-core` 不直接访问 SQLite，而是依赖 `AssetRepository` 协议。

详细方案见：[资产数据库设计总结](../契约/资产数据库设计.md)。

### 2.5 基础资产范围

- 角色、武器、圣遗物等数据进入基础资产数据库。
- 敌人基础抗性/等级信息不接入基础资产数据库。
- 多语言文本第一版不纳入基础资产数据库。
- 复杂机制行为由仿真代码实现；数据库只保存参数和处理器标识。

### 2.6 模块边界

新项目 Python 包位于 `backend/src/genshin_sim/`，顶层模块：

- `core/`
- `content/`
- `assets/`
- `infrastructure/`
- `application/`
- `cli/`

核心原则：

- `core/` 是纯仿真运行时核心，不依赖数据库、UI、应用层或具体内容实现。
- `content/` 保存具体角色、武器、圣遗物和 handler 实现。
- `application/` 负责编排 UI/CLI、资产库、内容实现、仿真核心、结果库和分析能力。
- `infrastructure/` 保存 SQLite、文件存储、日志等具体技术实现。
- 前端为独立 `frontend/` Web 工程，Python 侧由与 CLI 同级的 `server/` 入口暴露应用能力（见 2.27）。
- `core/space` 使用统一的轻量空间实体表示当前场上角色空间实体与多个简单目标点位；内容创建空间对象运行态也归入 `core/space`，并复用 `core/entity_states/lifecycle.py` 的通用生命周期值对象；目标不在空间层建模复杂体型、多 hitbox 或碰撞。
- 按键输入事实在组装阶段由 `InputTraceCompiler` 配对为不可变 `InputSessionPlan`；`ActionManager` 按帧处理 PRESS、RELEASE、派生 HOLD 和 CANCEL。完整计划中的未来 release 不向解释器提前暴露。
- `ActionManager` 统一拥有运行时输入会话、解释器调用、动作准入、具名锁、动作实例和生命周期；它通过 `ActionInterpreterRegistry` 路由输入，不硬编码切人键或具体角色动作含义。
- 动作是否发生、动作类型和动作开始帧由输入会话固定绑定的队伍或角色解释器决定。解释器只返回 `ActionInterpretationResult`、`PreparedAction` 或语义化控制命令，不直接修改动作实例或提交动作状态。
- 元素战技与元素爆发解释器通过显式 `CharacterAbilityConditionPort` 查询冷却与标准元素能量公共条件，再判断 content 私有状态和专属资源；`ActionManager` 负责锁、中断、会话和实例创建的最终准入。
- 所有 Action 在组装阶段注册到 `ActionRegistry`；解释器只返回稳定 `action_key` 和准备参数。`ActionManager` 获取不可变 Action 定义后创建 `ActionInstance`，实例持有本次动作的可变 `action_state`。
- 所有被接受的动作都创建 `ActionInstance`，包括切人。切人由 `TeamActionInterpreter` 准备 `TeamSwitchAction`，再由动作实例修改 `TeamRuntimeState` 并同步 `player:active`。
- HOLD 始终先交给原输入会话绑定的解释器；解释器可以继续等待、启动动作或返回控制已有实例的语义命令。ActionManager 同时独立逐帧调用 Action 推进动作运行态。
- 动作冲突通过具名锁和中断策略表达：Action 声明具名锁和中断策略，ActionManager 完成最终准入检查，并在全部冲突可中断时原子取消当前实例并创建新实例。
- 解释器不得回溯生成开始帧早于当前仿真帧的动作请求；真实角色缺少解释器或其声明的 Action 时应在组装阶段报错。
- `Space` 保存 `player:active`、`target:*` 与内容创建实体的空间实体；`TargetRuntimeCollection` 由 `SpaceRuntime` 持有并管理多个简单目标运行态；`TargetRuntimeState` 第一版只保存 `scene.targets` 已有的目标 id、等级、抗性和空间实体关联，不引入生命值、韧性、元素附着等尚未确认的机制状态。
- `core/` 不保留独立 `summons` 模块。游戏语义上的召唤物、场地物或临时造物若存在于战场空间中，应作为带生命周期的空间实体处理；无空间位置的持续逻辑归机制、状态或 hook。
- Action 在运行过程中产生 `ActionImpactPoint`。动作索敌只负责选择瞄准目标与攻击方向；伤害 Impact 到期时再由 `ImpactRuntime` 按实际 AOE 和当前空间状态解析全部受击目标。
- Action、Reaction、周期状态和空间实体产生的伤害统一进入 Damage Impact 流程；Reaction 不直接构造 `DamageRequest`，也不拥有独立伤害结算入口。
- `ImpactFactory` 接收 `ActionImpactContext` 并展开为真实 `ImpactRequest`；反应生成的 Damage Impact 由元素结算协调器在下一 settlement round 交给同一 Impact 目标解析与机制分发流程。
- `content` registry 第一版按角色、武器、圣遗物和 impact 拆分专用 runtime request 与创建入口，不保留泛化 `RuntimeHandlerRequest`。
- `SimulationAssembler` 通过 `ContentUnitRegistry` 编译 `ContentUnit` 并构造 `RuntimeContentBundle`，再拆分注入 `ActionInterpreterRegistry`、`ActionRegistry`、`CharacterAbilityConditionCoordinator`、解释上下文 provider、`ImpactDispatcher`、`ImpactRequestDispatcher`、`ActionManager`、`ImpactRuntime`、`CreatedObjectRuntime`；内容专属状态由 `ContentStateMount` 挂载在 `CharacterRuntimeState.content_states`；`core/` 不接触完整内容单元对象。
- 当前 content 验证阶段只确认“资产 -> `handler_key` -> content unit -> runtime 注入”的装配链路，不验证真实伤害、治疗、Buff、反应或属性修饰数值。

详细方案见：[新项目模块边界设计](../架构/模块边界设计.md)。

### 2.7 仿真快照与结果库

- 新项目允许 `sim-core` 生成快照。
- 快照用于复盘、审计、分析和调试。
- 快照不是资产数据，也不是项目配置文件。
- 快照生成属于 `core/`，快照持久化属于 `infrastructure/`。
- 运行期结果库与基础资产库职责分离。
- 所有仿真都保存完整结果数据，不区分 `summary_only` 与 `recorded` 模式。
- 运行期结果库采用 SQLite 持久化，以事件流与投影表支持复盘与分析，按当前模块边界落位。

### 2.8 能力迁移与实现分层

能力迁移按以下方式处理：

- 资源数据库：重新实现。
- 模拟架构中的按键输入与动作解释：重新设计并重新落位。
- UI：完全重设计。
- 其余游戏逻辑：按有价值的行为目标、算法思路和测试入口，结合当前边界、契约与验证要求迁移。
- 迁移代码即使可以局部复用，也必须满足当前架构与数值可信度要求。

能力覆盖与迁移路线图见[分析系统设计](../架构/分析系统设计.md)与[文档入口](../文档入口.md)的工程文档。

### 2.9 日志系统

第一版日志系统采用 Python 标准库 `logging`，不新增第三方依赖。

已确认原则：

- `infrastructure/logging/` 保存日志配置、handler、formatter、输出路径和轮转策略。
- CLI 与 UI 作为入口负责初始化日志。
- 其他模块只使用标准库 `logging.getLogger(__name__)`，不依赖 `infrastructure/logging`。
- 工程日志与 `core/events`、快照和结果库职责分离。
- 日志配置不进入 `SimulationInput`。

2026-08-11 补充确认：

- 日志主读者为开发者；自动化日志分析暂不纳入设计。
- 文件日志固定 JSONL，控制台保持文本；顶层键为 `ts`/`level`/`logger`/`message`/`fields`/`exception`。
- 日志目录为 `<data_dir>/logs/`，每次打开创建一个 `genshin-sim-<时间戳>-<进程号>.jsonl`；保留 30 天、最多 200 个文件，启动时清理。
- 项目模式（存在 `config.toml`）默认启用文件日志；`project init` 与帮助类入口豁免；缺失配置时报错处理。
- `session_id` 通过 `extra` 约定关联，关键日志点由测试钉住，不放开 `application` 对 `infrastructure/logging` 的依赖。

详细方案见：[日志系统设计](../架构/日志系统设计.md)。

### 2.10 领域运行态与共享抽象

有身份和生命周期的运行态由对应 `core/systems/<domain>/` 直接拥有：

- 每个领域直接定义强类型实例引用、完整记录、生命周期、索引、命令、计划和提交入口。
- 护盾由 `ShieldStore` 原子拥有完整 `ShieldRecord`，采用单一 Store 聚合管理。
- `source_context`、`creator_ref` 和领域 affected scope 使用不同语义，分别表达来源、创建者与影响范围。
- capability 是领域 Runtime 暴露的类型化只读协议，不是实例上的单一字符串字段。
- Buff、冷却、ICD 和元素附着分别设计自己的状态模型与 Store。
- 中立值对象或提交工具只在至少两个已实现领域证明相同不变量后提取；共享模块按需建立。
- 状态先按领域计划提交，事实后发布；事件回调不能同步写入当前结算。

技术边界见[领域运行态实现规范](../工程/领域运行态实现规范.md)；所有原神游戏机制的设计、数值可信度和验证要求见[原神游戏机制实现规范](../工程/原神游戏机制实现规范.md)。

### 2.11 属性与伤害
- 属性采用确定性查询与解析，不保存可任意修改的最终面板：公共属性由 `core/attributes` 封闭定义，content 只注册私有属性；modifier 以结构化 term 固定阶段贡献；当前生命、能量、Buff、冷却、附着等运行态不作为普通公共属性。
- 伤害统一走 Damage Impact：先经 Space 解析实际 AOE 目标，再逐目标构造单目标 `DamageRequest`；主攻击标签经 `DamageProfileRegistry` 解析 `formula_key`，未注册的非反应标签默认通用公式，`reaction.` 标签必须显式注册；`formula_key` 不作为请求或自由 payload 显式填写的字段。
- `elemental_amount=0` 仍可造成元素伤害但不产生元素施加；正元素量经 ICD 后与目标 Aura 决定反应；`strike_type=BLUNT` 是碎冰的稳定攻击侧证据。
- 通用公式固定倍率、增伤、暴击、反应、防御和抗性区；调试倍率通过 `DebugDamageAdjustment` 构造注入，生产默认 `1.0`，content 不得使用。
- 角色伤害由角色受伤协调器应用到护盾和血量，协调器不参与或反馈伤害计算。

详细见[属性系统设计](../架构/属性系统设计.md)、[属性系统契约](../契约/属性系统契约.md)和[伤害系统设计](../架构/系统/伤害系统设计.md)。

### 2.12 生命、治疗、护盾与受伤协调
- 生命：角色当前生命由 `CharacterHealthStore` / `HealthRuntime` 拥有，只接受角色主体；最大生命来自 `stat.hp.max`；有效变化发布事件，满血恢复、零伤害和完全阻止的扣血不发布。
- 治疗：理论结算与生命提交分层，`HEALING_RESOLVED` 先于提交发布；`HealthRuntime` 是当前生命唯一受控写入口。
- 护盾：`ShieldStore` 以完整 `ShieldRecord` 聚合拥有；创建帧快照公式属性，动态护盾强效在承伤帧查询；多盾基于同一承伤前快照扣减，穿透取单盾可保护来伤量的最大值。
- 受伤协调：`CharacterDamageTakenCoordinator` 只编排护盾与血量计划，预校验后无回调提交；`DAMAGE_APPLIED` 表示正伤害目标是角色（即使被完全吸收），`CHARACTER_HEALTH_CHANGED` 只表示血量实际减少；直接扣血和流血不进入协调器。

详细见各系统设计/契约与[角色受伤协调器设计](../架构/协调/角色受伤协调器设计.md)；护盾剩余工作见[护盾系统后续实现计划](../工程/护盾系统后续实现计划.md)。

### 2.13 系统自治与跨系统协调
- `core/systems/<domain>/` 只拥有本领域状态、公式、计划、写入口和领域事实；领域系统不依赖其他领域的具体 Runtime 或 Store。
- 跨 Store 写入由 `core/coordination/<flow>/` 写协调器统一准备、预校验、无回调提交并按契约发布事实；只读协调器只能组合领域条件和校验证据。
- coordinator 不拥有长期领域状态，不实现领域公式，也不充当全局万能 pipeline；EventEngine 只发布和记录已提交事实。

正式决策见[系统自治与跨系统协调规范](../工程/系统自治与跨系统协调规范.md)。

### 2.14 状态效果（Buff）系统架构
- `core/systems/buff/` 直接拥有有限时长 Buff/Debuff/状态标记的定义、完整记录、Store、应用策略、生命周期与领域事实；第一版支持 replace、refresh、stack refresh 和 coexist。
- 属性 provider 在组装阶段固定注册，查询无副作用；直接或间接改变 `stat.hp.max` 的 Buff 在第一版组装阶段拒绝。
- 事件触发、周期 tick、动态场上角色作用域等按真实内容单独升级契约，不进入万能 callback 框架。
- 第一版工程闭环已落地；真实 Buff golden case 因缺少可信资料仍待补充，测试 content 不代表真实机制完成。

详细见[状态效果系统设计](../架构/系统/状态效果系统设计.md)和[状态效果系统契约](../契约/状态效果系统契约.md)。

### 2.15 能量、冷却与能力条件
- 能量：`EnergyRuntime` 是元素能量唯一写入口；微粒/晶球以在途记录调度，同元素/无元素/异元素倍率 `3/2/1`，四人/三人/二人队后台倍率 `0.6/0.7/0.8`；标准爆发扣能入口与只读条件已提供，`cost=0` 的专属资源角色不走普通元素能量。
- 冷却：`core/systems/cooldown/` 拥有充能次数、串行恢复、时长解析与修改命令；真值使用整数帧 `ready_frame`，查询不推进时间；效果自身触发 CD 与附着 ICD 不进入该 Store。
- 条件协调：`CharacterAbilityConditionCoordinator` 是只读协调器，返回逐项领域证据和全部稳定阻塞原因；E 只要求冷却，标准 Q 要求冷却加满能量，私有资源条件委托 content；动作解释器只依赖 `CharacterAbilityConditionPort`。

详细见[元素能量系统设计](../架构/系统/元素能量系统设计.md)、[冷却系统设计](../架构/系统/冷却系统设计.md)和[角色能力条件协调器设计](../架构/协调/角色能力条件协调器设计.md)。

### 2.16 元素附着、ICD 与反应架构
- 真值来源：元素机制以项目维护者确认的资料为真值；AI 查询与第三方实现仅作参考线索。
- Aura：逐来源贡献账本是元素量与贡献归属的唯一真值，`current_amount` 只是投影；标准强度档位（弱/中/强/超强）与衰减已固定；Aura 不进入 `TargetRuntimeState`。
- ICD：只拥有附着冷却的 Definition、Binding 和限时序列；按攻击者、目标、标签、组别四维 Key；结果是精确元素量系数而非布尔，系数 `0` 仍推进游标但阻止施加。
- Reaction：定义、候选、状态、Gate 与资源由 reaction 领域拥有；content 只提供类型化意图和能力证据；复合候选由公共组件拥有，机制目录不得互相调用。
- 协调器：Aura/ICD/Reaction 通过隔离 BatchPlanner 准备、统一校验并无回调提交，原子性止于一个 `ElementalInteractionBatch`；后续工作走强类型工作队列（单 root 最大轮次 `64`），不使用 Event 回调。
- 事实收敛为 `REACTION_OCCURRED`、`REACTION_STATE_CHANGED` 和 `REACTION_RESOURCE_CHANGED` 三类通用事件。

详细见[元素反应架构文档索引](../架构/系统/元素反应/文档索引.md)、[元素反应协调器设计](../架构/协调/元素反应协调器设计.md)和[元素附着、ICD 与反应设计规范](../工程/元素附着、ICD与反应设计规范.md)。

### 2.17 元素反应契约冻结
- 普通反应由本次元素、ICD 后实际元素量和目标 Aura 决定；碎冰额外读取稳定 `strike_type=BLUNT` 证据，来源种类、武器显示类型和布尔“允许反应”开关不参与。
- 反应处理当前 Impact 时只能调整该 Impact 已携带的关联伤害；新增伤害一律成为同帧下一 settlement round 的子 Damage Impact。
- 增幅/剧变：Profile 拆为 `AmplifyingReactionProfile | TransformativeReactionProfile` 强类型联合；超载、超导使用独立稳定 key 与 Gate，effect group 在下一 settlement round 执行。
- 燃烧：普通燃烧火草建立时创建 `2 GU` 燃元素与 `BurningState`；周期火每 `15` 帧造成 `0.25` 倍率火元素剧变伤害，普通火每 `120` 帧施加 `1 GU`，不进入 Aura ICD。
- 激化：原激化按草雷 `1:1` 实际消费创建 `QUICKEN`；超激化/蔓激化不消费激元素，在通用公式的激化附加区结算（`CatalyzeReactionInput`），倍率 `1.15/1.25`，精通公式已固定。
- 绽放：普通绽放/绽放爆炸/超绽放/烈绽放，水与类草 `2:1` 消费；草原核持续 `360` 帧、每队最多五枚，容量淘汰引爆最老核心；`bloom_family` 共享 `30` 帧两次 Gate，三种伤害分类独立。

各反应稳定字段、key 和验收入口见[元素反应契约文档索引](../契约/元素反应/文档索引.md)下的对应设计/契约。

### 2.25 结果存储系统

- 正式名称为“结果存储系统”（Results Store），“结果库”指 `infrastructure/results_sqlite/` 的 SQLite 实现；“持久化”不作为正式术语。
- 结果数据服务于分析与可视化，第一职责是还原模拟的整个过程；还原依靠存储的事实（事件流 + 初始快照），不依靠重跑。复现不等于历史保真，用当前引擎重跑旧输入得到的是新结果；重跑只能作为验证手段或显式“重新计算”动作（生成新运行记录）。
- 数据分层：真值层（运行记录、输入快照、事件流、初始快照）成功后不可变；派生层（分析摘要、时间序列、任意帧状态、跨运行对比）由分析模板执行器读取侧计算；跳变表等物化产物按性能需要建立且可重建。
- 事件契约：`EventType.name` 冻结（只追加、不改名、不复用）；payload 只增字段不改语义，破坏性变更走新事件类型；状态变化事件必须携带 `before/after` 或稳定引用证据；事件持久化不存 `source_type` 与分类元信息。
- 高频状态数据（HP/能量等）不按帧存数值：初始快照为基线，事件为变化证据，查询时折叠还原；跳变表（jump track）为可选物化。
- 事件流第一版存结果库 SQLite 表；文件化归档预留（单次运行超限、库总体积超限、批量/长仿真模式三种触发），阈值参数化待实测，第一版不实现。
- schema 版本：结果库结构版本（库级）与输入 schema 版本（运行级）语义分离；开发阶段版本不兼容时显式重建，正式版后再设计逐级迁移。
- 失败/取消运行在结果库留最小记录（`session_id`、状态、时间、输入快照、错误摘要），不保存事件流与元摘要；任务状态归任务系统，`job_id ↔ session_id` 单向关联，结果库不存 `job_id`。
- 模拟输入源文件归工作区，扫描 `<data_dir>/inputs/` 发现、`input_key` 定身份；项目配置为 `config.toml`（TOML + 注释，`tomlkit` 写入），第一批配置项 `schema_version` 与 `workspace.data_dir`；资产库位置独立，不随 `data_dir` 搬迁。

详细见[结果存储系统设计](../架构/结果存储系统设计.md)、[结果库契约](../契约/结果库契约.md)与[结果存储系统规范](../工程/结果存储系统规范.md)。

### 2.27 UI 技术选型与入口

探索结论（2026-08-16/17）：

- Flet 原生控件方案不通过：画布高频视口更新需要逐帧回传 Python 并 diff 控件树，60 节点约 791 个控件时 Python 侧 diff 约 29.3 ms，已接近或超过 60 FPS 单帧预算；10/30/60 节点基准分别约 16.8/23.5/29.3 ms。
- node_flow + Flet User Extension 方案技术上可满足性能路径，但需要维护 Flutter/Dart 双技术栈，与项目重点不符，未入选。
- PySide6/Qt 与 QML 方向于 2026-08-17 讨论后未采纳：无成熟 QML 画布库，QtWidgets 现成方案视觉与自绘成本高；如需重新评估须人工批准。

正式选型（2026-08-17 确认）：

- UI 采用 Python 后端 + Web 前端：前端为 React + React Flow 纯客户端，Node 仅存在于开发/构建期；桌面壳使用 pywebview 或自动打开浏览器，运行时为 Python。
- 桌面是主产品；网页服务是同代码的可选部署方式（同一前端构建产物 + 同一 HTTP API），不做多用户账号体系。
- 单工作区：应用管理默认数据目录（如 `%APPDATA%/GenshinSimLab`），内部沿用现有项目布局；支持数据导出迁移；不支持多工作区。
- 网页服务为自托管、小范围使用；公网暴露时使用可选访问令牌，无账号体系。
- 仓库结构调整为 `backend/`（Python）+ `frontend/`（Web）；`prototypes/` 为临时本地原型，计划删除。
- 任务执行：单 worker 单进程，状态轮询；成员小并行，默认 `min(4, CPU)`；结果库写入需要超时与重试；取消语义为排队立即取消、运行中跑完标记取消。
- 枚举/区间节点进入 MVP；区间序列“下一步 ≤ 终点即包含”并使用 Decimal 计算；成员上限 200，超限报错并预览；不同路径组输出叉乘、同路径覆盖并警告。
- API 边界：工作区信息、工作流存档 CRUD（不透明 JSON，不校验图）、已展开成员的输入校验与批次提交/状态/整批取消、结果查询、资产只读搜索；分析区域接口、账号、上传、资产构建更新后置。HTTP 服务端与 CLI 同属入口层，均只通过 `application/` 公开能力调用内部模块。工作流图语义归属见 2.28；端点与字段见 [UI API 契约](../契约/ui/UI API 契约.md)。
- API 采用同源托管、统一错误模型 `{code, message, details?}`；`server/` 负责 HTTP DTO，pydantic 仅用于 server 层 DTO，结合 OpenAPI 生成 TypeScript 类型。
- 桌面安装包（PyInstaller + pywebview）后置；MVP 先保证 server 本地启动与网页服务两种模式（启动入口见下）。
- 资产库初始化从用户提供的 manifests 构建；桌面安装包内置 manifests，首次启动自动构建。

启动入口与 CLI 边界（2026-08-19 确认）：

- CLI 是纯命令行入口，不启动 HTTP 服务；Web 服务由 `server/` 入口启动（见下）。
- Web 服务由 `server/` 入口直接启动（`genshin-sim-server` 或 `python -m genshin_sim.server.main`），负责 HTTP API 与前端静态托管。
- 桌面形态（pywebview 或自动打开浏览器）后置，作为独立启动层，不经过 CLI。

详细方案见 [模块边界设计](../架构/模块边界设计.md)、[画布设计](../架构/UI/画布设计.md)、[UI API 契约](../契约/ui/UI API 契约.md) 与 [前端工程规范](../工程/前端工程规范.md)。

### 2.28 工作流图语义与运行模型

图语义归属前端（2026-08-17 确认）：

- 工作流是 UI 产品面。CLI 不提供工作流的创建、校验或运行；CLI 只处理 `SimulationInput` 文件（`genshin-sim run` / `input validate`）。
- 后端不实现完整工作流引擎。不设 `application/workflow/` 图校验或运行时；不提供节点类型注册表 API，也不按工作流定义编译成员。
- 前端拥有图：区域、节点、连线、语义注册表、`WorkflowValidator`、片段合并、枚举/区间展开、覆盖警告与成员预览。
- 后端只认已展开成员：校验每份 `SimulationInput`、按批投递现有 job、跟踪成员状态、整批取消、读写结果。
- 工作流 JSON 是画布存档。`<data_dir>/workflows/` 由后端做不透明文件存取（列表/读取/保存/删除），服务端不解析图语义。
- `POST /runs` 接受有序成员列表 `(item_id, SimulationInput)`，不接受工作流 ID 或内联图定义。批次轮询合并进 `GET /runs/{run_id}`。配置区域预览使用 `POST /inputs/validate`，不跑仿真。
- `application/batch/` 只编排已展开成员的批次任务，不做变体编译。

模拟节点术语（2026-08-22 确认）：

- kind 为 `simulation` 的跨区域执行节点统一称「模拟节点」；文档、注册表 displayName 与 UI 文案一致。
- 注册表 `NodeKindSpec.region` 使用 `RegionKind | null`，`null` 表示画布级节点（不归属任何区域）。
- 跨区域连线规则表述为「配置区域边界输出 → 模拟节点 → 分析区域边界输入」；不引入新的类别层，后续跨区域节点如出现再评估。
- 前端诊断码使用 `CANVAS_NODE_REGION_INVALID`；该值不落盘（工作流 JSON 中画布级节点 `region_id` 为 `null`），无存档迁移。

运行语义（2026-08-22、2026-08-23 确认）：

- 一个模拟节点 = 一个批次。「全部运行」遍历画布上的模拟节点，每个节点按输入连线收集所连配置区域边界输出的成员，各自提交一个批次；多个区域连同一节点时按连线顺序合并成一批；一个区域连多个节点时数据复制、各自成批。
- 模拟执行唯一路径：配置区域边界输出 → 模拟节点，不存在绕过模拟节点的模拟提交；区域级入口只做校验，不执行模拟（见「区域校验与区域运行」）。
- 未连接模拟节点的配置区域：警告并跳过，不参与任何批次；错误只挂在「批次无法成立」（所连节点收集成员为 0 或超过上限 200）。空区域 `EMPTY_REGION` 的报错语义随之收窄为「所连批次无法成立」。
- 「全部运行」按画布顺序依次串行执行各节点的批次：前一批到终态才提交下一批；某批失败不中断后续批次；取消停止当前批次并跳过剩余未提交批次。
- 批次命名与并发度归属节点：批次名取该节点所连第一个区域的元信息名称；并发度为模拟节点参数 `concurrency`（整数 1–16，缺省「自动」，不传走后端 `min(4, CPU)`）。
- 「运行」是分阶段的执行过程：构建 → 模拟 → 终态；指标展示后置到分析区域（见 2.29）。
  - 构建阶段（前端）：编译所有参与运行的配置区域（变体展开、片段合并、覆盖警告）并执行前端图校验；任何错误则本次运行终止于构建阶段，不提交任何批次；警告（覆盖、未连接区域）不阻断。
  - 校验职责分层：前端管图校验与编译，后端只校验 `SimulationInput`。后端输入校验（资产存在性、handler 可运行性）不进构建阶段，由各批次提交时 `POST /runs` 的内部校验承担；失败批次标失败、不中断后续批次。
  - 模拟阶段（后端批次）：一个模拟节点一个批次、按画布顺序依次串行、某批失败不中断后续、取消停止当前批并跳过剩余。
- 运行生命周期：构建中 → 模拟中 → 完成 / 失败（构建）/ 已取消；运行期间的全局编辑锁覆盖全程。
- 重跑模式：全部重跑 = 构建 → 模拟；仅分析重跑后置（入口随分析能力落地后由区域/分析入口承担）。

执行轨迹（2026-08-22 确认）：

- 运行过程以「执行轨迹」表达：一次运行 = 有序步骤序列，每步引用画布对象，承载状态与诊断，支持逐步查看。
- 配置区域构建是逐方法过程：节点 = 方法（合并输入、应用自身片段、分发输出），按「根节点 → … → 区域边界输出」的拓扑序逐节点应用。构建阶段轨迹按此展开：每个参与节点一个「方法应用」步骤（片段路径、变体数、是否被覆盖），区域以「边界收拢」步骤收尾（成员集与校验状态）。共享子图只应用一次，轨迹中每节点出现一次。
- 模拟阶段：每个模拟节点一个「批次」步骤（`run_id`、成员状态、终态），按运行语义串行推进。
- 画布表现由轨迹驱动：节点与区域按步骤状态着色（等待、运行中、成功、失败、结果过期），运行中对象的连线高亮，未参与本次运行的对象（游离草稿、未连接区域）置灰，执行路径一眼可辨。
- 编译采用声明式整图编译；轨迹忠实记录真实应用顺序。
- 构建阶段按方法轨迹逐节点限速推进：每个方法步骤保留最小执行时长（150ms），步骤状态（等待/应用中/已应用/跳过）随运行真实推进；取消时剩余步骤立即标记跳过。设置弹窗提供「运行动画」开关（默认启用，关闭后步骤状态瞬间完成、不等待）。

RunState 结构与运行链路（2026-08-22、2026-08-23 确认）：

- RunState 不持久化，单块 `run`（当前/最近一次工作流运行）；区域校验结果由问题面板呈现（见「区域校验与区域运行」）。
- `run` 按执行轨迹骨架实现：`phase`（building/simulating/completed/build_failed/cancelled）、`build`（参与区域的构建切片：方法轨迹 + 成员数）、`batches`（按模拟节点 id 索引的批次视图：步骤状态、后端 run_id 与批次状态（含校验中/校验通过）、成员状态、错误）；批次视图不含指标字段（指标读取见 2.29）。
- 运行链路：`workflow/runner.ts` 负责构建阶段规划（一节点一批次、多区域按连线顺序合并、item_id 重复与成员上限为构建错误、未连接区域跳过）；`App` 负责串行编排（构建失败零提交；某批失败不中断后续；取消停止当前批并跳过剩余）。
- 画布表现：运行进行中执行路径外的节点置灰；模拟节点编辑器只展示本节点批次视图（含并发度参数）；运行/检查期间删除与撤销等破坏性交互锁定。
- 构建限速推进已落地：构建方法步骤带状态与节点显示名，轨迹面板逐行展示，画布高亮当前应用中的节点；「运行动画」设置持久化到后端项目配置（config.toml 的 `ui` 节，经 `GET/PUT /api/v1/settings` 读写），设置弹窗随之实现（「运行」分组，外观分组后置）。

区域校验与区域运行（2026-08-23 确认）：

- 校验分两级：
  - 节点校验：只考虑节点自身。参数与路径合法性为前端实时编译诊断；资产存在性在工作流加载/切换时对图中全部资产引用做一次批量后端预检，失效引用以 `ASSET_NOT_FOUND` 诊断显示在节点与问题面板；编辑时不做逐次后端校验（资产选择器入口已保证选取时资产存在）。槽位冲突、成员上限、区域—模拟连线、图结构等跨节点检查不进入编辑期实时诊断，由区域校验/运行的构建阶段执行。跨节点检查的参与范围按连线判定：槽位冲突、多根节点等基于区域内节点聚合的检查只统计已连入区域数据链（边界汇入边上游）的节点；未接线草稿不参与编译，也不参与此类判定。id 重复、节点归属等身份/放置类检查对全量对象生效。预检只是提前暴露，运行时的区域校验是权威闸门；全部运行按全量节点诊断阻断，区域运行只被目标区域内节点、连线及所连模拟节点的错误诊断阻断，其他区域节点错误不阻断区域运行。
  - 区域校验：跨节点统一校验——合并路径、冲突检测、变体展开成成员后，对成员做配置结构与资产/handler/组装 dry-run 校验（即 `POST /inputs/validate` 的能力）。区域校验是区域运行/全部运行流程中的阶段，也是「区域校验」入口的完整内容。
- 区域运行 = 全部运行的区域子集，复用同一编排：构建限速动画（仅该区域切片）→ 批次区域校验 → 提交 → 轮询 → 终态与结果面板联动；画布置灰/高亮、两级取消交互自然继承。
- 「区域校验」入口 = 区域运行的子集：复用同一份区域计划与构建限速动画，逐批执行 `POST /inputs/validate` 后终止于「校验完成」终态（批次通过状态「校验通过」），不提交批次、不创建结果；校验失败仍为批次级「失败」并附成员级聚合错误；取消语义与运行一致（「跳过」）。该入口只呈现校验流程，不改变运行阶段模型。
- 失败呈现：区域校验/构建阶段的诊断（含槽位冲突等跨节点错误与成员级校验诊断）统一进入问题面板并自动打开；顶部横幅只保留保存、网络等操作类错误。运行中若存在区域校验失败，运行结束不自动切换到结果面板，保留问题面板。
- 批次步骤增加「校验中」：每个批次提交前先做其来源区域的区域校验；校验失败该批标记「失败」并附成员级聚合错误，「跳过」专指取消语义；全部运行中某区域校验失败不影响其余批次照跑。

详细方案见[画布设计](../架构/UI/画布设计.md)、[工作流定义契约](../契约/ui/工作流定义契约.md)、[批量配置变体契约](../契约/ui/批量配置变体契约.md)、[节点与区域契约](../契约/ui/节点与区域契约.md)、[UI API 契约](../契约/ui/UI API 契约.md)与 [前端工程规范](../工程/前端工程规范.md)。

### 2.29 结果面板与批次监控

- 结果面板定位为「结果库历史浏览器」：左侧工具面板（与「节点」「问题」互斥开合），只读 `GET /results`。列表视图：批次名、状态、相对时间、帧数/事件数，状态筛选、分页与手动刷新；详情视图：状态、结束原因、时长（帧 ÷ 60）、事件数、起止时间、`session_id`（可复制）与失败/取消错误信息。面板任何视图不展示指标数值。
- 过程信息全部由画布承担：阶段与构建步骤经节点高亮/置灰呈现，批次与成员进度在模拟节点卡片内；构建失败（零提交）错误经顶部错误横幅呈现。
- 指标数值展示后置到分析区域落地时实现，成员行与结果面板详情均不展示指标数值；结果面板为纯记录浏览器。
- 模拟节点定位为「模拟入口 + 批次监控」：节点不提供命名，批次身份沿用区域 `meta.name`；批次监控为聚合呈现——状态徽章 + 计数行（如「完成 12/30 · 失败 1 · 已取消 2」）+ 分段进度条（按成员状态着色：完成/失败/已取消/运行中/停止中/排队）；批次状态行只呈现徽章与计数，不重复展示后端原始 state 文本。
- 失败成员展示可见错误行（item_id + 错误文本，直接呈现于面板）：组装阶段失败不落结果库（executor 只记日志），且批次成员视图不携带失败成员的 session_id，节点错误行是这类失败信息的唯一 UI 出口。
- 取消交互分两级：
  - 节点内「取消本批」：仅取消当前正在执行的批次（对当前 `run_id` 调用后端取消），该批终态后后续批次照常继续；后端取消语义为排队成员立即取消、运行中成员跑完当前仿真后作废，不支持帧级中断。
  - 顶栏运行按钮在运行期间变为取消入口，双击触发整次取消（取消当前批并跳过剩余批次）。
  - 被取消的批次标记「已取消」，与整次取消中被跳过的批次（「跳过」）区分。
- 运行结束自动打开结果面板、刷新列表并定位最新记录。
- 历史结果不带变体身份（结果库 API 不暴露输入快照）；「结果详情暴露输入摘要/成员标签」作为后置能力登记到 [UI API 契约](../契约/ui/UI API 契约.md) 后置清单。
- 「仿真结果摘要的展示位置」定案：历史记录面板（记录浏览器）+ 批次监控（进度条聚合），指标数值出口后置到分析区域。

详细见 [前端工程规范](../工程/前端工程规范.md) 与 [UI API 契约](../契约/ui/UI API 契约.md)。

### 2.30 分析能力重做：模板下沉（2026-08-25）

- 分析能力按「数据 = 结果库内容、处理 = SQL 模板」重做：删除顶层 `analysis/` 模块及其 processors（状态还原、路径寻址、序列、指标、对比）。
- 模板注册表（声明 + SQL + 可选 Python 行变换）落在 `infrastructure/results_sqlite/templates.py`，与结果库 schema 同处；契约模型与用例在 `application/`（`AnalysisTemplatesService`），HTTP 端点在 `server/`（`/api/v1/analysis/templates` 与 execute）。
- 前端不传 SQL：只提交「模板 id + 参数绑定 + 关系表」；参数走 prepared statement，关系输入由执行器拼装为连接级临时表。
- 展开参数 v1 只有 `union` 模式，每次模板执行返回一张表；`per_value`（组输出）不进 v1。
- 模板声明与 SQL 一起放 infrastructure，避免声明/实现两处漂移。

### 2.32 分析算子化重做：取数节点与关系算子族（2026-08-25）

- （2026-08-26 修订）两个取数节点合并为单个 `fetch`（`source: runs | events`）：显示名「获取数据」，卡内来源切换「运行记录 / 事件记录」；存量 `fetch_runs` / `fetch_events` 定义加载时自动迁移，连线与输出结构不变。「运行取数 / 事件取数」术语退役。
- （2026-08-26 补充）分析区域新增「运行分析」入口，运行分三阶段：获取输入（边界连接的模拟节点 `last_sessions` 缺失或为空时自动补跑其批次并写回，数据提供节点直接取数，多源保序合并）→ 数据处理（区域级查询计划一次执行）→ 视图加载；任一补跑批次失败或取消即整次中止；补跑复用现有批次运行编排（构建动画、进度、取消与全局编辑锁）。

### 2.33 表格视图尺寸自适应（2026-08-27）

- 表格视图节点尺寸语义定稿：**高度始终手动**（画布几何，默认 360px、夹持 240–720px，随工作流保存），不做内容自适应；行多时表格区内部滚动 + 窗口化渲染，避免数据过多撑破界面。
- **宽度双模式**（`table_config` 参数 `width_mode`）：`auto` 宽度 = min(内容自然宽, 内部软上限 960px)，内容超出软上限时右侧列裁剪隐藏，不出现横向滚动条；裁剪时表格右缘渐隐 + 悬停提示，右缘出现缩放手柄，拖宽自动切到 `fixed` 并一次原子提交「节点尺寸 + `width_mode: fixed`」。
- 内容自然宽按表头与单元格格式化文本估算，单列夹持 72–240px；固定模式可拖范围 [560, 内容自然宽]，硬上限随数据动态变化（隐藏列越多越大），数据缩小后自动夹回。
- （2026-08-27 修订）**软上限是内部常量（960px），不进入配置参数、不对用户开放**：`width_mode` 是用户可感知的行为选择，随 `table_config` 参数保存；高度不进入配置节点参数。
- 视图节点画布几何新增可选 `size`（`WorkflowNode.size`），与 `position` 同类随工作流保存；存量定义缺省按默认语义处理，无迁移。
- 尺寸语义常量与解析统一由 `frontend/src/workflow/view_size.ts` 持有，表格为首个使用者，其余视图沿用同一套节点卡与状态原则。
- （2026-08-27 修订）视图显示名由「成员指标表」调整为「**表格**」：表格视图消费通用结果行表，名称不应特指“成员/指标”；内部 kind 保持 `member_table`，端口语言与存档结构不变，存量工作流无需迁移。

### 2.46 视图尺寸统一与图表视图自适应（2026-09-01）

- 统一视图节点尺寸语义：悬停/选中时宽度与高度手柄常驻为视图基础能力，是否内容驱动由各视图声明；节点宽高为持久化画布几何，按轴分别保存（拖高不覆盖宽度，反之亦然）。
