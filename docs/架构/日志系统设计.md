# 日志系统设计

> 状态：第一版已实现，后续演进中。
> 本文档定义项目工程日志的定位、边界、默认策略和第一版实现方向。

最后更新：2026-07-06

## 1. 定位

日志系统用于记录项目运行过程中的工程诊断信息。

它负责：

- 记录 CLI、UI、应用服务和基础设施的运行边界。
- 记录失败原因、异常栈和关键诊断上下文。
- 辅助开发、测试、用户反馈和本地问题排查。
- 为未来桌面 UI 提供可导出的本地诊断日志。

它不负责：

- 保存仿真事件流。
- 替代快照、结果库或分析数据。
- 作为机制逻辑的驱动来源。
- 作为配置契约、资产契约或结果契约的一部分。
- 在导入模块时自动修改全局日志配置。

仿真过程中“发生了什么”由 `core/events/` 的结构化事件表达；工程日志只表达“系统如何运行、哪里失败、如何诊断”。

## 2. 边界原则

- `infrastructure/logging/` 负责日志配置、handler、formatter、输出路径和轮转策略。
- `cli/` 和 `ui/` 作为入口负责调用日志初始化。
- `application/`、`assets/`、`content/`、`analysis/`、`core/` 使用标准库 `logging.getLogger(__name__)` 获取 logger。
- 非基础设施模块不依赖 `genshin_sim.infrastructure.logging`。
- `core/` 不把工程日志当作仿真记录通道；仿真事实、输入事实、动作事实和结算事实仍通过事件系统、快照和结果模型表达。
- 日志配置不写入 `SimulationConfig`，也不影响仿真结果的可复现性。

## 3. 与事件、快照和结果库的区别

| 类型 | 所属模块 | 主要用途 | 是否作为仿真数据 |
| --- | --- | --- | --- |
| 工程日志 | `infrastructure/logging` 配置，各模块使用标准 logger | 诊断、排错、运行观测 | 否 |
| 事件流 | `core/events` | 表达仿真过程中的结构化事实和拦截点 | 是 |
| 快照 | `core/snapshots` | 导出运行时状态与当前帧事件 | 是 |
| 结果库 | `infrastructure/results_sqlite` | 持久化完整仿真结果、事件和投影数据 | 是 |

日志文件可以记录某次仿真开始、结束、失败、保存到哪个 `session_id`，但不记录完整事件流、完整配置快照或逐帧状态。

## 4. 第一版模块结构

建议结构：

```text
infrastructure/logging/
├── __init__.py
├── settings.py
├── setup.py
└── context.py
```

职责：

- `settings.py`：定义 `LoggingSettings`，保存日志级别、是否启用控制台、文件路径、轮转参数等。
- `setup.py`：提供 `configure_logging(settings)`，配置项目包 logger 和 handler。
- `context.py`：提供可选的上下文字段支持，例如 `command`、`operation_id`、`session_id`。
- `__init__.py`：导出入口 API，不在导入时自动配置日志。

第一版不引入第三方日志库，优先使用 Python 标准库 `logging`。

## 5. Logger 使用规则

各模块使用模块级 logger：

```python
import logging

logger = logging.getLogger(__name__)
```

使用原则：

- 正常用户输出仍由 CLI/UI 控制，不用日志替代命令结果展示。
- 应用服务记录用例边界，例如配置校验、组装开始、仿真开始、仿真结束、结果保存。
- 基础设施记录外部技术操作，例如数据库初始化、SQLite 写入失败、文件路径不可用。
- `content/` 可以记录 handler 注册、缺失或冲突等诊断信息。
- `analysis/` 可以记录分析任务开始、输入结果数量、聚合失败等诊断信息。
- `core/` 默认少打日志；需要时只记录异常诊断或极少量调试信息。

不建议：

- 在循环帧、事件发布或高频数值计算中默认写日志。
- 在日志中保存完整 `SimulationConfig`、完整事件 payload 或大型快照。
- 在库代码中调用 `logging.basicConfig()`。
- 在模块导入阶段写日志或创建文件 handler。

## 6. 日志级别

| 级别 | 使用场景 |
| --- | --- |
| `DEBUG` | 开发诊断、详细组装过程、调试用路径与计数。 |
| `INFO` | 重要运行边界，例如命令开始、数据库初始化、仿真完成、结果保存。 |
| `WARNING` | 可恢复但需要注意的问题，例如可选配置缺失、旧版本兼容路径、清理失败。 |
| `ERROR` | 当前命令或用例失败，但进程仍可返回可控错误码。 |
| `CRITICAL` | 进程级不可恢复故障。第一版很少使用。 |

仿真机制中的拒绝、命中、伤害、输入消费等事实不因“重要”而进入工程日志；这些内容应进入事件系统或结果数据。

## 7. 输出策略

第一版支持两类输出：

- 控制台：面向开发者和 CLI 调试，默认写入 `stderr`。
- 文件：面向 UI 反馈和本地排错，使用轮转文件。

推荐默认：

- CLI 普通模式：控制台只输出 `WARNING` 及以上；命令结果仍使用 `stdout`。
- CLI 调试模式：控制台输出 `DEBUG` 及以上，并在顶层异常处记录异常栈。
- CLI 文件日志：通过参数或环境变量显式启用，避免普通命令产生额外文件。
- UI 模式：应用启动时默认启用文件日志，路径由 UI 启动配置决定。
- 测试：不在包导入时自动配置日志，测试使用 `caplog` 或临时 handler 验证。

文件日志第一版使用 `RotatingFileHandler`，默认轮转参数可以从较小值开始，例如单文件 5 MB、保留 5 个备份。具体路径不写入 `SimulationConfig`。

## 8. 上下文字段

日志上下文字段用于串联一次命令、一次应用操作或一次仿真。

第一版建议字段：

| 字段 | 含义 |
| --- | --- |
| `command` | CLI 命令或 UI 操作入口。 |
| `operation_id` | 一次入口操作的临时追踪 ID。 |
| `session_id` | 结果库保存后的仿真会话 ID。 |
| `config_name` | `SimulationConfig.meta.name`，仅作辅助诊断。 |
| `asset_db` | 当前资产库路径。 |
| `result_db` | 当前结果库路径。 |

实现上可以使用 `contextvars` 保存入口上下文，并通过 formatter/filter 为缺失字段提供默认值，避免普通 logger 调用必须重复传入所有字段。

敏感或高体积内容默认不进入日志：

- 完整配置 JSON。
- 完整事件列表。
- 完整快照。
- 大型 SQLite 查询结果。

如确需诊断，可在 `DEBUG` 级别记录摘要、计数或截断内容。

## 9. 异常记录策略

- 入口层负责记录未处理异常，例如 CLI `main()` 或 UI 应用启动边界。
- 应用服务可以在用例边界记录失败摘要，但不重复记录完整异常栈。
- 需要保留异常栈时使用 `logger.exception()`，并继续让异常按既有错误模型传播。
- `EventEngine` 不捕获 handler 异常，保持事件系统当前失败语义。
- 日志不改变错误暴露层级；缺资产、缺 handler、JSON 格式错误仍应在组装或校验阶段抛出明确异常。

目标是“一次失败有一个清晰异常栈”，避免每层都重复打印同一栈。

## 10. 第一版实现范围

第一版已经覆盖：

1. 在 `infrastructure/logging/` 实现 `LoggingSettings`、`configure_logging()` 和上下文 filter。
2. 给 CLI 增加全局日志参数，例如 `--log-level`、`--debug`、`--log-file`。
3. 支持 `GENSHIN_SIM_LOG_LEVEL` 与 `GENSHIN_SIM_LOG_FILE` 环境变量。
4. 在 CLI 顶层初始化日志，并在调试模式下记录未处理异常栈。
5. 在 `application/services` 的关键用例边界增加少量日志。
6. 为日志配置补充单元测试，覆盖上下文字段、文件日志和 handler 去重。

后续 UI 启动方案确定后，再补 UI 文件日志路径和导出诊断日志能力。

## 11. 验收标准

第一版完成后应满足：

- 不新增第三方依赖。
- 导入 `genshin_sim` 不会自动创建日志文件或修改 root logger。
- CLI 正常输出不被日志污染。
- `--debug` 或等价配置可以看到异常栈和关键诊断信息。
- 日志实现不破坏既有模块依赖方向。
- 仿真事件、快照和结果库职责不被日志替代。
- 测试能覆盖日志初始化、上下文字段默认值和 handler 去重。

## 12. 当前实现评估

第一版日志系统整体判断是轻量、稳定且边界清楚，适合作为当前重建阶段的基础设施。

当前优点：

- 不新增第三方依赖，继续使用 Python 标准库 `logging`。
- `infrastructure/logging/` 只负责日志配置，不要求 `application/`、`core/` 反向依赖它。
- CLI 正常命令输出和日志输出分离，命令结果继续走 `stdout`，日志走 `stderr` 或文件。
- `configure_logging()` 可以重复调用，并会移除自身创建的旧 handler，避免测试或多次初始化时重复输出。
- `contextvars` 比普通全局变量更适合保存临时日志上下文，后续异步任务中也更容易扩展。
- 工程日志与仿真事件、快照、结果库保持分离，没有把日志变成第二套仿真记录系统。

当前局限：

- 默认日志格式较长，很多场景下 `session_id`、`config_name` 等字段可能为空。
- 当前仍是文本日志，不是真正的结构化日志；未写入 formatter 的 `extra` 字段默认不会显示。
- CLI 日志参数是顶层参数，通常需要写在子命令前，例如 `genshin-sim --debug config validate xxx.json`。
- 文件日志路径策略尚未覆盖 UI 场景，未来需要结合桌面应用的数据目录设计。
- 普通模式下只输出错误摘要，完整异常栈主要在 `--debug` 模式下记录。
- 代码中的日志消息语言需要继续统一，若项目要求所有可见文本使用中文，应同步调整日志消息。

## 13. 后续演进方向

后续可按以下顺序调整：

1. 统一日志消息语言，优先把新增日志消息改为中文。
2. 区分控制台格式和文件格式：控制台保持简洁，文件保留更多上下文字段。
3. 调整异常记录策略：文件日志可以保留异常栈，控制台普通模式只显示摘要。
4. 改进 CLI 参数体验，让日志参数可在子命令前后更自然地使用。
5. UI 方案确定后，补充默认日志目录、日志清理策略和“导出诊断日志”能力。
6. 批量任务或并发运行出现后，再评估是否需要 `QueueHandler`、任务级日志文件或结构化 JSON 日志。

需要重点关注的问题：

- 高频仿真路径不能默认写日志，尤其是帧循环、事件发布、伤害计算和属性计算。
- `RotatingFileHandler` 适合单进程场景，多进程批量任务可能出现轮转竞争或写入交错。
- 日志中不应保存完整 `SimulationConfig`、完整事件列表或大型快照，避免体积膨胀和诊断信息过载。
- 如果未来需要自动分析日志，文本格式可能不够，应考虑文件日志支持 JSON Lines。
- 日志上下文字段应保持少而稳定，避免演变成另一套业务数据模型。
