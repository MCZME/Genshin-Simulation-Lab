# 事件类型

> 状态：目标事件语义已定案；`DAMAGE_APPLIED` 分类、payload 和零伤害发布条件待随角色受伤协调器迁移。
> 本文档记录当前已经确认的 `EventType`、默认记录规则和载荷类型。事件系统整体设计见：[系统设计](./系统设计.md)。

最后更新：2026-07-14

## 1. 范围

当前事件类型覆盖已经确认的模拟器生命周期、输入事实、输入会话边界、伤害结算事实、治疗结算事实、角色生命值状态变化、护盾授予/吸收/应用闭环、状态效果第一版创建/刷新/叠层/替换/离场事实，以及元素能量载体和直接能量变化事实。

`HEALING_RESOLVED` 已随治疗系统当前契约实现；护盾新增事件已随护盾核心运行时实现；`BUFF_APPLIED` 与 `BUFF_REMOVED` 已随状态效果第一版工程闭环实现。元素与 Reaction 事件已经完成设计但尚未实现；队伍切换事件仍等待对应模块评审。

## 2. 事件类型

| 事件类型 | 分类 | 默认记录 | 含义 |
| --- | --- | --- | --- |
| `SIMULATION_STARTED` | `BOUNDARY` | 是 | 一次仿真开始运行。 |
| `SIMULATION_ENDED` | `BOUNDARY` | 是 | 一次仿真结束。 |
| `FRAME_STARTED` | `BOUNDARY` | 否 | 进入某一帧。 |
| `FRAME_ENDED` | `BOUNDARY` | 否 | 某一帧处理完成。 |
| `INPUT_KEY_RECEIVED` | `INTENT` | 是 | 某个配置输入事实在当前帧进入运行时处理。 |
| `INPUT_SESSION_BOUNDARY_REACHED` | `INTENT` | 是 | 某个输入会话边界被 `ActionManager` 处理。 |
| `DAMAGE_RESOLVED` | `FACT` | 是 | 一次伤害数值已经完成结算，但尚不表示目标生命已经扣减。 |
| `HEALING_RESOLVED` | `FACT` | 是 | 一次理论治疗量已经完成结算，但尚不表示目标生命已经增加。 |
| `CHARACTER_HEALTH_CHANGED` | `STATE_CHANGE` | 是 | 角色当前生命已经发生有效变化。 |
| `CHARACTER_MAX_HP_CHANGED` | `AUDIT` | 否 | 角色最大生命同步导致当前生命按比例调整；不属于普通生命变化。 |
| `SHIELD_GRANTED` | `STATE_CHANGE` | 是 | 护盾实例已经创建、替换、刷新、叠加或保留。 |
| `SHIELD_CAPACITY_CHANGED` | `STATE_CHANGE` | 是 | 护盾原生剩余量已经因吸收、刷新或叠加发生变化。 |
| `SHIELD_REMOVED` | `STATE_CHANGE` | 是 | 护盾因耗尽、过期、替换或显式原因离开活动状态。 |
| `SHIELD_ABSORPTION_RESOLVED` | `FACT` | 是 | 一次正伤害的并行护盾吸收已经完成。 |
| `DAMAGE_APPLIED` | `FACT` | 是 | 一份正伤害已经以角色为目标完成护盾与血量提交。 |
| `BUFF_APPLIED` | `STATE_CHANGE` | 是 | Buff 实例已经创建、替换、刷新、叠层或到顶刷新。 |
| `BUFF_REMOVED` | `STATE_CHANGE` | 是 | Buff 实例因过期、替换、驱散、消费或显式原因离开活动状态。 |
| `ENERGY_PICKUP_SPAWNED` | `STATE_CHANGE` | 是 | 元素微粒或晶球已经进入在途队列。 |
| `ENERGY_PICKUP_SETTLED` | `FACT` | 是 | 一个在途元素能量载体已经向当前队伍完成结算。 |
| `DIRECT_ENERGY_CHANGE_RESOLVED` | `FACT` | 是 | 一次直接恢复、直接扣除或爆发扣能已经提交。 |
| `CHARACTER_ENERGY_CHANGED` | `STATE_CHANGE` | 是 | 角色当前元素能量已经发生有效变化。 |

说明：

- `SIMULATION_STARTED` 和 `SIMULATION_ENDED` 覆盖 `BOUNDARY` 的默认记录规则，默认进入记录。
- `FRAME_STARTED` 和 `FRAME_ENDED` 继承 `BOUNDARY` 默认规则，不默认记录，避免每帧产生大量结果数据。
- 输入事件属于意图事件，只说明输入事实或会话边界进入处理，不说明动作成功或状态变化。
- `INPUT_KEY_RECEIVED` 记录原始按键事实和关联的输入会话 id，不记录派生的 `held_frames`。
- `INPUT_SESSION_BOUNDARY_REACHED` 记录会话边界、解释器 binding 和是否会调用解释器，用于解释 release 为什么可能因 `detached/canceled` 被跳过。
- `DAMAGE_RESOLVED` 保存不可变 `DamageResult`，可以驱动后续机制；生命系统未来使用独立状态变化事件表达伤害已经应用。
- `HEALING_RESOLVED` 保存不可变 `HealingResult`，由 `HealingRequestHandler` 在生命提交前发布；满血和零治疗仍保留该理论结算事实。字段与序列化见[治疗系统契约](../../契约/治疗系统契约.md)。
- `CHARACTER_HEALTH_CHANGED` 保存不可变 `CharacterHealthChangeResult`，只在角色生命真实变化时发布；零伤害、满血恢复和被最低生命限制完全阻止的扣血不发布该事件。
- `CHARACTER_MAX_HP_CHANGED` 只用于最大生命同比变化的审计，不触发普通生命变化机制，也不默认进入结果记录。
- `SHIELD_CAPACITY_CHANGED` 和 `SHIELD_REMOVED` 按稳定 `instance_id` 发布；耗尽时先发布容量变化，再发布移除。
- `SHIELD_ABSORPTION_RESOLVED` 只在正伤害且有活动护盾参与时发布；无盾和零伤害不伪造吸收事实。
- `DAMAGE_APPLIED` 在 `CharacterIncomingDamage.amount > 0` 且目标是角色时发布，并保存 `CharacterDamageTakenRecord`。完全吸收时仍发布，但不会因此产生 `CHARACTER_HEALTH_CHANGED`；零伤害不发布。
- 护盾事件的详细字段、发布条件和序列化见[护盾系统契约](../../契约/护盾系统契约.md)。
- `BUFF_APPLIED` 和 `BUFF_REMOVED` 的详细字段、批量应用顺序和 JSON 序列化见[状态效果系统契约](../../契约/状态效果系统契约.md)。
- `ENERGY_PICKUP_SETTLED` 即使所有角色实际获得量均为 `0` 也会发布；`DIRECT_ENERGY_CHANGE_RESOLVED` 即使实际变化为 `0` 也会发布，以保留溢出和未应用量审计。
- `CHARACTER_ENERGY_CHANGED` 只在 `effective_amount > 0` 时发布；微粒/晶球接收结果由 `ENERGY_PICKUP_SETTLED` 聚合，不再额外发布直接结算事实。
- 能量事实只在状态提交后发布。事件 handler 不得同步写入能量，必须进入下一结算轮次或未来帧。
- 能量事件的 payload 字段、发布顺序和序列化见[元素能量系统契约](../../契约/元素能量系统契约.md)。
- 除 `DAMAGE_APPLIED` 的目标调整外，表中事件已经恢复运行时发布逻辑；当前代码差异见[角色受伤协调器契约](../../契约/角色受伤协调器契约.md)。
- 事件使用结构化 payload，不使用松散 `data` 字典作为核心事件对象的载荷。

## 3. 载荷

| 载荷类型 | 用途 | 字段 |
| --- | --- | --- |
| `EmptyPayload` | 无字段事件。 | 无 |
| `SimulationEndedPayload` | 仿真结束事件。 | `stop_reason`、`end_frame`、`frames_run` |
| `InputKeyReceivedPayload` | 输入按键事实进入运行时处理事件。 | `key`、`phase`、`order`、`session_id` |
| `InputSessionBoundaryPayload` | 输入会话边界进入 `ActionManager` 处理事件。 | `session_id`、`key`、`phase`、`order`、`press_frame`、`held_frames`、`physical_state`、`control_state`、`owner_kind`、`owner_slot`、`interpreter_id`、`binding_scope`、`will_interpret`、`skip_reason` |
| `DamageResolvedPayload` | 伤害数值完成结算的事实事件。 | `result` |
| `HealingResolvedPayload` | 理论治疗量完成结算的事实事件。 | `result` |
| `CharacterHealthChangedPayload` | 角色当前生命变化状态事件。 | `result` |
| `CharacterMaxHpChangedPayload` | 角色最大生命同步审计事件。 | `result` |
| `ShieldGrantedPayload` | 护盾授予状态事件。 | `result` |
| `ShieldCapacityChangedPayload` | 护盾原生容量变化状态事件。 | `result` |
| `ShieldRemovedPayload` | 护盾移除状态事件。 | `result` |
| `ShieldAbsorptionResolvedPayload` | 并行护盾吸收事实事件。 | `result` |
| `DamageAppliedPayload` | 正伤害以角色为目标完成护盾与血量提交。 | `record` |
| `BuffAppliedPayload` | Buff 创建、替换、刷新或叠层状态事件。 | `result` |
| `BuffRemovedPayload` | Buff 离场状态事件。 | `result` |
| `EnergyPickupSpawnedPayload` | 元素微粒或晶球已入队。 | `record` |
| `EnergyPickupSettledPayload` | 元素微粒或晶球已经完成队伍结算。 | `result` |
| `DirectEnergyChangeResolvedPayload` | 直接恢复、直接扣除或爆发扣能已提交。 | `result` |
| `CharacterEnergyChangedPayload` | 角色当前元素能量已有效变化。 | `result` |

## 4. 后续扩展

新增事件类型时必须同步补充：

- `EventType` 成员。
- 对应 payload 类型。
- `EVENT_SPECS` 条目。
- 本文档中的事件表和载荷对应关系。

状态效果后续新增触发型 Buff、周期命令或专用结果投影时，必须先升级[状态效果系统契约](../../契约/状态效果系统契约.md)，再补充新的事件或 payload。

元素领域设计已经预留 `AURA_APPLIED`、`AURA_DEPLETED`、`AURA_INTERACTION_RESOLVED`、`AURA_ICD_RESOLVED`、`REACTION_OCCURRED`、`REACTION_STATE_CHANGED`、`REACTION_RESOURCE_CHANGED` 与 `ELEMENTAL_INTERACTION_RESOLVED`。这些名称只有在对应 Runtime/协调器实现、payload 和 EventSpec 同批落地后才加入上表，不能先添加空 EventType。详见[元素附着系统设计](../系统/元素附着系统设计.md)、[元素反应事务、事实与验证](../系统/元素反应/事务、事实与验证.md)和[元素反应协调器设计](../协调/元素反应协调器设计.md)。
