# 护盾系统规划

> 状态：规划草案，可作为实现输入；正式实施前只需评审第 26 节列出的少量产品边界。
> 最后更新：2026-07-13。
> 本文同时覆盖第一版架构、数据模型、运行时顺序、迁移策略、实施阶段和验收标准。

## 1. 规划结论摘要

护盾系统建议作为 `core/` 内独立的数值与状态系统实现，但护盾实例的通用身份和生命周期复用最小化的 `MechanicRuntime` 基础能力。护盾不是生命值、属性面板或普通 Buff：

- `ShieldResolver` 只负责在创建帧解析护盾基础吸收量，并冻结创建者相关属性结果。
- `MechanicRuntime` 拥有护盾实例身份、生命周期、过期和原子命令提交。
- `ShieldRuntime` 拥有护盾专用规则，负责授予、刷新、叠加、替换、并行承伤和查询。
- `HealthRuntime` 只接收护盾处理后的剩余伤害，不读取或修改护盾。
- `bonus.shield.strength` 属于当前受保护场上角色的动态属性，在每次承伤时查询，不能在护盾创建时乘入并保存。
- 多个不同护盾不把容量相加；同一次伤害会同时作用于全部活动护盾，最终穿透量由本次能保护最多伤害的护盾决定。
- 同名护盾是否刷新、替换、保留较强值或叠加到上限，不使用一个全局默认猜测，由请求携带显式生命周期策略。
- 直接扣血继续走 `CharacterHpDeduction`，默认绕过护盾；不使用松散的 `ignore_shield` tag 或布尔字段混入普通伤害。
- 第一版不修改 `SimulationConfig`、资产库 schema 或结果库 schema。
- 第一版完成边界为“类型化护盾授予 + 并行吸收 + 生命提交 + 事件/快照/测试闭环”；结晶反应和真实角色内容分后续阶段接入。

## 2. 目标与非目标

### 2.1 目标

第一版护盾系统需要做到：

1. 从稳定主体引用和类型化公式解析护盾基础吸收量。
2. 正确区分创建时快照量、动态护盾强效和元素吸收倍率。
3. 支持多个护盾同时存在并按游戏规则并行承伤。
4. 支持替换、刷新、独立共存和“增加容量但不超过上限”等生命周期规则。
5. 在伤害进入角色生命值前原子提交全部护盾变化。
6. 生成不可变、可序列化、可回放、可分析的授予和吸收结果。
7. 为“处于护盾保护下”“护盾受损”“护盾耗尽”“护盾过期”等内容机制提供稳定事实。
8. 支持动作、角色、武器、圣遗物、共鸣和未来结晶晶片通过统一请求接入。
9. 保持相同输入、属性状态、帧顺序和随机种子得到完全一致的结果。

### 2.2 第一版不负责

- 敌方元素盾、敌人护盾条或破盾元素量；它们属于未来 `Ward`/敌人机制系统。
- 敌人对角色的完整伤害公式；护盾入口消费已经完成防御、抗性和伤害减免处理的来伤量。
- 伤害减免、无敌帧、格挡、免疫和闪避本身；这些处理位于护盾之前。
- 韧性、抗打断和击退的完整结算；第一版只提供“当前是否被有效护盾保护”的查询事实。
- 元素反应、结晶触发、晶片生成和拾取空间逻辑；后续复用护盾授予入口。
- 侵蚀、生命流失或其他直接扣血机制；它们继续使用生命值系统的直接扣血入口。
- UI、专用结果数据库投影和护盾统计图表。
- 未经来源核对的具体角色、武器、圣遗物或反应数值。

## 4. 已确认的游戏行为目标

### 4.1 基础吸收量在创建时确定

护盾公式通常是：

```text
BaseAbsorption = fsum(CreatorAttribute[i] * Coefficient[i]) + FlatAbsorption
NativeAbsorption = BaseAbsorption * product(NativeMultiplier[i])
```

创建者的生命、防御、攻击或精通等公式输入在护盾创建帧解析并冻结。创建后创建者属性变化不反向修改已有护盾。

`NativeMultiplier` 表达护盾自身描述中的额外吸收效果，例如某个施放模式或命座对该护盾的额外倍率。它不是当前受保护角色的通用护盾强效。

### 4.2 护盾强效在承伤时动态读取

护盾强效只作用于当前受保护角色，角色切换后应使用新场上角色在受击帧的护盾强效：

```text
ShieldStrengthMultiplier = 1 + ActiveCharacterShieldStrength
```

因此护盾实例保存的是未乘动态护盾强效的剩余原生吸收量，而不是创建时已经放大的“护盾生命”。

### 4.3 元素吸收倍率

第一版标准策略：

| 护盾类型 | 来伤类型 | 元素吸收倍率 |
| --- | --- | ---: |
| 岩元素护盾 | 任意元素或物理 | `1.5` |
| 非岩元素护盾 | 与护盾同元素 | `2.5` |
| 非岩元素护盾 | 其他元素或物理 | `1.0` |
| 无元素护盾 | 任意 | `1.0` |

岩盾不再额外叠乘“同为岩元素”的 `2.5`；岩盾统一按 `1.5` 处理。

### 4.4 多盾不叠加容量

多个活动护盾同时收到完整来伤，不能把它们串行当成多层额外生命：

```text
for each active shield:
    independently absorb the same incoming amount

protected_damage = max(each shield's absorbable incoming damage)
health_bound_damage = incoming_damage - protected_damage
```

一个较弱护盾破裂不会先消耗完再把剩余伤害交给较强护盾。所有护盾在同一批次中基于承伤前快照计算并同时提交。

### 4.5 过量伤害会穿透

护盾可以在一次命中中耗尽并让超出部分进入生命值：

```text
incoming_damage = 1000
effective_remaining_absorption = 500
health_bound_damage = 500
```

不能因为命中开始时存在护盾就把整次伤害归零。

### 4.6 伤害减免先于护盾

建议完整顺序：

```text
命中成立
-> 伤害公式
-> 防御/抗性/伤害减免/格挡等承伤前处理
-> 已减免来伤量
-> 护盾并行吸收
-> CharacterDamageApplication
-> HealthRuntime
```

无敌帧或未命中应在进入护盾前终止，不消耗护盾。

### 4.7 直接扣血绕过护盾

侵蚀、生命流失和具体技能自扣血如果语义是 HP deduction，应使用：

```text
CharacterHpDeduction -> HealthRuntime.deduct_hp()
```

它们不构造护盾来伤请求。这样不需要容易误用的 `ignore_shield` 标记。

## 5. 系统边界

```text
content / reaction / rule
        |
        v
ShieldGrantRequest
        |
        v
ShieldResolver -- 创建帧属性查询 --> AttributeResolver
        |
        v
ShieldGrantResolution
        |
        v
ShieldRuntime -- 原子命令 --> MechanicRuntime / ShieldComponentStore


Resolved incoming damage
        |
        v
Pre-shield mitigation
        |
        v
CharacterIncomingDamage
        |
        v
ShieldRuntime.absorb()
        |
        +--> ShieldAbsorptionResult + shield state events
        |
        v
CharacterDamageApplication
        |
        v
HealthRuntime.apply_damage()
```

职责约束：

- `ShieldResolver` 不读取当前生命，不发布事件，不修改机制状态。
- `ShieldRuntime` 不重新计算敌方伤害公式，不修改角色当前生命。
- `HealthRuntime` 不读取护盾列表，不计算元素吸收或护盾强效。
- `content/` 构造护盾请求和生命周期策略，不直接写护盾容量。
- `application/assembly/` 组装 resolver、runtime、handler、属性定义和 dispatcher。
- `analysis/` 只消费结果和事件，不重新决定护盾真值。

## 6. 状态所有权与 MechanicRuntime

### 6.1 推荐所有权

护盾具有独立身份、持续时间、刷新、替换和过期行为，符合机制实例定义。为了避免护盾系统和未来 Buff 系统各自发明一套生命周期，第一阶段先实现满足护盾所需的最小 `MechanicRuntime` 切片：

```text
MechanicRuntime
├── MechanicInstanceStore       # 身份、owner/source、创建帧、过期帧、状态
├── ShieldComponentStore        # instance_id -> ShieldComponent
├── CommandBuffer               # 授予、批量吸收、移除
└── LifecycleEventPublisher
```

`ShieldRuntime` 是规则入口，不是第二份状态所有者。它通过受控命令查询和提交 `ShieldComponent`。

### 6.2 最小前置切片

本次不需要先实现完整通用 Buff 框架。最小切片只包含：

- 稳定 `MechanicInstanceId` 生成。
- 活动、耗尽、过期、替换和显式移除状态。
- `created_frame <= frame < expires_at_frame` 的生命周期边界。
- 按 owner、capability、mechanic key 和 instance id 的稳定索引。
- 单条授予命令和单次承伤的批量原子命令。
- 先提交状态、后发布不可变事实事件。
- 帧开始时过期，过期帧的 impact 不再受到该护盾保护。

叠层、光环、冷却和通用事件订阅等能力不为目录完整而提前实现。

## 7. 保护对象模型

### 7.1 为什么不能只绑定角色

单人队伍中的普通角色护盾会随切人继续保护新的场上角色，而不是留在创建时的角色身上。护盾强效也随当前场上角色变化。因此护盾默认归属于“玩家队伍的当前场上保护层”，不是某个固定 `AttributeSubjectRef`。

### 7.2 `ShieldProtectionRef`

建议模型：

```text
ShieldProtectionRef
├── kind: active_team | character
└── protection_id: str
```

第一版生产组装只使用：

```text
kind = active_team
protection_id = team:player
```

`character` 预留给未来联机、场景规则或明确只保护固定角色的机制，不在第一版真实内容中启用。

每次承伤时，`active_team` 通过 `TeamRuntimeState.current_character` 解析真实生命目标和护盾强效查询主体。请求中的角色目标必须与该帧场上角色一致，否则抛结构化错误，不能静默把队伍盾用于后台角色。

ShieldElement:

规则：

- 显示名称不参与实例冲突或刷新判断。

## 9. 创建公式模型

### 9.1 `ShieldScalingTerm`

```text
ShieldScalingTerm
├── component_key: str
├── attribute_key: AttributeKey
└── coefficient: float
```

要求：

- `component_key` 在单个公式内唯一。
- `attribute_key` 必须能对创建者角色解析。
- `coefficient` 必须是有限非负数。
- 多属性缩放通过多个 component 表达，不使用自由表达式字符串。

### 9.2 `ShieldNativeMultiplierTerm`

```text
ShieldNativeMultiplierTerm
├── multiplier_key: str
├── multiplier: float
└── source_context: RuntimeSourceRef
```

它表达护盾自身的创建时乘数，要求有限且非负。多个乘数按稳定 key 排序后相乘，并完整进入审计。

### 9.3 `ShieldCapacityFormula`

```text
ShieldCapacityFormula
├── scaling_terms: tuple[ShieldScalingTerm, ...]
├── flat_absorption: float
└── native_multipliers: tuple[ShieldNativeMultiplierTerm, ...]
```

公式：

```text
component_value[i] = creator_attribute[i] * coefficient[i]
base_absorption = fsum(component_value) + flat_absorption
native_absorption = base_absorption * product(native_multiplier)
```

普通替换盾只需要一个 grant formula。可叠加到上限的护盾可以同时提供：

```text
grant_formula
capacity_limit_formula
```

两者在同一创建帧和同一属性 session 中解析，避免动态属性在两个公式之间出现不一致。

## 10. 护盾授予请求与结果

### 10.1 `ShieldGrantRequest`

```text
ShieldGrantRequest
├── grant_id: str
├── frame: int
├── mechanic_key: str
├── handler_key: str
├── protection_ref: ShieldProtectionRef
├── creator_ref: AttributeSubjectRef
├── source_context: RuntimeSourceRef
├── element: ShieldElement
├── duration_frames: int
├── grant_formula: ShieldCapacityFormula
├── capacity_limit_formula: ShieldCapacityFormula | None
├── grant_policy: ShieldGrantPolicy
├── conflict_key: str
├── grants_interruption_resistance: bool
└── tags: frozenset[str]
```

关键约束：

- `mechanic_key` 是护盾语义身份；`handler_key` 是代码实现绑定入口。
- `conflict_key` 决定同类实例如何查找，不使用显示名称。
- `duration_frames` 必须为正整数。
- `capacity_limit_formula` 只允许 `add_capped_refresh` 使用。
- `coexist` 必须有明确的实例数量规则，第一版默认同一 conflict key 最多一个活动实例，不允许无限产生。
- 请求不携带“最终乘过护盾强效的 HP”。

### 10.2 `ShieldGrantResolution`

```text
ShieldGrantResolution
├── grant_id
├── frame
├── creator_ref
├── protection_ref
├── component_results
├── flat_absorption
├── native_multiplier_results
├── granted_absorption
├── capacity_limit
├── attribute_trace
└── source_context
```

该结果只说明本次能够授予多少原生吸收量，不说明 store 最终采用了创建、替换、叠加还是保留旧盾。

### 10.3 `ShieldGrantResult`

`ShieldRuntime` 提交生命周期决策后返回：

```text
ShieldGrantResult
├── resolution: ShieldGrantResolution
├── outcome: ShieldGrantOutcome
├── instance_id
├── replaced_instance_id: str | None
├── remaining_before
├── remaining_after
├── maximum_after
├── expires_at_before
└── expires_at_after
```

## 11. 护盾实例状态

### 11.1 `ShieldComponent`

```text
ShieldComponent
├── mechanic_key
├── handler_key
├── protection_ref
├── creator_ref
├── source_context
├── element
├── maximum_native_absorption
├── remaining_native_absorption
├── conflict_key
├── grants_interruption_resistance
├── grant_snapshot_ref
└── tags
```

通用 `MechanicInstance` 保存：

```text
instance_id
owner_ref
created_frame
expires_at_frame
lifecycle_state
```

数值不变量：

```text
maximum_native_absorption > 0
0 < remaining_native_absorption <= maximum_native_absorption
created_frame < expires_at_frame
```

耗尽后实例在同一原子提交中移出活动索引，因此活动 store 中不保留 `remaining == 0` 的护盾。

### 11.2 为什么保存原生剩余量

假设原生剩余量为 `500`：

- 当前角色护盾强效 `0%` 时可挡 `500` 伤害。
- 当前角色护盾强效 `35%` 时可挡 `675` 伤害。
- 切人失去 `35%` 后，仍然只剩 `500` 原生量，不应保留曾经的 `675` 有效量。

保存放大后的“当前盾 HP”会在切人和动态 Buff 失效时产生错误。

## 12. 来伤模型

### 12.1 `CharacterIncomingDamage`

建议在护盾 handler 边界增加：

```text
CharacterIncomingDamage
├── damage_id: str
├── frame: int
├── protection_ref: ShieldProtectionRef
├── target_ref: AttributeSubjectRef
├── mitigated_amount: float
├── element: DamageElement
├── source_ref: AttributeSubjectRef | None
├── source_context: RuntimeSourceRef | None
└── tags: frozenset[str]
```

`mitigated_amount` 明确表示已经完成普通伤害公式和所有护盾前减免后的非负来伤量。字段名称禁止使用含糊的 `raw_damage`。

第一版不增加 `bypass_shield`。应该绕过护盾的机制不构造该请求，而是使用直接扣血入口。

### 12.2 与现有 `DamageResult` 的关系

当前 `DamageRequest` 只支持角色攻击场景目标，不能直接作为敌人对角色的入口。第一版护盾测试和集成可以直接构造 `CharacterIncomingDamage`。

未来实现敌方伤害公式后增加显式 adapter：

```text
Incoming DamageResult
-> mitigation result
-> CharacterIncomingDamage
```

不应为了护盾先放宽现有 `DamageRequest` 的主体校验并混入不完整的敌方公式。

## 13. 并行吸收算法

### 13.1 单盾计算

对每个承伤前活动护盾 `i`：

```text
element_multiplier[i] = ElementalAbsorptionPolicy(
    shield.element,
    incoming.element,
)

shield_strength_multiplier = 1 + active_character_shield_strength

effective_multiplier[i] =
    element_multiplier[i] * shield_strength_multiplier

capacity_cost[i] = min(
    shield.remaining_native_absorption,
    incoming.mitigated_amount / effective_multiplier[i],
)

absorbable_incoming_damage[i] = min(
    incoming.mitigated_amount,
    shield.remaining_native_absorption * effective_multiplier[i],
)

remaining_after[i] =
    shield.remaining_native_absorption - capacity_cost[i]
```

`effective_multiplier` 必须为有限正数。护盾强效导致乘数小于或等于 `0` 时抛结构化错误，不使用 clamp 掩盖非法机制状态。

### 13.2 多盾聚合

所有单盾结果都使用同一个承伤前快照：

```text
protected_damage = max(absorbable_incoming_damage, default=0)
health_bound_damage = mitigated_amount - protected_damage
```

然后一次性提交所有 `remaining_after`。任何一个查询、计算或命令校验失败时，全部护盾保持原状。

### 13.3 数值规则

- 拒绝 `bool`、NaN、正无穷和负无穷。
- 所有容量和来伤必须非负；活动护盾容量必须为正。
- `-0.0` 规范化为 `0.0`。
- core 不做显示舍入。
- 加法使用 `math.fsum`；乘数按稳定 key 顺序处理。
- 浮点残差只在明确的近零规范化 helper 中处理，容差必须固定并有边界测试。
- 不能因为浮点误差留下不可见的极小活动护盾；归零策略要在模型 helper 中统一。

## 14. 吸收结果

### 14.1 `ShieldHitResult`

每个承伤前活动护盾生成一条结果：

```text
ShieldHitResult
├── instance_id
├── mechanic_key
├── element
├── native_before
├── native_cost
├── native_after
├── element_multiplier
├── shield_strength
├── shield_strength_multiplier
├── effective_multiplier
├── absorbable_incoming_damage
└── depleted
```

结果按稳定 `instance_id` 排序，不依赖列表插入或字典遍历顺序。

### 14.2 `ShieldAbsorptionResult`

```text
ShieldAbsorptionResult
├── damage_id
├── frame
├── protection_ref
├── target_ref
├── mitigated_amount
├── element
├── active_character_shield_strength
├── shield_hits: tuple[ShieldHitResult, ...]
├── protected_damage
├── health_bound_damage
├── had_active_shield_before
├── has_active_shield_after
└── depleted_instance_ids
```

不变量：

```text
0 <= protected_damage <= mitigated_amount
0 <= health_bound_damage <= mitigated_amount
mitigated_amount = protected_damage + health_bound_damage
```

### 14.3 `IncomingDamageApplicationRecord`

handler 最终返回完整编排记录：

```text
IncomingDamageApplicationRecord
├── incoming_damage
├── shield_result
├── health_application
└── health_result
```

完全吸收时仍产生记录，其中 `health_application.amount == 0`，生命系统返回零有效变化但不发布虚假生命变化事件。

## 15. 授予与刷新策略

### 15.1 `replace`

- 移除同 conflict key 的旧实例，原因 `replaced`。
- 创建新实例，容量等于本次 `granted_absorption`。
- 不自动保留旧盾较高剩余量。

### 15.2 `refresh_replace`

- 保留实例身份。
- 容量替换为新授予量。
- 过期帧更新为 `frame + duration_frames`。
- 用于明确描述为同一实例刷新且事件身份需要连续的内容。

### 15.3 `add_capped_refresh`

```text
remaining_after = min(
    remaining_before + granted_absorption,
    capacity_limit,
)
```

- 必须提供正数 `capacity_limit`。
- 同时刷新持续时间。
- 用于托马、绮良良等描述明确允许新盾吸收量叠加到上限的机制。

### 15.4 `keep_stronger_refresh`

```text
remaining_after = max(remaining_before, granted_absorption)
```

- 刷新持续时间。
- 只在真实内容来源确认该行为后使用。
- 不作为普通护盾默认策略。

### 15.5 `coexist`

- 不与不同 conflict key 合并。
- 同一 protection ref 上的不同护盾可以并存，并在承伤时同时受损。
- 同 conflict key 的实例数量必须由显式上限控制。

## 16. 运行时与事件顺序

### 16.1 帧内顺序

建议 `BasicRuntimeWorld` 的相关顺序调整为：

```text
MechanicRuntime（提交前序命令并过期到期实例）
-> ActionManager
-> ImpactRuntime
-> SpaceRuntime / CreatedObjectRuntime
```

无论具体 world 顺序如何，所有护盾公共入口都必须拒绝在请求帧已经过期的实例，不能依赖某个列表稍后清理。

生命周期边界沿用现有实体约定：

```text
created_frame <= frame < expires_at_frame
expires_at_frame = created_frame + duration_frames
```

### 16.2 护盾授予事件

原子提交完成后按以下顺序发布：

```text
SHIELD_REMOVED(reason=replaced)       # 仅发生替换时
-> SHIELD_GRANTED
```

`SHIELD_GRANTED` payload 保存 `ShieldGrantResult`。创建、刷新、叠加和保留旧值由 `outcome` 区分，不为每种策略增加一个事件类型。

### 16.3 承伤事件

```text
计算全部 ShieldHitResult
-> 原子提交全部容量变化和耗尽移除
-> SHIELD_CAPACITY_CHANGED（按 instance_id）
-> SHIELD_REMOVED(reason=depleted，按 instance_id）
-> SHIELD_ABSORPTION_RESOLVED（有护盾实际参与时）
-> CharacterDamageApplication
-> CHARACTER_HEALTH_CHANGED（仅生命真实减少时）
-> DAMAGE_APPLIED
```

`DAMAGE_APPLIED` 表达本次角色来伤编排已经完成，payload 同时保存护盾结果和生命结果。完全被护盾吸收时仍发布，因为护盾状态已经变化。

### 16.4 过期与显式移除

```text
SHIELD_REMOVED(reason=expired | dispelled | owner_removed)
```

过期不发布伪造的 `SHIELD_CAPACITY_CHANGED`；剩余容量没有被伤害消耗，只是实例不再活动。

### 16.5 事件规则

- 事件只表达已提交事实，不作为修改同一次吸收计算的可变 hook。
- 事件 handler 产生的新机制命令进入后续阶段，不能在当前吸收调用栈递归改变结果。
- 零来伤不消耗护盾，不发布容量变化或吸收事件。
- 无活动护盾时不发布 `SHIELD_ABSORPTION_RESOLVED`，但来伤 handler 仍形成普通 `DAMAGE_APPLIED` 记录。

建议新增事件：

| EventType | Category | 默认记录 | 语义 |
| --- | --- | --- | --- |
| `SHIELD_GRANTED` | `STATE_CHANGE` | 是 | 护盾实例已创建、刷新、叠加或保留。 |
| `SHIELD_CAPACITY_CHANGED` | `STATE_CHANGE` | 是 | 护盾原生剩余量因吸收或叠加发生变化。 |
| `SHIELD_REMOVED` | `STATE_CHANGE` | 是 | 护盾因耗尽、过期、替换或显式原因离开活动状态。 |
| `SHIELD_ABSORPTION_RESOLVED` | `FACT` | 是 | 一次来伤的并行护盾吸收已经完成。 |
| `DAMAGE_APPLIED` | `STATE_CHANGE` | 是 | 角色来伤已完成护盾与生命提交。 |

## 17. 属性系统接入

### 17.1 新公共属性

建议增加：

```text
bonus.shield.strength
```

契约：

| 项目 | 值 |
| --- | --- |
| 主体 | character |
| policy | additive |
| default | `0.0` |
| 百分比单位 | 小数，如 35% 为 `0.35` |
| 快照 | 不由护盾创建快照；承伤帧动态查询 |

该属性必须同步加入：

- `core/attributes/keys.py`。
- 公共属性 registry。
- [属性系统契约](../契约/属性系统契约.md)。
- 资产/配置静态 stat 映射（如果配置支持该词条）。

### 17.2 查询上下文

承伤查询至少携带：

```text
subject_ref = 当前场上角色
frame = 来伤帧
source_ref = 来伤来源上下文
target_ref = 来伤来源主体（若存在）
tags = 来伤 tags
```

这样共鸣、圣遗物或条件效果可以通过已有 `ModifierProvider` 贡献护盾强效，不需要护盾系统维护第二套 Buff 列表。

### 17.3 护盾自身加成不是公共护盾强效

“该技能生成的护盾吸收量提高”“长按额外提高吸收量”等规则进入创建公式的 `native_multipliers` 或专用 grant policy，不注册为角色全局 `bonus.shield.strength`，避免错误增强其他来源的护盾。

## 18. Impact 与 content 接入

### 18.1 新增 `ImpactKind.SHIELD`

建议给通用 impact 增加稳定 kind：

```text
shield
```

`APPLY_STATUS` 不足以表达护盾公式、容量和并行承伤契约，使用专用 kind 能在 dispatcher 边界尽早校验。

### 18.2 转换链路

```text
ActionImpactPoint
-> content ImpactFactory
-> ImpactRequest(kind=shield)
-> ShieldImpactRequestHandler
-> 类型化 ShieldGrantRequest
-> ShieldResolver
-> ShieldRuntime.grant()
```

`ImpactRequest.params` 只作为跨 content 边界的传输结构。进入护盾系统后必须转换为强类型请求，后续逻辑不重复读取自由字典。

### 18.3 content 责任

真实 content 负责提供：

- 稳定 `mechanic_key`、`handler_key` 和 `conflict_key`。
- 技能倍率到 `ShieldCapacityFormula` 的映射。
- 施放模式、命座和天赋产生的 native multiplier。
- 明确持续时间和 grant policy。
- 动作 impact 时机和目标 protection ref。

content 不得：

- 直接构造或修改 `ShieldComponent`。
- 把显示名称作为冲突 key。
- 在事件 handler 中直接扣盾。
- 把护盾剩余量保存到 `ContentStateStore`。

### 18.4 组装期校验

以下错误必须在组装阶段暴露：

- 真实资产声明护盾 impact 但缺少 handler。
- `handler_key` 未注册对应的 Shield factory。
- scaling 引用缺失或组件类型不受支持。
- 生命周期策略与请求字段不匹配。
- 私有属性依赖未声明。
- 同一 conflict key 注册了互相矛盾的策略。

## 19. 结晶接入规划

结晶不是第一版护盾核心完成条件，但架构必须支持：

```text
Geo 反应触发
-> 生成带元素的 CrystalShard CreatedObject
-> 晶片保存触发者、触发帧和护盾公式快照引用
-> 当前场上角色进入拾取范围
-> 晶片行为发出 ImpactRequest(kind=shield)
-> 结晶盾授予 active_team protection ref
-> 晶片移除
```

结晶基础量：

```text
CrystallizeAbsorption =
    LevelBaseAbsorption
    * (1 + (40 / 9) * EM / (1400 + EM))
```

KQM 页面给出的 90 级基础量为 `1851.06`，持续时间为 15 秒。正式实现前还需把完整等级表作为反应数据契约导入或冻结，不能在 content 中散落常量。

结晶专项要求：

- 晶片元素决定盾元素。
- 同元素伤害使用 `2.5` 倍吸收。
- 当前场上角色护盾强效继续在承伤时动态生效。
- 新晶片是否统一替换旧结晶盾、属性快照发生在反应帧还是拾取帧，进入反应实现批次时用当前版本来源和 golden case 冻结。
- 晶片共享拾取冷却、拾取范围和空间生命周期属于反应/空间系统，不进入护盾核心。

## 20. 快照、持久化与分析

### 20.1 core 快照

建议增加：

```text
ShieldSnapshot
├── frame
├── instances: tuple[ShieldInstanceSnapshot, ...]

ShieldInstanceSnapshot
├── instance_id
├── mechanic_key
├── protection_ref
├── creator_ref
├── source_context
├── element
├── maximum_native_absorption
├── remaining_native_absorption
├── created_frame
├── expires_at_frame
└── tags
```

快照保存原生容量，不保存某个角色当时推导出的“有效盾量”作为真值。UI 或 analysis 如需显示有效量，应把快照帧的护盾强效和指定来伤元素作为明确查询条件。

### 20.2 第一版结果持久化

沿用现有通用事件 JSON：

- 不增加专用护盾表。
- 不升级结果库 schema。
- 所有 payload 提供稳定 `to_dict()`。
- integration test 验证事件往返。

当真实仿真数据证明事件扫描成本过高后，再评审专用投影：

```text
shield_instances
shield_capacity_changes
shield_absorption_records
```

### 20.3 analysis 可派生指标

- 护盾覆盖时间和覆盖率。
- 每个来源的原生授予量、有效吸收量和浪费量。
- 耗尽次数、过期次数和替换次数。
- 穿透到生命的伤害。
- 多盾同时存在时的冗余吸收损失。
- 不同场上角色护盾强效对有效承伤的影响。

这些指标只消费事件和快照，不回写运行态。

## 21. 错误模型

建议错误层级：

```text
ShieldSystemError
├── ShieldValidationError
├── ShieldAttributeError
├── ShieldProtectionNotFoundError
├── ShieldTargetMismatchError
├── ShieldInstanceNotFoundError
├── ShieldPolicyError
├── ShieldCapacityError
├── ShieldStateConflictError
└── ShieldAtomicCommitError
```

典型错误：

| 错误 | 场景 |
| --- | --- |
| `ShieldValidationError` | 空 key、非法帧、负数、bool、NaN、无穷或非法枚举。 |
| `ShieldAttributeError` | 创建公式属性或受击帧护盾强效无法解析。 |
| `ShieldProtectionNotFoundError` | protection ref 未在当前运行时登记。 |
| `ShieldTargetMismatchError` | active team 请求目标不是当前场上角色。 |
| `ShieldInstanceNotFoundError` | 指定刷新/移除的实例不存在。 |
| `ShieldPolicyError` | capped policy 缺上限或策略字段组合非法。 |
| `ShieldCapacityError` | 公式结果非正、有效乘数不为正或状态违反不变量。 |
| `ShieldStateConflictError` | conflict key 与活动实例状态不一致。 |
| `ShieldAtomicCommitError` | 批量承伤提交无法完整应用。 |

错误发生时：

- resolver 错误不产生实例、事件或部分结果。
- grant 提交错误不修改旧实例。
- absorb 计算或提交错误不修改任何护盾，也不调用生命系统。
- 生命提交错误不能回滚已经提交的护盾；handler 记录失败阶段并保留已形成事实。若未来需要跨系统事务，必须单独评审，不能伪装为当前已有保证。

## 22. 确定性与原子性

### 22.1 稳定顺序

- 活动护盾按 `instance_id` 排序后计算和发布事件。
- grant 冲突候选按固定 owner、conflict key、created frame、instance id 排序。
- 属性 term 和 native multiplier 使用各自稳定 key。
- 结果序列化对 tags 排序。

### 22.2 批量原子提交

一次承伤必须使用：

```text
读取版本/活动实例快照
-> 纯计算全部变化
-> 校验 store 版本和全部实例前值
-> 一次性提交全部新值和移除
```

禁止逐盾边算边写。否则后一个盾、事件 handler 或查询可能观察到只提交了一半的状态。

### 22.3 重入规则

- `ShieldRuntime.absorb()` 处理期间不允许同一 protection ref 重入吸收。
- 事件产生的新伤害或护盾命令进入后续机制阶段。
- 超过同帧机制级联上限时使用 MechanicRuntime 的结构化循环错误。

## 23. 测试与 golden case

### 23.1 模型测试

- 所有 key、ref、枚举和数值字段的合法输入。
- 空字符串、错误主体、负帧、零持续时间、bool、NaN 和无穷。
- 公式 component key 和 multiplier key 重复。
- policy 与 capacity limit 的合法组合。
- 不可变集合和稳定序列化。

### 23.2 创建公式测试

- 单属性倍率加固定值。
- 多属性 component 使用 `math.fsum`。
- 多个 native multiplier 的稳定乘算和审计。
- grant 和 cap 公式共享属性 session。
- 创建后属性变化不影响已有原生容量。
- 公式得到零、负数或非有限数时拒绝授予。

### 23.3 吸收算法测试

至少冻结以下数值案例：

#### 案例 A：过量伤害

```text
原生容量 3500，倍率 1.0
连续四次来伤 1000

前三次：生命伤害 0，剩余容量依次 2500、1500、500
第四次：保护 500，生命伤害 500，护盾耗尽
```

该案例直接对应 KQM 的公开示例。

#### 案例 B：同元素盾

```text
火盾原生容量 1000
火伤 2000
元素倍率 2.5
容量消耗 800
剩余 200
生命伤害 0
```

#### 案例 C：岩盾

```text
岩盾原生容量 1000
物理伤害 1200
元素倍率 1.5
容量消耗 800
剩余 200
生命伤害 0
```

#### 案例 D：动态护盾强效与切人

```text
原生容量 1000
角色 A 护盾强效 35%，来伤 675 -> 消耗原生量 500，剩余 500
切换角色 B，护盾强效 0%，来伤 600 -> 保护 500，生命伤害 100
```

用于阻止把护盾强效错误快照进实例。

#### 案例 E：多盾同时承伤

```text
盾 A：原生 1000，有效倍率 1.0，可保护 1000
盾 B：原生 600，有效倍率 2.5，可保护 1500
来伤 1700

两个盾都基于 1700 同时耗尽
protected_damage = max(1000, 1500) = 1500
health_bound_damage = 200
```

用于阻止串行叠加为 2500。

#### 案例 F：伤害减免先于护盾

```text
理论来伤 2000
护盾前伤害减免 50%
mitigated_amount = 1000
原生容量 1000，倍率 1.0
最终生命伤害 0，护盾耗尽
```

#### 案例 G：容量叠加到上限

```text
旧剩余量 3000
本次授予量 2000
上限 4000
结果 4000，并刷新持续时间
```

#### 案例 H：过期边界

```text
frame 10 创建，duration 60，expires_at 70
frame 69 活动
frame 70 过期，frame 70 来伤不再消耗该盾
```

### 23.4 原子性与事件测试

- 多盾中任一计算失败时所有容量不变。
- 批量命令版本冲突时无部分提交。
- 容量变化和耗尽事件按 instance id 稳定排序。
- 事件 handler 不能递归修改同一次吸收。
- 完全吸收时有 `DAMAGE_APPLIED`，无 `CHARACTER_HEALTH_CHANGED`。
- 无盾普通承伤正确进入生命值。
- 过期、替换和耗尽使用不同 removal reason。
- 通用事件 JSON 往返不升级结果 schema。

### 23.5 第一条真实内容 golden

推荐在核心闭环后选择一个公式简单且能覆盖关键规则的真实护盾，优先级：

1. 迪奥娜冰盾：验证创建属性快照、冰伤 2.5 倍、点按/长按 native multiplier 和切人后的动态护盾强效。
2. 诺艾尔岩盾：验证防御缩放和岩盾 1.5 倍全伤害吸收。
3. 托马或绮良良：在基础生命周期稳定后验证 `add_capped_refresh`。

真实 handler 绑定前必须同时冻结资产倍率、天赋等级、角色属性、持续时间、预期原生容量和承伤结果。只完成测试请求不代表真实角色 content 已完整实现。

## 24. 旧项目迁移评估

### 24.1 可保留的行为目标

- 多个护盾同时承受同一次伤害。
- 最终穿透量使用各盾可保护伤害的最大值。
- 同元素 `2.5` 和岩盾 `1.5` 的吸收方向。
- 护盾生命周期和容量跳变需要可记录、可回放。

### 24.2 必须废弃或重写

| 旧实现 | 问题 | 新方案 |
| --- | --- | --- |
| `ShieldConfig` 使用 `Any` creator/target | 无稳定身份与组装校验 | 强类型 creator/protection/source ref |
| 创建时读取 creator 的“护盾强效” | 作用主体和时机错误 | 承伤帧读取当前场上角色属性 |
| 保存已乘强效的 `current_hp` | 切人或 Buff 失效后错误 | 保存原生剩余吸收量 |
| 可变 `BEFORE_HURT` 事件改写 `amount` | 顺序和重入不可审计 | 类型化同步 handler 和不可变结果 |
| `target.shield_effects` 列表 | 状态散落在实体上 | MechanicRuntime + ShieldComponentStore |
| 统一 `max(old, new)` 刷新 | 不符合不同盾的特殊规则 | 显式 grant policy |
| 直接减成负容量再 remove | 产生非法中间状态和负数事件 | clip 后原子耗尽移除 |
| `ignore_shield` 自由布尔 | 容易把 HP loss 混成普通伤害 | 直接扣血走独立入口 |
| 护盾系统内日志和数据库事件 | core 与基础设施耦合 | 结构化事件，由外层记录 |
| 缺少护盾单元测试 | 无迁移可信度 | 数值矩阵 + golden case |

旧持久化中的 `effect_lifecycles` 和 `shield_jumps` 只可作为分析需求参考，表结构不直接迁移。

## 26. 需要评审的事项

以下事项无法仅凭当前仓库和通用机制资料完全定案，但都不会阻塞阶段 A-E 的核心实现：

1. **第一条真实 content 选择**：推荐迪奥娜以覆盖最多关键规则；若希望最小实现量，可改为诺艾尔。这个选择只影响阶段 F。
2. **结晶快照帧**：反应触发帧还是晶片拾取帧读取触发者精通，需要在阶段 G 使用当前版本实测或可信证据冻结。架构已支持显式快照引用。
3. **结晶盾冲突规则**：新晶片是否跨元素统一替换旧结晶盾，需要在阶段 G 单独 golden；不要沿用旧项目猜测。
4. **专用结果投影时机**：第一版只使用通用事件 JSON。只有真实数据量证明查询成本不可接受时才增加护盾专表。
5. **固定角色 protection ref**：第一版生产只启用 `active_team`。未来联机或特殊机制确实需要固定角色盾时，再开放 `character` 并补目标选择规则。

除上述事项外，本文其余边界、模型、算法、顺序和阶段划分可直接作为实现基线。

## 27. 完成标准

护盾系统第一版只有同时满足以下条件才算完成：

1. 护盾创建属性在创建帧快照，护盾强效在承伤帧从当前场上角色动态查询。
2. 实例保存原生剩余吸收量，不保存已乘动态护盾强效的伪生命值。
3. 岩盾、同元素盾和普通盾的标准元素倍率正确且可替换为显式 policy。
4. 多盾基于同一承伤前快照同时扣减，生命穿透量使用最大保护量而不是容量求和。
5. 授予、刷新、叠加、替换、耗尽和过期都有强类型结果与事件。
6. 一次多盾承伤原子提交，失败时无部分容量变化。
7. 护盾处理后的剩余伤害通过 `CharacterDamageApplication` 进入唯一生命写入口。
8. 直接扣血不经过护盾，且没有通用 `ignore_shield` 逃生字段。
9. 护盾实例归 MechanicRuntime/ShieldComponentStore 所有，不重复保存在角色实体或 ContentStateStore。
10. Action/Impact、assembler、快照和通用结果事件形成纵向闭环。
11. 第 23 节模型、数值、顺序、原子性和持久化测试全部通过。
12. 至少一个真实护盾 golden case 有明确资产输入、来源、预期容量和承伤结果。
13. `pytest`、`ruff`、格式检查和 `pyright` 全部通过；无法运行时必须如实记录原因。
14. 架构、属性契约、事件文档、决策记录和迁移状态与最终实现同步。
