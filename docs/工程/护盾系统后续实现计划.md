当前开放任务：阶段 D（Buff 共享评审收尾与真实 Buff golden case）、阶段 E（触发与后续命令）、阶段 F（真实角色护盾 content）；暂缓范围见第 9 节。

## 2. 阶段 A：护盾领域记录与 Store（已完成）

### 2.1 实现范围

- 领域专用 `ShieldInstanceRef(domain_key="shield", sequence)`。
- 包含有限半开生命周期和移除审计的 `ShieldRecord`。
- 直接保存完整 `ShieldRecord` 的 `ShieldStore`。
- `ShieldMutationPlan` 的完整记录批量替换、version/前值校验和重复提交保护。
- protection、conflict key、mechanic key 和活动帧索引。

### 2.2 验收

- `ShieldStore` 只接受完整 `ShieldRecord` 和类型化领域计划。
- 同一护盾实例的元数据、生命周期和状态位于一条完整记录。
- 批量计划失败无部分记录提交。
- protection、mechanic key、活动帧和完整 instance ref 查询稳定。
- 护盾领域只暴露当前类型化写入口。

## 3. 阶段 B：护盾领域聚合（已完成）

### 3.1 实现范围

- 用 `ShieldState` 替代重复元数据的 `ShieldComponent`。
- 用 `ShieldStore` 原子拥有完整 `ShieldRecord`。
- 把 protection 和 conflict 索引收进 ShieldStore。
- 授予、刷新、替换、耗尽、到期和显式移除改为 `ShieldMutationPlan`。
- 移除护盾对 removal subscriber 的依赖。
- 删除尚无正式消费者的 `grants_interruption_resistance` 字段。

### 3.2 验收

- 不可能创建缺少 ShieldState 的活动护盾实例。
- mechanic key、handler key 和生命周期没有重复真值。
- replace 的旧记录移除和新记录创建一次提交。
- 并行耗尽在一个 Store 计划中提交。
- 现有公式、授予策略和多盾行为测试保持通过。

## 4. 阶段 C：角色受伤协调器（已完成）

### 4.1 实现范围

- 新建 `core/coordination/character_damage_taken/`。
- 将 `CharacterIncomingDamage` 和 `CharacterDamageTakenRecord` 移出 shield package。
- 将请求数值改为伤害系统已经完成计算的 `amount`，并删除 protection ref。
- ShieldRuntime 根据 target ref 解析全部适用保护范围。
- 为 ShieldRuntime 和 HealthRuntime 增加 prepare、validate 和 commit_prevalidated 计划入口。
- CharacterDamageTakenCoordinator 只依赖护盾和血量端口，负责统一预校验、无回调提交和最终事实顺序。
- 直接扣血和按生命流失建模的流血不进入协调器。

### 4.2 验收

- 无盾、零伤害、完全吸收和部分穿透行为符合角色受伤事件语义。
- active team 与固定角色保护可同时匹配。
- 护盾准备失败时生命不变。
- 生命准备失败时护盾不变。
- 任一计划前值冲突时两个 Store 均不提交。
- commit_prevalidated 不查询、不计算、不发布事件且不产生领域业务错误。
- 正伤害完全吸收时仍发布 DAMAGE_APPLIED，但不发布 CHARACTER_HEALTH_CHANGED；零伤害不发布 DAMAGE_APPLIED。
- DAMAGE_APPLIED 保存完整稳定的 CharacterDamageTakenRecord。

## 5. 阶段 D：Buff 独立设计与共享评审（工程闭环已实现，真实内容待验证）

状态：状态效果第一版工程闭环已实现；共享评审结论与真实 Buff golden case 待收尾。

选择一个不包含触发回调的简单限时属性 Buff，先按 Buff 领域自身不变量设计：

```text
ApplyBuffRequest
-> BuffRuntime
-> BuffStore -> BuffRecord
-> ModifierProvider read view
-> AttributeResolver
```

验收重点：

- Buff 直接拥有实例引用、生命周期、记录和写入口，不依赖护盾模型。
- 属性查询无副作用。
- Buff 过期后 provider 不再贡献 term。
- 比较 Buff 与护盾已经实现的身份、生命周期和提交不变量，而不是只比较字段名称。

只有两者存在相同且稳定的不变量时，才评审提取中立值对象或提交工具；否则保持两个领域实现独立。

正式设计见[状态效果系统设计](../架构/系统/状态效果系统设计.md)，字段、策略、事件和测试要求见[状态效果系统契约](../契约/状态效果系统契约.md)。共享评审基于 Buff 第一版实现与测试完成后的实际不变量，不能只比较设计字段。

## 7. 阶段 F：真实护盾 content

状态：待推进。

至少选择一个规则简单、资料充分的真实角色护盾，完成：

```text
资产与 handler_key
-> content action / impact
-> ShieldGrantRequest
-> ShieldRuntime / ShieldStore
-> CharacterDamageTakenCoordinator
-> HealthRuntime
-> 事件与结果持久化
```

实现前输入：

- 当前版本技能描述和资产倍率。
- 等级、天赋等级和创建属性。
- 持续时间、元素、授予策略和 conflict key。
- 长按、命座、固有天赋或特殊倍率影响。
- 抗打断需求只记录为后续系统输入，不写入临时布尔字段。
- 至少一个可复现的创建与承伤 golden case。

验收：

- 使用真实资产输入，不以测试参数替代正式数据链路。
- 创建公式中间量和最终原生容量可审计。
- 切换场上角色后动态护盾强效正确。
- 刷新、替换和过期行为与来源一致。
- handler 缺失或数据错误在组装阶段失败。
- 事件和结果库记录可复现完整过程。

## 8. 阶段 G：结晶反应（已完成）

稳定机制、字段和失败边界已经迁移到[结晶反应设计](../架构/系统/元素反应/反应/结晶反应设计.md)与[结晶反应契约](../契约/元素反应/反应/结晶反应契约.md)。本计划只保留护盾侧交付结果：

- `ShieldRuntime` 已提供 `prepare_grant()`、`validate()`、`commit_prevalidated()` 和授予事实入口。
- `CrystallizeShardPickupCoordinator` 已在一次批次中预校验并提交 Reaction State、Space Entity 和 Shield。
- 晶片元素映射为同元素结晶护盾；容量使用创建时捕获的 `native_absorption`。
- 默认 protection 为 active team，普通结晶护盾使用共享冲突键和 `REPLACE` 策略，持续 900 帧。
- 生产组装已暴露类型化拾取入口，golden case 已覆盖拾取、授盾和角色受伤吸收。

仍未实现的只有物理碰撞、距离、阵营、拾取资格、自动拾取和角色专属晶片规则；这些内容不属于 Shield 领域，也不在本计划中补定义。
