## 2. 候选与元素消费

星超导只匹配以下条件同时满足的交互：

1. 请求携带 `reaction_capability:stellar_conduct`；
2. 请求携带上游确认的角色来源集合 `character_source_refs`；
3. 当前触发来源 `source_ref` 属于该角色集合；
4. 冰雷方向：冰触发正雷 Aura，或雷触发正冰 Aura。

星超导 `selection_priority` 为 `110`，高于普通超导默认 `0`；无 capability 或合法角色触发来源时星候选不匹配，普通超导继续生效。capability 存在但后续计划缺少空间锚点、binding 不一致或其他技术前提缺失时整批失败，不静默回退为普通超导。

| incoming_element | observed_aura_kind | 消费关系 |
| --- | --- | --- |
| `cryo` | `electro` | `1:1` |
| `electro` | `cryo` | `1:1` |

```text
consumed = min(incoming_amount, aura_amount)
```

星超导 occurrence 不产生公共反应伤害，也不声明普通 Damage Gate；剩余后手元素量的处理与普通超导一致（不自动形成持久 Aura）。

## 3. 极星辉域 State

极星辉域 State 字段：

```text
instance_ref / space_entity_ref / subject_ref
created_by_occurrence_ref / trigger_source_ref / team_ref
created_frame / expires_at_frame / revision
```

约束：

- `instance_ref` 必须等于 `reaction-state:polestar-field:{created_by_occurrence_ref}`，`space_entity_ref` 必须等于 `reaction_object:polestar_field:{created_by_occurrence_ref}`；
- `expires_at_frame >= created_frame + 420`，创建时等于 `created_frame + 420`；领域生命周期的真值是"最近一次触发后 420 帧"；
- 刷新必须保留 `instance_ref`、`subject_ref`、`space_entity_ref`、`trigger_source_ref`、`created_by_occurrence_ref` 和创建帧，只延展存在时间并递增 `revision`；
- 刷新批次必须包含同一 Space 实体的生命周期更新：保留创建帧与位置，仅同步 `expires_at_frame`；State 刷新与 Space 更新数量一一对应，缺失或不一致时批次校验失败。

创建/刷新/替换规则（由 `plan_polestar_field_occurrence` 形成确定性计划）：

- 触发目标位置（Space 实体锚点）处于当前领域外（X/Z 距离 `> 12`）时：移除旧领域 State 与 Space 实体，以新位置创建新领域；
- 处于当前领域内（X/Z 闭区间 `<= 12`，忽略 Y 轴）时：保留实例与圆心，刷新 `expires_at_frame = frame + 420`，并同步更新 Space 实体的生命周期投影；
- 无领域时在触发目标当时位置创建，圆心与角色位置无关；
- 同一队伍至多一个领域，同一批次出现多个待建领域时由批次校验失败；
- 到期帧由 `PolestarFieldExpiryCoordinator` 原子移除 State、Space 实体与队伍共享计数。

半径 `12`、无限高度与 `420` 帧持续时间为实现基线；半径来源尚未完全确定，精确帧边界待来源化用例确认（见第 10 节）。

## 4. 队伍共享计数 State 与附着记录

计数 State 字段：

```text
instance_ref / subject_ref / team_ref
window_start_frame / next_settlement_frame / window_index
pending_count / settled_stacks
recorded_record_refs / excluded_attack_refs / revision
```

约束：

- `instance_ref` 必须等于 `reaction-state:stellar-conduct-counter:{team_ref}`，slot scope 为队伍；
- `next_settlement_frame = window_start_frame + 240`；
- `window_index` 从 `1` 连续递增；`revision` 随每次变更递增；
- `recorded_record_refs` 与 `excluded_attack_refs` 不能重复。

附着记录使用 `StellarConductAttachmentRecord`：

```text
record_ref / attack_ref / element / frame / target_refs
```

- `element` 只允许冰或雷；`target_refs` 为非空去重序列；
- `attack_ref` 与 `excluded_attack_refs` 使用同一攻击根身份（交互批次归一化的 `root_work_id`），一次交互批次内所有敌人的冰雷 Aura 施加按攻击根聚合为一条记录，由 `ElementalInteractionCoordinator` 在同批次内调用 `record_stellar_conduct_attachment`；扩散等派生附着按各自派生 Impact 的攻击根独立聚合；
- 追加必须满足：计数与领域 State 存在、领域未到期、`record_ref` 未在当前窗口记录、`attack_ref` 不在 `excluded_attack_refs`、至少一个目标 X/Z 距离领域圆心 `<= 12`；
- 一次攻击对多个敌人的附着只生成一条记录；双判的两次攻击为两条记录；同一攻击多目标与多个辉映角色都不重复计数；
- 新领域生成（创建或替换）时，触发该次星超导的攻击身份写入 `excluded_attack_refs`，只在当前窗口生效；
- 领域替换不重置计数：窗口、层数与计时跨领域替换继承，共享会话结束时才整体移除。

## 5. 周期结算

`4` 秒（`240` 帧基线）窗口到期时：

1. 帧规范化把本帧 due 的计数结算冻结为 `StellarConductCounterSettlementRootWork`（cause kind `stellar_conduct_counter_settlement`，`tick_index = window_index`）；
2. 同一批次推进窗口：`settled_stacks = pending_count`、清空 `pending_count` / `recorded_record_refs` / `excluded_attack_refs`、`window_index += 1`、`next_settlement_frame += 240`；
3. scheduled root adapter（`reaction_scheduled_root_adapter.stellar_conduct`）返回无 Effect 的 `prepared`；State 缺失时返回 `cancelled_state_ended`；
4. 结算不生成公共反应伤害；结算协调器收尾该 root 时以最新 `settled_stacks` 统一刷新队伍角色的辉映·星烁 Buff 数值（不延长 Buff 存在时间；共享计数已随领域到期移除时跳过）。

层数查询按 `12` 层封顶：`stacks = min(settled_stacks, 12)`；State 保留原始计数。

## 6. 层数系数映射

直伤星烁基础系数（`n` 为结算层数快照）：

```text
n = 0            -> 1
1 <= n <= 12     -> 1.4 + 0.05 * n
n > 12           -> 2
```

辉映·星超导领域内冰/雷普通伤害增益：

```text
n = 0            -> 20%
1 <= n <= 12     -> 28% + 1% * n
n > 12           -> 40%
```

映射出处为[梅信心：伤害公式](https://meropide.cn/chs/reference/%E4%BC%A4%E5%AE%B3%E5%85%AC%E5%BC%8F/)（2026-09-10 版本基线）。冰/雷普通增伤通过辉映 Buff 的 `bonus.damage.cryo` / `bonus.damage.electro` 属性修正进入通用伤害增伤区；直伤星烁基础系数通过辉映 Buff 的 `stellar.conduct.direct_base_multiplier` 属性词条供角色能力读取。

## 7. 辉映·星烁 Buff 与领域来源物理减抗

辉映·星烁 Buff（`buff.reaction.stellar_conduct.radiance`）契约：

- 目标主体为角色；应用策略 `REFRESH`、数值刷新 `REPLACE_LATEST`、至多 1 层；conflict key 为 `buff_conflict.reaction.stellar_conduct.radiance`；
- 携带三个属性词条模板：`stellar.conduct.radiance.cryo_bonus` -> `bonus.damage.cryo`、`stellar.conduct.radiance.electro_bonus` -> `bonus.damage.electro`、`stellar.conduct.radiance.direct_base_multiplier` -> `stellar.conduct.direct_base_multiplier`，均为 `FLAT_ADD`；
- 每次星超导触发（创建、域内刷新、域外替换）后，星超导协调在元素交互批次内为队伍每个角色统一申请或刷新该 Buff：数值取当前 `settled_stacks` 对应的系数映射（`0` 层为 `20%/20%/1.0`），`duration_frames` 满足 `frame + duration = 领域到期帧 + 60`（`60` 为延续基线）；
- 领域到期后 Buff 不被提前移除，自然延续至到期帧 + 60 后经 Buff 生命周期过期；期间共享计数已移除；
- 4 秒窗口结算后由结算协调器以最新层数统一刷新全队 Buff 数值，不改变存在时间；
- `source_context` 固定为 `RuntimeSourceRef(MECHANIC, "reaction.stellar_conduct", player_team)`，保证刷新兼容。

极星辉域来源的物理抗性降低契约：

- 复用普通超导减抗 Buff Definition `buff.reaction.superconduct.physical_resistance_reduction`、属性词条 `resistance.physical.reduction` 与 conflict slot，数值 `-0.40`；不另建领域专属 Buff，同一目标不叠加为 `-80%`；
- 来源 `source_context` 为 `RuntimeSourceRef(MECHANIC, "reaction.stellar_conduct.polestar_field", 领域实例 ref)`；
- 每次星超导触发后，领域内敌人（X/Z `<= 12`）获得该 Buff，`duration_frames` 等于领域剩余帧数；持有领域来源减抗但已离开领域的敌人被以 `EXPLICIT` 原因移除；普通超导来源记录不受影响；
- 两来源在同一 conflict slot 上按 `REPLACE` 语义互相替换，同一目标任意时刻至多一条活动实例。

## 8. 独立星烁伤害公式与请求边界

星烁伤害使用独立 `damage_formula.stellar_reaction`，不注册普通 Reaction Damage kind 或 Damage Gate；伤害分类使用主攻击标签 `星超导冰` / `星超导雷`（直伤星超导按伤害元素拆两个标签；`reaction.stellar_conduct` 是反应身份键，不再兼任伤害标签）。装配层注册这两个标签到星烁公式的 DamageProfile 映射（仅承担公式选择），公式由 `create_default_damage_formula_registry()` 组合进生产 bundle。

`damage_formula.stellar_reaction` 请求校验（`DamageRequest`）：

- 必须携带 `StellarReactionDamageInput`；非星烁公式不得携带该输入；
- 不得同时携带增幅、二次增幅、剧变、激化或月曜反应输入；
- **必须携带倍率区 `scaling_terms`**（`mode = character_direct`）：倍率与属性分别是 `scaling_terms` 的 `coefficient` 与 `attribute_key`，两者各自独立可修饰；请求仍不得携带 `flat_base_damage`——星烁公式没有普通"固定基础伤害"位置，固定加值落在直伤星烁羽毛区；
- `mode = character_direct` 用于直伤星超导；`mode = reaction_composite` 已随星扩散（`reaction.stellar_swirl`）启用，承担逐参与者结算与 `0.60 / 0.30 / 0.05 / 0.05` 稳定权重聚合，星超导 occurrence 不使用该模式。复合模式的倍率区基线是参与者自己的反应基础值（等级系数，观察期冻结），因此**不得携带请求级 `scaling_terms`**。

结算器分支（`StellarReactionDamageFormula`，已注册进默认公式注册表）：

- 公式按**位置**组装，每个位置的值 = 机制侧冻结基线（或面板读取）+ Σ(该位置槽位修饰项)。倍率区复用 `StandardScalingZonePolicy`（不自行预乘属性），暴击区复用 `CriticalZonePolicy`，抗性区复用 `StandardResistancePolicy`；
- 星烁基础系数、星烁基础增伤、星烁增伤、星烁大权区、直伤星烁羽毛区与星烁擢升的**基线**取自 `StellarReactionDamageInput` 的强类型字段；字段只承载机制侧冻结基线，不再是这些位置数值的唯一来源；
- 元素精通自来源属性实时读取（`mastery_bonus = 6 * EM / (EM + 2000)`），暴击沿用注入式 `CriticalDecisionProvider`，目标抗性按当前目标抗性分段函数实时读取（有效抗性 = 面板抗性 + Σ `resistance_add`）；三者均生成独立审计与面板读取词条；
- 结算结果写入 `DamageResult.stellar_reaction_resolution`，携带括号值、各槽位三段审计（冻结基线 / Σ修饰项 / 合并值）、面板词条、暴击区、抗性区与属性 trace；`DamageResult` 只有星烁公式可以携带该审计；
- `DAMAGE_RESOLVED` 的完整审计载荷（`to_audit_dict`）在 `reaction` 下以 `kind: "stellar"` 序列化各槽位合并值、槽位三段审计、元素精通、暴击与抗性审计。扁平结果把括号值写进 `base_damage`（与月曜同构），暴击、抗性与擢升留在各自乘区字段，不再出现"没有字段承载的乘区"。

直伤星烁区间顺序（十个位置）：

```text
direct_stellar_damage =
  (
    (attribute_value * coefficient)                        # 位置 1、2 倍率与属性
    * stellar_base_multiplier                              # 位置 3 星烁基础系数
    * (1 + stellar_base_bonus)                             # 位置 4 星烁基础增伤
    * (1 + 6 * elemental_mastery / (elemental_mastery + 2000) + stellar_bonus)  # 位置 5 精通和增伤区
    * stellar_authority_multiplier                         # 位置 6 星烁大权区
    + direct_stellar_feather_addition                      # 位置 7 直伤星烁羽毛区
  )
  * (1 + crit_rate * crit_damage)                          # 位置 8 暴击区
  * resistance_multiplier                                  # 位置 9 抗性系数
  * (1 + stellar_ascension_bonus)                          # 位置 10 星烁擢升
```

其中 `attribute_value * coefficient` 是倍率区合并值（`StandardScalingZonePolicy` 结果），其余位置按「基线 + Σ」合并。星烁**没有防御区**（月曜/星烁系剧变无视防御），`defense_reduction` / `defense_ignore` 永不对星烁开放。

- 直伤星烁不能产生元素附着，也没有普通攻击、重击、下落攻击、元素战技或元素爆发伤害类型标签；
- **十个位置全部可通过槽位账单被修饰**，星烁专属字段只承载机制侧冻结基线，不通过内容侧预乘或预换算写入：
  - 位置 1 倍率：`component_coefficient_percent_add` / `component_coefficient_flat_add`（复用通用阶段，需绑定 `component_key`）；
  - 位置 2 属性：由属性系统内部修饰负责，不外溢到伤害侧；
  - 位置 3 星烁基础系数：`stellar_base_multiplier_add`，`fsum` 汇总后**加算**到冻结系数（乘数型基线），不替换基线；
  - 位置 4 星烁基础增伤：`stellar_base_bonus_add`，并入 `(1 + Σ)` 括号；
  - 位置 5 精通和增伤区：`stellar_reaction_bonus_add`，并入 `stellar_bonus`；
  - 位置 6 星烁大权区：`stellar_authority_multiplier_add`，加算到大权区乘数；
  - 位置 7 直伤星烁羽毛区：`stellar_feather_addition_add`，并入括号内末项；
  - 位置 8 暴击区：`crit_rate_add` / `crit_damage_add`（复用通用阶段）；
  - 位置 9 抗性系数：`resistance_add`（复用通用阶段），有效抗性 = 面板抗性 + Σ；
  - 位置 10 星烁擢升：`stellar_ascension_bonus_add`，并入 `(1 + Σ)` 括号，多个来源互相加算；
- 星烁公式 `allowed_modifier_stages` 是「6 个星烁专属阶段 + 5 个共享通用阶段（倍率位两个、暴击位两个、抗性位一个）」的合集；普通阶段的其余项、以及剧变专属阶段都不得进入星烁公式，反之星烁专属阶段也不得进入剧变、月曜或通用公式，越界由阶段校验在入公式前拒绝；
- 公式实现无状态，不读取 Buff、ReactionState 或协调器；暴击沿用注入式 `CriticalDecisionProvider`；
- 角色直伤技能经 `DamageRequestHandler` 的 `stellar_reactions`（按目标映射的 `StellarReactionDamageInput`）输入通道提交，倍率区由对应 `DamageImpactSpec.scaling_terms` 声明；对应 ImpactRequest 的 DamageProfile 必须选择星烁公式；
- `reaction_composite` 的逐参与者结算、稳定排序与权重聚合已由星扩散接入，详见[星扩散反应契约](星扩散反应契约.md)第 7 节。

## 9. 事务、事实与错误边界

星超导候选、极星辉域 State/Space 创建与刷新、计数 State 变更、结算根与到期移除均使用 `prepare -> validate -> commit`。State、Space 与事实的前值/版本任一 stale 时，整批失败且不得部分提交；State 与 Space binding 不一致由 `validate_polestar_field_space_bindings` / `validate_polestar_field_space_terminalizations` 在提交前拒绝。辉映·星烁 Buff 与领域来源减抗的申请/移除计划随星超导触发的元素交互批次准备、跨领域统一校验后原子提交，Buff 事实在状态提交后发布；4 秒结算后的辉映 Buff 数值刷新在同一结算收尾内 `prepare -> validate -> commit`。

必须记录通用 `REACTION_OCCURRED`、`REACTION_STATE_CHANGED` 和 `ELEMENTAL_INTERACTION_RESOLVED`；周期结算不伪造 occurrence。同一 `record_ref` 重复记录、窗口外结算、刷新缩短存在时间、非冰雷附着元素都是显式失败；领域外目标与被排除的触发攻击是正常不计数结果。

## 10. 当前非目标与验收入口

契约不包含：

- 星扩散的完整行为语义：星辉风旋、反应星扩散·风/冰与 `reaction_composite` 的生产启用已由[星扩散反应契约](星扩散反应契约.md)独立承载；
- 角色直伤星超导的正式 content 技能模组（桑多涅、奥黛塔等角色资产接入）；
- `420` 帧、`240` 帧、延续 `60` 帧、半径 `12` 的精确数值冻结；当前为来源化实现基线，半径来源尚未完全确定，不作为正式数值 golden case；
- 辉映 Buff 与领域减抗的动态进出判定（主体移动进入/离开领域不实时增减 Buff，与领域减抗按触发时刻条件处置一致）。
