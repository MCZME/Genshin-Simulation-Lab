# 内容包结构约定

> 状态：已确认约定。
> 本文记录角色、武器、圣遗物 content 包结构的已确认结论。
> content 层稳定架构见[内容系统设计](../../架构/内容系统设计.md)。
> 版本语义见[内容版本约定](./内容版本约定.md)。
> 相关讨论仍在进行；未写入本文的内容一律视为未确认。

最后更新：2026-08-07。

## 1. 文档定位

本文回答：

- 角色、武器、圣遗物 content 包如何组织
- 三类内容共用哪些包结构规则
- 因内容类型不同而产生的目录与职责差异
- `version` 在包内的最小写法
- `__init__.py` 导出风格

本文不回答：

- 单内容机制实现规范与机制白名单
- 按技能 / 效果二次拆分时的目录与命名细则
- 圣遗物内部是否再按套装或其他方式细分
- 武器类型目录的具体英文命名清单
- registry 注册与资产绑定规则
- UI 限制实现细节

## 2. 共用规则

以下规则适用于角色、武器、圣遗物 content 包。

### 2.1 第一层文件以职责为主

第一层文件按**职责**组织，不按单个技能或单个效果名作为默认第一层语言。

允许在职责文件内部，或在某一职责明显变复杂后，再做内部二次拆分。
二次拆分是后续组织手段，不改变“第一层以职责为主”的默认方式。

### 2.2 最小文件集为半固定

| 文件 | 要求 |
| --- | --- |
| `content.py` | 必须有 |
| 其他文件 | 可选，按需要创建 |

说明：

- `content.py` 是内容包的固定身份入口。
- 角色包的稳定身份键（handler/action/impact key）与帧表、伤害数据统一放在
  `data.py`。
- 不要求每个内容包预先创建完整空模板。
- 没有对应职责时，不必创建空的可选文件。

### 2.3 常用可选职责文件命名

当内容包需要对应职责时，使用以下常用文件名：

| 文件 | 职责方向 | 说明 |
| --- | --- | --- |
| `actions.py` | 动作解释与 Action 定义 | 角色常用；不是武器 / 圣遗物的常用默认文件 |
| `data.py` | 稳定键、帧表与伤害数据 | 角色常用；身份键、帧表、动作表、输入映射与伤害数据独立于解释逻辑 |
| `impacts.py` | 影响契约编译与影响展开 | 三类都可按需使用；角色包在内容编译期把资产倍率编译为伤害/附着/治疗契约，运行期把影响点展开为 `ImpactRequest` |
| `state.py` | 专属运行态 | 三类都可按需使用 |
| `hooks.py` | 事件钩子 | 三类都可按需使用 |
| `modifiers.py` | 属性或伤害等修饰贡献 | 三类都可按需使用 |

说明：

- 这些文件仍然可选，不是每个内容包都必须创建。
- 这是第一层职责文件的常用命名，不要求现在按技能或效果拆分。

### 2.4 `version` 放在 `content.py`，并写入 contribution

内容包的 `version` 声明放在 `content.py`。

已确认的最小写法：

1. 在 `content.py` 使用模块级常量声明，例如 `VERSION = "dev-action"`。
2. 内容包工厂（`create_*_content_unit`）创建 `ContentUnit` 时写入正式字段 `version`。
3. 组装后通过 `ContentUnit.version` 读取。

更完整的版本语义与用途边界见[内容版本约定](./内容版本约定.md)。

### 2.5 `__init__.py` 使用窄导出，且不固定导出清单

内容包 `__init__.py` 采用**窄导出**。

包根只对外暴露少量稳定入口；内部实现符号需要时从对应子模块导入，不默认从包根大量导出。

不规定固定的最小导出清单。各内容包按需要自行决定包根暴露哪些少量入口，只要保持窄导出风格。

## 3. 角色包

### 3.1 目录

正式角色 content 保留地区层目录：

```text
content/characters/<region>/<character>/
```

示例：

```text
content/characters/mondstadt/barbara/
```

测试专用角色固定放在：

```text
content/characters/testing/<name>/
```

示例：

```text
content/characters/testing/runtime_probe/
```

测试角色不进入 `<region>/<character>/` 正式地区目录。

### 3.2 角色侧补充

- 角色包可以按需提供 `actions.py`，用于动作解释与 Action 定义。
- 角色包的其他结构规则直接使用第 2 节共用规则。

## 4. 武器包

### 4.1 大体沿用共用规则

武器 content 包**大体沿用**第 2 节共用规则，不另起一套平行的包组织哲学。

### 4.2 目录按武器类型分组

正式武器 content 按武器类型分组，处理方式与角色按地区分组类似：

```text
content/weapons/<weapon_type>/<weapon>/
```

示例：

```text
content/weapons/sword/splendor_of_tranquil_waters/
```

说明：

- `<weapon_type>` 是组织层，类似角色的 `<region>`。
- 查找与绑定仍通过 `handler_key`，不依赖目录路径。
- 本文确认“按武器类型分组”这一组织方式；各类型目录的具体英文名另可在实现时按现有资产/习惯落地，不在此展开成完整清单。

测试专用武器固定放在：

```text
content/weapons/testing/<name>/
```

测试武器不进入 `<weapon_type>/<weapon>/` 正式类型目录。

### 4.3 武器侧边界

- 武器包仍然产出 `ContentUnit`，通过 `handler_key` 绑定。
- 武器不提供角色动作解释器，也不把“提供角色动作解释器”作为默认包职责。
- `actions.py` 不是武器包的常用默认文件。

## 5. 圣遗物包

### 5.1 大体沿用共用规则

圣遗物 content 包**大体沿用**第 2 节共用规则，不另起一套平行的包组织哲学。

### 5.2 顶层目录

圣遗物不进入角色或武器目录，放在：

```text
content/artifacts/...
```

测试专用圣遗物固定放在：

```text
content/artifacts/testing/<name>/
```

### 5.3 圣遗物侧边界

- 圣遗物包仍然产出 `ContentUnit`，通过 `handler_key` 绑定。
- 圣遗物不提供角色动作解释器，也不把“提供角色动作解释器”作为默认包职责。
- `actions.py` 不是圣遗物包的常用默认文件。
- 圣遗物内部是否再按套装名等方式细分，尚未确认。

## 6. 明确排除的理解

以下理解不属于本文约定：

- 内容包默认采用宽导出，从包根大量暴露内部 key、类与实现细节
- 为所有内容包规定同一套固定 `__all__` / 导出清单
- 默认以 `normal_attack.py` / `skill.py` / `burst.py` 等作为第一层组织方式
- 每个内容包一开始就必须具备全套固定文件
- 把“允许以后再拆”理解成现在必须按技能或效果拆
- 把常用可选文件名理解成每个内容包都要预建空文件
- 测试内容与正式内容混放
- 为武器、圣遗物另造一套与共用规则完全不同的包组织哲学
- 要求武器、圣遗物使用 `characters/<region>/...` 目录
- 要求武器、圣遗物默认提供 `actions.py` 或角色动作解释器
- 把武器类型目录理解为查找或绑定依据，替代 `handler_key`
