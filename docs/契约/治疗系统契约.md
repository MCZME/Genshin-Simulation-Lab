# 治疗系统契约

> 状态：第一版已实现，当前契约覆盖阶段 A-C。
> 本文档固定治疗系统的公共数据模型、数值公式、错误语义、事件载荷和生命系统 adapter。架构背景见[治疗系统设计](../架构/系统/治疗系统设计.md)，实施记录见[治疗系统实现规划](../工程/治疗系统实现规划.md)。

最后更新：2026-07-13

## 1. 适用范围

本契约适用于：

- `core/systems/healing/` 的公开请求、结果、错误和 handler。
- `HEALING_RESOLVED` 的 payload 与默认事件规则。
- `HealingResult -> CharacterHealingApplication` 的字段映射。
- `application/assembly` 对治疗运行时的组装与暴露。
- 治疗模型、公式、事件、生命提交和结果持久化测试。

本契约不定义真实角色倍率、目标选择、周期调度、生命之契、复活或 `ImpactKind.HEAL` payload。

## 2. 通用规则

- 第一版治疗来源和目标都必须是 `AttributeSubjectKind.CHARACTER`。
- 主体身份使用 `AttributeSubjectRef`，不得使用显示名称。
- 百分比使用小数倍率，例如 20% 保存为 `0.2`。
- 数值统一保存为 `float`；`bool` 不得作为数字。
- NaN、正负无穷和转换溢出必须在模型或公式边界转换为治疗系统结构化错误。
- 集合字段进入模型后冻结为 `tuple` 或 `frozenset`。
- core 不进行显示舍入；显示格式化属于 UI 或 analysis。
- `-0.0` 统一规范为 `0.0`。

## 3. 请求模型

### 3.1 `HealingScalingTerm`

```text
HealingScalingTerm
├── component_key: str
├── attribute_key: AttributeKey
└── coefficient: float
```

校验规则：

- `component_key` 必须是非空字符串。
- `attribute_key` 必须是已登记的公共属性 key。
- `coefficient` 必须是有限非负数。
- 同一属性可以在一次请求中出现多次，但每个 component 独立审计。

### 3.2 `HealingRequest`

```text
HealingRequest
├── healing_id: str
├── frame: int
├── source_ref: AttributeSubjectRef
├── target_ref: AttributeSubjectRef
├── scaling_terms: tuple[HealingScalingTerm, ...]
├── flat_healing: float
├── source_context: RuntimeSourceRef | None
└── tags: frozenset[str]
```

校验规则：

- `healing_id` 必须是非空稳定标识，并透传到事件和生命变化的 `change_id`。
- `frame` 必须是非负整数，`bool` 不合法。
- `source_ref` 和 `target_ref` 第一版都必须是角色主体。
- `scaling_terms` 允许为空，但成员必须全部是 `HealingScalingTerm`。
- 单次请求内的 `component_key` 不能重复。
- `flat_healing` 必须是有限非负数。
- `source_context` 提供时必须是 `RuntimeSourceRef`。
- `tags` 中的值必须是非空字符串。
- `scaling_terms` 为空且 `flat_healing == 0` 是合法零治疗请求。

请求不得携带当前生命、最大生命、有效恢复量或未应用量。

## 4. 结果模型

### 4.1 `HealingComponentResult`

```text
HealingComponentResult
├── component_key: str
├── attribute_key: AttributeKey
├── scaling_value: float
├── coefficient: float
└── value: float
```

结果顺序必须与请求中的 `scaling_terms` 顺序一致。

### 4.2 `HealingResult`

```text
HealingResult
├── healing_id: str
├── frame: int
├── source_ref: AttributeSubjectRef
├── target_ref: AttributeSubjectRef
├── component_results: tuple[HealingComponentResult, ...]
├── flat_healing: float
├── base_healing: float
├── outgoing_healing_bonus: float
├── incoming_healing_bonus: float
├── healing_bonus_multiplier: float
├── final_healing: float
├── source_context: RuntimeSourceRef | None
└── tags: frozenset[str]
```

规则：

- 结果不可变。
- `base_healing`、`healing_bonus_multiplier` 和 `final_healing` 必须有限且非负。
- 单个治疗加成允许为负数。
- `final_healing` 是理论治疗量，不因目标当前生命或最大生命改变。
- 结果不包含 `hp_before`、`hp_after`、`effective_amount` 或 `unapplied_amount`。

### 4.3 `HealingApplicationRecord`

```text
HealingApplicationRecord
├── request: HealingRequest
├── result: HealingResult
└── health_result: CharacterHealthChangeResult
```

只有生命提交成功时才加入 `HealingRequestHandler.records`。生命提交失败时，已经发布的 `HEALING_RESOLVED` 仍保留，但不产生 application record。

## 5. 数值公式

每个 component：

```text
ComponentValue[i] = ScalingValue[i] * Coefficient[i]
```

基础治疗与最终治疗：

```text
BaseHealing = fsum(ComponentValue) + FlatHealing

HealingBonusMultiplier =
    1
    + OutgoingHealingBonus
    + IncomingHealingBonus

FinalHealing = BaseHealing * HealingBonusMultiplier
```

属性来源：

| 数值 | 查询主体 | 属性 key |
| --- | --- | --- |
| `ScalingValue[i]` | `source_ref` | `scaling_terms[i].attribute_key` |
| `OutgoingHealingBonus` | `source_ref` | `bonus.healing.outgoing` |
| `IncomingHealingBonus` | `target_ref` | `bonus.healing.incoming` |

查询上下文：

- 来源属性查询的 `target_ref` 是治疗目标。
- 目标受治疗加成查询的 `target_ref` 是治疗来源。
- 两类查询都透传请求的 `tags` 和 `source_context`。
- 同一次治疗使用一个 `AttributeResolutionSession`。

数值规则：

- component 按请求顺序解析和记录。
- 加法聚合使用 `math.fsum`。
- 不提前 `round()`。
- `HealingBonusMultiplier` 小于 `0` 时抛出 `InvalidHealingResultError`，不得 clamp。
- 数值转换、聚合或乘法产生溢出或非有限结果时，必须转换为治疗系统结构化错误。

通用治疗公式的机制来源见 [KQM 治疗公式](https://library.keqingmains.com/combat-mechanics/damage/healing)。真实 content 接入时仍须单独复核倍率、固定值、快照、目标和频率。

## 6. Resolver 契约

```text
HealingResolver(attribute_resolver, trace_level=TraceLevel.FULL)

resolve(request: HealingRequest) -> HealingResult
```

`HealingResolver`：

- 只读取属性并执行纯计算。
- 不发布事件。
- 不读取或修改 `HealthState`。
- 不计算有效治疗或溢出治疗。
- 任一校验或属性解析失败时不得返回部分结果。

## 7. Handler 与生命提交契约

```text
HealingRequestHandler(
    resolver,
    health_runtime,
    event_engine=None,
)
```

- `event_engine` 省略时必须复用 `health_runtime.event_engine`。
- 显式传入的 `event_engine` 必须与 `health_runtime.event_engine` 是同一实例，否则抛出 `HealingValidationError`。

`handle(request)` 固定执行：

```text
HealingResolver.resolve(request)
-> publish HEALING_RESOLVED
-> healing_result_to_application(result)
-> HealthRuntime.apply_healing(application)
-> HealingApplicationRecord
```

### 7.1 Adapter 字段映射

| `HealingResult` | `CharacterHealingApplication` |
| --- | --- |
| `healing_id` | `change_id` |
| `frame` | `frame` |
| `target_ref` | `target_ref` |
| `final_healing` | `amount` |
| `source_ref` | `source_ref` |
| `source_context` | `source_context` |
| `tags` | `tags` |

生命系统根据实时 `current_hp` 和 `stat.hp.max` 计算 `effective_amount` 与 `unapplied_amount`。治疗系统不得重新实现该逻辑。

## 8. 事件契约

### 8.1 `HEALING_RESOLVED`

```text
EventType.HEALING_RESOLVED
category = FACT
payload_type = HealingResolvedPayload
record_by_default = true
result_committed = true
mechanic_driver = true
```

```text
HealingResolvedPayload
└── result: HealingResult
```

语义：

- 表示理论治疗量已经成功结算。
- 不表示目标当前生命已经增加。
- 在生命提交前发布。
- 满血和零治疗仍发布。
- 生命提交失败不撤销该事件。

事件顺序：

```text
HEALING_RESOLVED
-> CHARACTER_HEALTH_CHANGED（仅 effective_amount > 0）
```

### 8.2 `HealingResult.to_dict()`

序列化字段固定为：

```text
healing_id
frame
source_ref: {kind, entity_id}
target_ref: {kind, entity_id}
component_results
flat_healing
base_healing
outgoing_healing_bonus
incoming_healing_bonus
healing_bonus_multiplier
final_healing
source_context: {kind, source_key, instance_id} | null
tags
```

`component_results` 保持请求顺序，`tags` 按字符串排序后输出。事件继续使用结果库通用事件 JSON，不新增治疗专用表，也不升级结果库 schema。

## 9. 结构化错误

| 错误类 | code | 用途 |
| --- | --- | --- |
| `HealingSystemError` | `healing_error` | 治疗系统错误基类 |
| `HealingValidationError` | `healing_validation_error` | 请求字段、数值或 handler 装配非法 |
| `UnsupportedHealingSubjectError` | `unsupported_healing_subject` | 来源或目标不是角色主体 |
| `InvalidHealingAttributeError` | `invalid_healing_attribute` | 属性不存在、主体不支持或解析失败 |
| `InvalidHealingResultError` | `invalid_healing_result` | 公式产生负乘数、溢出或非有限结果 |

错误通过 `detail` 暴露稳定的 `code` 和 `message`。

## 10. Application 装配契约

`SimulationAssembler` 必须：

1. 使用与 `HealthRuntime` 相同的 `AttributeResolver` 构造 `HealingResolver`。
2. 使用 `HealthRuntime` 和同一 `EventEngine` 构造 `HealingRequestHandler`。
3. 把 handler 注册到 `SimulationContext`。
4. 通过 `AssembledSimulation.healing_handler` 暴露稳定入口。

handler 不进入 `BasicRuntimeWorld.updatables`，因为第一版没有逐帧更新行为。

## 11. 测试要求

至少覆盖：

- 请求字段、主体、component 唯一性和不可变性。
- 多 component、同属性多 component、固定治疗和零治疗。
- 治疗加成与受治疗加成的同乘区计算。
- 负加成、负总乘数、NaN、无穷、超大整数和聚合溢出。
- 普通治疗、溢出治疗、满血治疗和生命提交失败。
- handler 事件引擎一致性。
- assembled handler 对真实 `HealthState` 的提交和事件顺序。
- `HEALING_RESOLVED` payload 与结果库通用 JSON 往返。

## 12. 暂缓范围

- `ImpactKind.HEAL` payload 和 dispatcher 接线。
- 队伍、范围和多目标治疗选择。
- 真实角色、武器、命座或圣遗物治疗 content。
- 周期治疗调度和快照策略。
- 生命之契、治疗禁止、吸收和转化。
- 复活、死亡和零生命治疗资格。
- 真实数值 golden case。
