# 仿真配置契约与最小闭环

> 本文档记录新项目第一版仿真配置契约与应用端 MVP 范围。
> UI 具体交互方案暂缓设计，本文只定义应用需要编辑、保存和运行的数据契约。

## 1. 配置契约目标

仿真配置用于描述一次仿真“要模拟什么”。

第一版配置契约需要满足：

- 可以由 UI 编辑。
- 可以由 CLI 运行。
- 可以由批量任务复用和变异。
- 可以被 `application/assembly/SimulationAssembler` 组装为仿真运行时对象。
- 可以长期保存，并通过 `schema_version` 做兼容处理。

配置契约不包含：

- UI 布局状态。
- 分析图表状态。
- 数据库路径。
- Flet 控件状态。
- 资产显示名作为识别依据。

## 2. 顶层结构

第一版使用 `SimulationConfig` 作为单次仿真配置。

顶层结构：

```text
SimulationConfig
├── schema_version
├── kind
├── meta
├── team
├── scene
├── input_trace
├── rules
└── run_options
```

建议 JSON 结构：

```json
{
  "schema_version": 1,
  "kind": "simulation_config",
  "meta": {
    "name": "芙宁娜测试",
    "description": ""
  },
  "team": [],
  "scene": {},
  "input_trace": [],
  "rules": {
    "enabled": []
  },
  "run_options": {
    "max_frames": 18000
  }
}
```

## 3. 身份引用规则

配置中的资产统一使用 `asset_key`。

示例：

```text
character:75
weapon:11512
artifact_set:15032
```

规则：

- 角色、武器、圣遗物套装引用 `asset_key`。
- 不使用显示名称作为仿真识别依据。
- `display_name` 可以作为辅助缓存存在，但不能参与组装判断。
- 输入轨迹记录按键输入事实，不使用角色名称。

## 4. 队伍配置

`team` 是队伍槽位列表。

组装阶段会为每个队伍槽位创建一个 `CharacterRuntimeState`，保存槽位、角色 `asset_key`、等级、命座、天赋等级和最小可变状态；`TeamRuntimeState` 通过这些角色运行态推导队伍规模与当前场上角色。

示例：

```json
[
  {
    "slot": 1,
    "character": {
      "asset_key": "character:75",
      "level": 90,
      "constellation": 2,
      "talents": {
        "normal_attack": 1,
        "elemental_skill": 10,
        "elemental_burst": 10
      }
    },
    "weapon": {
      "asset_key": "weapon:11512",
      "level": 90,
      "refinement": 1
    },
    "artifacts": {
      "sets": [
        {
          "asset_key": "artifact_set:15032",
          "pieces": 4
        }
      ],
      "stats": {}
    }
  }
]
```

第一版先支持：

- 角色资产。
- 角色等级。
- 命座。
- 天赋等级。
- 武器资产。
- 武器等级。
- 武器精炼。
- 圣遗物套装与件数。
- 圣遗物属性占位结构。

## 5. 场景配置

`scene` 描述本次仿真的当前场上角色空间起点、目标与场景条件。

敌人基础抗性/等级信息第一版不进入资产库，因此目标直接写在配置中。

第一版运行时空间使用 X/Z 平面做普通范围查询；`position.y` 保留给下落攻击等高度敏感机制，暂不参与普通半径判定。目标支持多个，但每个目标在空间层只作为简单点位靶子，不模拟复杂体型、碰撞、多 hitbox 或目标挤压。

组装阶段会为每个 `scene.targets[]` 创建一个 `TargetRuntimeState` 和一个 `target:<id>` 空间实体。目标运行态保存目标 id、等级和抗性；空间实体保存目标点位。两者通过 `spatial_entity_id` 关联。

动作层可以使用运行时空间查询候选空间实体。候选实体只表示“在本次范围查询内”，不表示最终命中、伤害结算或元素反应已经发生。

`player` 描述当前场上角色的初始空间实体；如果省略，默认位置为 `(0, 0, 0)`，朝向为 `(0, 0, 1)`。后台角色默认没有独立空间实体，切人只改变当前场上角色空间实体对应的队伍槽位。

示例：

```json
{
  "player": {
    "position": {"x": 0, "y": 0, "z": 0},
    "facing": {"x": 0, "y": 0, "z": 1}
  },
  "targets": [
    {
      "id": "target_1",
      "level": 90,
      "position": {"x": 0, "y": 0, "z": 5},
      "resistance": {}
    }
  ]
}
```

## 6. 输入轨迹

`input_trace` 描述仿真中的按键输入轨迹。

输入轨迹按帧分组，记录键盘或鼠标按钮的按下与松开。输入层只记录按键事实，不直接生成具体角色动作；战技点按、长按、切人后摇导致输入无效等行为由 `ActionManager`、当前场上角色和动作状态机解释。

示例：

```json
[
  {
    "frame": 120,
    "events": [
      {"key": "keyboard.e", "phase": "press"}
    ]
  },
  {
    "frame": 145,
    "events": [
      {"key": "keyboard.e", "phase": "release"}
    ]
  }
]
```

第一版输入轨迹只支持键盘和鼠标按钮，不支持移动键、鼠标视角、手柄或自定义键位；第 0 帧保留为仿真初始化帧，当前模拟器骨架要求输入帧号为正整数。详细草案见：[输入轨迹契约草案](./输入轨迹契约草案.md)。

## 7. 规则配置

`rules` 用于保存本次仿真的额外规则或开关。

第一版保留结构，但不急于扩展复杂规则系统。

示例：

```json
{
  "enabled": []
}
```

## 8. 运行选项

`run_options` 保存仿真运行控制项。

第一版保留：

```json
{
  "max_frames": 18000
}
```

确认决策：

- 不设置 `mode`。
- 所有仿真都保存完整结果数据。
- 不区分 `summary_only` 和 `recorded`。
- 结果数据体积通过结果清理、归档或会话管理策略处理。

未来可考虑加入：

- 随机种子。
- 结果标签。
- 运行备注。

## 9. ProjectConfig 与 SimulationConfig 的关系

`SimulationConfig` 只描述一次仿真。

未来可以设计 `ProjectConfig`，用于保存：

- 多个仿真配置。
- UI 工作区信息。
- 最近分析会话。
- 项目级模板。

但 `SimulationConfig` 本身应保持干净，避免混入 UI 状态。

## 10. 第一版 MVP

第一版应用端 MVP 定为最短闭环：

1. 创建或编辑一个 `SimulationConfig`。
2. 选择角色、武器和基础圣遗物构建。
3. 编辑输入轨迹。
4. 运行一次仿真。
5. 保存完整仿真结果数据。
6. 查看摘要结果。

第一版 MVP 暂不强制包含：

- 完整战斗复盘。
- 参数扫描。
- 多结果对比。
- 配置模板库。
- 复杂 UI 工作区。

这些能力作为后续阶段扩展，并以当前配置契约为基础。
