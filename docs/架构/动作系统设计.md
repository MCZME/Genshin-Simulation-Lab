# 动作系统设计

> 状态：正式规范。
> 本文描述动作系统：它把输入会话解释成可运行的动作实例，并在动作期间产生机制影响请求；包括解释器与实例的职责边界、准入与中断、影响点分发及内容组装。
> 最后更新：2026-09-05。

## 1. 定位

动作系统负责把已经编译的输入会话解释为可运行、可审计的动作实例，并在动作运行期间产生机制影响请求。

核心原则：

- 动作系统消费已经编译好的输入会话计划，不定义 `input_trace` JSON 结构。
- `ActionManager` 是动作系统唯一运行时入口和动作实例拥有者。
- `ActionManager` 不硬编码切人键、攻击键或具体角色动作含义。
- 动作解释器负责判断“当前应该做什么”，不直接执行动作或修改动作实例。
- 元素战技与元素爆发解释器通过只读协调端口查询冷却和标准元素能量公共条件，不直接拼接领域裸状态。
- `Action` 定义具体动作逻辑，`ActionInstance` 保存一次动作的可变运行态。
- 所有被接受的动作都创建 `ActionInstance`，包括切人。
- 动作产生 `ActionImpactPoint`，由 Impact 系统展开为具体机制请求。

目标流程：

```text
InputSessionTrace
-> ActionManager
-> ActionInterpreterRegistry
-> ActionInterpreter
-> CharacterAbilityConditionPort（仅 E/Q 公共条件）
-> ActionInterpretationResult
-> ActionManager
-> ActionRegistry
-> ActionInstance(Action)
-> ActionImpactPoint
-> ImpactRuntime
-> ImpactFactory
-> ImpactRequestDispatcher
-> mechanics / systems / space
```

## 2. 模块划分

`core/actions` 是动作系统的领域包，按职责拆分：

- `enums.py`：动作领域枚举。
- `models.py`：数据模型与规格（`TargetingSpec`、影响点、动作实例、执行上下文等）。
- `interpreters.py`：解释器协议、选择器与解释器注册表。
- `protocols.py`：`Action` 实现协议与 `ActionRegistry`。
- `actions.py`：通用定时动作、切人动作与队伍解释器。
- `manager.py`：`ActionManager` 运行时编排（输入会话、准入、实例与影响点）。
- `helpers.py`：内部校验与参数辅助。

## 3. 输入会话消费边界

动作系统从 `ActionManager` 持有的 `InputSessionTrace` 开始工作。输入 trace 的编译、`InputSessionPlan` / `InputSessionBoundary` / `InputSessionView` 等数据结构、PRESS / HOLD / RELEASE 语义与输入事件发布由按键输入系统维护，动作系统不重复定义。

动作系统只依赖以下边界：

- `InputSessionTrace.boundaries_at(frame)` 提供当前帧 PRESS / RELEASE 边界。
- `ActionManager` 在 PRESS 时解析并固定 `InterpreterBinding`。
- `ActionManager` 为解释器构造当前帧只读 `InputSessionView`，不提前暴露未来 release 信息。
- 解释器不得请求开始帧早于当前仿真帧的动作。

`RuntimeInputSession` 是 `ActionManager` 的内部运行态，不属于外部配置契约。它的物理状态、控制状态与触发语义由按键输入系统维护；动作系统只通过 `session_policy`、`bound_instance_id` 和 owner 取消接口影响该运行态。

## 4. 解释器体系

### 4.1 注册与绑定

`ActionManager` 不通过条件分支判断切人还是角色动作，而是使用 `ActionInterpreterRegistry` 解析输入键对应的解释器。第一版 selector 包括队伍级 `TeamInterpreterSelector` 与当前场上槽位对应的 `ActiveCharacterInterpreterSelector`；同一按键只能注册一个确定 selector，不使用带隐藏优先级的责任链。

`InterpreterBinding` 在 PRESS 时解析一次并写入运行时会话，固定解释器、owner 与 scope。HOLD、RELEASE 和 CANCEL 始终回到同一解释器，不因当前 `active_slot` 改变而重新路由。

组装阶段必须校验：配置允许出现的输入键都存在 selector、键不重复注册、真实角色槽位存在角色解释器、测试解释器不充当真实角色默认降级；找不到解释器或动作实现时在组装阶段报错。

### 4.2 解释职责

解释器负责判断：

- 当前输入对应哪个动作。
- 当前角色、队伍、资源、冷却和状态是否允许。
- 应继续等待、拒绝、启动动作还是控制已有动作。
- 为动作准备哪些参数和初始状态。

解释器不创建 `ActionInstance`、不获取或释放动作锁、不直接修改动作实例或状态、不执行动作逻辑、不直接产生伤害/治疗/状态变化。动作是否从 PRESS、HOLD 或 RELEASE 开始由对应解释器决定，通用层不设置统一开始规则。

解释结果一次只包含一个主指令：`wait` / `reject` / `start_action` / `control_action`。被拒绝时记录结构化拒绝；启动动作时提交 `PreparedAction`；控制已有实例时提交语义化 `ControlActionRequest`，命令不携带物理按键语义。

### 4.3 角色能力公共条件

元素战技与元素爆发的公共条件由 `CharacterAbilityConditionCoordinator` 组合，角色解释器只经 `CharacterAbilityConditionPort` 查询，不直接访问冷却或能量 Runtime：

- 元素战技要求冷却有可用 charge。
- 标准元素爆发要求冷却有可用 charge 且元素能量已满。
- `capacity = 0` 的爆发把私有资源条件委托给 content，不按标准能量不足拒绝。
- 解释器继续判断姿态、角色私有状态与专属资源。
- `ActionManager` 继续执行锁、中断、owner、会话与实例创建的最终准入。

协调器结果不是 reservation。解释器构造 `PreparedAction` 后，冷却实际启动与爆发实际扣能仍由具体能力时序分别提交。

## 5. Action 与运行实例

### 5.1 Action 与 ActionRegistry

`Action` 是无独立运行身份的具体动作逻辑，应尽量保持不可变；每次执行的可变状态由 `ActionInstance.action_state` 保存。`Action` 定义 `admission_policy` 与 `on_start` / `on_update` / `on_command` / `on_cancel` / `on_finish` 等钩子。

所有 `Action` 在组装阶段注册进 `ActionRegistry`。解释器只返回 `action_key` 与准备参数，不直接构造任意 Action 对象；`ActionManager` 从注册表获得 Action 后创建实例。第一版注册表直接保存不可变 Action 定义，不引入 ActionFactory。

`action_key` 是运行时动作实现身份，不使用显示名称，也不等同于资产 `asset_key` 或装配入口 `handler_key`。组装阶段必须检查 action key 非空且唯一、解释器声明的 `supported_action_keys` 全部已注册、动作声明的 impact key 已注册 factory 或明确不产生 impact。

### 5.2 ActionInstance

所有被接受并执行的动作都创建 `ActionInstance`。实例保存动作身份、owner、来源会话、开始帧、生命周期、`action_state`、参数、待处理命令与影响点等一次运行的可变状态。

实例生命周期为 `scheduled / running / completed / canceled`；被拒绝的动作请求不创建实例，只记录 `ActionDecision`。

`Action` 不直接修改实例生命周期。它接收只读 `ActionExecutionContext` 并返回结构化 `ActionExecutionResult`（新状态、影响点、生命周期指令、记录与取消原因）；只有 `ActionManager` 可以应用结果并改变实例生命周期。

### 5.3 输入控制与实例推进

HOLD / RELEASE 始终先交给输入会话绑定的解释器：尚未创建实例时解释器返回等待、拒绝或启动请求；已绑定实例时返回 `ControlActionRequest`，由 `ActionManager` 路由到实例的 `on_command()`。

同时 `ActionManager` 独立逐帧推进运行实例的 `on_update()`。输入控制和动作运行是两条并行链路：Action 不直接理解原始按键，解释器也不代替 Action 推进动作时间轴。输入边界先于 HOLD、显式输入先处理、运行态随后推进；本帧刚 `on_start()` 的实例不再执行 `on_update()`。

## 6. 准入、锁与中断

动作准入分三层：

```text
CharacterAbilityConditionCoordinator -> 冷却与标准元素能量公共条件
CharacterActionInterpreter           -> content 私有条件与动作语义
ActionManager                        -> 通用运行时冲突和最终实例准入
```

公共条件通过不等于动作已接受。解释器判断内容条件，`ActionManager` 判断通用运行时冲突：开始帧与 owner 是否合法、输入会话是否有效或已绑定、新动作需要的锁是否冲突、冲突实例是否允许被当前 interrupt kind 中断、是否能够原子取消旧实例并创建新实例。

`ActionManager` 不理解“普通攻击”或“切人”的具体逻辑，只比较 `ActionAdmissionPolicy` 声明的 `required_locks` 与 `interrupt_policy`。具名锁覆盖 `team.control`、`character:1.control` 等控制域；只有争用同一锁的动作才发生冲突。所有冲突必须完整检查后原子取消并创建，不能部分取消。同帧动作请求按输入边界原始顺序处理，前一个请求产生的实例和锁对后一个请求立即可见。

具体策略值、拒绝原因与决策记录结构见[动作系统契约](../契约/动作系统契约.md)，本文不重复。

## 7. Impact 边界

### 7.1 影响点

Action 只产生 `ActionImpactPoint`，不直接创建伤害、治疗等最终机制结果。影响点携带 `impact_key`、`scheduled_frame`、`targeting`、`params` 与取消语义；状态为 `pending / dispatched / canceled`。

动作取消时，已 dispatched 的影响点不回滚；pending 影响点按 `cancel_with_action` 决定取消或继续。独立投射物或持续对象优先使用 `create_entity` 创建空间对象，之后由对象自行产生影响请求。

### 7.2 索敌与 AOE 两阶段

动作索敌与实际 AOE 命中是两个阶段：`TargetingSpec` 只负责索敌候选、选择方式、瞄准目标与攻击方向，不等同于最终伤害范围；实际受击目标由 Damage Impact 的 AOE 在影响点到期时按当前空间状态解析。`resolve_on_impact` 为默认；只有明确需要锁定瞄准目标的动作才使用 `snapshot_on_emit`，且该快照不替代 AOE 到期时的目标查询。

Damage Impact 的元素、倍率、标签、AOE 语义与二维形状投影由伤害系统与战场空间维护，动作侧不重复定义。

### 7.3 ImpactRuntime 与分发

`ImpactRuntime` 负责读取到期影响点、执行索敌并确定攻击方向、经 `ImpactDispatcher` 按 `impact_key` 调用 ImpactFactory、按类型化 AOE 解析实际受击目标、冻结目标集合后产生 `ImpactRequest`，再交给 `ImpactRequestDispatcher`。

`ImpactRuntime` 不直接处理具体机制。`ImpactRequestDispatcher` 按 `ImpactRequest.kind` 分发给对应领域系统：

```text
damage                -> 伤害系统
shield                -> 护盾系统
heal                  -> 治疗系统
apply_aura            -> 元素附着系统
apply_infusion        -> 元素附魔系统
apply_status          -> 状态效果（Buff）系统
create_entity / extend_created_entity -> 创建对象运行时
energy                -> 元素能量系统
movement              -> 移动系统
```

动作完成不代表其所有影响点已经处理；停止条件还必须检查待处理影响点和机制请求。

### 7.4 下落攻击

下落攻击不使用固定时间线，也不由动作写位移：

- 空中实体由 `MovementSystem` 从速度 0 开始受重力自然下落；下坠碰撞与落地由 MovementSystem 发布事实。
- 通用 `FallPlungeAction` 在 `on_update` 读取当前帧事实：碰撞事实发出下坠碰撞影响点（每个下落过程一次），落地事实发出落地影响点并结束动作；影响点在事实帧当场发出，不预排帧。
- 位移由 `MovementSystem` 统一拥有，动作不再直接写空间位置。

## 8. 切人动作

切人是队伍级解释器产生的普通动作请求：

```text
keyboard.2 InputSession
-> TeamActionInterpreter
-> PreparedAction(action_key=team.switch, params.target_slot=2)
-> ActionManager
-> TeamSwitchActionInstance
-> TeamSwitchAction.on_start()
-> TeamRuntimeState.switch_to(2)
-> 同步 player:active
```

切人必须创建 `ActionInstance`。队伍状态修改属于 `TeamSwitchAction` 的动作逻辑；切人通常不需要 impact。

## 9. content 与组装

角色内容贡献由内容系统提供，可包含动作解释器、Action、ImpactFactory 与状态扩展等切片。组装器收集队伍解释器与通用 Action、按槽位拆分的角色解释器、所有不可变 Action 定义、ImpactFactory 与其他内容贡献，构造：

```text
InputSessionTrace
CharacterAbilityConditionCoordinator
ActionInterpretationContext provider
ActionInterpreterRegistry
ActionRegistry
ImpactDispatcher           # impact_key -> ImpactFactory
ImpactRequestDispatcher    # ImpactRequest kind -> 领域系统
ActionManager
ImpactRuntime
```

`core/` 不接触完整 `ContentRuntimeContribution`，只接收拆分后的协议实现和注册表。
