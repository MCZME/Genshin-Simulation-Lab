# 治疗系统设计

> 状态：第一版已实现，当前完成边界为阶段 C。
> 本文档描述治疗系统的职责、依赖和运行时协作。公共字段、公式、错误和序列化见[治疗系统契约](../../契约/治疗系统契约.md)，实施记录见[治疗系统实现规划](../../工程/治疗系统实现规划.md)。

最后更新：2026-07-13

## 1. 系统定位

治疗系统负责把已经明确来源和目标的治疗参数解析为理论治疗量，并把结算事实与角色生命提交串成可审计的运行时闭环。

治疗数值与当前生命必须分层：

- `HealingResolver` 只计算理论治疗量。
- `HealthRuntime` 只根据实时生命状态应用已结算恢复量。
- `HealingRequestHandler` 编排事件发布与生命提交，但不直接写状态。

这种分层保证满血、溢出治疗和生命提交失败不会污染治疗公式，也保证当前生命仍只有一个受控写入口。

## 2. 职责边界

治疗系统负责：

- 解析来源角色的一个或多个缩放属性。
- 解析治疗加成与目标受治疗加成。
- 形成不可变理论治疗结果和公式审计。
- 发布 `HEALING_RESOLVED`。
- 把理论结果转换为生命系统请求。

治疗系统不负责：

- 保存或直接修改 `HealthState`。
- 计算有效治疗、溢出治疗或生命上限裁剪。
- 选择队伍目标、范围目标或多目标顺序。
- 调度周期治疗或决定快照时机。
- 处理生命之契、治疗禁止、治疗吸收、复活或死亡。
- 定义具体角色、武器、命座或圣遗物数值。

## 3. 模块与依赖

治疗实现位于：

```text
core/systems/healing/
├── models.py
├── errors.py
├── resolver.py
├── handler.py
└── __init__.py
```

模块职责：

- `models.py`：公开请求、结果和编排记录。
- `resolver.py`：属性查询和纯公式计算。
- `handler.py`：事件发布、adapter 和生命提交。
- `errors.py`：稳定错误体系。

依赖方向：

```text
application/assembly
    -> core/systems/healing
    -> core/systems/health

core/systems/healing/resolver
    -> core/attributes

core/systems/healing/handler
    -> core/events
    -> core/systems/healing/resolver
    -> core/systems/health 公共 API
```

禁止反向依赖：

- `core/systems/health` 不依赖治疗公式或 resolver。
- `core/systems/healing` 不依赖 assets、content、application、infrastructure 或 UI。
- content 不得绕过 handler 或 `HealthRuntime` 直接修改角色当前生命。

## 4. 运行时数据流

第一版入口是已经类型化且目标明确的单目标请求：

```text
HealingRequest
-> HealingRequestHandler
-> HealingResolver
-> HealingResult
-> HEALING_RESOLVED
-> CharacterHealingApplication
-> HealthRuntime.apply_healing()
-> CharacterHealthChangeResult
```

`HealingResolver` 在一次属性解析 session 中读取全部公式输入。它不接触事件引擎和生命状态，任一校验或属性错误都不会产生部分结果。

`HealingRequestHandler` 固定先发布理论结算事实，再调用生命系统。handler 与 `HealthRuntime` 必须共享同一个 `EventEngine`，避免治疗事实与生命变化被拆到不同事件流。

## 5. 状态所有权

治疗系统没有独立可变状态：

- 理论治疗结果是不可变值对象。
- 当前生命由 `CharacterRuntimeState.health` 保存。
- 最大生命由 `AttributeResolver` 查询 `stat.hp.max`。
- handler 的 records 只保存已经成功完成生命提交的编排记录快照。

有效恢复量与未应用量只能由生命系统根据提交时的实时状态确定。治疗结果不得复制这些字段。

## 6. 事件语义

`HEALING_RESOLVED` 是 `FACT` 事件，表达理论治疗已经完成结算，不表达生命已经增加。

事件顺序为：

```text
HEALING_RESOLVED
-> CHARACTER_HEALTH_CHANGED（仅生命真实增加时）
```

由此得到：

- 满血治疗仍有 `HEALING_RESOLVED`，没有虚假生命变化事件。
- 零治疗仍可保留理论结算事实。
- 溢出治疗不修改 `HealingResult.final_healing`。
- 生命提交失败不撤销已经发布的理论结算事实。

具体 EventSpec、payload 和 JSON 字段见[治疗系统契约](../../契约/治疗系统契约.md)。

## 7. Application 组装

`SimulationAssembler` 使用同一属性运行时和事件引擎构造：

```text
AttributeResolver
-> HealingResolver

HealingResolver + HealthRuntime + EventEngine
-> HealingRequestHandler
```

handler 注册到 `SimulationContext`，并通过 `AssembledSimulation.healing_handler` 暴露。第一版 handler 没有逐帧行为，不进入 `BasicRuntimeWorld.updatables`。

## 8. 扩展边界

### 8.1 真实 content 与目标选择

`ImpactKind.HEAL`、content payload 和目标选择属于后续阶段 D。上游负责把一次队伍或范围治疗拆成稳定顺序的单目标 `HealingRequest`；resolver 和 handler 继续保持单目标语义。

### 8.2 周期治疗与快照

持续时间、触发频率和快照时机由 content 或机制运行时决定。治疗系统只按请求帧解析一次请求，不创建逐帧任务。

### 8.3 治疗拦截

生命之契、治疗禁止、吸收和转化位于理论结果与生命提交之间：

```text
HealingResult
-> HealingInterceptionRuntime
-> CharacterHealingApplication
-> HealthRuntime
```

拦截层不得进入 `HealthState`，也不得要求 `HealingResolver` 查询当前生命。

### 8.4 生存状态

复活、死亡和零生命治疗资格属于后续生存状态系统。生命值为 `0` 本身不在治疗公式中推导死亡语义。

## 9. 当前完成边界

阶段 A-C 已完成：模型与公式、resolver、治疗事件、handler、生命提交闭环、assembler 暴露和通用事件持久化均已落地。

阶段 D 尚未开始，范围包括真实 content、目标分发、`ImpactKind.HEAL` 接线和真实数值 golden case。具体任务和验证记录见[治疗系统实现规划](../../工程/治疗系统实现规划.md)。
