# 资产数据库设计

> 本文档记录新项目第一版资产数据库的设计决策。
> 资产数据库用于保存角色、武器、圣遗物、技能倍率与效果参数等基础资产数据。

## 1. 设计目标

新项目的资产数据库用于替代旧项目中的 MySQL 静态资产库。

第一版目标：

- 使用本地数据库，便于离线运行与随应用分发。
- 保存角色、武器、圣遗物等仿真所需基础数据。
- 支持技能倍率、武器特效、命座、天赋、圣遗物效果等半结构化数据。
- 为 UI 提供资产列表与基础展示数据。
- 为仿真组装阶段提供稳定、明确的数据读取接口。
- 避免让仿真核心直接依赖 SQLite、SQL 或 UI 层。

## 2. 非目标

第一版暂不处理：

- 敌人基础抗性/等级信息。
- 多语言文本。
- 用户自定义资产。
- 在线资产更新。
- 复杂数据库迁移系统。
- 原始抓取数据归档表。

原始抓取数据不写入主资产库。如需追溯，可由导入流程在库外保存文件或缓存。

## 3. 数据库选型

第一版主资产库使用 SQLite。

资产库文件作为只读生成产物存在，例如：

```text
data/assets/assets.db
```

应用运行时只读使用该数据库，不直接修改主资产库。

## 4. 总体分层

资产库采用“结构化索引表 + JSON 半结构化负载”的混合模型。

核心分为两层：

- Index 层：保存 UI 和仿真经常查询的稳定字段。
- Payload 层：保存技能倍率、武器效果、命座、天赋、圣遗物效果等非标准结构。

数据库保存数据、参数和处理器标识；复杂行为逻辑仍由仿真代码实现。

## 5. 第一版表结构

第一版暂定表：

```text
asset_db_meta
asset_import_runs
characters
character_level_stats
weapons
weapon_level_stats
artifact_sets
artifact_set_bonuses
talent_scaling_entries
effect_payloads
```

### 5.1 `asset_db_meta`

保存当前资产库元信息。

建议字段：

```text
key    TEXT PRIMARY KEY
value  TEXT NOT NULL
```

建议内容：

```text
schema_version
data_version
importer_version
built_at
source_name
source_version
content_hash
```

### 5.2 `asset_import_runs`

记录资产库生成过程。

建议字段：

```text
id
source_name
source_version
schema_version
data_version
importer_version
imported_at
note
```

第一版每次整体重建资产库，因此该表不承担原始数据归档职责。

### 5.3 `characters`

角色基础索引表。

建议字段：

```text
asset_key    TEXT PRIMARY KEY
source_id    TEXT NOT NULL
name         TEXT NOT NULL
element      TEXT NOT NULL
weapon_type  TEXT NOT NULL
rarity       INTEGER NOT NULL
handler_key  TEXT NULL
```

### 5.4 `character_level_stats`

角色等级属性表。

建议字段：

```text
character_key     TEXT NOT NULL

base_def          REAL NOT NULL
```

### 5.5 `weapons`

武器基础索引表。

建议字段：

```text
asset_key    TEXT PRIMARY KEY

```

### 5.6 `weapon_level_stats`

### 5.7 `artifact_sets`

建议字段：

```text

```

### 5.8 `artifact_set_bonuses`

圣遗物二件套/四件套效果参数表。


`talent_key` 示例：


`owner_type` 示例：

## 6. 资产身份规则

不使用 SQLite 自增 ID 作为资产身份。

不使用显示名称作为资产身份。

配置文件与仿真组装统一引用 `asset_key`。

`asset_key` 使用 `{asset_type}:{source_id}` 格式，例如：

```text
character:75
weapon:11512
artifact_set:15032
```

`name` 只用于 UI 展示与人类阅读。

`display_name` 可以写入配置作为辅助缓存，但不能作为仿真识别依据。

## 7. `asset_key` 与 `handler_key`

`asset_key` 与 `handler_key` 分离。

- `asset_key`：资产身份，数据库与配置使用。
- `handler_key`：代码实现绑定键，由仿真代码注册表解析。

示例：

```text
asset_key   = character:75
handler_key = character.furina
```

未实现复杂逻辑的资产可以暂时没有 `handler_key`。

## 8. 技能倍率 `scaling_json`

`scaling_json` 只保存随技能等级变化的倍率/数值表，不保存技能行为逻辑。

百分比统一存储为小数倍率：

```text
7.864% -> 0.07864
48.3862% -> 0.483862
```

第一版使用组件式结构：

```json
{
  "schema_version": 1,
  "mode": "level_table",
  "level_min": 1,
  "level_max": 15,
  "components": [
    {
      "kind": "stat_ratio",
      "stat": "hp",
      "values": [0.07864, 0.084538, 0.090436]
    }
  ]
}
```

`mode` 第一版支持：

```text
level_table
constant
```

`components.kind` 第一版支持：

```text
stat_ratio
flat
plain_ratio
plain_value
```

混合治疗示例：

```json
{
  "schema_version": 1,
  "mode": "level_table",
  "level_min": 1,
  "level_max": 15,
  "components": [
    {
      "kind": "stat_ratio",
      "stat": "hp",
      "values": [0.048, 0.0516, 0.0552]
    },
    {
      "kind": "flat",
      "values": [462.2253, 508.4543, 558.5355]
    }
  ]
}
```

复杂行为、召唤物调度、持续时间、攻击间隔、元素附着等不进入 `scaling_json`。

## 9. 效果参数 `params_json`

`effect_payloads.params_json` 用于保存武器、天赋、命座、圣遗物等复杂效果的参数。

数据库只保存效果参数，不保存效果行为。

顶层固定包含：

```text
schema_version
params
```

示例：

```json
{
  "schema_version": 1,
  "params": {
    "modifiers": [
      {
        "target": "self",
        "stat": "hp_percent",
        "op": "add",
        "value": 0.2
      }
    ]
  }
}
```

精炼变化示例：

```json
{
  "schema_version": 1,
  "params": {
    "damage_bonus_by_refinement": [0.12, 0.15, 0.18, 0.21, 0.24],
    "duration_frames": 600,
    "stack_limit": 3
  }
}
```

简单效果可以使用通用 handler：

```text
generic.static_modifiers
generic.conditional_modifiers
```

复杂效果使用专用 handler：

```text
character.furina.c2
weapon.some_weapon.passive
artifact.some_set.4pc
```

## 10. 导入与版本管理

资产库是可重建的生成产物。

建议生成流程：

```text
读取源数据
-> 清洗/标准化
-> 生成临时 assets.tmp.db
-> 校验数据完整性
-> 校验通过后替换 assets.db
```

版本拆分：

```text
schema_version
data_version
importer_version
```

当 `schema_version` 不兼容时，优先重新生成或替换 `assets.db`。

当 `data_version` 较旧但 `schema_version` 兼容时，应用可以继续运行，并由 UI 提示数据版本较旧。

未来若支持用户自定义资产，再考虑 `user_assets.db` 或正式迁移系统。

## 11. 导入校验

导入校验至少包含：

- `asset_key` 唯一。
- `source_id` 存在。
- `name` 不为空。
- 等级属性覆盖必要等级。
- `scaling_json` 符合当前 schema。
- 百分比已经转换为小数倍率。
- `handler_key` 要么为空，要么能在代码注册表中找到。
- `effect_payloads.params_json` 是合法 JSON。
- 不存在孤儿外键。

## 12. 与仿真核心的接口

`sim-core` 不直接依赖 SQLite。

`sim-core` 不直接执行 SQL。

资产数据库只在仿真组装阶段被读取；仿真运行时尽量不再查询资产库。

新项目通过 `AssetRepository` 协议暴露资产读取能力。

SQLite 的具体实现放在 `SQLiteAssetRepository` 一类的基础设施实现中。

建议接口能力：

```text
get_meta()
list_characters()
get_character(character_key)
get_character_level_stats(character_key, level)
list_weapons(weapon_type)
get_weapon(weapon_key)
get_weapon_level_stats(weapon_key, level)
list_artifact_sets()
get_artifact_set(artifact_set_key)
get_talent_scalings(character_key, talent_key)
get_effect_payloads(owner_key, effect_kind)
```

仓库返回明确的数据对象，例如：

```text
CharacterAsset
WeaponAsset
ArtifactSetAsset
TalentScalingEntry
EffectPayload
```

不向核心层传递 SQL row。

## 13. Handler 注册表

`handler_key` 由代码注册表解析。

示例：

```text
character.furina -> Furina
character.furina.c2 -> FurinaC2Handler
generic.static_modifiers -> StaticModifierHandler
artifact.viridescent_venerer.4pc -> ViridescentVenerer4pcHandler
```

缺资产、缺 handler、JSON 格式错误应在组装阶段报错，不应延迟到仿真运行中。
