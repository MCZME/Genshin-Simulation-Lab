# 元素能量系统设计

> 状态：正式规范。
> 本文说明 `core/systems/energy/` 元素能量领域的职责与结构：定位与范围、核心结论、资料与可信度、模块边界、领域模型、状态所有权、结算流程、帧顺序、跨系统协作、事实与快照、原子性与重入、确定性与错误边界。
> 稳定 key、字段、公式、错误码、事件载荷、快照结构与验证基线以[元素能量系统契约](../../契约/元素能量系统契约.md)为准，本文不重复维护。
> 最后更新：2026-09-19。

## 1. 定位与范围

元素能量领域负责原神标准元素爆发资源：

- 角色标准元素能量的当前值与上限。
- 元素微粒、元素晶球及其无元素变体的队伍分配。
- 在途载体的生成、延迟、排序与结算。
- 直接恢复、直接扣除与标准爆发消耗。
- 上述状态变化的事实、快照与审计结果。

标准元素能量是独立领域，既不是公共属性，也不是 Buff、空间实体或 content 私有状态。

本领域不负责：

- **产球机制本身**：数量、概率、触发条件与延迟帧由 content 在确定帧产出 `ImpactKind.ENERGY` 请求，本领域只执行分配。
- **角色专属资源**：战意等资源由角色 content 私有状态拥有，不伪装成标准元素能量。
- **谁能施放元素爆发**：本领域只提供能量条件证据，条件组合由[角色能力条件协调器设计](../协调/角色能力条件协调器设计.md)承担。
- **载体的可视路径**：核心只保存生成帧与结算帧，三维运动由 UI 投影。
- **能量分析投影与专用结果表**：结果库按通用事件折叠。

## 2. 核心结论

1. `CharacterEnergyStore` 拥有当前能量与版本，`EnergyTransitQueue` 拥有在途载体，`EnergyRuntime` 是唯一业务写入口；Store 与 Queue 的提交方法只由 Runtime 调用。
2. 能量真值是 `EnergyState` 上的单个有限非负数值，不携带来源、元素或上限；上限由组装期冻结的 `CharacterEnergyProfile.capacity` 提供。
3. 载体不进入 `Space`：本领域只需要生成帧与结算帧，两者的距离由请求给定的 `travel_frames` 决定，领域不解释它从何而来。
4. 结算在**结算帧**读取前后台身份、队伍人数与充能效率，不冻结生成帧的上下文；因此结算前的切人与属性变化自然生效。
5. 单次分配量为 `count × 载体种类倍率 × 元素倍率 × 前后台倍率 × (1 + 充能效率)`，再截断到剩余容量；领域不做取整，只把 `-0.0` 归一为 `0.0`。
6. 上限为零的角色不参与分配，并以 `no_elemental_energy_resource` 出现在结算记录中，而不是被静默跳过。
7. 直接恢复、直接扣除与爆发消耗共用外部 `change_id` 幂等域，与内部载体结算的 operation id 相互隔离，合法外部 ID 不会阻塞载体结算。
8. 载体结算先计算全部接收者前值与目标值，再校验 Store 与 Queue 的 version，最后一次性提交并移除载体；任一校验失败都不修改状态、不发布事实。
9. 结算提交与事实发布期间禁止重入；事件在提交完成后发布，事件 handler 抛错不回滚已提交状态。
10. 本领域不 import 或查询其他领域的 Runtime / Store，也不通过事件回调或全局服务定位获取外部状态。

## 3. 资料与可信度

### 3.1 系统级规则来源

通用规则以以下资料为基线：

- [KQM TCL：Energy](https://library.keqingmains.com/combat-mechanics/energy)：通用微粒、晶球、前后台、队伍人数、充能效率和直接回能规则。
- [KQM Energy Evidence](https://library.keqingmains.com/evidence/combat-mechanics/energy)：能量实际结算时点等实测证据。
- [KQM TCL 固定快照](https://github.com/KQM-git/TCL/blob/a38879d06cf363fc7a7afd25e3dfda0d0b9705d5/docs/combat-mechanics/energy.md)：固定本设计使用的资料版本。
- [gcsim 能量实现](https://github.com/genshinsim/gcsim/blob/6d373678e949d30e91d390f418d930de09eeb547/pkg/core/player/character/energy.go)：独立工程实现对照，不作为游戏规则真值。
- 本地 Project Amber / Yatta 角色详情：角色元素与元素爆发结构化 `cost` 字段。

系统级已确认规则为：

1. 微粒和晶球向整个队伍分配能量。
2. 同元素、无元素、异元素基础倍率分别为 `3/2/1`。
3. 晶球是同类微粒的 `3` 倍。
4. 场上角色倍率为 `1.0`；后台倍率为 `1.0 - 0.1 × 队伍人数`。
5. 元素充能效率只影响微粒和晶球收入。
6. 前后台身份和充能效率都在实际结算帧读取。
7. 直接恢复只作用于明确目标，不自动扩散到队伍。
8. 满能量时保留请求量、实际量和溢出量审计。

### 3.2 由 content 提供、本领域不定义的量

以下不是系统常量：

- 具体技能的产球数量、概率和触发条件。
- 多段技能的产球段数与产球内部冷却。
- 载体从生成到结算的延迟帧。
- 元素爆发的实际扣能帧。
- 敌人生命阈值掉球与普通攻击随机回能。
- 角色、武器、圣遗物和命座造成的直接能量变化。

这些量进入真实 content 前必须有可信来源或 golden case，取证方式见[原神游戏机制实现规范](../../工程/原神游戏机制实现规范.md)。核心不提供猜测默认值。

资产字符串到 `EnergyElement`、`burst_energy_cost` 到能量档案的映射由 `application/assembly/` 完成。模块职责与依赖方向的总体规则见[模块边界设计](../模块边界设计.md)与[系统自治与跨系统协调规范](../../工程/系统自治与跨系统协调规范.md)。

## 5. 领域模型

- **元素**：`EnergyElement` 含七种角色元素与 `CLEAR`。`CLEAR` 是独立于角色元素的载体元素，不能作为角色档案的元素，`CharacterEnergyProfile` 直接拒绝它。
- **载体种类**：`EnergyPickupKind` 区分 `PARTICLE` 与 `ORB`，种类只通过倍率参与计算。
- **档案**：`CharacterEnergyProfile` 在组装期冻结角色主体引用、资产 key、元素与上限，是能量领域的只读前提。
- **写入请求**：`SpawnEnergyPickupRequest` 表达生成载体（带 `request_id`、生成帧、种类、元素、数量、`travel_frames`、来源与 tags）；`RestoreEnergyRequest` / `DrainEnergyRequest` 表达直接恢复与直接扣除（带外部 `change_id`）；`SpendBurstEnergyRequest` 表达标准爆发消耗（带 `change_id`、动作实例 id 与来源上下文）。
- **载体记录**：`EnergyPickupRecord` 保存生成帧、结算帧、来源与 tags，并附带单调递增的生成序号；稳定排序键为 `(settle_frame, created_frame, spawn_order, pickup_id)`，保证同帧多载体顺序与注册顺序无关。
- **结果**：每个接收者一条 `EnergyRecipientResolution`，含各层倍率、充能加成与对应的 `CharacterEnergyChangeResult`；整体由 `EnergyPickupSettlementResult` 汇总当次结算的载体、结算帧、场上槽位与队伍人数。`EnergyRecipientStatus` 区分 `APPLIED`、`CAPPED`（已满）与 `NO_ELEMENTAL_ENERGY_RESOURCE`。
- **条件证据**：`BurstEnergyConditionResult` 与 `BurstEnergyConditionStatus` 是只读条件输出，不改变状态。

字段级定义、枚举取值与序列化要求见契约第 3 至第 6 节。

## 6. 状态所有权

```text
CharacterRuntimeState
└── energy: EnergyState（当前能量，单个有限非负数值）
          ↑
CharacterEnergyStore
├── CharacterEnergyProfile 索引
├── 各角色当前能量的唯一真值
├── version
└── committed operation ids

EnergyTransitQueue
├── 未结算的 EnergyPickupRecord（恒按稳定排序键输出）
├── 已入队 request id
├── 生成序号
└── version

EnergyRuntime
├── 唯一业务写入口
├── 倍率与属性查询编排
├── Store / Queue 的准备与提交
└── 提交后事实发布
```

边界要求：

- `EnergyState` 只保存当前值，不解释来源、元素或上限。
- `CharacterEnergyStore` 提交前用 `assert_can_commit` 同时校验 operation 是否重复、Store version 是否前移、角色前值是否与预期一致。
- `EnergyTransitQueue` 入队按 request id 去重，取出与移除都以 version 校验为前提。
- content、Action、事件 handler 与其他领域不能直接写 `EnergyState` 或 Store。
- 所有业务变化必须通过 `EnergyRuntime` 的强类型请求。
- 只读出口是 `EnergyReadPort` 协议：当前能量、上限、是否使用标准资源、是否满能量与条件查询。

## 7. 结算流程

```text
上游在确定帧提交 SpawnEnergyPickupRequest(request_id, frame=F, travel_frames=D)
-> EnergyTransitQueue 记录 settle_frame = F + D，按稳定排序键落位
-> 到达结算帧，EnergyRuntime.update_frame 取出 due(frame) 的记录
-> 逐角色计算：
     capacity == 0            -> no_elemental_energy_resource，不参与分配
     否则                     -> base = count × kind × element × field
     该帧读取充能效率加成     -> requested = base × recharge_multiplier
     effective = min(requested, capacity - 前值)
-> 汇总全部接收者前值与目标值
-> store.assert_can_commit（operation 去重 + Store version + 前值）
-> queue.assert_current（Queue version）
-> 一次性提交全部角色能量并移除载体
-> 发布结算事实
```

设计后果：

- 结算帧之前的切人、Buff 生效与充能效率变化都会反映在结果里，因为上下文一律在结算帧读取。
- 队列非空时 `EnergyRuntime.is_idle()` 为假，仿真不会在载体仍在途时提前结束。
- 结算请求带 `request_id`，重复入队被拒绝，不会产生两枚同源载体。

## 8. 帧顺序与结算轮次

运行世界按阶段顺序推进：

```text
TIME_ADVANCE      buff → infusion → shield → elemental_settlement → cooldown → movement → resonance
ACTION_ADVANCE    action_manager
SETTLEMENT        impact → energy → space
FACT_RESPONSE     moonsign → resonance_reactions → content_hooks
SNAPSHOT          attributes_panel
```

对本领域的约束：

1. 能量领域处于 `SETTLEMENT` 阶段并排在 Impact 之后：同帧向全队提交的直接能量变化与爆发扣能先完成，同帧到达的载体随后结算，可以在爆发扣能之后补充能量。
2. `ACTION_ADVANCE` 早于 `SETTLEMENT`：同帧切人先提交，载体按切换后的前后台身份结算。
3. content 的产球请求在 `FACT_RESPONSE` 阶段产生，最早在下一轮结算被消费，不影响本轮的载体。
4. 结算阶段按轮次重复：每轮先排空意图，再执行事实响应阶段；意图队列为空即结束，超过轮次上限由帧管线报错。一轮内多个载体按队列稳定键逐个结算，前一个载体的提交对后一个可见。
5. 队伍人数必须在 1 到 4 之间，否则前后台倍率计算直接失败，不做兜底。

## 9. 跨系统协作

### 9.1 Impact 入口

`EnergyImpactRequestHandler` 是 `ImpactKind.ENERGY` 的唯一适配点，接受 `spawn_pickup`、`restore`、`drain`、`spend_burst` 四种操作。它校验 `params.energy` 的 `schema_version` 与允许字段集合，拒绝未知字段，再构造强类型能量请求交给 `EnergyRuntime`，并保存 `EnergyImpactRecord` 审计。handler 不实现任何倍率或资源公式。请求结构、允许字段与失败行为见契约第 10 节；行动侧的提交时点见[动作系统设计](../动作系统设计.md)。

### 9.2 属性与 Buff

- 当前能量与上限不是公共属性，不进入属性面板的通用修饰链路。
- `stat.energy_recharge` 是相对基础 100% 的加成比例，只在载体结算时读取。
- Buff 可以通过属性 provider 修改充能效率，但不能直接写能量。
- 直接回能型 Buff 必须生成后续强类型命令，不能在事实事件回调中同步调用 Runtime。

属性侧的稳定字段与查询协议见[属性系统契约](../../契约/属性系统契约.md)。

### 9.3 角色能力条件

能量领域通过 `query_burst_condition()` 输出结构化的 `BurstEnergyConditionResult`，供 `CharacterAbilityConditionCoordinator` 只读消费。协调器位于 `core/coordination/`，不属于本领域，也不得进入 Store 或重复实现能量分类公式。本领域**不提供能量预留或预扣**：实际扣能由 content 在有来源支撑的帧提交 `SpendBurstEnergyRequest`。

### 9.4 内容侧接入

content 通过事件 hook 产出 `ImpactKind.ENERGY` 请求：产球使用 `operation: spawn_pickup`，直接回能使用 `restore` / `drain`，爆发扣能使用 `spend_burst`。请求的产出时点、概率与数值依据属于 content 职责，见第 3.2 节。

## 10. 事实、事件与快照

能量事件只表达已经提交的事实：

| 事件 | 发布条件 |
| --- | --- |
| `ENERGY_PICKUP_SPAWNED` | 载体入队 |
| `ENERGY_PICKUP_SETTLED` | 每次载体结算 |
| `DIRECT_ENERGY_CHANGE_RESOLVED` | 每次直接恢复或扣除 |
| `CHARACTER_ENERGY_CHANGED` | 结算后实际变化量大于 `0` |

载荷只携带单条 record 或 result，字段定义见契约第 11 节。事件类型与命名见[事件类型](../事件系统/事件类型.md)。

快照由 `EnergySnapshot` 表达：帧号、每个角色的能量快照（主体引用、资产 key、元素、当前值、上限、爆发就绪）与未结算载体列表。它保存的是可复原的只读投影，不保存 resolver、provider 或调用方对象。

结果库按通用事件折叠能量变化，不设能量专用表。

## 11. 资产与组装

- SQLite 资产 schema 的 `characters.burst_energy_cost` 为 `REAL NOT NULL`；manifest 必须给出有限非负成本，`cost = 0` 表示角色不使用标准元素能量。
- 内存 `CharacterAsset` 允许 `None` 表达不完整或兼容资产，但组装必须拒绝该值。
- `capacity` 直接取自 `burst_energy_cost`；元素由资产元素字符串映射为 `EnergyElement`。
- 初始能量由规则提供的 `InitialEnergyPolicy` 决定，默认策略为零初始能量；`start_with_full_energy` 规则可切换为满能量起步。
- `SimulationInput` 不提供初始能量字段。
- 能量档案按队伍槽位与对应资产绑定，不依赖配置数组顺序。
- 武器与圣遗物副属性 `stat.energy_recharge` 由属性组装链路进入，不由本领域解析。
- 组装期抛出的 `EnergySystemError` 统一转为 `InvalidRuntimePayloadError`，不延迟到运行期暴露。

字段定义与 schema 约束见[资产数据库契约](../../契约/资产数据库契约.md)。

## 12. 原子性、幂等与重入

- **结算原子性**：先计算全部接收者前值与目标值，再校验 Store 与 Queue 的 version，最后一次性提交并移除载体。任一准备或校验失败都不得修改角色状态、移除载体或发布事件。
- **幂等域隔离**：直接恢复、直接扣除与爆发消耗共用外部 `change_id`，operation id 为 `direct:{change_id}`；载体结算使用 `pickup-settlement:{pickup_id}`，每个接收者再带 `{pickup_id}:{ref}` 的变化 id。两类 operation 互不阻塞。
- **重复请求**：队列入队按 request id 去重，重复入队直接拒绝。
- **重入保护**：领域以变更标志与事实发布标志守住两个阶段——状态或队列提交期间、已提交事实发布期间。提交期产生的事件进入待发布队列，延后到提交完成后发布。
- **查询不推进状态**：查询、快照与条件判断都不修改 Store、不推进时间、不发布事实。

运行态的提交与事实发布通用要求见[领域运行态实现规范](../../工程/领域运行态实现规范.md)。

## 13. 确定性与错误边界

确定性：

- 排序不依赖 dict / set 顺序、对象地址、显示名称或 content 注册顺序。
- 外部数字先拒绝 `bool`，再校验有限性与范围；乘法中间量必须保持有限非负。
- `-0.0` 统一归一为 `0.0`；不使用未记录 epsilon 判定满能量。
- 概率产球必须由上游仿真 RNG 解析成确定整数后再进入本领域。

错误边界按性质分组，具体错误码与抛点见契约第 13 节：

| 分组 | 代表错误 | 触界条件 |
| --- | --- | --- |
| 输入校验 | `EnergyValidationError` | 请求字段非法、`params.energy` 结构或 `schema_version` 不符 |
| 主体与资源 | `CharacterEnergyNotFoundError`、`UnsupportedEnergySubjectError`、`UnsupportedEnergyResourceError`、`UnsupportedEnergyElementError`、`UnsupportedEnergyOperationError` | 角色无档案、主体类型不支持、角色不使用标准能量、元素或操作不受支持 |
| 数值 | `InvalidEnergyAttributeError` | 充能效率加成非数字、非有限或得到非正倍率 |
| 一致性与重复 | `EnergyPlanConflictError`、`DuplicateEnergyRequestError` | version 前移、前值不符、载体未到结算帧、重复 operation 或 request |
| 重入 | `EnergyReentrancyError` | 提交期或发布期再次写入 |
| 引用 | `EnergyPickupNotFoundError` | 队列中不存在目标载体 |
| 业务拒绝 | `InsufficientEnergyAtSpendError` | 爆发消耗超过当前能量 |

验证入口：

- golden case 位于 `backend/tests/golden/energy/`，覆盖要素与数值基线见契约第 17 节。
- 分层职责、预期值来源与夹具要求见[测试规范](../../工程/测试规范.md)。

## 14. 范围外与禁止的简化

范围外：

- 玛薇卡战意、丝柯克蛇之狡谋等专属资源公式。
- 联机分配规则与多个玩家同时在场。
- 微粒的三维运动、碰撞、吸附与视觉路径。
- 敌人生命阈值掉球与普通攻击随机回能。
- content 自定义或覆盖核心倍率表。
- 通过事件回调同步修改当前结算。
- 能量预留与预扣。
- 能量专用结果表与分析投影。

禁止的简化：

- 不把能量建成逐帧递减的浮点秒数，也不把它降级为普通公共属性。
- 不把上限或充能效率写进 `EnergyState`。
- 不把载体注册到 `Space`。
- 不在生成帧冻结前后台身份或充能效率。
- 不把专属资源建模为标准元素能量。
- 不让查询、快照或条件判断隐式推进时间或发布事实。
- 不用 callback、事件回调或全局 service locator 获取外部状态。
- 不提供调用方可直接覆盖能量值的 setter。
