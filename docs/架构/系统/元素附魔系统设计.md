# 元素附魔系统设计

> 状态：正式规范。
> 本文说明 `core/systems/infusion/` 元素附魔与元素转化领域的职责边界：武器附魔与元素转化如何收敛为普攻/重击/下落的最终伤害元素，以及它为何不进入属性、Aura 或完整反应体系。
> 最后更新：2026-09-05。

稳定 key、模型字段、六对消耗规则、事件载荷、错误码与组装校验见[元素附魔系统契约](../../契约/元素附魔系统契约.md)，本文不重复维护。

## 1. 结论

`core/systems/infusion/` 是元素附魔与元素转化领域的唯一实现入口。核心结论：

- 元素附魔不是属性 modifier，不进入 Buff 系统；武器附着也不是 Aura 主体，不进入 Aura / ICD / Reaction 体系。
- 只做最终元素收敛，不做武器上的完整元素反应仿真：武器侧反应不产生 occurrence、伤害、效果，不读取元素精通或等级。
- 最终元素收敛采用最小 gauge / 消耗模型：按来源周期挂载定义配置的元素量、过期移除，并用封闭的两两消耗规则决定残留；不使用单一全局优先级表。
- 有效元素在 Damage Impact 结算帧解析，不在动作创建时快照；只影响普攻、重击、下落攻击的伤害元素与元素施加，不改变攻击自身的 ICD 标签 / 序列与 AOE 契约；物理或无元素量攻击在附魔后按来源 `weapon_gauge` 注入附着。
- 命中目标后的元素施加仍走现有 Aura / ICD / Reaction 流程，本系统不复制或替代该流程。

## 2. 术语

- **武器附魔（INFUSION）**：给近战武器挂载元素，可被其他来源消耗、顶替或刷新；影响普通攻击、重击、下落攻击的伤害元素。
- **元素转化（CONVERSION）**：角色自身攻击强制转为某元素，不可被武器附魔覆盖。
- **武器附着**：武器作为独立附着单位持有的元素残留；是 `InfusionStore` 的内部状态，不是 Aura 主体。
- **最终元素**：命中结算时实际使用的伤害元素。

## 3. 目标与非目标

目标：

- 为近战角色普攻 / 重击 / 下落的 `DamageImpactSpec.element` 提供结算帧解析。
- 支持单次附魔、周期附魔、同元素刷新、异元素消耗 / 顶替 / 共存、元素转化。
- 输出可审计的 `EffectiveElementResolution`：元素、模式、来源引用和原因码。
- 为真实角色内容迁移提供稳定组装入口（`ContentUnit.infusion_definitions` 与 `APPLY_INFUSION` Impact）。

非目标：

- 不仿真武器上的完整元素反应（无 reaction occurrence、无反应伤害、无效果、无精通参与）。
- 不把武器注册为 Aura 主体，不进入元素反应协调器。
- 不改变命中目标后的 Aura / ICD / Reaction 流程；附魔攻击的 ICD 由攻击自身契约决定，元素施加量来自来源 `weapon_gauge`。
- 不使用显示名称、全局 priority 或静态优先级表判定覆盖。
- 不实现尚未确认的角色数据：周期、时长、元素量、离场保留、弓 / 法器限制等推迟到具体角色实现时确认。

## 4. 领域边界

| 概念 | 归属 |
| --- | --- |
| 附魔 / 转化来源、生命周期与武器附着残留 | `core/systems/infusion/`（`InfusionStore`） |
| 最终元素收敛公式 | `core/systems/infusion/`（`InfusionResolver`） |
| 目标身上的元素施加、ICD 与反应 | Aura / Aura ICD / Reaction 系统 |
| 普攻、重击、下落攻击标签与命中契约 | 动作系统、Damage Impact 契约 |
| 命中伤害元素 | Damage Impact 结算帧由 infusion 适配器解析后替换 |
| 元素增伤、物理增伤与抗性 | 属性系统、伤害系统按元素查询 |

`core/systems/infusion/` 只依赖 `core/elements/`、`core/attributes/` 的身份模型和少量中立值对象，不依赖其他领域系统的 Runtime 或 Store。

## 5. 状态所有权

`InfusionStore` 是活动附魔与转化记录的唯一写入口和真值来源。每个角色持有自己的活动来源集合，记录包括定义、模式、元素、刷新策略与生命周期。

武器附着残留是 Store 内部投影，供 Resolver 纯计算使用，不对外暴露可变写入口：同元素新挂载清零其他同元素记录残留（刷新 / 顶替），异元素按六对规则逐次消耗，冻结后的下一次挂载直接顶替。

## 6. 收敛流程

每帧查询顺序：

```text
1. InfusionRuntime 在 FRAME_STARTED 后推进周期刷新与过期清理（幂等）
2. InfusionResolver 查询：存在有效 CONVERSION → 直接返回转化元素
3. 否则按稳定来源顺序应用活动 INFUSION 来源配置的元素量（weapon_gauge）并逐次执行武器侧消耗
4. 周期来源在 next_refresh_frame 重新挂载（重置残留并再次参与消耗）
5. 按伤害元素判定规则从残留中选出最终元素（冻结 → 冰、雷水共存 → 水、消耗空窗 → 基础元素）
6. 返回 EffectiveElementResolution（元素 + 来源 + 原因码 + weapon_gauge）
```

同一帧多个 PERIODIC 来源刷新时，按 instance ref 稳定顺序逐次重新挂载并消耗；该顺序是契约语义。单次来源只挂载一次，到 `expires_at_frame` 移除；消耗只影响武器附着投影，不发布反应事件、不产生伤害。

## 7. 与 Damage 链路的关系

```text
ImpactRequest（普攻/重击/下落）
→ InfusionEffectiveElementPort 按主攻击标签查询当前帧最终元素
→ 替换 DamageImpactSpec.element
→ 物理/零元素量攻击注入 weapon_gauge 与对应附着强度（icd 不变）
→ 生成 InfusionElementResolutionRecord 审计
→ 进入现有 Aura/ICD/Reaction 与 Damage 结算
```

- 适配器只对声明为“可附魔”的主攻击标签生效；战技、爆发伤害不查询附魔。
- `InfusionElementResolutionRecord` 审计保留原始请求元素（`base_element`）、最终有效元素、来源引用与是否应用。
- 附魔后不再吃到物理伤害加成，由伤害系统按最终元素查询增伤区天然处理。
- 装配链路：`ContentUnit.infusion_definitions` 编译附魔定义，`APPLY_INFUSION` Impact 处理器转为 `ApplyInfusionRequest`，`InfusionRuntime` 在帧推进阶段先于 Impact 结算刷新与过期。

## 8. 事件与快照

领域事实：

- `INFUSION_APPLIED`：一次创建、周期刷新或替换已提交。
- `INFUSION_REMOVED`：一个来源因过期、替换、消耗或显式原因离开活动状态。

两者均为 `STATE_CHANGE`、默认记录、提交后发布、载荷不可变。命中本身不发布新事件。`InfusionSnapshot` 保存指定帧活动记录，按 instance ref 稳定排序，供复盘与分析使用。
