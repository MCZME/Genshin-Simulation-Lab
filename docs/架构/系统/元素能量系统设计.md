# 元素能量系统设计

> 状态：正式。标准元素能量第一版核心、资产、Impact、事件、快照与组装链路已经实现；真实角色产球、直接回能和爆发扣能时点仍按 content 逐项取证。
>
> 本文只规定系统职责、状态所有权、依赖方向和运行时流程。稳定字段、公式、错误和序列化见[元素能量系统契约](../../契约/元素能量系统契约.md)。

最后更新：2026-07-14

## 1. 定位

元素能量系统负责原神标准元素爆发资源，包括：

- 角色当前标准元素能量和固定能量上限。
- 元素微粒、元素晶球与无元素微粒/晶球。
- 在途能量载体的生成、延迟、排序和队伍分配。
- 直接恢复、直接扣除与标准爆发消耗。
- 状态提交后的事件、快照和审计结果。

系统位于：

```text
core/entity_states/energy.py
└── EnergyState

core/systems/energy/
├── models / formulas / errors
├── CharacterEnergyStore
├── EnergyTransitQueue
├── EnergyRuntime
└── EnergyImpactRequestHandler
```

标准元素能量是独立领域，不是普通属性、Buff、空间实体或 content 私有状态。

## 2. 资料与可信度

### 2.1 系统级规则来源

当前通用规则以以下资料为基线：

- [KQM TCL：Energy](https://library.keqingmains.com/combat-mechanics/energy)：通用微粒、晶球、前后台、队伍人数、充能效率和直接回能规则。
- [KQM Energy Evidence](https://library.keqingmains.com/evidence/combat-mechanics/energy)：能量实际结算时点等实测证据。
- [KQM TCL 固定快照](https://github.com/KQM-git/TCL/blob/a38879d06cf363fc7a7afd25e3dfda0d0b9705d5/docs/combat-mechanics/energy.md)：固定本次设计使用的资料版本。
- [gcsim 能量实现](https://github.com/genshinsim/gcsim/blob/6d373678e949d30e91d390f418d930de09eeb547/pkg/core/player/character/energy.go)：独立工程实现对照，不作为游戏规则真值。
- 本地 Project Amber / Yatta 角色详情：角色元素与元素爆发结构化 `cost` 字段。

系统级已确认规则为：

1. 微粒和晶球向整个队伍分配能量。
2. 同元素、无元素、异元素基础倍率分别为 `3/2/1`。
3. 晶球是同类微粒的 `3` 倍。
4. 场上角色倍率为 `1.0`；后台倍率取决于实际队伍人数。
5. 元素充能效率只影响微粒和晶球收入。
6. 前后台身份和充能效率都在实际结算帧读取。
7. 直接恢复只作用于明确目标，不自动扩散到队伍。
8. 满能量时保留请求量、实际量和溢出量审计。

### 2.2 content 级待取证项

以下内容不是系统常量：

- 具体技能的产球数量、概率和触发条件。
- 多段技能的产球段数与产球内部冷却。
- 载体从生成到结算的延迟帧。
- 元素爆发的实际扣能帧。
- 敌人生命阈值掉球。
- 普通攻击随机回能。
- 角色、武器、圣遗物和命座的直接能量变化。

这些行为进入真实 content 前必须具有可信来源或 golden case。核心不提供猜测默认值。

## 3. 范围

### 3.1 当前已实现

- 一至四人单机队伍。
- 七种角色元素和无元素载体。
- 标准元素能量上限、就绪查询和完整爆发消耗。
- 微粒/晶球延迟调度与稳定顺序。
- 结算帧动态读取队伍状态和 `stat.energy_recharge`。
- 直接恢复、直接扣除、上限、下限和未应用量。
- `ImpactKind.ENERGY` 结构化入口。
- 事件、快照、停止条件、幂等和重入保护。
- `burst_energy_cost = 0` 的专属资源角色安全共存。

### 3.2 当前非目标

- 玛薇卡战意、丝柯克蛇之狡谋等专属资源公式。
- 联机分配规则和多个同时在场玩家。
- 微粒三维运动、碰撞、吸附和视觉路径。
- 敌人生命阈值掉球与普通攻击随机回能。
- content 自定义或覆盖核心倍率表。
- 通过事件回调同步修改当前能量结算。
- `SimulationConfig` 初始能量字段。
- 能量专用结果数据库表。

## 4. 状态所有权

```text
CharacterRuntimeState
└── EnergyState.current_energy
          ↑
CharacterEnergyStore
├── CharacterEnergyProfile
├── EnergyState 索引
├── version
└── committed operation ids

EnergyTransitQueue
└── 尚未结算的 EnergyPickupRecord

EnergyRuntime
├── 唯一业务写入口
├── 公式与属性查询编排
├── Store / Queue 提交
└── 提交后事实发布
```

边界要求：

- `EnergyState` 只保存最小当前值，不解释来源、元素或上限。
- `CharacterEnergyProfile` 保存组装时冻结的角色元素和能量上限。
- `CharacterEnergyStore` 拥有当前能量索引、版本和提交幂等。
- `EnergyTransitQueue` 拥有在途载体。
- content、Action、事件 handler 和其他领域不能直接写 `EnergyState` 或 Store。
- 所有业务变化必须通过 `EnergyRuntime` 的强类型请求。

## 5. 依赖边界

`core/systems/energy/` 可以依赖：

- `core/attributes` 的窄查询协议和 `stat.energy_recharge`。
- `core/entity_states` 的 `EnergyState`。
- `core/events` 的事实发布接口。
- 队伍状态的只读协议。
- 中立的角色主体引用和来源上下文。

它不能：

- 依赖 `assets`、`content`、`application`、`infrastructure` 或 UI。
- import 其他领域系统的具体 Runtime 或 Store。
- 读取伤害结果、敌人生命或命中历史决定是否产球。
- 通过 EventEngine 发起当前结算的递归写入。

资产字符串到 `EnergyElement`、`burst_energy_cost` 到能量档案的映射由 `application/assembly/` 完成。

## 6. 在途载体模型

微粒和晶球不注册到 `Space`。第一版只需要确定的生成帧和结算帧，不需要几何路径或碰撞。

```text
上游命中或机制触发
-> SpawnEnergyPickupRequest(frame=F, travel_frames=D)
-> EnergyTransitQueue(settle_frame=F+D)
-> 到达结算帧
-> 读取当前 active_slot、team_size 和充能效率
-> 准备全队结算结果
-> 原子提交角色能量并移除载体
-> 发布事实
```

这种设计保证：

- 后台角色没有独立空间实体时仍能获得队伍分配。
- 结算时切人和充能效率变化自然生效。
- UI 可以从生成帧和结算帧投影视觉动画，而不改变核心真值。

## 7. 帧顺序

当前运行世界顺序为：

```text
BuffRuntime
ShieldRuntime
ActionManager
ImpactRuntime
EnergyRuntime
SpaceRuntime
```

因此：

1. 当前帧切人先提交，微粒按切换后的前后台身份结算。
2. Action impact 产生的直接能量变化或爆发扣能先提交。
3. 同帧到达的微粒随后结算，可以在爆发扣能后补充能量。
4. 同帧多个直接变化沿 Impact 已冻结的请求顺序提交。
5. 同帧多个载体按队列稳定键逐个结算，前一个载体的提交对后一个可见。

只要在途队列非空，`EnergyRuntime.is_idle()` 就返回 `False`，防止仿真提前结束。

## 8. Action 与 Impact

### 8.1 当前接口

能量领域提供 `EnergyReadPort`，用于读取当前能量、上限、是否使用标准资源和是否满能量。写入通过 `ImpactKind.ENERGY` 或限定核心调用方提交强类型请求。

`EnergyImpactRequestHandler` 负责：

```text
ImpactRequest.params.energy
-> 校验 schema_version 和操作字段
-> 构造强类型能量请求
-> 调用 EnergyRuntime
-> 保存适配审计记录
```

handler 不实现倍率或资源公式。

### 8.2 尚未实现的公共能力条件协调

标准元素爆发最终需要在动作解释阶段组合冷却和能量条件。该目标方案已经冻结，但角色能力条件协调器运行时代码尚未实现。

因此当前正式能量契约只包含 `EnergyReadPort` 和 `is_burst_ready()`。规划中的 `BurstEnergyConditionReadPort`、`BurstEnergyConditionResult` 与 `CharacterAbilityConditionCoordinator` 不属于当前已实现 API。

公共条件查询未来也不执行能量预留。实际扣能仍由 content 在有来源支撑的帧提交 `SpendBurstEnergyRequest`。

## 9. 属性、Buff 与专属资源

- 当前能量和能量上限不是普通公共属性。
- `stat.energy_recharge` 是相对基础 100% 的加成比例，只影响载体收入。
- Buff 可以通过属性 provider 修改充能效率，但不能直接写能量。
- 直接回能型 Buff 必须生成后续强类型命令，不能在事实事件回调中同步调用 Runtime。
- 普通元素能量不保存到 `ContentStateStore`。
- 专属资源由角色 content 私有状态拥有，不伪装成 `EnergyState`。

## 10. 事件、快照与结果

能量事件只表达已经提交的事实：

- `ENERGY_PICKUP_SPAWNED`
- `ENERGY_PICKUP_SETTLED`
- `DIRECT_ENERGY_CHANGE_RESOLVED`
- `CHARACTER_ENERGY_CHANGED`

事件发布期间禁止能量写入重入。事件 handler 抛错不回滚已经提交的状态，因此当前结算必需行为不能依赖事件回调。

快照包含角色能量档案、当前能量、爆发就绪状态和在途载体。第一版结果库继续记录通用事件 JSON，不增加能量专用表。

## 11. 资产、配置与组装

- SQLite 资产 schema `2` 的 `characters.burst_energy_cost` 为 `REAL NOT NULL`。
- manifest 必须显式提供有限非负成本。
- `cost = 0` 表示角色不使用标准元素能量。
- 内存 `CharacterAsset` 允许 `None` 表达不完整或兼容资产，但 `SimulationAssembler` 必须拒绝该值。
- 所有角色第一版从 `0` 能量开始，`SimulationConfig` 不提供初始能量。
- 能量档案必须按队伍槽位与对应资产绑定，不能依赖配置数组顺序。

## 12. 原子性、幂等与重入

载体结算先读取全部角色前值和属性，再校验 Store/Queue version，最后无回调提交全队状态。任一准备或校验失败都不得修改角色状态、移除载体或发布事件。

直接恢复、直接扣除和爆发消耗共享外部 `change_id` 幂等域。Runtime 必须把外部直接变化和内部载体结算 operation 隔离，避免合法外部 ID 阻塞内部结算。

能量事务在以下阶段禁止重入：

- 状态或队列提交期间。
- 已提交事实发布期间。

## 13. 迁移结论

旧项目中保留的行为目标包括上限、载体延迟、元素关系、前后台、充能效率和爆发消耗。以下旧设计不再迁移：

- `BEFORE_ENERGY_CHANGE` 作为同步写命令。
- 微粒预绑定单个接收角色。
- 固定四人队后台倍率 `0.6`。
- 把微粒注册为空间战斗实体。
- 用布尔组合区分固定回能和独立回能。
- 角色对象直接 `gain/clear`。
- 用负能量表示未初始化。

更完整的能力覆盖状态见[旧项目能力盘点](../../工程/旧项目能力盘点.md)。

## 14. 后续扩展

后续能力按独立专题进入，不扩展成万能资源系统：

- 第一个具有可信产球和扣能时序的真实角色 content。
- 直接回能或西风类效果的真实 golden case。
- 角色能力条件协调器运行时实现。
- 敌人阈值掉球和普通攻击随机回能。
- 初始能量配置。
- 能量分析投影。
- 专属资源与标准能量事实的限定协作。
