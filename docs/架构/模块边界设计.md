# 模块边界设计

> 本文档记录新项目的目录结构、模块职责与依赖边界。
> UI 具体设计暂缓，本文只保留 UI 与其他层之间的边界原则。

## 1. 总体决策

新项目采用：

- 单仓库单包。
- Python 包名暂定 `genshin_sim`。
- `src/` 布局。
- 使用 `uv` 管理项目。
- `pyproject.toml` 作为项目配置入口。

推荐目录：

```text
new-project/
├── pyproject.toml
├── README.md
├── docs/
├── data/
│   ├── assets/
│   │   └── assets.db
│   └── results/
│       └── results.db
├── src/
│   └── genshin_sim/
│       ├── __init__.py
│       ├── core/
│       ├── content/
│       ├── assets/
│       ├── infrastructure/
│       ├── application/
│       ├── analysis/
│       ├── ui/
│       └── cli/
└── tests/
    ├── unit/
    ├── integration/
    └── golden/
```

## 2. 总体依赖方向

核心原则：

```text
core            -> 运行仿真
content         -> 具体角色/武器/圣遗物实现
assets          -> 资产数据对象与仓库协议
infrastructure  -> 外部存储与具体技术实现
application     -> 用例编排
analysis        -> 结果加工、聚合、比较
ui / cli        -> 用户入口
```

依赖方向：

```text
ui / cli
  -> application
      -> core
      -> assets
      -> content registry
      -> analysis
      -> repository / writer protocols
          <- infrastructure implements
```

硬规则：

- `core/` 不能 import `assets`、`infrastructure`、`application`、`ui`、`content`。
- `core/` 只处理仿真运行时对象与纯数据结构。
- `content/` 可以依赖 `core/` 和 `assets/` 的数据对象。
- `application/` 负责组装用例，不直接编写具体 SQLite 查询。
- `infrastructure/` 实现外部存储和技术细节，不被 `core/` 依赖。
- `analysis/` 只做数据加工，不写库、不画 UI。
- `ui/` 和 `cli/` 通过 `application/` 调用能力。

## 3. `core/`

`core/` 是纯仿真运行时核心，负责“怎么模拟”。

不负责：

- 数据从哪里来。
- 结果存在哪里。
- UI 怎么展示。
- 具体角色、武器、圣遗物的实现。

建议结构：

```text
core/
├── simulation/
├── events/
├── actions/
├── impacts/
├── entity_states/
├── attributes/
├── mechanics/
├── systems/
├── space/
└── snapshots/
```

职责：

- `simulation/`：仿真上下文、模拟器、时钟、基础运行结果。
- `events/`：事件类型、事件对象、事件分发与事件处理接口。
- `actions/`：队伍动作控制器、输入会话、角色动作解释器协议、动作状态、动作管理器和动作时间轴。
- `impacts/`：动作影响点到机制请求或空间实体创建请求的通用请求模型、分发器和工厂协议。
- `entity_states/`：角色运行态状态、目标运行态状态、通用生命周期值对象和目标状态索引；实体本身及其空间查询入口由 `space/` 表达。
- `attributes/`：基础属性、动态属性、属性计算器和修饰符计算。
- `mechanics/`：元素附着、ICD、反应算法、附魔、能量等纯机制算法。
- `systems/`：伤害、反应、生命、护盾、能量、共鸣、规则等上下文系统。
- `space/`：战场空间、位置、索敌、空间实体管理和内容创建空间对象运行态。当前最小实现登记当前场上角色空间实体、多个简单目标点位和内容创建的带生命周期空间对象，并提供 X/Z 平面范围查询。目标不建模复杂体型、多 hitbox、刚体碰撞或目标挤压。
- `snapshots/`：快照模型与快照导出器，只生成快照，不写数据库。

旧项目映射：

- `SimulationContext` -> `core/simulation/`
- `Simulator` -> `core/simulation/`
- `GameEvent` / `EventType` / `EventEngine` -> `core/events/`
- `ActionCommand` -> `core/actions/`
- `CombatSpace` -> `core/space/`

## 4. `content/`

`content/` 是具体游戏内容实现层。

负责：

- 具体角色实现。
- 具体武器效果实现。
- 具体圣遗物效果实现。
- 命座、天赋和复杂效果 handler。
- 通用效果 handler。

不负责：

- 读取 SQLite。
- 读取配置文件。
- 创建 `SimulationAssembler`。
- Flet UI。

建议结构：

```text
content/
├── __init__.py
├── bootstrap.py
├── registry.py
├── models.py
├── characters/
├── weapons/
├── artifacts/
└── generic/
```

角色目录示例：

```text
content/characters/fontaine/furina/
├── __init__.py
├── content.py
├── actions.py
├── impacts.py
├── state.py
└── hooks.py
```

武器目录示例：

```text
content/weapons/sword/splendor_of_tranquil_waters/
├── __init__.py
├── content.py
├── impacts.py
└── hooks.py
```

注册规则：

- 使用 `handler_key` 作为唯一代码绑定入口。
- 不使用显示名称绑定代码。
- 不使用 `asset_key` 直接绑定代码。
- 不依赖自动扫描和隐式导入注册。
- 每个内容模块提供显式 `register(registry)` 函数。
- `content/bootstrap.py` 显式导入并注册内置内容。
- `registry` 第一版按角色、武器、圣遗物和 impact 拆分专用 request 与创建入口。

示例：

```text
character.furina
character.furina.c2
weapon.some_weapon.passive
artifact.some_set.4pc
generic.static_modifiers
```

组装流程：

```text
配置文件中的 character_key
-> AssetRepository 读取 CharacterAsset
-> CharacterAsset.handler_key
-> HandlerRegistry.create_character(CharacterRuntimeRequest)
-> Factory 创建 ContentRuntimeContribution
-> SimulationAssembler 构造 RuntimeContentBundle
-> 拆分注入 TeamActionController / ImpactDispatcher / ImpactRuntime / CreatedObjectRuntime / ContentStateStore
-> Simulator 运行
```

缺资产、缺 handler、JSON 格式错误应在组装阶段报错。

## 5. `assets/`

`assets/` 保存资产数据对象、仓库协议与资产相关错误。

建议结构：

```text
assets/
├── models.py
├── repository.py
└── errors.py
```

职责：

- 定义 `AssetRepository` 协议。
- 定义 `CharacterAsset`、`WeaponAsset`、`ArtifactSetAsset`。
- 定义 `TalentScalingEntry`、`EffectPayload`。
- 定义资产读取与数据校验相关错误。

不负责：

- SQLite 查询实现。
- 数据导入。
- 具体角色行为。
- UI 展示。

SQLite 实现放在 `infrastructure/assets_sqlite/`。

## 6. `application/`

`application/` 是用例编排层。

负责连接：

- UI / CLI。
- 资产库。
- handler 注册表。
- `content/` 实现。
- `core/` 运行时对象。
- 运行期结果库。
- `analysis/` 分析能力。

建议结构：

```text
application/
├── __init__.py
├── config/
├── assembly/
├── execution/
├── jobs/
├── services/
├── batch/
└── errors.py
```

职责：

- `config/`：配置契约与校验模型。
- `assembly/`：仿真组装逻辑，例如 `SimulationAssembler`。
- `execution/`：内部仿真执行原语，例如同步执行一次仿真、收集事件并调用结果写入协议。
- `jobs/`：仿真任务模型、任务状态、调度器协议和后续后台 worker 边界；当前已有内存版同步 runner 与通用 worker payload，用于验证任务接口。
- `services/`：给 UI 和 CLI 调用的对外用例服务门面，不保存单次同步运行原语。
- `batch/`：批量任务、参数扫描、配置变体编译和结果汇总；当前保留为未来能力，不承担任务执行调度职责。

旧项目映射：

- `SimulationAssembler` -> `application/assembly/`
- `Simulator` 单次运行编排 -> `application/execution/`
- `core/batch` -> `application/batch/`

依赖规则：

- 可以依赖 `core/`、`assets/`、`analysis/`、handler 注册表和仓库协议。
- 不依赖 Flet 控件。
- 不直接编写具体 SQLite 查询。
- SQLite 实现通过构造函数注入。
- 第一版不引入重型 DI 框架，使用显式构造函数注入。
- UI / CLI 只调用 `services/` 对外门面；`services/` 可以委托 `jobs/` 或过渡性委托 `execution/`。
- `jobs/` 负责任务状态与调度边界；具体仿真执行委托 `execution/`。
- `execution/` 可以调用 `assembly/` 和 `core/`，但不处理 UI 状态、CLI 参数解析或任务队列持久化。

## 7. `infrastructure/`

`infrastructure/` 是具体技术实现适配层。

负责：

- SQLite。
- 文件路径。
- JSON 文件。
- WAL。
- 异步写入。
- 日志等外部技术细节。

建议结构：

```text
infrastructure/
├── __init__.py
├── assets_sqlite/
├── results_sqlite/
├── jobs/
├── file_storage/
└── logging/
```

职责：

- `assets_sqlite/`：只读资产库实现，例如 `SQLiteAssetRepository`。
- `results_sqlite/`：运行期结果库实现，例如 `SQLiteResultWriter`、`SQLiteResultRepository`、投影器和 schema。
- `jobs/`：后台任务调度的具体技术实现，例如进程池 runner。
- `file_storage/`：项目配置、模板、导出 JSON 等普通文件存储。
- `logging/`：日志相关基础设施。

数据库职责：

```text
data/assets/assets.db    -> 只读资产库
data/results/results.db  -> 可写运行期结果库
```

运行期结果库继续使用 SQLite，继续采用“快照/事件输入 + 投影表存储”的模式。

结果保存策略：

- 所有仿真都保存完整结果数据。
- 不区分 `summary_only` 与 `recorded` 模式。
- 批量扫描产生的数据体积通过结果清理、归档或会话管理策略处理，而不是通过减少记录内容处理。

写入规则：

- 可使用异步队列写入。
- SQLite 建议启用 WAL。
- `core/` 只生成快照和事件数据，不负责写库。
- `results_sqlite/projector.py` 负责将快照和事件投影到 SQLite 表。

## 8. `analysis/`

`analysis/` 是仿真结果分析加工层。

负责把结果库中的原始结果加工成：

- 可解释的数据模型。
- 可展示的数据模型。
- 可比较的数据模型。
- 报告数据模型。

建议结构：

```text
analysis/
├── __init__.py
├── models.py
├── processors/
├── aggregators/
├── timeline/
├── comparison/
└── reports/
```

职责：

- `processors/`：原始结果数据加工，例如伤害、DPS、动作、附着、Buff、机制指标。
- `aggregators/`：摘要聚合，例如总伤害、DPS、角色伤害占比、反应统计、Buff 覆盖率。
- `timeline/`：复盘时间轴数据。
- `comparison/`：多次仿真结果对比。
- `reports/`：结构化报告对象与导出模型。

不负责：

- 运行仿真。
- 写数据库。
- 直接编写 SQLite 查询。
- Flet 控件。
- 具体角色、武器、圣遗物实现。

分析流程：

```text
AnalysisService
-> ResultRepository 读取结果数据
-> analysis processors / aggregators 加工
-> 返回 AnalysisResult
-> UI 展示
```

旧项目中的 `AnalysisDataProcessor` 适合迁入 `analysis/processors/`。

## 9. `ui/`

`ui/` 是 Flet 交互与展示层。

当前决策：

- UI 会大改。
- 暂不做具体页面、状态管理和 ViewModel 设计。
- 仅保留边界原则。

边界原则：

- UI 作为应用入口，通过 `application/` 调用能力。
- UI 不直接组装仿真对象。
- UI 不直接访问 SQLite。
- UI 不直接处理结果库投影。
- UI 不实现分析算法。

后续 UI 设计单独展开。

## 10. `cli/`

`cli/` 是命令行入口。

定位：

- 开发入口。
- 数据构建入口。
- 调试入口。
- 自动化运行入口。
- 不是 UI 的替代品。

第一版命令：

```text
genshin-sim assets build
genshin-sim assets fetch-source
genshin-sim assets build-manifest
genshin-sim assets audit-manifest
genshin-sim assets validate
genshin-sim assets info

genshin-sim config validate path/to/config.json

genshin-sim run config.json

genshin-sim results list
genshin-sim results inspect <session_id>
```

建议结构：

```text
cli/
├── __init__.py
├── main.py
├── assets.py
├── config.py
├── run.py
└── results.py
```

`pyproject.toml` 暴露入口：

```toml
[project.scripts]
genshin-sim = "genshin_sim.cli.main:main"
```

命令职责：

- `assets build`：生成 `data/assets/assets.db`；无 `--manifest` 时生成最小烟测库，带 `--manifest` 时从本地资产 manifest JSON 构建，先写临时库，校验通过后替换正式库。
- `assets fetch-source`：开发期抓取 Project Amber / Yatta 当前默认 API 响应，保存为本地 raw JSON cache；默认抓取角色、武器、圣遗物套装索引和成长曲线，详情通过 `--character-id`、`--weapon-id`、`--artifact-set-id` 或 `--all-details` 显式指定；正式发布和运行时不携带该 cache。
- `assets build-manifest`：开发期把本地 raw JSON cache 转换为标准资产 manifest；第一版转换角色/武器/圣遗物套装基础索引、已有详情文件对应的等级属性、角色核心战斗天赋倍率、角色固有天赋与命座效果参数、武器精炼效果参数和圣遗物套装效果参数。
- `assets audit-manifest`：开发期验收标准资产 manifest 的基础数据质量，检查唯一键、引用关系、等级覆盖、技能倍率和效果参数基础 schema。
- `assets validate`：校验现有资产库 schema、版本、`asset_key`、JSON payload 和 handler。
- `assets info`：输出资产库版本、构建时间、数据版本、角色/武器/圣遗物数量。
- `config validate`：校验 `SimulationConfig` 是否符合当前 schema，但不运行仿真。
- `run`：读取 `SimulationConfig`，组装仿真，运行并保存完整结果。
- `results list`：列出已有仿真会话。
- `results inspect`：查看单个会话摘要与基础元信息。

规则：

- CLI 只作为入口。
- CLI 调用 `application/` 服务。
- CLI 不直接写 SQL。
- CLI 不重复实现仿真组装逻辑。
- UI 不调用 CLI，而是和 CLI 共享 `application/` 服务。
- 数据构建逻辑不塞进 CLI 文件，CLI 只做参数解析和用例调用。
- 第一版使用标准库 `argparse` 即可，后续如有需要再引入 Typer 或 Rich。

## 11. 测试组织

建议测试目录：

```text
tests/
├── unit/
├── integration/
└── golden/
```

职责：

- `unit/`：核心算法、属性计算、事件系统、数据模型等小粒度测试。
- `integration/`：组装、资产仓库、结果库、服务编排测试。
- `golden/`：迁移旧项目能力时保留的数值基准用例。

迁移原则：

- 测试不能直接照搬旧项目测试文件，必须基于新项目架构、配置契约和模块边界重新编写。
- 旧项目测试只能作为行为覆盖范围与数值预期的参考。
- 每迁移一个核心能力，都应补充最小测试或 golden case。
- 伤害、治疗、反应、Buff 覆盖等数值逻辑优先保留 golden case。
