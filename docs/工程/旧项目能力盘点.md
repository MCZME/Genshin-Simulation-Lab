# 旧项目能力盘点

> 状态：持续维护的能力覆盖矩阵。
> 最后更新：2026-08-09。
> 本文档记录旧项目能力在新项目中的保留价值、替代状态与验证缺口。它不规定实施顺序，也不作为具体系统的实现说明。

## 1. 文档定位

本盘点回答以下问题：

- 旧项目具备哪些值得保留或复核的能力。
- 旧能力在新项目中由哪个模块或设计替代。
- 迁移时应保留行为、算法、测试样例，还是仅保留需求背景。
- 当前已经覆盖到什么程度，还缺少哪些可信来源、golden case 或运行时基础。

实施顺序与跨系统依赖见：[迁移阶段安排](./迁移阶段安排.md)。长期边界与已确认结论以 `架构/`、`契约/` 和[项目决策记录](../决策/项目决策记录.md)为准。

## 2. 盘点口径

### 2.1 处理方式

- **参考迁移**：保留旧项目的行为目标、算法思路或测试样例，但按新架构和新契约重新实现。
- **重新设计**：旧项目的模块边界或数据契约不再适用，只保留需求、经验和失败教训。
- **明确舍弃**：确认不进入新项目，并记录原因，避免后续重复评估。
- **待评估**：尚未确认保留价值、可信来源或目标边界。

“直迁”不再作为正式分类。即使旧代码可以局部复用，也必须先通过新模块边界、类型契约和测试要求。

### 2.2 覆盖状态

- **已替代**：新项目已有明确实现和验证入口，旧实现不再承担设计指导职责。
- **部分替代**：新项目已有第一版能力，但尚未覆盖旧项目的完整行为范围。
- **仅有设计**：边界或实施规划已形成，运行时代码尚未完成。
- **待迁移**：确认需要保留，但尚未进入实现。
- **待评估**：是否保留或如何落位尚未确认。
- **不迁移**：已确认舍弃。

覆盖状态描述的是能力范围，不等同于单个文件或提交是否完成。

## 3. 当前总体结论

- 新项目已经越过启动期盘点和单一 MVP 骨架期，运行时、资产、数值系统、内容验证和应用任务正在并行演进。
- 输入、动作、空间、Impact、属性、伤害、生命值、治疗和护盾核心均已按新架构建立第一版边界，不能再按旧项目目录直接搬运。
- 资产库、源站适配、组装和结果持久化已有新实现；旧 MySQL、旧组装器和旧持久化耦合只作为反例或需求来源。
- 真实数值与复杂机制仍必须以可信资料和 golden case 为准。旧测试可以提供候选预期，但不能自动视为正确答案。
- UI 仍属于产品工作流重设计；旧 UI 只可用于识别用户任务，不作为界面结构模板。

### 4.5 明确不迁移

| 旧内容 | 结论 | 原因 |
| --- | --- | --- |
| 旧 MySQL 运行依赖 | 不迁移 | 服务器已销毁，新项目统一使用职责分离的本地 SQLite |
| `core/` 直接访问数据库或 UI | 不迁移 | 违反新项目模块边界 |
| 以显示名称绑定资产或行为 | 不迁移 | 统一使用 `asset_key` 引用资产、`handler_key` 绑定代码 |
| 旧 `TeamActionController` 与单一 busy lock 链路 | 不迁移 | 已由输入会话、统一 `ActionManager`、具名锁和中断策略替代 |
| 旧 UI 页面结构与数据库直连工作流 | 不迁移 | UI 产品形态完全重设计，且只能通过应用服务访问能力 |
| 未经来源复核的旧机制数值 | 不直接迁移 | 旧实现和旧测试只能作为候选参考，不能替代可信资料与 golden case |

## 6. 单项能力迁移要求

每次处理一个能力时，至少更新对应矩阵行，并明确：

```text
保留的行为目标：
旧项目参考：
新项目目标模块：
依赖的现有运行时能力：
可信资料：
测试或 golden case：
明确不迁移的旧设计：
剩余缺口：
```

满足以下条件后，状态才能标记为“已替代”：

- 新实现具有明确的模块所有权和依赖方向。
- 关键行为有单元测试、集成测试或 golden case。
- 旧项目中仍有价值但未覆盖的行为已明确登记为缺口或明确舍弃。
- 对应架构、契约或决策文档已经同步。

## 7. 维护规则

- 本文只维护能力覆盖，不维护开发先后顺序。
- 大能力必须拆成可独立判断状态的行，不能把生命、护盾、能量或多种地区规则合并为一个迁移项。
- 新系统第一版完成时，优先标记为“部分替代”；只有覆盖范围和明确舍弃项都可解释时才标记“已替代”。
- 具体实现细节进入系统设计或实现规划，不在矩阵备注中重复展开。
- 迁移路线变化同步更新[迁移阶段安排](./迁移阶段安排.md)，长期决策变化同步更新[项目决策记录](../决策/项目决策记录.md)。
