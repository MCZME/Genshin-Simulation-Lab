# 元素能量系统契约

> 状态：正式。本文记录当前已经实现并可由 Runtime、Impact、事件、快照和组装层依赖的稳定契约。
>
> `BurstEnergyConditionStatus`、`BurstEnergyConditionResult` 与 `EnergyRuntime.query_burst_condition()` 已作为只读公共条件证据实现。角色能力条件协调器的组合结果契约见[角色能力条件协调器契约](./角色能力条件协调器契约.md)；Action 解释上下文注入仍不属于当前能量领域契约。

最后更新：2026-07-14

## 1. 适用边界

本契约适用于：

```text
core/entity_states/energy.py
core/systems/energy/
core/events/ 中的能量事件
core/snapshots/ 中的能量快照
ImpactKind.ENERGY
application/assembly/ 的能量组装
assets / SQLite 的 burst_energy_cost
```

系统职责和依赖方向见[元素能量系统设计](../架构/系统/元素能量系统设计.md)。

## 2. 稳定术语

| 术语 | 含义 |
| --- | --- |
| 标准元素能量 | 标准元素爆发消耗的角色资源 |
| capacity | 角色标准元素能量上限，同时是标准爆发完整消耗量 |
| 微粒 | `pickup_kind = particle` 的队伍能量载体 |
| 晶球 | `pickup_kind = orb` 的队伍能量载体 |
| 无元素 | `clear`，独立于七种角色元素 |
| 生成帧 | 载体进入 `EnergyTransitQueue` 的帧 |
| 结算帧 | 载体向当前队伍分配能量的帧 |
| 请求量 | 公式或调用方请求改变的非负数值 |
| 实际量 | 经过上下限约束后真实改变状态的非负数值 |
| 未应用量 | 恢复溢出或扣除不足部分 |

## 3. 稳定枚举

### 3.1 `EnergyElement`

```text
pyro
hydro
electro
cryo
anemo
geo
dendro
clear
```

- 角色能量档案只能使用七种角色元素。
- 微粒和晶球可以使用七种元素或 `clear`。
- 能量领域不复用伤害或护盾元素枚举。

### 3.2 `EnergyPickupKind`

```text
particle
orb
```

### 3.3 `EnergyChangeKind`

```text
pickup_restore
direct_restore
direct_drain
burst_spend
```

### 3.4 `EnergyRecipientStatus`

```text
applied
capped
no_elemental_energy_resource
```

- `applied`：实际获得量大于 `0`。
- `capped`：请求量为正，但角色已满能量，实际量为 `0`。
- `no_elemental_energy_resource`：`capacity = 0`，不查询充能效率，也不创建角色能量变化结果。

## 4. 状态与档案

### 4.1 `EnergyState`

```text
current_energy: float
```

不变量：

```text
current_energy 是有限数
current_energy >= 0
```

`EnergyState` 不保存元素、上限、来源、场上状态或爆发就绪状态。业务写入只能由 `EnergyRuntime` 发起。

### 4.2 `CharacterEnergyProfile`

```text
character_ref: AttributeSubjectRef(character)
character_key: str
element: EnergyElement
capacity: float
```

不变量：

- `character_ref` 必须是角色主体。
- `character_key` 必须是非空稳定资产 key。
- `element` 不能是 `clear`。
- `capacity` 必须是有限非负数。
- `capacity = 0` 表示不使用标准元素能量。

档案在组装阶段冻结，不由属性 modifier 动态改变。

### 4.3 `CharacterEnergyStore`

Store 索引：

```text
AttributeSubjectRef.character(combat_entity_id)
-> CharacterEnergyProfile
-> EnergyState
```

Store 必须：

- 拒绝重复角色引用。
- 校验 `0 <= current_energy <= capacity`。
- 对 `capacity = 0` 强制 `current_energy = 0`。
- 保存单调版本号和已提交 operation id。
- 在提交前校验期望版本和角色能量前值。
- 一次提交载体涉及的全部角色新值。

Store 不查询属性、不计算倍率、不发布事件。

### 4.4 `EnergyPickupRecord`

```text
pickup_id: str
request_id: str
created_frame: int
settle_frame: int
pickup_kind: EnergyPickupKind
element: EnergyElement
count: int
source_ref: AttributeSubjectRef | None
source_context: RuntimeSourceRef | None
tags: frozenset[str]
spawn_order: int
```

规则：

- `pickup_id` 由系统生成。
- `request_id` 由上游提供，用于幂等和审计。
- `count` 必须是正整数。
- `settle_frame >= created_frame`。
- `spawn_order` 由 Runtime 单调分配。
- 一个记录可以代表同时生成且同时到达的多个同类载体。
- 浮点期望产球量不进入 `count`。

### 4.5 `EnergyTransitQueue`

队列稳定排序键为：

```text
(settle_frame, created_frame, spawn_order, pickup_id)
```

同帧多个载体按该顺序逐个结算。队列必须拒绝重复 `request_id` 和重复 `pickup_id`，并为前值校验维护单调版本号。

## 5. 强类型请求

### 5.1 `SpawnEnergyPickupRequest`

```text
request_id: str
frame: int
pickup_kind: EnergyPickupKind
element: EnergyElement
count: int
travel_frames: int
source_ref: AttributeSubjectRef | None
source_context: RuntimeSourceRef | None
tags: frozenset[str]
```

约束：

- `frame` 和 `travel_frames` 是非负整数。
- `count` 是正整数。
- `settle_frame = frame + travel_frames`。
- 真实 content 必须显式提供延迟，核心没有默认真实延迟。

### 5.2 `RestoreEnergyRequest`

```text
change_id: str
frame: int
target_ref: AttributeSubjectRef(character)
amount: float
source_ref: AttributeSubjectRef | None
source_context: RuntimeSourceRef | None
tags: frozenset[str]
```

`amount` 必须是有限非负数。直接恢复不读取元素、队伍人数、前后台或充能效率。

### 5.3 `DrainEnergyRequest`

字段与 `RestoreEnergyRequest` 相同。语义为从目标当前能量扣除最多 `amount`，不足部分进入 `unapplied_amount`。

### 5.4 `SpendBurstEnergyRequest`

```text
change_id: str
frame: int
target_ref: AttributeSubjectRef(character)
action_instance_id: str
source_context: RuntimeSourceRef | None
tags: frozenset[str]
```

规则：

- 只用于标准元素爆发。
- Runtime 从 `CharacterEnergyProfile.capacity` 读取消耗量。
- `capacity` 必须大于 `0`。
- 当前能量必须不少于 `capacity`，否则抛出 `InsufficientEnergyAtSpendError`。
- 成功后当前能量变为 `0`。

固定数值扣能或最多扣除当前能量使用 `DrainEnergyRequest`，不能伪装成爆发消耗。

## 6. 结果模型

### 6.1 `CharacterEnergyChangeResult`

```text
change_id
frame
change_kind
target_ref
source_ref
source_context
requested_amount
effective_amount
unapplied_amount
energy_before
energy_after
capacity
delta
tags
```

不变量：

```text
requested_amount >= 0
effective_amount >= 0
unapplied_amount >= 0
requested_amount = effective_amount + unapplied_amount
0 <= energy_before <= capacity
0 <= energy_after <= capacity
delta = energy_after - energy_before
```

- `direct_restore` 和 `pickup_restore` 的 `delta >= 0`。
- `direct_drain` 和 `burst_spend` 的 `delta <= 0`。
- amount 字段始终是非负绝对值。

### 6.2 `EnergyRecipientResolution`

```text
target_ref
slot
status
is_active
character_element
pickup_element
pickup_kind
count
kind_multiplier
element_multiplier
field_multiplier
recharge_bonus
recharge_multiplier
base_amount
requested_amount
change_result | None
```

`capacity = 0` 时必须满足：

```text
status = no_elemental_energy_resource
recharge_bonus = None
recharge_multiplier = None
requested_amount = 0
change_result = None
```

### 6.3 `EnergyPickupSettlementResult`

```text
pickup: EnergyPickupRecord
settled_frame: int
active_slot: int
team_size: int
recipients: tuple[EnergyRecipientResolution, ...]
```

`recipients` 按角色槽位升序排列，保存一次队伍分配的完整审计。

## 7. 微粒与晶球公式

### 7.1 倍率

种类倍率：

```text
particle -> 1
orb      -> 3
```

元素倍率：

```text
pickup.element == character.element -> 3
pickup.element == clear             -> 2
其他                                 -> 1
```

前后台倍率：

```text
active   -> 1.0
inactive -> 1.0 - 0.1 * team_size
```

| 队伍人数 | 场上 | 后台 |
| --- | ---: | ---: |
| 1 | 1.0 | 不存在 |
| 2 | 1.0 | 0.8 |
| 3 | 1.0 | 0.7 |
| 4 | 1.0 | 0.6 |

`capacity = 0` 的角色仍计入队伍人数。

### 7.2 元素充能效率

`stat.energy_recharge` 表示相对基础 100% 的加成比例：

```text
recharge_multiplier = 1 + recharge_bonus
```

示例：

```text
0.0 -> 100% -> 1.0
0.5 -> 150% -> 1.5
2.0 -> 300% -> 3.0
```

倍率必须是有限正数。属性查询失败或得到非法倍率时，整个载体结算失败。

### 7.3 完整公式

```text
base_amount = count
              * kind_multiplier
              * element_multiplier
              * field_multiplier

requested_amount = base_amount * recharge_multiplier
effective_amount = min(requested_amount, capacity - energy_before)
energy_after = energy_before + effective_amount
unapplied_amount = requested_amount - effective_amount
```

核心不提前舍入，结果保留 Python `float`。

## 8. 直接变化规则

### 8.1 直接恢复

```text
effective_amount = min(requested_amount, capacity - energy_before)
energy_after = energy_before + effective_amount
unapplied_amount = requested_amount - effective_amount
```

对 `capacity = 0` 的目标抛出 `UnsupportedEnergyResourceError`。

### 8.2 直接扣除

```text
effective_amount = min(requested_amount, energy_before)
energy_after = energy_before - effective_amount
unapplied_amount = requested_amount - effective_amount
```

允许部分扣除并降到 `0`。

### 8.3 爆发消耗

```text
requested_amount = capacity
effective_amount = capacity
unapplied_amount = 0
energy_after = 0
```

动作准入与实际扣能之间不做隐式预留。扣能帧能量不足属于运行时错误。

## 9. 帧与顺序

### 9.1 载体结算

结算帧读取：

- 当前 `active_slot`。
- 当前实际队伍人数。
- 每个标准资源角色当前能量。
- 每个标准资源角色当前 `stat.energy_recharge`。

产球帧的场上角色或充能效率不进入结算公式。

### 9.2 同帧顺序

```text
ActionManager
-> ImpactRuntime
-> EnergyRuntime
```

因此同帧直接变化和爆发消耗先于载体到达结算；同帧切人也先于载体结算。

同帧到达集合在 `EnergyRuntime.update_frame()` 开始时冻结。事实事件 handler 不能把新载体插入当前结算轮次。

### 9.3 停止条件

```text
EnergyTransitQueue 非空 -> EnergyRuntime.is_idle() == False
```

直接变化没有待处理状态时不延长仿真。

## 10. `ImpactKind.ENERGY`

### 10.1 创建载体

```json
{
  "energy": {
    "schema_version": 1,
    "operation": "spawn_pickup",
    "pickup_kind": "particle",
    "element": "hydro",
    "count": 3,
    "travel_frames": 42,
    "tags": []
  }
}
```

### 10.2 直接恢复或扣除

```json
{
  "energy": {
    "schema_version": 1,
    "operation": "restore",
    "amount": 6.0,
    "tags": []
  }
}
```

`operation = drain` 使用相同字段。

### 10.3 爆发消耗

```json
{
  "energy": {
    "schema_version": 1,
    "operation": "spend_burst",
    "action_instance_id": "action:27",
    "tags": []
  }
}
```

约束：

- `schema_version` 必须为 `1`。
- 每个 operation 的字段集合封闭，未知字段被拒绝。
- `tags` 可省略；存在时必须是字符串数组，其中每个元素都是非空字符串，空数组合法。
- `spawn_pickup` 不使用 `target_refs`。
- 其他三种操作必须解析为一个明确角色目标。
- 真实 content 必须显式提供数量、延迟和扣能时点。

## 11. 事件契约

### 11.1 事件类型

| 事件 | 分类 | 发布条件 |
| --- | --- | --- |
| `ENERGY_PICKUP_SPAWNED` | `STATE_CHANGE` | 载体已进入队列 |
| `ENERGY_PICKUP_SETTLED` | `FACT` | 全队状态已提交且载体已移除；即使实际获得均为 0 也发布 |
| `DIRECT_ENERGY_CHANGE_RESOLVED` | `FACT` | 合法直接变化已完成；即使实际变化为 0 也发布 |
| `CHARACTER_ENERGY_CHANGED` | `STATE_CHANGE` | `effective_amount > 0` |

四类事件默认记录、结果已经提交且可以驱动后续机制。

### 11.2 payload

```text
EnergyPickupSpawnedPayload.record: EnergyPickupRecord
EnergyPickupSettledPayload.result: EnergyPickupSettlementResult
DirectEnergyChangeResolvedPayload.result: CharacterEnergyChangeResult
CharacterEnergyChangedPayload.result: CharacterEnergyChangeResult
```

### 11.3 顺序

载体结算：

```text
提交全队状态并移除载体
-> ENERGY_PICKUP_SETTLED
-> 按槽位发布有效 CHARACTER_ENERGY_CHANGED
```

直接变化：

```text
提交角色状态
-> DIRECT_ENERGY_CHANGE_RESOLVED
-> 有效变化时 CHARACTER_ENERGY_CHANGED
```

创建载体：

```text
记录入队
-> ENERGY_PICKUP_SPAWNED
```

事件发布期间同步能量写入必须抛出 `EnergyReentrancyError`。事件 handler 抛错不回滚已提交状态。

## 12. 快照契约

`SimulationSnapshot.energy` 为可选对象；上下文注册 `EnergyRuntime` 时包含：

```text
energy
├── frame
├── characters[]
│   ├── character_ref
│   ├── character_key
│   ├── element
│   ├── current_energy
│   ├── capacity
│   └── burst_ready
└── pending_pickups[]
    ├── pickup_id
    ├── request_id
    ├── created_frame
    ├── settle_frame
    ├── pickup_kind
    ├── element
    ├── count
    ├── source_ref
    ├── source_context
    ├── tags
    └── spawn_order
```

角色按队伍槽位排列，载体按队列稳定键排列。

## 13. 错误契约

```text
EnergySystemError
├── EnergyValidationError
├── CharacterEnergyNotFoundError
├── UnsupportedEnergySubjectError
├── UnsupportedEnergyResourceError
├── UnsupportedEnergyElementError
├── UnsupportedEnergyOperationError
├── InvalidEnergyAttributeError
├── EnergyPlanConflictError
├── EnergyReentrancyError
├── DuplicateEnergyRequestError
├── EnergyPickupNotFoundError
└── InsufficientEnergyAtSpendError
```

| 错误 | 典型场景 |
| --- | --- |
| `EnergyValidationError` | 帧、数值、count、延迟、标签、id 或 Impact payload 非法 |
| `CharacterEnergyNotFoundError` | 角色未登记到 Store |
| `UnsupportedEnergySubjectError` | 目标不是角色主体 |
| `UnsupportedEnergyResourceError` | 对 `capacity = 0` 角色执行标准能量直接操作 |
| `UnsupportedEnergyElementError` | 未知元素或角色使用 `clear` |
| `UnsupportedEnergyOperationError` | Impact operation 未知 |
| `InvalidEnergyAttributeError` | 充能效率解析失败或产生非法倍率 |
| `EnergyPlanConflictError` | Store、Queue 或前值冲突 |
| `EnergyReentrancyError` | 提交或事实发布期间尝试同步写入 |
| `DuplicateEnergyRequestError` | 相同 request/change id 重复提交 |
| `EnergyPickupNotFoundError` | 载体不存在或已经结算 |
| `InsufficientEnergyAtSpendError` | 爆发扣能帧能量不足 |

错误消息应携带可定位的稳定 id、角色引用或字段路径。

## 14. 资产与组装契约

### 14.1 持久化字段

SQLite 资产 schema `2`：

```text
characters.burst_energy_cost REAL NOT NULL
```

manifest 中每个角色也必须显式提供 `burst_energy_cost`。转换器从角色详情中唯一 `talent.type == 1` 的 `cost` 读取，拒绝缺详情、缺成本、多个爆发天赋、非数字、非有限或负数。

### 14.2 内存资产

```text
CharacterAsset.burst_energy_cost: float | None
```

`None` 只表示不完整或兼容资产对象，不是专属资源。`SimulationAssembler` 必须拒绝 `None`。

### 14.3 组装

组装必须：

1. 按队伍槽位绑定 `RuntimeAssetBundle`，不能按配置数组下标猜测。
2. 显式映射资产元素到 `EnergyElement`。
3. 为每个角色创建 `CharacterEnergyProfile` 和初始为 `0` 的 `EnergyState`。
4. 创建 Store、Queue、Runtime 和 Impact handler。
5. 将 Runtime 放在 `ImpactRuntime` 之后推进。
6. 向 `AssembledSimulation` 暴露能量 Store、Queue、Runtime 和 handler。

第一版不修改 `SimulationConfig`，所有角色从 `0` 开始。

## 15. 原子性、幂等与重入

### 15.1 载体批量结算

一次载体结算必须先完成全部角色的档案、前值、充能效率和结果计算，再校验 Store/Queue version，最后提交。

任一步失败都必须满足：

```text
所有角色能量不变
载体仍在队列
不发布能量事实
```

### 15.2 幂等域

- 载体 `request_id` 在 Queue 生命周期内全局去重，并在结算后继续保留已提交身份。
- `RestoreEnergyRequest`、`DrainEnergyRequest` 和 `SpendBurstEnergyRequest` 共享外部 `change_id` 幂等域。
- 内部载体结算 operation 与外部直接变化使用隔离命名空间。
- 内部 operation id 不属于事件或结果的公共 API。

### 15.3 重入

Runtime 在状态提交和事实发布期间拒绝新的能量写入。只读查询不受影响。

## 16. 确定性要求

- 所有外部数字先拒绝 `bool`，再校验有限性和范围。
- 乘法中间量必须保持有限非负。
- `-0.0` 规范化为 `0.0`。
- 不使用未记录 epsilon 判定满能量。
- 排序不依赖 dict、set、显示名称或 content 注册顺序。
- 概率产球必须由上游仿真 RNG 先解析成确定整数。

## 17. 最小验证基线

当前至少覆盖以下案例：

### 17.1 四人队同元素微粒

```text
slot 1：火，场上，100% -> 3.0
slot 2：火，后台，100% -> 1.8
slot 3：水，后台，150% -> 0.9
slot 4：capacity = 0 -> no_elemental_energy_resource
```

### 17.2 三人队无元素晶球

```text
场上 -> 6.0
后台 -> 4.2
```

### 17.3 结算前切人

frame 10 生成、frame 39 切人、frame 40 结算时，frame 40 的场上角色使用 `1.0` 倍率。

### 17.4 同帧扣能与载体到达

同帧爆发消耗先提交，随后载体结算，最终能量大于 `0`。

### 17.5 失败与边界

- 第二个角色充能属性查询失败时全队不变且载体保留。
- 相同 `change_id` 跨恢复、扣除和爆发消耗只提交一次。
- 外部 `change_id` 不得阻塞内部载体结算。
- 事实事件 handler 同步写能量被拒绝。
- 旧 schema 数据库不能被误标为 schema `2`。
- 乱序队伍配置仍按槽位绑定正确资产档案。

真实角色的产球与爆发 rotation golden case 仍待 content 迁移。

## 18. 公共条件接口

以下能量领域只读 API 已实现，并供角色能力条件协调器通过窄端口使用：

- `BurstEnergyConditionStatus`
- `BurstEnergyConditionResult`
- `EnergyRuntime.query_burst_condition()`

`CharacterAbilityConditionCoordinator` 位于 `core/coordination/`，不属于能量领域 Runtime；`ActionInterpretationContext.ability_condition_port` 的注入和真实角色动作接入仍是后续工作，不能由能量领域隐式承担。
