# 护盾系统设计

> 状态：领域聚合与角色受伤端口第一版已实现。
> 本文冻结角色侧护盾的领域职责、状态所有权、吸收规则和目标运行流程。精确目标字段见[护盾系统契约](../../契约/护盾系统契约.md)。

最后更新：2026-07-13

## 1. 范围

护盾系统负责：

- 在创建帧解析护盾原生吸收量。
- 管理护盾授予、刷新、替换、叠加、共存和移除。
- 原子保存护盾实例元数据、生命周期和领域状态。
- 根据受伤目标解析全部适用保护范围。
- 对同一次角色伤害并行结算全部匹配护盾。
- 在承伤帧动态读取受保护角色的护盾强效。
- 生成护盾领域结果和已经提交的事实。

护盾系统不负责：

- 角色生命提交和最终 `DAMAGE_APPLIED` 事实。
- 敌方元素盾、敌人护盾条或破盾元素量。
- 敌人对角色的完整伤害公式。
- 伤害减免、无敌、格挡、闪避和免疫。
- 抗打断、韧性和击退的完整结算。
- 元素附着、反应、结晶晶片创建和拾取。
- 侵蚀、生命流失或其他直接扣血机制。
- UI、分析图表或专用结果数据库投影。

角色受伤跨系统协调见[角色受伤协调器设计](../协调/角色受伤协调器设计.md)。

## 2. 依据与可信度

当前通用行为基线沿用已有资料核对结果：

- [KQM 护盾机制](https://library.keqingmains.com/combat-mechanics/damage/shields)：基础吸收量、护盾强效、元素倍率、多盾同时承伤和创建属性快照。
- [KQM 护盾证据库](https://library.keqingmains.com/evidence/combat-mechanics/damage/shields)：伤害减免顺序、同元素倍率和快照证据。
- [Genshin Impact Wiki - Shield](https://genshin-impact.fandom.com/wiki/Shield)：溢出伤害、多盾并行、岩盾倍率和当前场上角色护盾强效的交叉核对。

这些资料只支撑通用表达能力。具体角色、武器、圣遗物和反应的倍率、持续时间、叠加上限和例外在接入时重新核对当前版本，并提供 golden case。

## 3. 核心决策

- 护盾不是额外生命，不进入 `HealthState`。
- 护盾实例由 `ShieldStore` 以领域专用 `ShieldRecord` 直接拥有；通用原则见[领域运行态设计](../领域运行态设计.md)。
- `ShieldStore` 中每条活动记录同时包含实例元数据、生命周期和 `ShieldState`。
- 创建者属性在创建帧解析；护盾强效在每次承伤帧动态查询。
- 活动状态保存未乘动态护盾强效的原生容量。
- 多个不同护盾同时承受同一份来伤，不把容量相加。
- 来伤请求只指定受伤角色，不能指定要使用哪个 protection ref。
- ShieldRuntime 不依赖 HealthRuntime，不发布最终伤害应用事件。
- 抗打断不是护盾状态上的预留布尔字段；后续由正式能力协议从活动护盾派生贡献。

## 4. 目标结构

```text
ShieldImpactRequestHandler
-> ShieldGrantRequest
-> ShieldResolver
-> ShieldGrantResolution
-> ShieldRuntime
   ├── ShieldStore -> ShieldRecord
   ├── AttributeResolver
   ├── ShieldProtectionResolver
   └── Event/Facts adapter
```

角色受伤链路：

```text
CharacterDamageTakenCoordinator
-> ShieldRuntime.prepare_absorption()
-> HealthRuntime.prepare_damage()
-> 校验并提交完整计划
-> ShieldRuntime 发布护盾事实
-> HealthRuntime 发布生命事实
-> DAMAGE_APPLIED
```

## 5. 状态所有权

### 5.1 ShieldRecord

完整护盾实例：

```text
ShieldRecord
├── instance_ref
├── mechanic_key
├── handler_key
├── created_frame
├── expires_at_frame
├── lifecycle_state
├── removed_frame?
├── removal_reason?
└── state
    ├── protection_ref
    ├── creator_ref
    ├── source_context
    ├── element
    ├── maximum_native_absorption
    ├── remaining_native_absorption
    ├── conflict_key
    ├── grant_snapshot_ref
    └── tags
```

规则：

- instance ref、mechanic key、handler key 和生命周期只保存一次。
- protection ref 同时提供护盾影响范围和领域清理依据；不额外保存可由它推导的通用 anchor。
- 活动护盾必须满足 `0 < remaining <= maximum`。
- 耗尽记录在同一次 Store 提交中进入 removed 状态，并保留 `remaining=0` 的最终审计状态。
- Store 中不能存在缺少 ShieldState 的 shield instance。

### 5.2 ShieldStore

`ShieldStore` 直接拥有全部 `ShieldRecord` 并提供：

- protection ref 和 conflict key 领域索引。
- 创建、刷新、替换和移除的完整记录提交。
- 并行吸收的批量完整记录替换。
- 到期和显式移除审计。

外部只能读取不可变记录或只读 view。content、事件 handler 和其他领域系统不能直接调用 Store 写入口。

## 6. 保护对象

### 6.1 active_team

普通角色护盾默认保护对应玩家队伍的当前场上角色：

```text
kind = active_team
protection_id = team:player
```

承伤时由 `ShieldProtectionResolver` 判断来伤目标是否是该队伍当前角色。切人不转移或重建护盾实例，只改变该帧实际受保护角色与动态护盾强效查询主体。

### 6.2 character

固定角色保护只匹配指定角色 entity id，可用于未来联机或特殊内容规则。

### 6.3 匹配规则

`CharacterIncomingDamage` 不携带 protection ref。ShieldRuntime 根据 target ref 收集所有匹配保护范围；同一目标可以同时获得 active-team 和 character 护盾保护。

不匹配的护盾不是错误。保护范围配置无效、队伍不存在或引用无法解析才是结构化错误。

## 7. 创建公式

```text
BaseAbsorption = fsum(CreatorAttribute[i] * Coefficient[i]) + FlatAbsorption
NativeAbsorption = BaseAbsorption * product(NativeMultiplier[i])
```

规则：

- 创建者属性在 request frame 查询并冻结。
- coefficient、固定值和原生倍率为有限非负数。
- base absorption 和最终 native absorption 为有限正数。
- NativeMultiplier 表示护盾自身描述中的额外吸收效果，不是公共护盾强效。
- 可叠加护盾可使用同结构的独立公式计算容量上限。
- Resolution 保存公式分量、属性 trace、来源和查询帧。

## 8. 动态护盾强效

护盾强效使用公共属性：

```text
bonus.shield.strength
```

承伤帧查询：

```text
subject_ref = incoming target
frame = incoming frame
shield_strength_multiplier = 1 + bonus.shield.strength
```

乘数必须为有限正数。动态值不写入 ShieldState，也不改变原生最大容量真值。

## 9. 元素吸收倍率

| 护盾类型 | 来伤类型 | 倍率 |
| --- | --- | ---: |
| 岩元素护盾 | 任意伤害 | 1.5 |
| 非岩元素护盾 | 同元素伤害 | 2.5 |
| 其他组合 | 任意伤害 | 1.0 |

```text
EffectiveMultiplier = ElementMultiplier * ShieldStrengthMultiplier
NativeCost = min(RemainingNative, IncomingDamage / EffectiveMultiplier)
NativeAfter = RemainingNative - NativeCost
AbsorbableDamage = min(IncomingDamage, RemainingNative * EffectiveMultiplier)
```

接近零的浮点残差按护盾契约归一化为零。

## 10. 多盾并行吸收

全部匹配活动护盾使用同一份输入独立计算：

```text
ShieldHitResult[i] = resolve(matched_shield[i], incoming_damage)
ProtectedDamage = max(AbsorbableDamage[i], default=0)
HealthBoundDamage = IncomingDamage - ProtectedDamage
```

禁止容量相加或逐盾串行抵扣。所有 hit 和完整记录替换集先计算，再通过 Store version 和完整记录前值一次提交。

## 11. 授予与冲突策略

冲突查找键为：

```text
protection_ref + conflict_key
```

### 11.1 replace

- 在同一 Store 事务中把旧记录标记为 replaced，并创建新 instance ref。
- 旧记录移除与新记录创建要么同时成功，要么都不发生。

### 11.2 refresh_replace

- 保留 instance ref。
- 容量替换为本次授予量。
- 生命周期刷新为新过期帧。

### 11.3 add_capped_refresh

- 保留 instance ref。
- `remaining_after = min(remaining_before + granted, capacity_limit)`。
- maximum 更新为本次解析的 capacity limit。
- 同时刷新生命周期。

### 11.4 keep_stronger_refresh

- 保留 instance ref。
- remaining 和 maximum 分别保留旧值与新授予量中的较大值。
- 无论容量是否变化都刷新生命周期。

### 11.5 coexist

- 不与不同 conflict key 合并。
- 同一 protection ref 上不同 conflict key 可以并存。
- 当前同一冲突键最多一个活动实例。

策略仍由类型化授予请求显式给出。接入真实 content 后，若同一 mechanic key 永远使用固定策略，应把策略固化到组装期定义并增加一致性校验。

## 12. 生命周期

护盾使用有限半开生命周期：

```text
created_frame <= frame < expires_at_frame
```

ShieldRuntime 在 Action 和 Impact 前提交到期记录。到期帧产生的新授予视为新实例或按当时活动冲突重新决策，不能刷新已经到期的旧记录。

纯护盾存在本身不延长仿真；若未来到期触发后续效果，该内容必须登记明确的未来工作，不能依赖共享机制 Store 猜测。

## 13. 准备与提交

授予、移除和吸收均使用领域计划：

```text
计算完整结果
-> 构造 ShieldMutationPlan
-> 校验 Store version 和完整记录前值
-> 一次提交全部记录
-> 生成结果与事实
-> 发布事实
```

吸收计划由角色受伤协调器准备并统一预校验；预校验后的提交只应用完整记录替换，不再查询、计算或发布事件。未来触发行为进入下一结算轮次。

## 14. 事件顺序

授予：

```text
SHIELD_REMOVED(reason=replaced)   # 仅替换
-> SHIELD_CAPACITY_CHANGED        # 仅刷新导致容量变化
-> SHIELD_GRANTED
```

承伤：

```text
SHIELD_CAPACITY_CHANGED（instance ref 顺序）
-> SHIELD_REMOVED(depleted，instance ref 顺序）
-> SHIELD_ABSORPTION_RESOLVED
```

血量变化和最终角色受伤事实由 CharacterDamageTakenCoordinator 在护盾事实之后发布。零伤害不消耗护盾；无匹配护盾时不发布吸收事实。

## 15. Impact 与组装

护盾继续使用 `ImpactKind.SHIELD`。Handler 把结构化 payload 转成 `ShieldGrantRequest`，来源上下文由已注册 content 和 ImpactRequest 推导，不允许 payload 任意覆盖。

目标装配结果暴露：

- `ShieldStore` 的只读访问入口。
- `ShieldResolver`。
- `ShieldRuntime`。
- `ShieldImpactRequestHandler`。
- `CharacterDamageTakenCoordinator`。

其他系统只能获得护盾领域的只读 view 和类型化端口。

## 16. 快照、持久化与分析

护盾快照保存完整活动实例视图：

- 完整 instance ref、mechanic key 和 handler key。
- protection、creator 和 source context。
- 元素、原生最大与剩余吸收量。
- 创建帧和过期帧。
- tags。

快照不保存指定角色和来伤元素下推导出的有效盾量作为真值。结果持久化继续复用通用事件 JSON；专用投影由真实分析需求驱动。

## 17. 错误边界

护盾系统区分：

- 输入和值对象验证错误。
- 创建公式或动态属性查询错误。
- 保护范围不存在或无法解析。
- 授予策略和冲突错误。
- ShieldStore version 或完整记录前值冲突。
- 计划重复提交和结算重入。

非法状态不能 clamp 后继续运行，也不能静默跳过缺失领域状态的实例。

## 18. 验证基线

除现有数值行为外，目标架构新增以下验收：

- Store 中不存在拆分或缺失的护盾聚合。
- 创建、替换、刷新、耗尽和到期均为单 Store 原子提交。
- mechanic key、handler key 和生命周期没有重复真值。
- 来伤不携带 protection ref，且能匹配多个适用保护范围。
- 护盾准备失败不修改生命；生命准备失败不修改护盾。
- 事实只能观察到提交前或提交后的完整状态。
- 抗打断字段在正式系统设计前不进入 ShieldState。

## 19. 当前实现

ShieldStore 已直接拥有完整 ShieldRecord。授予、刷新、替换、移除、到期和吸收均以完整记录替换提交；角色伤害应用由独立 CharacterDamageTakenCoordinator 编排。真实护盾 content 必须通过当前类型化请求和协调器接口接入。
