# 分析区域节点运行时草案

> 状态：已落地（2026-09-03 登记决策 2.55）。本文保留为设计过程记录，正式真值以
> [分析系统设计](../架构/分析系统设计.md)、[分析区域设计](../架构/UI/分析区域设计.md)、
> [分析系统契约](../契约/分析系统契约.md)与[项目决策记录](../决策/项目决策记录.md)为准。

## 1. 背景与问题

当前分析区域采用「整图编译」执行模型：前端把区域内从边界可达的取数/算子子图编译为结构化查询计划，
一次提交 `POST /api/v1/analysis/query`，后端把整条子图编译成 CTE 链一次执行，中间结果不出后端。

这套模型暴露了三类限制：

1. **节点不是独立运行单元**：分析区域像一个大方法，只有输入输出。节点状态、中间表和单节点失败重试
   都不是一等对象。
2. **视图打断数据流**：视图被定义为展示终端，`selection` 由点击在客户端派生；契约虽然把饼图/柱状图
   selection 登记为 `table`，但“下游算子继续消费”没有真正打通，视图后的数据处理节点无法处理数据。
3. **缺少数据构造能力**：现有算子只能基于已有行做有限派生，无法方便地为角色状态详情等节点构造
   `(session_id, frame, character_key, attribute_key)` 形式的描述符行。

产品方向希望工作流表达为**有顺序的流程**：每个节点独立接收输入、独立处理、独立物化输出；视图可以位于
流程中间；视图输出（含用户选择）可以被后续节点继续消费；未来新增列级改写与行级生成节点。

## 2. 已对齐的边界

讨论后确认以下边界不变：

- 前端不直接访问后端 SQLite，不组装查询 SQL；取数、算子和状态折叠的语义由后端唯一持有。
- 前端只通过 `server` 暴露的 HTTP API 编排流程与获取展示数据。
- 工作流图仍是无环有向图，边顺序表达节点执行顺序；同一节点只执行一次，下游只在上游之后执行。
- 派生分析结果可重建、不写入结果库真值；节点参数与图结构随工作流保存，节点运行态不随工作流保存。
- 相同工作流定义、输入、参数、顺序与数据必须得到相同结果；交互选择如果影响结果，必须能够被
  表达为可复现的参数或明确的瞬态语义。

## 3. 目标模型

### 3.1 数据面与控制面分离

- 数据与计算留在后端：后端持有每个节点执行后的**阶段结果表**（stage），前端不搬运中间表。
- 前端负责控制面：按拓扑序向后端提交「执行节点」请求，接收节点状态与需要渲染的终端数据。
- 节点的输出不是隐式 SQL 中间态，而是可寻址、可缓存、可被下游引用的阶段引用。

### 3.2 节点运行态

每个分析节点在运行时拥有独立状态：

```text
node_state = {
  status: idle | loading | ready | error | stale,
  output_stage: stage_ref | null,   // 本节点输出表（后端持有）
  input_stages: [stage_ref, ...],   // 本次执行使用的输入
  version: number,                  // 输入或参数变化后的执行版本
  error: node_error | null,
}
```

参数或任一输入变化时，只使受影响节点的下游置脏并按拓扑序增量重算；未变化的节点保留旧输出，避免整区
大方法式重跑。

### 3.3 视图节点

视图节点是流程中的普通成员：

- `member_table` / `pie` / `bar` 读取数据阶段的表用于渲染；
- 视图统一只保留 `selection` 输出端口，不提供 data 透传；
- 用户点击产生的 `selection` 不是“前端从表里再筛一份后本地继续加工”，而是提交**选择意图**
  （命中哪个阶段、哪组或哪些行），由后端生成选择阶段；选择阶段驱动的下游分支只在用户
  选中时执行。

### 3.4 描述符与构造节点

角色状态详情等单项节点仍消费单行表或阶段行；构造描述符的列级改写、行级生成节点与现有取数/算子
在同一运行时内实现，不依赖视图后的本地加工。

## 4. 阶段（Stage）概念

阶段是后端分析运行上下文中的一张派生结果表：

```text
stage = {
  stage_id: string,
  columns: [column, ...],     // 名称 + 类型
  rows: [row, ...],           // 按当前上限策略截断或分页读取
  source_node_id: string,
  version: number,
}
```

阶段来源：

- `fetch`：从结果库读取并提取列；
- 表算子：消费一个或多个上游阶段，应用过滤/投影/聚合/连接/计算等；
- 视图 selection：由用户选择意图派生；
- 未来的构造节点：造列或造行后产生的新阶段。

阶段生命周期随分析运行上下文，不写入结果库；上下文失效或重新执行后旧阶段可回收。

## 5. 执行流程示意

```text
fetch runs ──> filter ──> aggregate ──> member_table

pie/bar 点击 ──> selection intent ──> backend 选择阶段 ──> 下游算子 ──> 详情/表格
```

视图后处理只由 `selection` 驱动：依赖用户交互，需要把选择表达为意图或参数后才能进入可复现语义；
未选中时不执行下游分支。

## 6. 与现有实现的差异

### 6.1 保留

- 节点种类、参数结构、表达式语言、形状推导与查询语义的冻结清单继续有效；
- 图校验仍负责无环、语言匹配、形状推导与列引用检查；
- 取数节点仍是后端读取结果库的唯一入口；
- 单项详情节点仍通过详情接口按需取数，不进入表流水线。

### 6.2 需要修订

- 分析系统执行模型：从「整图一次计划」扩展为「后端节点运行时 + 阶段物化」；
- 视图端口模型：视图统一保留 selection 输出，输出语义改为选择意图；
- 图校验：允许饼图/柱状图 selection 被后续表节点消费，分支只在选中时执行；
- 前端运行逻辑：区域级一次请求改为按脏节点拓扑序逐步执行，同时保留防抖与竞态丢弃；
- 分析系统契约与 UI 契约：登记阶段执行协议、选择意图协议与节点运行态错误；
- 后端模块：阶段存储与单节点执行能力落位到 `infrastructure`，用例编排保持在 `application`，
  HTTP 入口由 `server` 提供。

## 7. 建议的后端执行策略

阶段执行的首选实现是“每个节点一次小型执行”，不在浏览器复制算子语义：

1. `fetch` 节点：在结果库上执行 JSON 提取与基础列读取，输出阶段表；
2. 纯表算子：后端对输入阶段执行该节点的语义，输出新阶段表；
3. 一段连续且无交互边界的纯算子链，仍可作为一个“执行单元”交给现有 CTE 编译器融合执行，
   作为性能优化而不是语义模型；
4. 视图与选择边界是执行单元的自然切分点。

阶段存储优先考虑后端进程内临时表或临时 SQLite 表；具体选型与生命周期在评审时确定。

## 8. 开放问题

1. 阶段表行数上限与截断语义：沿用 10000 行截断还是支持分页/增量读取？
2. 任意行集选择如何映射为后端可寻址选择阶段：命中行是否有稳定键（`session_id + ordinal`、
   唯一行号）？没有稳定键时是否只能传“分组谓词”？
3. 选择阶段是否随工作流保存：当前倾向不保存，只允许用户把选择固化为下游过滤参数/预设。
4. 现有 `POST /api/v1/analysis/query` 与存量工作流的迁移路径：新运行时以增量方式并存还是直接替代？
5. 分析运行上下文的生命周期：单用户桌面场景下保留多久、何时回收、取消与重算如何管理。
6. 逐节点执行的错误语义：单节点失败后保留哪些旧输出、下游标记为 stale 还是 error。

## 9. 建议落地顺序

1. 评审本草案，确认目标模型、阶段生命周期与选择语义；
2. 后端先做阶段运行时的最小闭环：现有节点种类按拓扑序逐个执行、阶段可寻址、脏节点增量重算；
3. 打通视图数据透传与 selection 选择阶段，允许视图后接算子；
4. 在运行时上新增列级改写与行级生成节点；
5. 重新设计角色状态详情等单项节点的输入构造方式；
6. 完成契约、架构文档、golden case 与存量工作流迁移方案后，再登记正式决策。

## 10. 开放问题的建议口径（供评审）

以下口径用于收敛第一版后端最小闭环，不视为最终契约：

1. **行数上限与分页**：第一版沿用单表 10000 行硬上限与 `truncated` 标记。阶段在后端完整保存
   至上限；视图读取接口继续一次性返回行集。分页/增量读取后置。
2. **选择意图**：
   - 饼图/柱状图的分组选择提交 `{ stage_ref, version, kind: "group", 分组列与命中值 }`，
     由后端对输入阶段重新派生选择阶段，不依赖行号；
   - 表格行选择提交 `{ stage_ref, version, kind: "row", row_index }`；
     阶段版本变化后行号语义失效，前端作废该选择（与现在排序/绑定变化后重置选择一致）；
   - 任意行集选择（无稳定键的多选）不进第一版。
3. **选择持久化**：选择阶段是运行态瞬态，不随工作流保存；用户需要复用时，由 UI 把选择固化为
   下游 filter 节点参数或“下钻预设”，进入正常图定义。
4. **旧接口迁移**：`POST /api/v1/analysis/query` 保留为过渡执行策略，直到新运行时对现有节点
   种类通过同一组 golden case；之后降级为纯算子链的可选融合优化或正式退役。存量工作流的节点
   kind 与参数不需要迁移，只换执行方式。
5. **阶段生命周期**：阶段属于“分析运行上下文”（analysis context）。前端创建上下文时携带
   区域标识、定义指纹与会话组；后端进程内保存，超时回收；桌面单用户场景下暂不做跨进程共享。
6. **失败语义**：失败节点进入 `error` 并定位到节点；其下游标记 `stale`，可保留旧展示但不再把
   旧输出当作可继续计算的输入。

## 11. 后端最小闭环设计（建议）

### 11.1 目标

用现有节点种类（`fetch`、filter、project、sort、aggregate、limit、join、compute 与视图/单项详情）
跑通一条完整分析区域：

- 后端按拓扑序逐个执行节点，每个节点输出可寻址阶段；
- 前端不复制算子语义，也不搬运中间表；
- 脏节点增量重算、单节点失败定位、视图数据读取与当前行为等价；
- 不新增构造节点、不打通选择阶段，只验证运行时骨架。

### 11.2 组件划分（建议）

```text
server / router
  └─ application / analysis_runtime（编排：上下文、脏节点、拓扑序）
        ├─ protocol: StageStore / NodeExecutor
        └─ infrastructure / results_sqlite
             ├─ analysis_stage_store.py   阶段表存储
             └─ analysis_node_executor.py 单节点执行
```

- `infrastructure`：负责阶段表物化与单节点 SQL 编译执行；
- `application`：负责上下文生命周期、节点顺序、增量重算与错误聚合；
- `server`：提供 HTTP 入口，不直接接触阶段存储或结果库。

### 11.3 阶段存储

- 每个分析上下文持有一个进程内 SQLite 连接（或 `TEMP` 表方案）；
- 每个阶段落为一张安全命名的临时表 `stage_<uuid>`，列名与类型来自形状推导；
- 行插入使用参数绑定；超过 10000 行时阶段表只保留上限行并置 `truncated`；
- 阶段元数据（列、行数、`truncated`、版本、来源节点）由应用层维护。

### 11.4 单节点执行

- `fetch`：沿用结果库读取与 JSON 提取规则，输出阶段；
- filter/project/sort/limit：对输入阶段表执行单节点 SQL；
- aggregate/join/compute：对一或两个输入阶段表执行单节点 SQL；
- 参数校验、类型与形状校验继续复用现有分析契约规则；
- 现有 CTE 整图编译器保留为“连续纯算子段”的优化执行器，不在第一版移除。

### 11.5 前端运行时

- 保留现有图校验与形状推导；
- 节点结果状态从“整表快照”扩展为“阶段引用 + 可渲染行集”；
- 执行时按脏节点拓扑序逐个提交，相同节点版本结果复用；
- 自动重算防抖与竞态序号语义不变。

### 11.6 最小闭环验收

- 代表性区域（含 fetch、join、compute、aggregate、多输入视图）在新旧执行器下输出一致，
  以 golden case 对齐；
- 节点可按顺序看到独立状态；单节点失败只影响其下游；
- 视图读取的数据与当前行为一致；
- 全程前端未直接访问 SQLite、未携带中间表执行算子。

## 12. 非目标

- 前端本地实现 SQL/关系算子语义；
- 前端直接读取或修改结果库；
- 视图选择结果作为未声明语义的任意本地表流入保存的工作流；
- 在本草案确认前修改正式契约、分析系统设计或前端执行模型（2026-09-03 已随决策 2.55 确认，
  本条不再适用）。

## 13. 草案实现进度（2026-09-03）

已按本草案落地“后端最小闭环 + 前端节点式执行”，并登记正式决策 2.55：

- 查询编译执行器支持内部物化阶段输入（`__stage_source`），可复用形状推导、参数校验与 SQL 语义；
- 新增 `SQLiteAnalysisStageExecutor`：分析上下文、阶段临时表、单节点执行、阶段读取与关闭；
- 分析上下文空闲超过 30 分钟随下一次上下文创建回收；前端在切换/新建/删除工作流与页面卸载时
  主动关闭上下文，避免长期占用后端连接；
- 新增应用层 `AnalysisRuntimeService` 与 facade 方法，前端通过 HTTP 创建上下文、逐节点执行、
  读取阶段与关闭上下文；
- 后端新增分组/行选择阶段接口，视图点击可选择在后续转换为后端选择阶段；
- 后端新增同结构阶段合并接口，供饼图/柱状图多路输入在点击前物化为统一选择输入阶段；
- 前端 `analysis_runner` 新增节点运行时执行路径，App 的分析区域刷新已切换到该路径并保留
  最近一次阶段上下文。
- 饼图/柱状图点击联动已接通：点击把分组意图提交后端派生选择阶段，随后从选择阶段执行下游
  表算子分支并刷新下游视图。
- 新增 `derive`（设置列值）节点：可给输入表追加 string/int/float/bool 类型化值列，
  也可把同名同类型输入列改写为指定值；用于构造/改写角色定位与属性聚焦等描述符字段。
- 角色状态详情输入构造链路已验证：`fetch runs → derive(slot、attribute_key) →
  member_table → attribute_detail` 可通过图校验并形成描述符行。
- 新旧执行器已对 fetch/filter/aggregate/join/compute/derive 代表链做 golden 对照。

保留边界与后置项：

- 表格行选择已接入后端 `row` 选择阶段，可驱动下游表分支；单项详情只消费 0..1 行表
  （2026-09-03 决策 2.57 起）。
- 表达式类派生（非字面量）为后续扩展，本版 `derive` 覆盖列值改写；
- 旧整图查询接口按决策 2.55 保留为过渡执行策略，正式退役待长期 golden 通过后另行决定。
