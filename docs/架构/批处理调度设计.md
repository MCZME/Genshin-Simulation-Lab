# 批处理调度设计

> 状态：已确认（2026-08-19）。
> 本文定义批处理的统一概念、边界、生命周期、调度、失败与结果归属。批是调度层面的概念，不进入仿真核心；本文不重复工作流图语义、变体编译或结果库 schema，相关规则见文末关联文档。

## 1. 定位与定义

- **批**：一次提交、一次需要处理的数据集合。数据多少不改变性质；一个成员也是一批，只是批大小为 1。
- **成员**：批内的一个处理单元，由稳定 `item_id` 与一份完整 `SimulationInput` 组成。
- **批处理**：对一次提交的有序成员集合进行调度与执行的职责。

批处理只处理 `SimulationInput`，不处理其他数据种类。变体编译、输入文件解析与图语义都在批处理之外完成；批处理只接受已经形成的成员集合。

## 2. 边界与身份

- 批是纯调度概念，不进入 `core/`，也不进入仿真核心概念。
- 批不持久化，运行结束后不再追踪；服务重启后不存在。
- 需要追踪运行期批时使用服务端生成的内存句柄 `run_id`。`run_id` 只用于运行期寻址，不是持久身份；批释放后作废。
- `item_id` 由提交方（前端）拥有，是批内稳定成员链接键，稳定指向“这份参数从哪来”；不使用显示值、数组下标或 `session_id` 作为成员链接。`item_id` 只在提交时要求批内唯一，不持久化。
- 所有入口统一提交一个批；单成员是成员数为 1 的批，不保留独立的单任务入口。
- 唯一持久身份是结果库的 `session_id`。`run_id`、`item_id`、`job_id` 都是运行期调度键。

## 3. 生命周期

### 3.1 批级状态

```text
queued
running
stopping
completed
partial
failed
cancelled
```

- `queued`：全部成员 `queued`。
- `running`：未请求取消，且存在未终态成员。
- `stopping`：已请求取消，且仍有未终态成员。
- `completed`：全部成员 `completed`。
- `partial`：全部终态，包含成功与失败，且未请求取消。
- `failed`：全部成员 `failed`。
- `cancelled`：已请求取消，且全部终态。

`completed`、`partial`、`failed`、`cancelled` 为批级终态。部分失败是正常结果。

### 3.2 成员级状态

```text
queued
running
stopping
completed
failed
cancelled
```

- `queued`：已提交到批，尚未交给执行器。
- `running`：已占执行槽，正在执行。
- `stopping`：整批取消已请求，该成员仍在跑，跑完后标 `cancelled`。
- 终态：`completed`、`failed`、`cancelled`。

### 3.3 释放与查询窗口

- 批进入终态后停止调度，不再推进状态。
- 终态批保留固定 60 秒查询窗口；窗口内 `GET /runs/{run_id}` 可取得最后一次完整视图，含成员状态与已完成成员的 `item_id → session_id`。
- 窗口按绝对截止时刻计算，读取不续期；重复查询不延长窗口。
- 到期后从内存释放，`run_id` 作废；再次查询按不存在处理。释放采用懒清理：批处理操作时顺带清掉过期终态批，不另起后台线程。
- 60 秒为 `application/batch/` 内部常量，不进入 `SimulationInput`，不进入 API；数值可按真实轮询节奏校准。
- 终态窗口是批与前端之间唯一的状态交接点。前端应在取得终态视图时自行保存需要的 `item_id → session_id` 映射，后端不代管。

## 4. 成员与任务

- 成员是公开概念：`item_id + SimulationInput`，拥有成员状态。
- job 是纯内部执行句柄：一次“把一份输入交给执行器并追踪其执行”的调度单元，不对前端、facade、CLI 或 API 暴露。
- 批服务私有维护 `item_id → job_id` 映射；job 状态是执行真值，成员状态由 job 状态加批级决策派生。
- job 不持久化，不成为身份；批释放时随批丢弃。
- 执行器只负责执行一份 `SimulationInput` 并产生结果，不知道批、不知道成员。

## 5. 调度

- 批服务是唯一调度者。runner/执行器只执行单份输入，不持有独立任务队列。
- 批级并发槽是唯一真值。进程执行时，执行后端容量按批调度上限（`MAX_BATCH_CONCURRENCY`）准备，成员仍由批服务按并发槽逐个投递，后端不持有第二队列。
- “已提交给执行器”等价于“已占槽、正在或即将执行”；批内 `queued` 只表示尚未提交给执行器。
- 成员按提交顺序 FIFO 补位；完成允许乱序，但查询视图始终按提交顺序排列。
- 补位由轮询驱动：`submit` 或 `get` 时推进批次（pump），空槽才补新成员。接受“无查询不推进”：前端在批运行期间持续轮询是既定协议，批不依赖后台线程。

## 6. 失败与取消

- 第一版不自动重试，失败即成员终态；错误模型为有限重试预留可重试语义。
- 取消：排队成员直接 `cancelled`；运行中成员不硬杀，等自然结束再标 `cancelled`，其结果不作为成功结果暴露。
- 错误分三层：
  1. 输入/组装错误：输入结构、资产、handler 等在执行前发现的问题。
  2. 执行失败：真实执行过的仿真运行失败。
  3. 调度/基础设施错误：调度、进程、写库等临时或外部故障。
- 只有真实执行过的失败写结果库；排队取消、提交前校验失败不写结果库。

## 7. 结果归属

- 每个成员最多对应一个 `session_id`；排队、取消、失败成员的 `session_id` 为空。
- 结果库查询与批运行无关：结果持久化后即可按 `session_id` 单独查询，不依赖批存活。
- 重试或重跑同一成员时生成新 `session_id`，覆盖前端保存的 `item_id → session_id` 映射，映射保持一对一。结果库旧记录不变，只是不再被该 `item_id` 指向。
- 结果库不知道 `run_id`、`item_id` 或 `job_id`，只保存 `session_id`。

## 8. 状态持久化

- 批状态纯内存，不持久化；服务重启后 `run_id` 全部作废，客户端通过结果库而不是批恢复历史。
- 批不写任何批级记录进结果库。
- 失败/取消留下的最小结果记录仍按结果库自身规则保存；批级状态与结果身份不混合。

## 9. 错误语义

- 错误使用稳定错误码，不使用 Python 异常类名；对前端提供面向用户的消息、成员定位与可选细节。
- 输入侧沿用已有子码：`CONFIG_INVALID`、`ASSET_NOT_FOUND`、`HANDLER_UNAVAILABLE`。
- 执行侧使用 `SIMULATION_FAILED`。
- 基础设施侧使用 `WORKER_CRASHED`、`RESULT_WRITE_FAILED`、`SQLITE_BUSY`、`CANCEL_RACE`。
- 批服务内部无法识别的调度异常使用 `SCHEDULING_FAILED`；真实执行过的失败在结果库与批视图使用同一稳定码。
- 进结果库的判据是“这次执行真实开始且失败”。执行失败时，批视图与结果库同一条失败记录原样一致；调度上下文（如内部尝试信息）只放在批视图额外字段，不进结果库。

## 10. 职责边界

| 层 | 职责 |
| --- | --- |
| `core/` | 同步仿真运行时，不感知批、job 或调度 |
| `application/execution/` | 执行一份输入、收集事实、写结果库，分配 `session_id` |
| `application/jobs/` | 单次执行句柄与执行器协议；不拥有批 |
| `application/batch/` | 批级调度、校验、并发槽、状态派生、取消与终态窗口 |
| `infrastructure/jobs/` | 进程等具体执行后端；执行器不感知批 |
| `frontend/` | 编译成员、提交一个批、轮询终态、自行保存结果映射 |

- CLI 与 server 默认装配均已接入进程执行路径；CLI 的单份输入是单成员批。

- 结果写入已补齐超时、有限重试与并发写验证。
- 三层错误分类与稳定错误码已落地；`assembling/saving` 等内部阶段状态已移除。
