# 按键输入系统设计

> 状态：正式规范。
> 本文说明按键输入在运行时的协作方式：`input_trace` 事实如何编译为输入会话、`ActionManager` 如何按帧处理 PRESS / RELEASE / HOLD、binding 为何在 PRESS 固定，以及输入系统与动作系统的职责边界。
> 最后更新：2026-09-05。

稳定数据契约（按键集合、JSON 结构、校验规则、会话数据结构与事件 payload）见[按键输入契约](../契约/按键输入契约.md)；动作实例、准入、锁与影响点见[动作系统设计](./动作系统设计.md)。本文只讲运行时协作与边界，不重复定义字段。

## 1. 定位与流程

按键输入系统回答：`SimulationInput.input_trace` 编译后的输入会话在运行时如何协作，边界为什么这么划。

目标链路：

```text
SimulationInput.input_trace
-> InputTraceCompiler
-> InputSessionTrace
-> ActionManager.update_frame
-> ActionInterpreterRegistry
-> InterpreterBinding
-> ActionInterpretationResult
-> ActionManager 动作准入
```

核心原则：

- 配置层只记录按键事实。
- 按键事实在组装阶段配对为输入会话计划，并编译为 `InputSessionTrace`。
- `ActionManager` 是运行时输入会话的拥有者。
- 动作是否发生、动作类型和开始帧由对应解释器决定。
- 完整输入计划中的未来 release 不向解释器提前暴露。

本文档不定义具体动作如何解释、角色动作帧数、动作锁、中断窗口和资源规则，也不定义伤害、命中、索敌、元素附着、反应或其他机制结算。

## 2. 组装阶段编译

```text
SimulationInput
-> application/input 结构校验
-> InputTraceCompiler.compile()
-> InputSessionTrace
-> SimulationAssembler 注入 ActionManager
```

`InputTraceCompiler` 只在组装阶段运行：它把配置中的 press / release 事实配对为不可变输入会话计划，生成按帧读取的边界索引，并校验帧号、按键、阶段、顺序与按键生命周期。配置错误必须在组装或运行前暴露。

`InputTraceCompiler` 不作为每帧运行对象，不调用动作解释器，不决定动作是否发生。

解释器注册、动作注册与真实角色槽位的组装校验属于动作系统，见[动作系统设计](./动作系统设计.md)。

## 3. 每帧处理顺序

输入处理是 `ActionManager.update_frame` 的一部分：

```text
1. 启动此前预约在本帧开始的动作
2. 按原始 order 处理本帧 PRESS / RELEASE
3. 每次解释后立即应用结果
4. 处理仍为 held/listening 的 HOLD
5. 推进运行中的动作实例
6. 处理本帧 impact
```

设计要点：

- 输入边界先于 HOLD，保持“显式输入先处理、运行态随后推进”的帧语义。
- 同帧输入按原始顺序处理，顺序会影响后续解释结果；当前帧接受并开始的动作立即执行 `on_start()`，使同帧后续输入看到其状态变化。
- 新 press 与 release 当帧都不再调用 HOLD。
- HOLD 不写入 `input_trace`，由 `ActionManager` 根据运行时会话状态逐帧派生。

## 4. 运行时会话状态

运行时输入会话同时保存物理状态与动作控制状态，两者分离：

- 物理状态为 `held / released`，表示按键事实本身。
- 动作控制状态为 `listening / detached / canceled`，表示动作系统是否还需要该会话继续调用解释器。

语义：

- `listening`：后续 HOLD、RELEASE 或未来启用的 CANCEL 继续调用原解释器。
- `detached`：动作已不再需要输入控制；物理按键仍可保持按下。
- `canceled`：动作控制因切人或其他规则失效；未来 release 仍作为物理事实处理。

`detached / canceled` 不删除或改写未来 release 输入事实，只影响运行时是否继续调用解释器。HOLD 与 CANCEL 都不是新的外部按键事实，因此不写入 `input_trace`。

## 5. PRESS 时固定 binding

`ActionManager` 使用 `ActionInterpreterRegistry` 从按键解析输入会话：

```text
key
-> selector
-> InterpreterBinding
```

selector 分队伍级与当前场上角色级。binding 在 PRESS 时解析并写入运行时会话；后续 HOLD、RELEASE 和未来可能启用的 CANCEL 始终使用同一 binding，不因当前 `active_slot` 改变而重新路由。

示例：

```text
frame 100: active_slot=1, keyboard.e press
frame 110: 切到 slot 2
frame 130: keyboard.e release
```

该 E 会话仍归属 press 时的 slot 1。切人成功后可以取消它的动作控制，但不能把 release 路由给 slot 2。

原因：

- 输入会话的 owner 在开始时就应稳定。
- 长按类动作需要同一个解释器连续观察 PRESS、HOLD 和 RELEASE。
- 切人、状态变化或其他动作不能把已经开始的物理按键会话改写为另一个角色的输入。
- 完整输入计划不能被运行时 active slot 变化重新解释为不同事实。

## 6. 解释器职责边界

`ActionInterpreterRegistry` 只负责从按键和运行时上下文得到 `InterpreterBinding`。

- 队伍解释器处理队伍级按键（如切到指定槽位），返回语义化动作请求，不直接修改队伍运行态。
- 角色解释器按当前 owner 角色的输入会话、状态、资源与动作状态返回解释结果，判断继续等待、拒绝、启动动作或控制已有动作。

解释器不创建 `ActionInstance`、不获取或释放动作锁、不直接修改动作实例或状态、不执行动作逻辑、不产生伤害/治疗/状态变化，也不读取未来 release 信息。它只返回解释结果、启动请求或语义化控制命令；`ActionManager` 负责最终动作准入、锁冲突检查、实例创建、旧实例取消与生命周期推进。

## 7. 事件与其它系统的边界

输入事实、会话边界和动作判断是不同层级：

```text
KeyEvent
InputSessionBoundary
ActionInterpretationResult
ActionDecision
ActionInstance lifecycle
```

`ActionManager` 处理输入边界时发布 `INPUT_KEY_RECEIVED` 与 `INPUT_SESSION_BOUNDARY_REACHED` 两类事件：前者记录原始按键事实，后者记录会话状态、binding 与是否调用解释器。事件类型与 payload 真值见[按键输入契约](../契约/按键输入契约.md)。

输入事件只用于复盘、审计和结果记录，不作为动作机制的驱动来源。事件定义与分发归 `core/events`，不写数据库；结果库持久化输入事实、会话边界与后续动作事件；快照与结果库的具体持久化格式见[后续实现计划](../工程/后续实现计划.md)。

## 8. 扩展边界

后续扩展应保持当前边界：

- 自定义键位：在配置或用户设置层把物理输入映射到稳定 key；`InputTraceCompiler` 仍只接收规范化 key。
- 手柄：新增手柄 key 命名空间，并在契约层定义按钮和轴输入是否进入同一会话模型。
- 移动：移动键若需要连续方向输入，先确认属于按键会话、运动控制状态还是独立移动意图流。
- 镜头：鼠标移动、视角和准星不伪装成 press / release，需要单独的输入事实契约。
- CANCEL 回调：只有真实角色或机制需要取消通知时再启用解释器 CANCEL 触发，并补充事件与测试。
