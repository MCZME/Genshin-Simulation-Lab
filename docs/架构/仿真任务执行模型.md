# 仿真任务执行模型

> 状态：建议方案，待实现验证。
> 本文档记录仿真运行如何从同步调用演进为后台任务，重点解决 UI 或主进程不被长时间仿真堵塞的问题。

最后更新：2026-07-06

## 1. 背景

当前项目已经把单次仿真组装为独立运行时实例。每次运行会创建新的 `SimulationContext`、输入系统、动作管理器、运行世界和 `Simulator`，可以隔离不同仿真之间的运行态影响。

但“实例隔离”不等于“不会堵塞主进程”。

当前过渡实现中的同步执行链路位于 `application/execution/SynchronousSimulationExecutor`：

```text
execute_config
-> SimulationAssembler.assemble
-> Simulator.run
-> ResultWriter.save_run
-> return outcome
```

调用方线程会等待仿真帧循环和结果保存全部完成。因此如果 UI 直接调用该服务，长仿真会占用 UI 主线程；如果未来批量扫描直接串行调用，也无法自然表达任务状态、取消和并行度。

## 2. 目标

仿真任务执行模型第一版需要满足：

- UI 提交仿真后不阻塞主界面。
- 单次仿真仍然保持独立运行态。
- `core/` 保持同步、纯粹、可测试，不感知 UI 调度或异步框架。
- CLI 普通 `run` 命令可以继续同步等待结果。
- 后续批量扫描可以复用同一套任务模型。
- 任务失败、取消和完成状态可以被 UI 或 CLI 查询。

第一版不要求：

- 分布式执行。
- 跨机器任务队列。
- 多用户服务端调度。
- 实时逐帧 UI 回放。

## 3. 当前实现评估

当前已经具备的基础：

- `SimulationAssembler` 每次组装都会创建新的核心运行时对象，适合作为 worker 内的单次运行入口。
- `Simulator.run()` 只依赖传入的上下文、输入系统和运行世界，不直接依赖 SQLite、UI 或应用层。
- 资产库读取通过 `AssetRepository` 协议进入应用层，SQLite 资产仓库是只读连接。
- 结果库写入通过 `ResultWriter` 协议进入应用层，SQLite 结果库每次保存运行结果时新开连接。
- 结果库 schema 已启用 WAL，适合支持读写并存和后续多任务场景的基础验证。

当前缺口：

- 已有 `application/jobs/InMemorySimulationJobRunner` 作为同步内存 runner，用于验证任务 ID、任务状态、失败原因和门面接口。
- 已有 `SimulationWorkerPayload` 与 `run_simulation_worker()` 作为通用 worker 边界；它只依赖可序列化 payload 和 `SimulationExecutor` 协议，不直接创建 SQLite 适配器。
- 已有 `infrastructure/jobs/ProcessSimulationJobRunner` 作为第一版进程 runner；它会把可序列化 payload 投递到子进程，并在 worker 内重建 SQLite 仓库、默认 registry 和同步执行器。
- 没有进度回传或阶段性状态。
- 没有并发运行测试。
- 没有 UI 侧任务轮询或通知机制。

## 4. 技术选择

第一版推荐：

```text
进程隔离为主，异步只作为主进程调度外壳。
```

原因：

- 仿真是 CPU 密集型帧循环，`async def` 本身不能让 CPU 计算离开主线程。
- 把 `Simulator.run()` 改成异步循环会让 `core/` 感知调度细节，破坏当前清晰边界。
- 线程可以避免 UI 直接卡住，但 Python GIL 会限制 CPU 密集任务的真实并行能力。
- 进程可以隔离运行态、内存增长和 worker 崩溃，更符合仿真任务的长期需求。
- `SimulationConfig`、数据库路径、运行参数等可以序列化传入 worker；SQLite 连接和已组装运行时对象不应跨进程传递。

`async` 的适合位置：

- UI 主进程提交任务。
- 轮询任务状态。
- 接收任务完成或失败通知。
- 更新界面。
- 管理后台 worker 的生命周期。

不推荐：

- 将 `core/simulation/Simulator` 改为异步模拟器。
- 在 `SimulationConfig` 中加入运行模式、异步开关或进程参数。
- 跨进程传递 SQLite connection、已实例化的 handler、`SimulationContext` 或 `Simulator`。

## 5. 推荐结构

```text
ui / cli / batch
  -> application/services/SimulationTaskService
      -> application/jobs/SimulationJobRunner
          -> worker process
              -> create repositories and registry
              -> application/execution/SynchronousSimulationExecutor
                  -> SimulationAssembler.assemble
                  -> Simulator.run
                  -> ResultWriter.save_run
```

职责划分：

| 模块 | 职责 |
| --- | --- |
| `core/` | 保持同步仿真运行时，不关心后台任务。 |
| `application/execution/SynchronousSimulationExecutor` | 内部同步执行一次仿真，是 worker 调用的执行原语。 |
| `application/jobs/SimulationJobRunner` | 提交任务、查询状态、取消任务、收集结果。 |
| `application/services/SimulationTaskService` | UI/CLI 调用的对外服务门面。 |
| `infrastructure/jobs/ProcessSimulationJobRunner` | 基于进程池实现后台调度，并负责 worker 进程内的基础设施重建。 |
| `infrastructure/` | 提供 worker 需要的 SQLite 仓库、结果写入器和日志适配。 |
| `ui/` | 调用任务执行器，不直接运行 `Simulator`。 |
| `cli/` | 普通 `run` 可继续同步；未来可增加后台或批量命令。 |
| `application/batch/` | 后续复用任务执行器做参数扫描和并发控制。 |

## 6. 任务模型

建议第一版任务状态：

```text
queued
running
completed
failed
cancelled
```

建议任务结果：

```text
SimulationJobResult
├── job_id
├── state
├── session_id
├── summary
├── error_message
└── created_at / started_at / finished_at
```

任务提交参数应保持可序列化：

- `SimulationConfig` 的字典或配置文件路径。
- 资产库路径。
- 结果库路径。
- 可选任务名称。
- 可选并发池配置。

当前 `SimulationWorkerPayload` 已覆盖：

- `job_id`
- `config_payload` 或 `config_path`
- `asset_db_path`
- `result_db_path`
- `created_at`

其中 `asset_db_path` 和 `result_db_path` 是后续进程 worker / infrastructure 适配层重建依赖所需的路径。通用 worker 函数不直接使用 SQLite 路径，也不 import 具体 SQLite 实现。

worker 内部重新创建：

- `SQLiteAssetRepository`
- `HandlerRegistry`
- `SQLiteResultWriter`
- `SynchronousSimulationExecutor`

## 7. 取消与进度

第一版取消策略可以先做粗粒度：

- 任务尚未开始：从队列移除并标记 `cancelled`。
- 任务正在运行：终止 worker 进程并标记 `cancelled` 或 `failed`，具体状态由调用方策略决定。

后续再考虑细粒度取消：

- 在 `Simulator` 帧循环中加入可选的取消检查协议。
- 每 N 帧或每个阶段检查一次取消信号。
- 保持该协议在 `application` 或 `core` 协议层清晰定义，避免 UI 直接渗透到 `core`。

第一版进度可以先使用阶段性状态：

- `queued`
- `assembling`
- `running`
- `saving`
- `completed`

逐帧进度、实时事件流和 UI 回放属于后续能力，不应阻塞第一版后台运行。

## 8. SQLite 与并发

资产库：

- 第一版按只读库处理。
- worker 内部各自打开连接。
- 不跨进程共享连接。

结果库：

- 第一版继续使用 SQLite。
- WAL 已作为基础策略。
- SQLite 仍然是单写者模型，多 worker 同时保存结果时需要处理写入等待或重试。
- 如果批量扫描并发度升高，应增加写入超时、重试策略或集中写入队列。

日志：

- 多进程写同一个轮转日志文件可能出现竞争。
- 第一版可以先让主进程记录任务状态，worker 只记录简要边界。
- 后续再评估任务级日志文件或 `QueueHandler`。

## 9. CLI、UI 与批量任务

CLI：

- `genshin-sim run config.json` 可以继续同步运行并输出 `session_id`。
- 后续如有需要，可增加 `run --background` 或专门的批量命令。

UI：

- UI 不直接调用 `SynchronousSimulationExecutor`。
- UI 通过 `SimulationTaskService` 调用任务能力，服务内部再委托 `SimulationJobRunner`。
- UI 通过轮询或通知刷新任务状态。
- UI 只读取任务结果或结果库摘要，不直接访问 SQLite。

批量任务：

- 批量扫描应复用任务执行器。
- 并发度应显式配置，并设置合理默认值。
- 批量任务不应把所有完整事件流一次性堆在主进程内存中。

## 10. 实施阶段

建议分五步实施：

1. 保留 `execution/` 同步执行原语，新增 `jobs/` 任务模型和 `SimulationJobRunner` 协议。当前已完成。
2. 实现内存版 `SimulationJobRunner`，先支持提交、查询、完成和失败。当前已完成同步骨架。
3. 新增通用 worker payload 和 worker 函数。当前已完成。
4. 接入进程 worker，worker 内部重建仓库、registry 和同步执行器。当前已完成第一版。
5. 增加运行中取消、进度回传、任务状态持久化和批量任务复用。

每一步都应保持 `core/` 不依赖 `application/`、`infrastructure/` 或 UI。

## 11. 验收标准

第一版后台执行完成后应满足：

- UI 或测试中的主调用方提交任务后可以立即继续执行。
- worker 内部可以完成一次最小仿真并保存结果。
- 完成任务能返回 `session_id` 和摘要。
- 失败任务能返回明确错误信息。
- 多个任务之间的运行态不会互相污染。
- 结果库中可以查询到完成任务的保存结果。
- 不改变 `SimulationConfig` 契约。
- 不把异步调度逻辑引入 `core/`。

建议补充测试：

- 单任务后台运行完成。
- 任务失败状态记录。
- 两个任务并发运行后各自保存独立 `session_id`。
- UI 或调用线程提交任务后不会同步等待仿真完成。
- 取消未开始任务。
- 取消运行中任务。

## 12. 风险与待确认

待确认问题：

- 第一版 worker 使用 `ProcessPoolExecutor`，还是自定义单 worker process。
- UI 是否需要显示实时进度，还是只显示阶段状态。
- 运行中取消应标记为 `cancelled` 还是保留失败原因。
- 批量扫描默认并发度如何设置。
- 多进程日志是否需要第一版一并处理。

需要重点控制的风险：

- 不要把后台任务参数塞进 `SimulationConfig`。
- 不要跨进程共享 SQLite connection 或已组装运行时对象。
- 不要让 `core/` 依赖 UI、异步框架或进程池。
- 不要在主进程收集无限增长的事件数据。
- 不要让多个 worker 无限制同时写入 SQLite。
