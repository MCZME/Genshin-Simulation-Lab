# 机制系统设计

> 状态：当前基础能力已实现；通用 Buff、冷却、光环、附着和级联命令处理仍属于后续范围。
> 本文定义 `core/mechanics` 的状态所有权、生命周期和受控写入边界，不定义伤害、治疗、护盾、反应等原神游戏机制的具体公式。

最后更新：2026-07-13

## 1. 定位

机制系统为需要稳定身份和生命周期的运行态对象提供最小公共基础设施。当前首个使用者是护盾系统，未来可在独立评审后承载 Buff、状态、冷却、元素附着、ICD 窗口或其他可独立创建和移除的运行态实例。

本文中的“机制系统”特指：

```text
core/mechanics/
├── MechanicInstance
├── MechanicInstanceStore
├── MechanicRuntime
└── 受控创建、刷新与移除命令
```

它不是所有原神游戏机制的总调度器。普通伤害、治疗等一次性结算可以拥有独立的请求、解析器和结果，不要求先创建 `MechanicInstance`。

## 2. 设计目标

- 为每个活动实例分配稳定的运行期身份。
- 统一表达创建帧、过期帧、活动、过期和显式移除。
- 通过受控命令修改生命周期，不暴露任意 Store 写入口。
- 提供按 owner、capability 和 mechanic key 查询的稳定活动索引。
- 让能力专用组件在实例移除后得到统一通知。
- 保证相同输入和帧顺序产生相同结果。
- 保持 `core/` 的纯运行时边界，不依赖 assets、content、application、infrastructure 或 UI。

## 3. 非目标

当前机制系统不负责：

- 解释具体角色、武器或圣遗物行为。
- 计算伤害、治疗、护盾容量或反应数值。
- 提供全局 ECS 世界或任意组件 patch API。
- 实现完整 Buff 层数、冷却、光环、附着或 modifier 聚合。
- 扫描和自动注册 content handler。
- 充当事件总线或允许事件回调递归修改世界。
- 保存能力专用字段，例如护盾元素、容量、冲突键或公式快照。

## 4. 状态所有权

机制系统只拥有通用实例身份和生命周期：

```text
MechanicRuntime
└── MechanicInstanceStore
    ├── 全量实例记录
    ├── 活动 instance_id 索引
    ├── 下一个 instance_id
    └── Store version
```

能力专用状态由对应系统拥有：

```text
MechanicInstanceStore       -> 通用身份和生命周期
ShieldComponentStore        -> 护盾元素、原生容量、保护对象和冲突键
未来 BuffComponentStore     -> Buff 层数、参数和能力专用状态
ContentStateStore           -> handler 自身长期内容状态
```

同一份状态不得在多个 Store 中重复维护。能够独立创建、刷新、移除或过期的公共运行态优先使用机制实例；只对单个 content handler 有意义的计数器和模式保留在 `ContentStateStore`。

## 5. MechanicInstance

当前 `MechanicInstance` 字段为：

```text
MechanicInstance
├── instance_id
├── capability_key
├── mechanic_key
├── handler_key
├── owner_ref
├── created_frame
├── expires_at_frame
├── lifecycle_state
├── removed_frame?
└── removal_reason?
```

字段语义：

- `instance_id`：单次仿真内递增且唯一的正整数。
- `capability_key`：能力类别，例如 `shield`。
- `mechanic_key`：稳定机制语义 key，不使用显示名称。
- `handler_key`：行为实现绑定入口。
- `owner_ref`：实例所有权索引使用的稳定引用。
- `created_frame`：实例进入活动状态的帧。
- `expires_at_frame`：实例不再活动的第一帧。
- `lifecycle_state`：`active`、`expired` 或 `removed`。
- `removed_frame`、`removal_reason`：非活动实例的审计信息。

机制实例是不可变值对象。Store 通过替换值对象提交变化，不向调用方暴露可变字段。

## 6. 生命周期

### 6.1 半开区间

活动区间统一为：

```text
created_frame <= frame < expires_at_frame
```

`expires_at_frame` 当帧不再视为活动。运行世界在 `ActionManager` 和 `ImpactRuntime` 之前推进 `MechanicRuntime`，因此到期实例不会参与过期帧的 impact。

### 6.2 活动状态

活动实例不得携带 `removed_frame` 或 `removal_reason`。活动索引只保存生命周期状态仍为 `active` 的实例 id；带帧查询时还必须满足半开区间。

### 6.3 显式移除

显式移除只能发生在实例活动区间内：

```text
created_frame <= remove_frame < expires_at_frame
```

在创建前或到期后提交 `removed` 必须返回结构化错误，不能生成时间倒置的审计记录。

### 6.4 到期提交

到期提交使用 `expired` 状态，提交帧必须满足：

```text
remove_frame >= expires_at_frame
```

正常逐帧运行时二者相等；Store 仍允许延迟清理在更晚帧记录实际提交时间。

## 7. 受控命令

### 7.1 CreateMechanicInstanceCommand

创建命令包含能力 key、机制 key、handler key、owner、创建帧和正持续帧数：

```text
expires_at_frame = frame + duration_frames
```

创建成功后分配新的 `instance_id`，登记全量实例和活动索引，并递增 Store version。

### 7.2 RefreshMechanicExpiryCommand

刷新命令包含：

```text
instance_id
frame
expires_at_frame
```

约束：

- 实例在 `frame` 必须实际活动。
- `expires_at_frame` 必须晚于执行帧。
- 非活动或已经到期但尚未清理的实例不能通过刷新复活。

### 7.3 RemoveMechanicInstanceCommand

移除命令包含 instance id、执行帧和非空原因。显式移除必须发生在活动区间；到期由 `MechanicInstanceStore.expire_due()` 使用专用状态提交。

## 8. MechanicInstanceStore

Store 提供以下受控能力：

- `create()`：创建并登记实例。
- `refresh_expiry()`：校验执行帧并刷新过期帧。
- `remove()`：提交显式移除或到期。
- `expire_due()`：按稳定 instance id 顺序提交到期实例。
- `active_instances()`：按帧、owner、capability 和 mechanic key 过滤活动实例。
- `get()`、`require()`、`require_active()`：只读查找。

Store 不提供：

- 任意字段 patch。
- 任意组件增删。
- 绕过命令的活动索引写入。
- 基于显示名称的查找。

## 9. MechanicRuntime

`MechanicRuntime` 是 Store 的运行时门面：

- 转交创建、刷新和移除命令。
- 在每帧开始调用 `expire_due(frame)`。
- 在状态提交后向 removal subscriber 发布不可变 `MechanicRemovalRecord`。
- 作为 `FrameUpdatable` 加入 `BasicRuntimeWorld`。

当前 `is_idle()` 返回 `True`。活动机制实例本身不延长仿真；仿真是否继续由动作、输入、空间对象等拥有未来工作的运行时决定。

## 10. 能力组件协作

能力系统通过 `instance_id` 把专用组件与通用实例关联。以护盾为例：

```text
MechanicInstance(instance_id=7, capability_key="shield")
<->
ShieldComponent(instance_id=7, ...)
```

规则：

- 机制实例先分配身份，能力组件使用相同 instance id。
- 活动查询同时检查通用实例和能力组件。
- 通用实例移除后，removal subscriber 清理能力组件。
- 能力系统负责发布领域事实事件，机制系统不伪造护盾、Buff 或附着事件。
- 能力专用批量状态变化由能力 Store 实现原子提交，不向通用 Store 增加万能 patch API。

## 11. 顺序、原子性与重入

- 全量和过滤查询结果按 `instance_id` 稳定排序。
- 到期实例按 `instance_id` 稳定提交。
- 状态先提交，removal subscriber 后通知。
- subscriber 不得在同一调用栈中形成无限递归生命周期修改。
- 需要多组件原子变化的能力系统必须先计算完整更新集，再一次提交。
- 事实事件只能描述已经提交的状态。

护盾系统在授予、移除和吸收期间缓存事实事件，完整提交后再发布；发布期间同步发起的护盾写操作会被结构化拒绝。该能力属于护盾运行时事务边界，不表示当前已经实现通用命令缓冲器。

## 12. 与其他系统的边界

### 12.1 属性系统

活动机制未来可以贡献 modifier provider，但属性查询必须保持无副作用。查询期间不能创建、刷新或移除机制实例。具体属性契约见[属性系统契约](../契约/属性系统契约.md)。

### 12.2 ImpactRuntime

`ImpactRequest` 可以表达创建某类机制的意图。领域 handler 负责把请求转换为强类型领域请求，再调用对应系统；Impact factory 不直接写机制 Store。

### 12.3 EventEngine

`EventEngine` 记录已经发生的事实。机制系统的 removal subscriber 是提交后内部通知，不把 EventEngine 当作生命周期写入入口。

### 12.4 content

具体角色、武器和圣遗物通过稳定 `handler_key` 构造领域请求、modifier 或后续影响，不创建全局 `MechanicRuntime`，也不直接访问 Store。详细边界见[内容系统设计草案](./内容系统设计草案.md)。

## 13. 错误模型

机制系统使用以下结构化错误：

- `MechanicSystemError`：错误基类。
- `MechanicValidationError`：命令、值对象或生命周期不满足契约。
- `MechanicInstanceNotFoundError`：实例不存在或在指定帧不活动。
- `MechanicAtomicCommitError`：未来批量提交无法完整应用的预留边界。

调用方不得通过捕获宽泛 `Exception` 把非法生命周期静默降级为无操作。

## 14. 验证要求

至少覆盖：

- instance id 唯一且稳定递增。
- 半开生命周期边界。
- 创建前、到期帧和到期后的显式移除被拒绝。
- 过期实例不能通过刷新复活。
- 到期顺序稳定。
- owner、capability 和 mechanic key 索引正确。
- removal record 保存最终状态与原因。
- 能力组件在通用实例移除后同步清理。

测试必须断言结构化状态和记录，不依赖日志文本。

## 15. 后续范围

以下能力尚未形成正式契约：

- 通用 Buff 和层数模型。
- 冷却、光环、元素附着和 ICD 组件。
- 通用 `MechanicRuntimeView`。
- content 能力 Protocol 和能力索引。
- 通用 CommandBuffer、同帧级联轮次和循环检测。
- 通用机制快照与恢复。
- modifier 生命周期与机制实例的正式连接协议。

这些能力进入实现前必须单独评审，不能从当前护盾切片外推未确认接口。
