# 动作系统设计

> 状态：正式。输入会话、动作解释、Action 注册、动作实例、影响点、通用定时动作
> （动态时间线与垂直位移）与 ImpactRuntime 已落地；机器可验证接口见
> [动作系统契约](../契约/动作系统契约.md)。
> 本文档确定动作解释、动作实例、动作准入、动作调度与影响请求之间的设计边界
> 与协作。按键输入数据契约和输入会话运行语义见独立文档；未决机制见第 16 节。

最后更新：2026-08-08

## 1. 设计目标

动作系统负责把已经编译的输入会话解释为可运行、可审计的动作实例，并在动作运行期间产生机制影响请求。

核心原则：

- 动作系统消费已经编译好的输入会话计划，不定义 `input_trace` JSON 结构。
- `ActionManager` 是动作系统唯一运行时入口和动作实例拥有者。
- `ActionManager` 不硬编码切人键、攻击键或具体角色动作含义。
- 动作解释器负责判断“当前应该做什么”，不直接执行动作或修改动作实例。
- 元素战技与元素爆发解释器通过只读协调端口查询冷却和标准元素能量公共条件，不直接拼接领域裸状态。
- `Action` 定义具体动作逻辑，`ActionInstance` 保存一次动作的可变运行态。
- 所有被接受的动作都创建 `ActionInstance`，包括切人。
- 动作产生 `ActionImpactPoint`，Impact 系统再展开为具体机制请求。

目标流程：

```text
InputSessionTrace
-> ActionManager
-> ActionInterpreterRegistry
-> ActionInterpreter
-> CharacterAbilityConditionPort（仅 E/Q 公共条件）
-> ActionInterpretationResult
-> ActionManager
-> ActionRegistry
-> ActionInstance(Action)
-> ActionImpactPoint
-> ImpactRuntime
-> ImpactFactory
-> ImpactRequestDispatcher
-> mechanics / systems / space
```

`core/actions` 模块划分：

- `enums.py`：动作领域枚举。
- `models.py`：数据模型与规格（`TargetingSpec`、影响点、动作实例、执行上下文等）。
- `interpreters.py`：解释器协议、选择器与解释器注册表。
- `protocols.py`：`Action` 实现协议与 `ActionRegistry`。
- `actions.py`：通用定时动作、切人动作与队伍解释器。
- `manager.py`：`ActionManager` 运行时编排（输入会话、准入、实例与影响点）。
- `helpers.py`：内部校验与参数辅助。

按键输入的稳定数据契约见：[按键输入契约](../契约/按键输入契约.md)；输入会话编译、PRESS/HOLD/RELEASE、binding 固定和输入事件发布见：[按键输入系统设计](./按键输入系统设计.md)。本文档只保留动作系统需要消费的输入会话边界。

## 2. 输入会话消费边界

动作系统从 `ActionManager` 持有的 `InputSessionTrace` 开始工作。`InputTraceCompiler` 的输入输出、`InputSessionPlan`、`InputSessionBoundary` 和 `InputSessionView` 的完整数据结构由按键输入契约维护，动作系统不重复定义。

动作系统只依赖以下边界：

- `InputSessionTrace.boundaries_at(frame)` 提供当前帧 PRESS/RELEASE 边界。
- `ActionManager` 在 PRESS 时解析并固定 `InterpreterBinding`。
- `ActionManager` 为解释器构造当前帧只读 `InputSessionView`。
- `InputSessionView` 不提前暴露未来 release 信息。
- 解释器不得请求开始帧早于当前仿真帧的动作。

### 2.1 RuntimeInputSession

`RuntimeInputSession` 是 `ActionManager` 内部运行态，不属于外部配置契约。

```text
RuntimeInputSession
├── session_id
├── key
├── press_frame
├── physical_state
├── control_state
├── interpreter_binding
├── owner
├── bound_instance_id?
├── cancel_reason?
└── released_frame?
```

运行时输入会话的物理状态、控制状态和触发语义以[按键输入系统设计](./按键输入系统设计.md)为准。动作系统只通过 `session_policy`、`bound_instance_id` 和 owner 取消接口影响该运行态。

## 3. 解释器注册与归属

### 3.1 ActionInterpreterRegistry

`ActionManager` 不通过条件分支判断切人还是角色动作，而是使用解释器注册表：

```text
ActionInterpreterRegistry
├── register(key, selector)
└── resolve(key, runtime_context) -> InterpreterBinding
```

第一版 selector 包括：

- `TeamInterpreterSelector`：解析队伍级输入。
- `ActiveCharacterInterpreterSelector`：解析当前场上槽位对应的角色解释器。

同一按键第一版只能注册一个确定 selector，不使用带隐藏优先级的责任链。

### 3.2 InterpreterBinding

```text
InterpreterBinding
├── interpreter_id
├── interpreter
├── owner
└── scope
```

```text
ActionOwnerRef
├── kind: team | character
└── slot?
```

binding 只在 PRESS 时解析一次并写入运行时会话。HOLD、RELEASE 和 CANCEL 始终回到同一解释器，不因当前 `active_slot` 改变而重新路由。

### 3.3 组装校验

- 所有允许出现在配置中的输入键必须存在 selector。
- 同一个键不能重复注册 selector。
- 真实角色槽位必须存在角色动作解释器。
- 测试解释器不能作为真实角色的默认降级。
- 找不到解释器或动作实现时应在组装阶段报错。

角色不支持某个输入时，应由已经解析出的解释器返回结构化拒绝，而不是报告解释器缺失。

## 4. 动作解释器

动作解释器负责判断：

- 当前输入对应哪个动作。
- 当前角色、队伍、资源、冷却和状态是否允许。
- 应继续等待、拒绝、启动动作还是控制已有动作。
- 为动作准备哪些参数和初始状态。

解释器不负责：

- 创建 `ActionInstance`。
- 获取或释放动作锁。
- 直接修改动作实例或动作状态。
- 执行动作逻辑。
- 直接产生伤害、治疗或状态变化。

动作是否从 PRESS、HOLD 或 RELEASE 开始完全由对应解释器决定。通用层不设置统一开始规则。

解释器不得回溯生成开始帧早于当前仿真帧的动作请求。

### 4.1 角色能力公共条件

元素战技和元素爆发的公共条件由 `CharacterAbilityConditionCoordinator` 组合：

```text
CharacterActionInterpreter
-> CharacterAbilityConditionPort.evaluate(query)
   ├── CooldownConditionResult
   └── BurstEnergyConditionResult（仅爆发）
-> CharacterAbilityConditionResult
```

公共结果只表示冷却和标准元素能量门槛：

- 元素战技要求冷却有可用 charge。
- 标准元素爆发要求冷却有可用 charge 且元素能量已满。
- `capacity = 0` 的爆发把私有资源条件委托给 content，不按标准能量不足拒绝。
- 解释器继续判断姿态、角色私有状态和专属资源。
- `ActionManager` 继续执行锁、中断、owner、会话与实例创建的最终准入。

解释器目标依赖使用显式上下文：

```text
ActionInterpretationContext
├── simulation_context
└── ability_condition_port: CharacterAbilityConditionPort
```

`ActionManager` 在调用解释器时构造该上下文。解释器不得使用 `SimulationContext.get_system()`、类名字符串或完整 CooldownRuntime/EnergyRuntime 查找公共条件。

协调器结果不是 reservation。解释器构造 `PreparedAction` 后，冷却实际启动和爆发实际扣能仍由具体能力时序分别提交。

## 5. ActionInterpretationResult

第一版解释结果包含一个主要指令：

```text
ActionInterpretationKind
├── wait
├── reject
├── start_action
└── control_action
```

```text
ActionInterpretationResult
├── kind
├── prepared_action?
├── control_request?
├── session_policy
└── reason?
```

- `wait`：保持会话并等待后续触发。
- `reject`：记录拒绝，不创建实例。
- `start_action`：提交准备完成的动作请求。
- `control_action`：向已存在的动作实例提交语义化控制命令。

一个解释结果第一版不同时启动多个动作。一个动作产生多个机制结果应通过多个 impact 表达。

### 5.1 PreparedAction

```text
PreparedAction
├── action_key
├── owner
├── requested_start_frame
├── params
├── source_session_id
├── bind_session_on_accept
├── continue_on_reject
├── interrupt_kind?
└── metadata
```

- `bind_session_on_accept`：动作接受后，HOLD/RELEASE 是否继续控制该实例。
- `continue_on_reject`：管理器拒绝请求后，会话是否继续等待后续判断。
- `interrupt_kind`：本次动作请求用于判断是否允许中断冲突实例的语义标识。

### 5.2 ControlActionRequest

```text
ControlActionRequest
├── target_instance_id
├── command
└── params
```

命令是动作语义，例如：

```text
continue
enter_stage
release
cancel
finish
```

命令不携带 `keyboard.e` 等物理按键语义。解释器不能直接修改 `instance.state`。

## 6. Action 与 ActionRegistry

### 6.1 Action

`Action` 是无独立运行身份的具体动作逻辑：

```text
Action
├── action_key
├── admission_policy
├── create_initial_state()
├── on_start()
├── on_update()
├── on_command()
├── on_cancel()
└── on_finish()
```

Action 应尽量保持不可变。每次执行的可变状态由 `ActionInstance.action_state` 保存。

### 6.2 ActionRegistry

所有 Action 必须在组装阶段注册：

```text
ActionRegistry
├── register(action)
├── get(action_key)
└── contains(action_key)
```

解释器只返回 `action_key` 和准备参数，不直接构造任意 Action 对象。ActionManager 从注册表获得 Action 后创建实例。

第一版注册表直接保存不可变 Action 定义，不引入 ActionFactory。只有未来确认 Action 对象本身必须按实例构造时再扩展。

### 6.3 action_key

`action_key` 是运行时动作实现身份，不使用显示名称，也不等同于资产 `asset_key` 或装配入口 `handler_key`。

组装阶段必须检查：

- action key 非空且唯一。
- 解释器声明的 `supported_action_keys` 全部已注册。
- 动作声明的 impact key 已注册 factory，或明确声明不产生 impact。

## 7. ActionInstance

所有被接受并执行的动作都创建实例，包括切人。

```text
ActionInstance
├── instance_id
├── action
├── action_key
├── owner
├── source_session_id?
├── created_frame
├── start_frame
├── lifecycle
├── action_state
├── params
├── pending_commands
├── impact_points
├── completed_frame?
└── cancel_reason?
```

生命周期：

```text
scheduled
running
completed
canceled
```

被拒绝的动作请求不创建实例，拒绝只记录在 `ActionDecision`。

Action 不直接修改实例生命周期。它接收只读执行上下文并返回结构化结果：

```text
ActionExecutionContext
├── frame
├── instance_id
├── owner
├── source_session_id?
├── start_frame
├── elapsed_frames
├── action_state
├── simulation_context
└── params
```

```text
ActionExecutionResult
├── next_state?
├── emitted_impacts
├── lifecycle_directive
├── records
└── cancel_reason?
```

`lifecycle_directive` 第一版为 `continue/finish/cancel`。只有 ActionManager 可以应用结果并改变实例生命周期。

## 8. HOLD 与动作实例

HOLD 始终先交给输入会话绑定的解释器。

尚未创建实例时：

```text
HOLD
-> interpreter
-> wait | reject | start_action
```

已绑定实例时：

```text
HOLD | RELEASE
-> interpreter
-> ControlActionRequest
-> ActionManager
-> ActionInstance
-> Action.on_command()
```

同时，ActionManager 独立逐帧推进运行实例：

```text
ActionManager
-> ActionInstance
-> Action.on_update()
```

因此输入控制和动作运行是两条并行链路。Action 不直接理解原始按键，解释器也不代替 Action 推进动作时间轴。

## 9. 动作准入、锁与中断

### 9.1 判断边界

动作准入分为三层：

```text
CharacterAbilityConditionCoordinator -> 冷却与标准元素能量公共条件
CharacterActionInterpreter           -> content 私有条件与动作语义
ActionManager                        -> 通用运行时冲突和最终实例准入
```

公共条件通过不等于动作已经接受。解释器判断内容条件，ActionManager 判断通用运行时冲突。

ActionManager 最终检查：

- 开始帧和 owner 是否合法。
- 输入会话是否有效或已绑定。
- 新动作需要的锁是否冲突。
- 冲突实例是否允许被当前 interrupt kind 中断。
- 是否能够原子取消旧实例并创建新实例。

### 9.2 ActionAdmissionPolicy

```text
ActionAdmissionPolicy
├── action_tags
├── required_locks
├── interrupt_policy
└── concurrency_policy
```

ActionManager 不理解“普通攻击”或“切人”的具体逻辑，只比较 Action 声明的锁和中断信息。

### 9.3 具名锁

第一版锁不单独建模为运行时对象。Action 通过 `required_locks` 声明具名控制域，ActionManager 根据 scheduled/running 实例的锁集合判断冲突。

具名锁示例：

```text
team.control
character:1.control
character:1.movement
```

只有争用同一锁的动作才发生冲突。

### 9.4 中断策略

```text
ActionInterruptPolicy
├── allowed_interrupt_kinds
├── active_from_frame
├── active_until_frame?
└── cancel_policy
```

第一版 `cancel_policy`：

```text
reject_new
cancel_current
```

`queue_new`、`truncate_current` 和 `allow_parallel` 后续按真实需要扩展。

所有冲突必须先完整检查，再原子取消旧实例并创建新实例，不能出现部分取消。

### 9.5 ActionDecision

```text
ActionDecision
├── request_id
├── source_session_id?
├── accepted
├── frame
├── action_key
├── reject_reason?
├── created_instance_id?
└── interrupted_instance_ids
```

建议拒绝原因：

```text
invalid_start_frame
invalid_owner
session_not_active
session_already_bound
lock_conflict
interrupt_not_allowed
instance_not_found
invalid_command
unsupported_action
```

同帧动作请求按输入边界原始顺序处理，前一个请求产生的实例和锁对后一个请求立即可见。

## 10. 每帧处理顺序

第 N 帧：

```text
1. 发布 FRAME_STARTED
2. 启动此前预约在第 N 帧开始的实例
3. 按原始顺序处理第 N 帧 PRESS / RELEASE 边界
4. 每次解释后立即应用动作请求或控制命令
5. 按 session_id 处理仍为 held/listening 的 HOLD
6. 推进此前已经运行的 ActionInstance
7. 完成或取消到期实例
8. ImpactRuntime 处理第 N 帧影响点
9. 其他机制与空间运行态收尾
10. 发布 FRAME_ENDED
```

规则：

- 当前帧接受且 `start_frame=N` 的动作立即调用 `on_start()`，同帧后续输入可见其状态变化。
- 本帧刚执行 `on_start()` 的实例不再执行 `on_update()`。
- 控制命令立即调用 `on_command()`；若实例仍运行，可以在动作推进阶段执行 `on_update()`。
- RELEASE 帧不再调用 HOLD。
- 输入边界先于 HOLD，保持“显式输入先处理、运行态随后推进”的帧语义。
- Action 产生的本帧 impact 可以在同一帧后半段结算。

## 11. Impact 边界

### 11.1 ActionImpactPoint

Action 只产生动作影响点，不直接创建伤害、治疗等最终机制结果。

```text
ActionImpactPoint
├── impact_point_id
├── source_instance_id
├── owner
├── action_key
├── impact_key
├── scheduled_frame
├── targeting
├── params
├── cancel_with_action
└── status
```

状态为 `pending/dispatched/canceled`。

动作取消时：

- 已 dispatched 的影响点不回滚。
- pending 且 `cancel_with_action=true` 的影响点取消。
- pending 且 `cancel_with_action=false` 的影响点继续。

独立投射物或持续对象优先使用 `create_entity` 创建空间对象，之后由对象自行产生影响请求。

### 11.2 目标解析

动作索敌与实际 AOE 命中是两个阶段：

```text
Action Targeting
-> 选择瞄准目标和攻击方向
-> Damage Impact Area
-> Space 解析全部实际受击目标
```

`TargetingSpec` 只负责索敌候选、选择方式和攻击方向，不等同于最终伤害范围。最终目标必须由 Damage Impact 的 AOE 在影响点到期时按当前空间状态解析。

目标结构（已落地）：

```text
TargetingSpec
├── search_area?
├── selection_policy_key?
├── kinds
├── exclude_entity_ids
└── snapshot_policy
```

- 资料中的索敌形状和索敌范围进入 `search_area`，选择方式进入稳定 `selection_policy_key`；例如“分数”必须在组装阶段映射为注册策略 key，不能直接使用显示文本判断。
- 索敌只返回瞄准目标并确定本地前方；没有索敌时使用 Effect 已确认的锚点和朝向。

已落地该形态：`search_area` 保存圆柱（如 `15,10`，当前 X/Z 模型投影为同半径
圆），`selection_policy_key="分数"` 时运行时按
`distance_xz, stable_entity_id` 选择最近目标；下落攻击复用同一机制。

```text
snapshot_policy
├── resolve_on_impact
└── snapshot_on_emit
```

默认使用 `resolve_on_impact`。只有明确需要锁定瞄准目标的动作才使用 `snapshot_on_emit`；该快照不替代实际 AOE 在 Impact 到期时的目标查询。

### 11.3 Damage Impact 定义

Action 只负责产生类型化 Damage Impact 定义并交给 `ImpactRuntime`。`area`、
元素、衰减、标签、倍率与 AOE 解析的完整契约以[伤害系统设计](./系统/伤害系统设计.md)、
[战场空间设计](./战场空间设计.md)和[内容系统设计](./内容系统设计.md)为准，
本文档不重复。动作侧只承诺：

- 影响点携带稳定 `impact_key` 与 `TargetingSpec`；
- 影响点到期后由 content impact factory 展开为带 `DamageImpactSpec` 的
  DAMAGE 请求；
- 主攻击标签经 `DamageProfileRegistry` 选择完整公式，附加标签只参与条件和
  修饰。

当前空间只模拟 X/Z 水平平面，AOE 规范化为：

```text
ImpactArea2D = OrientedBox | Circle | CircleSector

OrientedBox
├── width       # 原始 Box.x，完整左右长度
├── depth       # 原始 Box.z，完整前后长度
└── local_offset_xz

Circle / CircleSector
├── radius
├── angle       # 未标注时为 360°
└── local_offset_xz
```

- Box 原始 `(x, y, z)` 中，运行时使用完整边长 `x` 与 `z`，内部命中计算可转换为半长 `x/2`、`z/2`；`y` 不进入当前查询。
- Circle 原始 `(R, H, Angle)` 中使用 `R` 与圆心角，`H` 在当前模拟中没有意义；未标注角度为 `360°`。
- Sphere 在当前 X/Z 模型中投影为半径相同的 Circle。
- 本地偏移和 AOE 朝向跟随 Action 索敌得到的攻击方向旋转；`local_offset.y` 当前忽略。
- 削韧、冲击、停滞和 Deployable 等资料字段在没有对应运行时消费者前不进入本契约。

### 11.4 ActionImpactContext

ImpactFactory 接收专门的动作影响上下文，不再使用 `ImpactRequest(kind=action)` 作为临时入口：

```text
ActionImpactContext
├── frame
├── impact_point_id
├── source_instance_id
├── owner
├── action_key
├── impact_key
├── target_refs
└── params
```

```text
ImpactFactory.create_requests(context)
-> tuple[ImpactRequest, ...]
```

`ImpactRequest.kind` 只表达真实机制意图：

```text
damage
heal
apply_aura
apply_status
create_entity
energy
movement
```

### 11.5 ImpactRuntime 与机制分发

`ImpactRuntime` 负责：

- 读取到期影响点。
- 执行 Action 索敌并确定攻击方向。
- 调用 ImpactFactory。
- 根据类型化 Damage Impact AOE 通过 Space 解析实际受击目标。
- 产生已经冻结目标集合的 ImpactRequest。
- 把请求交给机制请求分发器。

`ImpactRuntime` 不直接处理 `create_entity` 或其他具体机制。

```text
ImpactRequestDispatcher
├── damage        -> DamageSystem
├── heal          -> HealingSystem
├── apply_aura    -> AuraSystem
├── apply_status  -> StatusSystem
├── create_entity -> CreatedObjectRuntime
├── energy        -> EnergySystem
└── movement      -> MovementSystem
```

动作完成不代表其所有影响点已经处理。停止条件还必须检查待处理 impact 和机制请求。

### 11.6 下落攻击：MovementSystem 事件驱动

下落攻击不使用固定时间线，也不由动作写位移：

- 空中实体（`position.y > 0`）由 `MovementSystem` 从速度 0 开始受重力自然
  下落；下坠碰撞按实体碰撞箱（角色箱与目标箱 X/Z 与 Y 区间重叠）产生
  `MOVEMENT_COLLIDED` 事实，落地产生 `MOVEMENT_LANDED` 事实。
- 通用 `FallPlungeAction` 在 `on_update` 读取 Movement 当前帧事实：碰撞事实
  发出下坠碰撞影响点（每个下落过程一次），落地事实发出落地影响点并结束
  动作；影响点在事实帧当场发出，不预排帧。
- 伤害契约（球/圆柱 AOE、元素量、攻击标签）按法器通用资料表维护，AOE 以
  `player:active` 当前位置为锚点展开；削韧、冲击、停滞不进入契约。
- 位移由 `MovementSystem` 统一拥有，动作不再直接写 `Space` 位置。

## 12. 切人动作

切人是队伍级解释器产生的普通动作请求：

```text
keyboard.2 InputSession
-> TeamActionInterpreter
-> PreparedAction(action_key=team.switch, params.target_slot=2)
-> ActionManager
-> TeamSwitchActionInstance
-> TeamSwitchAction.on_start()
-> TeamRuntimeState.switch_to(2)
-> 同步 player:active
-> finish 或进入切人后摇
```

切人必须创建 `ActionInstance`。队伍状态修改属于 `TeamSwitchAction` 的动作逻辑。切人通常不需要 impact。

## 13. content 与组装

角色内容贡献（当前形态见[内容系统设计](./内容系统设计.md)）：

```text
ContentRuntimeContribution
├── action_interpreter?
├── actions
├── impact_factories
├── state_extension?
└── ...
```

组装器收集：

- 队伍动作解释器和队伍通用 Action。
- 按槽位拆分的角色动作解释器。
- 所有不可变 Action 定义。
- ImpactFactory。
- 其他内容运行时贡献。

构造：

```text
InputSessionTrace
CharacterAbilityConditionCoordinator
ActionInterpretationContext provider
ActionInterpreterRegistry
ActionRegistry
ImpactDispatcher
ImpactRequestDispatcher
ActionManager
ImpactRuntime
```

`core/` 不接触完整 `ContentRuntimeContribution`，只接收拆分后的协议实现和注册表。

## 14. 停止条件

模拟器只有在以下条件全部满足时才能自然结束：

- 所有输入会话计划已经完成。
- 没有 held/listening 的运行时输入会话。
- 没有 scheduled/running 动作实例。
- 没有待处理 ActionImpactPoint。
- 没有待分发或待结算 ImpactRequest。
- 没有运行中的空间对象或其他机制任务。

## 15. 当前实现状态

已落地：

- `InputTraceCompiler` 在组装阶段生成 `InputSessionTrace`，并由
  `SimulationAssembler` 注入 `ActionManager`；按帧处理 PRESS、RELEASE 和派生
  HOLD，`RuntimeInputSession` 与 binding 固定语义生效。
- `ActionInterpreterRegistry`、`TeamInterpreterSelector` 与
  `ActiveCharacterInterpreterSelector` 已接入组装校验。
- `ActionInterpretationResult`、`PreparedAction`、`ControlActionRequest` 和
  `InputSessionPolicy` 作为解释器返回边界；`ActionRegistry`、`ActionInstance`、
  `ActionAdmissionPolicy`、`ActionInterruptPolicy` 与 `ActionDecision` 已落地。
- `TimedImpactAction` 使用注册期固定的时间线；下落攻击由 `FallPlungeAction`
  按 MovementSystem 的碰撞/落地事实事件驱动，不预排影响帧、不写位移。
- `TeamSwitchAction` 作为普通 Action 修改 `TeamRuntimeState` 并同步
  `player:active`。
- `ActionImpactPoint`、`TargetingSpec`（`search_area`、分数选择）与
  `ImpactRuntime` 已落地：索敌先按分数选择最近目标，再按 Damage Impact 的球
  AOE 以目标为锚点解析实际受击目标（当前 X/Z 模型投影为同半径圆）。
- 下落攻击触发链路已接入：空中（`player:active.position.y > 0`）普攻按当前
  高度启动 `plunge` 动作；下坠碰撞与落地冲击由 MovementSystem 事实驱动
  （`FallPlungeAction` 在碰撞/落地帧当场发出影响点），高度真值与低空/高空
  分档使用全角色统一临时数据（见决策记录 2.19）。
- 下落攻击伤害数据已按法器通用资料表接入（球 `1.5` / 圆柱 `3.0/3.5`，
  见决策记录 2.19）：索敌为空，AOE 以 `player:active` 当前位置为锚点展开；
  `ImpactRequest.anchor_entity_id` 支持显式锚点，圆柱投影为同半径圆。
- MovementSystem 已落地：空中实体从速度 0 开始受重力自然下落，落地/碰撞
  发布事实；`ImpactKind.MOVEMENT` 已接线；动作不再直接写 `Space` 位置，
  `TimedImpactAction` 的垂直位移能力已删除。
- `ImpactRequestDispatcher` 已接入 `create_entity` 与 damage/elemental
  settlement 等请求；未接入的机制请求记录为暂未处理。
- `ActionInterpretationContext` 携带 `ability_condition_port`，
  `CharacterAbilityConditionCoordinator` 已接入 `ActionManager`；解释器只经
  该端口查询 E/Q 公共条件，不再允许用 `SimulationContext.get_system()` 拼接
  领域裸状态。
- `TimedActionSpec` 支持多影响点（`impact_points`：影响帧 + impact_key +
  可选 per-point targeting），`TimedImpactAction` 按注册期固定的时间线发出
  多个影响点；定时动作支持在指定帧开始冷却（`cooldown_start_frame` +
  `cooldown_ability_key`），由动作在对应帧通过 `CooldownRuntime` 提交。

未决项见第 16 节。

## 16. 未决与后续增强

以下内容不阻塞本文档正式化，但尚未成为契约：

- 结构化 reason code 与 evidence 如何进入动作解释/决策审计；在正式字段落地
  前，`reason` 保持字符串，不得把中文显示文本作为机器判断依据。
- 动作解释结果、动作决策和动作生命周期的最终事件类型与 payload。
- `action_state` 的快照序列化协议和恢复边界。
- 具体角色 `action_key`、控制命令与参数 schema 的最终清单。
- 下落攻击时序数值（低空线、高空线、重力）仍为临时值待确认；碰撞帧由
  `MovementSystem` 按实体碰撞箱逐帧判定；二维 Box/扇形 AOE 仍待扩展。
- `MovementSystem`：出现第二个位移来源（击退、投射物、敌人移动）时启用，
  不在当前契约内提前搭建。
- 同帧多个机制请求的结算顺序。
- 多影响点之外的动作能力（按帧动态参数、多阶段时间线）仍按真实需求逐项
  评估，不提前预建。
- 冷却开始帧之外的冷却写路径（减秒、重置、多充能消费）仍按真实能力逐项
  接线。
- 停止条件与运行中空间对象、待处理机制请求之间的最终协作校验。
