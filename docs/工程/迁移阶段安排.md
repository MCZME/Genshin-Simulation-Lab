# 迁移阶段安排

> 状态：草案。
> 本文档用于记录从旧项目迁移到新项目的整体阶段安排。具体阶段的范围和验收标准可以随着实现推进继续细化。

## 1. 目标

本次迁移的目标不是复制旧项目代码，而是在当前项目已经确认的模块边界、配置契约和数据契约基础上，逐步迁移旧项目中仍然有效的能力。

迁移过程优先保证：

- 架构边界稳定。
- 数据契约可追踪。
- 数值与机制行为可验证。
- 每一步都有测试或可复现检查。
- 旧项目能力进入新项目时能找到明确的新模块归属。

## 2. 旧项目查看方式

旧项目位置：

```text
E:\project\Genshin Damage calculation
```

查看旧项目时按以下顺序进行：

1. 先阅读当前项目文档，确认本次任务涉及的模块边界、契约和质量要求。
2. 再阅读旧项目相关文档，优先查看架构、模拟流程、数据传输、持久化、测试指南和具体机制文档。
3. 最后查看旧项目代码与测试，把旧代码作为行为来源、覆盖范围和实现参考。

常用定位命令：

```powershell
rg --files "E:\project\Genshin Damage calculation"
rg -n "class SimulationContext|class Simulator|class GameEvent|class EventEngine|class ActionCommand|class SimulationAssembler" "E:\project\Genshin Damage calculation"
```

旧项目中的高价值参考入口：

- `core/context.py`：`SimulationContext`、`EventEngine`。
- `core/event.py`：`GameEvent`、`EventType`。
- `core/simulator.py`：帧驱动模拟器。
- `core/action/action_data.py`：`ActionCommand`、动作状态和动作帧数据。
- `core/factory/assembler.py`：旧组装器。
- `core/persistence/database.py`、`core/persistence/projector.py`：运行期结果库与投影。
- `core/batch/models.py`：批量项目、节点和变异规则模型。
- `tests/`：行为覆盖范围和数值预期参考。

规则：

- 不直接照搬旧项目测试文件。
- 不把旧项目的 MySQL、UI 或持久化依赖带入 `core/`。
- 不以显示名称作为仿真识别依据。
- 涉及具体角色、武器、圣遗物、反应或敌人机制时，必须先确认来源和验收方式。

## 3. 迁移范围分层

当前阶段对旧项目能力的处理方式分为两类：

### 3.1 需要重新设计的内容

- 资源数据库的重新实现。
- 模拟架构的调整，重点是动作序列与组装边界。
- UI 的完全重新设计。

这三类内容不按旧代码路径直接迁移，而是按新项目的契约、边界和使用方式重新落地。

### 3.2 直接迁移的内容

- 游戏逻辑相关实现。
- 纯算法、规则、机制和数值处理。
- 只要不依赖旧 UI 形态、旧数据库结构或旧动作序列契约，就优先直接迁移到新项目对应模块。

直接迁移并不等于原封不动拷贝。代码实现可以复用，但仍要符合新项目的模块边界和测试要求。

## 4. 阶段总览

迁移分为以下阶段：

```text
阶段 0：迁移准备与风险盘点
阶段 1：纯核心最小运行时
阶段 2：配置、资产与组装闭环
阶段 3：最小仿真闭环
阶段 4：结果持久化与分析闭环
阶段 5：资产构建与内容迁移
阶段 6：批量任务与参数扫描
阶段 7：UI 工作流重设计
阶段 8：数值校准、回归体系与扩展迁移
```

阶段之间可以小步交错，但不能跳过对应的契约、测试和文档同步要求。

## 5. 阶段 0：迁移准备与风险盘点

目标：

- 建立旧项目能力清单。
- 建立旧能力到新模块的映射。
- 明确第一批迁移对象与不迁移对象。
- 补齐测试与 golden case 策略草案。
- 先冻结直迁范围，再单独讨论动作序列重设计。

参考来源：

- 当前项目的模块边界、资产库设计和仿真配置契约。
- 旧项目架构、模拟流程、测试指南和核心系统文档。
- 旧项目 `tests/` 中已有覆盖范围。

交付物：

- 旧项目能力清单。
- 迁移优先级列表。
- 每个候选能力的新模块归属。
- 高风险能力清单，例如复杂反应、角色机制、持久化 schema、UI 工作流。
- 第一批直迁顺序。
- 动作序列重设计问题清单。

建议同步维护：[旧项目能力盘点](./旧项目能力盘点.md)。

验收：

- 每个候选能力都能说明迁移原因、目标模块和验证方式。
- 不确定的机制或数值被标注为待确认。
- 直迁与重设计的边界不会互相污染。
- 第一批直迁范围足够小，能在一轮内验证。

阶段 0 建议按以下顺序推进：

1. 冻结直迁清单，先不碰动作序列细节。
2. 给直迁项补风险等级和 golden case 来源。
3. 标记必须重设计的边界，尤其是动作序列和 UI。
4. 选择第一批最小迁移对象，作为阶段 1 入口。

## 6. 阶段 1：纯核心最小运行时

目标：

- 在 `core/` 中建立不依赖数据库、UI、资产库和具体内容的最小运行时。
- 优先迁移低依赖、可测试的核心概念。

建议顺序：

1. 事件系统：`EventType`、`GameEvent`、`EventHandler`、`EventEngine`。
2. 动作指令：`ActionCommand` 和基础动作状态。
3. 仿真上下文：最小 `SimulationContext`、帧计数和快照接口占位。
4. 模拟器骨架：帧推进、动作队列和终止条件。

注意：

- 第一版动作指令应适配新配置契约，动作序列引用队伍槽位，不引用角色名称。
- 快照只由 `core/` 生成，不在 `core/` 中写数据库。
- 不在本阶段迁移伤害、反应、角色技能等复杂数值逻辑。

交付物：

- `core/events/`、`core/actions/`、`core/simulation/` 的最小实现。
- 单元测试覆盖事件分发、取消、帧事件缓冲、动作命令结构和帧推进。

验收：

```powershell
uv run pytest
uv run ruff check
uv run pyright
```

## 7. 阶段 2：配置、资产与组装闭环

目标：

- 落地 `SimulationConfig` 第一版校验模型。
- 落地资产数据对象与 `AssetRepository` 协议。
- 建立 `handler_key` 注册和组装阶段错误检查。

建议顺序：

1. `application/config/`：配置模型、基础校验和 JSON 读写。
2. `assets/`：资产模型、仓库协议和资产错误类型。
3. `content/registry.py`：handler 注册表。
4. `application/assembly/`：最小 `SimulationAssembler`。

注意：

- 组装阶段发现缺资产、缺 handler 或 JSON payload 错误时立即报错。
- `application/` 可以编排仓库和 handler，但不直接写 SQL。
- `core/` 不依赖 `assets/`、`content/`、`application/` 或 `infrastructure/`。

交付物：

- 配置校验模型。
- 资产仓库协议。
- handler 注册表。
- 组装器最小闭环测试。

## 8. 阶段 3：最小仿真闭环

目标：

- 跑通一次最小仿真：读取配置、组装运行时、执行动作序列、生成结果摘要。
- 先使用测试内容或通用占位内容，不急于迁移真实角色复杂机制。

建议范围：

- 一个测试角色或通用动作 handler。
- 一个目标。
- 一段动作序列。
- 一个可断言的事件流或结果摘要。

交付物：

- `genshin-sim config validate path/to/config.json`。
- `genshin-sim run path/to/config.json` 的最小行为。
- 集成测试覆盖配置到运行的闭环。

验收：

- CLI 通过 `application/` 调用能力。
- UI、SQLite 和具体内容逻辑没有泄漏进 `core/`。
- 运行结果具备可复现断言。

## 9. 阶段 4：结果持久化与分析闭环

目标：

- 迁移并整理旧项目较成熟的 SQLite 结果持久化、事件流和投影思路。
- 将旧项目 `ResultDatabase`、`DataProjector`、`AnalysisDataProcessor` 的有效概念分别落入新项目边界。

目标归属：

- 快照模型与快照导出：`core/snapshots/`。
- SQLite 写入、schema、WAL、投影器：`infrastructure/results_sqlite/`。
- 结果读取协议：`application/` 依赖的 repository / writer protocol。
- 结果加工、聚合、时间轴和报告模型：`analysis/`。

注意：

- 运行期结果库与基础资产库分离。
- 所有仿真都保存完整结果数据。
- `core/` 只生成快照和事件数据，不负责写库。

交付物：

- 结果库 schema 草案或实现。
- 结果写入器和读取器。
- 结果摘要分析。
- 持久化集成测试。

## 10. 阶段 5：资产构建与内容迁移

目标：

- 构建本地 SQLite 基础资产库。
- 逐步迁移角色、武器、圣遗物和通用 handler。

建议顺序：

1. 资产库 DDL 和校验工具。
2. 数据导入流程，从源数据生成临时库并校验后替换正式库。
3. 通用静态 modifier handler。
4. 一个最小真实内容切片，例如一个角色、一个武器或一个圣遗物套装。

注意：

- 复杂行为进入 `content/`，参数进入资产库。
- `asset_key` 与 `handler_key` 分离。
- 数据来源、字段转换和百分比倍率转换必须可追踪。

交付物：

- `genshin-sim assets build`。
- `genshin-sim assets validate`。
- `genshin-sim assets info`。
- 至少一个内容切片的测试或 golden case。

## 11. 阶段 6：批量任务与参数扫描

目标：

- 迁移旧项目 `BatchProject`、`BatchNode`、`MutationRule` 等批量任务概念。
- 让批量任务基于新 `SimulationConfig` 做配置变异和结果汇总。

目标归属：

- 批量模型、编译器和执行编排：`application/batch/`。
- 结果聚合和对比：`analysis/`。
- 批量运行数据持久化：视结果库设计放入 `infrastructure/results_sqlite/` 或独立存储适配。

注意：

- 第一版只支持确定性、可解释的配置替换和区间枚举。
- 并行执行策略可以后置，先保证编译和结果一致性。

交付物：

- 批量配置模型。
- 批量编译器。
- 批量运行摘要。
- 参数扫描测试。

## 12. 阶段 7：UI 工作流重设计

目标：

- 基于新架构重做 UI 工作流。
- UI 只通过 `application/` 调用能力。

建议顺序：

1. 配置编辑。
2. 队伍、角色、武器和圣遗物基础构建。
3. 动作序列编辑。
4. 单次仿真运行。
5. 结果摘要。
6. 后续再扩展复盘、对比和批量任务界面。

注意：

- UI 不直接访问 SQLite。
- UI 不直接组装仿真核心对象。
- UI 不实现分析算法。
- 旧项目 Flet MVVM 分层思路可以保留，但具体界面需要重新设计。

## 13. 阶段 8：数值校准、回归体系与扩展迁移

目标：

- 建立长期数值可信度体系。
- 逐步扩大角色、武器、圣遗物、反应和机制覆盖范围。

重点：

- 补充 `tests/golden/`。
- 为核心机制建立最小可复现实例。
- 为复杂角色机制记录来源、旧项目参考、预期行为和验证方式。
- 将测试分层稳定为 `unit/`、`integration/`、`golden/`。

注意：

- AI 不能仅凭记忆实现游戏机制数值。
- 来源不明确时必须标注不确定性并请求人工确认。
- 数值机制变更必须同步文档。

## 14. 每次迁移任务模板

每次开始具体迁移前，建议按以下格式记录任务：

```text
目标：
范围：
旧项目参考：
新项目目标模块：
涉及契约：
验收标准：
测试或 golden case：
禁止事项：
待确认问题：
```

## 15. 暂停并请求确认的情况

遇到以下情况应暂停实现并请求人工确认：

- 改变顶层模块职责或依赖方向。
- 改变 `SimulationConfig`、资产库 schema 或结果库核心结构。
- 引入新的外部依赖、数据源、网络抓取流程或大型工具链。
- 实现尚无可信来源或 golden case 支撑的游戏机制数值。
- 删除或覆盖用户已有改动。
- 需要大范围改写旧项目逻辑且无法小步验证。
