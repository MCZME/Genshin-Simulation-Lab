# 内容版本约定

> 状态：已确认约定。
> 本文只记录 content 版本参数的已确认结论，不展开角色、武器、圣遗物的具体实现规范。
> content 层稳定架构见[内容系统设计](../../架构/内容系统设计.md)。
> 相关讨论仍在进行；未写入本文的内容一律视为未确认。
> 最后更新：2026-08-09。

## 1. 文档定位

本文回答：

- content 如何表达“当前实现状态”
- 版本名如何书写
- 版本信息是否进入代码，以及后续用途边界
- 角色、武器、圣遗物 content 中 `version` 的声明位置、写法和组装后读取方式

本文不回答：

- 单内容开发细则
- 完整分支策略（见仓库 `commit-workflow` skill；与 `version` 的配合见 2.6）
- 资产 `handler_key` 的完整绑定规则（结论与入口见 2.6）
- registry 默认挂载细则（结论见 2.6）
- 版本晋升、历史谱系或其他复杂版本逻辑
- UI 限制交互的具体产品设计

## 2. 已确认结论

### 2.1 只有一个版本参数

content 使用单一参数 `version` 表达该内容的**当前状态**。

不引入以下附加参数作为版本模型的一部分：

- 独立的阶段字段
- 来源版本
- 晋升记录
- 版本历史链

`version` 描述的是“这个内容现在处于什么状态”，不是“它从哪个版本发展而来”，也不是“应按哪个历史版本继续开发”。

### 2.2 版本命名

| 当前状态 | 写法 | 说明 |
| --- | --- | --- |
| 开发 | `dev-<阶段名>` | 阶段名无严格限制，可按当前开发内容自行设置 |
| 测试 | `v<n>` | `n` 为数字；从 `v1` 开始 |
| 正式 | `release` | 表示当前为正式版 |

示例：

```text
dev-action
dev-heal
v1
v2
release
```

说明：

- 开发中做动作时，当前版本可以是 `dev-action`
- 进入测试时，当前版本可以是 `v1`、`v2` 等
- 作为正式内容时，当前版本是 `release`

### 2.3 版本表示当前状态

开发者当前在做什么，`version` 就写成什么。

例如：

- 正在开发角色动作：`dev-action` 或同类开发名
- 正在测试该内容：`v1`
- 该内容已是正式版：`release`

同一内容在某一时刻只有一个当前 `version` 值。

### 2.4 代码可读取，用途保持简单

`version` 需要进入代码，并可被读取。

已确认的用途只有：

1. 展示当前版本，例如后续 UI 显示。
2. 做简单限制，例如后续 UI 设置是否允许使用非正式版内容。

不把 `version` 做成复杂版本系统。不在本约定中引入版本比较、多 active 实现调度、自动晋升流程等逻辑。

后续若做非正式版限制，预期只是读取 `version` 后做简单判断，例如是否等于 `release`。

### 2.5 声明、写入与读取

角色、武器、圣遗物 content 的 `version` 按同一最小方式处理：

1. **声明位置**：放在对应内容包的 `data.py`。
2. **声明形式**：使用模块级常量，例如 `VERSION = "dev-action"` 或带内容前缀的 `BARBARA_CONTENT_VERSION = "dev-elemental-burst"`。
3. **写入组装产物**：内容包工厂（`create_*_content_unit`）创建 `ContentUnit` 时写入正式字段 `version`。
4. **读取方式**：组装后通过 `ContentUnit.version` 读取；值为普通字符串。
5. **校验**：第一版只要求必填且为非空字符串；不在本约定中强制复杂格式校验。

不采用以下方式作为主路径：

- 声明在包内但组装后不可读（未写入 `ContentUnit.version`）
- 仅放入 `metadata["version"]` 作为稳定读取口
- 引入独立版本对象、阶段字段或晋升链路

包结构见：

- [内容包结构约定](./内容包结构约定.md)

### 2.6 registry、handler_key 与分支

以下周边规则已经确认，正文见对应正式文档：

1. **进入 registry**：默认 registry 显式注册所有已添加条目（`create_default_content_unit_registry()`），不按 `version` 筛选或做多实现调度；`dev-*` / `v<n>` / `release` 只是同一注册条目的状态标签，非正式版限制由后续 UI 按 `version` 简单判断（见[内容系统设计](../../架构/内容系统设计.md)第 8 节）。
2. **真实资产绑定 `handler_key`**：资产默认 `handler_key = NULL`；当 `content/` 已添加并注册对应实现条目后，通过 `assets set-handler` 维护命令写入唯一键（可带 `--manifest` 写回本地 manifest），或使用 `sync-handlers` 批量补同步；未添加前保持 NULL 或 `*.unimplemented_*` 占位键，`generic.noop` / `generic.test_*` 只用于测试（见[资产数据库设计](../../契约/资产数据库设计.md)第 11 节）。
3. **分支配合**：分支按仓库 `commit-workflow` 的 `<type>/<topic>` 命名（Codex 用 `codex/` 前缀），不表达内容版本；`version` 独立表示内容当前状态，开发中内容在分支上以 `dev-<阶段名>` 声明。

## 3. 明确排除的理解

以下理解不属于本文约定：

- `version` 之外再维护 `stage`
- 记录 `release` 由哪个 `vN` 晋升
- 把 `version` 当作开发谱系或历史归档
- 因版本展示需求而引入复杂 content 版本管理框架
- 以 `metadata["version"]` 作为长期稳定读取契约
- 在 registry 中按 version 做多实现调度
