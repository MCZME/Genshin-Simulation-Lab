# 原神游戏机制实现规范

> 状态：正式规范。
> 本文约束伤害、治疗、生命、护盾、能量、元素附着、ICD、反应、抗打断等原神游戏机制在本项目中的设计、实现和验证方式。
> 最后更新：2026-08-09。

## 1. 术语与范围

本文使用以下术语：

- **原神游戏机制**：伤害、治疗、护盾、反应、附着、ICD、能量等领域规则。
- **领域系统**：`core/systems/<domain>/` 中拥有某一类机制状态、公式、计划、提交入口和事实的实现。
- **游戏内容**：角色、武器、圣遗物和通用效果的具体行为实现，位于 `content/`。

三者不能混用。领域系统直接维护适合自身规则的状态模型；普通伤害、治疗等一次性结算不要求创建长期实例。游戏内容通过稳定入口向领域系统构造请求，不拥有领域系统的全局状态。领域运行态边界见[领域运行态实现规范](./领域运行态实现规范.md)。

## 2. 总体原则

- 先确定可信行为目标和验收方式，再写实现。
- 纯公式解析、状态提交和外层编排必须分离。
- 每个状态只有一个所有者和唯一写入口。
- 事件表达已经发生的事实，不作为当前结算的可变 hook。
- 相同配置、资产版本、输入、帧顺序和随机种子必须得到相同结果。
- 所有可持久化模型使用强类型值对象并提供稳定序列化。
- 缺少可信数值来源或 golden case 时不得凭记忆补齐游戏规则。

## 3. 资料与可信度

### 3.1 来源优先级

专题规范可以为特定机制确认更严格的真值规则，并优先于本节通用顺序。元素附着、ICD 与反应以[元素附着、ICD 与反应设计规范](./元素附着、ICD与反应设计规范.md)中的人工确认规则为准。

机制实现按以下顺序选择依据：

1. 当前版本游戏内描述、官方说明和可重复观测结果。
2. 维护良好且提供证据的机制资料库。
3. 当前版本 Wiki 或社区文档的交叉验证。
4. 旧项目实现和测试，仅作为迁移范围与历史行为参考。
5. 明确标注的待确认假设，不得作为正式数值真值。

### 3.2 版本敏感性

每个真实机制必须记录来源适用版本。角色倍率、持续时间、覆盖规则、反应系数和特殊例外在接入时重新核对；旧版本资料只能用于证明模型需要具备某种表达能力。

### 3.3 Golden case

复杂数值逻辑至少提供一个最小可复现 golden case，记录：

- 输入资产与等级。
- 相关属性和状态。
- 帧顺序。
- 公式中间量。
- 预期结构化结果。
- 数值或行为来源。

## 4. 设计文档要求

一个新的领域机制进入编码前，必须明确：

- 目标与非目标。
- 输入请求和输出结果。
- 状态所有者与唯一写入口。
- 使用创建时快照还是运行时动态查询。
- 与属性、生命、Action、Impact、Event 和 Space 的边界。
- 原子提交范围和事件顺序。
- 错误模型。
- 测试矩阵与可信数值来源。
- 当前不实现的范围。

稳定字段、枚举、序列化和跨模块数据结构应进入 `docs/契约/`；长期职责和运行流程进入 `docs/架构/`；阶段任务、迁移清单和未完成工作进入 `docs/工程/`。

开始编码前按上述各项逐项确认。

## 5. 推荐实现分层

领域机制优先沿用以下分层，但不为目录完整创建空抽象：

```text
类型化请求
-> 纯 Resolver / Formula
-> 不可变 Resolution / Result
-> Runtime / Store 原子提交
-> Handler / Adapter 编排
-> 事实事件与快照
```

### 5.1 请求

请求描述结算意图和所需上下文，不保存已推导的最终值。请求必须使用稳定引用、强类型枚举和有限数值，不能依赖显示名称或松散 tag 猜测核心语义。

### 5.2 Resolver 与公式

Resolver 负责纯查询和纯计算：

- 不写 Store。
- 不修改生命、护盾或实体状态。
- 不发布状态变化事件。
- 不读取 UI、数据库或文件。
- 返回中间量足够完整的不可变结果，支持审计。

### 5.3 Runtime 与 Store

Runtime 拥有领域状态提交顺序；Store 拥有具体状态。涉及多个实例或多个字段时必须先计算完整更新集并校验前值，再一次提交，不能逐条边算边写。

### 5.4 Handler 与 Adapter

Handler 负责把上游通用请求转换为领域强类型请求，并编排多个明确写入口。Handler 不重复实现领域公式，也不通过字符串字段重新解释已经类型化的结果。

## 6. 数值规则

- 所有外部数值先拒绝 `bool`，再校验为有限 `int | float`。
- 对非负、正数、比例或上下限使用显式验证，不依赖后续公式自然报错。
- 浮点求和优先使用稳定顺序和 `math.fsum()`。
- 接近零归一化必须有明确容差和领域理由。
- 不使用无文档的 clamp 掩盖非法状态。
- 中间乘数和最终结果都必须校验有限性。
- 结果保存参与审计所需的公式分量、倍率、来源和上下文。

## 7. 快照与动态查询

每个公式输入必须明确属于以下哪一类：

- 创建时快照。
- 结算帧动态查询。
- 运行态累计状态。
- 上游已经结算完成的输入。

不得把动态属性提前乘入实例真值，也不得在结果分析阶段重新决定运行时真值。快照发生帧和查询主体必须进入契约或结果记录。

## 8. 状态所有权

- 属性定义和 modifier 聚合由属性系统拥有。
- 当前生命由 `HealthRuntime` 和健康 Store 拥有。
- 有身份和生命周期的领域实例由对应领域 Runtime 和 Store 拥有。
- 护盾完整记录和容量由 `ShieldStore` 拥有，不进入生命状态。
- 空间位置和空间实体登记由 Space 拥有。
- handler 自身长期专属状态由挂载在 `CharacterRuntimeState.content_states` 下的 `ContentStateMount` 拥有。

同一状态不得同时保存在实体、content state 和多个领域 Store 中。跨系统只能通过类型化请求、只读查询或明确 adapter 协作。

## 9. 标识与绑定

- 资产身份使用 `asset_key`。
- 行为实现绑定使用 `handler_key`。
- 机制语义、冲突和公式分量使用稳定 key。
- 运行期实例使用稳定 instance id。
- 显示名称不参与查询、冲突、覆盖或 handler 绑定。

缺 handler、能力不匹配、JSON 格式错误和引用不存在应尽量在组装阶段失败，不延迟到仿真运行中。

## 10. 事件、命令与重入

- 命令或强类型方法调用表达状态变更意图。
- 事件只表达已经提交的事实。
- 状态先提交，事件后发布。
- 事件 handler 不能在当前调用栈中递归修改同一次结算。
- 需要后续触发时，应进入明确的后续阶段或命令队列。
- 尚未实现通用队列的系统必须通过领域事务边界拒绝同步重入。
- 事件顺序是契约的一部分，测试必须断言。

## 11. 确定性与原子性

- 所有多实例查询和提交使用稳定排序键。
- 不依赖 `set`、普通 dict 构造来源或注册顺序的偶然遍历结果。
- 同帧输入集合在处理阶段开始前冻结。
- 多对象状态变化先完整校验再提交。
- 提交失败不能留下只更新一部分实例的中间状态。
- 事件、快照和结果记录只能观察到提交前或提交后的完整状态。

## 12. 跨系统边界

### 12.1 属性

领域系统通过 `AttributeResolver` 或更小的只读协议查询属性。modifier 查询无副作用，不创建、刷新或移除运行态实例。

### 12.2 生命

生命写入统一经过 `HealthRuntime` 的类型化入口。伤害、治疗、护盾和直接扣血在进入生命系统前完成各自公式与前处理，不直接修改 `HealthState`。

### 12.3 Action 与 Impact

Action 只描述动作时间轴、索敌和到期影响点。Action、Reaction、周期状态和空间实体产生的伤害必须统一形成 Damage Impact，由 Impact/Space 按实际 AOE 解析目标，再逐目标进入元素与 Damage 流程；任何领域不得绕过 Impact 直接构造另一套伤害结算入口。

Damage Impact 必须保留稳定主攻击标签、附加攻击标签、打击类型、远近类型、元素量和 ICD 标签/序列标识。主攻击标签映射 Damage Profile；`formula_key` 不作为 content 或 Reaction 显式填写的公开变量，未注册的非反应主攻击标签默认使用通用公式。

### 12.4 Event

EventEngine 负责事实发布和记录，不负责计算领域结果或拥有领域状态。

### 12.5 Space

范围、位置和目标选择由 Space 提供。当前 Damage Impact AOE 只使用 X/Z 平面的定向 Box、Circle 和 CircleSector，不使用高度；领域系统消费稳定目标引用，不自行维护第二份空间索引。

## 13. 错误模型

每个领域系统至少区分：

- 输入或模型验证错误。
- 属性或依赖查询错误。
- 状态或实例不存在。
- 生命周期或策略冲突。
- 原子提交冲突。
- 不支持的枚举、公式或 handler。

错误消息应包含稳定 key、instance id、主体引用或字段路径，不能只输出显示名称。非法输入不得静默忽略，除非上游契约明确把该请求定义为可审计的 ignored request。

## 14. 测试要求

### 14.1 模型测试

覆盖强类型、不可变性、有限数值、枚举、引用、边界值和稳定序列化。

### 14.2 公式测试

覆盖每个公式分量、乘数、快照时机、动态查询和非法中间值。

### 14.3 状态测试

覆盖创建、提交、刷新、替换、过期、显式移除、无目标、零值和失败不修改状态。

### 14.4 顺序与原子性测试

覆盖同帧多请求、多实例稳定顺序、批量前值冲突、事件顺序和事件回调重入。

### 14.5 集成与 golden

集成测试验证 Action/Impact、组装、领域系统、生命、事件和结果持久化的纵向链路。真实数值必须由 golden case 支撑；测试 content 只能证明工程链路，不能冒充真实机制完成。

## 15. 文档同步

以下变化必须同步正式文档：

- 领域状态所有者或依赖方向。
- 请求、结果、枚举和序列化结构。
- 快照与动态查询时机。
- 事件类型和发布顺序。
- 资产或配置字段。
- 测试基线、迁移策略和完成范围。

正式设计不得长期保留“建议实现”和“实际实现差异”两套叙述。当前实现与正式契约不一致时，应先评审并更新其中一方。

## 16. 禁止事项

- 不凭记忆实现版本敏感数值。
- 不用显示名称绑定行为或判断冲突。
- 不把所有领域状态塞进通用 dict。
- 不让 Resolver、modifier 查询或事件回调产生隐式副作用。
- 不让领域系统直接访问 SQLite、UI 或 application 服务。
- 不让 content 直接写领域 Store 或完整 `SimulationContext`。
- 不使用单一全局优先级替代明确的覆盖和冲突策略。
- 不为尚未确认的未来能力提前建立万能框架。
