# 元素反应系统边界与领域模型

> 状态：生效；当前覆盖普通蒸发、融化、超载、超导、冻结、碎冰、感电、扩散、结晶、燃烧、激化和绽放所需的公共基础。

最后更新：2026-08-07

## 1. 系统定位

`core/systems/reaction/` 是元素反应领域系统。它根据一次已经通过元素施加入口形成的交互请求、目标当前 Aura 观察值和 Reaction 自身状态，决定：

- 是否形成反应；
- 命中哪个明确方向；
- 后手元素预算与先手 Aura 的精确消费；
- 是否形成 `ReactionOccurrence`；
- 是否输出当前 Impact 伤害调整或其他强类型 Effect；
- 是否需要 Reaction 自身状态、Gate、周期根或实体计划。

Reaction 不直接修改 Aura，不执行最终伤害公式，也不负责跨系统提交。

## 2. 唯一真值与职责

| 领域 | 拥有的唯一真值 | Reaction 与它的边界 |
| --- | --- | --- |
| Aura | Aura Component、贡献元素量、衰减和 Link | Reaction 只输出精确元素变化语义，由 Aura 计划和提交实际变化 |
| Aura ICD | Binding 对应的窗口、序列游标和系数决议 | Reaction 只接收 ICD 后实际后手预算，不推进 ICD |
| Reaction | Definition、Profile、候选顺序、occurrence、ReactionState、Gate 与资源 | 不复制 Aura 元素量，不读取 Damage 最终结果 |
| Damage | Damage Profile、属性读取、公式、中间量审计和 DamageResult | Reaction 只输出强类型伤害调整 |
| Space | 实体、位置、目标查询和空间变更 | Reaction 只声明强类型目标选择或实体效果 |
| Coordination | 跨系统准备、校验、提交和事实顺序 | 不拥有长期领域状态或反应公式 |
| EventEngine | 已发生事实的同步发布和记录 | 不作为当前结算的递归写入口 |

这些边界遵守系统自治：Reaction 不能 import Aura、Damage 或 Space 的具体 Runtime/Store，也不能直接修改其他系统状态。

## 4. Definition、签名与 Profile

`ReactionDefinition` 是一个反应机制的注册单元，包含：

- `reaction_key`：稳定反应身份；
- `handler_key`：规则实现绑定入口；
- `trigger_signatures`：允许的后手元素、先手 Aura 与方向 key；
- `profiles`：每个方向使用的强类型数值 Profile；
- `rule`：纯反应判定与效果构造实现；
- `entry_kind`：反应进入方式。

元素交互型 Definition 必须至少声明一个签名和一个 Profile，且签名与 Profile 的 `direction_key` 一一对应。方向不能依赖注册顺序推断。

普通蒸发和融化使用 `AmplifyingReactionProfile`：

```text
profile_key
reaction_key
direction_key
trigger_element
base_multiplier
```

`base_multiplier` 必须为正数。Reaction Profile 只声明反应语义，不读取元素精通或执行最终伤害公式。

普通超载、超导和燃烧使用 `TransformativeReactionProfile`，额外声明 Damage Profile、Element、基础倍率、Gate Definition 和 damage kind。Profile 不保存空间目标、运行时 Gate Record 或最终 Damage 输入。

普通冻结使用 `StateReactionProfile` 声明不直接修改当前伤害的持续状态方向。普通碎冰使用 `entry_kind = STATE_TRIGGER`，由强类型打击证据与状态观察进入，可以不声明元素签名和方向 Profile。

## 5. Registry 与生产组装

`ReactionRegistry` 通过 `reaction_key` 注册 Definition：

- 重复 `reaction_key` 在注册阶段失败；
- `definition_for()` 对未注册 key 报错；
- `definitions` 以稳定 key 排序返回；
- 禁止自动扫描、隐式导入注册或依赖目录顺序决定候选结果。

生产 assembler 通过 `create_default_reaction_bootstrap()` 构造完整 `ReactionBootstrap`，再由 bundle 的 `create_runtime()` 同时注入 Registry、伤害 Gate 与成立 Gate。每个 mechanic 拥有自身 Definition 和 Gate，bootstrap 只负责显式组合当前生产能力；禁止维护按历史版本递增的平行注册入口。

## 6. 交互输入

`ReactionEvaluationRequest` 至少表达：

```text
interaction_id
target_impact_ref
frame
order
source_ref
subject_ref
incoming_element
incoming_amount
observed_aura
current_damage_element?
transformative_source_observation?
trigger_context?
    observed_frozen_state?
    freeze_resistance_observation?
    character_source_refs?
    reaction_capabilities?
```

后续机制可以增加强类型来源观察、触发上下文和 Reaction 状态观察；不能通过松散 metadata 绕过模型。

其中：

- `incoming_amount` 是 ICD 决议后的实际后手预算；
- `observed_aura` 是协调器从 Aura 领域取得的只读观察；
- `current_damage_element` 只用于判断当前关联伤害是否具备调整资格；
- `target_impact_ref` 关联同一次目标级 Impact，不承担请求去重职责。
- `transformative_source_observation` 为即时剧变冻结来源等级、元素精通和等级系数提供中立证据；
- `trigger_context` 保存钝击等非元素触发语义，不把物理伪装成 Element。
- `observed_frozen_state` 与 `FROZEN` Aura 必须通过同一 Link 形成一致的只读投影；
- `freeze_resistance_observation` 是值域 `[0, 1]` 的目标级只读输入，当前生产未提供时固定使用 `0.0`。
- `character_source_refs` 是协调器从队伍运行态提供的角色来源白名单；Reaction 只能用它冻结月反应参与者，不能根据任意字符串反推角色身份。
- `reaction_capabilities` 是同一帧队伍 capability 观察的窄投影；月变体 Rule 可以据此排他匹配，但 capability provider 不自动成为参与者。

## 7. 决议模型

`ReactionResolution` 保存规范化后的 `ReactionDecisionSequence`。序列由从 `0` 连续编号的 `ReactionDecisionStep` 组成，每一步保存：

- 被选中的候选 key；
- 精确元素变化 Effect；
- Reaction 状态变化 Effect；
- 本步骤形成的 occurrence；
- 必要的强类型状态计划意图。

普通蒸发和融化各形成一个步骤、一个 occurrence 和一个 `ElementalTransitionEffect`。无匹配反应时，序列为空；它是正常结果，不是异常。

即时剧变 occurrence 还可以冻结 `ReactionEffectGroup`。group 统一保存执行轮次、目标选择和有序 Effect；机制只声明效果，不直接执行范围查询、Damage 或 Buff。

## 8. Occurrence 与元素变化

一次成立的普通反应使用 `ReactionOccurrence` 保存：

```text
occurrence_ref
interaction_id
reaction_key
direction_key
profile_key
source_ref
subject_ref
transition
```

`ElementalTransitionEffect` 保存：

```text
aura_kind
incoming_before
incoming_consumed
incoming_remaining
aura_before
aura_consumed
aura_remaining
```

当前模型没有 `matched_component_ref`。匹配到的 Aura 类别和精确消费通过 `aura_kind` 与前后元素量表达；Aura 领域根据该 Effect 执行实际 Component 变化。

## 9. 无状态、即时 Effect 与耦合状态

普通蒸发和融化是无状态反应：

- 不创建伪 `ReactionStateRecord`；
- 不创建 Gate、资源、周期工作或反应实体；
- occurrence 提交本身不推进 Reaction Store version；
- 仍然通过 operation/interaction 身份与预期 Store version 防止重复提交和 stale plan。

无状态不等于无事务。反应成立、Aura 消费和当前伤害调整仍必须进入同一个元素交互批次。

普通超载、超导本身同样不创建长期 ReactionState，但会冻结下一 settlement round 的 Effect Group：

- 超载：范围 Damage Effect；
- 超导：共享范围的 Damage Effect 与 Status Effect；
- Damage Gate Record 属于 ReactionStore；
- 超导 Debuff 实例只属于 BuffStore。

普通冻结首次建立耦合状态：

- `FROZEN` Aura 保存冻元素量；
- `FrozenState` 保存 Link、衰减速率历史和下一必需处理帧；
- `FreezeRecoveryState` 只保存解冻后的惰性速率恢复历史，不表示目标仍处于冻结；
- Aura 与 State 的创建、刷新和移除必须经过同一跨系统 Link 预校验。

普通碎冰读取 `StrikeType.BLUNT` 与活动冻结投影，完整消费 linked 冻元素和 `FrozenState`，并冻结下一 settlement round 的物理 Damage Effect。碎冰不把物理元素加入 `Element`，也不把钝击解释为控制行为。

## 10. 非目标

本阶段基础文档不重新定义：

- Aura 附着损耗、同元素叠加和自然衰减公式；
- ICD Binding、窗口和系数序列；
- Damage 完整直伤公式；
- 月反应等尚未进入正式契约和生产验证的机制；
- 环境附着、自身附着、元素盾和特殊目标例外。

这些内容分别属于对应领域文档或后续反应专文。
