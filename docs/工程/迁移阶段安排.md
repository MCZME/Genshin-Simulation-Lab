# 迁移阶段安排

> 状态：持续维护的迁移路线图。
> 最后更新：2026-07-13。
> 本文档按并行工作流、依赖门槛和验收条件组织迁移，不再把阶段编号视为严格执行顺序。

## 1. 文档定位

本路线图回答以下问题：

- 当前有哪些迁移工作流，它们各自处于什么状态。
- 一项能力开始迁移前必须具备哪些契约、运行时基础和验证资料。
- 不同工作流之间有哪些依赖，哪些工作可以并行推进。
- 如何选择下一项足够小、可验证的迁移任务。

旧项目能力是否保留、当前覆盖到什么程度，见[旧项目能力盘点](./旧项目能力盘点.md)。具体系统的长期边界以 `架构/`、`契约/` 和[项目决策记录](../决策/项目决策记录.md)为准。

## 2. 迁移原则

- 新项目是重建，不以复制旧目录或恢复旧调用链为目标。
- 旧代码主要提供行为线索、算法参考、测试覆盖入口和已知风险。
- 所有迁移能力必须重新落入当前模块边界，并通过新契约组装。
- 数值与复杂机制必须先确认可信来源和验收方式，不能仅凭旧实现或记忆落地。
- golden case 是数值能力的进入门槛，不是项目末期统一补做的工作。
- 工作流可以并行，但单项任务不能跳过自身依赖门槛。
- 每次迁移保持小切片，完成实现、测试、文档和能力矩阵更新后再扩大范围。

## 3. 旧项目查看方式

旧项目位置：

```text
E:\project\Genshin Damage calculation
```

查看顺序：

1. 阅读当前项目对应架构、契约和实现规划，确认新边界。
2. 阅读旧项目相关文档和测试，提取行为目标、输入条件和候选预期。
3. 阅读旧代码，识别算法、隐式依赖、历史兼容逻辑和需要舍弃的耦合。
4. 把结论写入迁移任务或 golden case，不让旧代码直接成为新架构契约。

常用定位命令：

```powershell
rg --files "E:\project\Genshin Damage calculation"
rg -n "class SimulationContext|class Simulator|class GameEvent|class EventEngine|class SimulationAssembler" "E:\project\Genshin Damage calculation"
```

禁止事项：

- 不直接照搬旧测试文件。
- 不把旧 MySQL、UI、持久化或全局 registry 依赖带入 `core/`。
- 不沿用以显示名称识别资产或绑定行为的方式。
- 不把旧测试通过视为新实现数值可信的充分条件。

## 4. 历史阶段模型

项目早期曾按以下阶段规划：

```text
阶段 0：迁移准备与风险盘点
阶段 1：纯核心最小运行时
阶段 2：配置、资产与组装闭环
阶段 3：最小仿真闭环
阶段 4：结果持久化与分析闭环
阶段 5：资产构建与内容迁移
阶段 6：批量任务与参数扫描
阶段 7：UI 工作流重设计
阶段 8：数值校准、回归体系与扩展迁移
```

该模型完成了启动期的范围拆分，但不再作为当前执行顺序，原因如下：

- 资产构建、内容验证、数值系统和任务执行已经跨阶段并行推进。
- golden case 必须伴随每个数值切片建立，不能延后到最终阶段。
- UI 壳层、应用服务和任务模型可以先验证边界，完整产品工作流则可以后置。
- 同一阶段内的能力依赖差异很大，例如生命、护盾、能量不能作为一个迁移批次处理。

后续提交和文档不再使用“当前处于阶段 N”描述整体项目。需要回顾启动期历史时，可以引用上述模型。

## 6. 工作流 A：仿真运行时基础

### 6.1 目标

- 保持 `core/` 为纯仿真运行时，不依赖资产库、应用层、UI 或具体内容。
- 提供具体数值和内容机制可以安全接入的状态所有权、事件阶段和命令提交边界。
- 保证同一配置、输入和随机种子产生确定性结果。

### 6.2 当前基线

- `core/events/`：事件类型、payload、handler 与事件引擎。
- `core/simulation/`：时钟、上下文、队伍、输入会话和模拟器。
- `core/actions/`：统一 `ActionManager`、动作实例、锁和中断处理。
- `core/space/` 与 `core/entity_states/`：轻量空间实体、目标运行态和生命周期。
- `core/impacts/`：影响点、目标解析和请求分发。
- `application/assembly/`：把资产、内容贡献和核心运行时显式组装。

### 6.3 下一层门槛

实现 Buff、状态、被动、冷却、附着或持续效果前，必须先落地对应的最小机制运行时能力：

- 机制实例的稳定身份和生命周期。
- handler 只读视图与结构化命令。
- 确定性的命令校验、排序和提交阶段。
- modifier provider 与机制实例所有权的连接方式。
- 快照、事件和错误模型。

完整边界见：[游戏机制运行时架构规范](../架构/游戏机制运行时架构规范.md)。

### 6.4 完成门槛

本工作流没有一次性“全部完成”状态。每新增一种运行时能力，至少需要：

- 纯 `core/` 单元测试。
- 与组装或 content contribution 的集成测试。
- 明确的状态所有者、读取接口和唯一写入入口。
- 对事件顺序、快照和确定性的说明。

| 共鸣与地区规则 | 待拆分评估 | 不作为单个系统整体迁移 |

### 7.2 单项进入门槛

一个数值或机制系统开始编码前，必须明确：

- 输入请求、输出结果和状态所有者。
- 使用实时查询还是快照，以及快照发生时点。
- 与属性、事件、Impact、机制运行时和内容层的关系。
- 游戏规则和数值的可信来源。
- 至少一个正常案例和关键边界案例。
- 是否需要 golden case；伤害、治疗、反应、Buff 覆盖和时间轴默认需要。

### 7.3 单项完成门槛

- 纯公式或规则测试覆盖关键分支。
- 状态提交和事件顺序具有集成测试。
- 对无效请求、零值、上限、下限和缺失依赖有明确行为。
- 结果可以被快照或通用事件记录，不要求立即新增专用结果表。
- 能力盘点中的覆盖状态和剩余缺口已更新。

## 8. 工作流 C：内容迁移

### 8.1 迁移单位

内容迁移以可独立验证的纵向切片为单位，而不是以整个角色、武器目录或旧模块为单位。一个切片应包含：

```text
资产参数
-> handler_key
-> content contribution
-> Action / Impact / modifier / 机制请求
-> core 运行时结果
-> 事件、快照或 golden case 断言
```

### 8.2 选择规则

优先选择满足以下条件的内容：

- 依赖的运行时和数值系统已经存在。
- 资产参数可以从当前数据源稳定取得或由测试资产明确给出。
- 旧项目有可复核的行为入口，但不需要携带旧架构耦合。
- 能在一个小切片内形成可断言结果。

不应为了“先迁一个完整角色”而同时临时实现多个未经设计的通用系统。

### 8.3 当前状态与门槛

- runtime probe 用于验证运行时贡献和状态流转，不算真实内容覆盖。
- 芭芭拉切片已经验证角色 Action 与 Impact 接入，但不代表完整角色机制已经迁移。
- 武器和圣遗物迁移应先区分静态属性、运行时 modifier、触发机制和内容私有状态。
- 每完成一个真实内容切片，都要登记资产来源、handler、依赖系统、测试入口和未覆盖能力。

## 9. 工作流 D：资产、配置与组装

### 9.1 当前基线

- `SimulationConfig` 使用稳定 `asset_key` 和按键事实 `input_trace`。
- 资产库使用本地只读 SQLite 生成物。
- `asset_key` 标识资产，`handler_key` 绑定代码实现。
- Project Amber / Yatta 当前默认数据通过开发期源站适配层进入 raw cache 和标准 manifest。
- 资产构建经过 fetch、manifest 转换、审计、SQLite 构建和校验。
- 缺资产、缺 handler 和 JSON payload 错误在组装阶段失败。

### 9.2 后续任务门槛

- 改变 `SimulationConfig` 或资产 schema 前必须请求人工确认。
- 新增数据源、网络抓取范围或依赖库前必须请求人工确认。
- 数据转换必须记录来源字段、单位和倍率转换规则。
- 真实资产默认不能绑定测试用 NoOp handler 冒充已实现机制。

### 9.3 验收

- manifest 审计覆盖唯一键、引用、等级范围和 JSON schema。
- 临时库校验通过后才能替换正式资产库。
- 组装集成测试同时覆盖成功路径和缺资产、缺 handler、非法 payload。

## 10. 工作流 E：结果、分析与任务

### 10.1 当前基线

- `core/snapshots/` 生成与技术存储无关的快照模型。
- `infrastructure/results_sqlite/` 保存最小会话和事件数据。
- `application/execution/` 提供同步仿真执行原语。
- `application/jobs/` 和 `infrastructure/jobs/` 已验证内存与进程执行边界。
- CLI 已通过应用服务提供配置校验、运行和基础结果查询。

### 10.2 推荐依赖顺序

```text
稳定结果读取协议
-> analysis 纯加工与摘要模型
-> 批量配置变体编译
-> 任务执行与结果关联
-> 多结果汇总和比较
```

进程并行不是批量能力的首要门槛。应先保证同一配置变体在同步和任务执行路径中得到一致结果。

### 10.3 完成门槛

- `analysis/` 不直接执行 SQL，由 repository 提供稳定读取模型。
- `application/batch/` 不承担进程池或 UI 状态职责。
- 所有仿真继续保存完整结果数据，不通过减少记录内容解决批量体积问题。
- 任务失败、取消或 worker 异常必须有明确状态转换和可诊断错误。

## 11. 工作流 F：UI 产品工作流

UI 与底层能力可以并行验证边界，但完整交互必须单独确认产品方案。

当前原则：

- UI 继续使用 Flet。
- UI 只调用 `application/services/`，不直接访问 SQLite 或组装核心对象。
- 旧 UI 只用于识别用户任务，不复用页面结构和数据库直连方式。
- 配置编辑、队伍构建、输入轨迹、运行、结果摘要和画布之间的关系以[UI 工作流画布设计草案](../架构/UI工作流画布设计草案.md)继续讨论。

进入实现前需要确认：

- 第一条端到端用户工作流。
- 页面或画布的状态所有权。
- 长任务的进度、取消、失败和结果跳转方式。
- UI 需要的稳定应用服务模型。

## 12. 工作流 G：可信度与回归

可信度工作贯穿所有迁移任务，不是独立的收尾阶段。

### 12.1 测试分层

- `tests/unit/`：纯模型、算法、状态提交和错误分支。
- `tests/integration/`：组装、仓库、执行、持久化和跨模块事件流。
- `tests/golden/`：有可信输入与预期结果的机制或数值基准。

### 12.2 Golden case 最小记录

每个 golden case 至少记录：

```text
验证能力：
资料来源及适用版本：
旧项目参考：
完整输入条件：
预期输出与允许误差：
不覆盖的行为：
```

旧项目测试可以帮助发现遗漏，但预期值进入新 golden case 前必须复核。

### 12.3 持续检查

```powershell
uv run pytest
uv run pytest --cov=genshin_sim
uv run ruff check
uv run ruff format --check
uv run pyright
```

文档任务可以只执行链接、引用和差异检查；未运行代码检查时必须在交付说明中明确。

## 13. 下一项迁移任务的选择方法

不再从全局阶段编号推导下一项工作。每次从工作流中选择任务时，按以下顺序判断：

1. 是否有明确的产品、架构或内容需求。
2. 依赖的契约和运行时能力是否已经存在。
3. 是否有可信资料、旧项目参考和可执行验收方式。
4. 能否拆成一次提交可完成的小切片。
5. 是否会迫使其他未确认系统临时定型。
6. 完成后是否能提升后续多个能力的可迁移性。

优先选择依赖已满足、验证成本可控、能形成纵向闭环的任务。依赖不满足时，先迁移最小公共能力，而不是在具体内容中建立临时旁路。

## 15. 暂停并请求确认的情况

遇到以下情况应暂停实现并请求人工确认：

- 改变顶层模块职责或依赖方向。
- 改变 `SimulationConfig`、资产库 schema 或结果库核心结构。
- 引入新的外部依赖、数据源、网络抓取流程或大型工具链。
- 实现尚无可信来源或 golden case 支撑的游戏机制数值。
- 决定舍弃旧项目中仍可能有价值的完整能力。
- 删除或覆盖用户已有改动。
- 需要大范围改写且无法拆成可独立验证的小切片。

## 16. 维护规则

- 工作流状态发生实质变化时更新“当前工作流总览”。

- 已完成的实施历史优先保存在对应实现规划或提交记录中，不在本路线图累积逐提交日志。
